Как я могу использовать claude + vscode для code-review

---

Хороший вопрос — тут есть несколько разных способов в зависимости от того, ревьюишь ли ты свой код перед коммитом, чужой PR, или хочешь автоматизировать. Уточню актуальные возможности, поскольку GitHub-интеграция и команды могли измениться.Отлично, тут есть несколько разных уровней — от ручного ревью своих изменений до автоматизации на PR. Поскольку ты только начинаешь, разложу от простого к сложному.

## 1. Самый простой старт: команда `/code-review` локально

В сессии Claude Code (внутри VS Code, в панели или через CLI в терминале) есть встроенная команда. Чтобы отревьюить diff локально в терминале без установки GitHub App, запусти команду `/code-review` в любой сессии Claude Code. Она проанализирует твои незакоммиченные изменения и выведет замечания прямо в панель.

Типичный цикл выглядит так: запускаешь локальный review (вывод в терминал) через /code-review, смотришь автоматический фидбэк, вносишь нужные правки, при желании постишь как комментарий к PR через /code-review --comment, мерджишь когда готово.

Важная деталь о том, как она работает под капотом: при запуске review несколько агентов параллельно анализируют diff и окружающий код, каждый ищет свой класс проблем, затем шаг верификации проверяет кандидатов на реальное поведение кода, чтобы отфильтровать ложные срабатывания. Поэтому она довольно точная — порог уверенности по умолчанию 80, false positives отфильтровываются.

## 2. Ещё проще: просто попросить словами

Тебе не обязательно знать команды. Раз плагин в VS Code — это тот же агент, можно просто написать в панель:

> «Посмотри мои незакоммиченные изменения (`git diff`) и сделай ревью: логические ошибки, edge-кейсы, нарушения наших конвенций из CLAUDE.md. Не придирайся к стилю, который и так ловит линтер.»

Это работает, потому что агент видит твой проект и где стоит курсор. На старте это даже полезнее команд — ты учишься формулировать, _что именно_ хочешь от ревью. Можно сузить: «отревьюй только `src/auth/`», «сфокусируйся на безопасности», «проверь только на race conditions».

## 3. Настрой, что именно ревьюить — через `CLAUDE.md`

Это связка с тем, что мы обсуждали раньше. Ты можешь настроить, что Claude флагует, добавив файл CLAUDE.md или REVIEW.md в репозиторий. То есть твои конвенции и few-shot примеры из прошлого вопроса напрямую улучшают ревью: агент будет проверять код на соответствие именно твоим правилам. Поддерживай понятные CLAUDE.md файлы для лучшей проверки на соответствие.

Логика проверки правил строгая, чтобы не зашумлять: флагуются только чёткие, однозначные нарушения CLAUDE.md, где можно процитировать конкретное нарушенное правило. Если агент не уверен, что проблема реальна, он её не флагует — ложные срабатывания подрывают доверие.

## 4. Когда дорастёшь: автоматическое ревью на PR

Это уже командный уровень и требует прав администратора в организации. После того как админ включит Code Review для организации, ревью запускаются при открытии PR, на каждый push или по ручному запросу — в зависимости от настройки репозитория. Комментарий `@claude review` запускает ревью на PR в любом режиме.

Если нужно гонять в своей инфраструктуре, чтобы запускать Claude в собственной CI вместо managed-сервиса, есть варианты GitHub Actions или GitLab CI/CD.

## Практический выбор инструмента

Про сам формат работы — небольшой нюанс из опыта сообщества, который тебе пригодится. Мнения разделены: CLI даёт больше мощности и фич — полная поддержка слэш-команд, лучшая работа с несколькими репозиториями, новые фичи появляются быстрее. Расширение же считается чище по UI/UX — заметно удобнее ревьюить диффы инлайн. Популярный третий вариант — запускать Claude Code CLI прямо внутри терминала VS Code, и многие считают именно его оптимальным: инлайн-диффы расширения плюс полный набор команд CLI.

Для ревью diff'ов инлайновый просмотр расширения особенно удобен, так что для твоей задачи расширение — хороший выбор, а если упрёшься в отсутствие какой-то команды, просто открой терминал в том же VS Code и запусти там.
