## Базовый принцип: контекст + задача + ограничения

Слабый промпт описывает желание, сильный — даёт модели всё, что нужно для одного правильного ответа. Структура, которая работает почти всегда:

1. **Контекст** — что за проект, стек, зачем нужна задача
2. **Конкретная задача** — что именно сделать, в виде глагола
3. **Ограничения** — что нельзя, какие соглашения соблюдать, какой стиль кода
4. **Формат ответа** — нужен ли только diff, объяснение, тесты

Сравните:

> ❌ «Сделай функцию для парсинга дат»

> ✅ «В этом TS-проекте (строгий tsconfig, без сторонних либ для дат) добавь функцию `parseISODate(input: string): Date | null`. Возвращай `null` на невалидном вводе, не бросай исключения. Покрой edge-кейсы: пустая строка, неполная дата, таймзоны. Дай только функцию и юнит-тесты на Vitest.»

Второй промпт почти не оставляет места для «не угадал».

## Конкретные приёмы для старта

**Давайте модели читать ваш код, а не пересказывайте его.** В IDE-плагине Claude видит открытые файлы и проект. Вместо «у меня есть класс User с полями…» скажите «посмотри на `User` в `models/user.ts` и добавь метод X в том же стиле». Опора на реальный код устраняет рассинхрон.

**Просите план до кода для нетривиальных задач.** «Сначала опиши план рефакторинга в 3-5 пунктах, не пиши код, дождись моего ок». Это дёшево ловит неверное направление до того, как сгенерится 200 строк не туда.

**Показывайте примеры (few-shot).** Если у вас есть устоявшийся паттерн — обработка ошибок, формат тестов, структура эндпоинта — приложите один существующий пример и скажите «делай по образцу этого файла». Это сильнее любого описания словами.

**Просите пошаговое рассуждение для сложной логики.** Для алгоритмов, багов, конкурентности: «разбери по шагам, прежде чем писать решение». Это заметно повышает корректность.

**Используйте отрицательные примеры.** «Не используй `any`», «не добавляй комментарии к очевидному коду», «не меняй публичный API» — явные запреты экономят итерации.

## Рабочий цикл, который стоит выработать

Хорошая постановка задачи — это не один идеальный промпт, а короткий диалог: задача → план → уточнение → код → ревью результата → правки. На старте полезно сознательно не пытаться получить всё с первого раза, а вести модель шагами. Когда ответ ушёл не туда — не переписывайте промпт с нуля, а скажите, что именно не так («тесты не покрывают таймзоны», «слишком сложно, упрости»).
