Слэш-команды — это твой инструмент для устранения «prompt drift»: когда ты раз за разом печатаешь одно и то же. Разложу подробно.

## Базовая механика

В сути всё предельно просто: кастомные слэш-команды — это markdown-файлы с инструкциями для Claude Code. Когда ты вызываешь команду, её содержимое становится промптом, отправляемым Claude. То есть ты «зашиваешь» удачный промпт в файл и вызываешь его одним словом.

**Куда класть файлы** (та же логика, что у skills и CLAUDE.md):

Проектные команды: `.claude/commands/` (шарятся через git, специфичны для проекта). Личные команды: `~/.claude/commands/` (доступны во всех проектах).

Имя файла становится именем команды: commit.md становится /commit. Создать можно буквально одной строкой:

```bash
mkdir -p .claude/commands
echo "Проанализируй этот код на проблемы производительности:" > .claude/commands/optimize.md
```

И всё — теперь `/optimize` работает. Команды появляются в автодополнении, когда ты печатаешь /.

## Аргументы: делаем команды гибкими

Самое полезное — команды могут принимать ввод. Плейсхолдер $ARGUMENTS позволяет указать, куда именно подставить ввод. Когда ты включаешь $ARGUMENTS в файл команды, Claude заменяет его тем текстом, что ты напечатал после имени команды.

Например, файл с текстом `Review the file $ARGUMENTS`, вызванный как `/review-colors penguin_scatter.py`, превращается для Claude в `Review the file penguin_scatter.py`.

Есть и **позиционные аргументы**, если нужно несколько разных: `Fix issue #$1 with priority $2` — вызов `/fix-issue 123 high` разворачивается в «Fix issue #123 with priority high». При этом $ARGUMENTS захватывает всё целиком: тот же вызов даёт $ARGUMENTS = "123 high".

## Внедрение живых данных из терминала (очень мощно)

Это то, что делает команды по-настоящему полезными для разработки. Можно подставить вывод bash-команды прямо в промпт. Через `!` можно инжектить живые данные из терминала прямо в промпт. Например, `!git diff --cached` автоматически подтянет твои staged-изменения.

Чтобы это сработало, нужно указать allowed-tools во frontmatter — тогда можно выполнять bash-команды и встраивать их вывод в промпт. Префикс `!` запускает команду.

Вот канонический пример — команда `/commit`, которая сама пишет осмысленное сообщение коммита:

```markdown
---
description: Create a git commit with a conventional message
allowed-tools: Bash(git add:*), Bash(git commit:*)
argument-hint: [message]
model: haiku
---
# Commit Changes
<git_diff>
!`git diff --cached`
</git_diff>

Create a commit message following Conventional Commits.
If $ARGUMENTS is provided, use it as the commit message.
```

Тут команда сама забирает diff из staged-области, анализирует его и пишет сообщение. Это пример из реального workflow, где автор заменил ручные git-ритуалы кастомными командами: /commit пишет сообщение, /branch "add dark mode" создаёт feat/add-dark-mode, /pr генерирует полное описание PR из коммитов.

## Frontmatter: настройки команды

YAML-блок в начале файла. Frontmatter полностью опционален — без него команда всё равно работает, Claude просто получит доступ ко всем инструментам по умолчанию, и команды не будет в меню. Но frontmatter делает команды более заметными и предсказуемыми.

Поля, которые реально используются:

**`description`** — одна строка, показываемая в пикере слэш-команд. Если пропустить, пикер покажет первую строку тела, что редко то, что нужно.

**`allowed-tools`** — ограничивает инструменты. Тут важна гранулярность для безопасности: `Bash(git:*)` разрешает любую git-подкоманду; `Bash(git status)` разрешает только эту точную команду. Для ревью-команды полезно ограничить её только чтением файлов без внесения изменений.

**`argument-hint`** — placeholder-текст в поле ввода. Чисто косметический, но подсказывает, какой формат ввода ждёт команда.

**`model`** — переопределяет модель сессии для этой команды. Полезно, чтобы направлять дешёвые механические команды на Haiku, оставляя Opus для тяжёлой работы. Для «починить точку с запятой» мощная модель не нужна — `model: haiku` и команда выполняется почти мгновенно.

Из двух полей, которые стабильно окупаются: description (чтобы команду в команде читали в пикере) и allowed-tools (чтобы команда не спрашивала разрешение каждый запуск).

## Организация: неймспейсы

Когда команд станет много, их можно структурировать папками. Можно организовывать команды в подкаталоги. Например, файл `.claude/commands/frontend/component.md` создаёт команду `/frontend:component`.

## Слэш-команды vs skills — когда что

Раз ты только что спрашивал про skills, важно не путать. Разница простая:

Слэш-команда — это **действие, которое ты запускаешь вручную**, напечатав `/имя`. Skill — это **знание, которое агент подтягивает сам**, когда видит подходящую задачу. Команды для того, что ты хочешь дёргать осознанно (закоммить, открой PR, прогони ревью); skills для контекста, который должен применяться автоматически (как у нас пишутся тесты).

Любопытная деталь: в актуальной документации механизмы сблизились. И ты, и Claude можете передавать аргументы; они доступны через $ARGUMENTS. Чтобы команда не вызывалась моделью автоматически, ставится `disable-model-invocation: true` во frontmatter. То есть граница между ними стала тоньше, но ментальная модель «ручное действие vs авто-знание» по-прежнему рабочая.

## С чего начать тебе

Практичный первый набор для разработчика — три git-команды, которые экономят время каждый день: `/commit` (пример выше), `/pr` (описание PR из коммитов) и `/review` (ревью staged-изменений с `allowed-tools`, ограниченными чтением). Они дадут максимальный эффект при минимальных усилиях, и на них ты освоишь и `$ARGUMENTS`, и `!`-инъекцию, и frontmatter.

Официальная документация по слэш-командам со всеми полями frontmatter и edge-кейсами: https://code.claude.com/docs/en/slash-commands
