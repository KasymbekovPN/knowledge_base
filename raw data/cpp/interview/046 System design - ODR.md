# ODR (One Definition Rule)

## Формулировка

Три правила, образующие ODR:

1. **В пределах одной translation unit** — не более одного определения любой сущности (переменной, функции, класса, типа, шаблона).
    
2. **Во всей программе** — ровно **одно** определение для каждой не-inline функции и глобальной переменной, которые _используются_ (odr-used).
    
3. **Для сущностей, допускающих множественные определения** (inline-функции, классы, шаблоны, inline-переменные) — определения в разных TU должны быть **идентичны** (token-за-token, с одинаковым значением имён). Иначе — **UB**.
    

Нарушение → либо ошибка линковки (`multiple definition`), либо — что хуже — **тихий UB** (правило 3).

---

## Declaration vs Definition — фундамент

ODR оперирует определениями, поэтому надо чётко различать (мы касались в header/cpp):

**Объявлений** может быть сколько угодно:

```cpp
void f(int);              // объявление — можно повторять
extern int x;             // объявление переменной
class Widget;             // объявление класса (forward)
```

**Определение** — одно (per правила выше):

```cpp
void f(int x) { }         // определение функции
int x = 5;                // определение переменной
class Widget { int a; };  // определение класса
```

Граница: определение функции — с телом; определение переменной — выделяет память/инициализирует; определение класса — с телом `{}`.

---

## Правило 1: одна TU

```cpp
// один .cpp:
int x;
int x;              // ⚠️ ошибка: redefinition of 'x'

void f() { }
void f() { }        // ⚠️ ошибка: redefinition of 'f'

class W { };
class W { };        // ⚠️ ошибка: redefinition of 'W'
```

Компилятор ловит это сразу — в пределах одной TU повтор определения запрещён.

**Отсюда — include guards.** Заголовок с определением класса, включённый дважды в одну TU (транзитивно), даёт двойное определение:

```cpp
// widget.h без guard
class Widget { };

// main.cpp
#include "a.h"    // тянет widget.h
#include "b.h"    // тянет widget.h СНОВА
// → class Widget определён дважды в одной TU → ошибка
```

Guard (`#pragma once` / `#ifndef`) гарантирует однократное включение → правило 1 не нарушается.

---

## Правило 2: одна программа

Не-inline функции и глобальные переменные должны иметь **ровно одно** определение среди всех TU.

### Слишком много определений

```cpp
// util.h
int add(int a, int b) { return a + b; }   // ⚠️ ОПРЕДЕЛЕНИЕ в заголовке

// a.cpp: #include "util.h"  → определение add в a.o
// b.cpp: #include "util.h"  → определение add в b.o
// линкер: ⚠️ multiple definition of `add(int, int)'
```

Заголовок копируется в каждую включающую TU → определение дублируется. Это классическая причина `multiple definition` (разбирали в линковке).

**Решение** — объявление в .h, определение в одном .cpp:

```cpp
// util.h
int add(int a, int b);                    // объявление

// util.cpp
int add(int a, int b) { return a + b; }   // единственное определение
```

### Слишком мало определений

```cpp
void helper();            // объявлен
void foo() { helper(); }  // используется, но нигде не определён
// линкер: ⚠️ undefined reference to `helper()'
```

Ноль определений при использовании → `undefined reference` (тоже нарушение ODR — «ровно одно» нарушено в меньшую сторону).

### odr-used — тонкость «используется»

Определение требуется только если сущность **odr-used** — реально используется способом, требующим её наличия (вызов, взятие адреса, привязка к ссылке). Просто упоминание в невычисляемом контексте (`sizeof`, `decltype`) — **не** odr-use:

```cpp
extern int x;
sizeof(x);        // НЕ odr-use — определение x не требуется
int y = x;        // odr-use — x должен быть определён где-то
```

Тонкий случай — static constexpr член:

```cpp
struct S {
    static constexpr int N = 10;   // объявление+инициализатор
};
int arr[S::N];        // НЕ odr-use (значение известно compile-time) → OK без определения
const int* p = &S::N; // odr-use (берём адрес!) → нужно определение:
                       // до C++17: constexpr int S::N; в .cpp
                       // C++17: static constexpr неявно inline → определение не нужно
```

## Правило 3: идентичность определений — самое коварное

Сущности, которые **разрешено** определять в нескольких TU (потому что они попадают в заголовки), должны иметь **идентичные** определения. Иначе — **UB**, и линкер обычно **молчит**.

Что попадает под правило 3 (определяется в заголовках → в нескольких TU):

- классы/структуры
- inline-функции
- шаблоны
- inline-переменные (C++17)
- enum
- constexpr функции

### Почему нарушение тихое

Линкер видит несколько определений inline-функции и выбирает **любое одно** (обычно первое встреченное), молча отбрасывая остальные. Если они **различаются** — ты получаешь непредсказуемое поведение.

### Классический пример: разный класс в разных TU

```cpp
// a.cpp
struct Widget {
    int x;
    int y;
};
void useA() { Widget w; /* sizeof == 8 */ }

// b.cpp
struct Widget {        // ⚠️ ДРУГОЕ определение того же имени!
    int x;
    int y;
    int z;             // добавлено поле
};
void useB() { Widget w; /* sizeof == 12 */ }
```

Оба компилируются (каждая TU видит своё определение). Линкер **не проверяет** идентичность → **UB**: один и тот же тип `Widget` имеет разный размер/layout в разных TU. Если объект `Widget` передаётся между `useA` и `useB` — порча памяти.

Это тихий, крайне трудноуловимый баг. Часто возникает при:

- разных версиях одного заголовка (забыли пересобрать)
- **макросах**, меняющих определение:

```cpp
// a.cpp
#define FEATURE
#include "widget.h"    // Widget с полем (внутри #ifdef FEATURE)

// b.cpp
// (без #define FEATURE)
#include "widget.h"    // Widget БЕЗ поля
// → разные определения Widget → ODR violation, UB
```

Условная компиляция + заголовки с классами = мина замедленного действия.

### Пример: разные inline-функции

```cpp
// a.cpp
inline int getVersion() { return 1; }

// b.cpp
inline int getVersion() { return 2; }   // ⚠️ то же имя, ДРУГОЕ тело

// линкер выберет ОДНО (например, версию 1) для ОБОИХ вызовов
// → getVersion() в b.cpp вернёт 1, хотя написано 2 → UB
```

## Что МОЖНО определять в нескольких TU (исключения)

Сущности, которые ODR разрешает определять многократно (при идентичности):

```cpp
// 1. inline-функции
inline int f() { return 42; }

// 2. Методы, определённые ВНУТРИ класса (неявно inline)
class W { void g() { } };   // g неявно inline

// 3. Шаблоны (обязаны быть в заголовке — мономорфизация)
template<class T> T max(T a, T b) { return a > b ? a : b; }

// 4. Определение класса/структуры/enum
struct Point { int x, y; };

// 5. constexpr функции (неявно inline)
constexpr int square(int x) { return x * x; }

// 6. inline-переменные (C++17)
inline int globalCounter = 0;        // ✅ одна на программу, но определяется в заголовке

// 7. static constexpr члены (C++17 — неявно inline)
struct S { static constexpr int N = 10; };
```

Все они попадают в заголовки, включаются в множество TU → ODR **обязан** разрешить множественные определения, требуя лишь идентичности.

`inline` здесь = «разрешаю несколько идентичных определений, линкер выберет одно» (не «встрой меня» — мы это отмечали).

## inline-переменные (C++17) — решение старой проблемы

До C++17 глобальную переменную в header-only библиотеке определить было сложно:

```cpp
// ❌ до C++17
// config.h
int globalConfig = 0;   // ⚠️ определение в заголовке → multiple definition

// приходилось: объявление в .h + определение в одном .cpp (неудобно для header-only)
```

```cpp
// ✅ C++17
// config.h
inline int globalConfig = 0;   // ✅ inline-переменная — одна на программу,
                                //    определяется прямо в заголовке
```

`inline` для переменной работает как для функции: множественные определения допустимы, линкер сводит в одну. Спасение для header-only библиотек и глобального состояния в заголовках.

## Anonymous namespace / static — обход ODR через internal linkage

Иногда нужно **своё** определение в каждой TU (не разделяемое). Тогда — internal linkage:

```cpp
// helper.h
namespace {
    int helper() { return 42; }   // ✅ КАЖДАЯ TU получает СВОЮ копию
}                                  //    ODR не нарушается — это РАЗНЫЕ сущности

// или:
static int counter = 0;           // internal linkage — своя в каждой TU
```

**Важное различие:**

- `inline int x = 0;` — **одна** переменная на программу (external linkage, ODR сводит в одну)
- `static int x = 0;` в заголовке — **отдельная** переменная в каждой TU (internal linkage, N копий)

```cpp
// header.h
static int counter = 0;    // ⚠️ ОТДЕЛЬНЫЙ counter в КАЖДОМ .cpp!

// a.cpp: ++counter;   → своя копия
// b.cpp: ++counter;   → ДРУГАЯ копия
// значения не разделяются — частый баг «почему счётчик не растёт»
```

Anonymous namespace / static в заголовке — обычно **ошибка** (дублирование, раздувание кода), кроме случаев, когда именно нужна TU-локальная сущность.

## Обнаружение нарушений ODR

Правило 3 (разные определения) — **не ловится** линкером штатно. Инструменты:

```bash
# GNU gold linker — частичная проверка ODR
g++ -fuse-ld=gold -Wl,--detect-odr-violations

# LTO — часто выявляет несовпадения (видит весь код)
g++ -flto ...

# ASan имеет ODR-детектор для глобальных переменных
g++ -fsanitize=address    # ловит ODR violation для global vars с разным размером
```

Но полной защиты нет. Практика:

- **Единый source of truth** для каждого заголовка (не копировать)
- Осторожность с макросами/`#ifdef`, меняющими layout
- Единые флаги компиляции для всех TU (разбирали GCC dual ABI — это тоже вид ODR-нарушения)
- Модули C++20 (см. ниже) устраняют многие ODR-проблемы by design

---

## C++20 modules — устранение ODR-проблем

Модули (`import`, `export module`) заменяют текстовое включение заголовков:

```cpp
// widget.cppm (module interface)
export module widget;
export class Widget { /* ... */ };
```

```cpp
// main.cpp
import widget;   // ✅ не текстовое включение — импорт скомпилированного интерфейса
```

Преимущества относительно ODR:

- Нет препроцессорного копирования → нет случайного дублирования определений
- Макросы не «протекают» в модуль → нет ODR-нарушений через `#ifdef`
- Определения не пересобираются в каждой TU → быстрее компиляция
- Внутренние детали модуля не видны импортёрам → меньше зависимостей

Модули — стратегическое решение ODR-хрупкости, но внедрение медленное (поддержка компиляторов/сборки ещё дозревает на 2026).

## Формулировки на собеседовании

**«Что такое ODR?»** — One Definition Rule: (1) в одной TU — не более одного определения; (2) во всей программе — ровно одно определение для каждой odr-used не-inline функции/переменной; (3) для сущностей, определяемых в нескольких TU (inline, шаблоны, классы), определения должны быть **идентичны**, иначе UB.

**«Почему определение функции в заголовке даёт multiple definition?»** — Заголовок копируется препроцессором в каждую включающую TU → определение дублируется → нарушение правила 2. Решение: объявление в .h + определение в одном .cpp, либо `inline`.

**«Какие сущности можно определять в нескольких TU?»** — Классы, inline-функции, шаблоны, constexpr-функции, enum, inline-переменные (C++17), методы внутри класса. Все они попадают в заголовки; ODR требует лишь их идентичности.

**«Самое опасное нарушение ODR?»** — Правило 3: разные определения одной сущности (класса, inline-функции) в разных TU. Линкер молча выбирает одно → **UB**, не диагностируется. Частая причина — макросы/`#ifdef`, меняющие layout класса, или рассинхронизированные версии заголовка.

**«Разница `inline int x` и `static int x` в заголовке?»** — `inline` (C++17) — **одна** переменная на программу (external linkage, ODR сводит). `static` — **отдельная** копия в каждой TU (internal linkage). Static в заголовке часто баг (N несвязанных копий).

**«Что такое odr-used?»** — Использование, требующее определения: вызов, взятие адреса, привязка к ссылке. Упоминание в `sizeof`/`decltype` — не odr-use, определение не требуется.

**«Как модули C++20 помогают с ODR?»** — Заменяют текстовое включение импортом скомпилированного интерфейса: нет препроцессорного дублирования, макросы не протекают → ODR-нарушения через заголовки/`#ifdef` исключены by design.

---

Отличие от Java: там ODR-проблем **нет** — концепция отсутствует, потому что нет препроцессора, текстового включения и раздельной модели компиляции с заголовками. Каждый класс определён в **одном** `.java` файле, компилируется в один `.class`; дублирования определения быть не может by construction. Если два класса с одинаковым полным именем оказываются в classpath — JVM берёт **первый найденный** ClassLoader'ом (аналог «линкер выбирает одно»), но это разрешение имён в рантайме, а не ODR-violation с UB — поведение определено (хоть и может удивить). Нет «идентичности определений в разных TU», потому что нет разных TU для одного класса. По сути, Java-модель (один класс = один файл = один `.class`, динамическая загрузка по имени) **устраняет весь класс ODR-проблем**, которые в C++ порождены текстовым включением заголовков. C++20 modules — движение в ту же сторону: сделать единицей не текст-заголовок, а скомпилированный интерфейс, как `.class` в Java. Для тебя практический вывод: ODR — специфически C++ головная боль от препроцессорной модели; главные защиты — include guards (правило 1), объявление/определение split (правило 2), и дисциплина с макросами + единые флаги сборки (правило 3, самое коварное).
