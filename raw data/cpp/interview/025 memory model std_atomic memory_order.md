# Memory model, `std::atomic`, memory_order

Самая глубокая тема в C++ concurrency. На собеседовании обычно достаточно уверенно владеть `seq_cst`, `relaxed` и парой `acquire`/`release` — но понимать, **зачем** они нужны.

## Проблема: код не выполняется так, как написан

Три уровня переупорядочивания:

**1. Компилятор** переставляет инструкции при оптимизации:

```cpp
a = 1;
b = 2;   // компилятор может поменять местами — для одного потока результат тот же
```

**2. Процессор** выполняет out-of-order, спекулятивно:

- Store buffer: запись сначала попадает в буфер, а не в кэш → другие ядра увидят её позже
- Load может выполниться раньше предшествующего store (x86 разрешает StoreLoad reordering)

**3. Кэш-когерентность** — обновления распространяются между ядрами не мгновенно.

**Ключевой принцип: as-if rule.** Компилятор/процессор вправе делать что угодно, если **однопоточное** наблюдаемое поведение не изменилось. Про другие потоки они ничего не знают — если ты не сказал явно.

### Классическая демонстрация

```cpp
// Начально: x = 0, y = 0
// Поток 1:          Поток 2:
x = 1;               y = 1;
r1 = y;              r2 = x;

// Интуитивно: r1==0 && r2==0 невозможно (кто-то же записал первым)
// Реально на x86: ⚠️ ВОЗМОЖНО! оба ядра держат store в своём store buffer,
//                  а load читает из кэша старое значение
```

Это **StoreLoad reordering** — единственное, что переставляет даже x86 (относительно сильная модель). ARM/POWER переставляют гораздо больше.

## Data race — UB, а не «неверное значение»

```cpp
int x = 0;
// Поток 1: x = 1;
// Поток 2: std::cout << x;   // ⚠️ DATA RACE → UB
```

**Определение:** два потока обращаются к одной ячейке памяти, хотя бы один пишет, и между ними нет отношения **happens-before** → **UB**.

UB значит не «прочитаешь мусор», а **компилятор вправе предположить, что этого не бывает**, и оптимизировать соответственно:

```cpp
bool done = false;   // обычный bool, без синхронизации

void worker() { while (!done) { } }   // ⚠️ компилятор видит: done в цикле не меняется
                                       //    → выносит проверку из цикла
                                       //    → if (!done) while(true) {}  ← БЕСКОНЕЧНЫЙ ЦИКЛ
void stop() { done = true; }
```

Именно поэтому нужен `std::atomic<bool>` — он **запрещает** такие оптимизации.

## `std::atomic` — что даёт

Три гарантии:

1. **Атомарность** — операция неделима, нет промежуточных состояний
2. **Отсутствие data race** — атомарные обращения корректны без мьютекса
3. **Барьеры памяти** — упорядочивание относительно **других** обращений к памяти (задаётся через `memory_order`)

```cpp
#include <atomic>

std::atomic<int> counter{0};

counter++;                        // атомарный инкремент (RMW-операция)
counter.fetch_add(1);             // то же явно
counter.store(5);
int x = counter.load();
counter.exchange(10);             // атомарно записать и вернуть старое

// Compare-and-swap:
int expected = 5;
counter.compare_exchange_strong(expected, 10);
// если counter == expected → записать 10, вернуть true
// иначе → expected = текущее значение counter, вернуть false
```

### `is_lock_free`

```cpp
std::atomic<int> a;
a.is_lock_free();                  // рантайм-проверка
std::atomic<int>::is_always_lock_free;   // constexpr (C++17)
```

Атомики на типах, которые не влезают в машинное слово (или не имеют нужных инструкций), реализуются **через скрытый мьютекс** — тогда `is_lock_free() == false`, и вся выгода теряется.

```cpp
struct Big { int a[10]; };
std::atomic<Big> ab;   // ⚠️ почти наверняка НЕ lock-free — внутри мьютекс
```

Требования к `T` в `std::atomic<T>`: trivially copyable, copy-constructible, copy-assignable.

## Что такое happens-before

Фундаментальное отношение: если операция A **happens-before** B, то эффекты A **гарантированно видны** в B.

Источники happens-before:

1. **Sequenced-before** внутри одного потока (порядок выполнения)
2. **Synchronizes-with** между потоками — вот его и создают атомарные операции с правильным memory_order (или мьютексы, `join()`, и т.п.)

Data race = конкурентный доступ **без** happens-before между ними.

## `memory_order` — шесть значений

```cpp
memory_order_relaxed
memory_order_consume    // фактически deprecated, никто не реализует правильно
memory_order_acquire
memory_order_release
memory_order_acq_rel
memory_order_seq_cst    // ← ДЕФОЛТ
```

### `seq_cst` — sequential consistency (дефолт)

Самый строгий и **самый простой для рассуждений**: существует **единый глобальный порядок** всех seq_cst операций, который видят все потоки одинаково.

```cpp
std::atomic<int> x{0}, y{0};
int r1, r2;

// Поток 1:            Поток 2:
x.store(1);            y.store(1);
r1 = y.load();         r2 = x.load();
// с seq_cst: r1==0 && r2==0 НЕВОЗМОЖНО ✅
// (кто-то из store должен быть первым в глобальном порядке)
```

**Цена:** на x86 — `MFENCE` или `XCHG` на store (дорогая инструкция, десятки тактов). На ARM — полные барьеры. Это самый дорогой порядок.

**Правило: начинай с `seq_cst`. Ослабляй только после профилирования** и с полным пониманием.

### `relaxed` — только атомарность, без упорядочивания

Гарантирует **только** атомарность операции и отсутствие data race. **Никаких** гарантий о порядке относительно других обращений к памяти.

```cpp
std::atomic<int> counter{0};
counter.fetch_add(1, std::memory_order_relaxed);   // ✅ идеально для счётчика
```

**Когда уместен:** счётчики, статистика, метрики — где важно только итоговое значение, а порядок относительно других данных не важен.

```cpp
// ⚠️ НЕЛЬЗЯ использовать relaxed для передачи данных:
data = 42;                                    // обычная запись
ready.store(true, std::memory_order_relaxed); // ⚠️ может «обогнать» запись data!

// Другой поток:
if (ready.load(std::memory_order_relaxed))
    use(data);   // ⚠️ может увидеть ready==true, но data ещё 0!
```

Единственная гарантия relaxed: **modification order** каждой отдельной атомарной переменной согласован (все потоки видят изменения одной переменной в одном порядке). Но **между разными** переменными — никаких гарантий.

### `acquire` / `release` — синхронизирующая пара

Основной рабочий инструмент lock-free программирования.

- **`release`** (на store): все записи, сделанные **до** него в этом потоке, становятся видимы потоку, который сделает `acquire`-чтение этой переменной. Ничто не может быть переупорядочено **вниз** через release-store.
    
- **`acquire`** (на load): все чтения/записи **после** него не могут быть переупорядочены **вверх** через acquire-load. Если acquire прочитал значение, записанное release-store, то все записи до release видны.
    

```cpp
std::atomic<bool> ready{false};
int data = 0;                     // обычная переменная!

// Producer:
void producer() {
    data = 42;                                        // (1) обычная запись
    ready.store(true, std::memory_order_release);     // (2) release — «публикуем»
    // (1) НЕ может уехать ниже (2)
}

// Consumer:
void consumer() {
    while (!ready.load(std::memory_order_acquire)) { } // (3) acquire — «получаем»
    assert(data == 42);                                // ✅ ГАРАНТИРОВАНО!
    // (4) НЕ может уехать выше (3)
}
```

**Механика:** release-store (2) _synchronizes-with_ acquire-load (3), который прочитал записанное им значение. Это создаёт happens-before: (1) happens-before (4). Поэтому `data == 42` гарантировано **несмотря на то, что `data` — обычная неатомарная переменная**.

Это ключевая идея: **одна** атомарная переменная синхронизирует **все** обычные данные, записанные до release.

**Цена:** на **x86 acquire/release практически бесплатны** — процессор и так не переставляет loads с loads, stores с stores; нужен только барьер для компилятора. На ARM/POWER — требуются реальные инструкции барьеров (`dmb ish` и т.п.), но всё равно дешевле seq_cst.

### `acq_rel` — для RMW-операций

Read-Modify-Write операции (`fetch_add`, `exchange`, `compare_exchange`) читают **и** пишут → нужны обе гарантии:

```cpp
counter.fetch_sub(1, std::memory_order_acq_rel);
```

Классический пример — счётчик ссылок `shared_ptr`:

```cpp
// Инкремент — relaxed достаточно: мы уже держим объект, порядок не важен
ref_count.fetch_add(1, std::memory_order_relaxed);

// Декремент — нужен acq_rel (или release + acquire fence):
if (ref_count.fetch_sub(1, std::memory_order_acq_rel) == 1) {
    delete ptr;   // ✅ все записи других потоков в объект видны ДО удаления
}
```

Именно так реализованы счётчики в `shared_ptr` — инкремент relaxed (дёшево), декремент с синхронизацией (иначе деструктор мог бы не увидеть чужие изменения).

## Compare-and-swap (CAS) — основа lock-free

```cpp
bool compare_exchange_strong(T& expected, T desired,
                             memory_order success, memory_order failure);
bool compare_exchange_weak(T& expected, T desired, ...);
```

Семантика: **атомарно** — если текущее значение == `expected`, записать `desired` и вернуть `true`; иначе записать текущее значение в `expected` и вернуть `false`.

### `weak` vs `strong`

**`weak` может «провалиться ложно»** (spurious failure) — вернуть `false`, даже если значения совпадали. Причина: на некоторых архитектурах (ARM, POWER) CAS реализуется через LL/SC (load-linked / store-conditional), который может провалиться из-за постороннего события (прерывание, промах кэша).

**`weak` быстрее** (не нужен внутренний retry-цикл). Правило:

```cpp
// weak — в ЦИКЛЕ (retry всё равно есть, ложный провал не страшен):
int expected = counter.load();
while (!counter.compare_exchange_weak(expected, expected + 1)) {
    // expected обновлён текущим значением автоматически — просто повторяем
}

// strong — вне цикла (когда retry не нужен):
if (counter.compare_exchange_strong(expected, 0)) {
    // сработало ровно если было expected
}
```

### Типичный CAS-цикл (lock-free инкремент)

```cpp
std::atomic<int> value{0};

void atomic_multiply(int factor) {
    int old = value.load(std::memory_order_relaxed);
    while (!value.compare_exchange_weak(old, old * factor,
                                        std::memory_order_release,
                                        std::memory_order_relaxed)) {
        // old автоматически обновлён — повторяем с новым значением
    }
}
```

Это основа всех lock-free структур данных: читаем → вычисляем новое → пытаемся записать, если никто не влез → повторяем.

## ABA-проблема

Классическая ловушка lock-free программирования, которую любят спрашивать.

CAS проверяет **значение**, а не «было ли изменение». Если значение изменилось `A → B → A`, CAS этого **не заметит**:

```
Поток 1: читает head = A (планирует CAS: A → A->next)
Поток 2: pop A, pop B, push A обратно (но A->next теперь другой!)
Поток 1: CAS(head, A, A->next) → УСПЕХ (значение всё ещё A)
         но A->next указывает на УЖЕ УДАЛЁННЫЙ узел ⚠️
```

**Решения:**

- **Tagged pointers** — упаковать счётчик версии рядом с указателем; CAS на 128-битном (`std::atomic<struct{ptr; counter;}>` + DWCAS)
- **Hazard pointers** — отмечать узлы, которые «в использовании», не переиспользовать их
- **Epoch-based reclamation** / RCU
- Просто не переиспользовать память (не всегда возможно)

Одна из причин, почему **lock-free структуры данных писать очень сложно** — и почему на практике почти всегда лучше взять готовую библиотеку (`folly`, `boost::lockfree`) или обычный мьютекс.

## Практический паттерн: publish/consume

Самое частое реальное применение acquire/release:

```cpp
struct Config { int a, b, c; };

std::atomic<Config*> config{nullptr};

// Publisher
void publish() {
    Config* c = new Config{1, 2, 3};                  // (1) заполняем
    config.store(c, std::memory_order_release);       // (2) публикуем
    // все записи (1) видны любому, кто сделает acquire-load
}

// Consumer
void consume() {
    Config* c = config.load(std::memory_order_acquire);
    if (c) {
        use(c->a, c->b, c->c);   // ✅ гарантированно видим {1,2,3}, а не мусор
    }
}
```

Без release/acquire (с relaxed) consumer мог бы увидеть **ненулевой указатель**, но **неинициализированные поля** — классический баг double-checked locking, из-за которого паттерн долго считался сломанным.

## `std::atomic_flag` и спинлок

`atomic_flag` — единственный тип, **гарантированно** lock-free на всех платформах.

```cpp
class SpinLock {
    std::atomic_flag flag_ = ATOMIC_FLAG_INIT;
public:
    void lock() {
        while (flag_.test_and_set(std::memory_order_acquire)) {
            // ⚠️ желательно добавить паузу: std::this_thread::yield() или _mm_pause()
        }
    }
    void unlock() {
        flag_.clear(std::memory_order_release);
    }
};
```

`acquire` на lock, `release` на unlock — ровно та пара, что создаёт happens-before для защищённых данных (**то же, что делает мьютекс**).

**Когда спинлок:** критическая секция **очень** короткая (несколько инструкций) и контенция низкая. Иначе мьютекс лучше — он усыпляет поток вместо сжигания CPU. Наивный спинлок без паузы вредит гипертредингу и жжёт энергию.

## Что даёт мьютекс (связь с предыдущей темой)

`mutex::lock()` — **acquire**, `mutex::unlock()` — **release**. Именно поэтому мьютекс не только предотвращает одновременный доступ, но и **гарантирует видимость** изменений:

```cpp
// Поток 1:
{
    std::lock_guard lock(mtx);
    data = 42;              // защищено
}                           // unlock = release

// Поток 2:
{
    std::lock_guard lock(mtx);   // lock = acquire → synchronizes-with предыдущим unlock
    use(data);                    // ✅ видим 42
}
```

Мьютекс — это acquire/release пара с эксклюзивностью. Атомики позволяют получить только упорядочивание, без взаимного исключения.

## Практические рекомендации

**Иерархия предпочтений:**

1. **Мьютекс** — по умолчанию. Просто, корректно, достаточно быстро.
2. **`std::atomic` с `seq_cst`** — если мьютекс слишком дорог, но нужна простая переменная (флаг, счётчик).
3. **`relaxed`** — счётчики/метрики, где порядок не важен.
4. **`acquire`/`release`** — когда нужна публикация данных и профилировщик показал, что seq_cst дорог.
5. **Lock-free структуры** — только если ты **точно** знаешь, что делаешь, и есть измеренная необходимость.

**Реальность:** большинству кода хватает мьютексов. Lock-free — узкая ниша (высоконагруженные системы, ядра, аллокаторы), где ошибки крайне трудноуловимы (проявляются раз в миллион запусков на конкретной архитектуре).

**Инструменты:** TSan (`-fsanitize=thread`) ловит data races в рантайме — обязателен для многопоточного кода.

## Формулировки на собеседовании

**«Что такое data race?»** — Два потока обращаются к одной памяти, хотя бы один пишет, и между ними нет отношения happens-before → **UB** (не «неверное значение» — компилятор вправе оптимизировать, предполагая, что гонок нет).

**«Что даёт `std::atomic`?»** — Атомарность операции, отсутствие data race, и (в зависимости от `memory_order`) барьеры памяти, упорядочивающие **другие** обращения к памяти относительно атомарной операции.

**«Что такое `memory_order_seq_cst`?»** — Существует единый глобальный порядок всех seq_cst операций, одинаково видимый всем потокам. Самый строгий, дефолтный, самый простой для рассуждений и самый дорогой.

**«Объясни acquire/release.»** — Release-store: все записи **до** него не могут переехать ниже; они становятся видимы потоку, сделавшему acquire-load этой переменной. Acquire-load: обращения **после** не могут переехать выше. Пара создаёт **happens-before** → одна атомарная переменная синхронизирует все обычные данные, записанные до release.

**«Когда `relaxed` уместен?»** — Счётчики и метрики: важно только итоговое значение, порядок относительно других данных не важен. **Нельзя** для публикации данных (флаг может «обогнать» запись данных).

**«`compare_exchange_weak` vs `strong`?»** — `weak` может ложно провалиться (spurious failure — следствие LL/SC на ARM/POWER), но быстрее. Используй `weak` в цикле (retry всё равно есть), `strong` — вне цикла.

**«Что такое ABA-проблема?»** — CAS проверяет **значение**, а не факт изменения. Если значение сменилось A→B→A, CAS «успешно» сработает, хотя структура изменилась (например, узел удалён и переиспользован). Решения: tagged pointers (счётчик версии), hazard pointers, epoch-based reclamation.

**«Почему мьютекс гарантирует видимость данных?»** — `lock()` — acquire, `unlock()` — release. Эта пара создаёт happens-before между критическими секциями разных потоков.

---

Отличие от Java: там модель памяти (JMM) устроена **похоже** — `volatile` в Java ≈ `atomic` с `seq_cst` в C++ (обеспечивает и атомарность, и барьеры; в отличие от C/C++ `volatile`, который **не даёт никаких** гарантий для многопоточности — это очень частый вопрос-ловушка!). `synchronized`/`Lock` дают ту же acquire/release семантику. `AtomicInteger` и `java.util.concurrent.atomic` — аналоги `std::atomic`, но **без выбора memory_order**: Java даёт только seq_cst-подобную семантику (до VarHandle в Java 9, где появились `getAcquire`/`setRelease`). Главное различие: **в Java data race не даёт UB** — JMM гарантирует, что ты прочитаешь _какое-то_ корректно записанное значение (no out-of-thin-air values); в C++ data race — **чистый UB**, программа может делать что угодно, включая бесконечный цикл из примера выше.

**Отдельно запомни:** C++ `volatile` — это **НЕ** про многопоточность (только про memory-mapped I/O и подавление оптимизаций компилятора; никаких барьеров и атомарности). Java `volatile` — **про** многопоточность. Путаница между ними — классический вопрос на собеседовании для человека с Java-бэкграундом, так что тебя почти наверняка про это спросят.
