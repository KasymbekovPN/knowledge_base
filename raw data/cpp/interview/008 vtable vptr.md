# vtable / vptr и механика виртуального вызова

Сразу оговорка: **стандарт не предписывает vtable**. Он требует только поведение (динамическая диспетчеризация). Но практически все компиляторы (GCC, Clang, MSVC) реализуют её через таблицу виртуальных функций — это де-факто модель, которую и спрашивают.

## Устройство

**vtable** (virtual table) — статический массив указателей на функции, **один на класс**. Лежит в read-only секции бинарника.

**vptr** (virtual pointer) — скрытый указатель на vtable, **один на объект**. Добавляется компилятором в каждый объект полиморфного класса (обычно в начало).

```cpp
struct Base {
    virtual void f();
    virtual void g();
    virtual ~Base();
    int data_;
};

struct Derived : Base {
    void f() override;   // переопределяем
    // g() наследуется как есть
    int extra_;
};
```

Раскладка в памяти:

```
Base объект:                    vtable для Base (в .rodata):
┌──────────────┐               ┌──────────────────┐
│ vptr            │───────────>│ &Base::f         │  [0]
├──────────────┤               ├──────────────────┤
│ data_           │               │ &Base::g            │  [1]
└──────────────┘               ├──────────────────┤
                                   │ &Base::~Base        │  [2]
                                  └──────────────────┘

Derived объект:                 vtable для Derived:
┌──────────────┐               ┌──────────────────┐
│ vptr            │───────────>│ &Derived::f          │  [0]  ← переопределён
├──────────────┤               ├──────────────────┤
│ data_           │  (Base-часть)│ &Base::g            │  [1]  ← унаследован
├──────────────┤               ├──────────────────┤
│ extra_          │               │ &Derived::~Derived  │ [2]
└──────────────┘               └──────────────────┘
```

Ключевые моменты:

- **Порядок слотов одинаков** в базе и наследнике — по этому индексу и происходит вызов
- Наследник заменяет в своей vtable только переопределённые слоты
- vtable **одна на класс**, а не на объект → память платится только за vptr (8 байт на 64-битной)

---

## Ключевой факт: деструктор **никогда не наследуется**

В отличие от обычных методов, у **каждого** класса всегда есть свой деструктор. Если ты его не написал — компилятор генерирует **неявный** деструктор.

```cpp
struct Derived : Base {
    void f() override;
    int extra_;
    // деструктора нет в коде, но компилятор создаёт:
    // ~Derived() { /* пусто */ ; ~Base(); }   ← неявно
};
```

Это фундаментальное отличие деструктора от обычного метода:

| |обычный метод|деструктор|
|---|---|---|
|Если не объявлен в наследнике|**наследуется** реализация базы (тот же код)|**генерируется свой** новый|
|Может быть «переиспользован» из базы|да|нет — всегда собственный|

Почему деструктор не может «наследоваться как есть»: `~Base()` разрушает только Base-часть, а `Derived` содержит ещё `extra_` (и вообще может содержать члены с нетривиальными деструкторами). Поэтому `~Derived()` обязан быть **своей** функцией, которая:

1. выполняет тело (если есть)
2. разрушает члены `Derived` (в обратном порядке объявления)
3. **вызывает `~Base()`**

Такой цепочки в `~Base()` нет и быть не может — база не знает про наследника.

---

## Что это значит для vtable

Раз `~Derived()` — **другая функция**, чем `~Base()`, в vtable Derived в слоте деструктора лежит указатель именно на неё:

```
vtable для Base:                 vtable для Derived:
┌──────────────────┐            ┌────────────────────┐
│ &Base::f         │  [0]       │ &Derived::f        │  [0]  ← переопределён
├──────────────────┤            ├────────────────────┤
│ &Base::g         │  [1]       │ &Base::g           │  [1]  ← ТОТ ЖЕ адрес (наследуется)
├──────────────────┤            ├────────────────────┤
│ &Base::~Base     │  [2]       │ &Derived::~Derived │  [2]  ← ВСЕГДА своя функция
└──────────────────┘            └────────────────────┘
```

Разница между слотами [1] и [2] и есть ответ на твой вопрос:

- **`g()`** — в vtable Derived лежит **буквально тот же указатель** `&Base::g`. Наследник не создаёт новую функцию, слот копируется из базы.
- **`~Derived()`** — компилятор **сгенерировал новую функцию** (пусть даже с пустым телом), и в слот попадает её адрес, не `&Base::~Base`.

Даже если тело `~Derived()` пустое, это не тот же код, что `~Base()`: `~Derived()` дополнительно разрушает `extra_` и вызывает `~Base()`.

---

## Почему деструктор вообще занимает слот в vtable

Потому что в примере `Base` объявил `virtual ~Base()`. Виртуальность **наследуется**: раз деструктор базы виртуален, деструктор наследника **автоматически виртуален** (даже без ключевого слова `virtual` и без `override`).

```cpp
struct Base {
    virtual ~Base();
};
struct Derived : Base {
    // ~Derived() неявный, но АВТОМАТИЧЕСКИ virtual — унаследовал виртуальность
};
```

Это и есть весь смысл виртуального деструктора: слот в vtable позволяет `delete basePtr` попасть в `~Derived()`.

```cpp
Base* p = new Derived();
delete p;
// виртуальный вызов через vtable[2] → &Derived::~Derived
// → разрушает extra_, потом вызывает ~Base()
```

Если бы в vtable Derived в этом слоте лежал `&Base::~Base` (как для `g`), `delete p` разрушил бы только Base-часть — ровно та UB-утечка, ради предотвращения которой деструктор и делают виртуальным.

---

## Итог

Схема корректна, и вот точная формулировка:

- **`g()`**: не переопределена → слот в vtable Derived **указывает на функцию базы** (`&Base::g`). Наследование метода = переиспользование того же кода.
- **`~Derived()`**: деструктор **не наследуется никогда** — компилятор всегда генерирует его неявно, если не написан явно. В vtable Derived попадает адрес этой сгенерированной функции.

Моя фраза про `g()` («наследуется как есть») была верна, но по контрасту создавала впечатление, что деструктор в Derived «взялся ниоткуда». На самом деле он там всегда — просто невидим в исходнике.

---

**На собеседовании** это ложится в вопрос «наследуются ли конструкторы и деструкторы?». Ответ: **нет**. Конструкторы не наследуются (до C++11 совсем; с C++11 есть `using Base::Base;` — но это явный опт-ин, и формально это тоже генерация конструкторов наследника). Деструкторы не наследуются — каждый класс всегда получает собственный, явный или неявный. Наследуются только обычные методы и данные.

# Наследуется ли виртуальность?

**Да — для любого метода**, но с важной оговоркой: виртуальность наследуется **не «для всех методов класса», а для каждого метода, объявленного `virtual` в базе, и только при совпадении сигнатуры.**

## Основное правило

Если метод объявлен `virtual` в базе, то метод наследника **с той же сигнатурой** автоматически становится виртуальным — независимо от того, написал ли ты `virtual` или `override`:

```cpp
struct Base {
    virtual void f();
    void g();          // НЕ virtual
};

struct Derived : Base {
    void f();          // ✅ АВТОМАТИЧЕСКИ virtual (унаследовал виртуальность от Base::f)
    void g();          // ❌ НЕ virtual — Base::g не был virtual → это просто СКРЫТИЕ (hiding)
};
```

Виртуальность — свойство **конкретного метода** (точнее, слота в vtable), а не класса. Она распространяется вниз по иерархии от того метода, который её ввёл. Метод `g` не был виртуальным в базе — значит виртуальным он не станет ни в одном наследнике (переопределить нельзя то, чего нет в vtable).

```cpp
Base* p = new Derived();
p->f();   // → Derived::f  (виртуальный вызов через vtable)
p->g();   // → Base::g     (статический вызов по типу указателя!)
```

Вот это различие в поведении `f` и `g` — классический экзаменационный пример.

---

## Виртуальность неотменяема

Нельзя «отменить» виртуальность в наследнике. Раз метод виртуален в базе — он виртуален во всей иерархии ниже:

```cpp
struct A { virtual void f(); };
struct B : A { void f(); };        // virtual (унаследовано)
struct C : B { void f(); };        // тоже virtual — и так до конца иерархии
```

Единственное, что можно — **запретить дальнейшее переопределение** через `final`. Но метод при этом остаётся виртуальным (слот в vtable никуда не девается), просто ниже его переопределять запрещено:

```cpp
struct B : A {
    void f() final;   // всё ещё virtual, но C уже не сможет override
};
struct C : B {
    void f();         // ❌ ошибка компиляции: B::f is final
};
```

---

## Критическое условие: сигнатура должна совпадать

Виртуальность «подхватывается» только если сигнатура **точно совпадает** с базовой. Иначе это не переопределение, а **новый метод**, который **скрывает** базовый (name hiding):

```cpp
struct Base {
    virtual void f(int);
    virtual void h() const;
};

struct Derived : Base {
    void f(double);      // ⚠️ другой параметр → НЕ override → новый НЕ-виртуальный метод,
                         //    который вдобавок СКРЫВАЕТ Base::f(int)
    void h();            // ⚠️ потерян const → тоже НЕ override → новый метод
};

Base* p = new Derived();
p->f(1);   // → Base::f(int)! (Derived::f(double) не в vtable)

Derived d;
d.f(1);    // ⚠️ вызовет Derived::f(double) с преобразованием int→double!
           //    Base::f(int) СКРЫТ — не виден без явного using
```

Совпадать должны: имя, типы параметров, `const`/`volatile`-квалификаторы, ref-qualifier (`&`/`&&`). Возвращаемый тип — тоже, за исключением **ковариантных** возвращаемых типов:

```cpp
struct Base { virtual Base* clone() const; };
struct Derived : Base { Derived* clone() const override; };  // ✅ ковариантный возврат — OK
```

**Именно поэтому существует `override`** — он не добавляет виртуальности (она и так унаследуется), а **проверяет на этапе компиляции**, что метод действительно что-то переопределяет:

```cpp
struct Derived : Base {
    void f(double) override;   // ❌ ОШИБКА КОМПИЛЯЦИИ — ничего не переопределяет
    void h() override;         // ❌ ОШИБКА — потерян const
};
```

Без `override` эти опечатки компилируются молча и дают неверное поведение в рантайме. Практическое правило: **всегда пиши `override`** при переопределении.

---

## Name hiding — отдельная ловушка

Объявление **любого** метода с именем `f` в наследнике скрывает **все** перегрузки `f` из базы, даже виртуальные:

```cpp
struct Base {
    virtual void f(int);
    virtual void f(double);
};

struct Derived : Base {
    void f(int) override;   // переопределяем только одну перегрузку
};

Derived d;
d.f(1);      // ✅ Derived::f(int)
d.f(1.0);    // ⚠️ вызовет Derived::f(int) с преобразованием double→int!
             //    Base::f(double) СКРЫТ, хотя виртуален и не переопределён
```

Лечится через `using`:

```cpp
struct Derived : Base {
    using Base::f;          // возвращаем все перегрузки Base::f в область видимости
    void f(int) override;
};

d.f(1.0);   // ✅ теперь Base::f(double) — виртуальный вызов, как ожидалось
```

Важно: скрытие — это про **разрешение имени на этапе компиляции**, а не про vtable. Через указатель на базу `p->f(1.0)` вызовется `Base::f(double)` корректно — скрытие проявляется только при обращении через `Derived`.

## Особые случаи

### Деструктор

Работает по общему правилу — виртуальность наследуется, но сам деструктор **не наследуется** (мы это разбирали):

```cpp
struct Base { virtual ~Base(); };
struct Derived : Base { };   // ~Derived() неявный, но АВТОМАТИЧЕСКИ virtual
```

### Конструкторы

**Не могут быть virtual вообще.** Причина механическая: vptr устанавливается конструктором — на момент начала конструирования динамического типа ещё нет, диспетчеризовать не по чему.

(Идиома «виртуальный конструктор» — это паттерн через виртуальный `clone()`.)

### `static` методы

Не могут быть virtual — у них нет `this`, а значит нет объекта и нет vptr.

### Private virtual — можно и осмысленно

Виртуальность и доступ — **ортогональны**. Приватный виртуальный метод можно переопределить в наследнике (переопределение не требует доступа):

```cpp
struct Base {
public:
    void run() { step(); }        // публичный невиртуальный интерфейс
private:
    virtual void step() = 0;      // приватный виртуальный — точка кастомизации
};

struct Derived : Base {
private:
    void step() override { }      // ✅ переопределяем приватный метод базы
};
```

Это идиома **NVI** (Non-Virtual Interface): публичный невиртуальный метод фиксирует алгоритм/инварианты, а приватные виртуальные — точки расширения.

## Сводка

| |Наследуется?|
|---|---|
|Виртуальность **виртуального** метода (та же сигнатура)|✅ автоматически, неотменяемо|
|Виртуальность для **невиртуального** метода базы|❌ никогда (метод в наследнике просто скрывает базовый)|
|Метод с **другой** сигнатурой|❌ не override → новый метод + name hiding|
|Деструктор при `virtual ~Base()`|✅ виртуальность наследуется (но сам деструктор генерируется свой)|
|Конструктор|❌ не может быть virtual в принципе|
|`static` метод|❌ не может быть virtual|

## Формулировки на собеседовании

**«Нужно ли писать `virtual` в наследнике?»** — Не обязательно, виртуальность наследуется автоматически. Но нужно писать **`override`** — он не влияет на виртуальность, а проверяет корректность сигнатуры на этапе компиляции.

**«Все ли методы становятся виртуальными в наследнике полиморфного класса?»** — Нет. Виртуальность привязана к **конкретному методу**, а не к классу. Только те методы, что объявлены `virtual` в базе (или выше по иерархии), виртуальны в наследниках.

**«Можно ли отменить виртуальность?»** — Нет. Можно только запретить дальнейшее переопределение через `final`, но слот в vtable остаётся.

**«Что будет, если сигнатура не совпала?»** — Не переопределение, а новый метод + скрытие всех одноимённых перегрузок базы. Без `override` компилируется молча — источник трудноуловимых багов.

---

Отличие от Java: там методы **виртуальны по умолчанию** (нужно явно писать `final`, чтобы запретить переопределение), а `@Override` — тоже опциональная compile-time проверка, аналог C++'ного `override`. В C++ виртуальность **opt-in** — платишь только за то, что явно попросил. Это то самое различие философий, о котором мы говорили про vtable.

## Механика вызова

```cpp
void call(Base* p) {
    p->f();   // виртуальный вызов
}
```

Компилятор генерирует примерно (псевдоассемблер):

```
1. загрузить vptr из объекта:      vptr = *(void**)p          ; разыменование #1
2. загрузить адрес функции:        func = vptr[0]             ; разыменование #2 (индекс f = 0)
3. вызвать:                        call func(p)               ; косвенный вызов
```

Три шага: **два разыменования + косвенный call**. Индекс слота (`0` для `f`) известен **на этапе компиляции** — он одинаков во всех vtable иерархии.

```cpp
Derived d;
Base* p = &d;
p->f();   // vptr указывает на vtable Derived → слот[0] → Derived::f
          // тип *p (Base*) статический, но vptr «знает» динамический тип
```

Именно поэтому вызывается `Derived::f`, хотя указатель — `Base*`. Динамический тип закодирован в vptr самого объекта.

---

## Кто и когда устанавливает vptr

**Конструктор** устанавливает vptr, **деструктор** его «откатывает». Это критично для понимания одного из главных подводных камней.

При создании `Derived`:

1. Конструктор `Base` начинает работу → vptr = vtable **Base**
2. Тело `Base::Base()` выполняется (vptr указывает на Base!)
3. Конструктор `Derived` начинает работу → vptr **переустанавливается** на vtable **Derived**
4. Тело `Derived::Derived()` выполняется

При разрушении — в обратном порядке (vptr «понижается» обратно к Base перед `~Base()`).

### Следствие: виртуальный вызов из конструктора/деструктора

```cpp
struct Base {
    Base() { f(); }              // ⚠️ вызовет Base::f, НЕ Derived::f!
    virtual void f() { std::cout << "Base::f\n"; }
    virtual ~Base() { f(); }     // ⚠️ тоже Base::f
};

struct Derived : Base {
    void f() override { std::cout << "Derived::f\n"; }
};

Derived d;   // печатает: "Base::f" (из конструктора), потом "Base::f" (из деструктора)
```

Причина: во время `Base::Base()` vptr ещё указывает на vtable Base — Derived-часть объекта не сконструирована, вызывать `Derived::f` было бы обращением к неинициализированным полям. Классический вопрос-ловушка.

Если у `Base` вызвать **чисто виртуальную** функцию из конструктора — UB (обычно рантайм-ошибка "pure virtual method called").

## Виртуальный деструктор — зачем

```cpp
struct Base {
    ~Base() { }          // НЕ virtual
};
struct Derived : Base {
    std::vector<int> big_;
    ~Derived() { }
};

Base* p = new Derived();
delete p;   // ⚠️ UB! вызовется только ~Base(), ~Derived() пропущен → утечка big_
```

Без `virtual` деструктор вызывается **статически** — по типу указателя. Компилятор видит `Base*` и зовёт `~Base()`. Derived-часть не разрушается.

```cpp
struct Base {
    virtual ~Base() { }   // ✅
};

Base* p = new Derived();
delete p;   // виртуальный вызов через vtable → ~Derived() → потом ~Base()
```

Правило: **если класс полиморфный (имеет хоть одну виртуальную функцию) и предполагается удаление через указатель на базу — деструктор должен быть virtual.**

Альтернатива для не-полиморфного использования: `protected` не-виртуальный деструктор (запрещает `delete` через базу).

## Стоимость

**Память:**

- +1 указатель на **объект** (vptr) — 8 байт на 64-битной
- +1 vtable на **класс** (в .rodata, разделяется всеми объектами)

```cpp
struct NonPoly { int x; };            // sizeof == 4
struct Poly { virtual void f(); int x; };  // sizeof == 16 (vptr 8 + int 4 + padding 4)
```

**Время:**

- 2 загрузки из памяти + косвенный вызов
- Сам оверхед мал, но **главная цена — блокировка инлайнинга**: компилятор не знает, какая функция будет вызвана, поэтому не может встроить тело. Для маленьких функций в горячем цикле это ощутимо.
- Косвенный вызов хуже предсказывается процессором (branch/indirect target prediction), хотя современные CPU справляются неплохо при стабильном динамическом типе

## Девиртуализация

Компилятор **может** убрать виртуальный вызов, если докажет динамический тип:

```cpp
Derived d;
d.f();          // статический вызов — тип известен точно (объект, не указатель)

Base* p = new Derived();
p->f();         // компилятор может девиртуализовать, если видит new Derived рядом (LTO/оптимизации)
```

`final` помогает девиртуализации — компилятор знает, что переопределений больше не будет:

```cpp
struct Derived final : Base {
    void f() override { }
};

Derived* p = getDerived();
p->f();   // Derived final → переопределений нет → прямой вызов, можно инлайнить
```

Отсюда практический совет: помечай `final` классы/методы, где переопределение не планируется — это не только семантика, но и оптимизация.

## Множественное наследование — несколько vptr

```cpp
struct A { virtual void fa(); int a_; };
struct B { virtual void fb(); int b_; };
struct C : A, B { void fa() override; void fb() override; };
```

Объект `C` содержит **два** vptr — по одному на каждую полиморфную базу:

```
C объект:
┌──────────┐
│ vptr_A   │──> vtable для A-части C
│ a_       │
├──────────┤
│ vptr_B   │──> vtable для B-части C
│ b_       │
└──────────┘
```

Причина: `B* pb = &c;` должен дать указатель, который выглядит как настоящий `B` — с vptr в начале своей части. Поэтому при приведении `C*` → `B*` указатель **сдвигается** на offset B-части.

```cpp
C c;
A* pa = &c;   // pa == &c (offset 0)
B* pb = &c;   // pb == &c + sizeof(A-part) — АДРЕС ДРУГОЙ!
```

Это тот самый случай, о котором говорили в контексте `shared_ptr`: при приведении к базе указатель может сдвинуться, поэтому `shared_ptr` хранит указатель на объект отдельно от указателя на control block.

Когда `pb->fb()` вызывает `C::fb()`, а `C::fb` ожидает `this` типа `C*` — используется **thunk**: маленькая переходная функция, корректирующая `this` обратно на начало `C`.

## `override` и `final` — не про рантайм, а про компиляцию

```cpp
struct Base {
    virtual void f(int);
};
struct Derived : Base {
    void f(double) override;   // ❌ ошибка компиляции: не переопределяет (другая сигнатура)
    // без override — тихо создался бы НОВЫЙ метод, скрывающий Base::f
};
```

`override` — проверка на этапе компиляции, что метод действительно что-то переопределяет. Не влияет на vtable, но ловит опечатки в сигнатуре (частая ошибка: разные const, разные типы).

`final` запрещает дальнейшее переопределение (метод) или наследование (класс) — плюс помогает девиртуализации.

## Формулировки на собеседовании

**«Как работает виртуальный вызов?»** — объект содержит vptr на vtable своего динамического класса; вызов = загрузить vptr, взять функцию по фиксированному индексу слота, вызвать косвенно. Индекс известен на этапе компиляции, конкретная функция — в рантайме.

**«Сколько vtable у класса? Сколько vptr у объекта?»** — одна vtable на класс (в .rodata); один vptr на объект (при множественном наследовании — по одному на каждую полиморфную базу).

**«Почему нельзя вызывать виртуальную функцию из конструктора?»** — vptr во время работы конструктора базы указывает на vtable **базы**, потому что производная часть ещё не сконструирована; вызов уйдёт в базовую версию. Для pure virtual — UB.

**«Зачем виртуальный деструктор?»** — иначе `delete` через указатель на базу вызовет только `~Base()` (статическая диспетчеризация) → производная часть не разрушится → UB/утечка.

**«Сколько стоит виртуальный вызов?»** — +8 байт на объект, два разыменования и косвенный call; главный минус — невозможность инлайнинга.

---

Отличие от Java: там **все** методы виртуальны по умолчанию (кроме `static`/`private`/`final`), и JVM использует похожую vtable-диспетчеризацию, но с мощной рантайм-девиртуализацией через JIT (monomorphic inline caches — JIT видит, что в конкретном месте всегда приходит один тип, и инлайнит с проверкой). В C++ виртуальность **opt-in** (`virtual`), девиртуализация — только статическая, на этапе компиляции/LTO. Это принципиальное различие в философии: C++ не платит за то, что не использует.
