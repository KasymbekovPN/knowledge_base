# Data race vs race condition

Мы касались этого дважды — теперь соберу целостно, потому что различие тонкое и его любят спрашивать, чтобы отделить «знаю про мьютексы» от «понимаю конкурентность».

## Определения

**Data race** — **техническое** свойство программы, определённое стандартом:

> Два потока обращаются к **одной ячейке памяти**, хотя бы один **пишет**, и между ними нет отношения **happens-before**.

Результат — **UB**. Не «неверное значение», а undefined behavior: компилятор вправе предполагать, что этого не бывает.

**Race condition** — **логическая** ошибка:

> Корректность результата зависит от **относительного порядка** выполнения операций в разных потоках.

Результат — **неверное поведение** программы (но не UB на уровне языка).

Ключевое: это **разные оси**. Одно может быть без другого.

---

## Data race без race condition

```cpp
int counter = 0;   // обычный int

void worker() {
    for (int i = 0; i < 1000; ++i)
        ++counter;   // ⚠️ DATA RACE
}
```

Здесь есть и то, и другое. Но вот пример **чистого data race** без логической гонки:

```cpp
bool done = false;   // обычный bool

void worker() {
    while (!done) { }   // ⚠️ DATA RACE (чтение без синхронизации)
    cleanup();
}

void stop() { done = true; }   // ⚠️ DATA RACE (запись)
```

Логически всё правильно: `done` пишется один раз, читается — порядок не важен, промежуточных состояний у `bool` нет. Даже если запись «увидится» с задержкой, программа корректна.

**Но это data race → UB.** И вот что реально происходит:

```cpp
// Компилятор видит: в цикле done не меняется (о других потоках он не знает)
// → выносит проверку из цикла:
if (!done) { while (true) { } }   // ⚠️ БЕСКОНЕЧНЫЙ ЦИКЛ
```

Программа зависает **не** из-за «неудачного тайминга», а из-за легальной оптимизации, разрешённой UB. Никакие повторные запуски не помогут — это детерминированное следствие.

**Исправление:**

```cpp
std::atomic<bool> done{false};   // ✅ data race устранён
void worker() { while (!done) { } }   // компилятор обязан перечитывать
void stop() { done = true; }
```

Это важный момент: **устранение data race здесь не было «синхронизацией логики»** — логика и так была верна. Мы просто запретили компилятору ломать программу.

## Race condition без data race

Обратный случай — и он **чаще всего и есть настоящий баг**.

```cpp
std::mutex mtx;
std::vector<int> v;

void consumer() {
    bool has_data;
    {
        std::lock_guard lock(mtx);
        has_data = !v.empty();     // ✅ под локом — data race НЕТ
    }
    // ⚠️ ЗДЕСЬ другой поток может опустошить v!
    if (has_data) {
        std::lock_guard lock(mtx);
        int x = v.back();          // ✅ под локом — data race НЕТ
        v.pop_back();              // ⚠️ но v может быть УЖЕ ПУСТ → UB!
    }
}
```

**Каждое обращение защищено мьютексом. Data race отсутствует.** Но программа сломана: между проверкой и использованием состояние изменилось.

Это **TOCTOU** (Time-Of-Check to Time-Of-Use) — самая частая форма race condition.

### Исправление: расширить критическую секцию

```cpp
void consumer() {
    std::lock_guard lock(mtx);   // ✅ проверка И действие — АТОМАРНО
    if (!v.empty()) {
        int x = v.back();
        v.pop_back();
    }
}
```

Мьютекс тот же — изменилась **гранулярность**. Вот в чём суть: **data race лечится синхронизацией; race condition лечится правильным выбором того, что считать атомарной операцией.**

## Почему у `std::stack` небезопасный интерфейс

Классический пример из Энтони Уильямса. Даже если сделать **каждый метод** потокобезопасным:

```cpp
// Гипотетический "thread-safe" stack — каждый метод под локом
if (!s.empty()) {      // (1) поток A: не пусто
    int x = s.top();   // (2) ⚠️ поток B успел сделать pop() → стек пуст → UB
    s.pop();           // (3) ⚠️ ещё один pop
}
```

**Вывод: потокобезопасность отдельных методов НЕ даёт потокобезопасности их композиции.** Интерфейс `empty()`/`top()`/`pop()` принципиально не может быть безопасным — нужна **атомарная** операция «извлечь, если есть»:

```cpp
std::optional<T> try_pop();   // ✅ атомарно: проверка + извлечение
```

Именно поэтому в thread-safe очереди (которую мы писали в теме condition_variable) нет отдельного `empty()` для принятия решений — `pop()` возвращает `optional<T>`.

Это очень частый вопрос на собеседовании: **«почему нельзя просто обернуть каждый метод std::stack в мьютекс?»**

## Ещё примеры race condition без data race

### 1. Check-then-act с атомиками

```cpp
std::atomic<int> counter{0};

if (counter.load() < 10) {      // ✅ атомарно
    counter.store(counter.load() + 1);   // ⚠️ RACE: между load и store другой поток инкрементил
}                                         //    → counter может превысить 10
```

Атомики устраняют data race, но **не** делают последовательность операций атомарной. Нужен CAS:

```cpp
int old = counter.load();
while (old < 10 && !counter.compare_exchange_weak(old, old + 1)) { }   // ✅ атомарно
```

### 2. Ленивая инициализация (double-checked locking)

```cpp
Widget* instance = nullptr;
std::mutex mtx;

Widget* get() {
    if (!instance) {                     // (1) проверка БЕЗ лока → ⚠️ data race
        std::lock_guard lock(mtx);
        if (!instance)                   // (2) повторная проверка
            instance = new Widget();     // ⚠️ запись без синхронизации с (1)
    }
    return instance;
}
```

Тут **и** data race (строка 1 читает без синхронизации), **и** более коварная проблема: даже с атомиком, при `relaxed` порядке поток мог бы увидеть **ненулевой указатель, но неинициализированный объект** (компилятор/CPU вправе опубликовать указатель до завершения конструктора).

Правильно (мы это разбирали в memory_order):

```cpp
std::atomic<Widget*> instance{nullptr};

Widget* get() {
    Widget* p = instance.load(std::memory_order_acquire);   // ✅
    if (!p) {
        std::lock_guard lock(mtx);
        p = instance.load(std::memory_order_relaxed);
        if (!p) {
            p = new Widget();
            instance.store(p, std::memory_order_release);   // ✅ публикуем
        }
    }
    return p;
}
```

**Ещё лучше — вообще не писать это руками:**

```cpp
Widget& get() {
    static Widget instance;   // ✅ C++11: инициализация thread-safe ГАРАНТИРОВАННО
    return instance;
}
```

Function-local static (Meyers singleton) — компилятор сам генерирует корректную синхронизацию. Это правильный ответ на собеседовании: «double-checked locking не нужен, есть magic statics».

### 3. Транзакция без атомарности

```cpp
void transfer(Account& from, Account& to, int amount) {
    {
        std::lock_guard lock(from.mtx_);
        from.balance -= amount;
    }
    // ⚠️ ЗДЕСЬ деньги нигде — если кто-то читает сумму, увидит недостачу
    {
        std::lock_guard lock(to.mtx_);
        to.balance += amount;
    }
}
```

Data race нет. Но инвариант «сумма всех счетов постоянна» нарушен в промежутке → race condition.

```cpp
void transfer(Account& from, Account& to, int amount) {
    std::scoped_lock lock(from.mtx_, to.mtx_);   // ✅ атомарно, и без deadlock
    from.balance -= amount;
    to.balance += amount;
}
```

## Сводная таблица

| |Data race|Race condition|
|---|---|---|
|Природа|техническая (определена стандартом)|логическая|
|Определение|конкурентный доступ к памяти, ≥1 запись, без happens-before|результат зависит от порядка выполнения|
|Последствие|**UB** (компилятор вправе оптимизировать как угодно)|неверное поведение|
|Лечение|синхронизация: мьютекс, `std::atomic`|**правильная гранулярность** атомарности|
|Детектируется|**TSan** (`-fsanitize=thread`) — надёжно|❌ автоматически почти невозможно|
|Проявление|может быть **детерминированным** (оптимизация ломает код)|зависит от тайминга, «плавающий» баг|

## Ключевые следствия

**1. Устранение всех data race ≠ корректная программа.** Обернуть каждый метод в мьютекс — необходимое, но **не достаточное** условие.

**2. Race condition — сложнее.** Data race ловится инструментами (TSan) и лечится механически. Race condition требует **проектирования**: понять, какая последовательность операций должна быть атомарной с точки зрения инвариантов.

**3. Правильный вопрос при проектировании:** не «где поставить мьютекс», а **«какая последовательность операций должна выглядеть атомарной для других потоков?»** — и уже под это определять критические секции и интерфейс.

**4. Отсюда — дизайн интерфейсов.** Потокобезопасный класс должен предоставлять **составные** операции (`try_pop()`, `compare_and_swap`, `increment_if_less_than(n)`), а не набор примитивов, из которых клиент вынужден собирать неатомарные последовательности.

---

## Инструменты

```bash
g++ -fsanitize=thread -g prog.cpp    # TSan — ловит DATA RACES в рантайме
```

TSan отслеживает happens-before между обращениями и сообщает о нарушениях. Работает отлично, но:

- ловит только **выполненные** пути (нужны хорошие тесты и стресс-нагрузка)
- **не** ловит race condition (логику он не знает)
- замедление ~5-15x, память ×5-10

Для race condition инструментов почти нет — только рассуждения, code review и стресс-тесты. Это принципиальная асимметрия.

## Формулировки на собеседовании

**«В чём разница data race и race condition?»** — Data race — **техническое** нарушение: конкурентный доступ к памяти, ≥1 запись, без happens-before → **UB**. Race condition — **логическая** ошибка: результат зависит от порядка выполнения. Ортогональны: можно иметь одно без другого.

**«Приведи race condition без data race.»** — TOCTOU: `if (!v.empty()) { x = v.back(); }` — обе операции под мьютексом (data race нет), но между ними другой поток мог опустошить вектор. Лечится расширением критической секции, а не добавлением синхронизации.

**«Приведи data race без race condition.»** — `bool done` без атомика: логически корректно (пишем один раз, читаем — порядок не важен), но это UB → компилятор выносит проверку из цикла → бесконечный цикл. Лечится `std::atomic<bool>`.

**«Почему нельзя просто обернуть каждый метод `std::stack` в мьютекс?»** — Потокобезопасность отдельных методов не даёт безопасности их **композиции**: `empty()` → `top()` → `pop()` — между вызовами состояние меняется. Нужна **атомарная составная** операция: `std::optional<T> try_pop()`.

**«Как детектировать?»** — Data race — **TSan** (`-fsanitize=thread`), надёжно. Race condition — автоматически почти невозможно, только проектирование, review и стресс-тесты.

**«Что не так с double-checked locking?»** — Классическая версия имеет data race на первой проверке и (даже с атомиком без release/acquire) может опубликовать указатель до завершения конструктора. В C++11+ решается через **function-local static** (magic statics) — компилятор гарантирует потокобезопасную однократную инициализацию.

---

Отличие от Java: там **data race не даёт UB** — JMM гарантирует, что чтение вернёт _какое-то_ значение, записанное каким-то потоком (no out-of-thin-air values). Программа с data race в Java может дать неверный результат, но не «взорвётся» непредсказуемо и компилятор не оптимизирует её в бесконечный цикл. В C++ data race — **чистый UB**, и это принципиально строже. Race condition в обоих языках одинаково опасны и одинаково не ловятся инструментами. Ещё одно следствие: Java-программист привыкает, что «забыл `volatile` → иногда неверное значение», а C++-программист должен понимать, что «забыл `atomic` → программа может делать буквально что угодно».
