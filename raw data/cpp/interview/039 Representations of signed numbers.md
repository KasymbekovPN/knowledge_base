# Представления знаковых чисел

Три исторических способа кодировать знак в битах. Понимание нужно, чтобы осознавать, **почему** знаковое переполнение было UB и откуда берётся асимметрия `INT_MIN`/`INT_MAX`.

Для примера везде используем **4-битные** числа (легче показать), диапазон значений — 16 комбинаций битов.

---

## 1. Sign-magnitude (знак-величина)

Самое «интуитивное»: старший бит — знак (0 = плюс, 1 = минус), остальные биты — модуль.

```
0 000  = +0        1 000  = -0     ← ДВА НУЛЯ!
0 001  = +1        1 001  = -1
0 010  = +2        1 010  = -2
0 011  = +3        1 011  = -3
0 100  = +4        1 100  = -4
0 101  = +5        1 101  = -5
0 110  = +6        1 110  = -6
0 111  = +7        1 111  = -7
^                  ^
знак               знак
```

Диапазон: **−7 … +7** (симметричный).

**Проблемы:**

- **Два нуля**: `+0` (0000) и `−0` (1000) — нужно обрабатывать оба при сравнении
- **Сложение сложное**: нельзя просто складывать биты — надо смотреть на знаки, сравнивать модули, вычитать
    
    ```
    +3 + (-1):  0011 + 1001 = 1100 = -4?  ❌ неверно! нужна спец-логика
    ```
    
- Нужны **отдельные схемы** для сложения и вычитания в железе

Использовалось в ранних машинах (IBM 7090). Сейчас — только в мантиссе float (IEEE 754 использует sign-magnitude для мантиссы).

---

## 2. One's complement (дополнение до единицы)

Отрицательное число = **побитовая инверсия** положительного.

```
0 000  = +0        1 111  = -0     ← СНОВА ДВА НУЛЯ!
0 001  = +1        1 110  = -1
0 010  = +2        1 101  = -2
0 011  = +3        1 100  = -3
0 100  = +4        1 011  = -4
0 101  = +5        1 010  = -5
0 110  = +6        1 001  = -6
0 111  = +7        1 000  = -7
```

Чтобы получить `−x`: инвертируй все биты `x`.

```
+3 = 0011
-3 = 1100   (инверсия)
```

Диапазон: **−7 … +7** (симметричный).

**Улучшение над sign-magnitude:** сложение почти работает обычным двоичным сложением, но нужен **end-around carry** — перенос из старшего разряда добавляется обратно к младшему:

```
+3 + (-1):  0011 + 1110 = 1)0001
            перенос 1 добавляем обратно: 0001 + 1 = 0010 = +2  ✅
```

**Проблемы:**

- **Два нуля** (`+0` = 0000, `−0` = 1111) — та же беда
- **End-around carry** усложняет железо

Использовалось (CDC 6600, PDP-1). Сейчас практически вымерло.

---

## 3. Two's complement (дополнение до двух) — современный стандарт

Отрицательное число = **инверсия битов + 1**. Или иначе: старший бит имеет **отрицательный вес**.

```
0 000  =  0
0 001  = +1
0 010  = +2
0 011  = +3
0 100  = +4
0 101  = +5
0 110  = +6
0 111  = +7        ← MAX = +7
1 000  = -8        ← MIN = -8   (АСИММЕТРИЯ!)
1 001  = -7
1 010  = -6
1 011  = -5
1 100  = -4
1 101  = -3
1 110  = -2
1 111  = -1
```

Как получить `−x`: инвертировать биты и прибавить 1.

```
+3 = 0011
инверсия: 1100
+1:       1101 = -3   ✅

проверка через "вес старшего бита" (для 4 бит старший бит = -8):
1101 = -8 + 4 + 0 + 1 = -3   ✅
```

Диапазон: **−8 … +7** (АСИММЕТРИЧНЫЙ — на одно отрицательное больше).

### Три ключевых преимущества

**1. Один ноль:**

```
+0 и -0 — это ОДНА комбинация 0000
-0 = инверсия(0000) + 1 = 1111 + 1 = 1)0000 → 0000 (перенос отброшен)
```

Нет проблемы двух нулей.

**2. Сложение/вычитание — ОБЫЧНОЕ двоичное сложение, без спецлогики:**

```
+3 + (-1):  0011 + 1111 = 1)0010 → 0010 = +2   ✅ (перенос просто отбрасывается)
+5 + (-3):  0101 + 1101 = 1)0010 → 0010 = +2   ✅
```

Одна и та же схема сумматора работает для знаковых и беззнаковых чисел. Вычитание = сложение с отрицанием. **Железо максимально простое** — это и есть причина победы two's complement.

**3. Знаковые и беззнаковые операции идентичны на уровне битов** (для +, −, *) — процессору не нужны отдельные инструкции сложения для signed/unsigned.

### Откуда асимметрия INT_MIN / INT_MAX

```
4 бита:  MIN = -8,  MAX = +7   →  |MIN| = 8 > 7 = |MAX|
32 бита: INT_MIN = -2147483648, INT_MAX = +2147483647
```

Причина: убрали дубликат нуля. В sign-magnitude и one's complement одна комбинация «тратилась» на `−0`. Two's complement переиспользовал её под лишнее отрицательное число (`1000` = `−8`, а не `−0`).

Отсюда все ловушки, которые мы разбирали в signed overflow:

```cpp
-INT_MIN;          // ⚠️ UB: +2147483648 не влезает (MAX только +2147483647)
std::abs(INT_MIN); // ⚠️ UB: та же причина
INT_MIN / -1;      // ⚠️ UB: результат +2147483648 не представим
```

`−INT_MIN` не имеет представления — вот прямое следствие асимметрии.

## Сравнение

| |Sign-magnitude|One's complement|Two's complement|
|---|---|---|---|
|Нулей|**два** (±0)|**два** (±0)|**один** ✅|
|Диапазон (n бит)|симметричный ±(2ⁿ⁻¹−1)|симметричный ±(2ⁿ⁻¹−1)|−2ⁿ⁻¹ … 2ⁿ⁻¹−1 (асимметр.)|
|Сложение|спецлогика|end-around carry|**обычное двоичное** ✅|
|Отрицание|инверсия знак-бита|инверсия всех битов|инверсия + 1|
|Аппаратная сложность|высокая|средняя|**минимальная** ✅|
|Используется сейчас|float-мантисса|почти нет|**везде** ✅|

## Как это связано с C++ и UB

### До C++20: реализация не фиксирована

Стандарт C++ (до C++20) **не требовал** конкретного представления. Компилятор мог использовать любое из трёх (теоретически). Отсюда:

- **Битовые операции над знаковыми были не переносимы** — `-1 >> 1`, `~x`, `x & mask` для отрицательных давали разные результаты на разных представлениях
- **Переполнение** объявили **UB**, чтобы не привязываться к поведению конкретного представления (в two's complement — wraparound, в sign-magnitude — что-то другое)

### C++20: two's complement стал обязательным (P0907)

```cpp
// C++20 гарантирует:
static_assert(-1 == ~0);   // ✅ гарантировано (two's complement)
```

Теперь стандарт **требует** two's complement для знаковых целых. Битовое представление зафиксировано.

### Но переполнение ОСТАЛОСЬ UB

Это ключевой момент, который часто путают:

```cpp
// C++20: представление two's complement — ГАРАНТИРОВАНО
// НО:
int x = INT_MAX;
x + 1;   // ⚠️ ВСЁ ЕЩЁ UB, хотя мы "знаем", что two's complement дал бы INT_MIN
```

Почему UB не убрали вместе с фиксацией представления: **оптимизации**. Компилятор всё ещё хочет предполагать «переполнения не бывает» (для векторизации циклов, упрощения `x+1 > x` → `true` и т.д. — мы разбирали). Если бы переполнение сделали wraparound (как `-fwrapv`), эти оптимизации стали бы невозможны.

Итог парадоксальный, но логичный: **представление фиксировано (two's complement), а переполнение — по-прежнему UB**. Ты «знаешь», какой результат дало бы железо, но полагаться на это нельзя.

## Практические следствия two's complement

### 1. Быстрые трюки (работают именно из-за two's complement)

```cpp
x & (x - 1)        // убрать младший установленный бит
x & -x             // выделить младший установленный бит (работает из-за two's complement!)
-x == ~x + 1       // отрицание
x >> 31            // знаковый бит int (арифметический сдвиг тиражирует знак)
```

`x & -x` — классика: `-x` в two's complement это `~x + 1`, и `&` оставляет только младший бит. В других представлениях не работало бы.

### 2. Арифметический vs логический сдвиг

```cpp
int x = -8;         // 1000 (4 бита)
x >> 1;             // арифметический: 1100 = -4 (знак тиражируется)

unsigned u = 8;
u >> 1;             // логический: 0100 = 4 (дополняется нулём)
```

Для знаковых `>>` — **арифметический** (сохраняет знак). До C++20 результат `>>` для отрицательных был implementation-defined; C++20 зафиксировал арифметический сдвиг.

### 3. Знак через старший бит

```cpp
bool negative = (x >> 31) & 1;   // старший бит = знак (для 32-бит int)
```

## Формулировки на собеседовании

**«Какие есть представления знаковых чисел?»** — Sign-magnitude (знак-бит + модуль), one's complement (инверсия), two's complement (инверсия + 1). Первые два имеют **два нуля** и симметричный диапазон; two's complement — **один ноль**, асимметричный диапазон, простейшее железо.

**«Почему победил two's complement?»** — Один ноль (нет `−0`); сложение/вычитание — обычное двоичное без спецлогики (одна схема для signed и unsigned); минимальная аппаратная сложность.

**«Откуда асимметрия `INT_MIN`/`INT_MAX`?»** — Two's complement убрал дубликат нуля из sign-magnitude/one's complement и переиспользовал эту комбинацию под лишнее **отрицательное** число. Поэтому `|INT_MIN| = |INT_MAX| + 1`, и `−INT_MIN` не представим → UB.

**«Гарантирует ли C++ two's complement?»** — С **C++20** — да (P0907), битовое представление зафиксировано. До C++20 — не гарантировалось. Но **переполнение осталось UB** даже в C++20 — ради оптимизаций (компилятор предполагает, что его нет).

**«Почему `-1 >> 1` для int даёт `-1`?»** — Арифметический сдвиг: знаковый бит тиражируется. В two's complement `-1` это все единицы, сдвиг вправо оставляет все единицы → `-1`. (C++20 зафиксировал арифметический сдвиг для знаковых.)

---

Отличие от Java: там представление **всегда two's complement**, зафиксировано с самого начала (Java Language Spec), для всех целых типов. Никакой implementation-defined неопределённости, как в C++ до C++20. Плюс переполнение в Java — **определённый wraparound** (не UB), поэтому `Integer.MIN_VALUE / -1` в Java даёт `Integer.MIN_VALUE` (заворачивается), а не UB. И `Math.abs(Integer.MIN_VALUE)` в Java возвращает `Integer.MIN_VALUE` (отрицательное!) — тоже следствие асимметрии, но **определённое** поведение, а не UB. Java с самого начала выбрала «фиксированное представление + определённый wraparound» ради простоты и переносимости; C++ выбрал «UB ради оптимизаций» и лишь в C++20 зафиксировал представление, но не поведение переполнения. Для тебя практический вывод: асимметрия `MIN`/`MAX` есть в обоих языках (это свойство two's complement), но в Java она даёт странные-но-определённые результаты, а в C++ — UB, которое надо ловить UBSan.
