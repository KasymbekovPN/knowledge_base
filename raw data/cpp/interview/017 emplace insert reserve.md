# `emplace` vs `insert` / `push_back`, и `reserve`

## `emplace` — конструирование на месте

Ключевая идея: `emplace_*` принимает **аргументы конструктора** и строит объект **прямо в памяти контейнера** (через placement new + perfect forwarding). `push_back`/`insert` принимают **готовый объект** и копируют/перемещают его.

```cpp
struct Point {
    int x_, y_;
    Point(int x, int y) : x_(x), y_(y) { std::cout << "ctor\n"; }
    Point(const Point&) { std::cout << "copy\n"; }
    Point(Point&&) noexcept { std::cout << "move\n"; }
};

std::vector<Point> v;
v.reserve(10);   // чтобы реаллокация не мешала эксперименту

v.push_back(Point(1, 2));   // "ctor" + "move"   — создали временный, потом переместили
v.emplace_back(1, 2);       // "ctor"            — построили сразу в векторе
```

`emplace_back` экономит одно перемещение (или копирование). Реализация — ровно тот perfect forwarding, который мы разбирали:

```cpp
template<class... Args>
void emplace_back(Args&&... args) {
    ::new (end_) T(std::forward<Args>(args)...);   // placement new прямо в память контейнера
    ++end_;
}
```

## Когда выигрыш реален, а когда его нет

**Выигрыш есть, если объект ещё не создан:**

```cpp
v.push_back(Point(1,2));   // ctor + move — лишнее перемещение
v.emplace_back(1, 2);      // ctor        — выигрыш ✅
```

**Выигрыша нет, если объект уже существует:**

```cpp
Point p(1, 2);
v.push_back(p);       // copy
v.emplace_back(p);    // copy — ТО ЖЕ САМОЕ, никакого выигрыша

v.push_back(std::move(p));      // move
v.emplace_back(std::move(p));   // move — тоже одинаково
```

Когда передан готовый объект, `emplace_back` просто форвардит его в copy/move конструктор — точно то же, что делает `push_back`. **`emplace` не магия, а устранение промежуточного временного объекта.**

**Для тривиальных типов разницы нет:**

```cpp
std::vector<int> v;
v.push_back(42);      // move int == copy int == ничего не стоит
v.emplace_back(42);   // то же самое
```

## Важное различие: `explicit` конструкторы

`emplace` использует **прямую инициализацию** (`T(args...)`), а `push_back`/`insert` — **копирующую** (`T x = arg`). Поэтому `emplace` может вызывать `explicit` конструкторы, а `push_back` — нет:

```cpp
struct Widget {
    explicit Widget(int) { }
};

std::vector<Widget> v;
v.push_back(10);      // ❌ ОШИБКА: explicit блокирует неявное преобразование int → Widget
v.emplace_back(10);   // ✅ ОК: прямая инициализация Widget(10)
```

Это одновременно и плюс (удобство), и **риск**: `emplace` обходит защиту, которую `explicit` был призван обеспечить.

```cpp
std::vector<std::unique_ptr<Widget>> v;
v.push_back(new Widget());      // ❌ ОШИБКА (explicit unique_ptr(T*)) — и хорошо!
v.emplace_back(new Widget());   // ✅ компилируется... но ОПАСНО ⚠️
```

Опасность в последней строке: если при реаллокации вектора выбросится `bad_alloc` **после** того, как `new Widget()` уже выполнился, но **до** того, как `unique_ptr` его принял — сырой указатель утечёт. Правильно:

```cpp
v.push_back(std::make_unique<Widget>());      // ✅ безопасно
v.emplace_back(std::make_unique<Widget>());   // ✅ тоже безопасно
```

## Ассоциативные контейнеры — тут тонкостей больше

### `map::emplace` vs `map::insert`

```cpp
std::map<int, std::string> m;

m.insert({1, "one"});               // создаётся pair, потом move в узел
m.emplace(1, "one");                // pair конструируется на месте
m.emplace(std::piecewise_construct,  // сложная форма — для конструирования обоих
          std::forward_as_tuple(1),
          std::forward_as_tuple(5, 'a'));   // value = string(5, 'a')
```

### Ловушка: `emplace` создаёт узел ДО проверки на дубликат

Это важный и неочевидный момент. `map`/`set` не допускают дубликатов ключа. Но `emplace`, чтобы узнать ключ, **должен сначала сконструировать элемент**:

```cpp
std::map<int, ExpensiveObject> m;
m.emplace(1, expensive_args...);   // конструирует узел
m.emplace(1, expensive_args...);   // ⚠️ снова конструирует узел, обнаруживает дубликат,
                                    //    и УНИЧТОЖАЕТ его → работа впустую (аллокация + ctor + dtor)
```

**Решения (C++17):**

```cpp
// try_emplace — конструирует value ТОЛЬКО если ключа ещё нет
m.try_emplace(1, expensive_args...);   // ✅ при дубликате value не конструируется вообще

// insert_or_assign — вставить или перезаписать
m.insert_or_assign(1, value);          // ✅ явная семантика, в отличие от m[1] = value
```

`try_emplace` — почти всегда лучший выбор для `map`. Дополнительный плюс: он **не перемещает** аргументы при неудаче (в отличие от `emplace`, который мог «съесть» перемещённый объект и затем откатиться):

```cpp
std::map<int, std::string> m{{1, "one"}};
std::string s = "value";

m.emplace(1, std::move(s));       // ⚠️ s МОЖЕТ быть перемещён, хотя вставка не произошла!
                                   //    (реализация вправе сконструировать узел до проверки)
m.try_emplace(1, std::move(s));   // ✅ s гарантированно НЕ тронут при существующем ключе
```

### `operator[]` vs `insert` vs `try_emplace`

```cpp
std::map<int, std::string> m;

m[1] = "one";                    // ⚠️ default-конструирует string, потом ПРИСВАИВАЕТ
                                 //    (два шага; требует default-конструируемости value)
m.insert({1, "one"});            // конструирует pair, потом move
m.emplace(1, "one");             // конструирует на месте (но узел до проверки)
m.try_emplace(1, "one");         // ✅ лучшее: на месте, только если нужно
m.insert_or_assign(1, "one");    // вставить или перезаписать
```

Напомню ловушку `operator[]`: он **вставляет** элемент, если ключа нет:

```cpp
std::cout << m[42];   // ⚠️ вставил {42, ""}! size вырос
if (auto it = m.find(42); it != m.end()) { }   // ✅ для чтения
```

## Практический вердикт по emplace

- **Используй `emplace_back`/`emplace` по умолчанию** — не хуже, часто лучше
- **Выигрыш только когда объект строится из аргументов** (не когда передаёшь готовый)
- **Осторожно с `explicit`** — `emplace` обходит эту защиту (`emplace_back(new T)` компилируется, но небезопасен)
- **Для `map` предпочитай `try_emplace`** (C++17) — избегает лишнего конструирования и не «съедает» перемещённые аргументы
- Многие проекты всё равно пишут `push_back` для читаемости, когда выигрыш нулевой (`vector<int>`), — это нормально

## `reserve` — предварительное выделение

### vector

```cpp
std::vector<int> v;
v.reserve(1000);   // выделяет память под 1000 элементов, size остаётся 0
v.size();          // 0
v.capacity();      // >= 1000
```

**Зачем:** устранить реаллокации.

```cpp
// без reserve: ~10 реаллокаций, суммарно ~2000 перемещений
std::vector<Widget> v;
for (int i = 0; i < 1000; ++i) v.push_back(Widget());

// с reserve: одна аллокация, ноль перемещений
std::vector<Widget> v;
v.reserve(1000);   // ✅
for (int i = 0; i < 1000; ++i) v.push_back(Widget());
```

Для дорогих в перемещении типов выигрыш существенный. Плюс — **предсказуемость** (нет неожиданных пауз на реаллокацию).

### `reserve` vs `resize` — частая путаница

```cpp
std::vector<int> v;

v.reserve(10);   // capacity >= 10, size == 0 — ЭЛЕМЕНТОВ НЕТ
v[0] = 1;        // ⚠️ UB! элемента нет, только сырая память
v.push_back(1);  // ✅ правильно

v.resize(10);    // size == 10 — элементы СОЗДАНЫ (default-инициализированы нулями для int)
v[0] = 1;        // ✅ элемент существует
```

| |`reserve(n)`|`resize(n)`|
|---|---|---|
|`size()`|не меняет|становится `n`|
|`capacity()`|≥ n|≥ n|
|элементы|**не создаются**|**создаются** (default)|
|доступ `v[i]`|UB|✅ валиден|

Типичный баг:

```cpp
std::vector<int> v;
v.reserve(10);
for (int i = 0; i < 10; ++i) v[i] = i;   // ⚠️ UB! элементов нет
                                          //    (часто «работает», память-то выделена — тем хуже)
```

### `reserve` и инвалидация

```cpp
std::vector<int> v{1,2,3};
int* p = &v[0];
v.reserve(100);   // ⚠️ реаллокация → p ИНВАЛИДИРОВАН
```

`reserve` сам по себе — реаллокация (если capacity растёт), поэтому инвалидирует всё. Делай его **до** того, как берёшь указатели/итераторы.

Обратная сторона: **после `reserve(n)` первые n `push_back` гарантированно не инвалидируют** ничего:

```cpp
std::vector<int> v;
v.reserve(1000);
v.push_back(1);
int* p = &v[0];
for (int i = 1; i < 1000; ++i) v.push_back(i);   // ✅ реаллокаций нет → p валиден
```

Хрупко (стоит превысить 1000 — и всё сломается), но в горячем коде так делают.

### `shrink_to_fit`

```cpp
v.shrink_to_fit();   // просьба уменьшить capacity до size — НЕ ОБЯЗАТЕЛЬНА к исполнению
                     // ⚠️ может реаллоцировать → инвалидирует всё
```

Строго говоря — необязывающий запрос (non-binding request). Реализация вправе его проигнорировать. Гарантированный способ — swap-идиома (до C++11 это был единственный вариант):

```cpp
std::vector<int>(v).swap(v);   // создаём копию с точной capacity, свопаем
```

### `reserve` у `unordered_map`

Тоже есть, и очень полезен — устраняет rehash'и:

```cpp
std::unordered_map<int, int> m;
m.reserve(1000);   // выделяет достаточно бакетов, чтобы 1000 элементов не вызвали rehash
```

Формально `reserve(n)` ≈ `rehash(ceil(n / max_load_factor()))`.

### У кого `reserve` НЕТ

`map`, `set`, `list`, `deque` — узловые контейнеры, каждый элемент аллоцируется отдельно, резервировать нечего. (Оптимизировать их аллокации можно только кастомным аллокатором / пулом.)

```cpp
std::map<int,int> m;
m.reserve(100);   // ❌ ошибка компиляции — метода нет
```

### `string::reserve`

Работает так же, как у vector. Полезен при конкатенации в цикле:

```cpp
std::string s;
s.reserve(10000);   // ✅ избегаем множественных реаллокаций
for (...) s += chunk;
```

## Формулировки на собеседовании

**«В чём разница `emplace_back` и `push_back`?»** — `emplace_back` принимает аргументы конструктора и строит объект **на месте** в памяти контейнера (placement new + perfect forwarding); `push_back` принимает готовый объект и копирует/перемещает его. Выигрыш — одно устранённое перемещение, но **только** когда объект строится из аргументов.

**«Всегда ли `emplace_back` быстрее?»** — Нет. Если передан уже существующий объект (`emplace_back(p)`), это ровно то же копирование/перемещение, что и `push_back`. Для тривиальных типов разницы нет.

**«Чем `emplace` опасен?»** — Использует прямую инициализацию → обходит `explicit`-конструкторы. `v.emplace_back(new Widget())` для `vector<unique_ptr<Widget>>` компилируется (в отличие от `push_back`), но может утечь при исключении в реаллокации.

**«Почему `try_emplace` лучше `emplace` для map?»** — `emplace` конструирует узел **до** проверки на дубликат: при существующем ключе узел создаётся и тут же уничтожается (лишняя аллокация + ctor + dtor), и перемещённые аргументы могут быть «съедены». `try_emplace` конструирует value только если ключа нет.

**«Разница `reserve` и `resize`?»** — `reserve` меняет только capacity (элементы **не создаются**, `size` не меняется, `v[i]` — UB). `resize` меняет `size` (элементы создаются/удаляются).

**«Инвалидирует ли `reserve` итераторы?»** — Да, если capacity растёт — это реаллокация, инвалидируется всё. Но после `reserve(n)` последующие `push_back` до n элементов гарантированно ничего не инвалидируют.

**«Есть ли `reserve` у `map`?»** — Нет: узловой контейнер, элементы аллоцируются по одному. Есть у `vector`, `string`, `unordered_*`.

---

Отличие от Java: `ArrayList` имеет `ensureCapacity()` — прямой аналог `reserve`. Аналога `emplace` нет и быть не может: в Java объект **всегда** создаётся отдельно на heap, а в коллекцию кладётся **ссылка** — копирования объекта не происходит вовсе, поэтому «конструировать на месте» нечего оптимизировать. Вся проблематика emplace/push_back существует именно потому, что C++ контейнеры хранят объекты **по значению**, и мы боремся за устранение лишних копий/перемещений. Ровно та же причина, по которой в C++ вообще существует move-семантика.
