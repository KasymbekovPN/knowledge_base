# UB: нарушение порядка вычислений (evaluation order)

## Суть

В C++ порядок вычисления **подвыражений** внутри одного выражения в большинстве случаев **не определён** (unspecified), а модификация одного объекта дважды без «точки упорядочивания» между ними — **UB**.

```cpp
int i = 0;
int x = i++ + i++;   // ⚠️ UB (до C++17) — i модифицируется дважды без упорядочивания
```

Это отличается от предыдущих UB: тут проблема не в памяти, а в том, что компилятор волен вычислять части выражения в **любом порядке**, и код, полагающийся на конкретный порядок, ломается.

---

## Терминология: sequenced-before

C++11 заменил старое понятие «sequence points» на **sequenced-before** — отношение упорядочивания между вычислениями.

- **A sequenced-before B** — A полностью вычисляется (включая побочные эффекты) до B
- **unsequenced** — порядок A и B не определён, могут даже чередоваться
- **indeterminately sequenced** — либо A перед B, либо B перед A (но не чередуются) — например, вычисление аргументов функции

**Правило UB:** если два **побочных эффекта** на одном скалярном объекте **unsequenced** → UB. Если побочный эффект и чтение того же объекта unsequenced → UB.

---

## Категории

### 1. Множественная модификация одного объекта

```cpp
int i = 0;

i = i++ + 1;         // ⚠️ UB до C++17
i = ++i + i++;       // ⚠️ UB
a[i] = i++;          // ⚠️ UB — чтение i (в a[i]) и модификация i (i++) unsequenced
i++ * i++;           // ⚠️ UB
```

Компилятор может выполнить модификации в любом порядке или «смешать» их → результат непредсказуем.

### 2. Порядок вычисления аргументов функции — UNSPECIFIED (не UB, но опасно)

```cpp
void f(int a, int b);

int i = 0;
f(i++, i++);         // ⚠️ порядок вычисления аргументов НЕ определён
                     //    может быть f(0, 1) или f(1, 0)
                     //    (до C++17 это ещё и UB — модификации unsequenced)
```

Аргументы **indeterminately sequenced** относительно друг друга: компилятор вычисляет их в любом порядке, но не чередует. До C++17 модификация `i` дважды — UB; с C++17 — определённый, но **unspecified** порядок (либо `f(0,1)`, либо `f(1,0)`, зависит от компилятора).

```cpp
// Реальный баг:
std::cout << i++ << i++;   // ⚠️ порядок не определён — какой инкремент первый?
```

### 3. Порядок вычисления операндов бинарных операторов

```cpp
int f();
int g();

int x = f() + g();   // ⚠️ порядок вызова f() и g() НЕ определён!
```

Для большинства операторов (`+`, `-`, `*`, `/`, `<`, `,` в списке аргументов) порядок операндов **не специфицирован**. Если `f()` и `g()` имеют побочные эффекты, зависящие друг от друга — баг.

**Исключения** — операторы с гарантированным порядком (см. ниже).

### 4. Взаимодействие модификации и чтения

```cpp
int i = 5;
int arr[10];
arr[i] = i++;        // ⚠️ UB до C++17: i++ модифицирует i, arr[i] читает i — unsequenced

int x = i + i++;     // ⚠️ UB до C++17
```

---

## Операторы с ГАРАНТИРОВАННЫМ порядком

Не всё unsequenced. Эти операторы **упорядочивают** левый операнд перед правым:

```cpp
&&    // левый вычисляется первым; правый — только если левый true (short-circuit)
||    // левый первым; правый — только если левый false
,     // (оператор запятая) левый первым, потом правый
?:    // условие первым, потом выбранная ветвь
```

```cpp
if (p != nullptr && p->value > 0) { }   // ✅ p != nullptr вычисляется ПЕРВЫМ
                                         //    p->value только если p != nullptr — безопасно

int x = (a(), b());   // ✅ a() перед b() — оператор запятая упорядочивает
```

**Внимание:** это про **оператор** запятая, не про запятые-разделители аргументов:

```cpp
f(a(), b());          // ⚠️ запятая-РАЗДЕЛИТЕЛЬ — порядок a() и b() НЕ определён
int x = (a(), b());   // ✅ оператор ЗАПЯТАЯ — a() перед b()
```

---

## Что изменил C++17 (P0145)

C++17 добавил гарантии порядка для ряда операторов, убрав часть UB:

### 1. `a = b` — правая часть вычисляется до левой

```cpp
// C++17:
i = i++ + 1;         // ✅ теперь определено (было UB)
a[i] = i++;          // ✅ определено (было UB)
```

### 2. Постфикс/операторы — операнды упорядочены

```cpp
// C++17: для этих операторов левый операнд sequenced-before правый:
a[b]        // a перед b
a.b, a->b
a << b, a >> b   // ← важно для потоков!
a = b, a += b и т.д.
```

```cpp
// C++17: определённый порядок для потоков
std::cout << f() << g();   // ✅ C++17: f() перед g() (было unspecified)
                           //    (порядок ВЫВОДА был правильным всегда, но ВЫЧИСЛЕНИЯ — нет)
```

### 3. Что C++17 НЕ исправил

**Порядок вычисления аргументов функции остался unspecified:**

```cpp
f(i++, i++);         // C++17: больше НЕ UB, но порядок по-прежнему НЕ определён
                     //    может быть f(0,1) или f(1,0)
std::cout << i++ << i++;   // ✅ не UB, но какой инкремент первый — unspecified
```

**Порядок операндов `+`, `-`, `*` и т.д. остался unspecified:**

```cpp
int x = f() + g();   // C++17: порядок f() и g() ВСЁ ЕЩЁ не определён
```

Итог C++17: убрал UB для присваивания и ряда операторов, но **не сделал** порядок аргументов/арифметики детерминированным.

## Классический коварный пример: параметры и владение

```cpp
void process(std::shared_ptr<Widget> w, int priority);
int computePriority();

// ⚠️ ОПАСНО (до C++17 — потенциальная УТЕЧКА)
process(std::shared_ptr<Widget>(new Widget), computePriority());
```

Мы разбирали это в теме `make_shared`. Возможная последовательность (до C++17):

1. `new Widget` — объект создан
2. `computePriority()` — **бросает исключение**
3. `shared_ptr` не сконструирован → сырой `Widget` утёк

Порядок вычисления аргументов не определён, и части могут **чередоваться** (до C++17). Решение — `std::make_shared`:

```cpp
process(std::make_shared<Widget>(), computePriority());   // ✅ new и захват атомарны
```

C++17 запретил чередование (аргументы теперь indeterminately sequenced, не unsequenced) → утечка невозможна даже с сырым `new`. Но `make_shared` всё равно лучше (одна аллокация).

## Типичные баги

### 1. Инкремент в вызове/выражении

```cpp
arr[i] = i++;                    // ⚠️ UB до C++17
v[i] = v[i++];                   // ⚠️
int x = i++ + ++i;               // ⚠️ UB (i модифицируется дважды unsequenced)
```

### 2. Зависимые побочные эффекты в аргументах

```cpp
std::string s = "abc";
replace(s.begin(), s.end(), s.front(), 'x');   // ⚠️ порядок вычисления аргументов
                                                //    s.front() может вычислиться после begin/end
```

### 3. Одна переменная в нескольких аргументах с побочными эффектами

```cpp
int next() { static int n = 0; return n++; }

point p(next(), next());   // ⚠️ какая координата получит 0, какая 1? unspecified!
```

### 4. Присваивание в условии + использование

```cpp
int i = 0;
a[i] = i = 2;   // ⚠️ i модифицируется (=2) и читается (a[i]) — до C++17 UB
```

### 5. Функция, вызванная дважды с общим состоянием

```cpp
std::cout << readLine() << readLine();   // ⚠️ какая строка первая? unspecified
                                          //    (не UB, но порядок ЧТЕНИЯ из файла не гарантирован)
```

---

## Как избегать

**1. Одна модификация объекта на выражение:**

```cpp
// ❌
arr[i] = i++;

// ✅ разбить на два statement (между ними — полное упорядочивание)
arr[i] = i;
i++;
```

Между **statements** (`;`) всегда есть полное упорядочивание (sequenced-before) — разбиение решает проблему.

**2. Не полагаться на порядок вычисления аргументов:**

```cpp
// ❌
f(next(), next());

// ✅ явный порядок через переменные
int a = next();
int b = next();
f(a, b);
```

**3. Использовать фабрики вместо сырого `new` в аргументах:**

```cpp
process(std::make_shared<Widget>(), computePriority());   // ✅
```

**4. Не смешивать модификацию и чтение в одном выражении.**

## Обнаружение

```bash
g++ -Wall -Wsequence-point prog.cpp    # предупреждения о UB порядка вычисления
clang++ -Wunsequenced prog.cpp          # Clang — более точные предупреждения
```

`-Wsequence-point` (GCC) / `-Wunsequenced` (Clang) ловят классические случаи (`i = i++`, `arr[i] = i++`). Но **не все** — межпроцедурные зависимости (побочные эффекты в `f()` и `g()`) компилятор не видит.

UBSan **не ловит** unspecified порядок (это не UB, а неопределённость реализации). Ловит только настоящие UB (двойная модификация до C++17), и то не всегда.

---

## Формулировки на собеседовании

**«Определён ли порядок вычисления аргументов функции?»** — **Нет**, unspecified. Компилятор вычисляет в любом порядке (но не чередует — indeterminately sequenced). `f(i++, i++)` может дать `f(0,1)` или `f(1,0)`. До C++17 это ещё и UB (двойная модификация).

**«Почему `i = i++ + 1` — UB?»** — До C++17: `i` модифицируется дважды (`i++` и `=`) без упорядочивания между ними → unsequenced side effects → UB. C++17 исправил (присваивание теперь упорядочивает правую часть до левой).

**«Какие операторы гарантируют порядок?»** — `&&`, `||`, `,` (оператор), `?:` — левый операнд перед правым (+ short-circuit для `&&`/`||`). С C++17 — также `=`, `[]`, `<<`, `>>`, `.`, `->` (левый перед правым).

**«Что изменил C++17?»** — Добавил упорядочивание для присваивания, индексации, сдвигов (`<<` — важно для потоков) → убрал часть UB. Но порядок **аргументов функции** и **операндов арифметики** (`+`, `*`) остался unspecified.

**«Почему `process(shared_ptr<Widget>(new Widget), f())` опасно?»** — До C++17 части могли чередоваться: `new Widget` выполнен, `f()` бросил, `shared_ptr` не сконструирован → утечка. Решение — `make_shared`. C++17 запретил чередование, но `make_shared` всё равно предпочтителен.

**«В чём разница оператора запятая и запятой-разделителя?»** — Оператор `,` (`(a(), b())`) упорядочивает левое перед правым. Запятая-разделитель аргументов (`f(a(), b())`) — **не** упорядочивает, порядок не определён.

---

Отличие от Java: там порядок вычисления **строго определён — слева направо**, всегда. `f(i++, i++)` в Java гарантированно вызывает `f(0, 1)`; `a + b` вычисляет `a` перед `b`; аргументы вычисляются слева направо. Никакого unspecified, никакого UB. Java пожертвовала свободой оптимизатора ради **предсказуемости и переносимости** — код ведёт себя одинаково на любой JVM. C++ оставил порядок неопределённым, чтобы дать компилятору свободу генерировать оптимальный код под конкретную архитектуру (например, вычислять аргументы в порядке, удобном для регистров/стека). Практический вывод для тебя: Java-привычка «всё слева направо» в C++ **опасна** — `std::cout << i++ << i++` и `f(next(), next())` дают неопределённый порядок. Пиши так, чтобы результат не зависел от порядка вычисления подвыражений, либо разбивай на отдельные statements.
