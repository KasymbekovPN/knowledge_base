## Что такое инвалидация

Итератор (или указатель/ссылка на элемент) становится **невалидным** — любое его использование даёт **UB**. Причины две:

1. **Память переехала** — элементы физически перемещены в другой адрес (реаллокация vector)
2. **Элемент удалён** — объект, на который указывали, разрушен

Ключевой момент: инвалидированный итератор внешне выглядит нормально. Компилятор не предупредит, программа может «работать» — до тех пор, пока не сломается в непредсказуемом месте.

---

## Три разных уровня — важно различать

Не путать: инвалидация **итераторов** и инвалидация **ссылок/указателей** — **разные вещи**.

```cpp
std::deque<int> d{1,2,3};
int* p = &d[0];              // указатель на элемент
auto it = d.begin();         // итератор

d.push_front(0);
// it — ИНВАЛИДИРОВАН
// p  — ВАЛИДЕН! (элемент не перемещался)
```

Почему: итератор `deque` хранит внутреннее состояние навигации (текущий чанк, позиция в карте чанков), которое перестраивается при добавлении чанка. А сам элемент остался в том же чанке по тому же адресу.

Аналогично в `unordered_map` при rehash: узлы цепочек не перемещаются (переставляются только указатели) → ссылки живы, а итераторы (зависящие от структуры бакетов) — нет.

## Полная таблица

### `vector`

|Операция|Итераторы|Ссылки/указатели|
|---|---|---|
|`push_back` **с** реаллокацией|❌ ВСЕ|❌ ВСЕ|
|`push_back` **без** реаллокации|❌ только `end()`|✅ валидны|
|`insert(pos, ...)`|❌ от `pos` до конца (все, если реаллокация)|❌ так же|
|`erase(pos)`|❌ от `pos` до конца|❌ так же|
|`pop_back`|❌ только на удалённый и `end()`|❌ только на удалённый|
|`reserve` / `resize` (рост capacity)|❌ ВСЕ|❌ ВСЕ|
|`clear`|❌ ВСЕ|❌ ВСЕ|
|`shrink_to_fit`|❌ ВСЕ (может реаллоцировать)|❌ ВСЕ|
|чтение (`operator[]`, `at`, обход)|✅|✅|

**Правило vector: любое изменение capacity → всё умерло.**

### `deque`

|Операция|Итераторы|Ссылки/указатели|
|---|---|---|
|`push_front` / `push_back`|❌ ВСЕ|✅ **ВАЛИДНЫ**|
|`pop_front` / `pop_back`|❌ только на удалённый|❌ только на удалённый|
|`insert`/`erase` в **середину**|❌ ВСЕ|❌ ВСЕ|
|`clear`|❌ ВСЕ|❌ ВСЕ|

Уникальная особенность deque — ссылки переживают вставку в концы.

### `list` / `forward_list`

|Операция|Итераторы|Ссылки/указатели|
|---|---|---|
|`insert` (любая позиция)|✅ **ВСЕ ВАЛИДНЫ**|✅ ВСЕ|
|`erase`|❌ только на удалённый|❌ только на удалённый|
|`splice`|✅ валидны (переносятся с узлами!)|✅|
|`push_front`/`push_back`|✅|✅|

Максимальная стабильность: узлы — независимые аллокации, никогда не перемещаются. Это главное (и часто единственное) преимущество `list`.

### `map` / `set` / `multimap` / `multiset` (RB-tree)

|Операция|Итераторы|Ссылки/указатели|
|---|---|---|
|`insert` / `emplace`|✅ **ВСЕ ВАЛИДНЫ**|✅ ВСЕ|
|`erase`|❌ только на удалённый|❌ только на удалённый|
|`clear`|❌ ВСЕ|❌ ВСЕ|

Балансировка дерева **переставляет указатели** между узлами, но сами узлы (с данными) не перемещаются в памяти. Поэтому повороты RB-дерева ничего не инвалидируют — очень удобное свойство.

### `unordered_map` / `unordered_set`

|Операция|Итераторы|Ссылки/указатели|
|---|---|---|
|`insert` **с** rehash|❌ ВСЕ|✅ **ВАЛИДНЫ**|
|`insert` **без** rehash|✅ валидны|✅ валидны|
|`erase`|❌ только на удалённый|❌ только на удалённый|
|`rehash` / `reserve`|❌ ВСЕ|✅ ВАЛИДНЫ|

Опять: rehash перераспределяет узлы по бакетам (меняет указатели `next`), но узлы не перемещаются → ссылки живут.

### `array`

Ничего не инвалидируется — размер фиксирован, ничего не перемещается.

---

## Сводное правило (то, что стоит запомнить)

**Узловые контейнеры** (`list`, `map`, `set`, `unordered_*`) — узлы аллоцированы отдельно и **не перемещаются** → ссылки/указатели умирают только вместе со своим элементом.

**Непрерывные контейнеры** (`vector`, `string`) — элементы в одном блоке → **любая реаллокация убивает всё**.

**`deque`** — гибрид: чанки не перемещаются (ссылки живут при вставке в концы), но навигация перестраивается (итераторы умирают).

## Типичные баги

### 1. Указатель на элемент вектора

```cpp
std::vector<int> v{1, 2, 3};
int* p = &v[0];
v.push_back(4);      // ⚠️ реаллокация
*p = 10;             // ⚠️ UB — use-after-free
```

То же со ссылками и итераторами. Самая частая ошибка вообще.

### 2. Удаление в цикле — классика

```cpp
std::vector<int> v{1,2,3,4,5};

// ❌ НЕПРАВИЛЬНО
for (auto it = v.begin(); it != v.end(); ++it) {
    if (*it % 2 == 0) v.erase(it);   // it инвалидирован! ++it → UB
}

// ✅ ПРАВИЛЬНО — erase возвращает итератор на следующий элемент
for (auto it = v.begin(); it != v.end(); ) {
    if (*it % 2 == 0) it = v.erase(it);   // переприсваиваем
    else ++it;
}
```

**Для узловых контейнеров** та же проблема (итератор на удалённый элемент невалиден), решается так же:

```cpp
std::map<int, int> m;
for (auto it = m.begin(); it != m.end(); ) {
    if (cond(*it)) it = m.erase(it);   // ✅ erase возвращает следующий (C++11)
    else ++it;
}

// или классический пост-инкремент (работает и до C++11):
for (auto it = m.begin(); it != m.end(); ) {
    if (cond(*it)) m.erase(it++);   // it++ возвращает КОПИЮ (старую позицию),
    else ++it;                       // а сам it уже сдвинут → безопасно
}
```

**Идиоматично для vector — erase-remove:**

```cpp
v.erase(std::remove_if(v.begin(), v.end(), [](int x){ return x % 2 == 0; }), v.end());
// C++20:
std::erase_if(v, [](int x){ return x % 2 == 0; });   // ✅ короче и понятнее
```

### 3. Сохранённый `end()`

```cpp
std::vector<int> v{1,2,3};
auto end = v.end();          // сохранили
v.push_back(4);              // ⚠️ end инвалидирован (даже без реаллокации!)

for (auto it = v.begin(); it != end; ++it) { }   // ⚠️ UB
```

`end()` инвалидируется **всегда** при `push_back`, даже если реаллокации не было (`end()` сдвинулся). Никогда не кешируй `end()` через модификации.

### 4. Range-for + модификация

```cpp
std::vector<int> v{1,2,3};
for (int x : v) {
    v.push_back(x);   // ⚠️ UB! range-for использует итераторы, реаллокация их убьёт
}                      //     плюс бесконечный цикл по логике
```

Range-for разворачивается в цикл на итераторах — те же правила.

### 5. Ссылка из `map::operator[]` + вставка

```cpp
std::map<int, std::string> m;
auto& ref = m[1];
m[2] = "two";        // ✅ ОК для map — узлы не перемещаются, ref валидна
ref = "one";         // ✅

std::unordered_map<int, std::string> um;
auto& uref = um[1];
um.reserve(1000);    // rehash
uref = "one";        // ✅ ОК! ссылки переживают rehash
auto it = um.begin();
um[2] = "two";       // ⚠️ если был rehash — it мёртв
```

Иллюстрация того, что ссылки и итераторы ведут себя по-разному.

### 6. Инвалидация при `insert` в середину vector

```cpp
std::vector<int> v{1,2,3,4,5};
auto it = v.begin() + 3;   // указывает на 4
v.insert(v.begin() + 1, 99);   // ⚠️ it инвалидирован (позиция после точки вставки)
*it;   // UB
```

## Как защищаться

**1. Не храни итераторы/указатели через модификации.** Самое простое и надёжное правило.

**2. `reserve` заранее** — если знаешь размер, реаллокаций не будет:

```cpp
std::vector<int> v;
v.reserve(1000);
int* p = &v[0];
for (int i = 0; i < 1000; ++i) v.push_back(i);   // ✅ реаллокаций нет → p валиден
```

Но это хрупко: стоит превысить capacity — и всё ломается. Так делают только в оптимизированном коде с чёткой гарантией.

**3. Используй индексы вместо итераторов** для vector, если контейнер модифицируется:

```cpp
for (size_t i = 0; i < v.size(); ++i) {   // индекс переживает реаллокацию
    if (cond(v[i])) v.push_back(v[i]);    // v.size() перечитывается каждый раз
}
```

**4. Стабильность через узловые контейнеры** — если абсолютно нужны долгоживущие указатели на элементы, `std::list` / `std::map` / `std::deque` (для ссылок) дают гарантии.

**5. Уровень косвенности** — `vector<unique_ptr<T>>`: сам вектор реаллоцируется (перемещаются указатели), но **объекты T не переезжают**:

```cpp
std::vector<std::unique_ptr<Widget>> v;
v.push_back(std::make_unique<Widget>());
Widget* p = v[0].get();
v.push_back(std::make_unique<Widget>());   // реаллокация вектора
p->use();   // ✅ ВАЛИДЕН! сам Widget на heap, не перемещался
```

Частая идиома, когда нужны и производительность vector, и стабильные адреса.

**6. Sanitizers** — ASan ловит use-after-free от инвалидации в рантайме:

```bash
g++ -fsanitize=address -g prog.cpp
```

GCC/libstdc++ дополнительно имеет **debug-режим** контейнеров (`-D_GLIBCXX_DEBUG`), который ловит использование инвалидированных итераторов явно, с понятным сообщением. Очень рекомендую включать в debug-сборках.

## Формулировки на собеседовании

**«Что инвалидирует итераторы vector?»** — Любая реаллокация (`push_back` при заполненной capacity, `reserve`, `resize`, `shrink_to_fit`) → все итераторы, указатели и ссылки. `insert`/`erase` → всё от точки изменения до конца. `push_back` без реаллокации → только `end()`.

**«Инвалидируются ли итераторы map при вставке?»** — Нет. RB-дерево при балансировке переставляет **указатели** между узлами, но сами узлы не перемещаются в памяти. Инвалидируется только итератор на удалённый элемент при `erase`.

**«Что происходит при rehash в unordered_map?»** — **Итераторы** инвалидируются (структура бакетов перестроена), **ссылки и указатели остаются валидными** (узлы цепочек не перемещаются).

**«Как правильно удалять в цикле?»** — `erase` возвращает итератор на следующий элемент: `it = c.erase(it);`. Для vector идиоматичнее erase-remove или `std::erase_if` (C++20).

**«Чем отличается инвалидация итераторов от инвалидации ссылок?»** — Итератор может зависеть от внутренней структуры навигации (чанки deque, бакеты unordered_map), которая перестраивается без перемещения самих элементов. Тогда итератор умирает, а ссылка на элемент — нет.

**«Как получить стабильные адреса при использовании vector?»** — `vector<unique_ptr<T>>`: реаллокация перемещает указатели, но не сами объекты.

---

Отличие от Java: там итераторы **fail-fast** — при модификации коллекции во время итерации бросается `ConcurrentModificationException` (через `modCount`). Это не безопасность памяти (GC гарантирует, что объект жив), а защита от логической ошибки — и она **детектируется в рантайме явно**. В C++ инвалидация — это чистый **UB**: никаких исключений, программа может «работать», а может тихо портить память. Отсюда практический вывод: то, что в Java даёт понятный exception, в C++ даёт use-after-free — поэтому дисциплина и sanitizers обязательны.
