# ABI (Application Binary Interface)

## Что это

**ABI** — контракт на **бинарном** уровне: как скомпилированный код взаимодействует с другим скомпилированным кодом (без пересборки). Если API — это контракт на уровне исходников (какие функции есть, какие сигнатуры), то ABI — на уровне машинного кода.

Аналогия:

- **API** совместимость → код **компилируется** с новой версией
- **ABI** совместимость → уже **скомпилированный** бинарник работает с новой версией **без перекомпиляции**

```cpp
// API-совместимо: старый исходник компилируется с новой библиотекой
// ABI-совместимо: старый .exe линкуется со новой .so БЕЗ пересборки
```

---

## Что входит в ABI

Всё, что должно совпадать между раздельно скомпилированными частями:

### 1. Layout структур/классов

Размер, выравнивание, смещения полей:

```cpp
struct Point {
    int x;      // offset 0
    int y;      // offset 4
};              // sizeof == 8

// если клиент скомпилирован с этим layout, а библиотека — с добавленным полем:
struct Point {
    int x;      // offset 0
    int z;      // offset 4  ← ВСТАВИЛИ
    int y;      // offset 8  ← СДВИНУЛСЯ!
};
// ⚠️ клиент читает y по offset 4 → получает z → БИНАРНАЯ несовместимость
```

### 2. Calling convention (соглашение о вызовах)

Как передаются аргументы и возвращается значение:

- через регистры или стек
- порядок аргументов
- кто чистит стек (caller/callee)
- где возвращается результат (регистр `rax`/`xmm0`)

На x86-64 Linux — System V AMD64 ABI; на Windows — Microsoft x64. **Разные** → нельзя линковать код, скомпилированный под разные соглашения.

### 3. Name mangling

C++ кодирует имена функций с типами параметров (для перегрузки):

```cpp
void f(int);         // _Z1fi     (Itanium ABI, GCC/Clang)
void f(double);      // _Z1fd
void f(int, char);   // _Z1fic
```

Если mangling различается между компиляторами (исторически GCC vs MSVC) → символы не находятся при линковке.

### 4. Vtable layout

Для полиморфных классов — порядок виртуальных функций в vtable, расположение vptr (мы разбирали vtable):

```cpp
class Base {
    virtual void a();   // slot 0
    virtual void b();   // slot 1
};
// добавили virtual в СЕРЕДИНУ → сдвинулись слоты → клиент зовёт не ту функцию
```

### 5. Exception handling, RTTI, размеры типов

Механизм раскрутки стека, `type_info` layout, `sizeof(long)` (различается 32/64-bit, Windows/Linux).

---

## Почему C++ ABI хрупкий

C++ ABI **гораздо** более хрупкий, чем C. Причины:

### 1. Классы раскрывают layout

Приватные члены — часть ABI (мы это разбирали в pImpl):

```cpp
// v1.0 библиотеки
class Widget {
    int value_;         // sizeof == 4
public:
    void process();
};

// v1.1 — добавили приватное поле
class Widget {
    int value_;
    std::string name_;  // ⚠️ sizeof изменился!
public:
    void process();
};
```

Клиент, скомпилированный с v1.0, создаёт `Widget` размером 4 байта. Библиотека v1.1 ожидает больший объект → **при вызове методов — порча памяти, краши**.

Даже **добавление приватного поля** ломает ABI. Это фундаментально: в C++ размер класса виден в заголовке и «зашивается» в клиентский код.

### 2. Inline-функции зашиваются в клиента

```cpp
// header
inline int getValue() { return value_; }   // ⚠️ тело ВСТРАИВАЕТСЯ в клиента
```

Клиент компилирует тело inline-функции в свой код. Изменил тело в новой версии → клиент всё равно использует **старое** (уже встроенное) → нужна перекомпиляция.

### 3. Шаблоны инстанцируются в клиенте

`std::vector<int>` инстанцируется в клиентском коде. Если библиотека изменит внутреннее устройство `vector` — несовместимость. Поэтому передавать STL-типы через границы .so опасно, если версии stdlib различаются.

### 4. Всё, что в заголовке, — часть контракта

Заголовок раскрывает layout, inline-код, шаблоны, дефолтные аргументы — всё это компилируется в клиента.

## Что ЛОМАЕТ ABI (breaking changes)

```cpp
// ⚠️ ВСЕ эти изменения ломают ABI:

// 1. Добавление/удаление/переупорядочивание НЕстатических членов
class Widget { int a; int b; };  →  class Widget { int a; int c; int b; };

// 2. Изменение типа члена
int value_;  →  int64_t value_;

// 3. Добавление/удаление/переупорядочивание virtual функций
virtual void a(); virtual void b();  →  virtual void a(); virtual void x(); virtual void b();

// 4. Изменение базовых классов
class Widget {};  →  class Widget : public Base {};

// 5. Изменение сигнатуры функции (mangled name меняется)
void f(int);  →  void f(long);

// 6. Изменение возвращаемого типа
int getValue();  →  int64_t getValue();

// 7. Добавление членов с виртуальностью в невиртуальный класс (появляется vptr!)
class Widget { int x; };  →  class Widget { virtual ~Widget(); int x; };  // +vptr → sizeof вырос

// 8. Изменение inline-функции (если клиент её встроил)

// 9. Изменение default-аргументов (они зашиваются в call site клиента!)
void f(int x = 10);  →  void f(int x = 20);   // клиенты со старым дефолтом → 10
```

## Что НЕ ломает ABI (safe changes)

```cpp
// ✅ безопасные изменения:

// 1. Добавление НОВЫХ невиртуальных функций
class Widget {
    void process();
    void newMethod();   // ✅ не меняет layout, не трогает vtable
};

// 2. Добавление virtual функции В КОНЕЦ (осторожно — не всегда безопасно при наследовании)
//    добавление в конец vtable без наследников — обычно ОК

// 3. Изменение тела НЕ-inline функции (она в .cpp)
void Widget::process() { /* новая реализация */ }   // ✅ клиент не пересобирается

// 4. Добавление static членов/функций
static int counter_;   // ✅ не влияет на layout объекта

// 5. Переименование приватных членов (если не inline-доступ)
```

## Как обеспечивать ABI-стабильность

### 1. pImpl — главный инструмент

Мы разбирали подробно. Прячет layout за указателем → `sizeof` класса не меняется никогда:

```cpp
// widget.h — ABI-стабилен
class Widget {
public:
    Widget();
    ~Widget();
    void process();          // не-inline, определён в .cpp
private:
    class Impl;
    std::unique_ptr<Impl> pImpl_;   // sizeof(Widget) == sizeof(ptr), ВСЕГДА
};
```

Что бы ни добавляли в `Impl` — клиенты не пересобираются. Именно так Qt держит ABI между минорными версиями.

### 2. Абстрактные интерфейсы (pure virtual)

```cpp
// api.h — только чистый интерфейс
class IWidget {
public:
    virtual ~IWidget() = default;
    virtual void process() = 0;
    virtual int getValue() const = 0;
};

IWidget* createWidget();   // фабрика

// реализация — полностью в .so, скрыта
```

Клиент работает через указатель на интерфейс, не зная layout реализации. Добавление новых методов — **только в конец** (иначе сдвиг vtable).

### 3. C-интерфейс для стабильной границы (extern "C")

C ABI **гораздо стабильнее** C++ (нет mangling, vtable, layout классов). Библиотеки с максимальной совместимостью экспортируют C-API:

```cpp
extern "C" {
    Widget* widget_create();
    void widget_destroy(Widget* w);
    void widget_process(Widget* w);
    int widget_get_value(Widget* w);
}
```

`extern "C"` отключает name mangling → символы называются просто `widget_create` → линкуются из любого компилятора/языка. Так устроены системные библиотеки, драйверы, языковые FFI (Python ctypes, Rust FFI, etc.).

Плата — теряешь C++ удобства (классы, перегрузку, RAII на границе), опускаешься до указателей и функций.

### 4. Версионирование

**Semantic versioning + SONAME:**

```
libfoo.so.1.2.3
         │ │ └ patch — ABI-совместимо
         │ └── minor — ABI-совместимо (только добавления)
         └──── major — ABI МОЖНО ломать
```

`SONAME` (`libfoo.so.1`) — линкер использует его; смена major → новый SONAME → старые бинарники продолжают использовать старую .so. Ломающие изменения → бамп major.

### 5. Резервирование места (padding для будущего)

```cpp
class Widget {
    int value_;
    char reserved_[64];   // ⚠️ зарезервировано под будущие поля (хак)
};
```

Иногда встречается в C-API: заранее оставляют место, чтобы добавлять поля без изменения `sizeof`. Уродливо, но сохраняет ABI. pImpl обычно лучше.

## Практические примеры ABI-катастроф

### GCC 5 — libstdc++ ABI break (2015)

Изменение `std::string` (COW → SSO) и `std::list` (добавили `size_`) сломало ABI. GCC ввёл **dual ABI** (`_GLIBCXX_USE_CXX11_ABI`): старые и новые символы сосуществуют. До сих пор источник ошибок линковки при смешивании кода, скомпилированного с разными значениями флага:

```
undefined reference to `foo(std::__cxx11::string)`   // ← ABI mismatch
```

### MSVC vs GCC/Clang

Исторически **несовместимые** ABI (разный mangling, разный exception handling, разный layout). Нельзя было линковать код GCC с MSVC. Отсюда — C-интерфейсы для кроссплатформенных библиотек.

### STL через границы .so

Передача `std::vector`/`std::string` между .so, скомпилированными с разными версиями/флагами stdlib → UB (разный layout, разные inline-функции). Правило: **не передавай STL-типы через ABI-границу** нестабильных библиотек — используй C-типы или pImpl.

## Формулировки на собеседовании

**«Что такое ABI и чем отличается от API?»** — API — контракт на уровне **исходников** (совместимость → код компилируется). ABI — на уровне **машинного кода** (совместимость → скомпилированный бинарник работает без пересборки). ABI включает layout классов, calling convention, name mangling, vtable layout.

**«Почему C++ ABI хрупкий?»** — Классы раскрывают layout (даже приватные члены — часть ABI, добавление поля меняет `sizeof`); inline-функции и шаблоны зашиваются в клиента; vtable layout зависит от порядка виртуальных функций; всё, что в заголовке, — часть контракта.

**«Ломает ли ABI добавление приватного поля?»** — Да. `sizeof` класса меняется → клиенты, создающие объект по значению или обращающиеся к полям по смещению, ломаются. Решение — pImpl (размер класса = размер указателя, неизменен).

**«Как добавить virtual функцию, не сломав ABI?»** — Только **в конец** vtable (и без наследников, которые тоже имеют vtable). Вставка в середину сдвигает слоты → клиенты зовут не те функции.

**«Как обеспечить ABI-стабильность библиотеки?»** — (1) pImpl — прячет layout. (2) Чистые абстрактные интерфейсы + фабрики. (3) `extern "C"` — C ABI стабилен. (4) Версионирование (SONAME, semver). (5) Только добавляющие изменения в минорных версиях.

**«Зачем `extern "C"`?»** — Отключает name mangling → стабильные имена символов, совместимые между компиляторами и языками (FFI). C ABI намного стабильнее C++ ABI (нет классов, vtable, mangling).

**«Что такое dual ABI в GCC?»** — После break в GCC 5 (изменение `std::string`, `std::list`) старый и новый ABI сосуществуют через `_GLIBCXX_USE_CXX11_ABI`. Смешивание кода с разными значениями → ошибки линковки undefined reference.

---

Отличие от Java: там ABI-проблем в C++-смысле **практически нет**. JVM линкует классы **динамически по именам** (полей, методов, сигнатур), а не по смещениям/размерам. Следствия: (1) **добавление приватного поля бинарно совместимо** — JVM находит поля по имени в рантайме, layout вычисляется при загрузке класса; (2) **добавление метода совместимо** — резолвится по имени/сигнатуре; (3) нет name mangling (используются человекочитаемые дескрипторы вроде `(Ljava/lang/String;)I`); (4) нет vtable-layout проблемы — виртуальная диспетчеризация через имена/индексы, вычисляемые JVM. Java определяет **binary compatibility** в JLS (глава 13) — там перечислено, что совместимо: добавление методов/полей — да, удаление — нет, изменение сигнатуры — нет. То есть Java имеет свой «ABI», но он на уровне байткода и **намного стабильнее**, потому что JVM делает позднее связывание. Для тебя, работающего с C++ монолитом и библиотеками: ABI-стабильность — **уникальная C++ головная боль**, требующая pImpl/интерфейсов/C-API, тогда как в Java обратная совместимость библиотек достигается почти автоматически (пока не удаляешь/не меняешь публичные сигнатуры). Rust, кстати, тоже **не имеет стабильного ABI** (намеренно — `repr(Rust)` может меняться), и для FFI использует `extern "C"` + `#[repr(C)]` — ровно как C++; раз ты учишь Rust, это прямая параллель.
