# Уровни оптимизации и что делает компилятор

## Уровни `-O`

```bash
g++ -O0    # без оптимизаций (дефолт) — быстрая компиляция, отладка 1:1
g++ -O1    # базовые оптимизации, не увеличивающие сильно время компиляции
g++ -O2    # ⭐ стандарт для release — агрессивно, но без раздувания кода
g++ -O3    # + агрессивный инлайнинг, векторизация, unrolling (может раздуть)
g++ -Os    # оптимизация по РАЗМЕРУ (≈ -O2 минус то, что раздувает)
g++ -Oz    # ещё агрессивнее по размеру (Clang; GCC 12+)
g++ -Ofast # -O3 + -ffast-math — ⚠️ НАРУШАЕТ стандарт (IEEE 754)!
g++ -Og    # оптимизации, дружественные отладке — ⭐ для debug-сборок
```

### Практический выбор

|Сценарий|Флаги|
|---|---|
|Debug|`-Og -g` (лучше, чем `-O0 -g`)|
|Release|`-O2 -DNDEBUG`|
|Профилирование|`-O2 -g` (или `RelWithDebInfo`)|
|Embedded / размер критичен|`-Os`|
|Максимум скорости|`-O3 -march=native -flto`|
|Санитайзеры|`-O1 -g -fno-omit-frame-pointer`|

**`-Og` вместо `-O0` для отладки:** `-O0` даёт очень медленный код (каждая переменная в памяти, ноль инлайнинга), при этом `-Og` включает оптимизации, не портящие соответствие исходнику — отладка почти так же удобна, а код в разы быстрее.

**`-Ofast` — осторожно:** включает `-ffast-math`, который нарушает IEEE 754: разрешает переассоциацию float-операций (`(a+b)+c ≠ a+(b+c)` для float!), игнорирует NaN/Inf, включает reciprocal-приближения. Может тихо изменить численные результаты. Не использовать, если точность важна.

**CMake:**

```cmake
CMAKE_BUILD_TYPE=Debug          # -O0 -g       (переопредели на -Og -g)
CMAKE_BUILD_TYPE=Release        # -O3 -DNDEBUG (GCC/Clang; MSVC: /O2)
CMAKE_BUILD_TYPE=RelWithDebInfo # -O2 -g -DNDEBUG  ← для профилирования
CMAKE_BUILD_TYPE=MinSizeRel     # -Os -DNDEBUG
```

## Что конкретно оптимизирует компилятор

### 1. Inlining — фундамент

Подстановка тела функции в место вызова. **Ключевая** оптимизация — открывает путь всем остальным.

```cpp
inline int square(int x) { return x * x; }
int y = square(5);
// → int y = 5 * 5;  → int y = 25;  (constant folding после инлайнинга)
```

Что даёт: убирает overhead вызова (пролог/эпилог, передача аргументов), но главное — **делает видимым контекст**, позволяя дальше сворачивать константы, устранять проверки, векторизовать.

**Что мешает инлайнингу** (прямо связано с тем, что мы разбирали):

- **Виртуальные вызовы** — компилятор не знает целевую функцию (отсюда ценность `final` и девиртуализации)
- **Функции в другой TU** — не видно определения → нужен **LTO**
- **`std::function`** — type erasure, косвенный вызов (в отличие от лямбды через шаблон)
- Слишком большое тело, рекурсия, взятие адреса функции

`inline` — **не** директива инлайнинга (это про ODR — мы разбирали); компилятор решает сам по эвристикам. Форсировать: `__attribute__((always_inline))` / `[[gnu::always_inline]]`.

### 2. Constant folding / propagation

```cpp
int x = 2 + 3;         // → int x = 5;  (folding — вычислено при компиляции)
const int N = 10;
int arr[N * 2];        // → int arr[20];

int f() { int a = 5; return a * 2; }   // → return 10;  (propagation)
```

### 3. Dead code elimination

```cpp
int f() {
    int unused = compute();   // ← удалено (если compute() без побочных эффектов)
    if (false) { ... }         // ← удалена вся ветка
    return 42;
}
```

Работает вместе с constant propagation: если условие вычислилось в константу — мёртвая ветка удаляется.

### 4. Common Subexpression Elimination (CSE)

```cpp
int a = x * y + 1;
int b = x * y + 2;
// → int tmp = x * y;
//   int a = tmp + 1;
//   int b = tmp + 2;
```

### 5. Loop optimizations

**Loop-invariant code motion** — вынос инварианта из цикла:

```cpp
for (int i = 0; i < n; ++i)
    arr[i] = x * y + i;      // x*y не зависит от i
// → int tmp = x * y;
//   for (...) arr[i] = tmp + i;
```

**Loop unrolling** — разворачивание (`-O3`):

```cpp
for (int i = 0; i < 4; ++i) sum += arr[i];
// → sum += arr[0]; sum += arr[1]; sum += arr[2]; sum += arr[3];
// меньше проверок условия, больше ILP
```

**Vectorization (SIMD)** — ключевая на `-O3`:

```cpp
for (int i = 0; i < n; ++i)
    c[i] = a[i] + b[i];
// → SSE/AVX: обработка 4/8/16 элементов за инструкцию
```

Векторизации мешают: зависимости между итерациями, возможный aliasing указателей (отсюда важность **strict aliasing** и `restrict` — мы разбирали), непредсказуемое число итераций, вызовы функций внутри.

```bash
g++ -O3 -fopt-info-vec-missed prog.cpp   # ⭐ почему цикл НЕ векторизовался
g++ -O3 -fopt-info-vec prog.cpp          # что векторизовалось
```

**Loop fusion/fission**, **strength reduction** (`i*4` → `i+=4` в счётчике):

```cpp
for (int i = 0; i < n; ++i) arr[i*4] = 0;
// → указатель инкрементируется на 4, без умножения каждую итерацию
```

### 6. Register allocation

Держать переменные в регистрах вместо памяти. На `-O0` **каждая** локальная переменная живёт в стеке (отсюда медленность и точная отладка); на `-O2` — распределяются по регистрам, многие переменные вообще исчезают.

Это главная причина, почему в отладчике на `-O2` видишь `<optimized out>`.

### 7. Tail call optimization

```cpp
int f(int n, int acc) {
    if (n == 0) return acc;
    return f(n - 1, acc + n);   // хвостовой вызов
}
// → превращается в ЦИКЛ (нет роста стека → нет stack overflow)
```

Не гарантировано стандартом C++ (в отличие от Scheme), но GCC/Clang делают на `-O2`.

### 8. Devirtualization

Мы разбирали в контексте vtable. Компилятор превращает виртуальный вызов в прямой, если может доказать динамический тип:

```cpp
struct Derived final : Base { void f() override; };
Derived* p = ...;
p->f();     // final → нет переопределений → прямой вызов → инлайнинг
```

`final`, LTO, видимый `new Derived` рядом — всё помогает девиртуализации.

### 9. RVO / copy elision

Мы разбирали подробно — с C++17 для prvalue это **не оптимизация, а требование** стандарта. NRVO остаётся необязательной оптимизацией на усмотрение компилятора (обычно работает на `-O1+`).

### 10. Empty base optimization, layout

EBO (разбирали в `unique_ptr`) — не «оптимизация уровня -O», а свойство ABI, работает всегда.

## Что компилятор НЕ оптимизирует

Понимание границ важнее списка оптимизаций.

**1. Не меняет наблюдаемое поведение (as-if rule):**

```cpp
volatile int x = 5;     // ⚠️ volatile — обращения НЕ оптимизируются
std::cout << "hi";      // ввод-вывод — наблюдаемое поведение, не удаляется
```

**2. Не удаляет вызовы с побочными эффектами** (если не видит тело и не может доказать чистоту).

**3. Не может устранить косвенность через `std::function`, виртуальные вызовы без девиртуализации, указатели с возможным aliasing.**

**4. Не пересекает границы TU без LTO** — функция из другого `.cpp` не инлайнится.

**5. Не исправляет алгоритмическую сложность.** `O(n²)` останется `O(n²)` — компилятор оптимизирует константы, не алгоритм.

**6. Плохо оптимизирует через aliasing:**

```cpp
void f(int* a, int* b) {
    *a = 1;
    *b = 2;
    use(*a);   // компилятор ДОЛЖЕН перечитать *a — вдруг a == b
}
void g(int* __restrict a, int* __restrict b) {   // ✅ обещаем: не алиасят
    *a = 1; *b = 2; use(*a);   // → use(1), без перечитывания
}
```

## Опасное: UB + оптимизации

Ключевая связь с темами про UB. **Компилятор предполагает, что UB не происходит** — и на этом оптимизирует.

```cpp
// signed overflow (разбирали)
int f(int x) { return x + 1 > x; }
// -O0: реальное сложение → при INT_MAX даёт false
// -O2: → return true;   ← упрощено, "переполнения не бывает"

// разыменование null (разбирали)
void f(Widget* p) {
    p->use();              // компилятор: p != nullptr (иначе UB)
    if (p == nullptr) {    // ⚠️ УДАЛЕНО — проверка "избыточна"
        handle();
    }
}

// data race (разбирали)
bool done = false;         // не atomic
while (!done) { }          // → if (!done) while(true) {}  ← бесконечный цикл

// strict aliasing (разбирали)
float f = 1.0f;
int bits = *(int*)&f;      // работает на -O0, ломается на -O2
```

**Симптом «работает на -O0, ломается на -O2» — почти всегда UB.** Это не «баг оптимизатора», а корректная оптимизация на некорректном коде.

Диагностика: собрать с `-fsanitize=undefined,address` и прогнать.

## Полезные флаги вокруг оптимизации

```bash
-march=native            # ⭐ инструкции конкретного CPU (AVX-512 и т.д.) — но НЕ переносимо
-mtune=native            # оптимизировать под CPU, но использовать базовый набор инструкций
-flto                    # ⭐ Link-Time Optimization — межмодульный инлайнинг (разбирали)
-fno-omit-frame-pointer  # сохранить frame pointer — нужен для профайлеров/санитайзеров
-fno-exceptions          # без исключений (embedded)
-fno-rtti                # без RTTI (dynamic_cast/typeid недоступны)
-DNDEBUG                 # отключить assert
-ffunction-sections -fdata-sections -Wl,--gc-sections   # удалить неиспользуемый код
```

**`-march=native`** может дать серьёзный прирост (AVX-векторизация), но бинарник **не запустится** на CPU без этих инструкций. Для распространяемых сборок — `-mtune=native` или конкретный базовый уровень (`-march=x86-64-v2`).

**PGO (Profile-Guided Optimization)** — оптимизация по профилю реального выполнения:

```bash
g++ -fprofile-generate -O2 prog.cpp -o prog
./prog                                    # собираем профиль на реальной нагрузке
g++ -fprofile-use -O2 prog.cpp -o prog    # оптимизируем с учётом профиля
```

Компилятор узнаёт горячие ветки, реальные вероятности условий, типичные типы для девиртуализации. Даёт 5-20% на реальных приложениях. Часто в связке с LTO.

## Как посмотреть, что сделал компилятор

```bash
g++ -S -O2 -masm=intel prog.cpp -o -      # ассемблер в stdout
g++ -O2 -fopt-info-vec prog.cpp           # отчёт о векторизации
g++ -O2 -fopt-info-inline prog.cpp        # отчёт об инлайнинге
g++ -O2 -fopt-info-vec-missed prog.cpp    # ⭐ ПОЧЕМУ не векторизовалось
clang++ -O2 -Rpass=inline prog.cpp        # Clang remarks
clang++ -O2 -Rpass-missed=loop-vectorize prog.cpp
```

**Compiler Explorer (godbolt.org)** — стандартный инструмент: видишь ассемблер для любого компилятора/флагов рядом с исходником. На собеседовании упоминание godbolt как способа проверить, инлайнится ли функция или векторизуется цикл — хороший сигнал.

## Формулировки на собеседовании

**«Чем отличаются -O2 и -O3?»** — `-O3` добавляет агрессивный инлайнинг, loop unrolling и векторизацию, что может **раздуть код** (хуже кэш инструкций) — иногда `-O2` быстрее. Стандарт для release — `-O2`; `-O3` применяют после измерения.

**«Что использовать для отладки?»** — `-Og -g`, а не `-O0 -g`: включает оптимизации, не портящие соответствие исходнику; код в разы быстрее при сопоставимом удобстве отладки.

**«Чем опасен -Ofast?»** — Включает `-ffast-math`, **нарушающий IEEE 754**: переассоциация float-операций, игнорирование NaN/Inf, reciprocal-приближения → тихо меняет численные результаты.

**«Главная оптимизация?»** — **Inlining**: сам по себе убирает overhead вызова, но главное — открывает контекст для constant folding, dead code elimination, векторизации. Мешают ей: виртуальные вызовы, границы TU (лечится LTO), `std::function`.

**«Почему код ломается на -O2, работая на -O0?»** — Почти всегда **UB**: компилятор оптимизирует, предполагая его отсутствие (signed overflow → `x+1 > x` становится `true`; разыменование указателя → проверка на null удаляется; data race без atomic → цикл становится бесконечным; strict aliasing violation). Диагностика — UBSan/ASan.

**«Что даёт LTO?»** — Межмодульные оптимизации: инлайнинг через границы TU, девиртуализация, удаление мёртвого кода глобально. Ценой времени линковки. Побочно — детектор ODR-нарушений.

**«Что такое PGO?»** — Двухфазная сборка: собрать профиль на реальной нагрузке (`-fprofile-generate`), затем оптимизировать с его учётом (`-fprofile-use`). Компилятор знает горячие пути, реальные вероятности ветвлений → 5-20% прироста.

**«Как проверить, векторизовался ли цикл?»** — `-fopt-info-vec` / `-fopt-info-vec-missed` (GCC), `-Rpass=loop-vectorize` (Clang), или посмотреть ассемблер на godbolt.

---

Отличие от Java: там оптимизация — **рантайм** (JIT), а не compile-time. `javac` делает почти ничего (только простейший constant folding); всю работу выполняет **HotSpot JIT** во время выполнения. Ключевые различия: (1) JIT видит **реальный профиль** — сам делает то, что в C++ требует PGO, автоматически и адаптивно; (2) JIT делает **агрессивную девиртуализацию** через monomorphic inline caches — видит, что в конкретном call site всегда один тип, и инлайнит с guard'ом (в C++ девиртуализация только статическая); (3) **деоптимизация** — если предположение нарушилось, JIT откатывается к интерпретации (C++ так не умеет — решения окончательны); (4) нет UB → нет класса «оптимизация сломала код на -O2», JIT не может делать выводы из UB, потому что его нет. Цена Java-подхода: warm-up (первые вызовы интерпретируются), непредсказуемость (когда скомпилируется?), невозможность оптимизации под конкретный CPU так же глубоко, как `-march=native`. Для тебя вывод: в C++ ты **явно** управляешь оптимизацией (флаги, LTO, PGO, `final`, `restrict`), в Java она автоматична и адаптивна — на собеседовании понимание «почему компилятор не может заинлайнить виртуальный вызов, а JIT может» демонстрирует глубокое понимание обеих моделей.
