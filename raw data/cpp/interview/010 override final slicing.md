# `override`, `final`, slicing

`override` и `final` мы уже частично затрагивали — соберу здесь целостно и добавлю slicing, который логично их завершает.

## `override`

**Не добавляет виртуальности** (она наследуется автоматически) — это **compile-time проверка**, что метод действительно переопределяет виртуальный метод базы.

```cpp
struct Base {
    virtual void f(int);
    virtual void g() const;
    virtual void h();
};

struct Derived : Base {
    void f(double) override;   // ❌ ОШИБКА: другой параметр — ничего не переопределяет
    void g() override;         // ❌ ОШИБКА: потерян const
    void h() override;         // ✅ OK
};
```

Без `override` первые два молча компилируются как **новые методы**, скрывающие базовые → неверное поведение в рантайме, которое ловится только отладкой:

```cpp
struct Derived : Base {
    void f(double);   // компилируется! но это НЕ переопределение
};

Base* p = new Derived();
p->f(1);   // → Base::f(int) — не то, что ожидал программист
```

Что должно совпасть для успешного `override`:

- имя
- типы параметров
- `const` / `volatile` квалификаторы
- ref-qualifier (`&` / `&&`)
- возвращаемый тип (либо **ковариантный** — производный указатель/ссылка)

```cpp
struct Base    { virtual Base* clone() const; };
struct Derived : Base { Derived* clone() const override; };   // ✅ ковариантный возврат
```

**Практическое правило: всегда пиши `override`.** Стоит ноль, ловит целый класс молчаливых багов. Многие проекты включают `-Wsuggest-override` / `-Winconsistent-missing-override`.

Один нюанс: `override` подразумевает `virtual`, поэтому писать оба избыточно (и стилистически не принято):

```cpp
virtual void f() override;   // избыточно — достаточно void f() override;
```

## `final`

Две независимые роли.

### 1. `final` на методе — запрет дальнейшего переопределения

```cpp
struct A { virtual void f(); };
struct B : A { void f() final; };      // f всё ещё virtual, но переопределять ниже нельзя
struct C : B { void f() override; };   // ❌ ОШИБКА: B::f is final
```

Метод остаётся виртуальным (слот в vtable на месте), просто иерархия ниже его «замораживает».

`final` подразумевает `override` — если метод помечен `final`, он обязан что-то переопределять:

```cpp
struct B : A { void g() final; };   // ❌ ОШИБКА, если A::g не виртуален — нечего финализировать
```

### 2. `final` на классе — запрет наследования

```cpp
struct Widget final { };
struct Broken : Widget { };   // ❌ ОШИБКА: нельзя наследовать от final класса
```

### Зачем: семантика + девиртуализация

**Семантика:** явно фиксируешь контракт — «этот класс/метод не предназначен для расширения».

**Оптимизация:** компилятор знает, что переопределений больше не будет → может **девиртуализовать** вызов и **заинлайнить** его:

```cpp
struct Base { virtual int f() { return 1; } };
struct Derived final : Base { int f() override { return 2; } };

void call(Derived* p) {
    p->f();   // Derived final → нет наследников → динамический тип точно Derived
              // → компилятор вызывает Derived::f напрямую, может встроить тело
}
```

Без `final` компилятор обязан идти через vtable (вдруг где-то есть наследник Derived).

Это не мелочь: убрать виртуальный вызов в горячем цикле — значит открыть путь инлайнингу и всем последующим оптимизациям. Практический совет: помечай `final` классы и методы, которые точно не будут расширяться.

## Object slicing (срезка)

**Slicing** — потеря производной части объекта при **копировании по значению** в базовый тип.

```cpp
struct Base {
    int a_ = 1;
    virtual void speak() { std::cout << "Base\n"; }
};

struct Derived : Base {
    int b_ = 2;                 // ← дополнительные данные
    void speak() override { std::cout << "Derived\n"; }
};

Derived d;
Base b = d;      // ⚠️ SLICING! копируется только Base-часть
                 // b_ ПОТЕРЯН, vptr b указывает на vtable Base

b.speak();       // → "Base", не "Derived"!
```

### Почему так происходит

`Base b = d;` вызывает **copy-конструктор `Base`**, который знает только о полях `Base`:

```cpp
Base(const Base& o) : a_(o.a_) { }   // копирует только a_; b_ его вообще не касается
```

Объект `b` имеет `sizeof(Base)` — физически негде хранить `b_`. И vptr в `b` устанавливается конструктором `Base` → указывает на vtable **Base** → полиморфизм потерян.

```
d (Derived):              b (Base):
┌────────┐               ┌────────┐
│ vptr→D │               │ vptr→B │  ← vtable Base!
│ a_ = 1 │  ──copy──>    │ a_ = 1 │
│ b_ = 2 │               └────────┘
└────────┘                (b_ отрезан)
```

### Где встречается на практике

**Передача по значению:**

```cpp
void process(Base b);   // ⚠️ по значению → slicing при передаче Derived

Derived d;
process(d);   // объект срезан, полиморфизм не работает
```

**Присваивание:**

```cpp
Base b;
Derived d;
b = d;   // ⚠️ Base::operator= копирует только Base-часть
```

**Хранение в контейнере по значению** — самая частая и болезненная ошибка:

```cpp
std::vector<Base> v;
v.push_back(Derived());   // ⚠️ SLICING! в векторе лежат Base, не Derived

for (auto& x : v) x.speak();   // всегда "Base"
```

`vector<Base>` физически хранит объекты размера `sizeof(Base)` — производные туда просто не помещаются.

### Как избегать

**1. Работать через указатели/ссылки** — они не копируют объект:

```cpp
void process(Base& b);         // ✅ ссылка — полиморфизм работает
void process(const Base& b);   // ✅
void process(Base* b);         // ✅

Derived d;
process(d);   // → Derived::speak()
```

**2. В контейнерах хранить smart pointers:**

```cpp
std::vector<std::unique_ptr<Base>> v;   // ✅ полиморфный контейнер
v.push_back(std::make_unique<Derived>());

for (auto& p : v) p->speak();   // → "Derived"
```

**3. Запретить копирование базы** — самое надёжное, ошибка становится compile-time:

```cpp
struct Base {
    virtual ~Base() = default;
    virtual void speak();
protected:
    Base() = default;
    Base(const Base&) = default;              // копирование доступно только наследникам
    Base& operator=(const Base&) = default;   // (нужно им для своих copy-операций)
};

Derived d;
Base b = d;   // ❌ ОШИБКА КОМПИЛЯЦИИ — copy-ctor Base не public
```

Либо просто удалить:

```cpp
struct Base {
    Base(const Base&) = delete;
    Base& operator=(const Base&) = delete;
};
```

Это идиоматично: **полиморфные базовые классы не должны быть копируемыми по значению**. Клонирование, если нужно, делают через виртуальный `clone()`:

```cpp
struct Base {
    virtual std::unique_ptr<Base> clone() const = 0;   // «виртуальный конструктор копирования»
    virtual ~Base() = default;
};

struct Derived : Base {
    std::unique_ptr<Base> clone() const override {
        return std::make_unique<Derived>(*this);   // копируем ПОЛНЫЙ Derived
    }
};

std::unique_ptr<Base> p = original->clone();   // ✅ полиморфное копирование без slicing
```

## Связь трёх понятий

Все три — про **корректность полиморфизма**, но на разных уровнях:

- **`override`** — гарантирует, что переопределение действительно произошло (compile-time проверка сигнатуры)
- **`final`** — фиксирует границу иерархии (семантика + девиртуализация)
- **slicing** — что происходит, когда полиморфный объект копируется по значению (полиморфизм молча ломается в рантайме)

Общий вывод: **полиморфные объекты живут за указателями/ссылками, а не за значениями.** Значение — это `sizeof` конкретного статического типа, и производная часть в него не влезает.

## Формулировки на собеседовании

**«Что делает `override`?»** — Compile-time проверка, что метод переопределяет виртуальный метод базы. Виртуальности не добавляет (она наследуется), но ловит несовпадение сигнатуры, которое иначе создало бы новый скрывающий метод.

**«Зачем `final`?»** — Запрет наследования (класс) или переопределения (метод); плюс даёт компилятору возможность девиртуализовать вызов и заинлайнить его.

**«Что такое slicing и как его избежать?»** — Потеря производной части при копировании по значению в базовый тип; vptr сбрасывается на базовую vtable, полиморфизм теряется. Избегать: работать через ссылки/указатели, хранить `unique_ptr` в контейнерах, запретить копирование полиморфной базы (protected/deleted copy), для клонирования использовать виртуальный `clone()`.

**«Почему `vector<Base>` не может хранить Derived?»** — Контейнер хранит элементы размера `sizeof(Base)`; производный объект больше и не помещается → срезается. Нужен `vector<unique_ptr<Base>>`.

---

Отличие от Java: там slicing **невозможен** — переменные объектных типов всегда ссылки, объект целиком живёт на heap. `Base b = d;` в Java просто копирует ссылку, полиморфизм сохраняется. В C++ семантика значений делает slicing реальной и молчаливой ловушкой — компилятор не предупредит, поведение просто изменится. Это один из самых частых источников багов при переходе с Java на C++, так что на собеседовании ждать вопроса стоит.
