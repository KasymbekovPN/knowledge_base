# Сложность операций STL-контейнеров

## `std::vector` — динамический массив

**Устройство:** непрерывный блок памяти + три указателя (`begin`, `end`, `capacity_end`).

```
┌───┬───┬───┬───┬───┬───┬───┬───┐
│ 1 │ 2 │ 3 │ 4 │   │   │   │   │
└───┴───┴───┴───┴───┴───┴───┴───┘
  ^           ^               ^
begin        end          capacity
size = 4, capacity = 8
```

|Операция|Сложность|
|---|---|
|`operator[]`, `at()`|**O(1)**|
|`push_back` / `emplace_back`|**амортизированная O(1)**|
|`pop_back`|O(1)|
|`insert` / `erase` в середину|**O(n)** (сдвиг элементов)|
|`insert` / `erase` в начало|O(n)|
|поиск (`std::find`)|O(n)|
|`reserve`|O(n) (одна реаллокация)|

### Амортизированная O(1) — важно объяснить

При заполнении capacity вектор:

1. выделяет новый буфер **в K раз больше** (обычно K=2 в GCC/Clang, K=1.5 в MSVC)
2. **перемещает/копирует** все элементы
3. освобождает старый буфер

Одна реаллокация — O(n). Но она происходит редко. При росте в 2 раза за n вставок суммарно перемещено ~2n элементов → **амортизированно O(1)** на вставку.

```cpp
std::vector<int> v;
for (int i = 0; i < 1000; ++i) v.push_back(i);
// capacity растёт: 1, 2, 4, 8, ..., 1024 — всего ~10 реаллокаций, не 1000
```

**`reserve` устраняет реаллокации:**

```cpp
std::vector<int> v;
v.reserve(1000);   // одна аллокация заранее
for (int i = 0; i < 1000; ++i) v.push_back(i);   // ноль реаллокаций
```

### Инвалидация итераторов — критично

|Операция|Что инвалидируется|
|---|---|
|`push_back` **с** реаллокацией|**ВСЁ** (итераторы, указатели, ссылки)|
|`push_back` **без** реаллокации|только `end()`|
|`insert(pos)`|всё **от pos** до конца (и всё, при реаллокации)|
|`erase(pos)`|всё **от pos** до конца|
|`reserve`, `resize` (с ростом)|всё, если capacity изменилась|
|`clear`|всё|

```cpp
std::vector<int> v{1,2,3};
int* p = &v[0];
v.push_back(4);   // ⚠️ реаллокация → p ВИСЯЧИЙ! use-after-free при *p
```

Классический баг. Именно поэтому нельзя хранить указатели/итераторы на элементы вектора через модификации.

### Почему vector — дефолт

Несмотря на O(n) вставку в середину, `vector` часто **быстрее** списков и деков даже там, где асимптотика хуже: **непрерывная память → идеальная локальность кэша → префетчинг**. Обход `vector<int>` на порядок быстрее обхода `list<int>` той же длины. Асимптотика не учитывает константы, а разница между попаданием в L1-кэш и промахом в RAM — ~100x.

Практическое правило (совет Страуструпа): **используй `vector` по умолчанию**, меняй только если профилирование показало проблему.

## `std::deque` — double-ended queue

**Устройство:** массив указателей на **чанки** (блоки фиксированного размера). Не непрерывный!

```
map (массив указателей):
┌───┬───┬───┬───┐
│ ● │ ● │ ● │ ● │
└─┬─┴─┬─┴─┬─┴─┬─┘
  v   v   v   v
┌────┐┌────┐┌────┐┌────┐
│chunk││chunk││chunk││chunk│   ← блоки по ~512 байт
└────┘└────┘└────┘└────┘
```

|Операция|Сложность|
|---|---|
|`operator[]`, `at()`|**O(1)** (но медленнее vector — двойная косвенность)|
|`push_back` / `push_front`|**амортизированная O(1)**|
|`pop_back` / `pop_front`|O(1)|
|`insert` / `erase` в середину|O(n)|
|поиск|O(n)|

**Главное преимущество над vector:** `push_front` — **O(1)** вместо O(n).

**Ключевая особенность инвалидации:**

|Операция|Итераторы|Ссылки/указатели|
|---|---|---|
|`push_front` / `push_back`|**инвалидируются**|**остаются валидны!**|
|`insert`/`erase` в середину|всё|всё|
|`pop_front` / `pop_back`|только на удалённый|только на удалённый|

Уникальное свойство: при вставке в концы **ссылки на существующие элементы остаются валидными** (существующие чанки не перемещаются — добавляется новый чанк). Итераторы при этом инвалидируются, потому что могут перестраиваться внутренние структуры навигации.

**Минусы:** хуже локальность кэша (память фрагментирована по чанкам), доступ по индексу медленнее (вычислить чанк + смещение), больше overhead памяти.

**Когда использовать:** нужен быстрый `push_front`/`pop_front` **и** индексный доступ. Дефолтный контейнер для `std::queue` и `std::stack`.

## `std::map` / `std::set` — красно-чёрное дерево

**Устройство:** сбалансированное бинарное дерево поиска (RB-tree). Элементы **отсортированы** по ключу.

|Операция|Сложность|
|---|---|
|`find`|**O(log n)**|
|`insert` / `emplace`|**O(log n)**|
|`erase`|**O(log n)**|
|`operator[]` (map)|O(log n)|
|обход (begin→end)|O(n), **в отсортированном порядке**|
|`lower_bound` / `upper_bound`|**O(log n)**|

### Красно-чёрное дерево — инварианты

RB-tree — самобалансирующееся BST с пятью правилами:

1. Каждый узел красный или чёрный
2. Корень чёрный
3. Все листья (NIL) чёрные
4. У красного узла оба потомка чёрные (нет двух красных подряд)
5. Для каждого узла: все пути до листьев содержат **одинаковое число чёрных узлов** (black-height)

Следствие: самый длинный путь не более чем **вдвое** длиннее самого короткого → высота ≤ **2·log₂(n+1)** → все операции O(log n) **в худшем случае** (не амортизированно!).

Балансировка при вставке/удалении — через **повороты** (rotations) и перекраску. Амортизированно константное число поворотов.

**Почему RB-tree, а не AVL:** AVL строже сбалансирован (быстрее поиск), но требует больше поворотов при вставке/удалении. RB — компромисс: чуть медленнее поиск, заметно быстрее модификации. STL выбрал RB.

### Инвалидация — очень щадящая

|Операция|Инвалидируется|
|---|---|
|`insert`|**ничего**|
|`erase`|**только итераторы/ссылки на удалённый элемент**|

Узлы дерева не перемещаются в памяти. Это огромное преимущество: можно держать указатели на элементы, вставляя и удаляя другие.

```cpp
std::map<int, std::string> m;
auto& ref = m[1];        // ссылка на значение
m[2] = "two";            // ✅ ref остаётся валидной!
m[3] = "three";          // ✅
```

Сравни с `vector`, где любая реаллокация всё ломает.

### Уникальные возможности упорядоченности

```cpp
std::map<int, std::string> m{{1,"a"},{5,"b"},{10,"c"}};

auto it = m.lower_bound(3);   // первый элемент >= 3 → {5,"b"}   — O(log n)
auto it2 = m.upper_bound(5);  // первый элемент > 5  → {10,"c"}

for (auto& [k,v] : m) { }     // обход В ПОРЯДКЕ СОРТИРОВКИ

// range query — только у упорядоченного контейнера:
for (auto it = m.lower_bound(2); it != m.upper_bound(8); ++it) { }
```

`unordered_map` этого **не умеет** вообще.

### Ловушка `operator[]`

```cpp
std::map<int, std::string> m;
std::cout << m[42];   // ⚠️ ВСТАВЛЯЕТ {42, ""} если ключа нет!
                      //    m.size() теперь 1

// для чтения без вставки:
if (auto it = m.find(42); it != m.end()) { /* ... */ }   // ✅
// или m.at(42) — бросает out_of_range, если нет
```

Плюс `operator[]` **не работает** на `const map` (он может модифицировать) — только `find`/`at`.

## `std::unordered_map` / `unordered_set` — хеш-таблица

**Устройство:** массив **бакетов**; коллизии разрешаются **цепочками** (separate chaining — связные списки). Стандарт де-факто требует именно цепочки (из-за требований к инвалидации и `local_iterator`).

```
buckets:
[0] → nullptr
[1] → (key1,v1) → (key9,v9)    ← коллизия: цепочка
[2] → nullptr
[3] → (key3,v3)
[4] → (key4,v4) → (key12,v12) → (key20,v20)
```

|Операция|Средняя|Худшая|
|---|---|---|
|`find`|**O(1)**|**O(n)**|
|`insert`|**амортизированная O(1)**|O(n)|
|`erase`|**O(1)**|O(n)|
|обход|O(n), **порядок непредсказуем**|—|
|`lower_bound`|**отсутствует**|—|

### Механика

1. Вычислить `hash(key)` → `size_t`
2. Индекс бакета = `hash % bucket_count`
3. Пройти цепочку бакета, сравнивая ключи через `operator==`

Если хеш хороший и load factor мал — цепочки короткие (в среднем ~1 элемент) → O(1).

### Load factor и rehash

**Load factor** = `size / bucket_count` — среднее число элементов на бакет.

```cpp
std::unordered_map<int,int> m;
m.load_factor();       // текущий
m.max_load_factor();   // порог, по умолчанию 1.0
```

Когда `load_factor > max_load_factor` → **rehash**:

1. выделить новый массив бакетов (обычно ~вдвое больше, простое число)
2. **пересчитать бакет для каждого элемента** (хеш кешируется или пересчитывается)
3. перераспределить

**Rehash — O(n)**, но происходит редко → вставка **амортизированно O(1)**.

```cpp
std::unordered_map<int,int> m;
m.reserve(1000);   // ✅ заранее выделяет бакеты — избегаем rehash'ей
// или m.rehash(n) — задаёт минимальное число бакетов
```

### Худший случай O(n) — когда

- **Плохая хеш-функция** — все ключи в один бакет → одна длинная цепочка → линейный поиск
- **Hash flooding attack** — атакующий подбирает ключи с одинаковым хешем (реальная DoS-атака на веб-серверы; поэтому в языках вроде Python/Rust хеш рандомизирован)

```cpp
struct BadHash {
    size_t operator()(int) const { return 0; }   // всё в один бакет!
};
std::unordered_map<int,int,BadHash> m;   // O(n) на каждую операцию
```

### Инвалидация

|Операция|Итераторы|Ссылки/указатели|
|---|---|---|
|`insert` **с** rehash|**все**|**остаются валидны!**|
|`insert` **без** rehash|ничего|ничего|
|`erase`|только на удалённый|только на удалённый|

Важно: **ссылки на элементы переживают rehash** (перераспределяются узлы цепочек, но сами узлы не перемещаются — переставляются указатели). Итераторы — инвалидируются, т.к. зависят от структуры бакетов.

### Кастомный хеш и equal

Для своих типов нужны оба:

```cpp
struct Point { int x, y; };

struct PointHash {
    size_t operator()(const Point& p) const noexcept {
        return std::hash<int>{}(p.x) ^ (std::hash<int>{}(p.y) << 1);   // простой пример
    }
};
struct PointEq {
    bool operator()(const Point& a, const Point& b) const noexcept {
        return a.x == b.x && a.y == b.y;
    }
};

std::unordered_map<Point, int, PointHash, PointEq> m;
```

Или специализация `std::hash`:

```cpp
namespace std {
    template<> struct hash<Point> {
        size_t operator()(const Point& p) const noexcept { /* ... */ }
    };
}
// тогда достаточно: std::unordered_map<Point, int> m;  (нужен ещё operator== у Point)
```

**Требование:** если `a == b`, то `hash(a) == hash(b)` (обратное не обязано). Нарушение → элементы «теряются».

Замечание про качество хеша: `x ^ (y << 1)` — учебный пример, для реальных типов лучше комбинировать по-взрослому (boost::hash_combine или аналогичный подход с перемешиванием), иначе получится много коллизий на регулярных данных.

## `map` vs `unordered_map` — как выбирать

| |`map`|`unordered_map`|
|---|---|---|
|Сложность (средняя)|O(log n)|**O(1)**|
|Сложность (худшая)|**O(log n)**|O(n)|
|Порядок обхода|**отсортирован**|произвольный|
|`lower_bound`, range query|✅|❌|
|Требования к ключу|`operator<` (strict weak ordering)|`hash` + `operator==`|
|Память|меньше overhead на элемент|массив бакетов + цепочки|
|Локальность кэша|плохая (узлы разбросаны)|плохая (цепочки), но лучше при малом load factor|
|Стабильность (worst case)|✅ гарантия|❌ зависит от хеша|

**Выбирай `unordered_map`, если:** нужен просто быстрый lookup по ключу, порядок не важен, хеш нормальный.

**Выбирай `map`, если:** нужен отсортированный обход, range-запросы (`lower_bound`), гарантия worst-case O(log n), или у ключа нет хорошего хеша.

**Практическая тонкость:** на **малых n** (десятки элементов) `std::vector` пар с линейным поиском часто **быстрее обоих** — из-за локальности кэша. Асимптотика начинает выигрывать только на достаточно больших объёмах.

## Ещё контейнеры (кратко, для полноты)

|Контейнер|Устройство|Особенность|
|---|---|---|
|`list`|двусвязный список|O(1) вставка/удаление **по итератору**; `splice` O(1); поиск O(n); ужасная локальность|
|`forward_list`|односвязный|минимальный overhead, только forward-итератор|
|`array`|статический массив|на стеке, `sizeof` фиксирован, ноль overhead|
|`priority_queue`|бинарная куча (над vector)|`push`/`pop` O(log n), `top` O(1)|
|`multimap`/`multiset`|RB-tree|дубликаты ключей разрешены|
|`flat_map` (C++23)|отсортированный vector|лучшая локальность, O(n) вставка, O(log n) поиск|

`std::list` в практике используется редко: O(1) вставка звучит хорошо, но каждый узел — отдельная аллокация, обход разрушает кэш. Обычно `vector` быстрее даже при O(n) вставках.

## Формулировки на собеседовании

**«Почему `push_back` — амортизированная O(1)?»** — При реаллокации capacity растёт **геометрически** (×2). За n вставок суммарное число перемещений ~2n → O(1) в среднем на вставку.

**«Что инвалидирует итераторы vector?»** — Любая реаллокация (`push_back` при заполненной capacity, `reserve`, `resize`) инвалидирует **всё**. `insert`/`erase` инвалидируют от точки изменения до конца.

**«Как устроен `map`?»** — Красно-чёрное дерево: самобалансирующееся BST, высота ≤ 2·log(n+1) благодаря инварианту чёрной высоты → все операции O(log n) в **худшем** случае.

**«Когда `unordered_map` деградирует до O(n)?»** — При плохой хеш-функции (много коллизий → длинные цепочки) или при hash flooding атаке.

**«Что такое rehash?»** — Когда load_factor превысил max_load_factor, выделяется больший массив бакетов и все элементы перераспределяются — O(n). Избегается через `reserve()`.

**«Что происходит со ссылками при rehash?»** — **Остаются валидными** (узлы цепочек не перемещаются), а итераторы — инвалидируются.

**«`map` или `unordered_map`?»** — Нужен отсортированный обход / range-запросы / гарантия worst-case → `map`. Нужен просто быстрый lookup → `unordered_map`.

**«Почему `vector` часто быстрее `list`, хотя вставка O(n) vs O(1)?»** — Локальность кэша. Непрерывная память + префетчинг дают ускорение в разы; асимптотика не учитывает константы, а промах кэша дороже перемещения элементов в разы.

---

Отличие от Java: `ArrayList` ≈ `vector`, `LinkedList` ≈ `list`, `TreeMap` ≈ `map` (тоже RB-tree!), `HashMap` ≈ `unordered_map`. Но: Java `HashMap` с Java 8 при длинных цепочках **превращает их в дерево** (treeify) → худший случай O(log n), а не O(n) — защита от hash flooding. В C++ такой защиты нет, худший случай остаётся O(n). Ещё важнее: в Java контейнеры хранят **ссылки** на объекты (уровень косвенности, объекты разбросаны по heap), а в C++ `vector<T>` хранит объекты **по значению, непрерывно** — отсюда драматически лучшая локальность и то самое преимущество, которого в Java не достичь без специальных приёмов.
