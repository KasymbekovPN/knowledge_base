# Const correctness и `mutable`

## Const correctness — принцип

Помечать `const` всё, что не должно меняться. Это не про производительность (компилятор редко оптимизирует по `const` — из-за возможности `const_cast` и алиасинга), а про **выражение намерения в системе типов**: ошибки ловятся на этапе компиляции, а не в отладчике.

Принцип: **`const` по умолчанию, изменяемость — по необходимости.**

---

## Где применяется

### Параметры функций

```cpp
void process(const std::string& s);   // не изменяем — принимаем const&
void modify(std::string& s);          // изменяем — обычная ссылка
void take(std::string s);             // копия/move — const бессмыслен для вызывающего
```

Тонкость: `const` для параметра **по значению** ничего не говорит вызывающему (он всё равно получит копию), это лишь внутреннее обязательство функции. В объявлении его обычно опускают, в определении иногда пишут:

```cpp
void f(const int x);   // в объявлении бессмысленно — сигнатура та же, что void f(int)
```

### Методы класса

Метод, помеченный `const`, обещает не менять состояние объекта:

```cpp
class Buffer {
    std::vector<int> data_;
public:
    size_t size() const { return data_.size(); }   // ✅ не меняет — const
    void push(int x) { data_.push_back(x); }       // меняет — не const

    int get(size_t i) const {
        // data_.push_back(1);   // ❌ ошибка компиляции: нельзя менять в const-методе
        return data_[i];
    }
};
```

Механика: в `const`-методе `this` имеет тип `const Buffer*`, поэтому все члены становятся `const`.

**Критично:** `const`-объект может вызывать **только** `const`-методы.

```cpp
const Buffer b;
b.size();   // ✅
b.push(1);  // ❌ ошибка компиляции
```

Отсюда практическое следствие: если забыл пометить метод `const`, объект нельзя будет использовать через `const&` — а `const&` это стандартный способ передачи. **Пропущенный `const` вирусно ломает вызывающий код.**

### Const-перегрузка

Классическая пара — возвращать разный доступ в зависимости от константности объекта:

```cpp
class Buffer {
    std::vector<int> data_;
public:
    int& operator[](size_t i) { return data_[i]; }              // неконстантная версия
    const int& operator[](size_t i) const { return data_[i]; }  // константная
};

Buffer b;
b[0] = 42;          // ✅ неконстантная версия → int&

const Buffer cb;
int x = cb[0];      // ✅ константная → const int&
// cb[0] = 42;      // ❌ ошибка — const int& нельзя присвоить
```

Так устроены `operator[]`, `at()`, `front()`, `back()`, `begin()`/`end()` во всех STL-контейнерах.

Чтобы не дублировать логику, используют идиому «неконстантный вызывает константный» (Мейерс):

```cpp
int& at(size_t i) {
    return const_cast<int&>(std::as_const(*this).at(i));   // C++17: std::as_const
    // до C++17: const_cast<int&>(static_cast<const Buffer&>(*this).at(i));
}
const int& at(size_t i) const { /* вся реальная логика здесь */ }
```

Это **единственный** легитимный `const_cast`: мы точно знаем, что объект не const (мы в неконстантном методе), и просто снимаем const, который сами же и добавили.

## `const` и указатели — что именно константно

Читать надо **справа налево** от имени:

```cpp
int x = 5, y = 10;

const int* p;          // указатель на const int:  *p менять НЕЛЬЗЯ, p — можно
int const* p2;         // ТО ЖЕ САМОЕ (эквивалентная запись)
int* const p3 = &x;    // константный указатель:   *p3 менять МОЖНО, p3 — нельзя
const int* const p4 = &x;  // ни то, ни другое

// проверка:
const int* a = &x;
*a = 1;    // ❌
a = &y;    // ✅

int* const b = &x;
*b = 1;    // ✅
b = &y;    // ❌
```

Мнемоника: **`const` относится к тому, что слева от него; если слева ничего нет — к тому, что справа.**

Отсюда важный момент про **top-level** и **low-level** const:

```cpp
int* const     // top-level const (сам указатель) — теряется при копировании
const int*     // low-level const (указуемое) — часть типа, сохраняется
```

Это важно для вывода типов (`auto`, шаблоны): top-level const отбрасывается.

```cpp
const int c = 5;
auto a = c;         // a — int (не const int!) — top-level const отброшен
const auto b = c;   // b — const int

const int* p = &c;
auto q = p;         // q — const int* — low-level const СОХРАНЁН
```

## `mutable` — исключение из const

`mutable` позволяет менять член **даже в `const`-методе** и **даже у `const`-объекта**.

```cpp
class Cache {
    std::map<int, int> data_;
    mutable size_t hits_ = 0;      // счётчик — не часть логического состояния
    mutable std::mutex mtx_;       // мьютекс — тоже

public:
    int get(int key) const {       // логически const — данные не меняем
        std::lock_guard lock(mtx_);   // ✅ lock() меняет mutex — но mtx_ mutable
        ++hits_;                       // ✅ меняем статистику в const-методе
        return data_.at(key);
    }
};
```

### Ключевая идея: logical const vs bitwise const

- **Bitwise const** — ни один бит объекта не изменился (что и требует компилятор без `mutable`)
- **Logical const** — **наблюдаемое состояние** объекта не изменилось с точки зрения пользователя

`mutable` нужен, когда bitwise-константность слишком строга: внутренние детали (кеш, счётчик, мьютекс) меняются, но логическое состояние — нет.

### Канонические применения `mutable`

**1. Мьютекс** — самое частое и бесспорное:

```cpp
class ThreadSafeCounter {
    int value_ = 0;
    mutable std::mutex mtx_;   // без mutable нельзя лочить в const-методе
public:
    int get() const {
        std::lock_guard lock(mtx_);   // lock() модифицирует mutex
        return value_;
    }
};
```

Без `mutable` пришлось бы делать `get()` неконстантным — что абсурдно (чтение состояния не должно требовать неконстантного объекта).

**2. Ленивое вычисление / мемоизация:**

```cpp
class Matrix {
    std::vector<double> data_;
    mutable std::optional<double> cachedDet_;   // кеш детерминанта

public:
    double determinant() const {
        if (!cachedDet_)                        // ✅ вычисляем лениво
            cachedDet_ = computeDeterminant();  // ✅ пишем в кеш из const-метода
        return *cachedDet_;
    }
};
```

Логически объект не изменился — тот же детерминант вернётся при повторном вызове. Просто теперь быстрее.

**3. Счётчики/статистика** — метрики, не влияющие на поведение.

### `mutable` в лямбдах — другое значение!

Не путать. `mutable` у лямбды разрешает менять **захваченные по значению** переменные внутри тела:

```cpp
int counter = 0;

auto f = [counter]() mutable {   // без mutable — ошибка компиляции
    ++counter;                    // меняем СВОЮ КОПИЮ
    return counter;
};

f();  // 1
f();  // 2 — состояние сохраняется между вызовами (внутри самой лямбды)
std::cout << counter;   // 0 — ОРИГИНАЛ не изменился!
```

Причина: `operator()` лямбды по умолчанию **`const`**, а захваченные по значению переменные — члены сгенерированного класса. `mutable` снимает `const` с `operator()`.

```cpp
// лямбда [counter]() { ++counter; } разворачивается примерно в:
struct Lambda {
    int counter;
    auto operator()() const { ++counter; }   // ❌ const → нельзя менять counter
};
// с mutable:
    auto operator()() { ++counter; }         // ✅ не const
```

## Опасность: `mutable` + многопоточность

`const`-метод в C++ **подразумевает потокобезопасность для чтения** — стандартная библиотека это гарантирует для своих типов, и пользователи вправе ожидать того же. Если `mutable` член меняется без синхронизации, `const`-метод перестаёт быть thread-safe → **data race**:

```cpp
class BadCache {
    mutable std::optional<int> cached_;
public:
    int get() const {
        if (!cached_) cached_ = compute();   // ⚠️ ГОНКА при вызове из двух потоков!
        return *cached_;
    }
};
```

Два потока одновременно вызывают `get()` на одном `const`-объекте → оба пишут в `cached_` → data race, хотя формально «только читают».

**Правило: если есть `mutable` член, изменяемый в `const`-методе — синхронизируй его.**

```cpp
class GoodCache {
    mutable std::optional<int> cached_;
    mutable std::mutex mtx_;
public:
    int get() const {
        std::lock_guard lock(mtx_);
        if (!cached_) cached_ = compute();
        return *cached_;
    }
};
```

Либо `mutable std::atomic<...>`, если хватает.

## `const_cast` — снятие const

Формально позволяет убрать `const`, но:

**Модификация объекта, который изначально был `const` — UB:**

```cpp
const int x = 5;
const_cast<int&>(x) = 10;   // ⚠️ UB! x мог быть в read-only памяти
                             //    компилятор мог заинлайнить 5 везде

int y = 5;
const int& r = y;
const_cast<int&>(r) = 10;   // ✅ ОК — исходный объект y НЕ const
```

Легитимные применения `const_cast`:

1. **Устранение дублирования const/non-const перегрузок** (идиома выше)
2. **Взаимодействие с legacy C-API**, где забыли поставить `const`:

```cpp
void legacy_api(char* s);   // не меняет s, но const забыли

void wrapper(const std::string& s) {
    legacy_api(const_cast<char*>(s.c_str()));   // ⚠️ безопасно ТОЛЬКО если api реально не меняет
}
```

Во всех остальных случаях `const_cast` — признак ошибки дизайна.

---

## Практические рекомендации

- **Помечай `const` всё, что не меняется**: методы, параметры-ссылки, локальные переменные, указатели.
- **Пиши `const`-методы сразу**, а не потом — иначе придётся переделывать вызывающий код.
- **`mutable` — только для того, что не входит в логическое состояние**: мьютексы, кеши, счётчики, ленивая инициализация. Не для «обхода» константности.
- **`mutable` + `const`-метод → синхронизация обязательна** (иначе гонка).
- **`const_cast` — красный флаг** (кроме идиомы устранения дублирования и legacy C-API).

## Формулировки на собеседовании

**«Что означает `const` у метода?»** — `this` становится `const T*`, все члены — `const`; метод обещает не менять состояние; только такие методы можно звать у `const`-объекта.

**«Зачем `mutable`?»** — Для членов, не входящих в **логическое** состояние: мьютексы, кеши, счётчики. Позволяет менять их в `const`-методе, отделяя logical const от bitwise const.

**«Bitwise vs logical const?»** — Bitwise: ни один бит не изменился (то, что проверяет компилятор). Logical: наблюдаемое поведение объекта не изменилось. `mutable` — мост между ними.

**«Даёт ли `const` оптимизацию?»** — Как правило нет: компилятор не может полагаться на `const` из-за `const_cast` и алиасинга (кто-то может держать неконстантную ссылку на тот же объект). Исключение — объект, **объявленный** `const` (компилятор знает, что он в самом деле не менялся, может положить в .rodata и заинлайнить значение). `const` — про корректность, а не про скорость.

**«`const`-метод потокобезопасен?»** — Ожидается, что да (это контракт стандартной библиотеки). Но `mutable` члены без синхронизации это ломают — типичный источник скрытых гонок.

**«В чём разница `mutable` у члена и у лямбды?»** — Разные вещи: у члена снимает const-ограничение в const-методах; у лямбды снимает `const` с её `operator()`, позволяя менять захваченные по значению копии.

---

Отличие от Java: там `final` для поля означает «нельзя переприсвоить ссылку», но объект по ссылке **можно менять** (`final List<T> l` — `l.add()` работает). Аналога const-методов и глубокой const correctness нет вообще. `mutable`-проблематики тоже нет. Это одна из систем, которую Java-разработчик в C++ часто недооценивает: в C++ `const` — часть типа, влияет на разрешение перегрузок, и «забыть const» ломает совместимость с вызывающим кодом.
