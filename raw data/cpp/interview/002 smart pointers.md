# Smart pointers: устройство, control block, циклические ссылки

## `unique_ptr` — эксклюзивное владение

Владеет ресурсом единолично. Некопируем, только перемещаем.

**Устройство:** для stateless-deleter'а это буквально обёртка над одним указателем.

```cpp
template<class T, class D = default_delete<T>>
class unique_ptr {
    T* ptr_;          // + deleter через EBO (не занимает места, если пустой)
public:
    ~unique_ptr() { if (ptr_) get_deleter()(ptr_); }

    unique_ptr(const unique_ptr&) = delete;             // копирование запрещено
    unique_ptr(unique_ptr&& o) noexcept : ptr_(o.ptr_) { o.ptr_ = nullptr; }  // move — кража
};
```

- `sizeof(unique_ptr<T>) == sizeof(T*)` — нулевой оверхед
- Никаких счётчиков, никакой атомарности
- `release()` — отдать владение, `reset()` — заменить/освободить

Дефолтный выбор владеющего указателя. Используй его, если не нужно разделяемое владение.

## `shared_ptr` — разделяемое владение

Владение делится между несколькими `shared_ptr`. Объект живёт, пока жив хоть один. Основа — **control block** с атомарными счётчиками.

### Устройство: два указателя + control block

```cpp
template<class T>
class shared_ptr {
    T* ptr_;                    // указатель на сам объект
    ControlBlock* ctrl_;        // указатель на control block
};

struct ControlBlock {
    atomic<long> strong_count;  // сколько shared_ptr владеют
    atomic<long> weak_count;    // сколько weak_ptr наблюдают (+1 пока есть strong)
    // deleter, allocator (type-erased)
    // сам объект — если создан через make_shared
};
```

**`sizeof(shared_ptr) == 2 * sizeof(void*)`** — два указателя (объект + control block).

### Логика счётчиков

- Копирование `shared_ptr` → `++strong_count` (атомарно)
- Разрушение → `--strong_count`; когда дошло до **0** → **разрушается управляемый объект** (вызывается deleter)
- Когда `strong == 0` **и** `weak == 0` → освобождается сам control block

Два счётчика нужны, потому что объект и control block могут умирать в разные моменты: объект — когда `strong→0`, а блок — когда и `weak→0`.

# Почему в control block два счётчика

## Суть

Управляемый объект и сам control block — это **две разные вещи в памяти**, и они освобождаются в **разные моменты**:

- **Объект** разрушается, когда `strong_count → 0` (никто больше не владеет)
- **Control block** освобождается, когда `strong_count → 0` **И** `weak_count → 0` (никто больше не владеет и никто не наблюдает)

`weak_ptr` не должен продлевать жизнь объекта — но должен уметь **проверить, жив ли объект**. А чтобы проверять, ему нужен доступ к `strong_count`, который лежит в control block. Значит control block обязан пережить объект, пока есть хоть один `weak_ptr`. Отсюда — второй счётчик.

## Пошаговый пример

```cpp
struct Widget {
    int data = 42;
    ~Widget() { std::cout << "~Widget\n"; }
};

std::weak_ptr<Widget> wp;   // глобальный наблюдатель

void demo() {
    auto sp = std::make_shared<Widget>();   // [1]
    wp = sp;                                 // [2]

    std::cout << wp.expired() << "\n";       // [3] → 0 (жив)
    if (auto locked = wp.lock()) {           // [4]
        std::cout << locked->data << "\n";   //     → 42
    }                                        // [5]
}                                            // [6]  sp умирает

// [7] после demo():
std::cout << wp.expired() << "\n";           // → 1 (объект мёртв)
// [8] wp тоже когда-нибудь умрёт
```

### Разбор состояния счётчиков

**[1]** `make_shared<Widget>()` — одна аллокация: объект + control block рядом.

```
strong_count = 1   weak_count = 0
Widget жив
```

**[2]** `wp = sp` — weak-копия. Инкрементится **только weak**:

```
strong_count = 1   weak_count = 1
Widget жив
```

Важно: `wp` **не** держит объект живым — strong не тронут.

**[3]** `wp.expired()` — читает `strong_count`. `1 > 0` → `false`. Для этой проверки control block **обязан** существовать.

**[4]** `wp.lock()` — атомарно: `strong_count > 0`? Да → создаём временный `shared_ptr`, `++strong`:

```
strong_count = 2   weak_count = 1
Widget жив
```

**[5]** `locked` (временный shared_ptr) разрушается → `--strong`:

```
strong_count = 1   weak_count = 1
```

**[6]** выход из `demo()`, `sp` разрушается → `--strong` → **strong стал 0**:

```
strong_count = 0   weak_count = 1
→ ~Widget() ВЫЗЫВАЕТСЯ ЗДЕСЬ (печатается "~Widget")
→ но control block ЖИВ, потому что weak_count = 1
```

**Вот ключевой момент:** объект уже разрушен, а control block ещё существует — потому что `wp` на него смотрит и должен иметь возможность узнать `strong_count == 0`.

**[7]** `wp.expired()` — читает `strong_count` из **всё ещё живого** control block. `0` → `true`. Если бы блок освободился вместе с объектом, это чтение было бы use-after-free.

**[8]** когда `wp` разрушится → `--weak` → **weak стал 0**, а strong уже 0:

```
strong_count = 0   weak_count = 0
→ control block ОСВОБОЖДАЕТСЯ ЗДЕСЬ
```

---

## Визуально — две «смерти»

```
время →

strong: 1 ──── 2 ──── 1 ──────── 0 ═══════════════ 0
weak:   0 ──── 1 ──── 1 ──────── 1 ══════════════ 1 ──── 0
                                  │                        │
                             ~Widget()            освобождение
                          (объект умер)         control block'а
                                  │                        │
                          strong→0                  weak→0 (и strong=0)
                                  └── control block ЖИВ ───┘
                                      (wp ещё смотрит)
```

Между этими двумя точками control block жив, а объект — нет. `wp.expired()` в этом промежутке корректно возвращает `true`, читая живой счётчик.

## Что было бы с одним счётчиком

Представим гипотетический control block с одним счётчиком (только strong):

```cpp
// НЕПРАВИЛЬНО — один счётчик
struct BadBlock { atomic<long> count; };
```

Тогда при `strong → 0` пришлось бы освободить весь блок сразу. Но `wp` всё ещё хранит указатель на этот блок → любое `wp.expired()` / `wp.lock()` читало бы **освобождённую память** → use-after-free, UB.

Альтернатива без второго счётчика — заставить `weak_ptr` держать объект живым, но это уже не `weak_ptr`, а `shared_ptr` (и циклы снова текут).

Поэтому два счётчика — единственный способ дать `weak_ptr` семантику «наблюдаю, но не держу, и умею проверить живость безопасно».

## Нюанс с `make_shared`

Помнишь минус `make_shared` из прошлого сообщения — теперь он объясняется именно этим:

```cpp
auto sp = std::make_shared<BigWidget>();  // объект + блок в ОДНОМ куске памяти
std::weak_ptr<BigWidget> wp = sp;
sp.reset();   // strong→0: ~BigWidget() вызван, но ПАМЯТЬ не отдана ОС
              // потому что блок (weak_count=1) в том же куске → держит всё
// пока жив wp, вся память BigWidget'а занята, хоть объект и разрушен
```

При раздельной аллокации (`shared_ptr(new BigWidget)`) память объекта и блока — разные куски, поэтому память объекта отдаётся сразу при `strong→0`, а маленький блок висит отдельно до `weak→0`. Вот почему для больших объектов с долгоживущими `weak_ptr` иногда осознанно отказываются от `make_shared`.

**На собеседовании** формулировка: control block живёт до тех пор, пока на него ссылается хоть один `shared_ptr` **или** `weak_ptr`; управляемый объект — только пока есть `shared_ptr`. Два счётчика разделяют эти два времени жизни, что и позволяет `weak_ptr` безопасно проверять живость объекта, не удерживая его.

### `make_shared` vs `shared_ptr(new T)` — важный вопрос

```cpp
auto p = std::make_shared<Widget>(args);        // ОДНА аллокация
std::shared_ptr<Widget> q(new Widget(args));    // ДВЕ аллокации
```

`make_shared` выделяет объект **и** control block одним блоком памяти:

- Плюс: одна аллокация вместо двух (быстрее, лучше локальность)
- Плюс: exception-safe (нет «висячего» `new` при исключении в другом аргументе)
- Минус: память объекта не освобождается, пока живы `weak_ptr` (объект и блок в одном куске — блок держит weak_count, а значит держит и память объекта, хоть сам объект уже разрушен)

Для больших объектов с долгоживущими `weak_ptr` иногда предпочитают раздельную аллокацию именно из-за этого минуса.

### Атомарность — что thread-safe, а что нет (каверзный вопрос)

- **Счётчик** атомарен → можно копировать/разрушать один и тот же `shared_ptr` из разных потоков безопасно в смысле счётчика
- **Управляемый объект НЕ защищён** → одновременная запись в `*p` из двух потоков — data race, нужна своя синхронизация
- Сам объект `shared_ptr` (не его копии) при одновременной модификации из потоков — тоже гонка (нужен `atomic<shared_ptr>` в C++20 или `std::atomic_*` функции)

Формулировка: «shared_ptr гарантирует thread-safety **счётчика ссылок**, но не объекта и не самого указателя».

## `weak_ptr` — наблюдение без владения

Указывает на объект, которым владеет `shared_ptr`, **не** продлевая его жизнь. Решает две задачи: **циклические ссылки** и **безопасный доступ к возможно-удалённому объекту**.

```cpp
std::shared_ptr<Widget> sp = std::make_shared<Widget>();
std::weak_ptr<Widget> wp = sp;     // weak_count++, strong_count НЕ меняется

if (auto locked = wp.lock()) {     // atomic: если объект жив → shared_ptr, иначе nullptr
    locked->use();                 // здесь объект гарантированно жив
}                                  // locked разрушается — временное владение снято

wp.expired();                      // true, если strong_count == 0
```

`lock()` атомарно проверяет `strong_count > 0` и если да — создаёт `shared_ptr` (инкрементит strong). Это единственный **безопасный** способ доступа — нельзя просто «проверить expired() и потом обращаться», между проверкой и доступом объект может умереть в другом потоке.

## Циклические ссылки — утечка памяти

Классическая проблема `shared_ptr`: два объекта ссылаются друг на друга через `shared_ptr` → счётчики никогда не дойдут до 0.

```cpp
struct Node {
    std::shared_ptr<Node> next;
    std::shared_ptr<Node> prev;   // ← цикл!
};

auto a = std::make_shared<Node>();   // a.strong = 1
auto b = std::make_shared<Node>();   // b.strong = 1
a->next = b;                          // b.strong = 2
b->prev = a;                          // a.strong = 2

// выход из области: a и b как локальные умирают
// a.strong: 2 → 1 (b->prev всё ещё держит)
// b.strong: 2 → 1 (a->next всё ещё держит)
// оба остаются с count=1, деструкторы НЕ вызываются → УТЕЧКА
```

### Решение: разорвать цикл через `weak_ptr`

Одно из направлений связи делаем «наблюдающим», не владеющим:

```cpp
struct Node {
    std::shared_ptr<Node> next;   // владеет «вперёд»
    std::weak_ptr<Node>   prev;   // наблюдает «назад» — не держит
};

auto a = std::make_shared<Node>();   // a.strong = 1
auto b = std::make_shared<Node>();   // b.strong = 1
a->next = b;                          // b.strong = 2
b->prev = a;                          // a.strong = 1 (weak не инкрементит strong!)

// выход: b как локальная умирает → b.strong: 2→1
//        a как локальная умирает → a.strong: 1→0 → ~Node(a)
//        разрушение a обнуляет a->next → b.strong: 1→0 → ~Node(b)
// оба освобождены, утечки нет
```

**Правило:** владеющая связь — `shared_ptr`, обратная/наблюдающая — `weak_ptr`. Типичные примеры: parent владеет children через `shared_ptr`, child ссылается на parent через `weak_ptr`; observer'ы держат subject через `weak_ptr`; кеши.

## Сводная таблица

|                         | `unique_ptr`       | `shared_ptr`                       | `weak_ptr`             |
| ----------------------- | ------------------ | ---------------------------------- | ---------------------- |
| Владение                | эксклюзивное       | разделяемое                        | нет (наблюдение)       |
| Влияет на жизнь объекта | да                 | да (strong)                        | нет                    |
| Копируемость            | нет (только move)  | да                                 | да                     |
| Размер                  | 1 указатель        | 2 указателя                        | 2 указателя            |
| Оверхед                 | нулевой            | control block + атомарные счётчики | —                      |
| Доступ к объекту        | `*`, `->`, `get()` | `*`, `->`, `get()`                 | только через `.lock()` |

## Частые вопросы на собеседовании

**Почему у `shared_ptr` два указателя, а не один?** Управляемый указатель может отличаться от указателя на control block — например при aliasing constructor (shared_ptr на член объекта, разделяющий счётчик с владельцем целого объекта) или при указании на базовый класс.

**Что такое `enable_shared_from_this`?** Позволяет объекту безопасно получить `shared_ptr` на самого себя (`shared_from_this()`), переиспользуя существующий control block, а не создавая новый. Без него `shared_ptr<T>(this)` создал бы **второй** независимый control block → double-free.

**Дорого ли копировать `shared_ptr`?** Дороже, чем raw/unique — атомарный инкремент/декремент (барьеры памяти). В горячем коде передавай `const shared_ptr&` или сырой указатель/ссылку, если не нужно менять владение.

# Может ли управляемый указатель совпадать с указателем на control block?

Короткий ответ: **как значения указателей — практически никогда не совпадают** (они указывают на разные вещи), но при `make_shared` они указывают в **один и тот же выделенный блок памяти**, находясь рядом. Разберём, потому что тут легко запутать два разных вопроса.

## Два разных указателя внутри shared_ptr

Напомню устройство:

```cpp
template<class T>
class shared_ptr {
    T* ptr_;              // (1) указатель на управляемый ОБЪЕКТ (что даёт .get(), ->)
    ControlBlock* ctrl_;  // (2) указатель на CONTROL BLOCK (счётчики, deleter)
};
```

Это **всегда два отдельных поля**. Вопрос не в том, «одно поле или два» — их всегда два. Вопрос в том, **куда они указывают** и **совпадают ли адреса**.

---

## Случай 1: `make_shared` — рядом, но не совпадают

`make_shared` выделяет объект и control block **одним куском памяти**:

```cpp
auto sp = std::make_shared<Widget>();
```

```
        один malloc-блок
   ┌──────────────┬──────────────┐
   │ ControlBlock │    Widget     │
   └──────────────┴──────────────┘
   ^              ^
   ctrl_          ptr_
```

- `ptr_` и `ctrl_` указывают в **один и тот же аллоцированный регион**
- но **адреса разные** — `ptr_` смещён относительно `ctrl_` на размер control block'а
- `ptr_ != (T*)ctrl_` — это разные адреса

Так что даже в самом «слитном» случае значения указателей не равны. Просто они близко и живут/умирают вместе как единый malloc-блок.

(Порядок «блок, потом объект» — деталь реализации; у libstdc++/libc++ раскладка может отличаться, суть та же.)

---

## Случай 2: `shared_ptr(new Widget)` — вообще разные аллокации

```cpp
std::shared_ptr<Widget> sp(new Widget);
```

```
   аллокация A            аллокация B (отдельный malloc внутри shared_ptr)
   ┌──────────┐           ┌──────────────┐
   │  Widget   │          │ ControlBlock │
   └──────────┘           └──────────────┘
   ^                      ^
   ptr_                   ctrl_
```

Тут даже физически два разных куска памяти. Адреса очевидно разные и не связаны смещением. (Это и есть «две аллокации» — минус по сравнению с `make_shared`.)

---

## Случай 3: aliasing constructor — специально «разъезжаются»

Здесь `ptr_` намеренно указывает **не** на управляемый объект целиком, а на его часть, при этом счётчик разделяется:

```cpp
struct Widget {
    std::string name;
    int value;
};

auto owner = std::make_shared<Widget>();          // владеет всем Widget
std::shared_ptr<int> member(owner, &owner->value); // aliasing constructor
```

```
   ┌──────────────┬──────────────────────┐
   │ ControlBlock │  Widget{name, value} │
   └──────────────┴──────────────────────┘
   ^                             ^
   ctrl_ (общий с owner)         ptr_ → &value (середина объекта!)
```

- `member.get()` возвращает `&value` — указатель **внутрь** объекта
- но control block — **тот же**, что у `owner` → счётчик общий
- пока жив `member`, жив весь `Widget` (strong_count держит целое)
- `ptr_` и «начало объекта» тут даже не совпадают — `ptr_` показывает в середину

Это применяется, когда нужно раздать `shared_ptr` на подобъект/член, но время жизни привязать к владельцу целого.

---

## Случай 4: указатель на базовый класс

```cpp
struct Base { virtual ~Base() = default; };
struct Derived : Base { /*...*/ };

std::shared_ptr<Derived> d = std::make_shared<Derived>();
std::shared_ptr<Base> b = d;   // ptr_ может «сдвинуться» к суб-объекту Base
```

При множественном наследовании суб-объект `Base` может лежать не в начале `Derived`, поэтому `ptr_` в `b` — это адрес Base-части, отличный от адреса начала `Derived`. Control block — общий.

---

## Прямой ответ на вопрос

**«Может ли управляемый указатель не отличаться от указателя на control block?»**

Как **значения адресов** — практически никогда: `ptr_` указывает на объект (или его часть), `ctrl_` — на структуру со счётчиками, это разные адреса даже при `make_shared` (соседние, но не равные).

Как **факт наличия двух полей** — они всегда отдельные. Причина, по которой в `shared_ptr` держат именно два указателя, а не вычисляют один из другого, как раз в случаях 3 и 4: связь «объект ↔ control block» не фиксирована каким-то постоянным смещением, поэтому `ptr_` нельзя восстановить из `ctrl_`. При aliasing и при приведении к базе они «разъезжаются» произвольно, и оба нужно хранить явно.

---

**На собеседовании** формулировка: `shared_ptr` хранит два указателя, потому что адрес управляемого объекта не выводится из адреса control block'а — они совпадают по «региону» только при `make_shared`, но в общем случае (aliasing constructor, приведение к базовому классу, отдельная аллокация) указывают на разные, произвольно смещённые адреса. Поэтому оба поля хранятся независимо.

# `enable_shared_from_this`

## Проблема, которую он решает

Иногда объекту нужно получить `shared_ptr` **на самого себя** — например, чтобы передать себя куда-то (в колбэк, в контейнер, в асинхронную операцию), сохранив разделяемое владение.

Наивная попытка ломается:

```cpp
struct Widget {
    std::shared_ptr<Widget> getSelf() {
        return std::shared_ptr<Widget>(this);   // ← КАТАСТРОФА
    }
};

auto sp1 = std::make_shared<Widget>();   // control block #1, strong=1
auto sp2 = sp1->getSelf();               // control block #2 (НОВЫЙ!), strong=1
```

Проблема: `shared_ptr<Widget>(this)` создаёт **второй, независимый control block** для того же объекта. Теперь два счётчика ничего не знают друг о друге:

```
sp1 → [control block #1: strong=1] ──┐
                                      ├──→ один и тот же Widget
sp2 → [control block #2: strong=1] ──┘
```

Когда `sp2` умрёт → его strong→0 → **`delete` объекта**. А `sp1` всё ещё думает, что объект жив → при его разрушении → **второй `delete`** → **double-free, UB**.

---

## Решение — `enable_shared_from_this`

Наследуемся от `std::enable_shared_from_this<T>` (CRTP — базовый класс параметризован самим наследником):

```cpp
struct Widget : std::enable_shared_from_this<Widget> {
    std::shared_ptr<Widget> getSelf() {
        return shared_from_this();   // переиспользует СУЩЕСТВУЮЩИЙ control block
    }
};

auto sp1 = std::make_shared<Widget>();   // control block #1, strong=1
auto sp2 = sp1->getSelf();               // ТОТ ЖЕ control block #1, strong=2
```

```
sp1 ─┐
     ├──→ [control block #1: strong=2] ──→ Widget
sp2 ─┘
```

Теперь оба `shared_ptr` разделяют один счётчик. Объект удалится ровно один раз, когда strong дойдёт до 0.

---

## Как это работает внутри

`enable_shared_from_this<T>` хранит **`weak_ptr<T>` на самого себя**:

```cpp
template<class T>
class enable_shared_from_this {
    mutable std::weak_ptr<T> weak_this_;   // наблюдает за собственным объектом
public:
    std::shared_ptr<T> shared_from_this() {
        return std::shared_ptr<T>(weak_this_);   // lock'ает weak → shared с общим блоком
    }
    std::weak_ptr<T> weak_from_this() { return weak_this_; }  // C++17
};
```

Ключевой момент: когда `shared_ptr` **впервые** создаётся для объекта, унаследованного от `enable_shared_from_this`, конструктор `shared_ptr` **обнаруживает** это (через специальную проверку типа) и **инициализирует** `weak_this_`, привязывая его к своему control block:

```cpp
auto sp = std::make_shared<Widget>();
// внутри: shared_ptr замечает, что Widget : enable_shared_from_this
//         → записывает в widget.weak_this_ = weak_ptr на этот control block
```

Дальше `shared_from_this()` просто делает `weak_this_.lock()` — получает `shared_ptr`, разделяющий тот самый блок. Weak (а не shared) — чтобы не было цикла «объект держит shared_ptr на себя».

---

## Критическое требование: объект уже должен управляться shared_ptr

`shared_from_this()` работает **только если объект уже принадлежит какому-то `shared_ptr`**. Иначе `weak_this_` не инициализирован.

### Ошибка 1: объект на стеке

```cpp
Widget w;                    // на стеке, никакого shared_ptr нет
auto sp = w.shared_from_this();   // weak_this_ пустой
// C++17+: бросает std::bad_weak_ptr
// до C++17: UB
```

### Ошибка 2: вызов из конструктора

```cpp
struct Widget : std::enable_shared_from_this<Widget> {
    Widget() {
        auto self = shared_from_this();   // ← ЕЩЁ рано!
        // объект в процессе создания, shared_ptr снаружи ещё не существует,
        // weak_this_ не инициализирован → bad_weak_ptr
    }
};
```

Инициализация `weak_this_` происходит **после** того, как конструктор объекта отработал и `shared_ptr` его «принял». Поэтому в конструкторе `shared_from_this()` вызывать нельзя.

**Обходной паттерн** — фабрика + init после создания:

```cpp
struct Widget : std::enable_shared_from_this<Widget> {
private:
    Widget() = default;
    void init() {
        // здесь shared_from_this() уже валиден
        registerCallback(shared_from_this());
    }
public:
    static std::shared_ptr<Widget> create() {
        auto p = std::shared_ptr<Widget>(new Widget());   // теперь weak_this_ инициализирован
        p->init();                                         // безопасно
        return p;
    }
};
```

## Классический пример: async с Boost.Asio

Прямо релевантно твоему стеку (Asio + coroutines). Типичная идиома — продлить жизнь объекта на время асинхронной операции, захватив `shared_from_this()` в лямбду-хендлер:

```cpp
class Session : public std::enable_shared_from_this<Session> {
    boost::asio::ip::tcp::socket socket_;
    std::array<char, 1024> buf_;
public:
    void read() {
        auto self = shared_from_this();   // +1 strong: объект жив, пока операция в полёте
        socket_.async_read_some(
            boost::asio::buffer(buf_),
            [this, self](auto ec, auto n) {   // self держит объект живым в колбэке
                if (!ec) {
                    process(n);
                    read();                    // следующая операция снова захватит self
                }
                // когда цепочка операций закончится и self выйдет из scope → strong-1
            });
    }
};
```

Без `self` объект мог бы быть разрушен (например, при закрытии соединения) **пока асинхронная операция ещё выполняется** → хендлер обратился бы к мёртвому `this` → UB. Захват `shared_from_this()` гарантирует, что объект переживёт операцию.

Это стандартный паттерн «shared_ptr + async» в сетевом коде на Asio — почти наверняка всплывёт, если собеседование связано с сетью/асинхронщиной.

## Нюансы для собеседования

**Наследование должно быть публичным:**

```cpp
struct Widget : std::enable_shared_from_this<Widget> { };   // public
```

**Проблема наследования иерархий** — если и база, и наследник хотят `enable_shared_from_this`, наследоваться должна только база, а `shared_from_this()` вернёт указатель на тип базы (нужен `static_pointer_cast` для приведения к наследнику).

**`weak_from_this()` (C++17)** — если нужен `weak_ptr` без немедленного продления жизни (например, чтобы сохранить наблюдателя, не удерживая объект).

**Почему внутри weak, а не shared?** Если бы `enable_shared_from_this` хранил `shared_ptr` на себя — объект держал бы сам себя → strong_count никогда не дошёл бы до 0 → объект никогда не удалится (тот же цикл, что мы разбирали). Поэтому строго `weak_ptr`.

---

**Формулировка на собеседовании:** `enable_shared_from_this` даёт объекту способ получить `shared_ptr` на себя, переиспользуя уже существующий control block вместо создания нового (что привело бы к double-free). Работает через хранимый `weak_ptr`, который инициализируется в момент, когда объект впервые попадает под управление `shared_ptr`. Отсюда два ограничения: нельзя звать из конструктора и нельзя звать для объекта, не управляемого `shared_ptr` (иначе `bad_weak_ptr`).

EBO — **Empty Base Optimization** (оптимизация пустого базового класса).

## Проблема

В C++ любой объект обязан иметь размер **минимум 1 байт**, даже если у него нет полей. Это нужно, чтобы у разных объектов были разные адреса.

```cpp
struct Empty {};                    // нет полей
static_assert(sizeof(Empty) == 1);  // но размер = 1, не 0
```

Если положить пустой класс **полем**, он займёт место (плюс возможный padding):

```cpp
struct Foo {
    int x;        // 4 байта
    Empty e;      // +1 байт → +3 padding = 8 байт всего
};
static_assert(sizeof(Foo) == 8);
```

## Решение — EBO

Стандарт разрешает пустому **базовому классу** занимать **ноль байт** в наследнике (у него нет своих данных, а адрес можно разделить с наследником).

```cpp
struct Foo : Empty {   // наследуем, а не храним полем
    int x;
};
static_assert(sizeof(Foo) == 4);   // Empty занял 0 байт!
```

## Причём тут smart pointers

Именно так `unique_ptr` добивается нулевого оверхеда для stateless-deleter'а. Если бы deleter хранился **полем**, каждый `unique_ptr` был бы толще на байт(ы):

```cpp
// наивно — deleter полем:
template<class T, class D>
class unique_ptr {
    T* ptr_;
    D  deleter_;   // пустой FileCloser занял бы место + padding → 16 байт
};
```

Реальные реализации хранят указатель и deleter в чём-то вроде сжатой пары, наследуясь от deleter'а. Пустой deleter → EBO → он занимает 0 байт → `sizeof(unique_ptr) == sizeof(T*)`.

```cpp
std::unique_ptr<FILE, FileCloser>  // FileCloser пустой → EBO → размер = 1 указатель
```

Если бы deleter имел состояние (поля), EBO не сработала бы, и размер вырос бы.

## Где встретишь на практике

- `std::unique_ptr` (deleter)
- `std::vector`, `std::map` и др. (аллокатор — обычно пустой, EBO прячет его)
- `std::tuple` (пустые типы)
- Раньше — `boost::compressed_pair`; в C++20 появился атрибут **`[[no_unique_address]]`**, который даёт тот же эффект для **полей** (не требуя наследования):

```cpp
template<class T, class D>
class unique_ptr {
    T* ptr_;
    [[no_unique_address]] D deleter_;   // C++20: пустой D займёт 0 байт как поле
};
```

## На собеседовании

Если спросят «почему `unique_ptr` со stateless-deleter'ом весит как один указатель, хотя deleter где-то хранится?» — ответ: **EBO** (или `[[no_unique_address]]` в C++20). Deleter наследуется, а пустой базовый класс занимает 0 байт. Хороший маркер понимания того, как zero-overhead abstractions реализуются на уровне layout'а.

---

Отличие от Java: там GC сам разбирает даже циклы (mark-and-sweep находит недостижимые объекты). В C++ reference counting **не** справляется с циклами — отсюда и нужен `weak_ptr` вручную. Это принципиальный момент: reference counting детерминированен и без пауз GC, но требует от программиста осознанно разрывать циклы. Частый вопрос — «почему shared_ptr течёт на циклах, а Java GC нет?».
