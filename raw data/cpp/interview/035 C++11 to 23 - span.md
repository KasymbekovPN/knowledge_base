# `std::span` (C++20)

## Что это

**Невладеющий view на непрерывную последовательность объектов** любого типа. Обобщение `string_view` на произвольные `T`.

```cpp
#include <span>

std::span<int> s;   // указатель + размер

// Устройство (dynamic extent):
class span {
    T* data_;
    size_t size_;
};
sizeof(std::span<int>);   // 16 на 64-bit
```

`string_view` : `char` = `span` : любой `T`. Только `span` может быть **мутабельным** (`span<int>` позволяет менять элементы, `string_view` — нет).

---

## Проблема, которую решает

Классическая C++ проблема — передача массива в функцию:

```cpp
// ❌ Указатель + размер — легко перепутать, легко ошибиться
void process(int* data, size_t size);
process(arr, 10);        // ⚠️ а если размер неверен? UB
process(arr, 100);       // ⚠️ компилятор молчит

// ❌ Только vector — не принимает массив, std::array, подмассив
void process(std::vector<int>& v);
process(cArray);         // ❌ не скомпилируется
process(stdArray);       // ❌ тоже

// ❌ Шаблон — работает, но код раздувается, и заголовок обязателен
template<class Container>
void process(Container& c);

// ✅ span — единый интерфейс, размер внутри
void process(std::span<int> s);
process(vec);                    // ✅
process(arr);                    // ✅ C-массив — размер выводится!
process(stdArray);               // ✅
process({ptr, len});             // ✅ сырой буфер
process(std::span(vec).subspan(2, 5));   // ✅ подмножество
```

Главное: **span несёт размер с собой** → `size()` доступен, границы известны.

## Конструирование

```cpp
std::vector<int> v{1,2,3,4,5};
int arr[5] = {1,2,3,4,5};
std::array<int,5> a{1,2,3,4,5};

std::span<int> s1 = v;              // из vector
std::span<int> s2 = arr;            // ✅ из C-массива — РАЗМЕР ВЫВОДИТСЯ автоматически!
std::span<int> s3 = a;              // из std::array
std::span<int> s4(ptr, len);        // из указателя + длины
std::span<int> s5(begin, end);      // из пары итераторов

std::span<const int> cs = v;        // ✅ read-only view
```

Ключевое отличие от `int*`: **из C-массива размер выводится компилятором** — распада (decay) не происходит.

```cpp
void old(int* p) { /* размер? неизвестен */ }
void neu(std::span<int> s) { s.size(); /* ✅ 5 */ }

int arr[5];
old(arr);   // ⚠️ распад до int* — размер потерян
neu(arr);   // ✅ span<int> с size()==5
```

## API

```cpp
std::span<int> s = v;

s.size();
s.size_bytes();        // размер в БАЙТАХ
s.empty();
s[0];                  // ⚠️ без проверки границ (как у vector)
s.front(), s.back();
s.data();              // T*

// Итераторы — работают все алгоритмы
for (int x : s) { }
std::sort(s.begin(), s.end());   // ✅
std::ranges::sort(s);             // ✅ span — это range

// Подмножества — все O(1)
s.first(3);            // первые 3 элемента
s.last(3);             // последние 3
s.subspan(2, 5);       // с индекса 2, длиной 5
s.subspan(2);          // с индекса 2 до конца
```

Все операции создания подмножества — **O(1)**, просто новый span (указатель + размер).

**Мутабельность:**

```cpp
std::span<int> s = v;
s[0] = 42;           // ✅ меняет v[0] — span НЕ владеет, но даёт доступ на запись

std::span<const int> cs = v;
cs[0] = 42;          // ❌ ошибка компиляции
```

## Static extent — размер в типе

Второй параметр шаблона — размер, известный на этапе компиляции:

```cpp
template<class T, size_t Extent = std::dynamic_extent>
class span;
```

```cpp
std::span<int, 5> fixed = arr;      // размер В ТИПЕ — sizeof == 8 (только указатель!)
std::span<int> dynamic = arr;       // размер в рантайме — sizeof == 16

fixed.size();     // ✅ constexpr — известно на этапе компиляции
```

**Преимущества static extent:**

- **Меньше размер** (8 vs 16 байт — размер не хранится)
- Компилятор знает границы → лучше оптимизации, возможен unrolling
- Несовпадение размера — **ошибка компиляции**:

```cpp
int arr3[3];
std::span<int, 5> s = arr3;   // ❌ ОШИБКА КОМПИЛЯЦИИ — размеры не совпадают
```

```cpp
void process3(std::span<int, 3> s);   // ✅ ТОЛЬКО массивы из 3 элементов
process3(arr3);   // ✅
process3(arr5);   // ❌ ошибка компиляции
```

Преобразование static → dynamic безопасно, обратное — требует явности:

```cpp
std::span<int, 5> fixed = arr;
std::span<int> dyn = fixed;                            // ✅ неявно
std::span<int, 5> back = fixed.first<5>();             // ✅ статические подмножества
auto sub = dyn.subspan<2, 3>();                        // ✅ span<int, 3> — статически
```

## Практические применения

### 1. Параметр функции — дефолт для «массив только для чтения/записи»

```cpp
// Чтение:
int sum(std::span<const int> data) {
    return std::accumulate(data.begin(), data.end(), 0);
}

// Запись:
void fill(std::span<int> data, int value) {
    std::ranges::fill(data, value);
}

std::vector<int> v(10);
int arr[10];
fill(v, 1);      // ✅
fill(arr, 1);    // ✅
sum(v);          // ✅
```

Одна функция — все контейнеры с непрерывной памятью.

### 2. Работа с бинарными данными

```cpp
std::span<std::byte> bytes = std::as_writable_bytes(std::span(v));   // ✅ view на байты
std::span<const std::byte> cbytes = std::as_bytes(std::span(v));     // ✅ read-only

// Сетевой буфер:
void parsePacket(std::span<const std::byte> packet) {
    auto header = packet.first(8);
    auto payload = packet.subspan(8);   // ✅ O(1), без копий
}
```

`as_bytes` / `as_writable_bytes` — легальный способ смотреть на объект как на байты (мы разбирали в теме `reinterpret_cast`: доступ через `std::byte*` — исключение из strict aliasing).

### 3. Zero-copy обработка

```cpp
// Разбить буфер на чанки без копирования
void processChunks(std::span<const int> data, size_t chunkSize) {
    for (size_t i = 0; i < data.size(); i += chunkSize) {
        auto chunk = data.subspan(i, std::min(chunkSize, data.size() - i));
        process(chunk);   // ✅ ноль аллокаций
    }
}
```

### 4. Матрицы / многомерные данные (до `mdspan`)

```cpp
class Matrix {
    std::vector<double> data_;
    size_t rows_, cols_;
public:
    std::span<double> row(size_t r) {
        return std::span(data_).subspan(r * cols_, cols_);   // ✅ строка как span
    }
};
```

(C++23 добавил `std::mdspan` — полноценный многомерный view.)

## Ловушки

### 1. Dangling — та же опасность, что у `string_view`

```cpp
std::span<int> bad() {
    std::vector<int> v{1,2,3};
    return v;              // ⚠️ v умрёт → span повиснет → UB
}

std::span<int> s = getVector();    // ⚠️ временный вектор умирает
s[0];                               // ⚠️ UB

std::vector<int> v{1,2,3};
std::span<int> sp = v;
v.push_back(4);                     // ⚠️ РЕАЛЛОКАЦИЯ → sp повис!
sp[0];                              // ⚠️ UB
```

Последний случай — прямое следствие инвалидации итераторов `vector` (мы это разбирали). `span` — по сути пара итераторов, и умирает вместе с ними.

**Правило то же:** span — для параметров и локального использования. Не храни в членах, не возвращай (если не гарантируешь время жизни источника).

### 2. Нет проверки границ у `operator[]`

```cpp
std::span<int> s(arr, 3);
s[10];   // ⚠️ UB — как у vector::operator[]
```

`span` **не имеет** `at()` (в отличие от `vector`). Проверка границ — на тебе.

Некоторые реализации (MSVC в debug, `_GLIBCXX_ASSERTIONS`) добавляют проверки. Gsl::span (из Guidelines Support Library) — проверяет всегда, что и было изначальной мотивацией: `span` пришёл в стандарт именно из GSL как средство борьбы с buffer overflow.

### 3. Только непрерывная память

```cpp
std::list<int> l;
std::span<int> s = l;    // ❌ ОШИБКА — list не contiguous

std::deque<int> d;
std::span<int> s2 = d;   // ❌ ОШИБКА — deque не contiguous (чанки!)
```

Работает только с `vector`, `array`, C-массивами, `string`, и всем, что удовлетворяет `contiguous_range` (мы разбирали категории итераторов — вот где `contiguous_iterator` из C++20 и нужен).

### 4. `span<const T>` vs `const span<T>`

Классическая путаница (top-level vs low-level const — мы это разбирали):

```cpp
std::span<const int> a = v;   // low-level: ЭЛЕМЕНТЫ const, сам span можно переприсвоить
a[0] = 1;                      // ❌ ошибка
a = otherSpan;                 // ✅ ОК

const std::span<int> b = v;   // top-level: САМ SPAN const, элементы изменяемы!
b[0] = 1;                      // ✅ ОК! (span не владеет — const у span не транзитивен)
b = otherSpan;                 // ❌ ошибка
```

**Для read-only параметра нужен `span<const T>`, не `const span<T>`.** Точно как `const char*` vs `char* const`.

Это следствие того, что `span` — **view**, а не контейнер: его `const` не распространяется на элементы (в отличие от `const vector<int>`, где элементы становятся const).

## `span` vs `string_view` vs `vector`

| |`std::span<T>`|`std::string_view`|`std::vector<T>`|
|---|---|---|---|
|Владение|❌|❌|✅|
|Мутабельность элементов|✅ (если не `const T`)|❌ (всегда const)|✅|
|Типы|любой `T`|только `char`|любой `T`|
|Строковые операции|❌|✅ (`find`, `starts_with`)|❌|
|Размер|16 (dyn) / 8 (static)|16|24|
|Аллокация|❌|❌|✅|
|Static extent|✅|❌|❌|

## Формулировки на собеседовании

**«Что такое `std::span`?»** — Невладеющий view на **непрерывную** последовательность объектов: указатель + размер. Обобщение `string_view` на произвольные типы, с возможностью **мутации** элементов.

**«Зачем, если есть указатель + размер?»** — Размер **инкапсулирован** и не может рассинхронизироваться; из C-массива выводится автоматически (нет decay); работает единообразно с `vector`, `array`, C-массивом, сырым буфером; поддерживает итераторы и алгоритмы.

**«Главная опасность?»** — **Dangling**, как у `string_view`: не владеет данными. Особенно коварна реаллокация `vector` — span повисает, точно как итераторы.

**«В чём разница `span<const T>` и `const span<T>`?»** — `span<const T>` — **элементы** const (low-level), сам span переприсваиваем. `const span<T>` — **сам span** const (top-level), но **элементы изменяемы** (const у view не транзитивен!). Для read-only нужен первый.

**«Что даёт static extent?»** — Размер в типе (`span<int, 5>`): sizeof 8 вместо 16, `size()` — constexpr, несовпадение размера — **ошибка компиляции**, лучше оптимизации.

**«С какими контейнерами не работает?»** — С непрерывными — работает (`vector`, `array`, C-массив, `string`). Не работает с `list`, `deque`, `map` — память не непрерывна.

**«Откуда взялся?»** — Из **GSL** (Guidelines Support Library, Core Guidelines) как средство борьбы с buffer overflow: заменить «сырой указатель + размер» на безопасную абстракцию, несущую границы.

---

Отличие от Java: там прямого аналога **нет**. Массивы в Java всегда несут длину (`arr.length`) и проверяются в рантайме (`ArrayIndexOutOfBoundsException`) — то есть проблема «указатель без размера», которую решает `span`, в Java **просто не существует**. Для подмножества без копии есть `ByteBuffer.slice()` и `Arrays.asList()` (view на массив), но общего механизма нет. Ближайшее по духу — **`MemorySegment`** (Java 21, Foreign Function & Memory API) — view на область памяти с границами, для взаимодействия с нативным кодом. Ещё аналогия: Java `List.subList()` — тоже view (изменения видны в оригинале), но с fail-fast проверкой при модификации источника, тогда как в C++ реаллокация `vector` даёт **тихий dangling**. Это повторяющийся паттерн, который мы уже видели: там, где GC-язык даёт исключение, C++ даёт UB — и потому требует дисциплины «принимай view, храни владеющий тип».
