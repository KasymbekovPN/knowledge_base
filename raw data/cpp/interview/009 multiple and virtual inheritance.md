# Множественное и виртуальное наследование, ромб

## Множественное наследование

C++ позволяет наследоваться от нескольких баз одновременно (в отличие от Java, где только один `extends`):

```cpp
struct Serializable { virtual void save() = 0; };
struct Printable    { virtual void print() = 0; };

struct Document : Serializable, Printable {
    void save()  override { }
    void print() override { }
};
```

Пока базы независимы — проблем нет. Это частый и безопасный случай: наследование от нескольких **интерфейсов** (абстрактных классов без данных).

### Раскладка памяти и сдвиг указателя

Мы это упоминали в контексте vtable — теперь подробно. Каждая полиморфная база даёт свой **vptr** и свой суб-объект:

```cpp
struct A { virtual void fa(); int a_; };
struct B { virtual void fb(); int b_; };
struct C : A, B { void fa() override; void fb() override; int c_; };
```

```
C объект (64-bit):
адрес    ┌──────────────┐
+0       │ vptr_A       │──> vtable для A-части C
+8       │ a_           │
+16      │ vptr_B       │──> vtable для B-части C   ← начало B-суб-объекта
+24      │ b_           │
+32      │ c_           │
         └──────────────┘
```

**Критическое следствие — приведение к базе сдвигает указатель:**

```cpp
C c;
A* pa = &c;   // pa == адрес c        (offset 0)
B* pb = &c;   // pb == адрес c + 16   (offset B-части) — ДРУГОЙ АДРЕС!

std::cout << (void*)&c << " " << (void*)pa << " " << (void*)pb;
// печатает, например: 0x7ffd1000  0x7ffd1000  0x7ffd1010
```

Указатель `B*` обязан «выглядеть» как настоящий `B` — с vptr в начале своей части. Поэтому компилятор при приведении добавляет offset. Обратное приведение (`static_cast<C*>(pb)`) offset вычитает.

Это и есть причина, по которой `shared_ptr` хранит **два** указателя (объект и control block) — при приведении к базе указатель на объект «уезжает», а control block остаётся тот же.

**Ловушка:** сравнение указателей разных типов:

```cpp
if ((void*)pa == (void*)pb) { }   // FALSE! хотя это один и тот же объект
if (pa == static_cast<A*>(pb)) { } // TRUE — корректное сравнение через общий тип
```

### Thunk

Когда `pb->fb()` вызывает `C::fb()`, а `C::fb` ожидает `this` типа `C*` (offset 0), но получил `B*` (offset 16) — компилятор вставляет **thunk**: маленькую переходную функцию, которая корректирует `this` (вычитает 16) и прыгает в реальную `C::fb`. В vtable B-части лежит адрес thunk'а, а не самой `C::fb`.

## Проблема ромба (diamond problem)

Возникает, когда два базовых класса имеют **общего предка**:

```cpp
struct Animal {
    int age_;
    virtual void speak();
};

struct Mammal : Animal { };
struct Bird   : Animal { };

struct Bat : Mammal, Bird { };   // ромб!
```

```
        Animal
        /    \
   Mammal    Bird
        \    /
         Bat
```

### Что происходит без виртуального наследования

**`Bat` содержит ДВЕ копии `Animal`:**

```
Bat объект:
┌────────────────────┐
│ Mammal::Animal::age_ │  ← копия #1
├────────────────────┤
│ Bird::Animal::age_   │  ← копия #2
└────────────────────┘
```

Последствия:

```cpp
Bat b;
b.age_ = 5;        // ❌ ОШИБКА КОМПИЛЯЦИИ: ambiguous — какой age_?

b.Mammal::age_ = 5;   // приходится уточнять
b.Bird::age_ = 3;     // ...и это ДВЕ РАЗНЫЕ переменные

Animal* p = &b;    // ❌ ОШИБКА: ambiguous — к какому Animal приводить?
Animal* p = static_cast<Mammal*>(&b);   // приходится уточнять путь
```

Дублируется всё: данные, vptr, конструктор `Animal` вызывается **дважды**. Логически неверно — летучая мышь одно животное, а не два.

---

## Виртуальное наследование — решение

Ключевое слово `virtual` при наследовании говорит: «этот базовый суб-объект — **разделяемый**, если он встретится в иерархии несколько раз, экземпляр должен быть один».

```cpp
struct Animal {
    int age_;
    virtual void speak();
};

struct Mammal : virtual Animal { };   // ← virtual
struct Bird   : virtual Animal { };   // ← virtual

struct Bat : Mammal, Bird { };
```

Теперь `Bat` содержит **одну** копию `Animal`:

```
Bat объект:
┌──────────────────┐
│ Mammal-часть     │
├──────────────────┤
│ Bird-часть       │
├──────────────────┤
│ Animal (одна!)   │  ← разделяется обеими ветками
└──────────────────┘
```

```cpp
Bat b;
b.age_ = 5;        // ✅ однозначно — один age_
Animal* p = &b;    // ✅ однозначно
```

`virtual` должен стоять **у промежуточных классов** (Mammal, Bird), а не у Bat. Именно они объявляют «мой Animal — разделяемый».

---

## Как виртуальное наследование реализовано

Проблема: `Mammal` компилируется **сам по себе**, не зная, будет ли он частью ромба. Смещение до `Animal`-части не может быть зашито статически — оно зависит от полного (most-derived) типа:

- В отдельном `Mammal` объекте `Animal` лежит на одном offset'е
- В `Bat` объекте `Animal` — на другом (в конце, разделяемая)

Решение: **offset до виртуальной базы ищется в рантайме**, обычно через vtable (в GCC/Clang — через **vtt** и записи vbase_offset в vtable):

```
Mammal объект (сам по себе):        Bat объект:
┌──────────────┐                   ┌──────────────┐
│ vptr            │───┐               │ vptr(Mammal)   │───┐
├──────────────┤   │               ├──────────────┤   │
│ mammal-данные  │   │               │ vptr(Bird)     │   │
├──────────────┤   │               ├──────────────┤   │
│ Animal          │   │               │ Animal         │<──┘ (offset ДРУГОЙ)
└──────────────┘   │               └──────────────┘
                      v
            vtable: [vbase_offset, ..., функции]
                     ^^^^^^^^^^^^ смещение до Animal — читается в рантайме
```

Доступ к `age_` через `Mammal*` требует: прочитать vptr → взять vbase_offset из vtable → прибавить к `this` → получить адрес Animal-части. Это **дополнительное косвенное обращение** на каждый доступ к члену виртуальной базы.

**Цена виртуального наследования:**

- Больше памяти (доп. указатели/смещения)
- Доступ к членам виртуальной базы — медленнее (косвенность через vtable)
- `static_cast` от виртуальной базы вниз (`Animal*` → `Mammal*`) **запрещён** — нужен `dynamic_cast` (компилятор не знает offset статически)

```cpp
Animal* p = &bat;
Mammal* m = static_cast<Mammal*>(p);    // ❌ ошибка компиляции
Mammal* m = dynamic_cast<Mammal*>(p);   // ✅ рантайм-разрешение
```

## Инициализация виртуальной базы — неочевидное правило

**Виртуальную базу инициализирует most-derived класс напрямую**, минуя промежуточные:

```cpp
struct Animal {
    int age_;
    Animal(int a) : age_(a) { }
};

struct Mammal : virtual Animal {
    Mammal() : Animal(1) { }   // этот вызов ИГНОРИРУЕТСЯ при создании Bat!
};

struct Bird : virtual Animal {
    Bird() : Animal(2) { }     // тоже игнорируется
};

struct Bat : Mammal, Bird {
    Bat() : Animal(3),         // ← Bat ОБЯЗАН инициализировать Animal сам
            Mammal(), Bird() { }
};

Bat b;   // b.age_ == 3
```

Логика: раз `Animal` **один**, кто-то должен решить, как его конструировать. Оба промежуточных класса претендуют — конфликт. Стандарт назначает ответственным most-derived класс.

**Следствие:** если у `Animal` нет default-конструктора, `Bat` **обязан** явно вызвать `Animal(...)` в списке инициализации, иначе ошибка компиляции. И промежуточные классы `Mammal`/`Bird` тоже обязаны его вызывать (для случая, когда они создаются самостоятельно, не как часть Bat).

Порядок конструирования в `Bat`: **сначала виртуальные базы** (Animal), потом невиртуальные (Mammal, Bird в порядке объявления), потом члены, потом тело.

## Практический вердикт

**Множественное наследование от интерфейсов** (чистые абстрактные классы, без данных) — **нормально и полезно**. Ромба с данными не возникает, дублирование не страшно:

```cpp
struct IDrawable { virtual void draw() = 0; virtual ~IDrawable() = default; };
struct ISerializable { virtual void save() = 0; virtual ~ISerializable() = default; };

class Shape : public IDrawable, public ISerializable { };   // ✅ идиоматично
```

**Множественное наследование с данными и ромбом** — источник сложности. Виртуальное наследование это чинит, но платит производительностью и запутывает инициализацию. В большинстве кодовых баз (включая Google C++ Style Guide) его **избегают**, предпочитая:

- **композицию** вместо наследования
- наследование только от интерфейсов (mixins без состояния)

Реальные примеры виртуального наследования в стандартной библиотеке: иерархия `iostream` (`basic_iostream` виртуально наследует от `basic_istream` и `basic_ostream`, которые оба виртуально наследуют `basic_ios`) — как раз ромб, разрешённый виртуальным наследованием.

## Формулировки на собеседовании

**«Что такое проблема ромба?»** — при множественном наследовании от классов с общим предком производный класс получает **две копии** базы: неоднозначность доступа к членам, дублирование данных, двойной вызов конструктора базы.

**«Как решается?»** — виртуальным наследованием (`: virtual Base`) у промежуточных классов: базовый суб-объект становится разделяемым, экземпляр один.

**«Чем платим?»** — доступ к членам виртуальной базы через дополнительную косвенность (offset читается из vtable в рантайме); запрет `static_cast` вниз от виртуальной базы; усложнённая инициализация.

**«Кто инициализирует виртуальную базу?»** — most-derived класс напрямую; вызовы конструктора виртуальной базы из промежуточных классов игнорируются.

**«Почему смещение до виртуальной базы нельзя зашить статически?»** — оно зависит от полного типа объекта: `Mammal` сам по себе и `Mammal` внутри `Bat` имеют разное расположение `Animal`-части, а код `Mammal` компилируется один раз для обоих случаев.

---

Отличие от Java: там множественное наследование **классов** запрещено — только один `extends`, но сколько угодно `implements` (интерфейсов). Ромб данных невозможен в принципе, потому что интерфейсы не имеют состояния (до Java 8; с default-методами появился «ромб поведения», решаемый явным `Interface.super.method()`). C++ разрешает полноценное множественное наследование и потому вынужден предоставлять механизм разрешения ромба — виртуальное наследование. Это ровно тот случай, где C++ даёт больше мощности ценой большей сложности.
