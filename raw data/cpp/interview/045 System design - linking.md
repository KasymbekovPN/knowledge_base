# Линковка (linking)

## Место в процессе сборки

```
исходники → [препроцессор] → [компилятор] → [ассемблер] → объектные файлы → [ЛИНКЕР] → исполняемый/библиотека
  .cpp          .i              .s             .o/.obj                        a.out/.exe/.so/.a
  препроц.    развёрнутый     ассемблер      машинный код             СШИВКА всех .o + библиотек
              текст                          + таблица символов
```

Компилятор обрабатывает каждый `.cpp` **независимо** (translation unit) и не знает о других. Линкер — тот, кто **сшивает** результаты: разрешает ссылки между TU, подключает библиотеки, формирует финальный образ.

---

## Что делает линкер

### 1. Symbol resolution — разрешение символов

Каждый объектный файл содержит **таблицу символов**: что он **определяет** (defined) и что ему **нужно извне** (undefined/external).

```cpp
// a.cpp
void helper();            // undefined — нужен извне
void foo() { helper(); }  // defined — предоставляет foo

// b.cpp
void helper() { }         // defined — предоставляет helper
```

```
a.o: defines foo, needs helper
b.o: defines helper
      ↓ линкер
линкер связывает "needs helper" из a.o с "defines helper" из b.o
```

Если символ **нужен**, но **нигде не определён** → `undefined reference`:

```cpp
void foo() { helper(); }   // helper объявлен, но НИГДЕ не определён
// линкер: ⚠️ undefined reference to `helper()`
```

Если символ определён **дважды** (в разных TU) → `multiple definition` (нарушение ODR):

```cpp
// a.cpp: int global = 1;
// b.cpp: int global = 2;
// линкер: ⚠️ multiple definition of `global`
```

### 2. Relocation — привязка адресов

Компилятор не знает финальных адресов функций/переменных (они в других TU). Он оставляет «дырки» (relocations), а линкер их заполняет реальными адресами после раскладки всех секций в памяти.

### 3. Секции — сборка образа

Линкер объединяет одноимённые секции из всех .o:

```
.text   — код (исполняемый)
.data   — инициализированные глобальные/static переменные
.bss    — неинициализированные (занимают 0 места в файле, зануляются при загрузке)
.rodata — константы (const, строковые литералы, vtable)
```

## Name mangling — как символы называются

Мы касались этого в ABI. C++ кодирует имена с типами (для перегрузки, namespace, шаблонов):

```cpp
void f(int);              // _Z1fi
void f(double);           // _Z1fd
namespace ns { void g(); } // _ZN2ns1gEv
template class Vec<int>;   // _Z...
```

Линкер работает с **mangled** именами. Отсюда типичные ошибки:

```cpp
// header.h
void process(int);        // объявление: mangled _Z7processi

// вызов в main.cpp → ищет _Z7processi

// но в lib.cpp определили:
void process(long);       // mangled _Z7processl  ← ДРУГОЕ имя!
// линкер: undefined reference to `process(int)` — не нашёл _Z7processi
```

Несовпадение сигнатуры → разные mangled имена → undefined reference, хотя «функция вроде есть».

### `extern "C"` — отключить mangling

```cpp
extern "C" void f(int);   // символ называется просто "f" (C-стиль)
```

Нужно для: линковки с C-кодом, FFI, стабильных API (разбирали в ABI). C не имеет перегрузки → mangling не нужен → имя = имя функции.

## Виды библиотек

### Статическая библиотека (.a / .lib)

**Архив объектных файлов**, вкомпилированный в исполняемый файл на этапе линковки.

```bash
ar rcs libmath.a add.o sub.o mul.o    # создать статическую библиотеку (просто архив .o)
g++ main.o -L. -lmath -o program       # слинковать (код библиотеки КОПИРУЕТСЯ в program)
```

Характеристики:

- **Код копируется** в исполняемый файл → больше размер бинарника
- **Самодостаточность** — не нужна библиотека при запуске
- Обновление библиотеки → **перелинковка** программы
- Линкер вытаскивает **только нужные** .o из архива (не весь архив)

### Динамическая/разделяемая библиотека (.so / .dll / .dylib)

**Загружается в рантайме**, разделяется между процессами.

```bash
g++ -shared -fPIC add.cpp sub.cpp -o libmath.so   # создать .so (-fPIC обязателен!)
g++ main.o -L. -lmath -o program                   # линкуем (только ССЫЛКА, не код)
```

Характеристики:

- **Код НЕ копируется** — программа хранит только ссылку; библиотека загружается при запуске
- **Разделяется** между процессами (одна копия в памяти → экономия RAM)
- Обновление библиотеки → **не нужна** перелинковка (если ABI совместим — мы разбирали!)
- Требует наличия .so при запуске (иначе `error while loading shared libraries`)

### Сравнение

| |Статическая (.a)|Динамическая (.so)|
|---|---|---|
|Когда линкуется|compile-time|часть — compile-time, часть — runtime|
|Код в бинарнике|✅ копируется|❌ ссылка|
|Размер бинарника|больше|меньше|
|Разделение между процессами|❌|✅ (экономия памяти)|
|Обновление без пересборки|❌|✅ (если ABI совместим)|
|Скорость запуска|быстрее|медленнее (загрузка + relocation)|
|Зависимость при запуске|нет|нужна .so|
|ABI-проблемы|нет (всё зашито)|✅ есть (разбирали)|

## `-fPIC` — Position Independent Code

```bash
g++ -shared -fPIC ...   # -fPIC обязателен для .so
```

`.so` загружается по **произвольному** адресу (разный в разных процессах, ASLR). Код должен работать независимо от адреса загрузки → обращения к глобальным данным идут через **GOT** (Global Offset Table), а не по абсолютным адресам.

Без `-fPIC`:

```
/usr/bin/ld: relocation R_X86_64_32 against `.rodata' can not be used when making a shared object; recompile with -fPIC
```

Для исполняемых файлов PIC не обязателен (но `-fPIE` — PIC для executable — часто дефолт ради ASLR-безопасности).

## Динамическая линковка в рантайме

### Как .so находится при запуске

```
1. rpath/runpath — пути, зашитые в бинарник (-Wl,-rpath)
2. LD_LIBRARY_PATH — переменная окружения
3. /etc/ld.so.cache (ldconfig)
4. /lib, /usr/lib — стандартные пути
```

```bash
ldd program              # показать зависимости .so
# libmath.so => ./libmath.so (0x...)
# libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6

# частая ошибка:
./program
# error while loading shared libraries: libmath.so: cannot open shared object file
# → .so не в путях поиска → добавить LD_LIBRARY_PATH или rpath
```

### SONAME и версионирование

```
libmath.so.1.2.3    — реальный файл
libmath.so.1        — SONAME (симлинк) — с ним линкуется программа
libmath.so          — dev-симлинк для линковки
```

Программа записывает **SONAME** (`libmath.so.1`), а не полное имя. Смена major (`.so.2`) → новый SONAME → старые программы продолжают использовать `.so.1` (мы разбирали в ABI). Это механизм сосуществования несовместимых версий.

### Ленивая линковка (lazy binding / PLT)

По умолчанию адреса функций из .so резолвятся **при первом вызове** (через PLT — Procedure Linkage Table), а не при загрузке. Ускоряет старт. `LD_BIND_NOW=1` форсирует немедленную резолюцию всех символов.

### `dlopen` — явная загрузка

```cpp
#include <dlfcn.h>
void* handle = dlopen("libplugin.so", RTLD_LAZY);   // загрузить .so в рантайме
auto func = (void(*)())dlsym(handle, "pluginMain");  // получить символ
func();
dlclose(handle);
```

Основа **плагинной архитектуры**: загружать .so динамически по имени. Для C++ символов нужен `extern "C"` (иначе mangled имя не угадать) — типичный паттерн: C-экспорт фабрики, возвращающей C++ интерфейс:

```cpp
extern "C" IPlugin* createPlugin();   // C-имя для dlsym, возвращает C++ объект
```

## Типичные ошибки линковки

### 1. undefined reference — символ не найден

```cpp
// причины:
void foo();          // объявлен, но нигде не определён
                     // → забыли .cpp с определением при линковке

// mangling mismatch:
void f(int);  // вызов ищет _Z1fi
void f(long); // определён _Z1fl  → не совпадает

// забыли слинковать библиотеку:
g++ main.o -o prog   // но main использует libmath → нужно -lmath

// порядок библиотек! (для статических — важен):
g++ -lmath main.o    // ⚠️ может не найти — библиотеки ПОСЛЕ объектников
g++ main.o -lmath    // ✅ правильный порядок
```

**Порядок статических библиотек:** линкер обрабатывает слева направо, вытаскивая символы по мере надобности. Библиотека должна идти **после** того, кто её использует. Циклические зависимости → повторить библиотеку или `--start-group/--end-group`.

### 2. multiple definition — ODR нарушен

```cpp
// определение в заголовке без inline (разбирали):
// util.h: int add(int a, int b) { return a+b; }  → в каждой TU
// → multiple definition

// решение: inline, или объявление в .h + определение в одном .cpp
```

### 3. undefined reference to vtable — забыт виртуальный метод

```cpp
class Widget {
    virtual void f();   // объявлен, но НЕ определён
    virtual ~Widget();  // тоже
};
// линкер: undefined reference to `vtable for Widget`
```

Особый случай: если **первая** невстроенная виртуальная функция не определена, компилятор не генерирует vtable (эвристика: vtable эмитится в TU, где определена первая non-inline virtual). Забыл определить — нет vtable → ошибка. Правило: определяй хотя бы одну не-inline виртуальную функцию (часто деструктор) в .cpp.

### 4. `extern "C"` mismatch

```cpp
// header.h (C++ проект)
void c_func(int);          // C++ mangling: _Z6c_funci

// но реализация в C-файле:
void c_func(int) { }       // C: символ "c_func"
// → undefined reference (mangled vs unmangled)

// решение:
extern "C" void c_func(int);   // в заголовке → оба используют "c_func"
```

### 5. ABI mismatch (GCC dual ABI)

```cpp
// undefined reference to `foo(std::__cxx11::string)`
// ↑ смешали код с _GLIBCXX_USE_CXX11_ABI=0 и =1 (разбирали в ABI)
```

## LTO — Link-Time Optimization

```bash
g++ -flto -O2 a.cpp b.cpp -o program
```

Обычно компилятор оптимизирует каждую TU **отдельно** → не может инлайнить функцию из другого .cpp, не видит межмодульных возможностей.

**LTO** откладывает часть оптимизаций до линковки, когда виден **весь** код → межмодульный инлайнинг, девиртуализация (разбирали в vtable), удаление мёртвого кода через границы TU.

Плата: медленная линковка, больше памяти. Даёт заметный прирост в горячем коде, где важен межмодульный инлайнинг.

## Формулировки на собеседовании

**«Что делает линкер?»** — (1) **Symbol resolution** — связывает «нужные» символы одних TU с «определёнными» в других. (2) **Relocation** — заполняет адреса, неизвестные на этапе компиляции. (3) Объединяет секции (.text/.data/.bss/.rodata) в финальный образ. Подключает библиотеки.

**«undefined reference — причины?»** — Символ объявлен, но нигде не определён; забыли .cpp/библиотеку при линковке; **несовпадение сигнатуры** (разные mangled имена); неверный порядок статических библиотек; забыт `extern "C"`.

**«Статическая vs динамическая библиотека?»** — Статическая (.a) — код **копируется** в бинарник на этапе линковки (больше размер, самодостаточность, перелинковка при обновлении). Динамическая (.so) — загружается в **рантайме**, разделяется между процессами (меньше бинарник, обновление без пересборки при ABI-совместимости, но зависимость при запуске).

**«Зачем `-fPIC`?»** — Position Independent Code: .so загружается по произвольному адресу (ASLR), обращения к глобальным данным — через GOT, а не абсолютные адреса. Обязателен для .so.

**«Что такое SONAME?»** — Версионное имя .so (`libfoo.so.1`), записываемое в бинарник. Смена major → новый SONAME → несовместимые версии сосуществуют; старые программы используют старую .so.

**«undefined reference to vtable — почему?»** — Не определена первая non-inline виртуальная функция класса; компилятор эмитит vtable в TU, где она определена. Забыл — нет vtable. Определяй хотя бы одну (часто деструктор) в .cpp.

**«Что такое LTO?»** — Link-Time Optimization: оптимизации откладываются до линковки, когда виден весь код → межмодульный инлайнинг, девиртуализация, удаление мёртвого кода через границы TU. Ценой скорости линковки.

**«Почему важен порядок статических библиотек?»** — Линкер обрабатывает слева направо, вытаскивая символы по требованию. Библиотека должна идти **после** использующего её объектника; иначе символ ещё не «востребован» и не подтягивается.

---

Отличие от Java: там линковки в C++-смысле **нет**. (1) Компиляция `javac` → `.class` файлы (байткод), каждый класс отдельно; **нет линкера**, объединяющего их. (2) Связывание — **динамическое, в рантайме**: JVM загружает классы по мере обращения (`ClassLoader`), резолвит символы **по именам** при первом использовании (lazy). (3) Нет name mangling — методы идентифицируются именем + дескриптором (`add(II)I`). (4) Нет статической/динамической библиотеки — есть `.jar` (архив `.class`, всегда «динамический» в смысле загрузки классов). (5) `undefined reference` эквивалент — `NoClassDefFoundError`/`NoSuchMethodError` **в рантайме**, а не при сборке. Ключевое различие: C++ резолвит символы **на этапе линковки** (рано, статически, ошибки при сборке), Java — **в рантайме** (поздно, динамически, ошибки при запуске). Это тот же паттерн, что с ABI: Java откладывает связывание на рантайм, получая гибкость (hot-swap классов, плагины без пересборки) ценой отсутствия ранней проверки. C++ линкует статически, ловит ошибки раньше, но требует пересборки/перелинковки. `dlopen` в C++ — попытка получить Java-подобную динамическую загрузку, и она требует `extern "C"` именно потому, что C++ обычно резолвит символы статически. Rust, кстати, ближе к C++ — статическая линковка по умолчанию, свой линкер-этап; знакомая тебе модель.
