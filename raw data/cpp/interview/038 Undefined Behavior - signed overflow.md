# UB: signed integer overflow

## Суть

Переполнение **знакового** целого — **UB**. Переполнение **беззнакового** — определено (обёртка по модулю 2ⁿ). Это одно из самых неинтуитивных различий в C++.

```cpp
int x = INT_MAX;
x + 1;              // ⚠️ UB — знаковое переполнение

unsigned u = UINT_MAX;
u + 1;              // ✅ определено: 0 (wraparound по модулю 2³²)
```

```cpp
INT_MAX  ==  2147483647
INT_MAX + 1  → UB (НЕ -2147483648, как можно ожидать!)

UINT_MAX ==  4294967295
UINT_MAX + 1 → 0    (определено)
```

---

## Почему знаковое — UB, а беззнаковое — нет

**Историческая причина:** во времена стандартизации существовали разные представления знаковых чисел (two's complement, one's complement, sign-magnitude). Комитет не хотел привязываться к одному → объявил переполнение UB.

**Современная причина (важнее):** UB даёт компилятору право на **оптимизации**. Раз переполнение «не может произойти», компилятор предполагает, что его нет:

```cpp
// Компилятор может доказать, что цикл завершается:
for (int i = 0; i <= n; ++i) { }
// предполагает: i не переполнится → цикл конечен → можно разворачивать, векторизовать

// С unsigned такой гарантии нет (wraparound легален):
for (unsigned i = 0; i <= n; ++i) { }   // если n == UINT_MAX → бесконечный цикл!
```

Конкретные оптимизации, которые UB знакового переполнения разрешает:

```cpp
// 1. x + 1 > x  →  всегда true (для signed)
if (x + 1 > x) { }   // компилятор: всегда true (переполнения "не бывает")
                     // для unsigned это НЕ упростить (при UINT_MAX даёт false)

// 2. x * 2 / 2  →  x
// 3. упрощение индексов циклов, promotion int → размер указателя без проверок
// 4. a < a + 1  →  true
```

С C++20 знаковые числа **гарантированно** two's complement, но переполнение **осталось UB** — именно ради этих оптимизаций.

---

## Почему это коварно

### 1. «Работает» на большинстве платформ

На типичном железе `INT_MAX + 1` даёт `INT_MIN` (wraparound two's complement). Поэтому код «работает»... пока компилятор не применит оптимизацию, полагающуюся на отсутствие UB:

```cpp
int f(int x) {
    return x + 1 > x;   // "очевидно" зависит от x?
}
// -O0: реальное сложение → при INT_MAX даёт false
// -O2: компилятор УПРОСТИЛ до `return true;` (переполнения "не бывает")
```

Один и тот же код даёт **разный результат** на разных уровнях оптимизации — классический признак UB.

### 2. Проверки переполнения, которые компилятор выкидывает

```cpp
// ❌ НАИВНАЯ проверка — НЕ РАБОТАЕТ
int safe_add(int a, int b) {
    int sum = a + b;        // ⚠️ UB уже ЗДЕСЬ, если переполнение
    if (sum < a) {          // ⚠️ компилятор может ВЫКИНУТЬ эту проверку!
        // переполнение
    }
    return sum;
}
```

Компилятор рассуждает: «`a + b` не переполняется (иначе UB), значит `sum >= a` всегда, значит `sum < a` — всегда false» → **удаляет проверку**. Проверка переполнения _после_ переполнения бессмысленна — UB уже случилось.

Реальный CVE-класс: проверки безопасности, оптимизированные прочь.

---

## Правильные способы проверки переполнения

### 1. Проверка ДО операции

```cpp
int safe_add(int a, int b) {
    if (b > 0 && a > INT_MAX - b) return /* overflow */;   // ✅ проверка ДО
    if (b < 0 && a < INT_MIN - b) return /* underflow */;
    return a + b;   // ✅ гарантированно без переполнения
}
```

### 2. Builtin-функции компилятора (лучший способ)

```cpp
int result;
if (__builtin_add_overflow(a, b, &result)) {   // GCC/Clang
    // переполнение
}
// возвращает true при переполнении, result содержит "обёрнутый" результат
```

Есть `__builtin_add_overflow`, `__builtin_sub_overflow`, `__builtin_mul_overflow`. Компилируются в одну инструкцию + проверку флага переполнения процессора — эффективно и корректно.

### 3. C++26: `<numeric>` overflow-функции (готовится)

```cpp
// C++26 (P0543):
auto r = std::add_sat(a, b);        // saturating: при переполнении → INT_MAX/INT_MIN
auto [val, of] = std::add_overflow(a, b);   // с флагом
```

### 4. Более широкий тип

```cpp
int64_t sum = int64_t(a) + int64_t(b);   // ✅ int + int не переполнит int64_t
if (sum > INT_MAX || sum < INT_MIN) { /* overflow */ }
```

## Другие проявления signed overflow UB

### 1. Отрицание INT_MIN

```cpp
int x = INT_MIN;   // -2147483648
-x;                // ⚠️ UB! +2147483648 не влезает в int (INT_MAX == 2147483647)
std::abs(x);       // ⚠️ UB по той же причине для INT_MIN!
```

Асимметрия two's complement: `INT_MIN` по модулю больше `INT_MAX` на 1. Классическая ловушка.

### 2. Деление INT_MIN / -1

```cpp
INT_MIN / -1;      // ⚠️ UB — результат +2147483648 не влезает
INT_MIN % -1;      // ⚠️ UB (на некоторых платформах)
```

### 3. Сдвиги

```cpp
int x = 1;
x << 31;           // ⚠️ UB — сдвиг в знаковый бит (для int)
                   //    (1 << 31 переполняет int)
1u << 31;          // ✅ unsigned — определено

x << 32;           // ⚠️ UB — сдвиг на >= разрядности типа
x << -1;           // ⚠️ UB — отрицательный сдвиг
```

Сдвиг на величину >= ширины типа и отрицательный сдвиг — UB **для обоих** знаковых и беззнаковых.

### 4. Умножение при integer promotion

Коварный случай — переполнение при неявном продвижении:

```cpp
uint16_t a = 50000, b = 50000;
uint32_t result = a * b;   // ⚠️ UB!
// a и b продвигаются до INT (не unsigned int!) перед умножением
// 50000 * 50000 = 2.5e9 > INT_MAX → знаковое переполнение int
```

Хотя операнды беззнаковые, `integer promotion` продвигает `uint16_t` до `int` (не `unsigned`), и умножение происходит в знаковом `int` → переполнение → UB. Нужно:

```cpp
uint32_t result = uint32_t(a) * b;   // ✅ явно расширяем до unsigned
```

## Знаковое vs беззнаковое — что выбрать

### Беззнаковое переполнение определено, но создаёт СВОИ баги

```cpp
unsigned a = 3, b = 5;
a - b;             // ✅ определено, но = 4294967294 (не -2!)

for (unsigned i = v.size() - 1; i >= 0; --i) { }   // ⚠️ БЕСКОНЕЧНЫЙ ЦИКЛ!
                   // i >= 0 всегда true для unsigned; при i==0, --i → UINT_MAX
```

Классическая ошибка обратного цикла с `unsigned`.

```cpp
if (v.size() - 1 < someValue) { }   // ⚠️ если v пуст: 0 - 1 = UINT_MAX → сравнение сломано
```

### Позиция Core Guidelines и экспертов

Спорный вопрос, но преобладающая рекомендация:

- **Используй знаковые (`int`) для арифметики** — даже если UB. Логика: беззнаковый wraparound даёт **тихо неверные** результаты (баги, которые не ловятся), а знаковое переполнение с санитайзером **ловится** (UBSan).
- **Беззнаковые — только для битовых операций и когда wraparound нужен явно** (хеши, модульная арифметика, циклические буферы).

Прискорбный факт: `size()` контейнеров возвращает **беззнаковый** `size_t` — источник ошибок «signed/unsigned mismatch». C++20 добавил `std::ssize()` (знаковый размер) как частичное решение:

```cpp
for (int i = std::ssize(v) - 1; i >= 0; --i) { }   // ✅ знаковый → обратный цикл работает
```

### Signed/unsigned сравнения — ловушка

```cpp
int a = -1;
unsigned b = 1;
a < b;             // ⚠️ FALSE! a конвертируется в unsigned → -1 становится UINT_MAX
                   //    UINT_MAX < 1 → false

// C++20: безопасные сравнения
std::cmp_less(a, b);   // ✅ true — корректно сравнивает разные знаковости
std::cmp_equal, std::cmp_greater, ...
```

`-Wsign-compare` предупреждает о таких сравнениях.

## Обнаружение

### UBSan — ловит signed overflow в рантайме

```bash
g++ -fsanitize=undefined -g prog.cpp
```

```
prog.cpp:5:11: runtime error: signed integer overflow:
2147483647 + 1 cannot be represented in type 'int'
```

Ловит: signed overflow, INT_MIN negation, INT_MIN/-1, некорректные сдвиги, и другие UB. Замедление небольшое (~1.2-2x). **Обязателен в CI.**

Отдельные флаги:

- `-fsanitize=signed-integer-overflow` — только это
- `-fsanitize=shift` — некорректные сдвиги

### `-ftrapv` / `-fwrapv`

```bash
g++ -ftrapv    # прерывать программу при знаковом переполнении (медленно)
g++ -fwrapv    # ⚠️ ОПРЕДЕЛИТЬ переполнение как wraparound (убирает UB, но и оптимизации)
```

`-fwrapv` делает знаковое переполнение определённым (как беззнаковое) — иногда используют для legacy-кода, полагающегося на wraparound. Ценой потери оптимизаций.

## Формулировки на собеседовании

**«Что происходит при знаковом переполнении?»** — **UB**. При беззнаковом — определённый wraparound по модулю 2ⁿ. Знаковое — UB исторически (разные представления) и для **оптимизаций** (компилятор предполагает отсутствие переполнения).

**«Почему проверка `if (a + b < a)` не работает?»** — Если `a + b` переполняется — UB уже случилось. Компилятор рассуждает «переполнения не бывает → `a+b >= a` всегда → проверка всегда false» и **удаляет** её. Проверять надо **до** операции или через `__builtin_add_overflow`.

**«Приведи неочевидный signed overflow UB.»** — `-INT_MIN` и `std::abs(INT_MIN)` (результат не влезает); `INT_MIN / -1`; `1 << 31` для `int`; `uint16_t * uint16_t` (продвигаются до `int`, не `unsigned` → переполнение в знаковом).

**«signed или unsigned для арифметики?»** — Знаковые: беззнаковый wraparound даёт тихо неверные результаты, знаковое переполнение ловится **UBSan**. Беззнаковые — только для битов и явной модульной арифметики. `std::ssize()` (C++20) для обратных циклов.

**«Что не так с `for (unsigned i = n-1; i >= 0; --i)`?»** — Бесконечный цикл: `i >= 0` всегда true для беззнакового; при `i == 0` декремент даёт `UINT_MAX`. Используй знаковый индекс или `std::ssize`.

**«Как безопасно сравнить `int` и `unsigned`?»** — `std::cmp_less`/`cmp_equal`/... (C++20). Обычное `<` конвертирует `int` в `unsigned` (`-1` → `UINT_MAX`) → неверный результат.

---

Отличие от Java: там **всё определено** — переполнение (и знаковое, и беззнаковое) даёт **wraparound** two's complement, никакого UB. `Integer.MAX_VALUE + 1 == Integer.MIN_VALUE` гарантированно. Плюс в Java **нет беззнаковых типов** вообще (до Java 8; потом добавили `Integer.divideUnsigned` и т.п. как методы, но не типы). Отсюда для Java-разработчика два сюрприза в C++: (1) знаковое переполнение — **UB**, а не тихий wraparound, значит компилятор оптимизирует агрессивнее и код может «сломаться» на `-O2`; (2) существуют беззнаковые типы с определённым wraparound, порождающие свой класс багов (обратные циклы, signed/unsigned сравнения). Java-привычка «переполнение просто заворачивается» в C++ опасна: для `int` это UB. Для точного контроля переполнения в Java есть `Math.addExact()` (бросает исключение) — прямой аналог C++ `__builtin_add_overflow` по назначению.
