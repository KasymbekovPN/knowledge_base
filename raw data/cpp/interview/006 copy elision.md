# RVO / NRVO и copy elision

## Что это

**Copy elision** — оптимизация, при которой компилятор **устраняет** копирование/перемещение объекта, конструируя его сразу в целевом месте. Даже если copy/move конструктор имеет побочные эффекты (печать, счётчики), они **не выполняются** — это разрешённое стандартом исключение из правила «as-if».

Две основные разновидности:

- **RVO** (Return Value Optimization) — элизия для **безымянного** временного при возврате
- **NRVO** (Named RVO) — элизия для **именованной** локальной переменной при возврате

---

## Проблема без элизии

Возврат объекта по значению «наивно» требует лишних построений:

```cpp
std::string make() {
    return std::string("hello");   // 1) построить временный
}                                   // 2) скопировать/переместить в возвращаемое значение
std::string s = make();            // 3) скопировать/переместить в s
```

До оптимизаций — до трёх конструирований. Copy elision схлопывает это в **одно**: объект строится прямо в `s`.

---

## RVO — возврат prvalue (безымянного временного)

```cpp
struct Widget {
    Widget() { std::cout << "ctor\n"; }
    Widget(const Widget&) { std::cout << "copy\n"; }
    Widget(Widget&&) { std::cout << "move\n"; }
};

Widget makeRVO() {
    return Widget();   // возвращаем безымянный временный
}

Widget w = makeRVO();
```

**Вывод (C++17 и позже):**

```
ctor
```

Только один конструктор. Никаких copy/move — объект `Widget()` строится непосредственно в `w`.

---

## Copy elision в C++17 — обязательная гарантия для prvalue

До C++17 элизия была **разрешена, но не обязательна** — компилятор _мог_ её не делать, и тогда требовался доступный copy/move конструктор.

**С C++17 элизия prvalue стала обязательной** (mandatory copy elision). Причём формально это уже не «оптимизация копии», а изменение самой модели: prvalue больше не создаёт временный объект, который потом копируется — prvalue материализуется прямо в целевом объекте.

Практические следствия mandatory elision:

### 1. Работает даже с удалёнными copy/move

```cpp
struct NonMovable {
    NonMovable() = default;
    NonMovable(const NonMovable&) = delete;
    NonMovable(NonMovable&&) = delete;
};

NonMovable make() {
    return NonMovable();   // ✅ C++17: компилируется! элизия обязательна,
}                          //    copy/move даже не требуется
NonMovable x = make();     // ✅ тоже ОК
```

До C++17 это **не компилировалось** — формально требовался доступный move/copy, хоть он и элидировался. Хороший вопрос-ловушка на собеседовании.

### 2. Гарантия распространяется на цепочку

```cpp
NonMovable a = NonMovable();          // элизия
NonMovable b = (NonMovable());        // элизия
void take(NonMovable);
take(NonMovable());                   // элизия — временный строится прямо в параметре
```

Любое инициализирование объекта prvalue того же типа — гарантированно без копии.

## NRVO — возврат именованной локальной переменной

```cpp
Widget makeNRVO() {
    Widget w;         // именованная локальная
    // ... что-то с w ...
    return w;         // возврат по имени
}

Widget result = makeNRVO();
```

**Вывод (типично):**

```
ctor
```

Компилятор строит `w` прямо в месте результата — copy/move элидируется.

### НО: NRVO не гарантирован даже в C++17

**Ключевое отличие:** NRVO остаётся **разрешённой, но не обязательной** оптимизацией. Компилятор _может_ её применить, но не обязан. Если не применил — вызывается **move** (а не copy), потому что при возврате именованной локальной действует специальное правило:

> При `return localVar;` где `localVar` — локальный объект подходящего типа, сначала рассматривается перегрузка как для **rvalue** (implicit move), и только потом — как для lvalue.

То есть если NRVO не сработал, ты получишь `move`, а не `copy` (при наличии move-конструктора):

```cpp
Widget makeNRVO() {
    Widget w;
    return w;   // либо NRVO (ctor only), либо implicit move (ctor + move)
}
```

Почему NRVO сложнее гарантировать: у именованной переменной есть адрес и, возможно, несколько путей возврата (`if (...) return a; else return b;`) — компилятор не всегда может решить, какой объект строить в месте результата.

---

## Сводка гарантий (важнейшая таблица для собеседования)

|Ситуация|C++17|
|---|---|
|`return T();` (prvalue, безымянный)|**элизия обязательна** — 0 copy/move, даже если они deleted|
|`return localVar;` (NRVO)|элизия **разрешена, но не гарантирована**; если не применена → **implicit move**|
|`return std::move(localVar);`|**подавляет** NRVO → всегда move (антипаттерн)|
|`return member_;` / `return globalVar;`|элизия **не** применяется → copy или move|

## Частые ошибки

### 1. `std::move` в return — подавляет элизию

```cpp
Widget bad() {
    Widget w;
    return std::move(w);   // ❌ move(w) — это xvalue, НЕ именованная локальная
}                          //    → NRVO невозможен → форсированный move (медленнее элизии)

Widget good() {
    Widget w;
    return w;              // ✅ NRVO или implicit move — компилятор сам выберет лучшее
}
```

Классический антипаттерн. `std::move` при возврате локальной **никогда не помогает** и часто вредит — превращает потенциальную элизию (0 операций) в обязательный move.

**Исключение:** `std::move` при возврате оправдан, когда возвращаемый тип **отличается** от типа переменной (нет кандидата на элизию) или когда возвращаешь член/параметр:

```cpp
std::unique_ptr<Base> make() {
    auto d = std::make_unique<Derived>();
    return d;   // разные типы (Derived vs Base) → NRVO не применим,
                // но implicit move сработает (unique_ptr) → OK без move
}
```

Тут move не нужен явно — implicit move для unique_ptr сработает. Но, например, при возврате параметра:

```cpp
std::string transform(std::string s) {
    // ...
    return s;   // параметр — тоже кандидат на implicit move, тоже без std::move
}
```

### 2. Возврат члена не элидируется

```cpp
struct Holder {
    Widget w_;
    Widget get() { return w_; }   // copy! (w_ не локальная и не temporary)
    Widget take() && { return std::move(w_); }  // здесь move уместен (rvalue-квалиф. метод)
};
```

### 3. Несколько путей возврата ослабляют NRVO

```cpp
Widget make(bool flag) {
    Widget a, b;
    if (flag) return a;
    else return b;   // компилятор не может строить оба в одном месте → NRVO часто не срабатывает,
}                    // но implicit move гарантирует хотя бы move (не copy)
```

## Как проверить

Флаг `-fno-elide-constructors` (GCC/Clang) отключает **необязательную** элизию — полезно увидеть, сколько copy/move было бы без NRVO. Но mandatory prvalue-элизию C++17 этот флаг **не** отключает (она встроена в модель языка).

```bash
g++ -std=c++17 -fno-elide-constructors demo.cpp   # покажет move'ы, скрытые NRVO
```

## Формулировки на собеседовании

**«В чём разница RVO и NRVO?»** — RVO для безымянного temporary (prvalue), NRVO для именованной локальной переменной.

**«Что гарантирует C++17?»** — обязательную элизию для prvalue (возврат/инициализация безымянным временным): копия/перемещение не происходит, объект материализуется в цели; работает даже если copy/move удалены. NRVO осталась необязательной.

**«Что если NRVO не сработал?»** — вызывается implicit move (для возврата локальной действует правило: сначала пробуем как rvalue), а не copy.

**«Помогает ли `return std::move(x)`?»** — нет, вредит: подавляет NRVO/элизию, форсирует move. Возвращай локальную по имени.

**«Почему NRVO сложнее сделать обязательным?»** — у именованного объекта есть идентичность/адрес и возможны несколько путей возврата; компилятор не всегда может заранее выбрать целевое размещение.

---

Отличие от Java здесь концептуальное: в Java возврат объекта — это всегда возврат ссылки (сам объект на heap, копирования нет в принципе), поэтому проблемы «лишних копий при возврате по значению» не существует, как и понятия элизии. В C++ семантика значений делает это реальной оптимизацией с гарантиями на уровне стандарта.
