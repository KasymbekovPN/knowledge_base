# `condition_variable` и spurious wakeup

## Зачем: ожидание условия без busy-wait

Проблема: поток должен ждать, пока другой поток что-то приготовит. Наивно — крутить цикл:

```cpp
// ❌ BUSY-WAIT: жжём CPU впустую
while (true) {
    std::lock_guard lock(mtx);
    if (ready) break;
}   // 100% загрузка ядра на пустом месте
```

`condition_variable` позволяет **уснуть** и быть разбуженным, когда условие может стать истинным. Поток не потребляет CPU в ожидании.

---

## Базовое использование

```cpp
#include <condition_variable>

std::mutex mtx;
std::condition_variable cv;
bool ready = false;

// Поток-потребитель
void consumer() {
    std::unique_lock lock(mtx);              // ← unique_lock ОБЯЗАТЕЛЕН
    cv.wait(lock, []{ return ready; });      // ← ждём, пока предикат не станет true
    // здесь: мьютекс залочен, ready == true
    process();
}

// Поток-производитель
void producer() {
    {
        std::lock_guard lock(mtx);
        ready = true;                         // ← меняем состояние ПОД ЛОКОМ
    }
    cv.notify_one();                          // ← будим (лок уже отпущен)
}
```

### Что делает `wait(lock, pred)` — атомарно

```cpp
cv.wait(lock, pred);
// эквивалентно:
while (!pred()) {          // ← ЦИКЛ, не if!
    cv.wait(lock);         // атомарно: unlock(mtx) + уснуть; при пробуждении: lock(mtx)
}
```

Три ключевых момента:

1. **`wait()` атомарно разблокирует мьютекс и засыпает.** Это критично: если бы unlock и sleep были раздельными операциями, между ними мог бы вклиниться producer, послать notify — и потребитель уснул бы навсегда (lost wakeup).
    
2. **При пробуждении мьютекс снова захватывается** — код после `wait()` выполняется под локом.
    
3. **Предикат проверяется в цикле** — вот причина, ради которой всё это.
    

---

## Spurious wakeup — ложное пробуждение

**Поток может проснуться от `wait()` БЕЗ вызова `notify`.** Это разрешено стандартом и реально происходит.

### Почему так

- На уровне ОС (POSIX `pthread_cond_wait`) пробуждение может быть вызвано сигналом, прерыванием, внутренними механизмами планировщика
- Гарантировать отсутствие spurious wakeup было бы **дороже** (потребовало бы дополнительной синхронизации) — комитеты решили переложить проверку на пользователя, раз цикл всё равно нужен

### Почему цикл нужен даже без spurious wakeup

Даже если бы ложных пробуждений не было, **цикл всё равно обязателен** — из-за гонки за мьютексом:

```
Producer:  ready = true; notify_one();
Consumer A: просыпается, ждёт мьютекс...
Consumer B: (был другой поток) захватил мьютекс первым, СЪЕЛ данные, ready = false
Consumer A: наконец получил мьютекс — но условие УЖЕ ЛОЖНО!
```

Между `notify` и фактическим захватом мьютекса пробуждённым потоком другой поток мог изменить состояние. Это **не** spurious wakeup, а обычная гонка — и она гораздо частее.

### Следствие — золотое правило

```cpp
// ❌ НИКОГДА так:
if (!ready) cv.wait(lock);        // проснулись → продолжили, не проверив условие

// ✅ ВСЕГДА так:
while (!ready) cv.wait(lock);     // проверяем условие ПОСЛЕ каждого пробуждения

// ✅ или (эквивалентно, идиоматично):
cv.wait(lock, []{ return ready; });   // предикат-версия делает цикл сама
```

**Всегда используй версию с предикатом** — она встроенно защищает и от spurious wakeup, и от гонок, и от lost wakeup.

---

## Почему нужен `unique_lock`, а не `lock_guard`

`wait()` должен **разблокировать** мьютекс перед сном и **заблокировать** обратно. `lock_guard` этого не умеет — он блокирует в конструкторе и разблокирует в деструкторе, без промежуточного контроля.

```cpp
std::unique_lock lock(mtx);
cv.wait(lock, pred);          // ✅ cv вызывает lock.unlock() / lock.lock()

std::lock_guard lock(mtx);
cv.wait(lock, pred);          // ❌ не компилируется — нет нужного интерфейса
```

Для `shared_mutex` и других типов локов есть `std::condition_variable_any` (работает с любым лок-типом, но чуть дороже).

---

## `notify_one` vs `notify_all`

```cpp
cv.notify_one();   // будит ОДИН ожидающий поток (какой — не определено)
cv.notify_all();   // будит ВСЕ ожидающие потоки
```

**Когда `notify_one`:** любой из ожидающих может обработать событие, и обработать может **только один** (например, один элемент в очередь → достаточно разбудить одного потребителя). Дешевле — меньше конкуренции за мьютекс.

**Когда `notify_all`:**

- Ожидающие ждут **разных** условий на одной cv
- Событие может обслужить несколько потоков (например, «все стоп» или «данные готовы для всех читателей»)
- Добавили **несколько** элементов сразу

**Ловушка `notify_one`:** если потоки ждут разных условий на одной cv, `notify_one` может разбудить «не того» — тот проверит свой предикат, увидит false, уснёт обратно, а нужный поток так и не проснётся → **зависание**.

```cpp
// ⚠️ ОПАСНО: два разных условия на одной cv + notify_one
cv.wait(lock, []{ return has_data; });      // поток A
cv.wait(lock, []{ return has_space; });     // поток B
cv.notify_one();   // может разбудить B, когда нужен был A → deadlock
```

Правильно: либо **отдельные cv** для разных условий, либо `notify_all`.

## Критично: менять состояние ПОД мьютексом

```cpp
// ❌ НЕПРАВИЛЬНО — lost wakeup
void producer() {
    ready = true;          // ⚠️ БЕЗ лока!
    cv.notify_one();
}
```

Гонка:

```
Consumer: проверил pred() → false
Producer: ready = true;  notify_one();   ← notify «в пустоту», никто ещё не спит
Consumer: cv.wait(lock)  → УСНУЛ НАВСЕГДА
```

Изменение состояния **должно** быть под тем же мьютексом, который защищает условие — тогда `wait()` (который держит мьютекс до момента засыпания) не сможет «пропустить» изменение.

```cpp
// ✅ ПРАВИЛЬНО
void producer() {
    {
        std::lock_guard lock(mtx);
        ready = true;          // ✅ под локом
    }                          // ✅ отпустили ПЕРЕД notify (оптимизация)
    cv.notify_one();
}
```

**`notify` под локом или после?** Оба варианта **корректны**. Вне лока — обычно эффективнее: разбуженный поток сразу получит мьютекс, а не проснётся и тут же заблокируется на нём («hurry up and wait»). Хотя современные реализации часто оптимизируют этот случай (wait morphing), привычка отпускать лок перед notify — хорошая.

## Практический пример: thread-safe очередь

Канонический пример, который часто просят написать на собеседовании:

```cpp
template<class T>
class BlockingQueue {
    std::queue<T> queue_;
    mutable std::mutex mtx_;
    std::condition_variable cv_;
    bool stopped_ = false;

public:
    void push(T value) {
        {
            std::lock_guard lock(mtx_);
            queue_.push(std::move(value));
        }
        cv_.notify_one();          // ✅ один элемент → достаточно одного потребителя
    }

    // Блокирующее извлечение
    std::optional<T> pop() {
        std::unique_lock lock(mtx_);
        cv_.wait(lock, [this]{ return !queue_.empty() || stopped_; });
        //              ^^^ ждём: данные ИЛИ остановка

        if (queue_.empty()) return std::nullopt;   // остановлены и пусто

        T value = std::move(queue_.front());
        queue_.pop();
        return value;
    }

    // Корректное завершение
    void stop() {
        {
            std::lock_guard lock(mtx_);
            stopped_ = true;
        }
        cv_.notify_all();          // ✅ ВСЕ должны проснуться и увидеть stopped_
    }
};
```

Обрати внимание на три вещи, которые обычно и проверяют:

1. **Предикат учитывает и данные, и остановку** — иначе при `stop()` потоки зависнут в `wait()`
2. **`notify_all` при остановке** — разбудить всех, а не одного
3. **Возврат `optional`** — потому что pop может завершиться без значения (при остановке). Возвращать `T` по значению и одновременно сигналить остановку невозможно.

Ещё нюанс, связанный с race condition из прошлой темы: интерфейс `empty()` + `pop()` принципиально небезопасен (TOCTOU), поэтому у thread-safe очереди **нет** отдельного `empty()` для принятия решений — извлечение атомарно.

## Таймауты

```cpp
std::unique_lock lock(mtx);

// wait_for с предикатом → bool: true если предикат стал истинным, false если таймаут
if (cv_.wait_for(lock, 100ms, [this]{ return ready_; })) {
    // ✅ дождались
} else {
    // ⏱️ таймаут — предикат всё ещё false
}

cv_.wait_until(lock, deadline, pred);   // до конкретного момента времени
```

Версия с предикатом сама обрабатывает spurious wakeup **и** корректно пересчитывает оставшееся время (без предиката пришлось бы делать это вручную в цикле).

## Отмена через `stop_token` (C++20)

Помнишь `jthread` и кооперативную отмену? `condition_variable_any` умеет интегрироваться с `stop_token`:

```cpp
void worker(std::stop_token st) {
    std::unique_lock lock(mtx);
    // wait просыпается либо по условию, либо при request_stop()
    cv_any.wait(lock, st, []{ return ready; });
    
    if (st.stop_requested()) return;   // отменили
    // ...
}

std::jthread t(worker);
t.request_stop();   // ✅ разбудит поток из wait()
```

Без этого пришлось бы городить флаг `stopped_` в предикате (как в примере с очередью выше) — что тоже работает, но менее удобно.

## Типичные ошибки

### 1. `if` вместо `while` / без предиката

```cpp
if (!ready) cv.wait(lock);   // ⚠️ spurious wakeup или гонка → продолжили с ready == false
```

### 2. Изменение состояния без мьютекса

```cpp
ready = true;      // ⚠️ lost wakeup (разбирали выше)
cv.notify_one();
```

### 3. `notify` без изменения состояния

```cpp
cv.notify_one();   // ⚠️ бесполезно, если ready не изменился — поток проснётся,
                   //    проверит предикат (false) и уснёт обратно
```

`notify` — не «передача данных», а лишь **сигнал «проверь условие ещё раз»**. Само условие должно быть выражено в состоянии, защищённом мьютексом.

### 4. `notify_one` при разных условиях на одной cv

Разбирали — разбудит не того → зависание. Используй `notify_all` или отдельные cv.

### 5. Забыть про завершение

```cpp
cv.wait(lock, [this]{ return !queue_.empty(); });   // ⚠️ при shutdown потоки зависнут навсегда
```

Всегда добавляй флаг остановки в предикат (или `stop_token`).

### 6. Потеря пробуждения при `notify` до `wait`

Если producer сделал `notify` **до** того, как consumer вошёл в `wait()`, сигнал **теряется** — cv не имеет памяти/счётчика (в отличие от семафора).

Именно поэтому нужен **предикат на состоянии**: consumer, входя в `wait(lock, pred)`, сначала проверяет `pred()` — и если данные уже есть, вообще не засыпает.

```cpp
cv.wait(lock, []{ return ready; });   // ✅ если ready уже true — не спим вообще
```

Это фундаментальное отличие от семафора (`std::counting_semaphore`, C++20), который **считает** сигналы и не теряет их.

## Формулировки на собеседовании

**«Что такое spurious wakeup?»** — Поток может проснуться из `wait()` без вызова `notify` — это разрешено стандартом (следствие реализации на уровне ОС; гарантировать отсутствие было бы дороже). Поэтому условие проверяется **в цикле**.

**«Почему нужен цикл, даже если бы spurious wakeup не было?»** — Между `notify` и фактическим захватом мьютекса пробуждённым потоком другой поток мог изменить состояние (съесть данные). Это обычная гонка, гораздо частее ложных пробуждений. Версия `wait(lock, pred)` делает цикл автоматически.

**«Почему `wait()` требует `unique_lock`, а не `lock_guard`?»** — `wait()` должен атомарно **разблокировать** мьютекс перед сном и **заблокировать** обратно при пробуждении. `lock_guard` не даёт такого контроля.

**«Почему `wait()` разблокирует и засыпает атомарно?»** — Иначе между unlock и sleep producer мог бы послать `notify` — и consumer уснул бы уже после сигнала → **lost wakeup**, зависание навсегда.

**«Зачем менять состояние под мьютексом перед `notify`?»** — Иначе возможен lost wakeup: consumer проверил предикат (false), producer успел изменить состояние и послать notify, consumer уснул → сигнал потерян. Мьютекс делает «проверка предиката → засыпание» атомарным относительно «изменение состояния → notify».

**«`notify_one` или `notify_all`?»** — `notify_one` дешевле, но опасен, если потоки ждут **разных** условий на одной cv (разбудит не того → зависание). `notify_all` — при shutdown, при разных условиях, при добавлении нескольких элементов.

**«Что если `notify` вызван до `wait`?»** — Сигнал **теряется** (cv не считает уведомления, в отличие от семафора). Защита — предикат на состоянии: `wait(lock, pred)` сначала проверяет `pred()` и не засыпает, если условие уже истинно.

---

Отличие от Java: там `Object.wait()`/`notify()`/`notifyAll()` — встроены в каждый объект (монитор). Семантика **та же**, включая spurious wakeup — Java-документация тоже требует цикл (`while (!condition) wait();`). `Condition` из `java.util.concurrent` (получаемый из `ReentrantLock.newCondition()`) — прямой аналог `std::condition_variable`, с той же необходимостью цикла. Главное различие: в Java `wait()` можно звать только внутри `synchronized`, и монитор реентерабелен; в C++ мьютекс не реентерабелен и лок передаётся в `wait()` явно. Плюс в Java есть `BlockingQueue` из коробки — в C++ стандартной блокирующей очереди **нет**, её пишут вручную (что и делает её любимой задачей на собеседовании).
