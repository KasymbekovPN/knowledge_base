# UB: use-after-free

## Что это

Обращение к памяти **после** её освобождения. Частный, самый опасный случай dangling — потому что память могла быть **переиспользована** для другого объекта.

```cpp
Widget* p = new Widget();
delete p;          // память освобождена
p->use();          // ⚠️ UB — use-after-free
```

Отличие от общего dangling: при use-after-free освобождённая память **возвращается аллокатору** и может быть немедленно выдана под другой объект. То есть ты можешь не просто читать мусор, а **читать/писать чужой живой объект**.

---

## Почему это критично для безопасности

Use-after-free — **вектор эксплуатации №1** в C/C++ (наряду с buffer overflow). Механика атаки:

```cpp
delete userObject;              // память освобождена
// злоумышленник аллоцирует свой объект → попадает в ТУ ЖЕ память
SomeOtherObject* evil = new SomeOtherObject();   // занял освобождённый блок
userObject->virtualCall();      // ⚠️ вызов через vtable... но vtable теперь чужой!
                                 //    → перехват потока управления
```

Аллокаторы переиспользуют освобождённые блоки (это эффективно). Если между `delete` и use-after-free вклинилась чужая аллокация того же размера — обращение идёт к **другому объекту**. Для полиморфных типов это особенно опасно: перезаписанный vtable-указатель → произвольное выполнение кода.

Именно поэтому Microsoft, Google, и др. активно двигаются к memory-safe языкам (Rust) — ~70% их CVE это memory safety, из них большая доля — use-after-free.

## Категории

### 1. Простой use-after-free

```cpp
int* p = new int(42);
delete p;
*p = 10;           // ⚠️ UB
```

### 2. Double-free

Освобождение уже освобождённой памяти — тоже форма use-after-free (обращение к метаданным аллокатора):

```cpp
int* p = new int(42);
delete p;
delete p;          // ⚠️ UB — double-free, повреждает структуры аллокатора
```

Double-free часто приводит к повреждению heap metadata → падение или эксплойт при следующей аллокации.

### 3. Use-after-free через алиас

Самый частый в реальном коде — два указателя на один объект:

```cpp
Widget* a = new Widget();
Widget* b = a;              // алиас
delete a;                   // освободили
b->use();                   // ⚠️ UB — b не знает об удалении
delete b;                   // ⚠️ double-free
```

### 4. Владение неясно — «кто удаляет?»

```cpp
void process(Widget* w) {
    // ...
    delete w;    // ⚠️ а вызывающий тоже удалит?
}

Widget* w = new Widget();
process(w);      // process удалил w
w->use();        // ⚠️ UB
delete w;        // ⚠️ double-free
```

Корень проблемы — **неясная семантика владения** сырых указателей: из `Widget*` не видно, кто отвечает за удаление.

### 5. Возврат/хранение указателя на объект, который будет удалён

```cpp
class Registry {
    std::vector<Widget> widgets_;
public:
    Widget* get(size_t i) { return &widgets_[i]; }   // ⚠️ указатель на элемент вектора
};

Registry r;
Widget* p = r.get(0);
r.addMany();     // ⚠️ реаллокация вектора → элементы разрушены и перемещены
p->use();        // ⚠️ UB — use-after-free (старый буфер освобождён)
```

Это смыкается с инвалидацией итераторов — реаллокация `vector` **освобождает** старый буфер, все указатели на элементы становятся use-after-free.

### 6. Self-delete + продолжение работы

```cpp
class Session {
public:
    void handleDisconnect() {
        cleanup();
        delete this;          // легально (если на heap)
        logDisconnect();      // ⚠️ UB — объект разрушен, this висит
    }
private:
    Logger logger_;
    void logDisconnect() { logger_.log("bye"); }   // обращается к member мёртвого объекта
};
```

`delete this` допустимо, но **после него нельзя трогать ничего** — ни члены, ни методы.

### 7. Освобождение внутри итерации/колбэка

```cpp
for (auto* observer : observers_) {
    observer->notify();   // ⚠️ если notify() вызовет removeObserver(this) →
                          //    delete + инвалидация контейнера → UAF на следующей итерации
}
```

Reentrancy: колбэк модифицирует структуру, по которой идёт итерация.

### 8. Асинхронный use-after-free

Прямо релевантно твоему стеку (Asio):

```cpp
class Connection {
    std::array<char, 1024> buffer_;
public:
    void read() {
        socket_.async_read(buffer_, [this](auto ec, auto n) {
            process(buffer_, n);   // ⚠️ если Connection удалён до колбэка → UAF
        });
    }
};

// где-то:
delete connection;   // ⚠️ а async-операция ещё в полёте → колбэк обратится к мёртвому buffer_
```

Решение — `shared_from_this()`, продлевающий жизнь объекта на время операции (мы разбирали в `enable_shared_from_this`).

## Как предотвращать

### 1. Smart pointers — основное средство

```cpp
// ❌ ручное управление
Widget* w = new Widget();
delete w;

// ✅ unique_ptr — автоматическое удаление, невозможен double-free
auto w = std::make_unique<Widget>();
// удалится сам; unique_ptr некопируем → нет случайных алиасов-владельцев

// ✅ shared_ptr — разделяемое владение, удаление когда последний владелец ушёл
auto w = std::make_shared<Widget>();
```

`unique_ptr` устраняет:

- забытый `delete` (RAII)
- double-free (некопируем — один владелец)
- use-after-free при исключении (деструктор всегда отработает)

### 2. Чёткая семантика владения через типы

Из типа должно быть видно, кто владеет:

```cpp
std::unique_ptr<Widget> create();         // ✅ вызывающий получает владение
void consume(std::unique_ptr<Widget>);    // ✅ функция забирает владение
void observe(Widget*);                     // ✅ НЕ владеет (или Widget&)
void observe(const Widget&);               // ✅ ещё лучше — не nullable, не владеет
```

Правило (Core Guidelines): **сырой указатель = наблюдение, никогда не владение.** Владение — только через smart pointer или контейнер.

### 3. `weak_ptr` — разорвать возможность UAF(use-after-free)

```cpp
std::weak_ptr<Widget> observer = shared;

if (auto locked = observer.lock()) {   // ✅ если объект жив — получаем shared_ptr
    locked->use();                      // ✅ гарантированно жив в этом блоке
}                                        // объект удалён → lock() вернул nullptr, не UAF
```

Единственный безопасный способ хранить «может быть удалён».

### 4. `shared_from_this` для асинхронности

```cpp
void read() {
    auto self = shared_from_this();   // ✅ +1 к счётчику — объект жив, пока операция в полёте
    socket_.async_read(buffer_, [this, self](auto ec, auto n) {
        process(buffer_, n);           // ✅ self держит объект
    });
}
```

### 5. Обнуляй указатель после delete (если уж сырой)

```cpp
delete p;
p = nullptr;      // ✅ повторное разыменование → детерминированный segfault, не UAF
delete p;         // ✅ delete nullptr — безопасен (no-op)
```

Не решает проблему алиасов (другие копии не обнулятся), но лучше, чем висячий указатель.

### 6. Не трогай `this` после `delete this`

```cpp
void selfDestruct() {
    delete this;
    // ⚠️ дальше НИЧЕГО — ни member_, ни методов
}
```

### 7. Не модифицируй контейнер во время итерации

```cpp
// ✅ собери «на удаление», удали после
std::vector<Observer*> toRemove;
for (auto* o : observers_) {
    if (o->shouldRemove()) toRemove.push_back(o);
}
for (auto* o : toRemove) remove(o);
```

## Инструменты обнаружения

### AddressSanitizer — основной

```bash
g++ -fsanitize=address -g prog.cpp
```

Ловит use-after-free **надёжно** и с точным отчётом:

```
==ERROR: AddressSanitizer: heap-use-after-free
READ of size 4 at 0x602000000010
  #0 0x... in main prog.cpp:8
freed by thread T0 here:      ← ГДЕ освобождено
  #0 0x... in operator delete
  #1 0x... in main prog.cpp:7
previously allocated here:     ← ГДЕ выделено
  #0 0x... in operator new
```

Механика ASan: помещает освобождённые блоки в **карантин** (не переиспользует сразу) и помечает как «отравленные» (poisoned) — любое обращение детектируется. Замедление ~2x.

### Valgrind (memcheck)

```bash
valgrind ./prog
```

Ловит то же, медленнее (~10-30x), но не требует перекомпиляции. ASan обычно предпочтительнее.

### Статический анализ

- clang-tidy: `bugprone-use-after-move`, `clang-analyzer-cplusplus.NewDelete`
- Компиляторные `-Wall -Wextra` ловят простейшие случаи

**Практика:** ASan в CI + code review семантики владения. Статический анализ ловит не всё (межпроцедурный UAF труден для анализа).

## Связанное: use-after-move

Не совсем UAF, но родственно — обращение к «содержимому» после move:

```cpp
std::string s = "hello";
std::string t = std::move(s);
std::cout << s;        // ✅ НЕ UB — s в valid but unspecified состоянии
                       //    (но значение не определено — обычно пусто)
s.size();              // ✅ можно вызывать
s[0];                  // ⚠️ UB если s пуст — обращение за границы

s = "new";             // ✅ переприсваивание всегда ОК
```

После move объект **валиден** (можно разрушить, переприсвоить), но **полагаться на значение нельзя**. Это мягче, чем UAF (не use-after-free памяти), но тоже баг. Мы это разбирали в теме move-семантики. clang-tidy `bugprone-use-after-move` ловит.

## Формулировки на собеседовании

**«Что такое use-after-free?»** — Обращение к памяти после её освобождения. Опаснее общего dangling, потому что освобождённая память может быть **переиспользована** под другой объект → чтение/запись чужого живого объекта, вектор эксплуатации.

**«Почему это эксплуатируется?»** — Аллокатор переиспользует освобождённые блоки. Если между `delete` и обращением вклинилась чужая аллокация того же размера, обращение идёт к другому объекту. Для полиморфных типов перезапись vtable-указателя → перехват потока управления.

**«Что такое double-free?»** — Освобождение уже освобождённой памяти. Повреждает метаданные аллокатора → падение или эксплойт при следующей аллокации.

**«Как предотвращать?»** — Smart pointers (`unique_ptr` устраняет double-free и забытый delete; `shared_ptr` — разделяемое владение); `weak_ptr` для наблюдения за возможно-удалённым; сырой указатель — только наблюдение, никогда владение; `shared_from_this` для async; ASan в CI.

**«В чём корень проблемы с сырыми указателями?»** — Неясная семантика владения: из `Widget*` не видно, кто отвечает за удаление → путаница «кто удаляет», алиасы, double-free. Smart pointers кодируют владение в типе.

**«Как ASan ловит UAF?»** — Освобождённые блоки помещаются в карантин и помечаются «отравленными»; любое обращение детектируется, с отчётом о месте выделения и освобождения.

---

Отличие от Java: use-after-free **невозможен** — GC не освобождает объект, пока на него есть хоть одна ссылка. Ты физически не можешь обратиться к освобождённой памяти. Цена — недетерминированность (не знаешь, когда объект удалится) и накладные расходы GC (паузы, память). В C++ ты получаешь детерминированное разрушение (RAII, предсказуемый деструктор) и нулевой оверхед — ценой того, что **сам** отвечаешь за то, чтобы не обратиться к мёртвому объекту. Это фундаментальный размен: Java исключает целый класс багов автоматически, C++ требует дисциплины (владение через smart pointers, RAII), но не платит за GC. Именно поэтому Rust так интересен как третий путь: borrow checker ловит use-after-free **на этапе компиляции**, давая и безопасность Java, и zero-cost/детерминизм C++ — раз ты учишь Rust, обрати внимание, что его правила владения (один owner, borrow rules, lifetimes) — это ровно формализация тех практик, которые в C++ приходится соблюдать вручную.
