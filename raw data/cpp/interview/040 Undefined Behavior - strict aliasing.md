# UB: strict aliasing

Мы касались этого в теме `reinterpret_cast` — теперь подробно, потому что это одно из самых коварных UB: код «работает» на `-O0` и ломается на `-O2`.

## Что такое aliasing

**Aliasing** — когда два указателя ссылаются на **одну и ту же память**.

```cpp
int x = 5;
int* p = &x;
int* q = &x;   // p и q — алиасы: указывают на один объект
```

Проблема для оптимизатора: если функция принимает два указателя, может ли запись через один изменить значение по другому?

```cpp
void f(int* a, int* b) {
    *a = 5;
    *b = 10;
    // *a всё ещё 5? Или b == a и теперь *a == 10?
    // компилятор ДОЛЖЕН перечитывать *a, если не уверен, что a != b
    use(*a);
}
```

Если компилятор **не может** доказать, что `a` и `b` не алиасят, он вынужден перечитывать память после каждой записи → меньше оптимизаций (нельзя держать значение в регистре).

---

## Strict aliasing rule

**Правило:** доступ к объекту через указатель/ссылку **несовместимого типа** — **UB**.

Следствие для оптимизатора: **указатели разных типов НЕ алиасят** (можно предполагать). Это разрешает держать значения в регистрах, переупорядочивать чтения/записи, векторизовать.

```cpp
void f(int* i, float* f) {
    *i = 5;
    *f = 3.14;      // компилятор ЗНАЕТ: float* не алиасит int* → *i всё ещё 5
    use(*i);        // может использовать закешированное 5, не перечитывая память
}
```

Если бы `i` и `f` могли указывать на одну память, оптимизация была бы неверна. Strict aliasing **разрешает** её, объявляя такой доступ UB.

---

## Что «совместимо» (можно), что нет (UB)

### ✅ Разрешённые типы доступа к объекту типа T

1. **`T`** (сам тип) и его cv-квалифицированные версии (`const T`, `volatile T`)
2. **Знаковая/беззнаковая версия** `T` (`int` ↔ `unsigned int`)
3. **`char`, `unsigned char`, `std::byte`** — могут алиасить **что угодно** (специальное исключение)
4. Базовый класс `T`
5. Агрегат/union, содержащий `T`

### ⚠️ UB — доступ через несовместимый тип

```cpp
float f = 3.14f;
int* p = reinterpret_cast<int*>(&f);
int bits = *p;         // ⚠️ UB — читаем float через int*

int arr[10];
float* fp = reinterpret_cast<float*>(arr);
fp[0] = 1.0f;          // ⚠️ UB — пишем в int-массив через float*

struct A { int x; };
struct B { int y; };
A a{5};
B* b = reinterpret_cast<B*>(&a);
b->y;                  // ⚠️ UB — хотя layout идентичен!
```

## Классический пример поломки

Type punning (интерпретация битов одного типа как другого) через `reinterpret_cast`:

```cpp
// ❌ НАРУШЕНИЕ strict aliasing
float fast_inverse_sqrt(float x) {
    int i = *reinterpret_cast<int*>(&x);   // ⚠️ UB — читаем float через int*
    i = 0x5f3759df - (i >> 1);              // магия Кармака
    x = *reinterpret_cast<float*>(&i);      // ⚠️ UB — читаем int через float*
    return x;
}
```

Знаменитый Quake III trick. На старых компиляторах работал, на современных с `-O2` — **ломается** (UB, компилятор оптимизирует, полагаясь на то, что `float*` и `int*` не алиасят).

### Демонстрация поломки

```cpp
int foo(float* f, int* i) {
    *i = 1;
    *f = 0.0f;       // ⚠️ если f и i алиасят (через reinterpret_cast) — но компилятор считает, что НЕТ
    return *i;       // компилятор: "*i не изменилось (f — другой тип)" → возвращает закешированную 1
}

int x;
foo(reinterpret_cast<float*>(&x), &x);   // мы-то знаем, что это ОДНА память
// -O0: вернёт результат реального *f = 0 → перечитанное *i
// -O2: вернёт 1 (компилятор закешировал, полагаясь на strict aliasing)
```

Один и тот же код → разный результат на разных `-O` → признак UB.

## Правильные способы type punning

### 1. `std::bit_cast` (C++20) — лучший

```cpp
float f = 3.14f;
int bits = std::bit_cast<int>(f);   // ✅ безопасно, constexpr, ноль стоимости

float f2 = std::bit_cast<float>(bits);   // ✅ обратно
```

Требования: одинаковый `sizeof`, тривиально копируемые типы. Компилируется в ноль инструкций (просто переинтерпретация регистра), но **без UB**.

### 2. `std::memcpy` (до C++20 — канонический способ)

```cpp
float f = 3.14f;
int bits;
std::memcpy(&bits, &f, sizeof(f));   // ✅ легально — memcpy работает с байтами
```

Выглядит как «копирование туда-сюда», но **компилятор оптимизирует его в ноль инструкций** (распознаёт паттерн). `memcpy` легален, потому что копирует **байтовое представление**, а доступ через `char`/байты разрешён.

### 3. Доступ через `char*` / `std::byte*` — всегда легален

```cpp
float f = 3.14f;
unsigned char* bytes = reinterpret_cast<unsigned char*>(&f);   // ✅ char* алиасит всё
for (size_t i = 0; i < sizeof(f); ++i)
    printf("%02x ", bytes[i]);       // ✅ читаем байтовое представление
```

**Ключевое исключение strict aliasing:** `char`, `unsigned char`, `std::byte` могут алиасить **любой** тип. Именно поэтому `memcpy` (работающий через байты) легален, и `std::span<std::byte>` / `as_bytes` (которые мы разбирали) безопасны.

### 4. `union` — легально в C, но type punning через union — UB в C++!

```cpp
union U { float f; int i; };
U u;
u.f = 3.14f;
int bits = u.i;   // ⚠️ UB в C++ (чтение неактивного члена)!
                  // ✅ легально в C (там union type punning разрешён)
```

Частая ловушка: в **C** чтение неактивного члена union — легальный type punning, в **C++** — UB (нужно писать в активный, читать из активного). На практике многие компиляторы это поддерживают как расширение, но по стандарту C++ — UB. Не полагайся на это.

---

## Сравнение способов

|Способ|Легально|Стоимость|Стандарт|
|---|---|---|---|
|`reinterpret_cast` + разыменование|❌ **UB**|0|—|
|`union` type punning|❌ **UB в C++** (✅ в C)|0|—|
|`std::memcpy`|✅|0 (оптимизируется)|C++98|
|`char*` доступ|✅|0|C++98|
|`std::bit_cast`|✅|0|C++20|

**Правило: для type punning — `std::bit_cast` (C++20) или `memcpy`. Никогда не `reinterpret_cast` + разыменование.**

---

## `restrict` (C, не стандартный C++) — обратная сторона

`restrict` — обещание компилятору, что указатели **не** алиасят (усиление оптимизации):

```c
void add(int* restrict dst, const int* restrict a, const int* restrict b, int n) {
    for (int i = 0; i < n; ++i)
        dst[i] = a[i] + b[i];   // компилятор ЗНАЕТ: dst не пересекается с a,b → векторизует
}
```

В стандартном C++ `restrict` нет, но компиляторы предоставляют `__restrict` (GCC/Clang/MSVC). Если нарушить обещание (передать алиасящие указатели) — UB.

Это «ручное» продолжение той же идеи: strict aliasing даёт бесплатный no-alias для разных типов, `restrict` — для одинаковых типов вручную.

---

## Почему strict aliasing существует

Без него компилятор был бы вынужден считать, что **любые** два указателя могут алиасить → перечитывать память после каждой записи через любой указатель:

```cpp
void scale(float* data, int n, float factor) {
    for (int i = 0; i < n; ++i)
        data[i] *= factor;   // без strict aliasing: а вдруг factor лежит в data[i]?
                             //    → перечитывать factor каждую итерацию, не векторизовать
}
```

Strict aliasing разрешает предположить, что `float* data` и `float factor` (разные... хотя тут одинаковый тип — плохой пример). Реально выигрыш на **разнотипных** указателях: индекс `int i` точно не пересекается с `float* data` → можно держать в регистре, векторизовать цикл.

Это **fundamental enabler** для оптимизаций в числовом коде. Отключение (`-fno-strict-aliasing`) может замедлить код в разы.

---

## `-fno-strict-aliasing`

```bash
g++ -fno-strict-aliasing prog.cpp   # ОТКЛЮЧИТЬ правило (сделать aliasing легальным)
```

Компилятор перестаёт предполагать, что разные типы не алиасят → `reinterpret_cast` type punning «работает». Ценой потери оптимизаций.

Ядро Linux собирается с `-fno-strict-aliasing` — там слишком много legacy type punning, дешевле отключить правило, чем переписать. Но для нового кода — **не полагайся на это**, используй `bit_cast`/`memcpy`.

---

## Обнаружение

```bash
g++ -Wstrict-aliasing=2 -O2 prog.cpp   # предупреждения о нарушениях
```

`-Wstrict-aliasing` ловит **часть** нарушений (не все — межпроцедурные трудны для анализа). Работает только с `-O2+` (нужен анализ потока данных).

Санитайзеры (ASan, UBSan) strict aliasing **не ловят надёжно** — это не runtime-нарушение памяти, а нарушение предположений оптимизатора. TySan (Type Sanitizer, экспериментальный в Clang) — специализированный инструмент, но пока сырой.

Отсюда коварство: **нет надёжного детектора**. Единственная защита — не писать `reinterpret_cast` type punning вообще.

## Формулировки на собеседовании

**«Что такое strict aliasing?»** — Правило: доступ к объекту через указатель/ссылку **несовместимого типа** — UB. Позволяет компилятору предполагать, что указатели разных типов **не алиасят** → держать значения в регистрах, переупорядочивать, векторизовать.

**«Какие типы могут алиасить любой объект?»** — `char`, `unsigned char`, `std::byte`. Специальное исключение — поэтому `memcpy` и байтовый доступ легальны.

**«Почему type punning через `reinterpret_cast` — UB?»** — Чтение объекта одного типа через указатель другого нарушает strict aliasing. Компилятор оптимизирует, полагаясь на «эти указатели не алиасят» → код ломается на `-O2`, хотя работает на `-O0`.

**«Как правильно делать type punning?»** — `std::bit_cast<T>(x)` (C++20) или `std::memcpy` (раньше). Оба легальны и оптимизируются в ноль инструкций. `char*`-доступ — для побайтовой работы.

**«Легален ли type punning через union?»** — В **C** — да, в **C++** — **UB** (чтение неактивного члена). Частая ловушка при переходе с C.

**«Почему strict aliasing сложно отлаживать?»** — Нет надёжного рантайм-детектора (это нарушение предположений оптимизатора, а не доступа к памяти). Проявляется как «работает на -O0, ломается на -O2». Единственная защита — не нарушать (использовать `bit_cast`/`memcpy`).

**«Что делает `-fno-strict-aliasing`?»** — Отключает правило: компилятор считает, что любые указатели могут алиасить. `reinterpret_cast` type punning становится безопасным, ценой потери оптимизаций. Так собирается ядро Linux.

---

Отличие от Java: там strict aliasing **не существует как проблема**. Причины: (1) нет `reinterpret_cast` и указателей — нельзя интерпретировать биты одного типа как другой напрямую; (2) для type punning есть явные API — `Float.floatToIntBits()`, `Double.doubleToLongBits()`, `ByteBuffer` — все **безопасные и определённые**; (3) JVM сама управляет памятью и типами, aliasing разных типов невозможен на уровне модели. То есть Java даёт то, что в C++ приходится делать через `bit_cast`, как встроенные безопасные методы. Для тебя вывод: привычного из Java «просто переинтерпретировать биты» в C++ через указатели **нельзя** — это UB; используй `std::bit_cast` (это и есть прямой аналог `Float.floatToIntBits`). Ещё: HotSpot JIT делает свои alias-анализы для оптимизации, но это внутреннее дело JVM, программисту невидимое и безопасное — в отличие от C++, где ответственность за соблюдение strict aliasing на тебе.
