# Header/cpp разделение

## Модель компиляции C++

Фундамент, из которого всё следует. C++ использует модель **раздельной компиляции**, унаследованную от C:

```
исходники → [препроцессор] → [компилятор] → объектные файлы → [линкер] → исполняемый файл
  .cpp                          каждый .cpp        .o/.obj
  .h                            отдельно
```

Каждый `.cpp` — **единица трансляции** (translation unit, TU) — компилируется **независимо**, ничего не зная о других. Линкер потом сшивает результаты по именам символов.

Ключевое: компилятор, обрабатывая `a.cpp`, **не видит** `b.cpp`. Всё, что нужно знать о коде из других TU, должно быть **объявлено** — через заголовки.

---

## Declaration vs Definition

Центральное различие.

**Объявление (declaration)** — «такая сущность существует, вот её имя и тип»:

```cpp
void f(int);              // объявление функции
extern int global;        // объявление переменной
class Widget;             // объявление класса (forward declaration)
int g(int x);             // объявление
```

**Определение (definition)** — «вот полная реализация/содержимое»:

```cpp
void f(int x) { /* тело */ }   // определение функции
int global = 42;               // определение переменной
class Widget { /* члены */ };  // определение класса
```

Правило: **объявлений может быть много, определение — одно** (ODR, см. ниже).

Заголовки содержат **объявления** (чтобы разные TU знали об интерфейсе), `.cpp` — **определения**.

## Что куда

### Header (.h/.hpp)

```cpp
// widget.h
#pragma once                       // include guard

#include <string>                  // нужные для интерфейса заголовки

class Widget {
public:
    Widget(int value);             // объявления методов
    void process();
    int getValue() const;

private:
    int value_;                    // определение класса (члены) — ОБЯЗАТЕЛЬНО в заголовке
    std::string name_;
};

void freeFunction(int x);          // объявление свободной функции
extern int globalCounter;          // объявление глобальной переменной
constexpr int MAX = 100;           // constexpr — можно в заголовке (implicitly inline)
```

Заголовок описывает **что** класс/функция делает — их интерфейс.

### Source (.cpp)

```cpp
// widget.cpp
#include "widget.h"

Widget::Widget(int value) : value_(value) {}    // определения методов
void Widget::process() { value_ *= 2; }
int Widget::getValue() const { return value_; }

void freeFunction(int x) { /* ... */ }          // определение функции
int globalCounter = 0;                           // определение переменной
```

`.cpp` описывает **как** — реализацию.

## ODR — One Definition Rule

Ключевое правило, объясняющее разделение.

**Каждая сущность (функция, переменная, класс) должна иметь ровно ОДНО определение во всей программе.**

Нарушение → ошибка линковки (или UB, если определения различаются).

### Почему определения функций — в .cpp

```cpp
// ❌ определение в заголовке
// util.h
int add(int a, int b) { return a + b; }   // определение

// a.cpp: #include "util.h"  → определение add попадает в a.o
// b.cpp: #include "util.h"  → определение add попадает в b.o
// линкер: ⚠️ "multiple definition of add" — ДВА определения!
```

Заголовок **копируется** препроцессором в каждый включающий `.cpp`. Если там определение — оно дублируется в каждой TU → нарушение ODR.

Решение: объявление в заголовке, определение в **одном** .cpp:

```cpp
// util.h
int add(int a, int b);      // ✅ объявление — можно во многих TU

// util.cpp
int add(int a, int b) { return a + b; }   // ✅ определение — в одной TU
```

### Исключения из ODR — что МОЖНО определять в заголовке

Некоторые сущности **разрешено** определять в заголовке (они «inline» — множественные идентичные определения допустимы):

```cpp
// ✅ разрешено в заголовке:
inline int add(int a, int b) { return a + b; }   // inline-функции
class Widget { void f() { } };                    // методы, определённые ВНУТРИ класса — неявно inline
template<class T> T max(T a, T b);                // ШАБЛОНЫ (мы разбирали — обязаны быть в заголовке)
constexpr int MAX = 100;                          // constexpr переменные
inline int counter = 0;                           // C++17: inline-переменные
```

`inline` здесь означает не «встрой меня», а «**разрешаю несколько идентичных определений**» — линкер выберет одно. Это и позволяет header-only библиотекам существовать.

## Include guards — защита от двойного включения

```cpp
// widget.h
#pragma once            // современный способ (нестандартный, но поддержан везде)

// или классический:
#ifndef WIDGET_H
#define WIDGET_H
// ... содержимое ...
#endif
```

**Зачем:** заголовок может быть включён несколько раз транзитивно:

```cpp
// a.h #include "widget.h"
// b.h #include "widget.h"
// main.cpp:
#include "a.h"    // тянет widget.h
#include "b.h"    // тянет widget.h СНОВА
// без guard: класс Widget определён ДВАЖДЫ в одной TU → ошибка "redefinition"
```

Guard гарантирует: содержимое заголовка вставится в каждую TU **один раз**, даже при множественном включении. Обязательны для **всех** заголовков.

`#pragma once` vs `#ifndef`: `#pragma once` короче, быстрее (компилятор не парсит файл повторно), но формально нестандартен (хотя поддержан всеми). `#ifndef` — стандартный, переносимый, но требует уникального имени макроса (коллизии → баги). На практике оба приемлемы.

## Forward declaration — уменьшение зависимостей

Если нужен только **указатель/ссылка** на тип (не его размер/члены) — достаточно **объявления**, не полного определения:

```cpp
// ❌ включаем полный заголовок — тяжёлая зависимость
// manager.h
#include "widget.h"       // тянет весь widget.h + его зависимости

class Manager {
    Widget* widget_;      // нужен только указатель!
};
```

```cpp
// ✅ forward declaration — минимальная зависимость
// manager.h
class Widget;             // ← достаточно объявления для указателя/ссылки

class Manager {
    Widget* widget_;      // ✅ указатель на неполный тип — ОК
    void process(Widget& w);   // ✅ ссылка в параметре — ОК
};

// manager.cpp
#include "widget.h"       // ✅ полное определение нужно ЗДЕСЬ (при использовании)
void Manager::process(Widget& w) { w.doSomething(); }   // тут нужен полный Widget
```

### Когда достаточно forward declaration

**Достаточно** (нужен только объявленный тип):

- указатель `Widget*` / ссылка `Widget&`
- параметр/возврат по значению **в объявлении** функции
- `friend class Widget;`

**Нужно полное определение** (компилятор должен знать размер/члены):

- член по значению `Widget w;` (нужен `sizeof`)
- наследование `class X : Widget`
- вызов методов `w.foo()`
- `new Widget` / `delete` / `sizeof(Widget)`
- контейнер по значению `std::vector<Widget>` (обычно; зависит от использования)

Forward declaration — главный инструмент **сокращения зависимостей компиляции**. Меньше `#include` в заголовках → быстрее сборка, меньше перекомпиляций при изменениях. Прямо связано с pImpl (мы разбирали): pImpl доводит эту идею до предела — forward-declared `Impl` полностью прячет реализацию.

## Проблема транзитивных зависимостей

```cpp
// widget.h
#include <boost/asio.hpp>    // ⚠️ тяжёлый заголовок

// a.h #include "widget.h"    → тянет boost::asio
// b.cpp #include "a.h"        → компилирует весь boost::asio, даже если не использует его напрямую
```

Каждый `#include` в заголовке **транзитивно** попадает во все включающие TU. Тяжёлые заголовки в публичных `.h` → медленная компиляция всего проекта.

**Правило: минимизируй `#include` в заголовках.**

- В заголовке — только то, что нужно **интерфейсу**
- Всё остальное — forward declaration + `#include` в `.cpp`
- Тяжёлые зависимости прячь через pImpl

```cpp
// ❌ widget.h тянет всё
#include <vector>
#include <boost/asio.hpp>
#include "database.h"

// ✅ widget.h минимален
#include <memory>     // только для unique_ptr
class Database;        // forward
struct Widget::Impl;   // pImpl прячет boost::asio и std::vector
```

## `inline` для header-only

Если хочешь функцию **в заголовке** (header-only библиотека) — помечай `inline`:

```cpp
// util.h — header-only
#pragma once

inline int square(int x) {        // ✅ inline → множественные определения ОК
    return x * x;
}

inline int counter = 0;           // ✅ C++17: inline-переменная (одна на программу)

template<class T>                 // ✅ шаблоны — неявно допускают множественные определения
T max(T a, T b) { return a > b ? a : b; }
```

Header-only удобны (нет `.cpp`, легко подключить), но:

- Определения видны всем TU → **дольше компиляция** (парсинг + инстанцирование в каждой TU)
- Изменение → перекомпиляция всех включающих (нет compilation firewall)

Компромисс: удобство подключения ↔ скорость сборки. Boost — исторически header-only (шаблоны вынуждают), отсюда его репутация «медленной компиляции».

## Что ДОЛЖНО быть в заголовке (нет выбора)

Некоторые вещи **обязаны** быть в заголовке, потому что компилятор должен видеть их определение в каждой TU:

1. **Определение класса** (члены, layout) — иначе нельзя создать объект, узнать `sizeof`
2. **Шаблоны** (мы разбирали — мономорфизация требует видеть тело для инстанцирования)
3. **inline-функции** (по определению)
4. **constexpr-функции/переменные** (нужны в compile-time контексте)
5. **enum** (нужен размер и значения)

Всё остальное (определения обычных функций, невиртуальных методов, глобальных переменных) — в `.cpp`.

## Практические правила организации

```cpp
// Порядок включений в .cpp (Google style):
#include "widget.h"        // 1. СВОЙ заголовок первым — проверяет самодостаточность
                           //    (если widget.h не включает нужное — ошибка вылезет сразу)
#include <vector>          // 2. стандартная библиотека
#include <string>
#include <boost/asio.hpp>  // 3. сторонние библиотеки
#include "database.h"      // 4. свои заголовки проекта
```

**Self-sufficiency:** каждый заголовок должен компилироваться **сам по себе** (включать всё, что использует). Проверяется тем, что `.cpp` включает свой `.h` первым.

**IWYU (Include What You Use):** включай ровно то, что используешь напрямую; не полагайся на транзитивные включения. Есть инструмент `include-what-you-use` (на базе Clang), который это проверяет.

## Формулировки на собеседовании

**«Почему в C++ разделяют .h и .cpp?»** — Модель раздельной компиляции: каждый `.cpp` компилируется независимо (translation unit), не видя других. Заголовки несут **объявления** (чтобы TU знали об интерфейсе), `.cpp` — **определения**. Линкер сшивает по именам символов.

**«Почему определение функции в заголовке даёт ошибку линковки?»** — Заголовок копируется в каждую включающую TU → определение дублируется → нарушение **ODR** (One Definition Rule) → "multiple definition". Решение: объявление в `.h`, определение в одном `.cpp`; либо `inline`.

**«Что такое ODR?»** — Каждая сущность должна иметь ровно одно определение в программе. Исключения (можно многократно): inline-функции, методы внутри класса, шаблоны, constexpr, inline-переменные (C++17) — они допускают идентичные определения в разных TU.

**«Зачем include guards?»** — Защита от многократного включения заголовка в одну TU (через транзитивные `#include`) → иначе повторное определение класса. `#pragma once` или `#ifndef/#define/#endif`.

**«Когда достаточно forward declaration?»** — Когда нужен только указатель/ссылка на тип (не размер/члены): `Widget*`, `Widget&`, параметры в объявлениях. Полное определение нужно для: члена по значению, наследования, вызова методов, `new`/`sizeof`.

**«Зачем минимизировать include в заголовках?»** — Транзитивные зависимости: каждый `#include` в `.h` попадает во все включающие TU → медленная компиляция и лишние перекомпиляции. Forward declaration + include в `.cpp` + pImpl разрывают зависимости.

**«Почему шаблоны в заголовках?»** — Мономорфизация: компилятор инстанцирует шаблон для конкретных типов в каждой TU, где он используется → нужно видеть **определение**, а не только объявление.

---

Отличие от Java: там **нет** разделения интерфейс/реализация на уровне файлов — один `.java` содержит и объявления, и реализацию. Причины, по которым это возможно: (1) Java компилируется **по классам** — компилятор читает `.class`-файлы зависимостей (содержащие сигнатуры), а не «заголовки»; байткод несёт метаданные о типах, поэтому «объявление» и «определение» не разделены. (2) Нет препроцессора и `#include` — зависимости резолвятся по `import` и classpath, транзитивного копирования текста нет. (3) Нет ODR-проблемы — каждый класс определён в своём файле, дублирования быть не может. (4) Нет forward declaration — компилятор видит все классы через classpath. Итог: вся машинерия header/cpp, ODR, include guards, forward declaration — это следствие **C-модели компиляции с текстовым включением**, которой в Java нет by design. Для тебя, работающего с большим C++ монолитом, практический вывод: управление зависимостями заголовков (forward declaration, pImpl, минимум include) — это **главный рычаг** контроля времени сборки, тогда как в Java время компиляции определяется в основном объёмом кода, а не структурой зависимостей заголовков.
