# UB: dangling references и pointers

## Что это

**Dangling** — указатель/ссылка/итератор/view, ссылающийся на объект, который **уже разрушен** или память которого освобождена.

Любое обращение через него — **UB**. Не «прочитаешь мусор», а именно UB: программа может работать «правильно» месяцами, а потом упасть в другом месте после безобидного изменения.

```cpp
int* p;
{
    int x = 42;
    p = &x;
}          // x разрушен
*p;        // ⚠️ UB — dangling pointer
```

---

## Почему опасно именно в C++

Память **не обнуляется** при разрушении объекта — там остаются старые байты. Поэтому dangling часто **«работает»**:

```cpp
int* danger() {
    int x = 42;
    return &x;    // ⚠️ UB
}

int* p = danger();
std::cout << *p;   // может напечатать 42! (стек ещё не перезаписан)

foo();             // вызов другой функции — тот же стековый фрейм перезаписан
std::cout << *p;   // теперь мусор
```

Это худший вид бага: **не воспроизводится, зависит от оптимизаций, компилятора, порядка вызовов**. Компилятор вправе предполагать, что UB не происходит, и оптимизировать соответственно — программа может вести себя как угодно.

---

## Категории dangling

### 1. Возврат ссылки/указателя на локальную переменную

Мы разбирали это в теме lifetime — самый базовый случай:

```cpp
int& bad1() {
    int x = 42;
    return x;              // ⚠️ UB
}

std::string& bad2() {
    return "hello";        // ⚠️ ссылка на временный string
}

int* bad3() {
    int arr[10];
    return arr;            // ⚠️ распад массива → указатель на локальный массив
}

std::string_view bad4() {
    std::string s = "hello";
    return s;              // ⚠️ view на локальную строку
}

std::span<int> bad5() {
    std::vector<int> v{1,2,3};
    return v;              // ⚠️ span на локальный вектор
}
```

Все компиляторы предупреждают о самых очевидных (`-Wreturn-local-addr`), но не ловят косвенные случаи.

### 2. Указатель на удалённый объект (use-after-free)

```cpp
Widget* p = new Widget();
delete p;
p->use();          // ⚠️ UB — use-after-free
delete p;          // ⚠️ UB — double-free

// Классика с shared состоянием:
Widget* w = new Widget();
Widget* alias = w;
delete w;
alias->use();      // ⚠️ UB — второй указатель не знает об удалении
```

**Хорошая практика:** после `delete` обнулять указатель (`delete p; p = nullptr;`) — тогда повторное разыменование хотя бы упадёт детерминированно. Но лучше — **не использовать сырой `new`/`delete`** вообще (smart pointers).

### 3. Инвалидация итераторов/указателей в контейнерах

Мы разбирали подробно — самая частая практическая причина:

```cpp
std::vector<int> v{1,2,3};
int* p = &v[0];
auto it = v.begin();

v.push_back(4);    // ⚠️ реаллокация → p и it — dangling

*p;                // ⚠️ UB
*it;               // ⚠️ UB
```

Опасность в том, что **выглядит невинно** — никакого `delete`, никакого выхода из области видимости.

Особенно коварно с `string_view` / `span`:

```cpp
std::string s = "short";
std::string_view sv = s;
s = "a much longer string";   // ⚠️ реаллокация (SSO больше не хватает) → sv повис
std::cout << sv;               // ⚠️ UB
```

### 4. Ссылка на элемент разрушенного временного

```cpp
// ⚠️ lifetime extension НЕ проходит через функцию
const int& identity(const int& r) { return r; }
const int& x = identity(42);   // ⚠️ временный 42 умер в конце выражения
std::cout << x;                 // ⚠️ UB

// ✅ прямая привязка — работает
const int& y = 42;             // ✅ временный живёт, пока живёт y
```

Мы это разбирали — продление жизни работает только при **непосредственной** привязке временного к ссылке.

Более коварный вариант — цепочка через member:

### Работает — привязка к **подобъекту** временного

```cpp
struct Widget { std::vector<int> data; };
Widget make();

const auto& v = make().data;   // ✅ КОРРЕКТНО, продление жизни РАБОТАЕТ
use(v);                         // ✅ временный Widget жив, пока жив v
```

`make()` — prvalue. Выражение `make().data` — обращение к **члену** временного объекта. Стандарт продлевает жизнь **всего** временного `Widget` до конца жизни `v`.

Правило: если ссылка привязывается к **подобъекту** временного (член, элемент массива, базовый класс), продлевается **весь** временный объект.

### Не работает — возврат ссылки из функции

```cpp
struct Widget { 
    std::vector<int> data;
    const std::vector<int>& getData() const { return data; }
};
Widget make();

const auto& v = make().getData();   // ⚠️ UB — продление НЕ работает
use(v);                              // ⚠️ временный Widget уже мёртв
```

Здесь `make().getData()` — это **вызов функции, возвращающей ссылку**. Компилятор видит только «выражение типа `const vector<int>&`» — он **не отслеживает**, откуда эта ссылка взялась. Механизм продления жизни не «проникает» сквозь возврат из функции.

Ровно то же, что мы разбирали в теме lifetime:

```cpp
const int& identity(const int& r) { return r; }
const int& x = identity(42);   // ⚠️ UB — продление не проходит через функцию
const int& y = 42;             // ✅ прямая привязка — работает
```

---

## Правило одной фразой

**Продление жизни работает только при _прямой_ привязке ссылки к временному объекту или его подобъекту. Оно не проходит через возврат ссылки из функции.**

```cpp
Widget make();

const Widget& a = make();              // ✅ прямая привязка временного
const auto& b = make().data;           // ✅ подобъект (член) временного
const auto& c = make().data[0];        // ✅ подобъект подобъекта
const auto& d = make().getData();      // ⚠️ UB — ссылка вернулась ИЗ ФУНКЦИИ
const auto& e = std::move(make());     // ⚠️ UB — тоже «прошло через функцию»
```

Почему так: компилятор реализует продление жизни синтаксически — он видит, что ссылка инициализируется **выражением, дающим временный** (или его часть), и продлевает. Функция, возвращающая `T&`, — это «просто ссылка», происхождение которой компилятор не анализирует.

---

## Практический вывод

Опасность именно в том, что оба случая **выглядят одинаково** в месте использования:

```cpp
const auto& v = make().data;        // ✅ безопасно
const auto& v = make().getData();   // ⚠️ UB
```

Разница — **только** в том, поле это или геттер. Причём геттеры куда типичнее в реальном коде.

**Надёжное правило: не привязывай ссылку к чему-либо, полученному из временного объекта через вызов функции. Материализуй временный:**

```cpp
auto w = make();                   // ✅ временный материализован в переменную
const auto& v = w.getData();       // ✅ w жив, пока жив v
```

Именно поэтому range-for по временному был UB до C++23 (`for (int x : make().get())`) — там ровно этот механизм: `auto&& __range = make().get();` — ссылка из функции, временный `Widget` не продлевается.

### 5. Range-for по временному (классическая ловушка)

```cpp
struct Widget { std::vector<int> data; std::vector<int>& get() { return data; } };
Widget make();

for (int x : make().get()) { }   // ⚠️ UB до C++23!
```

Механика: range-for разворачивается в

```cpp
auto&& __range = make().get();   // ⚠️ __range — ссылка на vector внутри ВРЕМЕННОГО Widget
                                  //    временный Widget умирает в конце этой строки!
for (auto __it = __range.begin(); ...) { }   // ⚠️ обход мёртвого вектора
```

Продление жизни применяется к результату `get()` (это ссылка, продлевать нечего), а **сам временный `Widget` не продлевается**.

**C++23 исправил это** (P2718R0): все временные в range-инициализаторе теперь продлеваются до конца цикла.

Но в C++20 и раньше — UB. Обход:

```cpp
auto w = make();                 // ✅ материализуем
for (int x : w.get()) { }        // ✅ w жив весь цикл
```

### 6. Лямбда, захватившая по ссылке

```cpp
std::function<int()> f;
{
    int x = 42;
    f = [&x]{ return x; };   // ⚠️ захват по ссылке
}                             // x умер
f();                          // ⚠️ UB
```

Мы разбирали в теме лямбд. `[&]` особенно опасен — не видно, что именно захвачено.

Асинхронный вариант (частый в Asio — твой стек):

```cpp
void Session::start() {
    async_read(buf, [this](auto ec) {   // ⚠️ this может умереть до колбэка
        process();
    });
}
```

Решение — `shared_from_this()` (разбирали).

### 7. Dangling `this`

```cpp
class Widget {
public:
    void selfDestruct() {
        delete this;      // легально (если объект на heap)
        member_ = 42;     // ⚠️ UB — объект разрушен!
    }
private:
    int member_;
};
```

### 8. Указатель на элемент, удалённый из контейнера

```cpp
std::map<int, Widget> m;
Widget* p = &m[1];
m.erase(1);        // ⚠️ элемент разрушен
p->use();          // ⚠️ UB
```

Хотя `map` не инвалидирует другие итераторы, **удалённый** элемент разрушен.

---

## Как защищаться

### 1. Не используй сырые владеющие указатели

```cpp
// ❌
Widget* w = new Widget();
delete w;

// ✅
auto w = std::make_unique<Widget>();   // ✅ автоматическое удаление
```

Смарт-указатели убирают целый класс ошибок: double-free, забытый delete, use-after-free при исключении.

### 2. `weak_ptr` для наблюдения

```cpp
std::weak_ptr<Widget> observer = sharedWidget;

if (auto locked = observer.lock()) {   // ✅ безопасная проверка
    locked->use();
} else {
    // объект уже удалён — не UB, а корректная обработка
}
```

Это единственный **безопасный** способ хранить «указатель, который может стать невалидным».

### 3. Владение вместо наблюдения

Идиома, которую мы повторяли: **принимай view, храни владеющий тип.**

```cpp
// ❌
class Config {
    std::string_view name_;   // ⚠️ на что указывает?
public:
    Config(std::string_view n) : name_(n) { }
};

// ✅
class Config {
    std::string name_;                         // ✅ владеет
public:
    Config(std::string_view n) : name_(n) { }  // ✅ копирует
};
```

### 4. Не храни итераторы/указатели через модификацию контейнера

```cpp
// ❌
auto it = v.begin();
v.push_back(x);
*it;   // ⚠️ UB

// ✅ используй индексы
size_t i = 0;
v.push_back(x);
v[i];   // ✅ индекс переживает реаллокацию
```

Или стабилизируй адреса через уровень косвенности:

```cpp
std::vector<std::unique_ptr<Widget>> v;   // ✅ объекты не переезжают при реаллокации
Widget* p = v[0].get();
v.push_back(...);                          // ✅ p валиден
```

### 5. Захват по значению в лямбдах, переживающих scope

```cpp
// ❌
return [&data]{ use(data); };

// ✅
return [data]{ use(data); };                   // копия
return [data = std::move(data)]{ use(data); }; // C++14: перемещение
```

### 6. Sanitizers — обязательны

```bash
g++ -fsanitize=address -g prog.cpp     # ASan — ловит use-after-free, heap-buffer-overflow
```

ASan детектирует:

- use-after-free
- use-after-return (нужен `ASAN_OPTIONS=detect_stack_use_after_return=1`)
- use-after-scope (`-fsanitize=address` + `-fsanitize-address-use-after-scope`)
- double-free
- heap/stack buffer overflow

Замедление ~2x, память ~2-3x. **В debug-сборке и CI — обязательно.**

Дополнительно для контейнеров:

```bash
g++ -D_GLIBCXX_DEBUG            # libstdc++: ловит инвалидированные итераторы явно
g++ -D_GLIBCXX_ASSERTIONS       # проверка границ в operator[]
```

### 7. Статический анализ

- `-Wall -Wextra` — базовые предупреждения (`-Wreturn-local-addr`, `-Wdangling-else`)
- `-Wdangling-gsl` (Clang) — dangling для GSL-типов (`string_view`, `span`)
- clang-tidy: `bugprone-dangling-handle`
- Lifetime profile (Core Guidelines) — экспериментальная проверка времени жизни

Компиляторы **улучшились**: Clang и GCC ловят многие очевидные dangling `string_view`/`span` на этапе компиляции. Но косвенные случаи (через несколько функций) — нет.

## Формулировки на собеседовании

**«Что такое dangling pointer?»** — Указатель на объект, который уже разрушен/освобождён. Обращение через него — **UB**.

**«Почему dangling опаснее, чем nullptr?»** — Разыменование `nullptr` обычно даёт немедленный segfault (детерминированно). Dangling **часто «работает»** (память ещё не перезаписана) → баг проявляется случайно, в другом месте, после безобидных изменений кода.

**«Основные источники dangling?»** — (1) Возврат ссылки/указателя на локальную переменную. (2) Use-after-free. (3) **Инвалидация итераторов/указателей** при реаллокации контейнера. (4) View (`string_view`, `span`), переживший источник. (5) Захват по ссылке в лямбде, живущей дольше scope. (6) Временный объект, не продлённый lifetime extension.

**«Почему `for (int x : make().get())` — UB?»** — Range-for привязывает `auto&& __range = make().get();`. Результат `get()` — ссылка, продлевать нечего; **сам временный объект** от `make()` умирает в конце строки → обход мёртвого контейнера. **C++23 исправил** (все временные в range-инициализаторе продлеваются).

**«Как защищаться?»** — Smart pointers вместо сырых; `weak_ptr` для наблюдения; **принимай view, храни владеющий тип**; не держи итераторы через модификацию; захват по значению в долгоживущих лямбдах; **ASan** в CI.

**«Что видит ASan?»** — use-after-free, use-after-return, use-after-scope, double-free, buffer overflow. Ловит в рантайме на выполненных путях (нужны хорошие тесты).

---

Отличие от Java: там dangling **невозможен** — GC не удалит объект, пока на него есть ссылка. Отсюда фундаментальное различие: в Java «баг времени жизни» превращается в **утечку памяти** (объект жив, хотя не нужен), в C++ — в **use-after-free** (объект мёртв, хотя используется). Java-разработчик приходит в C++ с интуицией «ссылка всегда валидна» — и это **самая опасная привычка**, потому что C++ ничего не проверяет и часто «работает». Именно поэтому в C++ владение — явная часть дизайна (кто владеет? кто наблюдает? как долго живёт?), и почему smart pointers, RAII и правило «принимай view, храни владеющий тип» настолько центральны.
