# pImpl (Pointer to Implementation)

## Что это

Идиома: спрятать все приватные члены класса за указателем на **неполный** тип реализации. В заголовке остаётся только публичный интерфейс + один указатель.

```cpp
// widget.h — то, что видят пользователи
class Widget {
public:
    Widget();
    ~Widget();
    void doSomething();
    int getValue() const;

private:
    class Impl;                      // ← forward declaration (неполный тип)
    std::unique_ptr<Impl> pImpl_;    // ← указатель на реализацию
};
```

```cpp
// widget.cpp — скрыто от пользователей
class Widget::Impl {                 // ← полное определение здесь
public:
    std::vector<int> data_;
    std::string name_;
    ComplexDependency dep_;          // ← тяжёлые зависимости НЕ в заголовке
    int value_ = 0;

    void doSomethingImpl() { /* ... */ }
};

Widget::Widget() : pImpl_(std::make_unique<Impl>()) {}
Widget::~Widget() = default;         // ← ВАЖНО: в .cpp, где Impl полный (см. ниже)

void Widget::doSomething() { pImpl_->doSomethingImpl(); }
int Widget::getValue() const { return pImpl_->value_; }
```

Пользователь видит `widget.h` без деталей реализации; всё «мясо» — в `widget.cpp`.

---

## Зачем: проблемы, которые решает

### 1. Compilation firewall — главная причина

**Проблема:** в C++ приватные члены **видны** в заголовке. Изменение приватного поля → **перекомпиляция всех**, кто включает заголовок.

```cpp
// widget.h
class Widget {
public:
    void doSomething();
private:
    std::vector<int> data_;
    HeavyDependency dep_;    // ⚠️ добавили новое поле →
                             //    ВСЕ .cpp, включающие widget.h, перекомпилируются!
};
```

В большом монолите (твой случай — большая монолитная C++ кодовая база) это критично: изменил приватную деталь одного класса → пересборка пол-проекта, минуты-часы ожидания.

**С pImpl:** приватные члены в `.cpp`. Изменение реализации → перекомпилируется **только** `widget.cpp`, интерфейс не тронут → зависимые модули **не пересобираются**.

```cpp
// widget.h НЕ изменился → зависимые TU не перекомпилируются
// изменения только в widget.cpp → пересобирается ОДИН файл
```

Это самый весомый аргумент в больших кодовых базах — **радикальное сокращение времени пересборки**.

### 2. Сокрытие зависимостей из заголовка

```cpp
// ❌ без pImpl — тащим heavy-зависимости в заголовок
// widget.h
#include <boost/asio.hpp>        // ⚠️ ВСЕ, кто включает widget.h, тянут boost::asio
#include "heavy_library.h"
class Widget {
    boost::asio::io_context ctx_;
    HeavyThing thing_;
};
```

```cpp
// ✅ с pImpl — заголовок чист
// widget.h
#include <memory>                // только это
class Widget {
    class Impl;
    std::unique_ptr<Impl> pImpl_;
};

// widget.cpp
#include <boost/asio.hpp>        // ✅ зависимость скрыта в .cpp
#include "heavy_library.h"
```

Пользователи `widget.h` не платят за включение тяжёлых заголовков → быстрее компиляция, меньше транзитивных зависимостей. Прямо релевантно твоему стеку с Boost.Asio.

### 3. Стабильный ABI (Application Binary Interface)

**Проблема:** размер класса — часть ABI. Добавил поле → `sizeof(Widget)` изменился → весь код, использующий `Widget` по значению, **бинарно несовместим** → нужно перекомпилировать всех клиентов библиотеки.

```cpp
// v1: sizeof(Widget) == 24
// v2: добавили поле → sizeof(Widget) == 32
// ⚠️ старый бинарник, ожидающий 24 байта, сломается
```

**С pImpl:** `sizeof(Widget) == sizeof(unique_ptr)` == размер указателя, **всегда**. Что бы ни добавляли в `Impl` — размер `Widget` не меняется → ABI стабилен.

Критично для **библиотек с бинарным распространением** (.so/.dll): можно обновлять реализацию, не заставляя клиентов пересобираться. Так устроены Qt (`Q_DECLARE_PRIVATE`), многие коммерческие SDK.

## Критическая тонкость: деструктор

**Самая частая ошибка pImpl.** Деструктор `unique_ptr<Impl>` вызывает `delete` на `Impl` → требует **полного** типа `Impl`. Но в заголовке `Impl` неполный!

```cpp
// widget.h
class Widget {
    class Impl;
    std::unique_ptr<Impl> pImpl_;
    // деструктор НЕ объявлен → компилятор генерирует НЕЯВНЫЙ в заголовке
};

// использование:
Widget w;   // ⚠️ ОШИБКА КОМПИЛЯЦИИ: неявный ~Widget() пытается удалить Impl,
            //    но Impl здесь НЕПОЛНЫЙ → "invalid application of sizeof to incomplete type"
```

`unique_ptr` использует `default_delete`, который делает `static_assert(sizeof(T) > 0)` — а для неполного типа `sizeof` невозможен.

**Решение: объявить деструктор в заголовке, определить в .cpp:**

```cpp
// widget.h
class Widget {
public:
    Widget();
    ~Widget();               // ✅ ОБЪЯВЛЕН (не определён)
    // ...
private:
    class Impl;
    std::unique_ptr<Impl> pImpl_;
};

// widget.cpp
Widget::~Widget() = default;   // ✅ определён ЗДЕСЬ, где Impl ПОЛНЫЙ
```

Ключевое: `~Widget() = default;` должен быть в `.cpp`, **после** полного определения `Impl`. Тогда `delete Impl` компилируется.

**То же касается move-операций** (они тоже могут вызвать деструктор Impl):

```cpp
// widget.h
Widget(Widget&&) noexcept;              // объявить
Widget& operator=(Widget&&) noexcept;

// widget.cpp — определить, где Impl полный
Widget::Widget(Widget&&) noexcept = default;
Widget& Widget::operator=(Widget&&) noexcept = default;
```

Это связано с правилом Rule of Five (мы разбирали): объявив деструктор, ты подавил генерацию move → нужно объявить их явно, иначе `Widget` станет только-копируемым (а точнее — не move-абельным).

## Полный корректный шаблон

```cpp
// widget.h
#include <memory>

class Widget {
public:
    Widget();
    ~Widget();                                    // объявлен
    Widget(Widget&&) noexcept;                    // move-ctor
    Widget& operator=(Widget&&) noexcept;         // move-assign
    Widget(const Widget&);                        // copy (если нужно — см. ниже)
    Widget& operator=(const Widget&);

    void doSomething();
    int getValue() const;

private:
    struct Impl;                                  // forward declaration
    std::unique_ptr<Impl> pImpl_;
};
```

```cpp
// widget.cpp
#include "widget.h"
#include <vector>
#include <string>

struct Widget::Impl {
    std::vector<int> data_;
    std::string name_;
    int value_ = 0;

    void doSomethingImpl() { value_ += 1; }
};

Widget::Widget() : pImpl_(std::make_unique<Impl>()) {}
Widget::~Widget() = default;
Widget::Widget(Widget&&) noexcept = default;
Widget& Widget::operator=(Widget&&) noexcept = default;

// copy — нужен РУЧНОЙ (unique_ptr некопируем → глубокое копирование Impl):
Widget::Widget(const Widget& other)
    : pImpl_(std::make_unique<Impl>(*other.pImpl_)) {}   // ✅ копируем содержимое Impl

Widget& Widget::operator=(const Widget& other) {
    if (this != &other) {
        *pImpl_ = *other.pImpl_;                          // ✅ копируем содержимое
    }
    return *this;
}

void Widget::doSomething() { pImpl_->doSomethingImpl(); }
int Widget::getValue() const { return pImpl_->value_; }
```

Важный момент про copy: `unique_ptr` некопируем, поэтому дефолтный copy-конструктор `Widget` был бы удалён. Если нужна копируемость — реализуй **глубокое копирование** `Impl` вручную (как выше). Если копирование не нужно — `= delete` или просто оставь move-only.

## Стоимость pImpl

Ничего не бесплатно. Минусы:

### 1. Дополнительная аллокация

```cpp
Widget w;   // make_unique<Impl> → аллокация в куче
```

Каждый объект `Widget` требует **отдельной heap-аллокации** для `Impl`. Для часто создаваемых мелких объектов — заметный оверхед.

### 2. Косвенность при каждом доступе

```cpp
int Widget::getValue() const { return pImpl_->value_; }
//                                    ^^^^^^ разыменование указателя — доп. обращение к памяти
```

Каждый доступ к члену — через указатель → лишний indirection, хуже кэш-локальность, **невозможность инлайнинга** (методы в .cpp, компилятор не видит их при использовании).

### 3. Больше кода — boilerplate

Объявить/определить деструктор, move, (возможно) copy — руками. Каждый метод — «прокладка», делегирующая в `Impl`.

### Когда НЕ использовать

- **Горячий код**, где важна производительность (индирекция + отсутствие инлайнинга)
- **Мелкие value-типы**, создаваемые массово (аллокация на каждый)
- **Header-only библиотеки** (pImpl требует .cpp)
- Простые классы, где перекомпиляция не проблема

pImpl — это **размен производительности на скорость компиляции и стабильность ABI**. Оправдан для крупных, редко создаваемых объектов на границах модулей/библиотек.

## pImpl vs абстрактный интерфейс (виртуальные функции)

Оба скрывают реализацию, но по-разному:

| |pImpl|Абстрактный базовый класс|
|---|---|---|
|Механизм|указатель на Impl|vtable + наследование|
|Сокрытие реализации|✅|✅|
|Стабильный ABI|✅|✅ (если не менять интерфейс)|
|Compilation firewall|✅|✅|
|Value-семантика|✅ (объект по значению)|❌ (всегда через указатель на базу)|
|Полиморфизм|❌|✅ (разные реализации)|
|Оверхед|аллокация + indirection|vtable + indirection + аллокация|
|Расширяемость извне|❌ (закрытая)|✅ (новые наследники)|

**Выбор:**

- Нужна **одна** скрытая реализация + value-семантика → **pImpl**
- Нужен **полиморфизм** (несколько реализаций, расширение) → **абстрактный интерфейс**

pImpl не даёт полиморфизма — это его отличие от «интерфейса». Он про инкапсуляцию **одной** реализации, а не про выбор из многих.

---

## Реальные примеры

- **Qt** — тотально использует pImpl (`Q_D`, `Q_DECLARE_PRIVATE`) ради ABI-стабильности между версиями Qt5.x
- **std::pmr, std::filesystem** — местами
- Многие коммерческие C++ SDK, распространяемые как .so/.dll

## Формулировки на собеседовании

**«Что такое pImpl и зачем?»** — Идиома: приватные члены прячутся за указателем на неполный тип `Impl`, определённый в `.cpp`. Даёт три вещи: (1) **compilation firewall** — изменение реализации не требует пересборки клиентов; (2) сокрытие зависимостей из заголовка; (3) **стабильный ABI** — `sizeof` класса не меняется при изменении реализации.

**«Главная ловушка pImpl?»** — Деструктор. `unique_ptr<Impl>` требует **полного** `Impl` для `delete`, но в заголовке он неполный. Решение: **объявить** деструктор в заголовке, **определить** (`= default`) в `.cpp`, где `Impl` полный. То же для move-операций.

**«Почему нужно объявлять move явно?»** — Объявление деструктора подавляет генерацию move (Rule of Five); без явного объявления класс станет не-move-абельным.

**«Как копировать pImpl-класс?»** — `unique_ptr` некопируем → дефолтный copy удалён. Нужно **глубокое копирование** `Impl` вручную: `make_unique<Impl>(*other.pImpl_)`.

**«Стоимость pImpl?»** — Дополнительная heap-аллокация на объект, косвенность при каждом доступе, невозможность инлайнинга, boilerplate. Размен производительности на скорость компиляции и ABI-стабильность.

**«pImpl vs абстрактный интерфейс?»** — pImpl скрывает **одну** реализацию, сохраняет value-семантику, без полиморфизма. Абстрактный интерфейс даёт **полиморфизм** (много реализаций, расширение извне), но требует работы через указатель на базу. Выбор по тому, нужен ли полиморфизм.

---

Отличие от Java: там проблемы, которые решает pImpl, **в основном не существуют**. (1) **Compilation firewall** — в Java изменение приватного поля не требует пересборки зависимых классов (компиляция по классам, приватные члены не «протекают» в клиентский байткод так, как в C++ заголовки). (2) **ABI-стабильность** — JVM линкует классы динамически по именам полей/методов, а не по смещениям/размерам, поэтому добавление приватного поля бинарно совместимо. (3) Разделения «заголовок/реализация» в Java нет вообще — один `.java` файл. То есть pImpl — это решение **C++-специфичных** проблем (модель компиляции с заголовками, ABI по layout), которых в Java нет by design. Ближайшая аналогия в Java — программирование к интерфейсу (`List` вместо `ArrayList`), но это про полиморфизм/абстракцию, а не про compilation firewall или ABI. Для тебя как для человека с большим монолитом это важный практический инструмент: pImpl — один из немногих способов в C++ **разорвать зависимости компиляции** и ускорить пересборку, чего в Java достигается самой моделью языка.
