## Search in Rotated Sorted Array

**Условие:** дан массив `nums`, изначально отсортированный по возрастанию, но затем "повёрнутый" (rotated) на неизвестное количество позиций относительно некоторого pivot (например, `[0,1,2,4,5,6,7]` → `[4,5,6,7,0,1,2]`). Все значения уникальны. Найти индекс `target` за **O(log n)**. Если элемента нет — вернуть -1.

### Идея

Массив уже не полностью отсортирован, поэтому наивно применить обычный бинарный поиск нельзя. Но ключевое наблюдение: **хотя бы одна из двух половин относительно `mid` всегда остаётся отсортированной** (целиком по возрастанию), даже если весь массив в целом — нет. Значит на каждом шаге:

1. Определяем, какая половина (левая `[left, mid]` или правая `[mid, right]`) отсортирована — сравнивая `nums[left]` с `nums[mid]`.
2. Проверяем, попадает ли `target` в диапазон значений этой отсортированной половины.
3. Если попадает — сужаем поиск до неё (это гарантированно как в обычном бинарном поиске). Если нет — значит `target` (если существует) находится в другой половине, сужаем поиск туда.

### Решение

```cpp
#include "search_rotated_sorted.h"  
  
#include <vector>  
#include <iostream>  
#include <format>  
  
namespace search_rotated_sorted {  
  
int search(const std::vector<int>& nums, const int target) {  
    int left{};  
    int right{static_cast<int>(nums.size()) - 1};  
  
    while (left <= right) {  
        const int mid{left + (right - left) / 2};  
  
        if (nums[mid] == target) return mid;  
  
        if (nums[left] <= nums[mid]) {  
            // левая половина [left, mid] отсортирована  
            if (nums[left] <= target && target < nums[mid]) {  
                right = mid - 1;  
            } else {  
                left = mid + 1;  
            }        
        } else {  
            // правая половина [mid, right] отсортирована  
            if (nums[mid] < target && target <= nums[right]) {  
                left = mid + 1;  
            } else {  
                right = mid - 1;  
            }        
        }    
    }
    return BAD_RESULT;  
}  
  
void demo() {  
    constexpr int BAD_TARGET{3};  
    constexpr int GOOD_TARGET{0};  
    const std::vector<int> NUMS{4,5,6,7,0,1,2};  
  
    std::cout << std::format("target: {} => {}\n", BAD_TARGET, search(NUMS, BAD_TARGET));  
    std::cout << std::format("target: {} => {}\n", GOOD_TARGET, search(NUMS, GOOD_TARGET));  
}  
  
}
```

### Разбор

- `nums[left] <= nums[mid]` — если это верно, значит на отрезке `[left, mid]` нет "разрыва" (точки поворота), то есть эта половина точно отсортирована по возрастанию целиком. Если неверно (`nums[left] > nums[mid]`) — значит точка поворота находится где-то внутри `[left, mid]`, а вот `[mid, right]` гарантированно отсортирована.
- Внутри "отсортированной" половины можно применить обычную логику бинарного поиска: `nums[left] <= target < nums[mid]` — проверка, что `target` попадает в диапазон значений этой половины (границы включительно/исключительно подобраны, чтобы не задваивать `mid`, который уже проверен отдельно выше).
- Если `target` не попадает в диапазон отсортированной половины — он гарантированно (если вообще существует в массиве) находится в **другой**, "разорванной" половине, туда и сужаем поиск.
- Условие `nums[mid] == target` проверяется в начале каждой итерации отдельно — избавляет от необходимости включать `mid` в один из диапазонов дважды.

```
  nums[4]=0 <= nums[5]=1 -> левая половина [4,5] отсортирована

Результат: 4
```

```
  mid=3, nums[3]=7 != 3
  nums[0]=4<=nums[3]=7 -> левая отсортирована
  target=3 в [4,7)? нет -> left=4
```

### Сложность

- Время: **O(log n)** — каждая итерация отбрасывает половину диапазона, несмотря на дополнительную логику определения "какая половина отсортирована".
- Память: **O(1)**.

### Частые вариации

- **Search in Rotated Sorted Array II** — массив может содержать **дубликаты**. Это ломает однозначность определения "какая половина отсортирована" в случае `nums[left] == nums[mid] == nums[right]` — приходится добавлять fallback: если не можем определить сторону, просто сужаем диапазон на 1 с обеих сторон (`++left; --right;`), что в худшем случае (все элементы одинаковы) деградирует до **O(n)**.
- **Find Minimum in Rotated Sorted Array** — по сути частный случай той же техники: ищем саму точку поворота, сравнивая `nums[mid]` с `nums[right]` (не с `nums[left]`, чтобы корректно обрабатывать граничные случаи из двух элементов).
- **Find Minimum in Rotated Sorted Array II** — тот же случай с дубликатами и аналогичной деградацией до O(n) в худшем случае.

### Частый доп. вопрос: "почему сравнение именно с `nums[left]`, а не `nums[right]`?"

Можно использовать любую из двух опорных точек (`nums[left]` или `nums[right]`) для определения, какая половина отсортирована — логика будет симметричной, просто с другими неравенствами. Важно лишь быть последовательным: если сравниваете с `nums[left]`, то и диапазон значений для "попадает ли target" проверяйте относительно этой же половины (`[nums[left], nums[mid])`), не смешивая половины местами — это частая причина off-by-one ошибок в этой задаче.
