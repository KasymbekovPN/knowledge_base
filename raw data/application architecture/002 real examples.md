**Qt event loop (QEventLoop, сигналы/слоты)** В основе — `QAbstractEventDispatcher`, который на разных платформах оборачивает нативный механизм ОС (на Linux — тот же select/poll/epoll на уровне glib или своего диспетчера, на Windows — GetMessage/PeekMessage из Win32, на macOS — CFRunLoop). `QEventLoop::exec()` — это, по сути, `while(true) { ждать событие; забрать; отправить получателю через QObject::event(); }`. События — это не только пользовательский ввод (`QMouseEvent`, `QKeyEvent`), но и внутренний механизм отправки сигналов между потоками.

Важный нюанс: сигналы/слоты в Qt бывают двух типов соединения. `DirectConnection` — слот вызывается синхронно, сразу же, как обычный вызов функции, без участия event loop. `QueuedConnection` (используется автоматически, когда отправитель и получатель живут в разных потоках) — вызов слота на самом деле упаковывается в `QMetaCallEvent` и кладётся в очередь событий потока-получателя; выполнится он только тогда, когда event loop того потока дойдёт до этого события. Это и есть механизм межпоточного взаимодействия в Qt без ручных мьютексов — de facto message passing поверх event loop, а не общая память с блокировками. `QTimer`, сетевые сокеты (`QTcpSocket`) и таймеры интеграции с ОС тоже реализованы как источники событий, которые диспетчер добавляет в тот же цикл.

**boost::asio::io_context** `io_context` — это сам event loop/reactor (на Linux использует epoll внутри, на Windows — IOCP, то есть демонстрирует именно то различие reactor/proactor, о котором говорили раньше — API единый, реализация под капотом разная). Модель работы: вы вызываете асинхронную операцию (`async_read`, `async_write`, `async_accept`, таймер `async_wait`) и передаёте completion handler — callback, лямбду или корутину. Сам вызов `async_*` не блокирует, он просто регистрирует операцию. Реальная работа происходит внутри `io_context::run()` — это и есть точка входа в цикл: поток крутится там, ждёт готовности/завершения операций и вызывает соответствующие handler'ы.

`strand` решает конкретную проблему: если `io_context::run()` вызван из нескольких потоков одновременно (частый паттерн для утилизации нескольких ядер — thread pool, все крутящий один и тот же `io_context`), то два handler'а могут выполниться параллельно и одновременно трогать одни и те же данные — гонка. `strand` — это обёртка, гарантирующая, что все handler'ы, привязанные к одному strand, никогда не выполнятся одновременно, даже если работают несколько потоков — по сути, сериализация доступа без явного мьютекса. Это даёт возможность одновременно иметь многопоточный `io_context` (для throughput) и однопоточную логику для конкретного соединения (для безопасности), не расставляя блокировки руками.

**libuv** То, что физически исполняет Node.js под капотом. Архитектура: единый event loop поток плюс отдельный thread pool (по умолчанию 4 потока) для операций, которые ОС не умеет делать асинхронно нативно — в первую очередь файловый I/O (на большинстве ОС нет полноценного асинхронного API для файлов, поэтому libuv эмулирует асинхронность, отправляя блокирующий вызов в поток из пула) и некоторые DNS-резолвы. Сетевые операции (TCP/UDP) в libuv настоящие асинхронные — построены поверх epoll на Linux, kqueue на macOS/BSD, IOCP на Windows — то есть опять тот же паттерн reactor/proactor под разным API в зависимости от платформы.

Сам цикл libuv на каждой итерации проходит через фиксированные фазы: сначала истёкшие таймеры, затем "pending callbacks" (некоторые системные обратные вызовы), затем poll for I/O (тут он блокируется на epoll_wait/kqueue с вычисленным таймаутом до ближайшего таймера — то есть поток не крутится вхолостую, а спит, если делать нечего), затем `check` (это фаза `setImmediate` в Node.js), затем закрытие handle'ов. Именно этот порядок фаз объясняет многие "странности" Node.js вроде разницы между `setTimeout(fn, 0)` и `setImmediate(fn)`.

**Game loop: fixed timestep vs variable** Это не про I/O-события, а про то, как часто и с каким шагом обновлять состояние игры (физика, логика) относительно отрисовки кадров — по сути свой вид "event loop", где основное периодическое событие — это тик кадра.

Variable timestep — обновление логики происходит с реальным прошедшим временем между кадрами (`deltaTime = now - lastFrameTime`), то есть если кадр отрисовался за 20 мс, а следующий за 30 мс — физика проматывается на реальное количество миллисекунд. Просто в реализации, но опасно для детерминизма и стабильности: при просадке FPS (лаге) большой `deltaTime` может "телепортировать" объект сквозь стену за один шаг физики (tunneling), а сама симуляция становится невоспроизводимой — одна и та же партия при разном FPS играется по-разному.

Fixed timestep — логика/физика обновляется строго фиксированными шагами (например, ровно 16.67 мс на шаг, то есть 60 обновлений в секунду), независимо от частоты кадров отрисовки. Реализуется через "аккумулятор": на каждой итерации game loop к аккумулятору добавляется реально прошедшее время, а затем в цикле `while (accumulator >= fixedStep) { updatePhysics(fixedStep); accumulator -= fixedStep; }` выполняется столько шагов физики, сколько накопилось. Отрисовка при этом происходит с той частотой, с какой успевает GPU, а между двумя последними шагами физики для сглаживания часто используют интерполяцию (`render(state, accumulator / fixedStep)`). Это классический паттерн Гленна Фидлера "Fix Your Timestep!" — даёт детерминированную, воспроизводимую физику независимо от производительности железа, но требует чуть больше кода (разделение update/render, интерполяция).

Общая нить через все четыре примера: везде event loop — это диспетчер, который либо ждёт готовности (reactor: epoll/select), либо получает уведомление о завершении (proactor: IOCP), либо просто тикает с фиксированной частотой (game loop) — а вся пользовательская логика вешается на это как обработчики/callback'и, не блокируя сам цикл.
