## Базовый синтаксис

```powershell
docker build -t name:tag .
```

- `-t` (tag) — имя и тег итогового образа. Можно указать несколько раз, чтобы сразу присвоить образу несколько тегов
- `.` — **build context**: путь к директории, содержимое которой будет отправлено демону

## Что такое build context и почему это важно

Это ключевой момент, который часто путает новичков. Команда `docker build -t name .` не просто говорит "собери по этому Dockerfile" — она **сжимает и отправляет демону всю директорию** (`.`), которую ты указал. Именно поэтому в твоих командах путь выглядел так:

```powershell
docker build -t practice:1.0 "C:/projects/.../003 images and containers"
```

Ты явно указал контекст — эту папку целиком отправило демону, а `COPY . .` внутри Dockerfile копирует уже из этого переданного контекста, а не напрямую с диска хоста.

**Практическое следствие:** если в этой папке случайно окажется папка `node_modules` на 500 МБ или `.git` с историей — весь этот объём будет упакован и отправлен демону **при каждой сборке**, даже если ничего из этого не используется в образе. Отсюда важность `.dockerignore`.

## `.dockerignore`

Работает как `.gitignore`, лежит рядом с Dockerfile:

```
.git
node_modules
*.log
.env
Dockerfile
```

Файлы отсюда вообще не попадают в build context — не отправляются демону, соответственно не могут случайно попасть в образ через `COPY . .`, и не участвуют в инвалидации кэша.

## Указать Dockerfile с другим именем/расположением

```powershell
docker build -f Dockerfile.prod -t myapp:prod .
```

Полезно, когда у тебя несколько Dockerfile для разных окружений (`Dockerfile.dev`, `Dockerfile.prod`).

## Build arguments — передать переменные во время сборки

В отличие от `ENV` (переменные окружения контейнера), `ARG` доступен только **во время сборки**:

```dockerfile
ARG NODE_VERSION=20
FROM node:${NODE_VERSION}
```

```powershell
docker build --build-arg NODE_VERSION=18 -t myapp .
```

## Управление кэшем

```powershell
docker build --no-cache -t myapp .
```

Полностью игнорирует кэш, пересобирает всё с нуля — полезно, если подозреваешь, что кэш "врёт" (например, после смены версии пакета без изменения `package.json`, что бывает редко, но случается).

```powershell
docker build --progress=plain -t myapp .
```

Показывает полный вывод каждого шага сборки без сворачивания — удобно для отладки, когда `RUN` падает и нужно видеть весь лог, а не обрезанный.

## BuildKit

С 2023+ Docker по умолчанию использует **BuildKit** — новый движок сборки (в твоём выводе он виден как `docker:desktop-linux` и параллельные шаги `[1/2]`, `[2/2]`). Он умеет:

- Параллелить независимые слои (например, в multi-stage build этапы, не зависящие друг от друга, собираются одновременно)
- Кэшировать точечно, монтируя кэш-директории между сборками (`--mount=type=cache`) — актуально для C++/CMake, чтобы не пересобирать всё с нуля каждый раз даже при `--no-cache` на уровне слоя
- Пропускать неиспользуемые этапы в multi-stage build

## Практический разбор твоего вывода

Возвращаясь к твоей более ранней сборке:

```
=> [internal] load build definition from Dockerfile     0.0s
=> [internal] load metadata for docker.io/library/alpine:3.20   0.1s
=> [internal] load .dockerignore     0.0s
=> [1/2] FROM docker.io/library/alpine:3.20@sha256:...   0.1s
=> [2/2] WORKDIR /app   0.0s
=> exporting to image   0.3s
```

Это ровно те шаги со схемы выше: чтение Dockerfile → загрузка контекста (у тебя он был почти пустой, отсюда `2B`) → выполнение инструкций `[1/2]`, `[2/2]` → `exporting to image` — финальная сборка слоёв в готовый образ с тегом.

## Этап 3. Volumes и работа с данными

**Темы:**

- Файловая система контейнера (эфемерность)
- Bind mounts vs named volumes
- `docker volume create`, `docker volume ls`
- Монтирование через `-v` и `--mount`

**Практика:**

- Запустить контейнер с базой данных (например, PostgreSQL) и сохранить данные в volume
- Смонтировать локальную папку с исходниками внутрь контейнера для разработки

**Цель:** понимать, как данные переживают перезапуск контейнера.

## Этап 4. Сети (networking)

**Темы:**

- Типы сетей: bridge, host, none
- Проброс портов (`-p`)
- Связь между контейнерами по имени (user-defined bridge network)
- `docker network create/ls/inspect`

**Практика:**

- Поднять два контейнера (например, приложение + база данных) и связать их через общую сеть

**Цель:** уметь настраивать взаимодействие между несколькими контейнерами.

## Этап 5. Многоэтапная сборка (multi-stage builds)

**Темы:**

- Проблема больших образов
- Multi-stage build: сборка в одном образе, запуск в другом
- Актуально для C++/CMake — компилятор и зависимости не должны попадать в финальный образ

**Практика:**

- Переписать Dockerfile из Этапа 2 в multi-stage вариант: этап сборки (с CMake, компилятором) → этап запуска (минимальный образ только с бинарником)
- Сравнить размер образов до/после

**Цель:** уметь собирать компактные production-образы.

## Этап 6. Docker Compose

**Темы:**

- Зачем нужен Compose (оркестрация нескольких контейнеров)
- Синтаксис `docker-compose.yml`: `services`, `volumes`, `networks`, `depends_on`
- Команды: `up`, `down`, `logs`, `build`

**Практика:**

- Собрать `docker-compose.yml` для связки: C++ приложение + PostgreSQL + (опционально) сервис кэша
- Поднять весь стек одной командой

**Цель:** уметь описывать и запускать многосервисные приложения декларативно.
