# Уменьшение количества слоёв

Мы уже частично разбирали эту тему на Этапе 2, когда говорили про кэширование (`RUN apt-get update && apt-get install...` одной строкой). Сейчас соберём это в единый набор практик — почему количество слоёв вообще имеет значение и как его минимизировать.

## Почему слоёв должно быть меньше

Каждый `RUN`, `COPY`, `ADD` создаёт отдельный слой — неизменяемую дельту поверх предыдущего состояния файловой системы. Проблема в том, что **слои не "сжимаются" автоматически**: если ты что-то создал в одном слое, а удалил в следующем — место на диске всё равно занято, потому что предыдущий слой физически хранится с этим файлом внутри, просто следующий слой "маскирует" его как удалённый.

```dockerfile
# Плохо — 3 слоя, промежуточный файл занимает место НАВСЕГДА
RUN wget https://example.com/big-archive.tar.gz
RUN tar -xzf big-archive.tar.gz
RUN rm big-archive.tar.gz
```

Даже после `rm`, архив `big-archive.tar.gz` физически остаётся в слое 1 — образ весит так, будто архив всё ещё там, просто он невидим в итоговой файловой системе.

**Правильно — всё в одном слое:**

```dockerfile
RUN wget https://example.com/big-archive.tar.gz && \
    tar -xzf big-archive.tar.gz && \
    rm big-archive.tar.gz
```

Теперь скачивание, распаковка и удаление происходят внутри **одной** RUN-инструкции — итоговый слой содержит только распакованные файлы, архив никогда не фиксируется как часть истории образа.

## Практика объединения `RUN`

```dockerfile
# Плохо: 4 отдельных слоя
RUN apk update
RUN apk add build-base
RUN apk add cmake
RUN apk add boost-dev

# Хорошо: 1 слой
RUN apk add --no-cache build-base cmake boost-dev
```

Заметь: `apk add --no-cache` даже не требует отдельного `apk update` — флаг `--no-cache` сам обновляет индекс и сразу же не сохраняет его на диске (это alpine-специфичная оптимизация, у Debian/Ubuntu аналог — явный `rm -rf /var/lib/apt/lists/*` в той же RUN-строке).

## `COPY` — тоже можно объединять

```dockerfile
# Не критично, но лишний слой
COPY CMakeLists.txt .
COPY main.cpp .

# Эквивалентно, один слой
COPY CMakeLists.txt main.cpp ./
```

Для двух файлов разница ничтожна, но если у тебя десятки отдельных `COPY` для разных файлов конфигурации — стоит сводить их к одной инструкции, где это осмысленно (с оговоркой про кэш — см. ниже).

## Важный нюанс — не переусердствуй с объединением

Объединение слоёв **противоречит** кэшированию, которое мы разбирали раньше, если делать это бездумно:

```dockerfile
# Один слой, но кэш ломается целиком при ЛЮБОМ изменении
RUN apk add --no-cache build-base cmake boost-dev && \
    cmake -B build -S . && \
    cmake --build build
```

Если тут `cmake --build build` зависит от исходников, которые меняются часто — весь этот один слой пересобирается каждый раз, включая переустановку `build-base`/`cmake`/`boost-dev`, которые на самом деле не менялись. **Правильный баланс — объединять то, что логически связано и меняется вместе, но НЕ объединять то, что имеет разную частоту изменений** (это тот же принцип, что мы разбирали для кэша: стабильное — отдельно от часто меняющегося).

```dockerfile
# Хороший баланс
RUN apk add --no-cache build-base cmake boost-dev   # редко меняется — свой слой
COPY CMakeLists.txt main.cpp ./
RUN cmake -B build -S . && cmake --build build       # часто меняется — свой слой
```

## Multi-stage — самый мощный инструмент для этой задачи

Мы это уже разбирали подробно (Этап 5), но стоит явно связать с текущей темой: multi-stage — это не только про размер, но и про **количество слоёв в финальном образе**. Даже если в `builder`-стадии слоёв много и они "грязные" (компилятор, промежуточные файлы) — в финальный образ попадает только результат `COPY --from`, обычно 2-4 слоя (база + рантайм-зависимости + бинарник).

## Инструмент для проверки — `docker history`

```powershell
docker history consumer:1.0
```

Покажет **каждый слой** образа с его размером — отличный способ найти, где именно "раздувается" образ:

```
IMAGE          CREATED BY                                      SIZE
a1b2c3d4e5f6   CMD ["./consumer"]                               0B
f6e5d4c3b2a1   COPY /src/build/consumer .                       2.1MB
9a8b7c6d5e4f   RUN apk add --no-cache libstdc++ boost-system    18MB
...
```

Если увидишь неожиданно большой слой — это сигнал разобраться, что именно он тащит, и не стоит ли переструктурировать Dockerfile.

## Практика на нашем проекте

Проверь текущий `consumer`:

```powershell
docker history consumer:3.0 --no-trunc
```

Обрати внимание, сколько слоёв в builder-стадии (их может быть много) против того, сколько реально попадает в **финальный** образ — именно последний нас должен волновать, потому что только он попадает в prod и именно его пуллят/пушат.
