## Образ (image)

Образ — это **неизменяемый шаблон**: файловая система + метаданные (какую команду запускать, какие переменные окружения, какие порты открывать). Внутри он состоит из **слоёв** — каждая инструкция в Dockerfile (`RUN`, `COPY` и т.д.) создаёт новый слой поверх предыдущего. Слои read-only и переиспользуются: если два образа основаны на одном `FROM ubuntu:22.04`, этот базовый слой физически хранится один раз на диске.

Образ сам по себе **ничего не выполняет** — это просто данные на диске, как ISO-файл или установочный пакет.

## Контейнер (container)

Контейнер — это **запущенный экземпляр** образа. Когда ты делаешь `docker run image_name`, Docker:

1. Берёт read-only слои образа
2. Добавляет сверху тонкий **writable-слой** (thin write layer) — именно в него пишутся все изменения: новые файлы, изменённые конфиги, логи
3. Запускает процесс

Отсюда ключевое следствие, которое хорошо видно на схеме: **один образ → сколько угодно независимых контейнеров**. Каждый контейнер получает свою собственную writable-прослойку, поэтому изменения в одном контейнере не затрагивают ни образ, ни другие контейнеры, запущенные из того же образа.

## Практическая аналогия

Если тебе ближе термины из ООП: **образ — это класс, контейнер — это объект (экземпляр класса)**. Можно создать множество объектов из одного класса, и они не будут друг на друга влиять.

## Ещё пара важных фактов

- Удаление контейнера **не удаляет** образ — образ остаётся, из него можно запустить новый контейнер
- Если контейнер остановлен (`docker stop`), его writable-слой сохраняется — можно запустить его снова (`docker start`) и данные будут на месте
- Если контейнер удалён (`docker rm`) — writable-слой теряется безвозвратно (если данные не были вынесены в volume — но это тема следующего этапа)


# Практика: образ vs контейнер живьём

## Шаг 1 — простой образ

```dockerfile
FROM alpine:3.20  
  
# Рабочая директория внутри контейнера  
WORKDIR /app  
  
# При старте контейнера просто открываем shell  
CMD ["sh"]
```

Собери образ:

```powershell
docker build -t practice:1.0 .
```

## Шаг 2 — запускаем ДВА контейнера из ОДНОГО образа

Открой два окна терминала (или запускай по очереди — не важно).

**Терминал 1:**

```powershell
docker run -it --name c1 practice:1.0
```

Ты попадёшь внутрь контейнера. Создай там файл:

```sh
echo "Я контейнер номер 1" > /app/note.txt
cat /app/note.txt
```

Не закрывай терминал, просто сверни (или открой второй терминал отдельно).

**Терминал 2:**

```powershell
docker run -it --name c2 practice:1.0
```

Ты снова внутри контейнера — но это **другой** экземпляр. Проверь:

```sh
cat /app/note.txt
```

Файла нет — потому что контейнер `c2` получил свою собственную writable-прослойку поверх того же образа, независимую от `c1`. Создай там свой файл:

```sh
echo "Я контейнер номер 2" > /app/note.txt
cat /app/note.txt
```

Выйди из обоих контейнеров командой `exit`.

## Шаг 3 — доказываем независимость

```powershell
docker ps -a
```

Увидишь оба контейнера `c1` и `c2` в статусе `Exited`. Запусти их заново и проверь файлы:

```powershell
docker start c1
docker exec c1 cat /app/note.txt
```

→ `Я контейнер номер 1`

```powershell
docker start c2
docker exec c2 cat /app/note.txt
```

→ `Я контейнер номер 2`

Файлы сохранились после остановки — потому что writable-слой контейнера никуда не делся, пока контейнер существует.

## Шаг 4 — доказываем, что образ не тронут

Запусти **третий**, свежий контейнер из того же образа:

```powershell
docker run -it --rm practice:1.0 cat /app/note.txt
```

Файла `/app/note.txt` там нет — потому что образ `practice:1.0` как был read-only шаблоном, так и остался. Всё, что мы писали в `c1` и `c2`, осталось только в их собственных writable-слоях.

(Флаг `--rm` тут удобен: контейнер удалится сразу после выполнения команды, не засоряя список.)

## Шаг 5 — необратимость удаления

```powershell
docker rm -f c1
docker rm -f c2
```

Теперь их writable-слои удалены безвозвратно. Если бы там были важные данные — они бы пропали. Это ровно та проблема, для решения которой в следующем этапе мы разберём **volumes**: способ хранить данные отдельно от writable-слоя контейнера, чтобы они переживали `docker rm`.

**Что должно было стать очевидным на практике:**

- Образ — общий read-only фундамент, из него можно наштамповать сколько угодно контейнеров
- Каждый контейнер изолирован от других своим writable-слоем
- Контейнер можно останавливать/запускать без потери данных, но `rm` данные стирает
