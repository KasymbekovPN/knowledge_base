## `alpine` — минимальный размер

Мы уже разбирали его подробно: musl libc, BusyBox, `apk`. Самый маленький вариант.

**Плюсы:** минимальный размер, минимальная поверхность атаки, быстрая загрузка/пересборка. **Минусы:** musl вместо glibc — риск несовместимости с бинарниками, скомпилированными под glibc; меньше готовых пакетов в репозитории, чем в Debian/Ubuntu; иногда сложнее найти готовые инструкции для специфичных библиотек (community чаще пишет под Debian/Ubuntu).

## `debian-slim` — компромисс

Урезанная версия обычного Debian — убраны документация, man-страницы, некоторые локали, но **glibc остаётся полноценным**.

```dockerfile
FROM debian:12-slim
RUN apt-get update && apt-get install -y --no-install-recommends libboost-system1.74.0 && \
    rm -rf /var/lib/apt/lists/*
```

**Плюсы:** совместимость glibc "из коробки" — то, с чем компилируется большинство C++ библиотек и prebuilt-пакетов по умолчанию; `apt` с огромным репозиторием пакетов; хорошая документация под Debian почти для всего. **Минусы:** заметно больше alpine (~80 МБ базово, до установки твоих зависимостей).

## `debian`/`ubuntu` (full) — максимальная совместимость

Полноценный дистрибутив с документацией, локалями, дополнительными утилитами предустановленными.

**Когда оправдано:** нужны системные утилиты, которых нет в slim/alpine (например, локали для конкретного языка, дополнительные codec'и, инструменты отладки прямо в образе); или это временный образ для разработки/CI, где размер не критичен, а удобство работы важнее.

## Как это соотносится с твоей проблемой musl/glibc

Мы уже сталкивались с последствиями выбора alpine — ошибка `Error loading shared library libstdc++.so.6`. Более глубокая версия той же проблемы: если у тебя есть **prebuilt** C++/Boost библиотека (не собранная тобой из исходников на alpine, а, скажем, скачанная как готовый `.so` из vcpkg-кэша, собранного под glibc) — на alpine она **вообще не запустится**, и апк-пакетом это не починить, потому что musl и glibc не ABI-совместимы. В этом случае `debian-slim` — единственный практичный вариант без пересборки всего из исходников под musl.

## Практическое правило выбора

|Ситуация|Рекомендация|
|---|---|
|Собираешь всё из исходников сам (как наш consumer/producer)|`alpine` — musl не проблема, раз всё компилируется в одном и том же окружении|
|Используешь готовые бинарные пакеты/библиотеки под glibc (vcpkg, conan с бинарным кэшем)|`debian-slim`|
|Нужны специфичные системные утилиты, локали, инструменты отладки|`debian`/`ubuntu` full|
|Максимальная безопасность в проде, минимальная поверхность атаки|`alpine`, при условии что нет конфликтов с glibc|

## Ещё один вариант — `distroless`

Отдельного упоминания заслуживает семейство образов `gcr.io/distroless/*` от Google — там нет вообще **ни shell'а, ни пакетного менеджера**, только рантайм-библиотеки и сам бинарник. Даже меньше поверхность атаки, чем у alpine (нельзя зайти через `docker exec sh`, потому что `sh` физически отсутствует), но и отладка сложнее — это уже продвинутая тема для по-настоящему прод-критичных образов.
