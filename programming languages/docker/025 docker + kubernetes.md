## Что такое Kubernetes концептуально

Kubernetes (K8s) — система оркестрации контейнеров: ты декларативно описываешь **желаемое состояние** ("мне нужно 3 реплики consumer, доступные через такой-то сервис"), а K8s постоянно сверяет это описание с реальностью и приводит кластер в соответствие — разворачивает, перезапускает, масштабирует, лечит упавшее.

## Control Plane — "мозг" кластера

- **API Server** — единая точка входа для всех команд (`kubectl` под капотом просто шлёт HTTP-запросы сюда). Все остальные компоненты общаются между собой тоже через него.
- **Scheduler** — решает, **на какой узел** поставить новый под, исходя из доступных ресурсов, ограничений, affinity-правил.
- **Controller Manager** — набор "контроллеров", каждый следит за своим аспектом состояния кластера (например, Deployment Controller следит, что реальное число реплик совпадает с желаемым, и если под упал — просит Scheduler создать замену).
- **etcd** — распределённое key-value хранилище, единственный источник истины о состоянии всего кластера. Если хочешь провести аналогию с тем, что уже знаешь — это отдалённо похоже на роль Docker daemon'а, который хранит метаданные о контейнерах, только распределённое между несколькими машинами и специально спроектированное для консистентности в кластере.

## Worker Node — где реально крутятся контейнеры

- **kubelet** — агент на каждом узле, получает от API Server задание "здесь должен быть под с такими-то контейнерами" и следит, чтобы это было реально исполнено
- **Container runtime** — то, что реально запускает контейнеры (сейчас чаще всего **containerd**, а не сам Docker Engine — важный нюанс ниже)
- **Pod** — минимальная разворачиваемая единица в Kubernetes. **Это не то же самое, что контейнер**

## Ключевое новое понятие — под (Pod)

Под может содержать **один или несколько** контейнеров, которые всегда живут и умирают вместе, делят один и тот же network namespace (то есть общаются друг с другом через `localhost`) и могут делить volumes. В большинстве случаев под содержит ровно один контейнер (наш `consumer` был бы одним подом с одним контейнером внутри), но иногда добавляют **sidecar**-контейнер — например, для сбора логов или проксирования трафика (service mesh вроде Istio так и работает).

## Важный нюанс, который может тебя удивить

Начиная с Kubernetes 1.24, **Docker Engine как container runtime официально не поддерживается** — Kubernetes использует **containerd** напрямую (сам Docker внутри тоже использует containerd, так что реального противоречия нет, просто убрали лишний промежуточный слой `dockershim`). Это не значит, что твои Docker-образы бесполезны для Kubernetes — наоборот, **любой образ, собранный `docker build`, прекрасно запускается в Kubernetes**, потому что формат образа (OCI — Open Container Initiative) — открытый стандарт, не завязанный конкретно на Docker Engine. Весь твой опыт с Dockerfile, multi-stage builds, слоями — напрямую переносится.

## Как выглядел бы наш `consumer` в виде Kubernetes-манифеста

Просто для ощущения формата (пока не углубляясь):

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: consumer
spec:
  replicas: 3          # три реплики вместо одного контейнера
  selector:
    matchLabels:
      app: consumer
  template:
    metadata:
      labels:
        app: consumer
    spec:
      containers:
        - name: consumer
          image: pablo/consumer:1.0
          ports:
            - containerPort: 5000
---
apiVersion: v1
kind: Service
metadata:
  name: consumer
spec:
  selector:
    app: consumer
  ports:
    - port: 5000
```

Обрати внимание на структурное сходство с `docker-compose.yml` (тот же образ, тот же порт) — но `replicas: 3` тут реально означает "распредели 3 копии по кластеру", а не "запусти 3 на этой же машине".

## Пробуем локально — `minikube` или `kind`

Для знакомства не нужен настоящий кластер из нескольких машин — есть инструменты, эмулирующие кластер локально:

```powershell
# Один из вариантов — minikube
minikube start
kubectl apply -f consumer-deployment.yaml
kubectl get pods
```
