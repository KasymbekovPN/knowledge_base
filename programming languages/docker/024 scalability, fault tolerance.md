## Ограничение №1 — один хост

Как видно на схеме: Compose управляет контейнерами **строго на одной машине**. Все сервисы, сколько бы их ни было, делят ресурсы (CPU, RAM, диск) этого единственного хоста. Если у тебя `consumer`, `producer` и `db` суммарно требуют больше, чем есть на этой машине — единственный выход в рамках Compose — взять более мощный сервер (вертикальное масштабирование). Горизонтально размазать сервисы по нескольким машинам Compose **не умеет** в принципе — у него просто нет для этого механизма.

## Ограничение №2 — отказоустойчивость

Если хост, на котором крутится Compose, упадёт (перезагрузка, авария оборудования, обновление ОС) — **упадут абсолютно все сервисы одновременно**, и никто автоматически их не поднимет на другой машине, потому что другой машины в модели Compose просто не существует. `restart: unless-stopped` спасает только от падения отдельного **процесса** внутри контейнера — не от падения самого хоста.

## Что даёт оркестратор (Kubernetes / Docker Swarm)

Правая часть схемы показывает ключевое отличие: контейнеры (в Kubernetes — точнее, **поды**) распределены по **нескольким узлам (nodes)**. Оркестратор постоянно следит за состоянием кластера, и если узел перестаёт отвечать — автоматически **пересоздаёт** упавшие контейнеры на других живых узлах, без вмешательства человека. Это называется **self-healing**.

## Что ещё Compose не умеет, а оркестратор — умеет

- **Настоящее горизонтальное масштабирование** — `docker compose up --scale producer=3` создаёт 3 копии, но все на одном хосте; Kubernetes может размазать эти 3 копии по разным физическим машинам, чтобы не зависеть от отказа одной из них
- **Rolling updates** — обновление версии сервиса без простоя: оркестратор поднимает новые версии контейнеров постепенно, проверяет их здоровье, и только потом гасит старые — ноль даунтайма для пользователей
- **Автоматическая балансировка нагрузки** между репликами одного сервиса на разных узлах
- **Service discovery на уровне кластера**, а не только внутри одной bridge-сети

## Когда Compose всё ещё достаточно

Важно не обесценивать Compose — он отлично подходит для:

- Локальной разработки (то, чем мы и занимались весь этот план)
- Небольших проектов на одном сервере, где простой на время редких перезапусков приемлем
- CI-окружений для интеграционных тестов (как в примере с GitHub Actions выше)

Переход к Kubernetes/Swarm оправдан, когда реально нужна отказоустойчивость в проде или нагрузка превышает возможности одной машины — не раньше, иначе это неоправданное усложнение архитектуры.

## Docker Swarm vs Kubernetes — коротко

**Docker Swarm** — встроен в сам Docker, синтаксис файлов очень похож на `docker-compose.yml` (фактически `docker stack deploy` использует тот же формат с небольшими дополнениями), порог входа ниже. **Kubernetes** — отраслевой стандарт, гораздо более мощный и гибкий, но и значительно сложнее в освоении и администрировании; почти весь индустриальный опыт и вакансии по оркестрации сейчас именно про Kubernetes.
