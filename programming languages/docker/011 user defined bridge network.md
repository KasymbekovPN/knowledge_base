## Проблема стандартного bridge

У дефолтного моста `bridge` (тот, что используется без явного указания сети) есть важное ограничение: **встроенный DNS не работает**. Контейнеры видят друг друга только по IP, который к тому же не гарантированно постоянный между перезапусками. Обращаться к базе данных как `172.17.0.3` — неудобно и хрупко.

## Решение — user-defined bridge

Создаёшь свою сеть явно:

```powershell
docker network create mynet
```

Подключаешь контейнеры к ней при запуске:

```powershell
docker run -d --name db --network mynet postgres:16
docker run -d --name app --network mynet my_app_image
```

Теперь внутри контейнера `app` можно обращаться к базе просто по имени:

```
db:5432
```

вместо `172.18.0.3:5432`. Docker поднимает встроенный **DNS-резолвер** внутри пользовательских сетей, который автоматически резолвит `--name` контейнера в его текущий IP. Это и есть ключевое отличие на схеме — стрелка между `app` и `db` подписана именем, а не IP.

## Почему это принципиально удобнее

- **IP может меняться** при пересоздании контейнера, а имя — нет
- **Не нужно хардкодить IP** в конфиге приложения — сразу пишешь `DATABASE_HOST=db`
- Это ровно то, что использует **Docker Compose** под капотом — когда пишешь `depends_on` и обращаешься к сервису по его имени из `docker-compose.yml`, там как раз создаётся user-defined bridge с DNS-резолвингом

## Управление сетями

```powershell
docker network create mynet          # создать
docker network ls                    # список сетей
docker network inspect mynet         # какие контейнеры подключены, их IP
docker network connect mynet c1      # подключить уже существующий контейнер
docker network disconnect mynet c1   # отключить
docker network rm mynet              # удалить (если никто не подключён)
```

## Практика — свяжем два контейнера

```powershell
docker network create mynet

docker run -d --name db --network mynet -e POSTGRES_PASSWORD=secret postgres:16

docker run -it --network mynet postgres:16 psql -h db -U postgres
```

Если всё настроено верно — `psql` подключится к базе **по имени `db`**, а не по IP, и попросит пароль (`secret`).


**Bridge-сеть (в том числе user-defined) существует строго в пределах одного Docker-хоста**. Это чисто локальный виртуальный мост на конкретной машине, у него нет механизма, который бы передавал трафик на другой физический/виртуальный хост.

## Почему это ограничение

Bridge-сеть технически — это виртуальный Linux-интерфейс (`docker0` или его user-defined аналог) плюс NAT-правила через `iptables`, которые работают строго в рамках сетевого стека одной машины. Демон на хосте А ничего не знает о демоне на хосте Б — они даже не обязаны быть в курсе существования друг друга.

## Что нужно для связи контейнеров на разных хостах

**1. Overlay network (Docker Swarm)**

Именно для этого случая существует отдельный драйвер сети — **overlay**. Он инкапсулирует трафик между хостами (обычно через VXLAN) и требует, чтобы хосты были объединены в **Docker Swarm** — встроенный в Docker кластерный режим:

```powershell
docker swarm init
docker network create --driver overlay mynet
docker service create --name db --network mynet postgres:16
```

Внутри overlay-сети точно так же работает DNS-резолвинг по имени сервиса — это прямое расширение идеи user-defined bridge, но через границы хостов.

**2. Kubernetes**

Если задача масштабнее — Kubernetes с CNI-плагином (Calico, Flannel, Cilium) решает ту же проблему на уровне пода/кластера, просто на другом уровне абстракции, не через Docker Swarm.

**3. "Наколеночные" варианты**

Просто пробросить порт на каждом хосте (`-p`) и обращаться между хостами по их обычным IP/DNS — без каких-либо Docker-специфичных сетевых механизмов, просто как к любым сетевым сервисам. Работает, но теряешь удобство DNS-резолвинга по имени контейнера.
