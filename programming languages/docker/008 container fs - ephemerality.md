## Что значит "эфемерность"

Файловая система контейнера технически называется **union filesystem** (в Docker обычно реализация **OverlayFS**). Она "склеивает" несколько слоёв в единую видимую файловую систему, но физически они разные:

- **Слои образа** (нижние) — read-only, приходят из Dockerfile, общие для всех контейнеров, запущенных из этого образа
- **Writable-слой контейнера** (верхний) — создаётся заново при каждом `docker run`, живёт ровно столько, сколько существует контейнер

Как только контейнер удаляется (`docker rm`) — верхний слой стирается безвозвратно. Всё, что там было — новые файлы, изменённые конфиги, логи, скачанные данные — пропадает без возможности восстановления.

## Copy-on-write — как это работает при изменении файла

Если процесс внутри контейнера хочет изменить файл, который лежит в одном из **read-only** слоёв (например, файл конфига из базового образа) — Docker не может изменить его на месте. Вместо этого срабатывает механизм **copy-on-write**:

1. Файл копируется из read-only слоя наверх, в writable-слой
2. Изменение применяется уже к этой копии
3. С этого момента процесс видит именно копию (она "перекрывает" оригинал за счёт union-механизма), а исходный слой образа остаётся нетронутым

Это же объясняет, почему у тебя в практике `note.txt` из `c1` не появлялся в `c2` — файл создавался прямо в writable-слое, минуя copy-on-write (создание нового файла — не изменение существующего), но принцип тот же: **писать можно только в свой собственный верхний слой**.

## Почему это важно понимать

Эфемерность — это не баг, а осознанный дизайн: контейнеры задумывались как **одноразовые, легко пересоздаваемые процессы**. Идея в том, что если контейнер сломался или устарел — его просто удаляют и запускают новый из того же образа, без раздумий о "накопленном состоянии" внутри. Это прямо противоположно подходу с виртуальными машинами, где привыкли беречь конкретный инстанс годами.

Но отсюда сразу возникает практическая проблема: **а как хранить данные, которые реально должны пережить перезапуск** — базу данных, загруженные пользователем файлы, логи для дальнейшего анализа? Именно писать их напрямую в writable-слой контейнера — плохая идея (потеряешь при `rm`, плюс это работает медленнее из-за copy-on-write при больших файлах).
