# Флаги компиляции для отладки

## `-g` и уровни отладочной информации

**`-g`** — базовый флаг, включает генерацию отладочной информации (по умолчанию эквивалентен `-g2`).

Уровни:

- **`-g1`** — минимум: только номера строк и информация о функциях (для backtrace без локальных переменных). Практически бесполезен для полноценной отладки.
- **`-g2`** (= `-g`) — стандартный уровень: локальные переменные, параметры функций, типы. Этого достаточно в 95% случаев.
- **`-g3`** — максимум: добавляет информацию о **макросах препроцессора**. Позволяет делать `info macro MY_MACRO` в GDB и видеть раскрытие макросов при отладке.

```bash
g++ -g3 -O0 main.cpp -o main
```

Практически: `-g3` стоит использовать, если у тебя много кода с макросами (например, логирование через макросы, feature-флаги через `#ifdef`). Для обычного кода `-g` (=`-g2`) достаточен и компилируется чуть быстрее.

## `-Og` vs `-O0`

Это частое заблуждение — многие думают, что `-Og` это "debug mode с оптимизациями пониже", но нюанс важнее:

| |`-O0`|`-Og`|
|---|---|---|
|Оптимизации|Отключены полностью|Включены оптимизации, **не мешающие отладке**|
|Скорость выполнения|Медленный|Заметно быстрее|
|Соответствие исходнику|Максимальное (WYSIWYG)|Хорошее, но не 100%|
|Переменные "optimized out"|Практически никогда|Изредка возможно|
|Порядок выполнения строк|Строго последовательный|Может немного отличаться (переупорядочивание)|

**`-Og`** появился как компромисс: GCC документация описывает его как оптимизацию, которая "не мешает отладке" — убираются мёртвый код, некоторые упрощения, но сохраняется предсказуемый маппинг на исходный код.

**Когда что использовать:**

- **`-O0`** — когда нужна абсолютная точность отладки (пошаговая отладка сложной логики, каждая переменная должна быть видна). Твой стандартный выбор для CMake `Debug` конфигурации.
- **`-Og`** — когда код слишком медленный на `-O0` (например, отладка производительности с элементами логики, где нужно быстрее прогонять итерации, но код всё ещё частично оптимизирован в релизе). Полезен как промежуточный вариант между `Debug` и `RelWithDebInfo`.

Важный момент про твой стек: **корутины C++20 почти никогда нормально не отлаживаются на `-O0`** в некоторых версиях компиляторов — есть известные баги, когда coroutine frame собирается некорректно без оптимизаций (нужен минимум `-Og` или даже `-O1`). Это стоит проверить на конкретной версии GCC/Clang, которую ты используешь.

## DWARF версии: `-gdwarf-4` vs `-gdwarf-5`

DWARF — формат отладочной информации. Версия влияет на то, что могут показать инструменты.

**`-gdwarf-4`** (дефолт во многих старых тулчейнах):

- Широко поддерживается всеми версиями GDB/LLDB
- Стабильный, "безопасный" выбор для CI/контейнеров с разными версиями отладчиков

**`-gdwarf-5`** (более новый, GCC 7+/Clang 5+):

- Компактнее (лучшая компрессия строковых таблиц через `.debug_str_offsets`)
- Улучшенная поддержка для C++ templates и inline-функций
- Более точная информация о local variable scope
- Требует **GDB ≥ 8.0** и достаточно новый **LLDB** для полной поддержки

```bash
g++ -gdwarf-5 -g -O0 main.cpp -o main
```

**Практическая рекомендация для твоего окружения:** раз ты работаешь с Alpine-контейнерами (multi-stage Docker) — стоит проверить версию `gdb`/`lldb` внутри Alpine image (`musl libc` иногда идёт с урезанными версиями бинутилс). Если версия GDB в контейнере старая — `-gdwarf-4` безопаснее, иначе можно словить "DWARF version N unhandled" ошибку.

Проверить версию DWARF в уже собранном бинарнике:

```bash
readelf --debug-dump=info main | head -5
# или
objdump --dwarf=info main | grep "DW_AT_producer" -A2
```

## Практический пример для CMake (актуально после твоего изучения CMake presets)

```cmake
# CMakeLists.txt
set(CMAKE_CXX_FLAGS_DEBUG "-g3 -Og -gdwarf-5")
```

Или через presets:

```json
{
  "configurePresets": [
    {
      "name": "debug",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug",
        "CMAKE_CXX_FLAGS_DEBUG": "-g3 -Og -gdwarf-5"
      }
    }
  ]
}
```
