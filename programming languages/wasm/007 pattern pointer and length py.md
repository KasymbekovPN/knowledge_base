**Почему просто «записать данные по любому смещению» нельзя**

В прошлый раз (демо с `mem_demo.wat`) мы сами вручную писали модуль и сами решали, что строка лежит по смещению 8 — это работало, потому что мы полностью контролировали содержимое модуля. В реальном плагине так делать нельзя: у гостя есть собственная память с уже занятыми областями — стек вызовов (эмулированный компилятором внутри linear memory, как разбирали в Дне 3), глобальные переменные, куча под собственные нужды плагина. Если хост наугад запишет данные «куда-нибудь», он рискует затереть что-то из этого.

**Решение — хост просит гостя выделить буфер, а не выбирает адрес сам**

```c
__attribute__((export_name("to_upper")))
void to_upper(char *buf, int len) {
    for (int i = 0; i < len; i++)
        if (buf[i] >= 'a' && buf[i] <= 'z') buf[i] -= 32;
}
```

собрал с явным экспортом аллокатора:

```
clang --target=wasm32-wasip1 -mexec-model=reactor -O2 -nostartfiles \
  -Wl,--no-entry -Wl,--export=to_upper -Wl,--export=malloc -Wl,--export=free \
  -o plugin_str.wasm plugin_str.c
```

```python
from wasmtime import Store, Module, Instance

store = Store()
module = Module.from_file(store.engine, "plugin_str.wasm")
instance = Instance(store, module, [])
exports = instance.exports(store)

malloc = exports["malloc"]
free = exports["free"]
to_upper = exports["to_upper"]
memory = exports["memory"]

text = b"hello from the host!"
length = len(text)

# 1) ХОСТ ПРОСИТ ГОСТЯ выделить буфер нужного размера -- НЕ выбирает смещение сам.
#    Гость сам знает, какие участки его linear memory свободны.
guest_ptr = malloc(store, length)
print(f"The guest allocated a buffer at its own offset: {guest_ptr}")

# 2) ХОСТ ЗАПИСЫВАЕТ байты в память гостя по этому смещению через API рантайма
#    (это ровно то же самое, что runtime делает под капотом при host_ptr + offset,
#     но с проверкой границ -- напрямую руками так не пишут).
memory.write(store, text, guest_ptr)

# 3) ХОСТ ВЫЗЫВАЕТ функцию плагина, передавая только (указатель, длина) -- как и
#    договорились в контракте. Плагин работает in-place внутри СВОЕЙ памяти.
to_upper(store, guest_ptr, length)

# 4) ХОСТ ЧИТАЕТ результат обратно из той же области памяти гостя.
result = memory.read(store, guest_ptr, guest_ptr + length)
print(f"Result after plugin calling: {result.decode()!r}")

# 5) ХОСТ ОБЯЗАН попросить гостя освободить буфер -- иначе при повторных вызовах
#    куча гостя будет расти бесконечно (в госте нет сборщика мусора).
free(store, guest_ptr)
print("Buffer free by guest (free-method called form host).")

```

По умолчанию `malloc`/`free` из wasi-libc — внутренние символы, наружу не торчат. `-Wl,--export=malloc -Wl,--export=free` делает ровно то же, что `export_name` делал для нашей функции — открывает аллокатор гостя для хоста.

**Полный цикл со стороны хоста (Python + wasmtime, тот же биндинг, что и в демо с памятью):**

1. `guest_ptr = malloc(store, length)` — хост не выбирает смещение сам, а вызывает функцию гостя. Возвращённое число (в демо — `66064`) — это смещение, которое сам аллокатор гостя посчитал свободным в своей куче. Хост воспринимает его просто как непрозрачный «адрес» внутри чужой памяти — не пытается его интерпретировать.
    
2. `memory.write(store, text, guest_ptr)` — хост копирует байты в linear memory гостя через API рантайма (то же самое действие, что мы делали руками через `data_ptr()` в предыдущем демо, только теперь пишем, а не читаем).
    
3. `to_upper(store, guest_ptr, length)` — вызываем функцию плагина, передавая классическую пару «указатель + длина». Плагин работает _in-place_ прямо в этом буфере — своей собственной памяти, к которой у него есть полный доступ, в отличие от хоста, у которого доступ к этой памяти только опосредованный, через API рантайма.
    
4. `memory.read(store, guest_ptr, guest_ptr + length)` — хост читает результат обратно из той же области. Получили `'HELLO FROM THE HOST!'`.
    
5. `free(store, guest_ptr)` — и вот тут я изначально ошибся, вызвав `free(store, guest_ptr, length)` по аналогии с некоторыми аллокаторами, которые требуют знать размер при освобождении. Получил честную ошибку от wasmtime: `too many parameters provided: given 2, expected 1`. Это хорошая иллюстрация важного момента: сигнатура экспортированной функции гостя — это часть контракта, который хост обязан знать и соблюдать буквально, никакой автоматической подгонки типов рантайм не делает. Здесь `free` — обычный C-`free(void*)`, размер ему знать не нужно, аллокатор сам помнит его по внутренним метаданным рядом с блоком. Убрал лишний аргумент — заработало.
    

**Зачем вообще звать `free`.** У гостя нет сборщика мусора — если хост будет раз за разом звать `malloc` и не освобождать, куча гостя будет расти безостановочно (`memory.grow` будет дёргаться снова и снова), пока не упрётся в лимит памяти модуля. В реальной плагинной системе это первый кандидат на утечку, если контракт «кто и когда обязан звать free» не продуман чётко — обычно решают так: либо каждая функция гостя, принимающая буфер, сама обязана вызвать `free` до возврата, либо хост всегда парно вызывает `malloc`→...→`free` вокруг каждого обращения, как в этом примере.Готов перейти к Дню 4 — встраиванию рантайма (Wasmtime C API) уже в C++ хост вместо Python-биндингов, если хочешь продолжать по плану.
