[[programming languages/wasm/_|<=]]

**Адресное пространство обычного процесса.** Когда C++ хост запускается, ОС даёт ему огромное виртуальное адресное пространство (на 64-битной системе — колоссальный диапазон адресов), и MMU процессора транслирует виртуальные адреса в физические страницы памяти. Указатель — это просто число внутри этого пространства, но оно случайно (ASLR рандомизирует базовые адреса при каждом запуске) и осмысленно только внутри данного процесса. Указатель из одного процесса ничего не значит в другом — именно на этом и держится изоляция процессов в ОС.

Запустил маленькую C-программу — вот реальные адреса переменных в этом процессе:

```
host_variable (heap/data segment) address: 0x55eaf66b9010
stack_variable (stack)             address: 0x7ffcc23b51f4
```

Огромные, «случайные на вид» 48-битные числа — типичные виртуальные адреса x86-64.

**Линейная память WASM.** У WASM-модуля нет виртуальной памяти и нет доступа к адресному пространству хоста вообще. У него есть только linear memory — по сути один непрерывный массив байт, который выделяется в кратных 64 KiB «страницах» (можно расширять через `memory.grow`, но не уменьшать). Всё, что в коде WASM выглядит как «указатель», — это просто индекс (i32, обычное 32-битное число) внутри этого массива, отсчитываемый от нуля.

В демо-модуле строка лежит по смещению 8 в его линейной памяти:

```
'Указатель' гостя (смещение в линейной памяти): 8
Строка, прочитанная хостом по этому смещению: 'Hello from guest linear memory!'
Размер всей линейной памяти гостя: 65536 байт (1 страница(ы) по 64 KiB)
```

`8` — это буквально всё, на что способен «указатель» гостя. Никакой связи с `0x55eaf66b9010` или `0x7ffcc23b51f4` у хоста нет и быть не может — это два полностью разных адресных пространства, у гостя оно даже не является настоящей памятью процесса в привычном смысле, а просто буфером, которым владеет рантайм (Wasmtime/WAMR).

**Почему это и есть механизм песочницы.** Реальный (нативный) указатель хоста рантайм держит у себя — это адрес, где именно в _своей_ памяти он выделил буфер под linear memory гостя. Когда исполняется код гостя и он обращается «по указателю 8», рантайм на лету делает `base_ptr_хоста + 8` и обязательно проверяет, что смещение не выходит за текущий размер памяти гостя. WASM-код физически не может сконструировать смещение, указывающее за пределы своей же линейной памяти — в отличие от кода, загруженного через `dlopen`, у которого есть указатели во всё адресное пространство процесса. Отсюда и вся ценность WASM для плагинов: даже вредоносный или багованный плагин не может прочитать/переписать память хоста напрямую, потому что у него физически нет доступа к настоящим адресам — только к числам-смещениям внутри собственного маленького буфера.

Практический вывод для Дня 3 плана (граница памяти): нельзя просто взять C++ указатель и «отдать» его гостю — гость не сможет его разыменовать, у него нет туда доступа. Поэтому паттерн всегда один: хост копирует байты _внутрь_ linear memory гостя по какому-то смещению (обычно полученному вызовом `malloc`, который экспортирует сам гость), либо читает байты _из_ неё — как я сделал выше через `memory.data_ptr()`/`memory.data_len()` в Python-биндинге. Прямого шаринга указателей между хостом и гостем не существует в принципе.

Ещё один нюанс, который встретится на Дне 2 при компиляции реального C/C++: у WASM есть и другой, отдельный «стек» — неявный операндный стек виртуальной машины (то, что использовали `local.get`/`i32.add` в примере с `add` из первого дня). Он не адресуем и не живёт в linear memory. Но когда компилятор (clang/emscripten) собирает C/C++ код, где есть `&local_variable`, он вынужден сам эмулировать адресуемый стек вызовов _внутри_ linear memory — потому что взять адрес операндного стека WASM невозможно. Так что «стек» в скомпилированном из C++ WASM-модуле — это на самом деле область в той же linear memory, а не встроенный примитив VM.Для запуска `mem_demo.py` у себя понадобится `pip install wasmtime` (это Python-биндинги к рантайму, отдельно от CLI). 

### mem_demo.cpp
```wat
(module
  ;; экспортируем линейную память: 1 страница = 64 KiB
  (memory (export "memory") 1)

  ;; кладём строку в линейную память по смещению 8, с завершающим нулём
  (data (i32.const 8) "Hello from guest linear memory!\00")

  ;; "указатель" гостя на строку — это просто смещение внутри его памяти
  (func (export "get_str_ptr") (result i32)
    i32.const 8)
)
```

### mem_demo.c
```c
#include <stdio.h>

/* обычная переменная в адресном пространстве ЭТОГО (хостового) процесса */
int host_variable = 42;

int main(void) {
    int stack_variable = 7;
    printf("host_variable (heap/data segment) address: %p\n", (void*)&host_variable);
    printf("stack_variable (stack)             address: %p\n", (void*)&stack_variable);
    return 0;
}
```

### mem_demo.py
```Python
from wasmtime import Store, Module, Instance

store = Store()
module = Module.from_file(store.engine, "mem_demo.wasm")
instance = Instance(store, module, [])

get_str_ptr = instance.exports(store)["get_str_ptr"]
memory = instance.exports(store)["memory"]

guest_ptr = get_str_ptr(store)  # это "указатель" внутри гостя — просто число
print(f"'Указатель' гостя (смещение в линейной памяти): {guest_ptr}")

# читаем сырые байты линейной памяти напрямую, находим по смещению guest_ptr нуль-терминированную строку
raw = memory.data_ptr(store)
data_len = memory.data_len(store)
buf = bytes(raw[i] for i in range(data_len))  # весь буфер линейной памяти (64 KiB), для наглядности
end = buf.index(0, guest_ptr)
text = buf[guest_ptr:end].decode()

print(f"Строка, прочитанная хостом по этому смещению: {text!r}")
print(f"Размер всей линейной памяти гостя: {data_len} байт ({data_len // 65536} страница(ы) по 64 KiB)")
```
