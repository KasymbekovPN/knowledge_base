[[programming languages/wasm/_|<=]]

**Установка**

Официальный способ (рекомендую его на своей машине):

```
git clone https://github.com/emscripten-core/emsdk.git
cd emsdk
./emsdk install latest
./emsdk activate latest
source ./emsdk_env.sh
```

У меня в песочнице этот путь не сработал — `emsdk install` качает node/clang с `storage.googleapis.com`, а исходящий доступ туда в моей текущей среде заблокирован сетевым фильтром. Это ограничение именно моей песочницы, у тебя на машине его не будет. Я обошёл это через `apt install emscripten` — там версия 3.1.6 (более старая, чем актуальный релиз через `emsdk`), но для сравнения тулчейнов концептуально этого достаточно.

**Компиляция того же примера**

`add.c` (та же функция, что и через wasi-sdk) — собрал как "side module" без JS-обвязки, ближе всего к библиотечному стилю:

```
emcc add.c -O2 -s SIDE_MODULE=1 -o add_em.wasm
```

`hello.c` — стандартным способом, под браузер/Node:

```
emcc hello.c -O2 -o hello_em.js
```

Это генерирует `.js`-файл со всей загрузочной обвязкой (`fetch`/`XMLHttpRequest` для браузера, `fs.readFileSync` для Node) плюс сам `.wasm`. Запуск через Node у меня с ходу упал — в старом 3.1.6 глюе есть баг совместимости с современным Node (там появился глобальный `fetch`, и старый код ошибочно пытается использовать его вместо чтения файла), пришлось запускать с `node --no-experimental-fetch hello_em.js`. Это чисто версионная проблема этой конкретной сборки, к самой архитектуре WASM отношения не имеет.

**Сравнение размеров — и тут важная поправка**

Первый прогон дал разброс, который выглядел драматично:

|файл|тулчейн|размер|
|---|---|---|
|`add.wasm` (ручной `.wat`)|—|41 байт|
|`add_c.wasm` (wasi-sdk)|wasi-sdk|19 451 байт|
|`add_em.wasm` (side module)|Emscripten|113 байт|
|`hello.wasm`|wasi-sdk|55 143 байт|
|`hello_em.js` + `hello_em.wasm`|Emscripten|16 728 + 2 072 байт|

19 КБ против 113 байт за одну и ту же функцию сложения выглядит как «Emscripten эффективнее», но разобрал секции `add_c.wasm` через `wasm-objdump -h` — и почти весь вес там (~19.3 КБ из 19.4) это отладочная информация: `.debug_info`, `.debug_line`, `.debug_str` и так далее, которую wasi-sdk по умолчанию оставляет в бинарнике. Реальный код (Type/Function/Table/Memory/Export/Code секции) занимает около 107 байт. Стрипнул через `wasm-strip`:

```
wasm-strip add_c_stripped.wasm
```

Результат: **107 байт** — практически идентично 113 байтам у Emscripten. Урок отсюда практический и важный: для реальных сборок всегда добавляй `-g0` (не включать debug info) или прогоняй `wasm-strip`/`wasm-opt --strip-debug` — иначе сравнение размеров будет нечестным, и в проде плагины будут раздуты зря.

**Под что заточен каждый тулчейн — в этом главное отличие, не в размере**

wasi-sdk целится в `wasm32-wasip1` — модуль, который ожидает быть загруженным _напрямую_ каким-то WASM-рантаймом (Wasmtime, WAMR, браузерный `WebAssembly.instantiate`, что угодно), общаясь с окружением через стандартизованный набор WASI-синсколов (`fd_write` для stdout и так далее — видно было в сгенерированном `hello_em.js`, там та же функция `fd_write` импортируется под `wasi_snapshot_preview1`, только вызывается уже из JS-эмуляции). Никакой JS-обвязки не требуется — то, что делали в прошлый раз через `wasmtime run hello.wasm` напрямую.

Emscripten по умолчанию целится в браузер (и Node как «эмулятор браузера»): для запуска ему нужен сгенерированный JS-файл, который знает, как подгрузить `.wasm`, создать линейную память, прокинуть browser/Node API (DOM, файловая система через виртуальную FS-прослойку, XHR/fetch). Это удобно, если конечная цель — веб-страница, но избыточно и неуместно для встраивания в нативный C++ хост как плагина: там не с чем «слушать fetch», не нужен браузерный event loop, а WASI-совместимый рантайм типа Wasmtime и так умеет находить нужные функции по имени и предоставлять свои имплементации системных вызовов напрямую, без прослойки JS.
