**`message` — базовая единица схемы**

```proto
syntax = "proto3";

package myapp;

message User {
  int32 id = 1;
  string name = 2;
  string email = 3;
  bool is_active = 4;
  double balance = 5;
  bytes avatar = 6;
}
```

`message` — это аналог struct/класса: именованный набор типизированных полей. Каждое поле имеет тип, имя и уникальный номер после `=`.

**Скалярные типы**

- `int32`, `int64` — знаковые целые. Эффективны для небольших положительных чисел, но для больших отрицательных значений кодируются неэффективно (varint даёт 10 байт вместо 4-5). Для чисел, которые часто бывают отрицательными, лучше `sint32`/`sint64` (zigzag-кодирование).
- `uint32`, `uint64` — беззнаковые.
- `fixed32`, `fixed64` — фиксированный размер (4/8 байт), выгоднее varint, если значения обычно большие (близкие к максимуму типа).
- `string` — UTF-8 текст.
- `bytes` — произвольные бинарные данные, без требования к кодировке.
- `bool` — true/false.
- `float`, `double` — числа с плавающей точкой, 4 и 8 байт соответственно, кодируются как fixed (не varint).

В сгенерированном C++ коде это напрямую мапится на `int32_t`, `int64_t`, `std::string`, `bool`, `float`, `double` — никаких сюрпризов в типах.

**Номера полей и wire-формат**

Номер после `=` — не порядковый индекс, а постоянный идентификатор поля в бинарном формате. Каждое закодированное поле в wire-формате — это пара tag-value, где tag вычисляется как `(номер_поля << 3) | wire_type`. То есть номер поля физически зашивается в каждый закодированный байт-tag сообщения.

Отсюда правила:

- Номера 1-15 кодируются в 1 байт tag'а — используй их для самых часто встречающихся полей.
- Номера 16-2047 занимают 2 байта — для менее частых полей это нормально.
- Номер поля нельзя менять после того, как схема ушла в продакшен — старые сериализованные данные и старые клиенты интерпретируют байты по номеру, а не по имени. Смена номера = потеря/порча данных при чтении.
- Имя поля можно менять свободно (не влияет на wire-формат, только на сгенерированный код).
- Тип поля менять нежелательно — совместимость есть только между типами с одинаковым wire_type (например, int32/uint32/bool все используют varint и формально взаимозаменяемы на уровне байтов, но семантически это плохая идея).
- Удалённые номера стоит помечать `reserved`, чтобы случайно не переиспользовать их для нового поля.

Пример с `reserved`:

```proto
message User {
  reserved 4, 7;
  reserved "old_field_name";

  int32 id = 1;
  string name = 2;
  string email = 3;
}
```

Это и есть механизм, который делает protobuf обратно/прямо совместимым: старый и новый парсер читают одни и те же байты, ориентируясь на номера полей, а не на позицию или имя.
