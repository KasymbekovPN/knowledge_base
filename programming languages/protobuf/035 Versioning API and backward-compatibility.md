[[programming languages/protobuf/_|<=]]

protoc принимает `[deprecated = true]` на поле и `option deprecated = true;` внутри `rpc` без ошибок.

**Пакет как единица версии — основной паттерн в gRPC**

```protobuf
// v1/user_service.proto
package myapp.v1;
service UserService { rpc GetUser(...) returns (...); }

// v2/user_service.proto
package myapp.v2;
service UserService { rpc GetUser(...) returns (...); }
```

Ключевая техническая деталь: gRPC маршрутизирует вызовы по **полному пути метода**, который включает пакет — `/myapp.v1.UserService/GetUser` и `/myapp.v2.UserService/GetUser` физически разные endpoint'ы. Это значит: сервер может зарегистрировать **обе** реализации одновременно (`builder.RegisterService(&v1_impl); builder.RegisterService(&v2_impl);`) и обслуживать старых и новых клиентов на одном порту без какого-либо конфликта. Именно так делают крупные API (Google Cloud API, AIP-181 — их официальное руководство по версионированию явно рекомендует major-версию прямо в имени пакета).

**Что считается breaking change (требует новой версии пакета)**

Смена типа существующего поля, переименование/удаление RPC-метода, смена семантики уже существующего поля (даже без изменения типа — например, поле раньше значило "цена без налога", а теперь "цена с налогом"), смена streaming/non-streaming у существующего метода. Всё это ломает контракт для уже задеплоенных клиентов — их нельзя менять "на месте" в v1, только выпускать как v2.

**Что НЕ требует новой версии (safe evolution — уже разбирали)**

Добавление нового поля с новым номером, добавление нового RPC-метода в существующий `service`, добавление нового `service` в тот же пакет, пометка поля `deprecated` без удаления. Это ровно то, что мы закрепляли правилами `reserved`/номеров полей — эволюция внутри одной major-версии обязана оставаться обратно совместимой именно по этим правилам.

**`deprecated` — явное объявление намерения, не механизм совместимости сам по себе**

```proto
message User {
  string legacy_full_name = 3 [deprecated = true];
}
service UserService {
  rpc GetUser(User) returns (User) {
    option deprecated = true;
  }
}
```

Это не ломает wire-формат и не меняет поведение — просто помечает элемент как "не использовать в новом коде", генераторы кода в некоторых языках проставляют соответствующие атрибуты (`[[deprecated]]` в C++, `@Deprecated` в Java), IDE подсвечивает предупреждением. Реальное удаление поля/метода — отдельный, более поздний шаг, обычно после периода наблюдения за метриками использования (тут пригождаются interceptors из прошлой темы — логировать, кто ещё реально дергает устаревший метод, прежде чем его выключать).

**Практический процесс версионирования в реальных сервисах**

1. Выпустить `v2` рядом с `v1`, не трогая `v1`.
2. Дать клиентам время мигрировать (обычно недели-месяцы, зависит от организации).
3. Мониторить через interceptor/метрики, кто ещё зовёт `v1`.
4. Когда трафик на `v1` упал до нуля (или до допустимого порога) — official deprecation period, затем удаление реализации `v1` с сервера.
5. Никогда не менять поведение существующего метода "по-тихому" — новая семантика = новый метод/пакет, а не переиспользование старого имени с другим смыслом (та же логика, что и с переиспользованием номера поля — тихая порча ожиданий клиента).

**Как это соотносится с организацией `.proto`-файлов**

Естественно ложится на структуру директорий из темы про CMake: `proto/v1/user_service.proto`, `proto/v2/user_service.proto` — отдельные файлы, отдельные пакеты, отдельные сгенерированные C++ namespace'ы (`myapp::v1::UserService`, `myapp::v2::UserService`), можно инклюдить и регистрировать оба одновременно в одном сервере без конфликтов имён.
