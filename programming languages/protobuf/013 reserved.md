### reserved_syntax.proto
```protobuf
syntax = "proto3";
package myapp.reserved_demo;

message Config {
  // Номера по одному
  reserved 2, 9;
  // Диапазон номеров (включительно с обеих сторон)
  reserved 4 to 6;
  // Диапазон "до максимума" (редко нужен, но валиден)
  // reserved 100 to max;
  reserved "old_flag", "legacy_mode";

  int32 id = 1;
  // 2 занят (reserved)
  string name = 3;
  // 4,5,6 заняты (reserved)
  bool active = 7;
  double score = 8;
  // 9 занят (reserved)
  int32 version = 10;
}
```

**`reserved` — синтаксис**

```proto
reserved 2, 9;
reserved 4 to 6;
reserved "old_flag", "legacy_mode";
```


**Unknown fields — что происходит на практике**

Старый `v1` отправил 11 байт: `08 64 12 05 63 6c 69 63 6b 18 05`. Последние два байта (`18 05`) — это поле 3 (`retry_count=5`, tag `0x18 = (3<<3)|0`). `v2good` не знает поля 3 (оно `reserved`), но при парсинге явно видно: `unknown fields count = 1`, `field #3, type=0, varint value = 5` — protobuf сохранил и номер, и тип wire-кодировки, и само значение, просто не смог сопоставить его ни с одним известным полем схемы.

**Round-trip без потерь**

Пересериализовав `v2good` обратно, получили ровно те же 11 байт: `08 64 12 05 63 6c 69 63 6b 18 05` — байт в байт идентично оригиналу. Это ключевое свойство protobuf: сообщение, прошедшее через промежуточный сервис (прокси, шину сообщений, кэш), который не знает всех полей, не портит и не теряет данные, если просто парсит-и-пересобирает без явной модификации.

**Явное отбрасывание unknown fields**

```cpp
good.GetReflection()->MutableUnknownFields(&good)->Clear();
```

После этого размер упал до 9 байт (`18 05` пропали) — намеренная очистка данных. Нужно, если сообщение уходит наружу и не должно тащить за собой "чужие" внутренние поля (приватность, безопасность API на границе сервисов).

**Практический вывод**

- `reserved` — превентивная защита компилятором от повторного использования номера/имени внутри схемы.
- Unknown fields — защитная сетка на рантайме: даже если кто-то забыл поставить `reserved`, старые данные не разрушаются молча при парсинге незнакомой схемой (в отличие от переиспользования номера с совпадающим wire_type, как было в прошлом демо — там опасность не в потере данных, а в их ложной интерпретации).
