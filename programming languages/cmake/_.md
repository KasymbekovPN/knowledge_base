# CTest — подробный разбор

CTest — это система запуска тестов, входящая в комплект CMake. Важно сразу понять: **CTest не фреймворк тестирования**, а оркестратор — он запускает тестовые исполняемые файлы, собирает результаты, фильтрует, распараллеливает и формирует отчёты. Сами тесты пишутся на чём угодно (Boost.Test, GoogleTest, Catch2, голый скрипт) — CTest лишь ими дирижирует.

---

## Базовая модель

CTest оперирует «тестами» — командами, которые он запускает. Тест считается **пройденным**, если команда вернула код выхода `0`, и **проваленным** при ненулевом коде (по умолчанию). Всё строится вокруг этого простого контракта.

```cmake
enable_testing()                       # включить тестирование в проекте
add_test(NAME my_test COMMAND my_exe)  # зарегистрировать тест
```

|Команда CMake|Назначение|
|---|---|
|`enable_testing()`|Активирует CTest для проекта (или `include(CTest)`)|
|`add_test(...)`|Регистрирует одну тестовую команду|
|`set_tests_properties(...)`|Настраивает свойства теста|

---

## 1. Регистрация тестов: `add_test`

### Простая форма

```cmake
add_test(NAME unit_tests COMMAND unit_tests)
#             ^имя в CTest        ^исполняемый файл (цель CMake или путь)
```

### С аргументами

```cmake
add_test(
    NAME calculator_suite
    COMMAND unit_tests --run_test=calculator_tests --log_level=all
)
```

Аргументы после `COMMAND` передаются исполняемому файлу. Здесь мы запускаем тот же бинарник, но просим Boost.Test выполнить только один сьют.

### С рабочей директорией

```cmake
add_test(
    NAME data_test
    COMMAND unit_tests
    WORKING_DIRECTORY ${CMAKE_CURRENT_SOURCE_DIR}/test_data
)
```

---

## 2. Свойства тестов: `set_tests_properties`

Тонкая настройка поведения каждого теста:

```cmake
set_tests_properties(my_test PROPERTIES
    TIMEOUT 30                          # макс. время в секундах
    WILL_FAIL TRUE                      # тест ДОЛЖЕН провалиться (инверсия)
    LABELS "unit;fast"                  # метки для группировки
    ENVIRONMENT "LOG_LEVEL=debug"       # переменные окружения
)
```

|Свойство|Назначение|
|---|---|
|`TIMEOUT`|Лимит времени; превышение → провал|
|`WILL_FAIL`|Инвертирует результат (ожидаем падение)|
|`LABELS`|Метки для фильтрации (`-L`)|
|`ENVIRONMENT`|Переменные окружения для теста|
|`WORKING_DIRECTORY`|Рабочая директория|
|`DEPENDS`|Запускать после другого теста|
|`RUN_SERIAL`|Не запускать параллельно с другими|
|`PROCESSORS`|Сколько ядер «занимает» тест (для планировщика)|
|`FAIL_REGULAR_EXPRESSION`|Провал, если вывод совпал с регуляркой|
|`PASS_REGULAR_EXPRESSION`|Проход только при совпадении вывода|
|`SKIP_RETURN_CODE`|Код выхода, означающий «пропущен»|

### Определение прохождения по выводу (а не по коду возврата)

```cmake
add_test(NAME output_check COMMAND my_program)
set_tests_properties(output_check PROPERTIES
    PASS_REGULAR_EXPRESSION "All checks passed"
    FAIL_REGULAR_EXPRESSION "ERROR|FATAL"
)
```

Полезно для программ, которые не выставляют код возврата, но печатают результат.

---

## 3. Запуск: команда `ctest`

Выполняется из директории сборки (или с `--test-dir`):

```bash
ctest                              # запустить все тесты
ctest --test-dir build            # указать директорию сборки явно
```

### Базовые опции вывода

|Опция|Назначение|
|---|---|
|`-V` / `--verbose`|Подробный вывод (показывает stdout тестов)|
|`-VV` / `--extra-verbose`|Ещё подробнее|
|`--output-on-failure`|Показать вывод **только** упавших тестов|
|`-Q`|Тихий режим|
|`--progress`|Компактный индикатор прогресса|

`--output-on-failure` — самый практичный флаг в повседневной работе: молчит на зелёных тестах, но показывает диагностику упавших.

```bash
ctest --test-dir build --output-on-failure
```

---

## 4. Фильтрация тестов

### По имени (регулярное выражение)

```bash
ctest -R calculator        # запустить тесты, чьё имя содержит "calculator"
ctest -R "^unit_tests$"    # точное совпадение
ctest -E slow              # ИСКЛЮЧИТЬ тесты с "slow" в имени (-E = exclude)
```

### По меткам (LABELS)

```bash
ctest -L unit              # только тесты с меткой "unit"
ctest -LE integration      # исключить метку "integration"
```

### По номеру

```bash
ctest -I 1,5               # тесты с 1-го по 5-й
ctest -I 1,10,2            # с 1 по 10, через один (шаг 2)
```

|Опция|Значение|
|---|---|
|`-R <regex>`|Включить по имени|
|`-E <regex>`|Исключить по имени|
|`-L <regex>`|Включить по метке|
|`-LE <regex>`|Исключить по метке|
|`-I <start,end,step>`|По индексам|

---

## 5. Параллельный запуск

Одно из главных преимуществ CTest — параллелизация:

```bash
ctest -j 8                 # запустить до 8 тестов одновременно
ctest --parallel 8         # то же самое
ctest -j $(nproc)          # по числу ядер (Linux)
```

Тесты, которые нельзя запускать параллельно (общий ресурс — файл, порт, БД), помечаются:

```cmake
set_tests_properties(db_test PROPERTIES RUN_SERIAL TRUE)
```

Или указывается «вес» в ядрах, чтобы планировщик не перегружал систему:

```cmake
set_tests_properties(heavy_test PROPERTIES PROCESSORS 4)
```

---

## 6. Повтор и устойчивость

### Повтор упавших (борьба с «мигающими» тестами)

```bash
ctest --repeat until-pass:3        # до 3 попыток, пока не пройдёт
ctest --repeat until-fail:5        # 5 раз, ловим нестабильность
ctest --repeat after-timeout:2     # повтор только при таймауте
```

### Остановиться на первом провале

```bash
ctest --stop-on-failure
```

### Перезапустить только упавшие с прошлого раза

```bash
ctest --rerun-failed
```

Очень удобно при отладке: исправил код — гоняешь только то, что падало, не весь набор.

---

## 7. Управление таймаутами

```bash
ctest --timeout 60                 # глобальный таймаут 60 сек на тест
```

Или на конкретный тест в CMake:

```cmake
set_tests_properties(slow_test PROPERTIES TIMEOUT 120)
```

Тесты, превысившие лимит, помечаются как провалившиеся с пометкой «Timeout». Защищает CI от зависших тестов, держащих пайплайн бесконечно.

---

## 8. Форматы вывода для CI

### JUnit XML (самый востребованный в CI)

```bash
ctest --output-junit results.xml
```

Этот файл понимают GitHub Actions, GitLab CI, Jenkins — они показывают разбивку по тестам в своём интерфейсе.

> Не путай с выводом самого фреймворка. Boost.Test тоже умеет JUnit (`--output_format=JUNIT`), но это отчёт о его внутренних тестах. `ctest --output-junit` — отчёт уровня CTest (какие зарегистрированные команды прошли). Часто в CI используют один из них; для детализации по отдельным `BOOST_AUTO_TEST_CASE` нужна интеграция (см. п.10).

## 9. Связка с этапом сборки

### Собрать и протестировать одной командой

```bash
ctest --build-and-test <src> <build> \
    --build-generator Ninja \
    --test-command ctest
```

### Через CMake-таргет (удобный повседневный приём)

В CMake часто добавляют цель, которая сначала собирает, потом тестирует:

```cmake
add_custom_target(check
    COMMAND ${CMAKE_CTEST_COMMAND} --output-on-failure
    DEPENDS unit_tests smoke_tests   # сначала соберёт тесты
)
```

Теперь `cmake --build build --target check` соберёт и прогонит тесты.

## 10. Автоматическая регистрация отдельных тест-кейсов

По умолчанию `add_test` регистрирует **весь бинарник** как один CTest-тест. Если он содержит 50 `BOOST_AUTO_TEST_CASE`, CTest видит их как единое целое — упал один, весь тест «красный», без детализации.

Чтобы каждый случай стал отдельным CTest-тестом, для разных фреймворков есть модули автодискавери:

```cmake
# Для GoogleTest:
include(GoogleTest)
gtest_discover_tests(unit_tests)

# Для Catch2:
include(Catch)
catch_discover_tests(unit_tests)
```

Для **Boost.Test** штатного `boost_test_discover_tests` в составе CMake **нет** (в отличие от GoogleTest/Catch2). Варианты:

- Ручная регистрация по сьютам:

```cmake
add_test(NAME calc COMMAND unit_tests --run_test=calculator_tests)
add_test(NAME repo COMMAND unit_tests --run_test=repository_tests)
```

- Сторонние CMake-модули, парсящие `--list_content` Boost.Test и генерирующие `add_test` на каждый случай (есть в открытом доступе, но не в стандартной поставке).

> Это стоит свериться с актуальной документацией CMake — поддержка дискавери расширяется от версии к версии. Хочешь, проверю, появился ли штатный модуль для Boost.Test в свежих CMake?

## 11. Dashboard и CDash (для больших проектов)

CTest исторически связан с CDash — веб-дашбордом результатов. Команды «Dashboard mode»:

```bash
ctest -D Experimental       # прогон с отправкой на дашборд
ctest -D Nightly            # ночная сборка
ctest -D Continuous         # непрерывная интеграция
```

Эти режимы выполняют цикл «обновить → собрать → протестировать → отправить результаты на CDash». Для большинства современных проектов это вытеснено GitHub Actions/GitLab CI, но в крупных C++-проектах (включая сам CMake) CDash ещё используется.

## Полный практический сценарий

```cmake
# CMakeLists.txt
enable_testing()

find_package(Boost REQUIRED COMPONENTS unit_test_framework)

add_executable(unit_tests test_main.cpp test_calc.cpp)
target_link_libraries(unit_tests PRIVATE core Boost::unit_test_framework)

# регистрируем с метками и таймаутом
add_test(NAME unit_tests COMMAND unit_tests --output_format=JUNIT)
set_tests_properties(unit_tests PROPERTIES
    LABELS "unit;fast"
    TIMEOUT 30
)

add_test(NAME smoke COMMAND smoke_tests)
set_tests_properties(smoke PROPERTIES LABELS "smoke")
```

Типичные команды в работе:

```bash
# повседневная разработка
ctest --test-dir build --output-on-failure -j$(nproc)

# отладка одного упавшего
ctest --test-dir build -R calculator -VV

# только быстрые тесты перед коммитом
ctest --test-dir build -L fast

# перегнать только то, что падало
ctest --test-dir build --rerun-failed --output-on-failure

# в CI
ctest --test-dir build --output-on-failure --output-junit results.xml
```

## Почему CTest стоит использовать (а не запускать бинарники вручную)

- **Единая точка входа** для разнородных тестов: Boost.Test, скрипты на Python, проверки выходных файлов — всё под одной командой `ctest`.
- **Параллелизация из коробки** без усилий со стороны тестов.
- **Фильтрация и повторы** ускоряют цикл отладки (`--rerun-failed`, `-R`).
- **Интеграция с CI** через JUnit XML и dashboard-режимы.
- **Управление ресурсами** (serial-тесты, таймауты, веса) для стабильных прогонов.

CTest особенно ценен, когда тестов много и они разнотипны: он превращает «куча отдельных бинарников» в управляемый, фильтруемый, параллельный набор с едиными отчётами.
