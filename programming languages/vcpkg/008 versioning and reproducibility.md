# Версионирование и воспроизводимость

Это пункт о том, как зафиксировать _конкретные_ версии библиотек, чтобы сборка была воспроизводимой: тот же код + тот же манифест = тот же набор версий зависимостей на любой машине и в любой момент времени. Тема целиком относится к **manifest-режиму**.

## Проблема, которую решает версионирование

Реестр портов vcpkg — это git-репозиторий, который постоянно обновляется: версии библиотек растут. Без фиксации версий вы получаете «плавающую» сборку:

- Сегодня `fmt` ставится версии 10.1.1, через месяц после `git pull` — уже 11.0.0.
- У вас на машине одна версия, у коллеги другая — потому что репозитории vcpkg в разном состоянии.
- «У меня собирается, у тебя нет» — классический симптом.

Версионирование делает набор версий детерминированным и привязанным к проекту.

## Ключевая идея: baseline

**Baseline** — это «снимок» состояния реестра портов в конкретный момент, заданный git-хешем коммита репозитория vcpkg. Он отвечает на вопрос: «какие версии библиотек считать актуальными по умолчанию?».

Задаётся полем `builtin-baseline` в `vcpkg.json`:

```json
{
  "name": "shapes-demo",
  "version": "0.1.0",
  "dependencies": [ "fmt" ],
  "builtin-baseline": "9f02c5cb4c3f3a4a0a8c9e2b1d6f7e8a9b0c1d2e"
}
```

Этот хеш — коммит из репозитория microsoft/vcpkg. Все зависимости берут свои версии из состояния реестра на этом коммите, если не указано иное. Поскольку хеш зафиксирован в манифесте и коммитится в git вашего проекта, набор версий становится воспроизводимым: vcpkg всегда «отматывает» реестр к этому состоянию.

### Как получить значение baseline

Самый простой способ — команда, которая запишет текущий хеш вашего локального vcpkg в манифест:

```bash
vcpkg x-update-baseline --add-initial-baseline
```

Она добавит (или обновит) `builtin-baseline` в `vcpkg.json`. Альтернативно — взять хеш вручную:

```bash
cd $VCPKG_ROOT
git rev-parse HEAD
```

и вставить в манифест.

## Уточнение версий: `version>=`

Baseline задаёт версии «по умолчанию». Если нужно потребовать **не ниже** определённой версии конкретной библиотеки, используется `version>=` в элементе зависимости:

```json
"dependencies": [
  {
    "name": "fmt",
    "version>=": "10.0.0"
  }
]
```

Семантика:

- vcpkg возьмёт версию `fmt` **не ниже** 10.0.0.
- Но не ниже baseline тоже: фактическая версия — это максимум из baseline-версии и указанного минимума.
- Это «минимальное ограничение», а не «точно эта версия». vcpkg намеренно избегает «закрепить ровно X», предпочитая модель минимальных версий (об этом ниже).

`version>=` полезен, когда вашему коду нужна фича, появившаяся в определённой версии, и вы хотите гарантировать, что библиотека не старее.

## Жёсткая фиксация: `overrides`

Когда нужно **точно** зафиксировать конкретную версию, игнорируя baseline и ограничения `version>=` от других зависимостей, используется `overrides`:

```json
{
  "dependencies": [ "fmt", "spdlog" ],
  "builtin-baseline": "9f02c5cb...",
  "overrides": [
    { "name": "fmt", "version": "10.1.1" }
  ]
}
```

Семантика:

- `fmt` будет **ровно** 10.1.1, что бы ни говорили baseline или транзитивные требования.
- `overrides` имеет высший приоритет — это «последнее слово».
- Часто нужен, когда транзитивная зависимость требует версию, несовместимую с вашим кодом, или нужно временно «прибить» проблемную версию.

> Важно: версия в `overrides` должна существовать в реестре (в базе `versions/`). Нельзя зафиксировать версию, которой нет в истории портов.

## Как эти механизмы взаимодействуют

Приоритет разрешения версий (от низшего к высшему):

1. **baseline** — версия по умолчанию из снимка реестра.
2. **`version>=`** — поднимает нижнюю границу, если она выше baseline.
3. **`overrides`** — перекрывает всё, фиксирует точную версию.

vcpkg использует модель **минимальных версий** (minimum version selection): он выбирает наименьшую версию, удовлетворяющую всем ограничениям. Это противоположно «всегда брать самое новое». Логика: если код собирается с минимально требуемыми версиями, он соберётся и с более новыми — а детерминизм при этом сохраняется. Чтобы поднять версии, вы осознанно двигаете baseline, а не получаете обновления самотёком.

## Обновление версий

Обновить зависимости — значит сдвинуть baseline на более свежий коммит vcpkg:

```bash
cd $VCPKG_ROOT
git pull                          # обновили локальный реестр

cd /path/to/your/project
vcpkg x-update-baseline           # подтянули новый baseline в манифест
```

После этого версии «по умолчанию» станут новее, но это произойдёт **явно** и зафиксируется в git вашего проекта как изменение `vcpkg.json`. То есть обновление — это осознанный коммит, а не побочный эффект.

## Registry baseline (несколько реестров)

Всё выше относилось к встроенному реестру vcpkg (отсюда `builtin-baseline`). Если вы подключаете **дополнительные реестры** (например, приватный со своими портами — отдельный пункт плана), у каждого реестра свой baseline. Это настраивается в файле `vcpkg-configuration.json`:

```json
{
  "default-registry": {
    "kind": "builtin",
    "baseline": "9f02c5cb..."
  },
  "registries": [
    {
      "kind": "git",
      "repository": "https://github.com/my-org/my-vcpkg-registry",
      "baseline": "abc123...",
      "packages": [ "my-internal-lib" ]
    }
  ]
}
```

Здесь:

- `default-registry` с baseline отвечает за стандартные порты.
- Дополнительный git-реестр со **своим** baseline отвечает за перечисленные в `packages` библиотеки.
- Каждый реестр версионируется независимо, но так же детерминированно.

Детали реестров — в следующем пункте плана; здесь важно понять, что **baseline существует у каждого реестра**, не только у встроенного.

## Применим к нашему проекту shapes-demo

Зафиксируем версии в манифесте примера:

```json
{
  "name": "shapes-demo",
  "version": "0.1.0",
  "dependencies": [
    {
      "name": "fmt",
      "version>=": "10.0.0"
    }
  ],
  "builtin-baseline": "9f02c5cb4c3f3a4a0a8c9e2b1d6f7e8a9b0c1d2e",
  "overrides": [
    { "name": "fmt", "version": "10.1.1" }
  ]
}
```

Что это даёт:

- `builtin-baseline` фиксирует общий снимок реестра.
- `version>=: "10.0.0"` декларирует, что коду нужен `fmt` хотя бы 10.0.0.
- `overrides` жёстко прибивает `fmt` к 10.1.1 — все, кто склонирует проект, получат ровно эту версию.

Команды для получения реального хеша baseline (заглушку выше нужно заменить):

```bash
cd shapes-demo
vcpkg x-update-baseline --add-initial-baseline
```

После этого `cmake --preset default` всегда ставит ту же версию `fmt`, независимо от состояния глобального vcpkg.

## Чек-лист воспроизводимой сборки

- В `vcpkg.json` задан **`builtin-baseline`** (через `x-update-baseline`).
- Манифест **закоммичен в git** вместе с проектом.
- Критичные версии при необходимости закреплены через **`version>=`** или **`overrides`**.
- Обновления зависимостей делаются **осознанно** — сдвигом baseline отдельным коммитом, а не самотёком.
- Для CI это означает: достаточно склонировать проект и собрать — версии придут из манифеста, а не из состояния машины.

## Что запомнить

Воспроизводимость в vcpkg держится на **baseline** — git-снимке реестра, зафиксированном в `vcpkg.json` и закоммиченном в проект. `version>=` поднимает нижнюю границу версии библиотеки, `overrides` жёстко фиксирует точную версию (высший приоритет). vcpkg выбирает минимальные версии, удовлетворяющие ограничениям, поэтому сборка детерминирована, а обновления происходят только когда вы явно двигаете baseline. У каждого подключённого реестра — свой baseline.
