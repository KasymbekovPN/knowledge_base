# Реестры (registries)

Реестр (registry) — это источник, из которого vcpkg берёт порты (рецепты сборки библиотек). До сих пор мы неявно пользовались одним — встроенным. Теперь разберём, что реестры бывают разные, зачем подключать дополнительные и как собрать собственный приватный.

## Зачем вообще нужны несколько реестров

Встроенного реестра (репозитория microsoft/vcpkg) хватает для open-source библиотек. Но в реальной работе возникают потребности, которые он не покрывает:

- **Внутренние/проприетарные библиотеки** компании, которых нет и не будет в публичном реестре.
- **Форки или пропатченные версии** публичных библиотек под нужды проекта.
- **Контроль и изоляция**: организация хочет держать свой курируемый набор портов, не завися напрямую от публичного репозитория.
- **Версии, которых нет** в текущем встроенном реестре.

Решение — подключить дополнительный реестр со своими портами, не теряя доступа к публичному.

## Типы реестров

vcpkg поддерживает несколько видов источников (поле `kind`):

|Тип (`kind`)|Что это|Когда|
|---|---|---|
|`builtin`|Встроенный реестр (репозиторий vcpkg, на который указывает `VCPKG_ROOT`)|Стандартные публичные порты|
|`git`|Любой git-репозиторий с портами в нужной структуре|Приватные/корпоративные реестры, форки|
|`filesystem`|Локальный каталог с портами|Локальная разработка, тесты, моно-репозитории|

Самый распространённый для приватных нужд — `git`.

## Файл конфигурации: `vcpkg-configuration.json`

Подключение реестров описывается не в `vcpkg.json`, а в отдельном файле **`vcpkg-configuration.json`** рядом с ним. Разделение логичное: `vcpkg.json` — _что_ нужно проекту (зависимости), `vcpkg-configuration.json` — _откуда_ это брать (источники).

```
shapes-demo/
├── vcpkg.json                  ← какие зависимости
├── vcpkg-configuration.json    ← откуда их брать (реестры)
├── CMakeLists.txt
└── ...
```

Базовая структура:

```json
{
  "default-registry": {
    "kind": "builtin",
    "baseline": "9f02c5cb4c3f3a4a0a8c9e2b1d6f7e8a9b0c1d2e"
  },
  "registries": [
    {
      "kind": "git",
      "repository": "https://github.com/my-org/vcpkg-registry",
      "baseline": "a1b2c3d4e5f6...",
      "packages": [ "my-lib", "my-other-lib" ]
    }
  ]
}
```

Разберём части.

### `default-registry`

Реестр «по умолчанию» — куда vcpkg идёт за любым портом, который не закреплён явно за другим реестром. Обычно это встроенный реестр со своим baseline. Можно задать `null`, чтобы вообще запретить дефолтный источник (тогда каждый пакет должен явно принадлежать какому-то реестру из `registries`).

### `registries`

Массив дополнительных реестров. Ключевое поле каждого — **`packages`**: список портов, за которые этот реестр отвечает. То есть маршрутизация по имени пакета: «`my-lib` бери отсюда, остальное — из default».

- `kind` — тип (`git` / `filesystem` / `builtin`).
- `repository` — URL git-репозитория (для `git`).
- `path` — путь к каталогу (для `filesystem`).
- `baseline` — снимок версий этого реестра (у каждого реестра свой baseline, как обсуждали в пункте про версионирование).
- `packages` — какие порты обслуживает этот реестр.

## Как vcpkg выбирает, откуда брать пакет

Логика маршрутизации:

1. Для каждого требуемого пакета vcpkg смотрит, упомянут ли он в `packages` какого-либо реестра из `registries`.
2. Если да — берёт порт из этого реестра (с его baseline).
3. Если нет — берёт из `default-registry`.

Это позволяет переопределять даже публичные порты: если в вашем git-реестре есть порт `fmt` и он указан в `packages`, ваш форк `fmt` «победит» публичный.

## Создание собственного git-реестра

Приватный реестр — это git-репозиторий с определённой структурой. Минимально нужны три вещи: каталог портов, база версий и baseline.

### Структура репозитория реестра

```
my-vcpkg-registry/
├── ports/
│   └── my-lib/
│       ├── portfile.cmake     ← как собрать
│       └── vcpkg.json         ← метаданные порта
└── versions/
    ├── baseline.json          ← текущие версии всех портов реестра
    └── m-/
        └── my-lib.json        ← история версий порта my-lib
```

Это та же структура, что у официального реестра vcpkg, в миниатюре:

- **`ports/<имя>/`** — сам порт (рецепт), как мы видели в структуре каталогов vcpkg.
- **`versions/baseline.json`** — baseline: какие версии портов считать актуальными.
- **`versions/<буква>-/<имя>.json`** — история версий конкретного порта с привязкой к git-деревьям.

### `versions/baseline.json`

```json
{
  "default": {
    "my-lib": { "baseline": "1.0.0", "port-version": 0 }
  }
}
```

### `versions/m-/my-lib.json`

Связывает версии порта с конкретными git-деревьями (`git-tree` — хеш дерева, а не коммита):

```json
{
  "versions": [
    {
      "version": "1.0.0",
      "port-version": 0,
      "git-tree": "<хеш-git-tree-каталога-порта>"
    }
  ]
}
```

### Инструмент для ведения базы версий

Заполнять `versions/` вручную тяжело и ошибкоопасно. vcpkg даёт команду, которая генерирует/обновляет записи версий из текущего состояния `ports/`:

```bash
# из корня репозитория реестра
git add ports/my-lib
git commit -m "Add my-lib port"

vcpkg --x-builtin-ports-root=./ports \
      --x-builtin-registry-versions-dir=./versions \
      x-add-version my-lib
```

Команда `x-add-version` вычисляет git-tree порта и добавляет запись в `versions/m-/my-lib.json` и в `baseline.json`. После этого делается ещё один коммит с обновлённой базой версий.

Типичный цикл публикации новой версии порта в своём реестре:

1. Изменили `ports/my-lib/` (новая версия в `vcpkg.json` порта).
2. Закоммитили изменения порта.
3. Запустили `x-add-version my-lib`.
4. Закоммитили обновлённую `versions/`.

## Подключение приватного реестра к проекту

В `vcpkg-configuration.json` проекта:

```json
{
  "default-registry": {
    "kind": "builtin",
    "baseline": "9f02c5cb..."
  },
  "registries": [
    {
      "kind": "git",
      "repository": "https://github.com/my-org/my-vcpkg-registry",
      "baseline": "<хеш-коммита-реестра>",
      "packages": [ "my-lib" ]
    }
  ]
}
```

А в `vcpkg.json` пакет используется как любой другой:

```json
{
  "name": "shapes-demo",
  "version": "0.1.0",
  "dependencies": [ "fmt", "my-lib" ],
  "builtin-baseline": "9f02c5cb..."
}
```

vcpkg увидит, что `my-lib` числится за git-реестром, и возьмёт порт оттуда; `fmt` придёт из встроенного реестра. Приватный git-репозиторий требует доступа — для CI настраивается через токены/SSH-ключи (HTTPS с токеном или git credential helper).

`baseline` git-реестра — это хеш коммита **репозитория реестра**, в котором есть корректная `versions/baseline.json`. Получить его так же, как для встроенного: `git rev-parse HEAD` в репозитории реестра.

## Filesystem-реестр (локальный)

Для локальной разработки или моно-репозитория удобен `filesystem`-реестр — порты лежат в каталоге, без отдельного git-репозитория:

```json
{
  "registries": [
    {
      "kind": "filesystem",
      "path": "./local-registry",
      "baseline": "default",
      "packages": [ "my-lib" ]
    }
  ]
}
```

Структура каталога та же (`ports/`, `versions/`), но источник — локальная папка. Удобно для быстрой итерации над собственным портом перед публикацией в git-реестр.

## Реестры vs overlay ports

Есть похожий, но более простой механизм — **overlay ports** (его коснёмся в продвинутом пункте). Разница:

- **Overlay ports** — просто папка с портами, подсунутая через `--overlay-ports`/`VCPKG_OVERLAY_PORTS`. Без версионирования, без baseline. Быстро, но не воспроизводимо «из коробки». Хорошо для разовых патчей и экспериментов.
- **Registry** — полноценный источник с базой версий и baseline. Воспроизводимо, версионируемо, подходит для командной работы и CI.

Грубо: overlay — «черновик/латка», registry — «production-источник».

## Связь нашего примера

Для shapes-demo, если бы `Point`/`Rect` выросли в отдельную внутреннюю библиотеку `shapes-core`, её можно было бы оформить портом в приватном git-реестре организации и подключать так же, как `fmt`:

```json
// vcpkg.json
"dependencies": [ "fmt", "shapes-core" ]
```

```json
// vcpkg-configuration.json
"registries": [
  {
    "kind": "git",
    "repository": "https://github.com/my-org/vcpkg-registry",
    "baseline": "...",
    "packages": [ "shapes-core" ]
  }
]
```

Это естественный мостик к следующему пункту — **созданию собственных портов**, ведь чтобы положить `shapes-core` в реестр, нужен корректный порт.

## Что запомнить

Реестр — источник портов. Встроенный (`builtin`) даёт публичные библиотеки; дополнительные реестры (`git`, `filesystem`) подключаются через `vcpkg-configuration.json` и обслуживают перечисленные в `packages` пакеты. Каждый реестр имеет свой baseline (воспроизводимость сохраняется). Собственный git-реестр — это репозиторий со структурой `ports/` + `versions/`, версии в котором ведутся командой `x-add-version`. Для лёгких разовых случаев есть overlay ports, для командного production — полноценные реестры.
