# Философия команд: GDB vs LLDB

## Исторический контекст

**GDB** (1986, GNU Project) — родился в эпоху командных Unix-интерфейсов, синтаксис команд ориентирован на **краткость и мнемонику** в стиле классических Unix-утилит (`bt`, `si`, `ni`).

**LLDB** (2010-е, Apple/LLVM) — создавался позже, с явной целью интеграции в **Xcode IDE**, поэтому команды структурированы по принципу `<noun> <verb> --flags`, похоже на git-подобный CLI (`git commit -m`, `git branch -d`) — предсказуемо и единообразно, но многословнее.

## Ключевое структурное отличие

| |GDB|LLDB|
|---|---|---|
|Паттерн команд|Глагол/аббревиатура|`noun verb --flag value`|
|Пример: breakpoint|`break main.cpp:26`|`breakpoint set --file main.cpp --line 26`|
|Пример: удалить breakpoint|`delete 1`|`breakpoint delete 1`|
|Пример: список breakpoint'ов|`info breakpoints`|`breakpoint list`|
|Автодополнение команд|Частичное совпадение по началу слова|Более строгая структура namespace'ов|

GDB-подход — это "запомни специфичное слово для каждого действия" (`break`, `watch`, `catch`, `tbreak` — все разные корни).

LLDB-подход — "структурируй как объект.метод": `breakpoint set/delete/list/disable`, `watchpoint set/delete/list`, `target create/delete` — единообразная grammar, легче предсказать команду, даже если её раньше не видел.

## Совместимость через алиасы — практическая деталь

LLDB **сознательно** добавил алиасы под привычные GDB-команды, чтобы не отпугивать пользователей, годами работавших с GDB:

```
(lldb) break main.cpp:26      ← алиас для breakpoint set --file ... --line ...
(lldb) b main.cpp:26          ← ещё короче
(lldb) bt                     ← алиас для thread backtrace
(lldb) r                      ← алиас для process launch / run
(lldb) c                      ← алиас для process continue
(lldb) n / s                  ← next / step, как в GDB
```

Именно поэтому в наших примерах выше `lldb` понимал и `break coro_demo.cpp:46`, и `bt` — это не "LLDB тоже так умеет от природы", а специально встроенная **совместимая обёртка** поверх "родной" философии `breakpoint set --file ...`.

## Практическое следствие для тебя

Раз ты одинаково активно работаешь и с Linux (WSL/Docker), и с Windows (MinGW/MSVC) — держи в голове три уровня владения LLDB:

1. **Минимальный** — используешь GDB-алиасы (`break`, `bt`, `c`, `r`, `n`, `s`) — работает почти всегда, переносишь привычки из GDB один в один
2. **Продвинутый** — переходишь на "родной" синтаксис `breakpoint set --file X --line Y --condition "i > 5"` — так доступны флаги, которых у алиасов может не быть (например, условные breakpoints через `--condition` вместо GDB-стиля `break X if cond`)
3. **Скриптовый** — Python API LLDB (`script`, кастомные команды) — тут разница философий проявляется сильнее всего, но это уже отдельная большая тема

## Небольшой нюанс, который может сбить с толку

GDB-алиасы в LLDB **не покрывают 100% функциональности** родных LLDB-команд. Например:

```
(lldb) break set -f main.cpp -l 26 -c "i == 5"   ← условный breakpoint через флаг
```

но краткий GDB-style алиас `break main.cpp:26 if i == 5` **не сработает** — такого синтаксиса алиас не поддерживает. Если что-то не получается через привычный GDB-синтаксис — это первый признак, что нужно перейти на "родной" LLDB grammar с явными флагами.

## Итоговая интуиция

- **GDB** — "выучи вокабуляр команд" (как выучить неправильные глаголы)
- **LLDB** — "выучи грамматику `noun verb --flag`" (как выучить правило, которое применяется системно)

Для разового использования GDB-алиасы в LLDB закроют 90% твоих потребностей. Для глубокой автоматизации (скрипты, кастомные команды, Python-биндинги) выгоднее сразу привыкать к "родному" LLDB-синтаксису — он более предсказуем и документирован именно в этой форме.
