## `Send`/`Sync` — фундамент "fearless concurrency"

Прежде чем к потокам — это те два трейта, на которых держится вся многопоточная безопасность Rust, и они уже несколько раз мелькали (в примерах с `Rc`, `RefCell`).

```rust
fn is_send<T: Send>() {}
fn is_sync<T: Sync>() {}

is_send::<i32>();       // OK
is_send::<Arc<i32>>();  // OK
is_send::<Mutex<i32>>(); // OK
// is_send::<Rc<i32>>(); // ОШИБКА -- Rc не Send

is_sync::<Mutex<i32>>(); // OK
// is_sync::<RefCell<i32>>(); // ОШИБКА -- RefCell не Sync
```

- **`Send`** — тип можно безопасно **передать** (переместить владение) в другой поток.
- **`Sync`** — тип можно безопасно **разделять** через `&T` между потоками одновременно (формально: `T: Sync` ⟺ `&T: Send`).

Оба трейта — **маркерные** (без методов), и почти всегда выводятся компилятором автоматически: структура `Send`, если все её поля `Send`. Ты никогда не видел этих трейтов явно в наших примерах раньше, потому что они работают в фоне на каждом вызове `thread::spawn` — сигнатура `spawn` требует `F: Send`, и если внутри замыкания оказался, например, `Rc`, компиляция просто падает **до того**, как гонка данных вообще стала бы возможна. В C++ ничего подобного нет: `std::thread` принимает любой callable, и ответственность за то, что захваченные данные потокобезопасны, целиком на программисте — TSan (ThreadSanitizer) находит такие баги только в рантайме, при реальном срабатывании гонки.

## `thread::spawn` — базовый API

```rust
let handle = thread::spawn(|| {
    let mut sum = 0;
    for i in 1..=100 { sum += i; }
    sum // возвращаемое значение доступно через join()
});

println!("основной поток продолжает работать");
let result = handle.join().unwrap();
println!("результат из потока: {result}"); // 5050
```

`JoinHandle<T>` — типизированная ручка на поток, где `T` — тип возвращаемого значения замыкания. `.join()` блокирует текущий поток до завершения и возвращает `Result<T, Box<dyn Any + Send>>` — `Err`, если поток запаниковал (уже разбирали это подробно в теме про `panic!`). Аналог `std::thread::join()` в C++, только там `join()` ничего не возвращает — если нужно значение из потока, приходится вручную городить `promise`/`future` или общую переменную под мьютексом.

## `move`-замыкание — обязателен для данных, не удовлетворяющих `'static`

```rust
let local = String::from("локальные данные");
let handle = thread::spawn(|| {
    println!("{local}"); // ОШИБКА без move
});
```

Ошибка:

```
error[E0373]: closure may outlive the current function, but it borrows `local`
note: function requires argument type to outlive `'static`
```

Это прямое продолжение темы про замыкания и lifetime: `thread::spawn` требует `'static` замыкание, потому что поток может пережить функцию, из которой был запущен — компилятор физически не может гарантировать, что `local` доживёт до момента, когда поток реально решит её прочитать. `move` решает это, перемещая владение `local` внутрь потока:

```rust
let data = vec![1, 2, 3];
thread::spawn(move || {
    println!("данные внутри потока: {data:?}");
});
```

## `thread::scope` — способ обойти требование `'static`, безопасно

Это относительно новая (стабилизирована в 1.63) и очень практичная фича, прямого аналога которой в C++ до `std::jthread`+`std::latch` вручную попросту нет:

```rust
let data = vec![1, 2, 3, 4, 5];

thread::scope(|s| {
    s.spawn(|| {
        println!("поток 1 видит: {:?}", &data[..2]);
    });
    s.spawn(|| {
        println!("поток 2 видит: {:?}", &data[2..]);
    });
}); // здесь гарантированно ВСЕ scoped-потоки уже завершены

println!("data всё ещё доступна в main: {data:?}");
```

Вывод:

```
поток 1 видит: [1, 2]
поток 2 видит: [3, 4, 5]
data всё ещё доступна в main: [1, 2, 3, 4, 5]
```

`thread::scope` даёт компилятору **гарантию**, что все `s.spawn`-потоки завершатся до выхода из блока `scope` (это встроено в саму сигнатуру функции, не соглашение) — поэтому можно заимствовать `&data` **без** `move`/`'static`, никакого `Arc` не требуется вообще. Это устраняет самый частый источник фрустрации новичка: "хочу расшарить локальный массив между несколькими потоками для параллельной обработки, а компилятор требует `'static`" — раньше единственным решением было оборачивать в `Arc`, теперь `thread::scope` — идиоматичный ответ, если время жизни потоков заведомо ограничено текущей функцией.

## `JoinHandle` НЕ джойнится автоматически — важное отличие от C++20 `jthread`

```rust
let handle = thread::spawn(|| {
    thread::sleep(Duration::from_millis(200));
    println!("поток проснулся и допечатал это ПОСЛЕ конца main, если main не подождал");
});
drop(handle); // не вызвали join() -- поток "отсоединяется"
println!("main продолжает и завершается, не дожидаясь поток");
thread::sleep(Duration::from_millis(400));
```

Вывод:

```
main продолжает и завершается, не дожидаясь поток
поток проснулся и допечатал это ПОСЛЕ конца main, если main не подождал
```

Проверил на практике: `drop(handle)` без `.join()` — поток **не** останавливается и не блокирует ничего, он просто продолжает выполняться в фоне ("detached"), независимо от родительского потока. Это отличается от `std::jthread` (C++20), который **автоматически джойнится** в своём деструкторе — забыл вызвать `.join()` на обычном `std::thread` в C++ до C++20 — падение программы через `std::terminate`, если поток ещё жив к моменту разрушения объекта. `JoinHandle` в Rust ведёт себя как классический `std::thread` (pre-C++20): если не хочешь detached-поведения — обязан вызвать `.join()` сам, забыть об этом не вызовет ни ошибки компиляции, ни паники, просто поток продолжит жить сам по себе.

## `Mutex<T>` — данные и блокировка неразделимы

Мы уже видели `Mutex` в теме про `panic!` (отравление), но не разбирали его как основную конструкцию:

```rust
use std::sync::{Arc, Mutex};

let counter = Arc::new(Mutex::new(0));
let mut handles = vec![];

for _ in 0..10 {
    let counter = Arc::clone(&counter);
    handles.push(thread::spawn(move || {
        let mut guard = counter.lock().unwrap();
        *guard += 1;
    })); // guard дропается здесь -- разблокировка автоматическая
}

for h in handles { h.join().unwrap(); }
println!("итог: {}", *counter.lock().unwrap()); // 10, гарантированно
```

Прогнал 10 потоков, каждый инкрементирует общий счётчик — итог ровно **10**, без гонки данных. Ключевое структурное отличие от C++: в `std::mutex` данные и блокировка — **раздельные** сущности (мьютекс сам по себе, защищаемые данные — отдельно, связь между ними держится только в голове программиста и в комментарии рядом):

```cpp
std::mutex m;
int counter = 0; // НИЧТО не мешает прочитать/записать counter, забыв взять m
```

В Rust `Mutex<T>` **физически оборачивает** данные — единственный способ добраться до `i32` внутри — это `.lock()`, который возвращает `MutexGuard<T>` (`Deref`/`DerefMut` до `T`, тот же механизм, что у `Box`). Прочитать/записать данные без блокировки **невозможно синтаксически** — компилятор не даст. Это устраняет целый класс багов "забыл взять лок перед доступом к общим данным", которые в C++ ловятся только дисциплиной программиста или TSan в рантайме.

`MutexGuard` разблокирует мьютекс в своём `Drop` — прямой аналог `std::lock_guard`/`std::unique_lock` в C++ (RAII-паттерн, уже давно знакомый), только тут это **единственный** способ работы с `Mutex`, а не опциональная best practice поверх raw `lock()`/`unlock()`.

## `RwLock<T>` — много читателей ИЛИ один писатель

```rust
use std::sync::{Arc, RwLock};

let data = Arc::new(RwLock::new(vec![1, 2, 3]));

// несколько читателей одновременно -- разрешено
for i in 0..3 {
    let data = Arc::clone(&data);
    thread::spawn(move || {
        let guard = data.read().unwrap();
        println!("читатель {i}: {:?}", *guard);
    });
}

// один писатель -- эксклюзивный доступ
{
    let mut guard = data.write().unwrap();
    guard.push(4);
}
println!("после записи: {:?}", *data.read().unwrap()); // [1, 2, 3, 4]
```

`.read()` даёт `RwLockReadGuard` (много одновременно, как `&T`), `.write()` даёт `RwLockWriteGuard` (эксклюзивно, как `&mut T`) — это буквально тот же принцип "N читателей XOR 1 писатель", который мы разбирали для borrow checker'а на этапе компиляции, только теперь применённый в рантайме между потоками. Прямой аналог — `std::shared_mutex` + `std::shared_lock`/`std::unique_lock` (C++17), тот же API-паттерн, только опять же — в Rust данные физически внутри `RwLock<T>`, а не рядом с ним.

**Практический выбор Mutex vs RwLock:** если чтений сильно больше, чем записей, и критическая секция достаточно длинная, чтобы оправдать overhead RwLock (он сложнее и чуть дороже Mutex на быстрых операциях) — `RwLock`. Если доступ в основном короткий и/или запись и чтение примерно поровну — обычно проще и быстрее `Mutex`.

## `Arc<Mutex<T>>` — прямая параллель с `Rc<RefCell<T>>` из прошлой темы

Стоит явно провести эту связь, раз мы только что закрыли `Rc<RefCell<T>>`:

|Однопоточный мир|Многопоточный мир|
|---|---|
|`Rc<RefCell<T>>`|`Arc<Mutex<T>>` (или `Arc<RwLock<T>>`)|
|Разделяемое владение|Разделяемое владение|
|Мутация через `&self`|Мутация через `&self`|
|Проверка правил в рантайме (счётчик)|Проверка через блокировку (ОС/атомик)|
|Нарушение → `panic!`|Нарушение невозможно — поток просто ждёт (блокируется)|

Это одна и та же архитектурная идея ("разделяемое владение + internal mutability"), просто с разной ценой и разными гарантиями в зависимости от того, нужна ли тебе многопоточность.

## `mpsc` — каналы, message passing вместо общей памяти

Это уже другая парадигма конкурентности — вместо "расшарить данные под блокировкой" (shared memory), потоки общаются, **посылая сообщения** друг другу (message passing, философия Go/Erlang, которую Rust тоже поддерживает нативно в std).

```rust
use std::sync::mpsc;

let (tx, rx) = mpsc::channel();

thread::spawn(move || {
    for i in 1..=5 {
        tx.send(i).unwrap();
        thread::sleep(Duration::from_millis(10));
    }
    // tx выходит из scope здесь -- канал закрывается
});

for received in rx { // rx работает как итератор
    println!("получено: {received}");
}
println!("канал закрыт, все сообщения получены");
```

Вывод:

```
получено: 1
получено: 2
получено: 3
получено: 4
получено: 5
канал закрыт, все сообщения получены
```

`mpsc` = **m**ultiple **p**roducer, **s**ingle **c**onsumer — много `Sender`'ов (`tx`), ровно один `Receiver` (`rx`). `for received in rx` работает, потому что `Receiver` реализует `Iterator` — итерация автоматически завершается, когда **все** `Sender`'ы, ассоциированные с этим каналом, оказались дропнуты (здесь — единственный `tx`, который вышел из scope внутри потока после цикла).

### Несколько производителей — клонирование `Sender`

```rust
let (tx, rx) = mpsc::channel();

for producer_id in 0..3 {
    let tx = tx.clone(); // Sender: Clone -- каждый поток получает свою копию
    thread::spawn(move || {
        tx.send(format!("сообщение от producer {producer_id}")).unwrap();
    });
}
drop(tx); // ВАЖНО: дропнуть оригинальный tx, иначе rx будет ждать вечно

let received: Vec<String> = rx.iter().collect();
```

Обрати внимание на `drop(tx)` после цикла — частая ловушка для новичков: если оригинальный `tx` (не клонированный) остаётся живым (например, держится в переменной до конца `main`), receiver **никогда** не узнает, что "больше отправителей не будет", и итерация по `rx` заблокируется навечно, ожидая сообщений, которые никогда не придут.

### `recv()` после закрытия канала — `Err`, не паника и не вечное ожидание

```rust
let (tx2, rx2) = mpsc::channel::<i32>();
drop(tx2);
match rx2.recv() {
    Ok(v) => println!("получено: {v}"),
    Err(e) => println!("канал закрыт: {e}"),
}
```

Вывод: `канал закрыт: receiving on a closed channel`. Закрытие канала — это `Result`, обрабатываемый штатно через `match`, а не исключительная ситуация — тот же принцип "ожидаемая ошибка — это `Result`", что мы разбирали в теме про `Result`/`?`.

### C++ параллель — прямого стандартного эквивалента нет

В C++ до сих пор **нет** канала в стандартной библиотеке (ни в C++20, ни в C++23) — ближайшие практические аналоги: вручную собранная очередь на `std::queue` + `std::mutex` + `std::condition_variable` (десяток строк бойлерплейта на каждый канал), либо сторонние библиотеки (`boost::lockfree::queue`, `moodycamel::ConcurrentQueue`). `mpsc::channel()` в Rust — это то, что в C++ приходится либо писать самому, либо тянуть внешнюю зависимость, здесь встроено в `std` с первого релиза, потому что message-passing — один из основных идиоматичных способов писать конкурентный код в Rust, а не нишевый паттерн.

## Сводная таблица

| Задача                                         | C++                                                                | Rust                                                    |
| ---------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------- |
| Запуск потока                                  | `std::thread`                                                      | `thread::spawn`                                         |
| Авто-join при выходе из scope                  | `std::jthread` (C++20)                                             | Нет — нужен явный `.join()`, иначе detach               |
| Заимствование локальных данных потоком         | Ручная синхронизация жизни (`join()` до конца scope) + `&`/UB риск | `thread::scope` — гарантия компилятора                  |
| Захват потокобезопасности замыкания            | Не проверяется компилятором                                        | `Send`/`Sync` bounds на `spawn`, проверяется статически |
| Взаимное исключение                            | `std::mutex` + `std::lock_guard`/`unique_lock`, данные отдельно    | `Mutex<T>`, данные внутри — доступ невозможен без лока  |
| Множественные читатели / один писатель         | `std::shared_mutex` + `shared_lock`/`unique_lock`                  | `RwLock<T>`                                             |
| Разделяемое изменяемое состояние               | `shared_ptr<T>` + `mutex` вручную                                  | `Arc<Mutex<T>>` / `Arc<RwLock<T>>`                      |
| Message passing между потоками                 | Нет в std — вручную или сторонние библиотеки                       | `mpsc::channel`                                         |
| Несколько производителей в канал               | Ручная реализация                                                  | `Sender: Clone`                                         |
| Гонка данных при обычном использовании std API | Возможна, ловится только TSan в рантайме                           | Предотвращается компилятором (`Send`/`Sync`)            |
