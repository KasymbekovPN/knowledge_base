## Добавление зависимостей — `cargo add` вместо ручного редактирования

```bash
cargo add serde --features derive
```

```
    Adding serde v1.0.229 to dependencies.
             Features:
             + derive
             + serde_derive
             + std
```

Автоматически дописывает в `Cargo.toml`:

```toml
[dependencies]
serde = { version = "1.0.229", features = ["derive"] }
```

Это прямой аналог `vcpkg add port serde` (в manifest-режиме) — только `cargo add` сразу резолвит и записывает **последнюю совместимую** версию, без отдельного шага `vcpkg install`.

## Semver-требования — синтаксис версий в `Cargo.toml`

|Запись|Значение|Допустимые версии|
|---|---|---|
|`"1.2.3"` или `"^1.2.3"`|Caret (по умолчанию)|`>=1.2.3, <2.0.0`|
|`"~1.2.3"`|Tilde|`>=1.2.3, <1.3.0`|
|`"=1.2.3"`|Точная версия|Только `1.2.3`|
|`"*"`|Любая|Не рекомендуется — непредсказуемо|
|`">=1.2, <1.5"`|Явный диапазон|`1.2.x`–`1.4.x`|

Caret (`^`, дефолт) — самое частое: "не ломай совместимость по semver" — для `0.x.y` версий (до 1.0) действует по-другому: `^0.2.3` означает `>=0.2.3, <0.3.0` (minor трактуется как breaking до первого мажорного релиза) — это тонкость semver, которую vcpkg-порты не формализуют так же строго, там версии просто фиксируются в baseline без встроенной семантики "что считается breaking".

## Разрешение версий и `Cargo.lock` — обновление точечно, не всем скопом

```bash
cargo update -p rayon-core --precise 1.11.0
```

Мы использовали это множество раз в разговоре для фиксации совместимых версий под старый rustc — это ровно та операция, которую делаешь, когда обнаруживаешь несовместимость: не трогаешь весь `Cargo.lock`, а точечно откатываешь/фиксируешь **одну** транзитивную зависимость, сохраняя всё остальное как есть. Прямая параллель — `vcpkg install package --version=X` или ручная правка `builtin-baseline` под конкретный порт в `vcpkg-configuration.json`, только без отдельного шага пересборки всего дерева портов.

## `cargo tree` — визуализация графа, поиск дублирующихся версий

Собрал реальный конфликт: добавил старый `clap@3` с фичей `derive`, который тянет `syn v1`, при том что `serde`/`thiserror` в этом же проекте уже используют `syn v3`:

```bash
cargo tree -d
```

```
syn v1.0.109
├── clap_derive v3.2.25 (proc-macro)
│   └── clap v3.2.25
│       └── deps_demo v0.1.0

syn v3.0.5
├── serde_derive v1.0.229 (proc-macro)
│   └── serde v1.0.229
│       └── deps_demo v0.1.0
└── thiserror-impl v2.0.20 (proc-macro)
    └── thiserror v2.0.20
        └── deps_demo v0.1.0
```

`-d`/`--duplicates` явно показывает, что `syn` присутствует в дереве **двумя разными мажорными версиями** одновременно. Это не ошибка — Cargo **разрешает** множественным версиям одного крейта сосуществовать в графе (в отличие от классического "одна версия на всё дерево" во многих других экосистемах) — просто раздувает время компиляции и размер бинарника, так как обе версии реально компилируются и линкуются. `cargo tree -d` — стандартный способ найти такие случаи и решить, стоит ли их убирать (обновлением зависимости, которая тянет устаревшую версию).

После удаления `clap` дерево снова чистое: `warning: nothing to print` для `-d` — дублей нет.

**Параллель с vcpkg:** vcpkg классически требует **одну** версию порта на весь граф зависимостей (нельзя, чтобы два порта в одном installation тянули разные версии одной библиотеки) — конфликт версий там **ошибка сборки**, а не то, что тихо разрешается. Cargo терпимее именно потому, что Rust-крейты обычно статически линкуются и не создают ODR-подобных проблем при дублировании (в отличие от C++ библиотек, где две версии одной .so/.lib в одном бинарнике почти всегда катастрофа).

## Виды зависимостей — три отдельные секции

```toml
[dependencies]      # линкуется в финальный артефакт
[dev-dependencies]  # только для тестов/примеров/бенчмарков (criterion, rstest — уже видели)
[build-dependencies] # только для build.rs (cc — уже видели)
```

Уже сталкивался с этим на практике во всех прошлых примерах — стоит явно свести это в одно место: `dev-dependencies` не попадают в зависимости твоей библиотеки, когда её кто-то использует (в отличие от vcpkg, где обычно нет встроенного разделения "зависимости для тестов" на уровне манифеста — приходится либо ставить их отдельно, либо городить через feature-подобные конструкции).

## crates.io — публикация своего крейта

```bash
cargo login <token>       # один раз, токен из аккаунта на crates.io
cargo package             # собрать .crate локально и проверить, что упаковка валидна
cargo publish             # опубликовать -- необратимо для конкретной версии
```

Ключевые правила crates.io, которых нет у vcpkg (там нет центрального публичного реестра в том же смысле — используется git-based модель портов):

- **Версии неизменяемы.** Опубликованная `1.2.3` никогда не может быть переопубликована с другим содержимым — только новая версия.
- **`cargo yank`** — "отозвать" версию (пометить как не рекомендуемую к новым установкам), но **не удалить** — существующие проекты, у которых она уже зафиксирована в `Cargo.lock`, продолжат собираться. Это мягче, чем полное удаление, и специально спроектировано так, чтобы не ломать чужие сборки задним числом.
- **docs.rs** — автоматически генерирует и хостит документацию (`cargo doc`) для **каждой** опубликованной версии каждого крейта, без каких-либо действий автора — прямая противоположность ручной публикации Doxygen-документации, которую приходится самому куда-то заливать.
- **Единый централизованный реестр** (как npm) — в отличие от vcpkg, где `ports/` — это git-репозиторий с рецептами сборки из исходников, а не централизованный хостинг пакетов как таковой.

## Проверка безопасности — `cargo audit`, аналог сканирования supply chain в vcpkg-мире

```bash
cargo install cargo-audit
cargo audit
```

Сверяет `Cargo.lock` с базой известных уязвимостей (RustSec Advisory Database) — концептуальный аналог сканирования CVE для зависимостей, которым в C++/vcpkg-мире обычно занимаются отдельные инструменты (OWASP Dependency-Check и подобные, не встроенные в сам vcpkg).

## Сводная таблица: Cargo vs vcpkg в управлении зависимостями

| |vcpkg|Cargo|
|---|---|---|
|Модель распространения|Git-based порты, сборка из исходников|Централизованный реестр (crates.io), тоже сборка из исходников|
|Версионирование|Baseline + overlay-порты|Semver-диапазоны в `Cargo.toml` + точная фиксация в `Cargo.lock`|
|Несколько версий одной зависимости одновременно|Обычно запрещено/конфликт|Разрешено, отслеживается `cargo tree -d`|
|Публикация своего пакета|Свой порт в overlay/registry (ручной процесс)|`cargo publish` — секунды, глобально видно всем|
|Откат опубликованной версии|Правка/удаление порта в своём registry|`cargo yank` — версия помечена, но не удаляется|
|Автогенерация документации|Нет из коробки|docs.rs — автоматически для каждой версии|
|Разделение test/build/runtime зависимостей|Нет явного механизма на уровне манифеста|`[dependencies]`/`[dev-dependencies]`/`[build-dependencies]`|
|Сканирование уязвимостей|Внешние инструменты|`cargo audit` (RustSec)|
|Точечное обновление одной транзитивной зависимости|Ручная правка baseline/overlay|`cargo update -p X --precise Y`|
