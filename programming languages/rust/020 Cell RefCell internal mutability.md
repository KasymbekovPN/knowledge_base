## Проблема, которую решают `Cell`/`RefCell` — internal mutability

**Internal mutability** (внутренняя изменяемость) — это паттерн проектирования в языке Rust, который **позволяет изменять данные даже при наличии неизменяемых (разделяемых) ссылок `&T` на них**.

Уже упоминал это мельком в теме про "классы" (в контексте `mutable` из C++) и только что столкнулись с ней на практике в примере с циклом `Rc`. Формулировка проблемы: у тебя `&T` (неизменяемая ссылка/владелец), но нужно изменить данные внутри. По обычным правилам borrow checker'а это невозможно — `&T` даёт только чтение. `Cell`/`RefCell` — это два способа легально обойти это ограничение, каждый — своей ценой.

## `Cell<T>` — для `Copy`-типов, вообще без проверок в рантайме

```rust
use std::cell::Cell;

struct Counter {
    count: Cell<i32>,
}

impl Counter {
    fn increment(&self) { // &self, НЕ &mut self!
        self.count.set(self.count.get() + 1);
    }
}

let c = Counter { count: Cell::new(0) };
c.increment();
c.increment();
c.increment();
println!("{}", c.count.get()); // 3
```

Ключевой трюк `Cell`: он **никогда не выдаёт ссылку** на то, что внутри — только `.get()` (копирует значение наружу) и `.set()` (кладёт новое значение внутрь), `.replace()` (кладёт новое, отдаёт старое). Раз ссылок наружу вообще не существует, invariant "либо N читателей, либо 1 писатель" физически невозможно нарушить — некому его нарушать, поэтому **никакой проверки в рантайме не требуется вообще**, `Cell` — это просто безопасная обёртка вокруг `UnsafeCell` с нулевым overhead поверх обычного присваивания. Это самый дешёвый вид internal mutability, но применим только к типам, которые дёшево копируются (`Copy`) — для `String`/`Vec` он тоже технически компилируется (`Cell<T>` не требует `T: Copy` для `set`, только для некоторых удобных методов), но `.get()` для не-`Copy` типа просто не скомпилируется, потому что копировать нечем.

## `RefCell<T>` — для любых типов, с проверкой в рантайме

```rust
use std::cell::RefCell;

struct Log {
    messages: RefCell<Vec<String>>,
}

impl Log {
    fn add(&self, msg: &str) { // тоже &self, не &mut self
        self.messages.borrow_mut().push(msg.to_string());
    }
    fn print_all(&self) {
        for m in self.messages.borrow().iter() {
            println!("{m}");
        }
    }
}

let log = Log { messages: RefCell::new(Vec::new()) };
log.add("первое");
log.add("второе");
log.print_all();
```

Вывод:

```
первое
второе
```

`RefCell` **выдаёт настоящие ссылки** (`.borrow()` → `Ref<T>`, ведёт себя как `&T`; `.borrow_mut()` → `RefMut<T>`, ведёт себя как `&mut T`), поэтому правило "1 writer XOR N readers" всё ещё должно соблюдаться — но, поскольку компилятор не может проверить это статически (мы же обошли обычный borrow checker через `&self` вместо `&mut self`), `RefCell` отслеживает это **сам, в рантайме**, через внутренний счётчик активных заимствований.

## Что случается при нарушении правила — паника, не ошибка компиляции

```rust
let cell = RefCell::new(5);
let b1 = cell.borrow_mut();
println!("держим b1 = {b1}");
let b2 = cell.borrow_mut(); // ПАНИКА
println!("{b2}");
```

Вывод:

```
держим b1 = 5
thread 'main' panicked at refcell2.rs:8:19:
already borrowed: BorrowMutError
```

Это ключевое отличие `RefCell` от обычного borrow checker'а: то же самое правило (никаких двух `&mut` одновременно), но проверка **перенесена с этапа компиляции на этап исполнения**. Если раньше (в примерах с обычными `&mut`) такая ошибка ловилась компилятором и код просто не собирался, то здесь код **компилируется**, но падает в рантайме, если правило действительно нарушено во время выполнения — прямая параллель с тем, как в C++ `assert()`-подобная защита (например, дебажный итератор-чекер в MSVC STL) ловит инвалидацию итератора не на этапе компиляции, а во время выполнения дебаг-сборки.

## `try_borrow`/`try_borrow_mut` — если паника нежелательна

```rust
let cell = RefCell::new(5);
let b1 = cell.borrow_mut();

match cell.try_borrow_mut() {
    Ok(_) => println!("получили второй borrow_mut (не должно случиться)"),
    Err(e) => println!("не удалось: {e}"),
}
println!("b1 всё ещё жив: {b1}");
```

Вывод:

```
не удалось: already borrowed
b1 всё ещё жив: 5
```

`try_borrow_mut()` возвращает `Result<RefMut<T>, BorrowMutError>` вместо паники — используется, когда конфликт заимствования — ожидаемая, обрабатываемая ситуация, а не баг программы (аналог `.parse()` возвращающего `Result` вместо паники, уже разбирали этот паттерн в теме про error handling).

## Классический паттерн: `Rc<RefCell<T>>` — разделяемое **и** изменяемое состояние в одном потоке

Вот где `Rc` (прошлая тема) и `RefCell` соединяются в одну идиому — она настолько распространена, что у неё есть неформальное имя в сообществе:

```rust
use std::rc::Rc;
use std::cell::RefCell;

struct Account {
    balance: RefCell<f64>,
}

let account = Rc::new(Account { balance: RefCell::new(100.0) });

let a1 = Rc::clone(&account);
let a2 = Rc::clone(&account);

*a1.balance.borrow_mut() += 50.0;
*a2.balance.borrow_mut() -= 30.0;

println!("итоговый баланс: {}", account.balance.borrow()); // 120
println!("strong_count: {}", Rc::strong_count(&account));   // 3
```

`Rc` сам по себе даёт только `&T` (много владельцев, но каждый может лишь читать). `RefCell` внутри `Rc` добавляет ту самую "дырку" для мутации через `&self`. Вместе `Rc<RefCell<T>>` даёт ровно то, что в C++ достигается сочетанием `shared_ptr<T>` + `mutable`-полей (или просто `shared_ptr<T>`, где `T` изменяется через неконстантные методы напрямую — в C++ `shared_ptr` не мешает мутации, потому что там нет borrow checker'а, который нужно было бы обходить в принципе). Разница философская: в C++ ты **всегда** можешь мутировать через `shared_ptr`, если у тебя не `const shared_ptr<const T>`. В Rust ты **обязан явно** попросить об этой возможности через `RefCell`, и обязан принять компромисс — либо рантайм-паника при нарушении правила, либо `Cell` для `Copy`-типов без паники вообще.

## `RefCell` не потокобезопасен — компилятор не даст использовать его между потоками

```rust
use std::sync::Arc;
use std::thread;

let shared = Arc::new(RefCell::new(0));
let s = Arc::clone(&shared);
thread::spawn(move || {
    *s.borrow_mut() += 1; // ОШИБКА
});
```

Ошибка:

```
error[E0277]: `RefCell<i32>` cannot be shared between threads safely
= help: the trait `Sync` is not implemented for `RefCell<i32>`
= note: if you want to do aliasing and mutation between multiple threads, use `std::sync::RwLock` instead
```

Компилятор не просто отказывает — он **прямо подсказывает** правильную замену. Причина: счётчик заимствований внутри `RefCell` — обычный, неатомарный (как `Rc` — тот же принцип "плачу за безопасность только там, где она реально нужна"). Если бы два потока одновременно вызвали `.borrow_mut()`, неатомарные инкременты/декременты счётчика могли бы гонку данных — сам механизм защиты `RefCell` стал бы небезопасным именно там, где должен защищать. Поэтому многопоточный аналог — `Mutex<T>`/`RwLock<T>` (уже мельком использовали `Mutex` в темах про `panic!`/потоки): тот же принцип internal mutability, но с настоящей блокировкой вместо счётчика, и настоящим ожиданием потока вместо мгновенной паники при конфликте.

## Сводная таблица

| |`Cell<T>`|`RefCell<T>`|`Mutex<T>` / `RwLock<T>`|
|---|---|---|---|
|Требование к `T`|Обычно `Copy` (для удобных методов)|Любой|Любой|
|Что происходит при доступе|Копирование значения (`get`/`set`)|Выдаёт `Ref<T>`/`RefMut<T>` (как `&T`/`&mut T`)|Выдаёт `MutexGuard<T>` (как `&mut T`)|
|Проверка правил заимствования|Не нужна (ссылок не существует)|В рантайме, через счётчик|В рантайме, через блокировку ОС/атомик|
|Что при нарушении правила|Невозможно нарушить|`panic!`|Поток **блокируется** и ждёт, пока лок освободится|
|Многопоточность|Нет (`!Sync`)|Нет (`!Sync`)|Да|
|Overhead|Практически нулевой|Небольшой (инкремент/декремент счётчика)|Заметный (синхронизация ОС/атомики)|
|C++ аналог|Нет прямого — ближе всего `mutable` для тривиальных типов|`mutable` + предположение, что программист не облажается|`std::mutex` + `std::lock_guard`/`std::shared_mutex`|

## Практическое правило выбора

1. Можешь обойтись обычным `&mut`/владением — используй его, `Cell`/`RefCell` не нужны вообще.
2. Тип тривиально копируется (числа, `bool`, маленькие `Copy`-struct'ы), и не нужны ссылки на содержимое — `Cell<T>`.
3. Тип не `Copy` (`String`, `Vec`, произвольная структура), нужен доступ через ссылку, всё в одном потоке — `RefCell<T>`.
4. Данные должны быть доступны из нескольких потоков — `Mutex<T>`/`RwLock<T>`, `RefCell` компилятор туда просто не пустит.
5. Нужно и разделяемое владение, и мутация одновременно — оборачиваешь `RefCell`/`Mutex` в `Rc`/`Arc` соответственно: `Rc<RefCell<T>>` (однопоточно) или `Arc<Mutex<T>>` (многопоточно) — вторая комбинация, кстати, прямая параллель с `Mutex` из твоего же примера с отравлением мьютекса из темы про `panic!`.
