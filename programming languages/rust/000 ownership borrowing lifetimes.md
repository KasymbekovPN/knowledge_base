## 1. RAII vs Ownership — общая идея, разная строгость

RAII в C++ — это **паттерн**, который держится на дисциплине: ты сам решаешь реализовать деструктор, конструктор копирования, конструктор перемещения (rule of 5), и компилятор не проверяет, что ты сделал это правильно.

```cpp
class FileHandle {
    FILE* f;
public:
    FileHandle(const char* path) : f(fopen(path, "r")) {}
    ~FileHandle() { if (f) fclose(f); }
    // Забыл удалить copy-конструктор? Получишь double-free.
};
```

В Rust ownership — это **правило языка**, проверяемое компилятором, а не соглашение:

```rust
struct FileHandle {
    f: File,
}

impl Drop for FileHandle {
    fn drop(&mut self) {
        // закрытие произойдёт автоматически через Drop у File
    }
}
```

Здесь просто невозможно случайно скопировать `FileHandle` — если ты не реализовал `Clone` (аналог copy-конструктора) явно, компилятор гарантирует, что владелец ровно один. Rule of 5 в Rust не существует как проблема, потому что "copy" по умолчанию **выключен**, а не включён.

## 2. Move-семантика — ключевое отличие

Вот где разница самая болезненная для C++-разработчика.

**В C++** `std::move` — это просто каст к rvalue-ссылке. Объект после перемещения **продолжает существовать** и доступен — просто находится в "valid but unspecified state". Использование объекта после `std::move` — это баг, но компилятор его не ловит:

```cpp
std::string s1 = "hello";
std::string s2 = std::move(s1);
std::cout << s1; // UB-ish, но компилируется. Скорее всего пустая строка, но не гарантировано.
```

**В Rust** перемещение — это не каст, а изменение состояния переменной на уровне компилятора. После move исходная переменная становится недействительной, и обращение к ней — **ошибка компиляции**, а не рантайм-баг:

```rust
let s1 = String::from("hello");
let s2 = s1; // move, не копирование
println!("{}", s1); // error[E0382]: borrow of moved value: `s1`
```

Это принципиально: в C++ use-after-move — это runtime footgun, который ловится (если повезёт) санитайзерами или в рантайме. В Rust это вообще не компилируется.

## 3. Copy vs копирование по умолчанию

В C++ копирование — поведение по умолчанию (если ты не удалил copy-конструктор). В Rust — наоборот: move по умолчанию, а копирование включается явно через типаж `Copy`, и то только для типов, где побитовое копирование безопасно (примитивы, `#[derive(Copy)]` для простых struct без владения ресурсами):

```rust
#[derive(Copy, Clone)]
struct Point { x: i32, Y: i32 } // безопасно копировать — просто числа на стеке

let p1 = Point { x: 1, Y: 2 };
let p2 = p1; // это КОПИЯ, не move — p1 всё ещё доступен
```

Если в структуре есть что-то вроде `String` или `Vec`, `Copy` реализовать нельзя в принципе (компилятор не даст) — только `Clone` (явный, "дорогой" аналог copy-конструктора, который нужно вызывать руками через `.clone()`, чтобы стоимость копирования была видна в коде).

## 4. Borrowing — это то, чего в C++ просто нет как концепции компилятора

Ссылки и указатели в C++ можно алиасить как угодно — компилятор не проверяет, не читаешь/пишешь ли ты через невалидную ссылку, не инвалидировал ли `push_back` твой итератор:

```cpp
std::vector<int> v = {1, 2, 3};
int& ref = v[0];
v.push_back(4); // потенциально инвалидирует ref — компилятор молчит
std::cout << ref; // UB, но компилируется и может "работать"
```

В Rust borrow checker физически не даст это написать:

```rust
let mut v = vec![1, 2, 3];
let r = &v[0];
v.push(4); // error[E0502]: cannot borrow `v` as mutable because it's also borrowed as immutable
println!("{}", r);
```

Правило простое и жёсткое: либо N неизменяемых ссылок (`&T`), либо ровно одна изменяемая (`&mut T`) — никогда одновременно. Это именно то правило, которое в C++ обеспечивается только твоей аккуратностью (и иногда — `const`, но `const` в C++ гораздо слабее: его легко обойти через `const_cast` или через отдельный неконстантный алиас).

## 5. Lifetimes — явная формализация того, что в C++ держится на "не верни ссылку на локальную переменную"

В C++ ты просто обязан помнить: не возвращай ссылку/указатель на объект, который вот-вот умрёт. Компилятор иногда предупреждает (с `-Wreturn-local-addr`), но это не часть системы типов:

```cpp
const std::string& getDefault() {
    std::string s = "temp";
    return s; // dangling reference, компилятор в лучшем случае варнинг выдаст
}
```

В Rust это часть сигнатуры функции. Lifetime-параметр `'a` — это способ сказать компилятору "эта ссылка на выходе не может пережить эту ссылку на входе":

```rust
fn longest<'a>(x: &'a str, Y: &'a str) -> &'a str {
    if x.len() > Y.len() { x } else { Y }
}
```

Компилятор буквально не скомпилирует функцию, которая пытается вернуть ссылку на локальную переменную — это ловится статически, при этом почти всегда lifetime выводятся автоматически (elision), и явно их пишешь только когда компилятор не может понять связь однозначно (несколько входных ссылок разного "происхождения").

## Итоговая таблица для быстрой сверки интуиции

|Концепция|C++|Rust|
|---|---|---|
|Управление ресурсом|RAII (деструктор, соглашение)|Ownership (правило языка)|
|Копирование по умолчанию|Да (если не удалено)|Нет (move по умолчанию)|
|Use-after-move|Runtime UB / unspecified state|Ошибка компиляции|
|Алиасинг ссылок|Не проверяется|Borrow checker: N read ИЛИ 1 write|
|Dangling reference|UB, иногда warning|Ошибка компиляции (lifetime)|
|"Глубокая копия"|Copy-конструктор (неявно)|`.clone()` (всегда явно)|

Главная ментальная перестройка: в C++ ты **обеспечиваешь корректность сам**, компилятор тебе доверяет. В Rust компилятор **не доверяет тебе** и требует доказательств корректности через типы — отсюда ощущение "борьбы с borrow checker" первые недели, которое проходит, когда начинаешь думать в терминах владения с самого начала, а не переносить C++-паттерны один в один.
