## Отправная точка: что такое замыкание в Rust

Прежде чем говорить про три способа передачи функций, важно понять, что такое замыкание (closure) как тип. В C++ лямбда компилируется в анонимный класс-функтор с `operator()` и полями для захваченных переменных. В Rust — то же самое по сути, но это явно закреплено в системе типов: **каждое замыкание имеет свой уникальный, анонимный, невыразимый тип**, который реализует один или несколько трейтов `Fn`/`FnMut`/`FnOnce`.

```rust
let x = 10;
let add_x = |Y| x + Y; // тип этого замыкания — уникальный, компилятор генерирует его сам
```

Ты никогда не напишешь тип этого замыкания руками (в отличие от C++, где тип лямбды тоже анонимный, но иногда его можно получить через `decltype`). Именно поэтому существуют три способа его _передать_ — потому что "просто взять и написать тип параметра" не вариант.

## Иерархия Fn / FnMut / FnOnce — это фундамент

Прежде чем перейти к `fn`/`impl Fn`/`dyn Fn`, нужно закрыть сами трейты — это то, чего в C++ нет как понятия вообще.

```rust
trait FnOnce<Args> {
    type Output;
    fn call_once(self, args: Args) -> Self::Output;
}

trait FnMut<Args>: FnOnce<Args> {
    fn call_mut(&mut self, args: Args) -> Self::Output;
}

trait Fn<Args>: FnMut<Args> {
    fn call(&self, args: Args) -> Self::Output;
}
```

(упрощённо — реальные сигнатуры чуть иначе, но суть та же). Заметь иерархию: `Fn` наследует `FnMut`, который наследует `FnOnce`. Значит, **любое** `Fn`-замыкание автоматически годится там, где ожидается `FnMut` или `FnOnce` — но не наоборот.

Что определяет, какой трейт получает замыкание — это то, **как** оно использует захваченные переменные, и компилятор выводит это автоматически:

```rust
let s = String::from("hello");

let borrows = || println!("{s}");           // читает s по ссылке → Fn
let mut counter = 0;
let mutates = || { counter += 1; };          // изменяет захваченное → FnMut
let consumes = move || { drop(s); };         // потребляет s → FnOnce (можно вызвать только раз)
```

В C++ это всё смешано в одном `std::function` без разделения на уровне типа — вызвать `std::function`, который внутри что-то `move`-ит при вызове, можно сколько угодно раз, и компилятор не предупредит, что второй вызов — это use-after-move того, что уже "съедено". В Rust `FnOnce` **физически нельзя вызвать второй раз** — это ловится на этапе компиляции.

### Пример с FnMut — счётчик

```rust
fn call_three_times<F: FnMut()>(mut f: F) {
    f(); f(); f();
}

fn main() {
    let mut count = 0;
    call_three_times(|| {
        count += 1;
        println!("{count}");
    });
}
```

### Пример с FnOnce — потребление значения

```rust
fn consume<F: FnOnce() -> String>(f: F) -> String {
    f()
}

fn main() {
    let s = String::from("hello");
    let closure = move || s; // забирает владение s, возвращает его — второй вызов невозможен
    let result = consume(closure);
    println!("{result}");
}
```

Если попробовать вызвать `closure` второй раз до передачи в `consume` — ошибка компиляции. Это прямой аналог "объект перемещён" из темы про move-семантику, только применённый к самому замыканию.

## Теперь — три способа принять "функцию как значение" параметром

### 1. `fn` — указатель на функцию (function pointer)

```rust
fn apply_fn_pointer(f: fn(i32) -> i32, x: i32) -> i32 {
    f(x)
}

fn double(x: i32) -> i32 { x * 2 }

apply_fn_pointer(double, 5);        // обычная функция — годится
apply_fn_pointer(|x| x + 1, 5);     // замыкание без захвата — тоже годится (coercion в указатель)
```

Ограничение: `fn` — это **буквально указатель**, как `int(*)(int)` в C++. Замыкание, которое **что-то захватывает**, сюда не подходит вообще — оно не является простым указателем на код, у него есть данные:

```rust
let Y = 10;
apply_fn_pointer(|x| x + Y, 5); // ОШИБКА: closure that captures cannot coerce to fn pointer
```

Прямой аналог в C++ — обычный указатель на функцию `int (*)(int)`. Захватывающая лямбда в C++ **тоже** не конвертируется в такой указатель (ровно та же причина — некуда положить захваченные данные), только non-capturing лямбда конвертируется в function pointer. Это единственное место, где интуиция из C++ переносится один в один.

### 2. `impl Fn(...)` / generic с trait bound — статическая диспетчеризация

```rust
fn apply_impl_fn(f: impl Fn(i32) -> i32, x: i32) -> i32 {
    f(x)
}

// это синтаксический сахар для:
fn apply_generic<F: Fn(i32) -> i32>(f: F, x: i32) -> i32 {
    f(x)
}
```

Здесь компилятор **мономорфизирует** — то есть генерирует отдельную версию функции `apply_impl_fn` под каждый конкретный тип замыкания, с которым её вызвали, точно так же, как с шаблонами C++:

```cpp
template <typename F>
int apply_generic(F f, int x) {
    return f(x);
}
```

Это буквально тот же механизм, что шаблонная функция, принимающая функтор/лямбду в C++ — **нулевой overhead**, вызов инлайнится, компилятор видит конкретный тип на этапе компиляции. Разница только в том, что Rust явно указывает _какому трейту_ должен соответствовать тип (`Fn`, `FnMut`, `FnOnce`), а C++ шаблон просто требует, чтобы `f(x)` скомпилировалось (duck typing на этапе инстанциирования, ошибка — там же, в точке использования, а не в сигнатуре — это, кстати, минус C++ версии: сообщения об ошибках для шаблонов исторически хуже читаемы).

Замыкание с захватом сюда **прекрасно подходит** — каждый захват просто становится полем анонимной структуры, которая передаётся по значению:

```rust
let Y = 10;
apply_impl_fn(|x| x + Y, 5); // работает — тип замыкания известен на этапе компиляции
```

### 3. `dyn Fn(...)` — динамическая диспетчеризация

```rust
fn apply_dyn_fn(f: &dyn Fn(i32) -> i32, x: i32) -> i32 {
    f(x)
}
```

Здесь `dyn Fn(...)` — это **trait object**: тип неизвестного размера, поэтому его всегда передают через указатель (`&dyn Fn`, `Box<dyn Fn>`, `Rc<dyn Fn>`). Под капотом это ровно то же самое, что `std::function` в C++ — **type erasure** через vtable:

- вызов идёт через таблицу виртуальных функций → есть overhead на индирекцию, как обычный виртуальный вызов;
- не инлайнится компилятором в общем случае;
- зато можно хранить **разные** типы замыканий в одной коллекции — то, что `impl Fn`/generic сделать физически не может, потому что каждый generic instantiation — отдельный конкретный тип.

```rust
let callbacks: Vec<Box<dyn Fn(i32) -> i32>> = vec![
    Box::new(|x| x + 1),
    Box::new(|x| x * 2),
    Box::new(double),
];

for cb in &callbacks {
    println!("{}", cb(5)); // 6, 10, 10
}
```

Такой `Vec<Box<dyn Fn(i32) -> i32>>` — это прямой аналог `std::vector<std::function<int(int)>>` в C++. Оба используют heap-аллокацию под замыкание и виртуальный вызов при вызове — цена одинаковая, просто в Rust это явно видно в сигнатуре типа (`dyn`, `Box`), а в C++ спрятано внутри реализации `std::function`.

## Возврат замыканий из функции — место, где различие становится практичным

Это классическая точка, где новички спотыкаются. Раньше в Rust нельзя было написать `-> Fn(i32) -> i32` напрямую (размер неизвестен на этапе компиляции — тип-то анонимный), поэтому долгое время единственным способом было:

```rust
fn make_adder(x: i32) -> Box<dyn Fn(i32) -> i32> {
    Box::new(move |Y| x + Y)
}
```

Сейчас (начиная с Rust 2018/стабилизации `impl Trait` в return position) можно избежать аллокации и виртуального вызова, если возвращаемый тип один и известен статически:

```rust
fn make_adder(x: i32) -> impl Fn(i32) -> i32 {
    move |Y| x + Y // компилятор мономорфизирует под конкретное место использования
}
```

`impl Fn` в возвращаемой позиции — это "непрозрачный, но конкретный, статически известный тип" — ноль overhead, но только если у тебя **одна** ветка возврата с одним конкретным типом замыкания. Если нужно вернуть _разные_ замыкания из разных веток `if`/`match` — обратно к `Box<dyn Fn>`, потому что статической диспетчеризации нужен единственный конкретный тип на выходе:

```rust
fn make_op(negate: bool) -> Box<dyn Fn(i32) -> i32> {
    if negate {
        Box::new(|x| -x)
    } else {
        Box::new(|x| x)
    }
}
```

## move-замыкания — явность вместо `[&]`/`[=]`

В C++ способ захвата пишется в списке захвата лямбды: `[&]` (всё по ссылке), `[=]` (всё по значению/копии), либо явно поле за полем. В Rust это единственное ключевое слово `move`, а _что именно_ происходит с каждой переменной (move или copy) компилятор решает сам, исходя из того, реализует ли тип `Copy`:

```rust
let v = vec![1, 2, 3];      // Vec не Copy
let s = 5;                   // i32 — Copy

let closure = move || {
    println!("{:?}, {}", v, s); // v — moved внутрь замыкания, s — скопирован
};
```

Без `move` замыкание по умолчанию старается захватывать **по минимально необходимым правам** — если только читает, берёт `&`; если мутирует — `&mut`; и только если это невозможно (например, замыкание должно пережить область видимости, как в потоках), _обязывает_ писать `move` явно:

```rust
let v = vec![1, 2, 3];
std::thread::spawn(move || {
    println!("{:?}", v); // без move — ошибка: v может не пережить поток
});
```

В C++ эквивалент — почти всегда `[v = std::move(v)]` в списке захвата, если хочешь передать владение в поток, либо `[&]`/`[=]`, что оставляет на тебе ответственность не словить dangling reference, если поток переживёт вызывающую функцию — компилятор C++ этого не проверит.

## Сводная таблица — когда что использовать

|Способ|Диспетчеризация|Overhead|Захват|Разные типы в одном месте|Аналог в C++|
|---|---|---|---|---|---|
|`fn`|статическая (прямой вызов)|нет|только non-capturing|нет|`int(*)(int)`|
|`impl Fn` / generic|статическая (мономорфизация)|нет (инлайнится)|любой|нет (один конкретный тип на инстанциацию)|шаблон + лямбда/функтор|
|`dyn Fn` (`&dyn`/`Box<dyn>`)|динамическая (vtable)|есть (виртуальный вызов + возможна heap-аллокация)|любой|да|`std::function`|

**Практическое правило:** по умолчанию используй `impl Fn`/generic-параметр — это idiomatic Rust и то, чем написана большая часть стандартной библиотеки (`Iterator::map`, `filter`, `sort_by` — все принимают `impl FnMut`/`impl Fn`, без единого виртуального вызова). `dyn Fn`/`Box<dyn Fn>` — только когда тебе реально нужна гетерогенная коллекция замыканий, или тип должен быть скрыт (например, в публичном API, где нельзя писать generic-параметр по архитектурным причинам), или замыкание возвращается из нескольких разных веток кода.
