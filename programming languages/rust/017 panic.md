## Что такое `panic!` концептуально

Уже упоминал вскользь в теме про error handling: `panic!` — не механизм обработки _ожидаемых_ ошибок (для этого `Result`), а сигнал "программа обнаружила нарушенный инвариант, из которого не может разумно продолжить". Механически это ближе к `std::terminate()`/неперехваченному исключению в C++ или к `assert()` в C, чем к обычному `throw`.

## Базовый вызов

```rust
fn divide(a: i32, b: i32) -> i32 {
    if b == 0 {
        panic!("деление на ноль: {a} / {b}");
    }
    a / b
}

fn main() {
    println!("до");
    let r = divide(10, 0);
    println!("после: {r}");
}
```

Вывод:

```
до
thread 'main' panicked at panic1.rs:3:9:
деление на ноль: 10 / 0
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

Код выхода процесса: **101** (это фиксированное значение для паники, не связанное со значением, которое ты передал — паника не возвращает "код ошибки" как таковой). `"после: {r}"` никогда не печатается — выполнение прервано в точке паники.

## `RUST_BACKTRACE` — управление детализацией трейса

```bash
RUST_BACKTRACE=1 ./program      # показать backtrace
RUST_BACKTRACE=full ./program   # показать полный backtrace, включая внутренности рантайма
./program                        # без переменной — backtrace скрыт, только подсказка его включить
```

По умолчанию backtrace **не печатается** — только однострочное сообщение с местом паники и подсказка, как включить полный трейс. Это отличается от C++, где `std::terminate()` при неперехваченном исключении обычно вообще не даёт трейса без внешнего инструментария (gdb/дебаггер) — в Rust трейс встроен и доступен по одной переменной окружения, без пересборки.

## Unwind vs Abort — два режима того, что происходит физически

Это ключевая механика, аналогичная выбору между исключениями с раскруткой стека и `std::terminate` в C++.

**По умолчанию (`panic = "unwind"`)** — паника раскручивает стек, вызывая деструкторы (`Drop`) всех живых значений на пути вверх, ровно как исключение в C++ на пути к `catch`. Если раскрутка долетает до границы потока — поток завершается, но **остальная программа продолжает работать** (что демонстрирует пример с `catch_unwind`/потоками ниже).

**`panic = "abort"`** — настраивается в `Cargo.toml`:

```toml
[profile.dev]
panic = "abort"
```

Я собрал и прогнал это на практике:

```
до паники
thread 'main' panicked at src/main.rs:3:5:
бум
Aborted
```

Код выхода — **134** (128 + сигнал SIGABRT), не 101. Никакой раскрутки стека вообще, никакого вызова `Drop` для живых объектов — процесс завершается немедленно через `abort()`. Это даёт чуть меньший размер бинарника (не нужны таблицы раскрутки стека — те самые `.eh_frame` секции, знакомые из C++) и чуть быстрее сам факт паники, но ценой невозможности `catch_unwind` (см. ниже) — типичный выбор для embedded/минимальных бинарников, где раскрутка стека не нужна в принципе.

## `catch_unwind` — единственный способ "поймать" панику

```rust
use std::panic;

fn risky(n: i32) -> i32 {
    if n < 0 { panic!("отрицательное число: {n}"); }
    n * 2
}

fn main() {
    let result = panic::catch_unwind(|| risky(5));
    println!("{:?}", result); // Ok(10)

    let result = panic::catch_unwind(|| risky(-1));
    match result {
        Ok(v) => println!("ok: {v}"),
        Err(_) => println!("паника была поймана, продолжаем работу"),
    }
    println!("программа продолжает работать после catch_unwind");
}
```

Вывод:

```
Ok(10)
паника была поймана, продолжаем работу
программа продолжает работать после catch_unwind
```

(Плюс в stderr — само сообщение о панике, оно печатается **до** того, как `catch_unwind` вернёт `Err`, потому что panic hook срабатывает независимо от того, поймают панику или нет.)

**Важная культурная разница с C++/Java:** `catch_unwind` **не предназначен** для повседневной обработки ошибок — это осознанно "тяжёлый", редко используемый инструмент, в первую очередь для границ между Rust-кодом и внешним миром: FFI-границы (нельзя дать панике пересечь границу с C-кодом — это UB), потоковые пулы (чтобы паника в одной задаче не убила весь пул), плагинные системы. Для обычной логики "функция может завершиться неудачей" — всегда `Result`, никогда `catch_unwind`. Это прямо противоположно культуре C++/Java, где `try/catch` — стандартный повседневный инструмент контроля потока.

## Паника в потоке — не убивает всю программу, но требует `.join()`

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let data = Arc::new(Mutex::new(0));
    let d = Arc::clone(&data);

    let handle = thread::spawn(move || {
        let mut guard = d.lock().unwrap();
        *guard += 1;
        panic!("паника внутри потока, держащего мьютекс");
    });

    let join_result = handle.join();
    println!("join вернул Err: {}", join_result.is_err());

    let lock_result = data.lock();
    match lock_result {
        Ok(_) => println!("лок получен нормально"),
        Err(poisoned) => {
            println!("мьютекс отравлен, но данные всё ещё доступны");
            let guard = poisoned.into_inner();
            println!("значение внутри: {guard}");
        }
    }
}
```

Вывод:

```
join вернул Err: true
мьютекс отравлен, но данные всё ещё доступны
значение внутри: 1
```

Два важных момента, которых в C++ `std::thread` нет вообще:

**1. `thread::spawn` внутри неявно вызывает `catch_unwind`** — паника в дочернем потоке не убивает процесс целиком (в отличие от C++, где необработанное исключение в потоке, не пойманное внутри самого потока, вызывает `std::terminate()` для **всей программы**). Результат паники приходит через `handle.join()`, возвращающий `Result` — `Err` с "payload" паники внутри.

**2. Poisoned mutex ("отравление")** — если поток паникует, **держа** захваченный `Mutex`, при следующей попытке взять этот же мьютекс `.lock()` возвращает не `Ok(guard)`, а `Err(PoisonError)`. Это защитный механизм: компилятор физически не может гарантировать, что данные внутри мьютекса остались в консистентном состоянии, если поток упал посреди их модификации — поэтому Rust явно сигнализирует об этом вызывающему, вместо того чтобы молча отдать потенциально повреждённые данные (в C++ `std::mutex` в аналогичной ситуации — если поток бросает исключение, держа `std::lock_guard`, деструктор `lock_guard` просто разблокирует мьютекс, и следующий захвативший поток **не узнает**, что данные могли остаться в промежуточном состоянии — тихий источник багов). При этом данные не потеряны — `poisoned.into_inner()` даёт доступ, если ты осознанно решил, что состояние всё же приемлемо использовать.

## `assert!`/`assert_eq!`/`debug_assert!` — семейство макросов на основе `panic!`

```rust
let x = 5;
assert!(x > 0, "x должен быть положительным, получено {x}");
assert_eq!(x, 5);

debug_assert!(x < 100); // компилируется в no-op в release-сборке (--release)
```

`assert!`/`assert_eq!`/`assert_ne!` работают **всегда**, в том числе в release-сборке — прямой аналог `assert()` в C/C++, только с гарантированно понятным сообщением (`assert_eq!` печатает оба значения при провале, не просто "assertion failed").

`debug_assert!`/`debug_assert_eq!` компилируются в **пустое место** (`--release`/`opt-level > 0` по умолчанию отключает их) — прямой аналог `assert()` в C, который сам традиционно отключается через `#define NDEBUG` в релизе. Используются для дорогих проверок инвариантов, которые нужны только на этапе разработки/отладки и не должны стоить производительности в продакшене.

## `unwrap()`/`expect()` — самый частый практический источник паники

Уже несколько раз использовали в разговоре — стоит явно назвать связь с `panic!`. `unwrap()` на `None`/`Err` — это паника с обобщённым сообщением; `expect("текст")` — то же самое, но с твоим собственным сообщением, что почти всегда лучше для отладки:

```rust
let v: Vec<i32> = vec![1, 2, 3];
let _ = v[10]; // паника: index out of bounds: the len is 3 but the index is 10
```

Индексация массива/среза `[]` — тоже паникует при выходе за границы, в отличие от C++, где `operator[]` для `std::vector` — это **неопределённое поведение** (никакой проверки вообще, если не использовать `.at()`, которая как раз кидает исключение). В Rust `[]` **всегда** проверяет границы и паникует при выходе — это тот самый "небесплатный" bounds-check, о котором говорил в разговоре про производительность; убрать его вручную можно через `get_unchecked` внутри `unsafe`, если действительно нужно и доказано безопасно.

## Кастомный panic hook — что происходит при панике до раскрутки/abort

```rust
use std::panic;

panic::set_hook(Box::new(|info| {
    let msg = info.payload().downcast_ref::<&str>().map(|s| s.to_string())
        .or_else(|| info.payload().downcast_ref::<String>().cloned())
        .unwrap_or_else(|| "неизвестно".to_string());
    if let Some(loc) = info.location() {
        eprintln!("[CUSTOM] паника в {}:{}: {msg}", loc.file(), loc.line());
    }
}));
```

Вывод при панике из-за индексации массива выше:

```
[CUSTOM] паника в panic4.rs:23: index out of bounds: the len is 3 but the index is 10
```

`set_hook` заменяет стандартный обработчик (тот, что печатает `thread 'main' panicked at ...`) на свой — практическое применение: структурированное логирование паники (JSON в лог-агрегатор вместо человекочитаемого текста в stderr), отправка в систему мониторинга ошибок (Sentry-подобные сервисы), или полное подавление вывода в продакшене. Hook вызывается **всегда**, независимо от того, поймана ли паника через `catch_unwind` дальше или нет — это просто точка "что напечатать/сделать в момент паники", а не сама обработка потока управления.

## Сравнение с C++/C — сводная таблица

|Механизм|C|C++|Rust|
|---|---|---|---|
|"Программа в невосстановимом состоянии"|`assert()` / `abort()`|Неперехваченное исключение → `std::terminate`|`panic!`|
|Раскрутка стека|Нет|Есть (для `throw`)|Есть (по умолчанию, `panic = "unwind"`)|
|Немедленное завершение без раскрутки|`abort()`|`std::terminate()` / `noexcept` с исключением внутри|`panic = "abort"` в `Cargo.toml`, либо паника поверх паники|
|"Поймать" и продолжить|Нет|`try`/`catch`|`catch_unwind` (редкий, не для обычной логики)|
|Паника в потоке|Обычно валит весь процесс|`std::terminate()` для всей программы, если не поймано в самом потоке|Только сам поток; `join()` возвращает `Err`|
|Данные после паники, державшей блокировку|UB, тихо|Мьютекс разблокирован молча, состояние неизвестно|Mutex "отравлен" (`PoisonError`), явно сигнализируется|
|Отключаемая проверка в релизе|`assert()` (через `NDEBUG`)|`assert()` (через `NDEBUG`)|`debug_assert!`|
|Всегда активная проверка|Ручная (`if (...) abort();`)|Ручная / `_STL_ASSERT`|`assert!`/`assert_eq!`|
|Проверка границ массива|Нет (UB)|Нет для `[]`, есть для `.at()` (исключение)|Всегда для `[]` (паника)|
|Кастомизация обработки|`atexit`/`std::set_terminate`-подобного нет в C|`std::set_terminate`|`panic::set_hook`|

## Практическое правило: когда `panic!`, когда `Result`

Возвращаясь к тому, что уже проговаривали в теме про error handling: `Result` — для **ожидаемых** сбоев (файл не найден, сеть недоступна, пользователь ввёл невалидные данные) — это часть нормального потока управления. `panic!` — для **нарушенных инвариантов**, ошибок программиста, состояний, которые "не должны" случиться, если код написан правильно (индекс гарантированно в границах по логике, но всё равно вышел — баг; функция получила аргумент, который по контракту API никогда не должен быть отрицательным, но пришёл отрицательным). Библиотечный код почти никогда не должен паниковать на пользовательский ввод — только на нарушение собственных invariants; решение "паниковать или возвращать `Result`" на границе публичного API — одно из важных архитектурных решений при проектировании библиотеки на Rust.
