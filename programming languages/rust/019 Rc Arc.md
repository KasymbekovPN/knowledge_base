## `Rc<T>` — разделяемое владение вместо единоличного

`Box<T>` (прошлая тема) — ровно один владелец. `Rc<T>` (**R**eference **c**ounted) — **несколько** владельцев одних и тех же данных одновременно, с подсчётом ссылок: данные уничтожаются, когда последний владелец исчезает.

```rust
use std::rc::Rc;

struct Data { value: i32 }

impl Drop for Data {
    fn drop(&mut self) {
        println!("Data с value={} уничтожается", self.value);
    }
}

fn main() {
    let a = Rc::new(Data { value: 42 });
    println!("count после создания a: {}", Rc::strong_count(&a));

    let b = Rc::clone(&a); // НЕ глубокая копия -- просто увеличивает счётчик
    println!("count после clone в b: {}", Rc::strong_count(&a));

    {
        let c = Rc::clone(&a);
        println!("count после clone в c: {}", Rc::strong_count(&a));
        println!("c.value = {}", c.value); // Deref работает как у Box
    } // c выходит из scope -- счётчик уменьшается

    println!("count после выхода c из scope: {}", Rc::strong_count(&a));
    println!("a.value = {}, b.value = {}", a.value, b.value);
}
```

Вывод:

```
count после создания a: 1
count после clone в b: 2
count после clone в c: 3
c.value = 42
count после выхода c из scope: 2
a.value = 42, b.value = 42
Data с value=42 уничтожается
```

**Критически важный момент** — `Rc::clone(&a)` (или эквивалентно `a.clone()`) **не копирует данные**. Это не `Clone` в обычном понимании (глубокая копия), а просто инкремент счётчика ссылок — дешёвая операция, O(1). `Data` уничтожается ровно один раз, только когда последний `Rc` (в примере — `b`, после `a` и `c` уже вышли из области видимости) выходит из scope. Прямой аналог — `std::shared_ptr<T>` в C++, тот же принцип: `shared_ptr` тоже дёшево копируется (атомарный инкремент счётчика), деструктор объекта вызывается при обнулении счётчика.

## `Rc` — однопоточный, компилятор это гарантирует статически

```rust
struct NotShareable;
fn requires_send<T: Send>(_: T) {}

fn main() {
    let data = Rc::new(NotShareable);
    requires_send(data); // ОШИБКА
}
```

Ошибка:

```
error[E0277]: `Rc<NotShareable>` cannot be sent between threads safely
= help: the trait `Send` is not implemented for `Rc<NotShareable>`
```

Причина простая: `Rc` использует **обычный, неатомарный** счётчик ссылок (`inc`/`dec` без синхронизации) — это специально сделано ради скорости в однопоточном сценарии. Если бы `Rc` можно было свободно передавать между потоками, два потока могли бы одновременно инкрементировать/декрементировать счётчик без синхронизации — классическая гонка данных (счётчик может "потерять" инкремент, что приведёт либо к преждевременному освобождению памяти при живых ссылках, либо к утечке). Компилятор Rust статически **не позволяет** этой ситуации возникнуть в принципе: `Rc<T>` не реализует трейт `Send` (маркер "можно безопасно передать владение в другой поток"), и любая попытка передать его в поток — ошибка компиляции, а не потенциальный runtime UB, как было бы в C++ с обычным (неатомарным) refcounting-указателем, случайно использованным в многопоточном коде.

## `Arc<T>` — то же самое, но потокобезопасно

```rust
use std::sync::Arc;
use std::thread;

fn main() {
    let data = Arc::new(vec![1, 2, 3, 4, 5]);
    let mut handles = vec![];

    for i in 0..3 {
        let data_clone = Arc::clone(&data);
        let handle = thread::spawn(move || {
            let sum: i32 = data_clone.iter().sum();
            println!("поток {i}: сумма = {sum}, strong_count = {}", Arc::strong_count(&data_clone));
        });
        handles.push(handle);
    }

    for h in handles { h.join().unwrap(); }
    println!("итоговый strong_count = {}", Arc::strong_count(&data));
}
```

Вывод (порядок строк может отличаться между запусками — потоки исполняются конкурентно):

```
поток 0: сумма = 15, strong_count = 2
поток 1: сумма = 15, strong_count = 3
поток 2: сумма = 15, strong_count = 2
итоговый strong_count = 1
```

`Arc` (**A**tomically **R**eference **c**ounted) — механически идентичен `Rc`, но счётчик — атомарный (`AtomicUsize` с `fetch_add`/`fetch_sub` внутри), поэтому безопасен для конкурентного доступа из нескольких потоков одновременно. Это прямой аналог `std::shared_ptr` в C++ (который **всегда** атомарный, независимо от того, нужна тебе многопоточность или нет) — только в Rust ты **явно выбираешь**, платить ли за атомарность (`Rc` — нет, `Arc` — да), а не платишь за неё всегда по умолчанию, как в C++.

## Стоимость: атомарные операции не бесплатны

Раз уж недавно обсуждали производительность — стоит явно проговорить: атомарный инкремент/декремент в `Arc` дороже обычного в `Rc` (кросс-ядерная синхронизация кэш-линии, memory fence) — разница обычно небольшая, но заметная в hot-path сценариях с частым клонированием. Отсюда практическое правило: если данные точно не покидают один поток — используй `Rc`, не `Arc`, компилятор всё равно не даст случайно отправить `Rc` в поток, так что "на всякий случай Arc везде" — это не защита, а просто ненужный overhead.

## Проблема: цикл сильных ссылок = утечка памяти

Вот куда обычно упирается интуиция "но ведь GC/refcounting не течёт" — течёт, если объекты ссылаются друг на друга циклически:

```rust
use std::rc::Rc;
use std::cell::RefCell;

struct Node {
    value: i32,
    next: RefCell<Option<Rc<Node>>>,
}

impl Drop for Node {
    fn drop(&mut self) {
        println!("Node {} уничтожается", self.value);
    }
}

fn main() {
    let a = Rc::new(Node { value: 1, next: RefCell::new(None) });
    let b = Rc::new(Node { value: 2, next: RefCell::new(None) });

    *a.next.borrow_mut() = Some(Rc::clone(&b));
    *b.next.borrow_mut() = Some(Rc::clone(&a)); // ЦИКЛ: a -> b -> a

    println!("a strong_count = {}", Rc::strong_count(&a)); // 2
    println!("b strong_count = {}", Rc::strong_count(&b)); // 2
    println!("--- конец main ---");
}
```

Вывод:

```
a strong_count = 2
b strong_count = 2
--- конец main ---
```

Обрати внимание: **ни одной строчки** `"Node ... уничтожается"` не напечаталось. Хотя `a` и `b` формально вышли из scope в конце `main`, счётчик у каждого из них падает только до **1**, а не до 0 — потому что `a` держит `Rc` на `b` (через `next`), а `b` держит `Rc` на `a`. Оба объекта продолжают жить в куче вечно, никогда не будут освобождены — это единственный вид "утечки памяти", который остаётся возможным при полностью safe-коде на Rust (borrow checker и владение защищают от use-after-free/double-free, но **не** от циклов сильных ссылок — это фундаментальное ограничение любого refcounting-подхода, ровно та же проблема бывает с циклами `shared_ptr` в C++).

`RefCell` здесь использован потому, что нужна мутабельность поля `next` через `&self` (нельзя получить `&mut Node` из `Rc<Node>`, когда владельцев несколько) — забегаю немного вперёд, это тема следующего разговора, здесь достаточно знать, что `RefCell` даёт "изменяемость по значению неизменяемой ссылки" ценой рантайм-проверки, уже упоминал этот механизм в контексте `mut`-модификаторов.

## `Weak<T>` — решение: слабая ссылка, не участвующая в подсчёте владения

```rust
use std::rc::{Rc, Weak};
use std::cell::RefCell;

struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,        // Weak -- не владеет
    children: RefCell<Vec<Rc<Node>>>,   // Rc -- владеет
}

impl Drop for Node {
    fn drop(&mut self) {
        println!("Node {} уничтожается", self.value);
    }
}

fn main() {
    let leaf = Rc::new(Node {
        value: 2,
        parent: RefCell::new(Weak::new()),
        children: RefCell::new(vec![]),
    });

    {
        let branch = Rc::new(Node {
            value: 1,
            parent: RefCell::new(Weak::new()),
            children: RefCell::new(vec![Rc::clone(&leaf)]),
        });

        *leaf.parent.borrow_mut() = Rc::downgrade(&branch); // Weak, не Rc::clone!

        if let Some(p) = leaf.parent.borrow().upgrade() {
            println!("родитель leaf: {}", p.value);
        }
    } // branch выходит из scope -- цикла нет, объект реально уничтожается

    println!("leaf.parent.upgrade() = {:?}", leaf.parent.borrow().upgrade().is_some());
}
```

Вывод:

```
родитель leaf: 1
Node 1 уничтожается
leaf.parent.upgrade() = false
```

`branch` корректно уничтожается сразу по выходу из своего scope — цикла больше нет, потому что связь `leaf → parent` идёт через `Weak`, а не через `Rc`. `Weak::upgrade()` возвращает `Option<Rc<T>>` — `Some`, пока объект жив, `None`, если он уже уничтожен (что и произошло после того, как `branch` вышел из scope: `upgrade()` вернул `false`/`None`, не панику и не dangling pointer — это ключевая гарантия безопасности, отличающая `Weak` от сырого указателя).

Идиоматичное правило (классика для деревьев/графов): **родитель владеет детьми через `Rc`, ребёнок ссылается на родителя через `Weak`** — направление владения совпадает с логической иерархией, а обратная ссылка не создаёт цикл. Аналог в C++ — комбинация `shared_ptr` (для владеющих связей) + `weak_ptr` (для обратных/наблюдающих связей), концептуально идентично, `Rc::downgrade`/`Weak::upgrade` — прямые аналоги `weak_ptr::lock()`.

## Сводная таблица

||C++ `shared_ptr<T>`|C++ `weak_ptr<T>`|Rust `Rc<T>`|Rust `Arc<T>`|Rust `Weak<T>`|
|---|---|---|---|---|---|
|Владение|Разделяемое|Не владеет|Разделяемое|Разделяемое|Не владеет|
|Потокобезопасность счётчика|Всегда атомарный|Всегда атомарный|Неатомарный|Атомарный|Как у пары `Rc`/`Arc`|
|Влияет на время жизни данных|Да|Нет|Да|Да|Нет|
|Доступ к данным|Прямое разыменование|Через `.lock()` → `shared_ptr` или `nullptr`|Прямое разыменование (`Deref`)|Прямое разыменование|Через `.upgrade()` → `Option<Rc/Arc<T>>`|
|Можно передать в другой поток|Да (сам `shared_ptr`, не то, на что указывает)|Да|Нет (не `Send`)|Да|Совпадает с parent-типом|
|Циклы создают утечку|Да|—|Да|Да|— (разрывает цикл)|

## Практическое правило выбора

- **Один владелец, точно известный на этапе компиляции** → обычное владение (структура/переменная), без обёртки вообще.
- **Один владелец, но данные должны жить в куче** (рекурсия, `dyn Trait`, большой размер) → `Box<T>` (прошлая тема).
- **Несколько владельцев, всё в одном потоке** → `Rc<T>`.
- **Несколько владельцев, доступ из разных потоков** → `Arc<T>`.
- **Обратная/родительская ссылка в структуре с потенциальным циклом** (деревья с parent-указателем, графы, наблюдатели/подписчики) → `Weak<T>` на "неглавной" стороне связи.

Следующий логичный шаг — `RefCell`/`Cell`/`Mutex`/`RwLock`, раз уже несколько раз всплыла необходимость мутировать данные через `Rc`/`Arc` (которые сами по себе дают только `&T`, не `&mut T`, потому что владельцев несколько). Идём туда, закрывая этим всю Фазу 2 из исходного плана?
