Раз уже несколько раз упоминали `match` мимоходом — вот подробный разбор.

## Базовый синтаксис — и сразу главное отличие от `switch`

```rust
let n = 3;

match n {
    1 => println!("один"),
    2 => println!("два"),
    3 => println!("три"),
    _ => println!("что-то другое"),
}
```

Внешне похоже на `switch` в C++:

```cpp
switch (n) {
    case 1: std::cout << "один"; break;
    case 2: std::cout << "два"; break;
    case 3: std::cout << "три"; break;
    default: std::cout << "что-то другое";
}
```

Но два принципиальных отличия сразу:

**1. Нет fallthrough.** Забытый `break` в C++ — классический источник багов (кейс "проваливается" в следующий). В Rust каждая ветка `match` изолирована, проваливания не существует как концепции вообще.

**2. Исчерпывающая проверка (exhaustiveness checking).** Компилятор Rust **требует**, чтобы `match` покрывал все возможные значения. Убери `_ => ...` из примера выше — получишь ошибку компиляции "non-exhaustive patterns", потому что `i32` теоретически может быть любым числом, не только 1/2/3. Это не украшение, а серьёзная гарантия корректности — особенно мощная в связке с `enum` (ниже).

## `match` — это выражение, не оператор

Как и `if`, `match` в Rust возвращает значение — это то же самое свойство языка, что мы видели у `if`/блоков в целом:

```rust
let description = match n {
    1 => "один",
    2 => "два",
    _ => "много",
};
```

В C++ `switch` — оператор, значения из него не возвращаются, поэтому паттерн обычно такой:

```cpp
std::string description;
switch (n) {
    case 1: description = "один"; break;
    case 2: description = "два"; break;
    default: description = "много";
}
```

Rust-версия короче и, что важнее, `let description` может быть `let` (неизменяемым) — при C++-подходе переменная обязана быть mutable, чтобы её можно было присвоить внутри `switch`.

## Настоящая сила — pattern matching на `enum`

Вот где `match` перестаёт быть просто заменой `switch` и становится совсем другим инструментом. В C++ нет полноценных алгебраических типов данных (ADT) — ближайшее приближение, `std::variant` + `std::visit`, появилось только в C++17 и синтаксически гораздо тяжелее.

```rust
enum Shape {
    Circle(f64),                  // вариант с одним полем
    Rectangle { width: f64, height: f64 }, // вариант с именованными полями
    Triangle(f64, f64, f64),      // вариант с несколькими полями
}

fn area(shape: &Shape) -> f64 {
    match shape {
        Shape::Circle(radius) => std::f64::consts::PI * radius * radius,
        Shape::Rectangle { width, height } => width * height,
        Shape::Triangle(a, b, c) => {
            let s = (a + b + c) / 2.0;
            (s * (s - a) * (s - b) * (s - c)).sqrt()
        }
    }
}
```

Если завтра добавишь `Shape::Square(f64)` и забудешь обновить `area` — **компилятор не даст скомпилироваться**, пока не обработаешь новый вариант (или явно не поставишь `_`). Это огромная практическая гарантия при рефакторинге — в C++ добавление нового значения в `enum class` и забытый `case` в одном из десятка `switch` по кодовой базе — тихий баг, который поймаешь (если повезёт) через `-Wswitch`.

## `Option` и `Result` — то, ради чего `match` используется чаще всего

Это прямое продолжение темы "нет null, нет исключений" из самого первого разговора:

```rust
fn divide(a: f64, b: f64) -> Option<f64> {
    if b == 0.0 { None } else { Some(a / b) }
}

match divide(10.0, 2.0) {
    Some(result) => println!("Результат: {result}"),
    None => println!("Деление на ноль"),
}
```

```rust
fn parse_num(s: &str) -> Result<i32, String> {
    s.parse().map_err(|_| format!("не число: {s}"))
}

match parse_num("42") {
    Ok(n) => println!("Число: {n}"),
    Err(e) => println!("Ошибка: {e}"),
}
```

Компилятор точно так же не даст забыть ветку `None` или `Err` — в C++ эквивалент (проверка на `nullptr`/пойманное исключение) целиком на дисциплине разработчика.

## Матчинг диапазонов

```rust
let age = 25;

match age {
    0..=12 => println!("ребёнок"),
    13..=19 => println!("подросток"),
    20..=64 => println!("взрослый"),
    _ => println!("пенсионер"),
}
```

Ближе всего в C++ — цепочка `if`/`else if` с `>=`/`<`, поскольку `switch` диапазоны в стандартном C++ не поддерживает (только GCC/Clang case-range как нестандартное расширение).

## Or-паттерны (`|`) — несколько значений в одной ветке

```rust
match n {
    1 | 2 | 3 => println!("маленькое"),
    4..=10 => println!("среднее"),
    _ => println!("большое"),
}
```

Аналог группировки `case 1: case 2: case 3:` (проваливание без кода между ними) в C++ — только явный и без риска случайного fallthrough куда-то ещё.

## Guards (`if` внутри `match`) — условие поверх паттерна

```rust
let pair = (2, -2);

match pair {
    (x, y) if x == y => println!("равны"),
    (x, y) if x + y == 0 => println!("в сумме ноль"),
    (x, _) if x % 2 == 0 => println!("первое чётное"),
    _ => println!("ничего особенного"),
}
```

Guard — это уже не часть системы паттернов как таковой (exhaustiveness checker его не учитывает при доказательстве полноты — он просто "довешивает" рантайм-условие поверх совпавшего паттерна), но синтаксически позволяет держать логику в одном месте вместо вложенных `if` внутри каждой ветки.

## `@`-байндинги — совместить проверку диапазона и захват значения

```rust
let n = 5;

match n {
    x @ 1..=5 => println!("в диапазоне 1-5, конкретно: {x}"),
    x @ 6..=10 => println!("в диапазоне 6-10, конкретно: {x}"),
    x => println!("другое: {x}"),
}
```

Без `@` пришлось бы либо терять конкретное значение (просто `1..=5 => ...` без доступа к `n`), либо дублировать проверку через guard (`x if (1..=5).contains(&x)`). Прямого аналога в C++ нет вообще.

## Деструктуризация вложенных структур — там же, где `let`-паттерны

```rust
struct Point { x: i32, y: i32 }
enum Shape2 {
    Circle { center: Point, radius: f64 },
}

let s = Shape2::Circle { center: Point { x: 0, y: 0 }, radius: 5.0 };

match s {
    Shape2::Circle { center: Point { x: 0, y: 0 }, radius } => {
        println!("круг в начале координат, радиус {radius}");
    }
    Shape2::Circle { center, radius } => {
        println!("круг в ({}, {}), радиус {radius}", center.x, center.y);
    }
}
```

Можно матчить сколь угодно глубоко вложенные структуры/enum'ы за один `match`, включая литеральные значения внутри (`x: 0, y: 0` выше) — это выходит далеко за пределы того, что `switch`/`if` в C++ умеют делать декларативно; в C++ пришлось бы писать это как цепочку явных проверок полей.

## Матчинг по ссылке — снова borrowing, но в контексте `match`

```rust
let v = vec![String::from("a"), String::from("b")];

match v.first() { // v.first() возвращает Option<&String>
    Some(s) => println!("{s}"), // s здесь — &String, не String — v не perемещается
    None => println!("пусто"),
}

println!("{:?}", v); // v всё ещё доступна
```

Это те самые match ergonomics, которые уже упоминали в разговоре про `mut`/`ref`: компилятор сам подстраивает байндинги (`s` автоматически становится `&String`), не заставляя писать `Some(ref s)` вручную, как приходилось в старых редакциях Rust.

## `_` vs именованный биндинг — игнорирование части данных

```rust
match shape {
    Shape::Rectangle { width, .. } => println!("ширина: {width}"), // остальные поля неважны
    _ => {}
}
```

`..` — "остальное неважно" для полей struct/tuple, `_` — "неважно вообще всё значение". И то, и другое просто позволяет не покрывать компилятору требованием "используй эту переменную" — знакомо по прошлому обсуждению `let _`.

## Сводная таблица: `match` vs `switch`

| Особенность                            | C++ `switch`                               | Rust `match`                         |
| -------------------------------------- | ------------------------------------------ | ------------------------------------ |
| Проваливание между ветками             | Есть (нужен `break`)                       | Нет никогда                          |
| Проверка полноты покрытия              | Нет (только `-Wswitch` warning для `enum`) | Обязательна, ошибка компиляции       |
| Возвращает значение                    | Нет                                        | Да, это выражение                    |
| Матчинг диапазонов                     | Нет в стандарте                            | Да (`1..=5`)                         |
| Матчинг по типу данных                 | Только целые/enum/строки (C++17)           | Любые типы, включая деструктуризацию |
| Условие поверх паттерна (guard)        | Нет                                        | Да (`if` после паттерна)             |
| Захват значения при проверке диапазона | Нет                                        | Да (`@`)                             |
| Работает с `enum` с данными (ADT)      | Нет (нужен `std::variant`+`std::visit`)    | Нативно                              |
