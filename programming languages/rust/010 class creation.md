## Создание "класса" — struct + impl, а не единая конструкция

В C++ `class` — это одна конструкция, где данные и поведение объявлены вместе. В Rust это **осознанно разделено**: `struct` описывает только данные, `impl` блок(и) добавляют поведение отдельно.

```rust
struct BankAccount {
    owner: String,
    balance: f64,
}

impl BankAccount {
    // сюда пойдут методы, конструкторы, статические методы
}
```

Можно иметь несколько `impl`-блоков для одного `struct` (например, разделяя основную логику и реализацию трейтов) — компилятор просто объединяет их:

```rust
impl BankAccount {
    fn deposit(&mut self, amount: f64) { self.balance += amount; }
}

impl BankAccount {
    fn withdraw(&mut self, amount: f64) -> Result<(), String> {
        if amount > self.balance {
            return Err("недостаточно средств".to_string());
        }
        self.balance -= amount;
        Ok(())
    }
}
```

В C++ второй `class BankAccount { ... }` с дополнительными методами просто не скомпилируется (переопределение класса) — там для разделения используют namespace/partial реализацию через отдельные `.cpp` файлы, но само тело класса всегда одно.

## Три вида struct

```rust
// Обычный, с именованными полями — как typical C++ class
struct Point {
    x: f64,
    y: f64,
}

// Tuple struct — поля без имён, доступ по индексу
struct Color(u8, u8, u8);
let red = Color(255, 0, 0);
println!("{}", red.0); // 255

// Unit struct — вообще без полей, часто как маркер/тег
struct Marker;
```

Tuple struct и unit struct — то, чего в C++ нет прямого аналога (ближе всего — `struct Color { std::array<uint8_t,3> data; }`, но без встроенного позиционного доступа).

## Видимость — `pub` на каждом уровне отдельно, не как в C++

Ключевое отличие от `public`/`private`/`protected` в C++: в Rust видимость назначается **на каждом элементе отдельно** (на самом `struct`, и **независимо** на каждом поле), а не одним модификатором сразу для целого блока:

```rust
pub struct BankAccount {
    pub owner: String,   // видно снаружи модуля
    balance: f64,        // приватно — видно только внутри модуля, где объявлен struct
}
```

Это принципиально другая модель. В C++:

```cpp
class BankAccount {
public:
    std::string owner;
private:
    double balance;
};
```

здесь `private`/`public` — секции, применяются ко всем полям под ними разом. В Rust нет ни `protected` (наследования как такового нет — об этом ниже), ни секций — каждое поле аннотируется индивидуально, и по умолчанию (без `pub`) — приватно.

Важно: видимость в Rust определяется **относительно модуля**, а не относительно "класса". `private`-поле видно **всему модулю**, где объявлен `struct`, включая другие функции/структуры в том же модуле — не только методам самого `struct`. Это ближе к friend-классам в одном namespace, чем к строгой C++ инкапсуляции на уровне класса.

Градации видимости шире, чем просто pub/private:

```rust
pub struct Account {
    pub(crate) balance: f64,      // видно во всём текущем крейте, но не снаружи
    pub(super) id: u32,            // видно только родительскому модулю
    pub(in crate::banking) note: String, // видно только в указанном пути модуля
}
```

Аналога такой гранулярности в C++ нет вообще — там либо `friend` (явно назвать конкретный класс/функцию), либо ничего.

## Поля — без модификаторов внутри одного поля, но с дефолтными значениями через трейт, а не в объявлении

В C++ можно задать значение по умолчанию прямо в теле класса:

```cpp
class Config {
    int timeout = 30;
    bool verbose = false;
};
```

В Rust так писать **нельзя** — `struct` это чисто описание layout'а, без значений по умолчанию в самом объявлении. Значения по умолчанию задаются либо явно в конструкторе, либо через трейт `Default`:

```rust
struct Config {
    timeout: i32,
    verbose: bool,
}

impl Default for Config {
    fn default() -> Self {
        Config { timeout: 30, verbose: false }
    }
}

let c = Config::default();
let c2 = Config { timeout: 60, ..Default::default() }; // задать одно поле, остальные — default
```

Последняя строка (`..Default::default()`) — синтаксис "structure update", удобная замена паттерну множественных конструкторов-перегрузок из C++ ("конструктор с частичными параметрами").

Если все поля реализуют `Default`, можно вообще не писать `impl Default` руками:

```rust
#[derive(Default)]
struct Config {
    timeout: i32,
    verbose: bool,
}
```

`#[derive(...)]` — макрос, который генерирует шаблонную реализацию трейта автоматически; в C++ ближайший аналог — generated default constructor (если все поля default-constructible), только явно закреплённый атрибутом, а не молчаливое поведение компилятора.

## Конструкторы — нет специальной синтаксической конструкции, только соглашение

Это фундаментальное отличие, уже мельком упоминалось в разговоре про методы. В Rust **нет** ключевого слова/специального метода-конструктора. Экземпляр создаётся просто литералом struct:

```rust
struct Point { x: f64, y: f64 }

let p = Point { x: 1.0, y: 2.0 }; // это уже валидный способ создать объект, без всякого "конструктора"
```

Идиоматичный "конструктор" — это обычная ассоциированная функция по соглашению `new` (можно назвать как угодно, `new` — просто конвенция сообщества, не зарезервированное слово):

```rust
impl Point {
    fn new(x: f64, y: f64) -> Self {
        Point { x, y } // field init shorthand — как в C++20 designated initializers, но проще
    }
}

let p = Point::new(1.0, 2.0);
```

**Ключевое следствие отсутствия конструктора как конструкции:** невозможен объект в "недоинициализированном" состоянии между `new`-вызовом класса и телом конструктора, как в C++ (где база класса, потом поля по порядку объявления, потом тело конструктора — и в теле конструктора объект уже формально "жив", хотя ещё может быть не полностью настроен). В Rust `struct`-литерал требует **все поля сразу**, компилятор не даст создать частично заполненный struct:

```rust
let p = Point { x: 1.0 }; // ОШИБКА: missing field `y`
```

Нет ни отдельного "конструктора по умолчанию" как явления языка, ни конструктора копирования, ни move-конструктора (все три — либо `Default`, либо `Clone`, либо просто встроенный move, который мы разбирали в начале разговора). Нет и перегрузки — поэтому, если нужно несколько способов создания, пишут несколько ассоциированных функций с разными именами:

```rust
impl Point {
    fn origin() -> Self { Point { x: 0.0, y: 0.0 } }
    fn from_tuple(t: (f64, f64)) -> Self { Point { x: t.0, y: t.1 } }
}
```

## Деструкторы — трейт `Drop`, вызывается автоматически, но нельзя вызвать напрямую

```rust
struct FileHandle {
    name: String,
}

impl Drop for FileHandle {
    fn drop(&mut self) {
        println!("Закрываю файл: {}", self.name);
    }
}

fn main() {
    let f = FileHandle { name: "data.txt".to_string() };
    println!("Работаю с файлом");
} // здесь автоматически вызывается f.drop()
```

Вывод:

```
Работаю с файлом
Закрываю файл: data.txt
```

Прямой аналог `~FileHandle()` в C++. Отличия:

**1. Порядок вызова — обратный порядку объявления полей**, как и в C++ для полей-членов (это совпадает), но, в отличие от C++, у struct вообще нет наследования, так что нет отдельного вопроса "сначала деструктор производного класса, потом базового" — вся иерархия сложнее только через композицию, а не наследование (см. ниже).

**2. Нельзя вызвать `drop()` напрямую как метод:**

```rust
f.drop(); // ОШИБКА: explicit use of destructor method
```

Компилятор специально это запрещает, потому что явный вызов `drop()`-метода не уничтожил бы значение (в отличие от C++, где `obj.~ClassName()` вызывает деструктор, но объект формально всё ещё "существует" до конца scope — классический источник double-free, если потом ещё раз вызовется деструктор автоматически). Вместо этого, если нужно уничтожить значение раньше конца scope, используется свободная функция:

```rust
drop(f); // std::mem::drop — забирает f по значению (move) и сразу дропает
println!("после этой строки f больше не существует");
```

Это безопасно именно потому что `drop(f)` **перемещает** `f` внутрь себя — исходная переменная становится недействительной, и повторный drop в конце scope просто не произойдёт (компилятор это отслеживает так же, как любой другой move).

**3. Нет виртуальных деструкторов как отдельной проблемы.** В C++ забытый `virtual ~Base()` при полиморфном удалении через указатель на базовый класс — классический источник утечек/UB. В Rust `Drop` для `dyn Trait` работает корректно автоматически, потому что vtable для trait object всегда включает указатель на `drop`, без необходимости явно помечать что-либо `virtual`.

## Наследования нет — вместо него композиция + трейты

Раз уж всплыла тема — важно проговорить явно, потому что C++-разработчик рефлекторно ищет `class Derived : public Base`. В Rust этого нет вообще. Переиспользование поведения — через:

**Композицию** (has-a вместо is-a):

```rust
struct Engine { power: u32 }
struct Car { engine: Engine, brand: String }
```

**Трейты** (для общего поведения между несвязанными типами) — следующая большая тема, к которой мы много раз подходили в этом разговоре.

## Методы — уже разбирали подробно, коротко напомню в контексте "класса"

```rust
impl Point {
    fn distance(&self, other: &Point) -> f64 {           // как const-метод
        ((self.x - other.x).powi(2) + (self.y - other.y).powi(2)).sqrt()
    }

    fn translate(&mut self, dx: f64, dy: f64) {           // как не-const метод
        self.x += dx;
        self.y += dy;
    }
}
```

(Полный разбор трёх видов `self` — в сообщении про методы выше.)

## Статические методы — ассоциированные функции без `self`

```rust
impl Point {
    fn new(x: f64, y: f64) -> Self {   // "статический метод" = функция без self в impl-блоке
        Point { x, y }
    }

    fn origin() -> Self {
        Point { x: 0.0, y: 0.0 }
    }
}

let p = Point::new(1.0, 2.0); // вызов через ::, не через .
```

Синтаксически то же самое, что `static` метод в C++ (`Point::new(...)` эквивалентно `Point::create(...)` в C++), с одним отличием: в Rust нет отдельного ключевого слова `static` для методов — функция становится "статической" просто по факту отсутствия параметра `self`. Компилятор различает "метод" и "ассоциированную функцию" исключительно по наличию/отсутствию `self` в сигнатуре.

## Статические поля — `const`/`static`, но не внутри struct

Здесь ещё одно структурное отличие от C++. В C++ можно объявить статическое поле прямо в теле класса:

```cpp
class Circle {
public:
    static constexpr double PI = 3.14159;
    static int instance_count;  // требует определения снаружи класса
};
int Circle::instance_count = 0;
```

В Rust `struct` **не может содержать** `static`/`const` поля внутри своего объявления — только обычные поля экземпляра. "Статические поля класса" реализуются как ассоциированные константы в `impl`-блоке (для констант времени компиляции) или как отдельная `static`-переменная модуля (для настоящего разделяемого состояния):

```rust
struct Circle {
    radius: f64,
}

impl Circle {
    const PI: f64 = 3.14159; // ассоциированная константа — аналог static constexpr

    fn area(&self) -> f64 {
        Self::PI * self.radius * self.radius
    }
}

println!("{}", Circle::PI); // доступ через ::, как static constexpr в C++
```

Для настоящего мутабельного "общего на все экземпляры" состояния (аналог `static int instance_count` с реальной памятью, не константа) — нужна отдельная глобальная `static`, и, поскольку общая мутабельная глобальная переменная небезопасна в многопоточном контексте, доступ к ней требует `unsafe` либо атомиков:

```rust
use std::sync::atomic::{AtomicU32, Ordering};

struct Circle { radius: f64 }

static INSTANCE_COUNT: AtomicU32 = AtomicU32::new(0);

impl Circle {
    fn new(radius: f64) -> Self {
        INSTANCE_COUNT.fetch_add(1, Ordering::SeqCst);
        Circle { radius }
    }
}
```

Это прямое следствие темы "fearless concurrency" из самого начала разговора: C++ разрешает `static int instance_count` с гонкой данных при многопоточном доступе без единого предупреждения компилятора (пока не запустишь ThreadSanitizer). В Rust голая мутабельная `static` без атомика/синхронизации **не скомпилируется** для доступа вне `unsafe` блока — компилятор заранее не даёт написать потенциальную гонку.

## Сводная таблица: класс C++ → "класс" Rust

|Концепция C++|Rust-эквивалент|
|---|---|
|`class`/`struct` (данные + методы вместе)|`struct` (данные) + `impl` (методы), раздельно|
|`public`/`private`/`protected` секции|`pub`/приватность на каждом элементе отдельно; `protected` нет (нет наследования)|
|Конструктор (`ClassName(...)`)|Нет спец. конструкции; конвенция — ассоциированная функция `new`|
|Конструктор по умолчанию|Трейт `Default`, часто через `#[derive(Default)]`|
|Копирующий конструктор|Трейт `Clone` (явный `.clone()`), либо `Copy` для дешёвых типов|
|Деструктор (`~ClassName()`)|Трейт `Drop`, метод `drop(&mut self)`, вызывается автоматически, нельзя вызвать напрямую|
|Обычный метод / const-метод|`fn f(&mut self)` / `fn f(&self)`|
|`static` метод|Ассоциированная функция (без `self`)|
|`static constexpr` поле|Ассоциированная константа (`const` в `impl`)|
|`static` мутабельное поле|Глобальная `static` (обычно `Atomic*`/`Mutex`), требует `unsafe` при простом доступе|
|Наследование (`: public Base`)|Нет; композиция + трейты|
|`virtual` метод|Трейты + `dyn Trait` (динамическая диспетчеризация)|
|`friend`|Видимость на уровне модуля (`pub(crate)`, `pub(super)`) — шире и декларативнее|


## `Self` (с большой буквы) — это тип, alias на "текущий тип из impl-блока"

```rust
struct Circle {
    radius: f64,
}

impl Circle {
    const PI: f64 = 3.14159;

    fn new(radius: f64) -> Self {   // Self здесь == Circle
        Self { radius }              // Self { ... } == Circle { ... }
    }

    fn area(&self) -> f64 {
        Self::PI * self.radius * self.radius  // Self::PI == Circle::PI
    }
}
```

`Self` — это просто сокращение, чтобы не писать имя типа заново внутри его собственного `impl`-блока. Можно было бы писать `Circle::PI` и `Circle { radius }` везде вместо `Self::PI`/`Self { radius }` — результат идентичен, `Self` это чистое удобство (и, что важнее, устойчивость к переименованию — если завтра переименуешь `Circle` в `Disk`, весь код внутри `impl` с `Self` не потребует правок).

Ближайший аналог в C++ — не совсем то же самое, но по духу похоже на `decltype(*this)` или (для конструкторов через delegating constructors) просто имя самого класса, повторяемое вручную, потому что в C++ `Self`-подобного алиаса нет — приходится каждый раз писать полное имя класса:

```cpp
class Circle {
public:
    static constexpr double PI = 3.14159;
    static Circle create(double r) { return Circle(r); } // приходится писать Circle, не "Self"
};
```

## `self` (с маленькой буквы) — это конкретный экземпляр, параметр метода

Твоя формулировка "экземпляр класса" верна, но чуть точнее: `self` — это не "экземпляр" абстрактно, а **параметр метода**, через который метод получает доступ к конкретному объекту, на котором его вызвали — ровно то же, что скрытый указатель `this` в C++, просто явный в сигнатуре:

```rust
impl Circle {
    fn area(&self) -> f64 {  // self — это &Circle, конкретный объект, для которого вызван area()
        Self::PI * self.radius * self.radius
        //  ^ тип                ^ данные конкретного экземпляра
    }
}

let c = Circle { radius: 2.0 };
c.area(); // self внутри area() == &c
```

## Где проходит грань — можно проверить механически

Правило простое: **`Self` встречается только там, где ожидается тип** (в сигнатуре возврата, в аннотации типа, перед `::` для доступа к ассоциированным членам). **`self` встречается только там, где ожидается значение** (как параметр функции, как выражение для доступа к полю через `.`).

```rust
impl Circle {
    fn new(radius: f64) -> Self {        // Self — тип (позиция возвращаемого типа)
        Self { radius }                   // Self — тип (имя struct перед {})
    }

    fn scaled(&self, factor: f64) -> Self {  // Self — тип
        Self { radius: self.radius * factor }
        //              ^ self — значение (доступ к полю через .)
    }

    fn compare_type() -> &'static str {
        std::any::type_name::<Self>()    // Self — тип (параметр дженерика)
    }
}
```

Единственное место, где грань может казаться размытой — это сокращённая запись типа параметра `self` в сигнатуре метода:

```rust
fn area(&self) -> f64 { ... }
```

`&self` здесь — это буквально сокращение для `self: &Self`. То есть **тип** параметра `self` — это `&Self` (ссылка на тип `Circle`), а сам параметр называется `self` (с маленькой буквы) и является **значением** этого типа при каждом конкретном вызове. Полная запись, которую иногда пишут явно (например, когда нужен специфичный тип-обёртка вроде `self: Rc<Self>`):

```rust
impl Circle {
    fn area(self: &Self) -> f64 { ... }     // ровно то же самое, что &self
    fn area2(self: Rc<Self>) -> f64 { ... } // self обёрнут в Rc — для методов, вызываемых только через Rc<Circle>
}
```

## Итоговое сравнение с C++, чтобы закрепить

|Rust|Что это|C++ аналог|
|---|---|---|
|`Self`|Тип — алиас на "тип текущего impl-блока"|Нет прямого аналога; ближе всего — вручную повторяемое имя класса|
|`self`|Значение — параметр метода, конкретный объект|`this` (но `this` — указатель, `self` может быть `&self`/`&mut self`/`self` — владеющее значение)|
|`Self::PI`|Доступ к ассоциированной константе через тип|`ClassName::PI` (статический доступ)|
|`self.radius`|Доступ к полю конкретного экземпляра|`this->radius` (неявно `radius` внутри метода)|

Ты понял правильно — единственное уточнение, которое стоит держать в голове: `self` это не "экземпляр" сам по себе, а _параметр, ссылающийся на экземпляр_ (или владеющий им, если это `self` без `&`) — тонкость, которая станет важна, когда дойдём до трейтов и будем разбирать `Box<dyn Trait>`, где `self`-параметр может иметь разные обёртки (`Rc<Self>`, `Pin<&mut Self>` и т.п.).
