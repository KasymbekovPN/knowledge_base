## Первое: почему в Rust нет исключений

Это не случайность, а осознанное решение. Исключения в C++ создают **невидимые пути управления** — глядя на сигнатуру `double parse(const string& s)`, невозможно понять, может ли она бросить исключение, не читая документацию или тело функции (`noexcept` — единственная подсказка, и она опциональная). В Rust возможность ошибки — **часть типа**, видна прямо в сигнатуре и обязательна к обработке компилятором.

## `Option<T>` — отсутствие значения без `null`

```rust
fn divide(a: f64, b: f64) -> Option<f64> {
    if b == 0.0 { None } else { Some(a / b) }
}

let result = divide(10.0, 2.0)
    .map(|x| x * 100.0)
    .unwrap_or(0.0);
println!("{result}"); // 500

println!("{:?}", divide(10.0, 0.0)); // None
```

Уже разбирали `Option` в контексте `match`/`enum` — здесь важно добавить **комбинаторы**: `.map()`, `.unwrap_or()`, `.and_then()` и подобные позволяют строить цепочки преобразований без явного `match` на каждом шаге, похоже на `std::optional::transform`/`value_or` (C++23) — только в Rust это часть языка с первого релиза, а не добавлено спустя 8 лет.

## `Result<T, E>` и `?` — распространение ошибки без исключений

```rust
fn parse_and_double(s: &str) -> Result<i32, std::num::ParseIntError> {
    let n: i32 = s.parse()?; // если Err — сразу return Err(...) из функции целиком
    Ok(n * 2)
}

println!("{:?}", parse_and_double("21"));  // Ok(42)
println!("{:?}", parse_and_double("abc")); // Err(ParseIntError { kind: InvalidDigit })
```

`?` — это оператор, который на каждой строке говорит: "если `Result` — `Ok(v)`, продолжай с `v`; если `Err(e)` — немедленно `return Err(e)` из всей функции". Механически это разворачивается примерно в:

```rust
let n: i32 = match s.parse() {
    Ok(v) => v,
    Err(e) => return Err(e),
};
```

Сравни с C++, где для той же цели пришлось бы либо городить исключения (`try { ... } catch`), либо вручную писать `if (!result) return result.error();` на каждой строке — `?` убирает этот шаблонный код полностью, при этом **видимость** пути ошибки в сигнатуре (`-> Result<...>`) сохраняется, в отличие от исключений.

## `?` умеет конвертировать тип ошибки через `From` — вот где начинается реальная сила

```rust
#[derive(Debug)]
enum ConfigError {
    Io(std::io::Error),
    Parse(std::num::ParseIntError),
}

impl From<std::io::Error> for ConfigError {
    fn from(e: std::io::Error) -> Self { ConfigError::Io(e) }
}
impl From<std::num::ParseIntError> for ConfigError {
    fn from(e: std::num::ParseIntError) -> Self { ConfigError::Parse(e) }
}

fn read_timeout(path: &str) -> Result<u32, ConfigError> {
    let content = std::fs::read_to_string(path)?; // io::Error -> ConfigError, автоматически
    let timeout: u32 = content.trim().parse()?;    // ParseIntError -> ConfigError, автоматически
    Ok(timeout)
}
```

Вывод при отсутствующем файле:

```
ошибка конфига: Io(Os { code: 2, kind: NotFound, message: "No such file or directory" })
```

`?` при несовпадении типа ошибки автоматически вызывает `ConfigError::from(original_error)`, если такой `impl From` существует. Это позволяет одной функции собирать ошибки из **разных** источников (файловый ввод-вывод + парсинг) в единый тип ошибки, не оборачивая каждый вызов вручную в `.map_err(...)`.

## `thiserror` — избавляет от ручного бойлерплейта вокруг своих enum ошибок

Писать `impl From` и `impl Display` руками для каждого варианта ошибки — рутина. `thiserror` — derive-макрос (та самая процедурная категория из темы про макросы), который генерирует всё это по атрибутам:

```rust
use thiserror::Error;

#[derive(Error, Debug)]
enum ConfigError {
    #[error("не удалось прочитать файл: {0}")]
    Io(#[from] std::io::Error),

    #[error("не удалось распарсить timeout: {0}")]
    Parse(#[from] std::num::ParseIntError),

    #[error("значение timeout вне допустимого диапазона: {value} (максимум {max})")]
    OutOfRange { value: u32, max: u32 },
}

fn read_timeout(path: &str) -> Result<u32, ConfigError> {
    let content = std::fs::read_to_string(path)?; // From сгенерирован через #[from]
    let timeout: u32 = content.trim().parse()?;
    if timeout > 3600 {
        return Err(ConfigError::OutOfRange { value: timeout, max: 3600 });
    }
    Ok(timeout)
}
```

Вывод:

```
Display: не удалось прочитать файл: No such file or directory (os error 2)
Debug: Io(Os { code: 2, kind: NotFound, message: "No such file or directory" })
```

Что именно генерирует `thiserror` за тебя:

- `#[error("...")]` → реализацию `std::fmt::Display` (человекочитаемое сообщение, с `{0}`/`{value}` — доступ к полям варианта).
- `#[from]` → `impl From<SourceError> for ConfigError` автоматически, то самое, что раньше писали вручную.
- Плюс реализацию трейта `std::error::Error` (нужен для совместимости с остальной экосистемой обработки ошибок — логированием, `Box<dyn Error>` и т.д.).

Это ближайший аналог написания собственного класса исключения в C++ (`class ConfigError : public std::exception { const char* what() const noexcept override { ... } };`), только без наследования, без виртуальных функций, и с готовой поддержкой нескольких вариантов в одном типе через `enum`.

## `anyhow` — когда не важен конкретный тип ошибки, а важна цепочка причин

`thiserror` — для **библиотечного** кода, где вызывающий может захотеть различить конкретные варианты ошибки через `match`. `anyhow` — для **прикладного** кода (бинарники, `main`, скрипты), где обычно всё равно, что именно произошло — важно вывести понятное сообщение и, может быть, залогировать цепочку причин.

```rust
use anyhow::{Context, Result, bail};

fn read_timeout(path: &str) -> Result<u32> {
    let content = std::fs::read_to_string(path)
        .with_context(|| format!("не удалось открыть конфиг {path}"))?;
    let timeout: u32 = content.trim().parse()
        .context("timeout должен быть числом")?;
    if timeout > 3600 {
        bail!("timeout {timeout} превышает максимум 3600");
    }
    Ok(timeout)
}

fn main() -> Result<()> {
    match read_timeout("/nonexistent/path") {
        Ok(t) => println!("timeout: {t}"),
        Err(e) => {
            println!("ошибка: {e}");
            println!("цепочка причин:");
            for cause in e.chain().skip(1) {
                println!("  -> {cause}");
            }
        }
    }
    Ok(())
}
```

Вывод:

```
ошибка: не удалось открыть конфиг /nonexistent/path
цепочка причин:
  -> No such file or directory (os error 2)
```

Ключевые вещи здесь:

- `anyhow::Result<T>` — это алиас на `Result<T, anyhow::Error>`, единый тип ошибки, способный обернуть **любую** ошибку, реализующую `std::error::Error` — не нужно писать свой enum вообще.
- `.context(...)`/`.with_context(...)` — добавляют человекочитаемый слой поверх исходной ошибки, **не теряя** оригинальную причину — `.chain()` потом позволяет пройтись по всей цепочке "что привело к чему" (похоже на `std::exception::what()` + вложенные исключения через `std::throw_with_nested` в C++, только гораздо удобнее в использовании).
- `bail!(...)` — быстрый способ сразу вернуть ошибку с форматированным сообщением, аналог `throw std::runtime_error(...)`, но без стека раскрутки исключений — это просто ранний `return Err(...)`.
- `fn main() -> Result<()>` — уже видели в теме про точку входа: если `main` вернёт `Err`, программа завершится с ненулевым кодом и напечатает ошибку через `Debug`.

## Сравнение производительности и модели — вот что реально принципиально отличается от C++

В C++ исключения используют **раскрутку стека** (stack unwinding) — при `throw` рантайм идёт вверх по стеку, вызывая деструкторы, пока не найдёт подходящий `catch`. Это дорого при самом факте throw (хотя bewässert "zero-cost" в отсутствие исключения — если не бросаешь, почти нет overhead), и не всегда предсказуемо по времени.

`Result` в Rust — это **обычное значение**, возвращаемое как любое другое. Нет раскрутки стека, нет рантайм-механизма поиска обработчика — просто `enum` с тегом, который каждый вызывающий явно проверяет (или явно передаёт выше через `?`). Стоимость — как у обычного возврата значения, полностью предсказуема и видна по коду.

## `panic!` — то, что в Rust ближе всего к исключению, но используется иначе

Стоит отдельно проговорить, чтобы не смешивать с `Result`: `panic!` — это не механизм обработки ожидаемых ошибок, а сигнал "программа в состоянии, из которого невозможно разумно продолжить" (нарушенный инвариант, баг). По умолчанию `panic!` тоже разворачивает стек (можно настроить `panic = "abort"` в `Cargo.toml`, чтобы сразу завершать процесс, как большинство asserts в C++). `.unwrap()`/`.expect()` на `Option`/`Result` вызывают `panic!`, если значения нет — это осознанный выбор "я уверен, что здесь не может быть ошибки, а если ошибся — пусть упадёт сразу", а не общий механизм обработки ошибок, как исключения в C++ часто используются (и там, и там неправильное использование — попытка "ловить" panic как обычный контроль потока, вместо `Result`, считается антипаттерном).

## Сводная таблица

|Задача|C++|Rust|
|---|---|---|
|"Может не быть значения"|`nullptr` / `std::optional<T>`|`Option<T>`|
|"Может завершиться с ошибкой"|Исключения / `std::expected<T,E>` (C++23)|`Result<T, E>`|
|Распространение ошибки вверх|`throw` + автоматическая раскрутка стека|`?`, явный `return Err`, видно в типе|
|Конвертация между типами ошибок|`catch (const A&) { throw B(...); }`|`?` + `impl From<A> for B` — автоматически|
|Читаемое сообщение об ошибке|`what()` виртуальный метод|`impl Display` (руками или через `thiserror`)|
|Библиотечный тип ошибки с вариантами|Иерархия классов исключений|`enum` + `thiserror`|
|Прикладной catch-all тип ошибки|`catch (const std::exception& e)`|`anyhow::Error` / `Box<dyn Error>`|
|Цепочка "ошибка из-за ошибки"|`std::throw_with_nested` (редко используется)|`.context()`/`.chain()` в `anyhow`|
|Неожидаемое, невосстановимое состояние|`assert()` / неперехваченное исключение → `terminate`|`panic!`|
|Стоимость при отсутствии ошибки|Формально ноль (zero-cost exceptions)|Ноль — обычный возврат значения|
|Стоимость при наличии ошибки|Дорого — раскрутка стека|Дёшево — обычный возврат значения|
|Видимость в сигнатуре|Не видно без чтения тела/документации (кроме `noexcept`)|Всегда явно — часть возвращаемого типа|

**Практическое правило выбора:** библиотека, которую будут использовать другие (и которым может понадобиться `match` по конкретному варианту) — `thiserror`. Бинарник/приложение/скрипт, где важно быстро долететь до понятного сообщения об ошибке с контекстом — `anyhow`. Простое `Option`/`Result` без сторонних крейтов — если ошибок не так много и/или проект не тянет лишнюю зависимость.

Дальше логично закрыть `Rc`/`RefCell`/`Arc`/`Mutex` (мы их несколько раз откладывали, и они прямо связаны с темой "когда `Result`/владение недостаточно, нужна разделяемая мутабельность") — или перейти к конкурентности/`async`, раз с ошибками разобрались? Что выбираешь?
