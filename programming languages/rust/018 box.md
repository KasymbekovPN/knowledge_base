## `Box<T>` — что это механически

`Box<T>` — самый простой из "умных указателей" Rust: **владеющий указатель на данные в куче**, с ровно одним владельцем. Это прямой, почти буквальный аналог `std::unique_ptr<T>` в C++ — единственное владение, автоматическое освобождение при выходе из scope, move-only (нельзя копировать, только перемещать).

```rust
let b = Box::new(42); // 42 положен в кучу, b -- указатель на него в стеке
```

## Размер — всегда указатель, независимо от размера `T`

```rust
struct Huge { data: [u8; 1_000_000] }

println!("{}", size_of::<Box<i32>>());  // 8
println!("{}", size_of::<Box<Huge>>()); // 8
println!("{}", size_of::<usize>());     // 8
```

Независимо от того, что внутри — один байт или мегабайт данных — сам `Box<T>` на стеке занимает ровно один указатель (8 байт на 64-битной системе). Реальные данные живут в куче. Это ровно то, зачем в принципе нужен `Box` в теме про рекурсивные `enum`, которую разбирали раньше: `List::Cons(i32, Box<List>)` имеет фиксированный размер именно потому, что `Box<List>` — это всегда 8 байт, сколько бы элементов ни было в списке фактически.

## `Deref`/`DerefMut` — прозрачное разыменование, как `operator->`/`operator*` у `unique_ptr`

```rust
struct Counter { value: i32 }

impl Counter {
    fn increment(&mut self) { self.value += 1; }
}

let mut boxed = Box::new(Counter { value: 0 });
boxed.increment();       // сахар для (*boxed).increment()
boxed.increment();
println!("{}", boxed.value); // тоже автоматическое разыменование
```

Вывод: `value = 2`. Компилятор автоматически разыменовывает `Box<T>` при вызове метода/доступе к полю через `.` — механизм называется **deref coercion**, реализован через трейты `Deref`/`DerefMut` (те же трейты, кстати, что делают `String` "похожим" на `&str`, а `Vec<T>` — на `&[T]`, единая система, не спецкейс для `Box`). Для C++-интуиции это ровно `operator->()`/`operator*()`, которые `unique_ptr` перегружает, только в Rust это происходит **неявно** на каждом вызове метода — не нужно писать `(*boxed).increment()` или `boxed->increment()` вручную.

## Move-семантика — Box нельзя скопировать, только переместить

```rust
let b1 = Box::new(42);
let b2 = b1; // move
println!("{b2}");
// println!("{b1}"); // ОШИБКА: b1 перемещён
```

Это прямое продолжение первой темы нашего разговора: `Box<T>` не реализует `Copy` (владеет ресурсом в куче — копирование по умолчанию было бы двойным освобождением при выходе обоих из scope), только `Clone` (если сам `T` его реализует, тогда `.clone()` делает **глубокое** копирование — выделяет новую область в куче и копирует данные, аналог copy-конструктора `unique_ptr`, которого у него, к слову, вообще нет — `unique_ptr` в C++ тоже move-only, только без `Clone`-аналога вообще, копирование через `unique_ptr` нужно писать вручную через `std::make_unique<T>(*ptr)`).

## `Drop` — освобождение происходит рекурсивно, при выходе `Box` из scope

```rust
impl Drop for Counter {
    fn drop(&mut self) {
        println!("Counter с value={} уничтожается", self.value);
    }
}

fn main() {
    let mut boxed = Box::new(Counter { value: 0 });
    boxed.increment();
    boxed.increment();
    println!("value = {}", boxed.value);
    println!("--- конец main, boxed должен быть уничтожен ---");
}
```

Вывод:

```
value = 2
--- конец main, boxed должен быть уничтожен ---
Counter с value=2 уничтожается
```

`Drop` для `Counter` вызывается **после** последней строки `main`, в момент, когда сам `boxed` выходит из scope — сначала освобождается память в куче, но перед этим корректно вызывается `Drop` для содержимого. Это ровно то, что делает деструктор `unique_ptr` в C++ — вызывает деструктор объекта, потом `delete` память.

## Зачем нужен `Box` — три практические причины

### 1. Рекурсивные типы (уже разбирали подробно)

```rust
enum List {
    Cons(i32, Box<List>),
    Nil,
}
```

Без `Box` компилятор не может вычислить размер типа (бесконечная рекурсия в размере) — `Box` даёт фиксированный размер (указатель), разрывая цикл через уровень индирекции.

### 2. Trait objects — `Box<dyn Trait>`

```rust
trait Shape { fn area(&self) -> f64; }
struct Circle { r: f64 }
impl Shape for Circle { fn area(&self) -> f64 { self.r * self.r } }

println!("{}", size_of::<Box<dyn Shape>>()); // 16
println!("{}", size_of::<&dyn Shape>());      // 16
```

Уже разбирали `dyn Trait` подробно в теме про трейты — `Box<dyn Shape>` даёт владеющий вариант trait object'а (в отличие от `&dyn Shape`, которая просто заимствует). Обрати внимание: размер — **16 байт**, не 8, потому что это "толстый указатель" (fat pointer): один указатель на данные + один указатель на vtable. Это именно то, что позволяет `Box<dyn Trait>` не знать конкретный тип на этапе компиляции, но всё равно корректно вызывать `Drop` для настоящего типа при уничтожении (vtable содержит указатель и на `drop`, не только на методы трейта — уже упоминал это в теме про "классы").

### 3. Перенос больших значений из стека в кучу

Если структура очень большая и часто перемещается между функциями по значению, оборачивание в `Box` может быть дешевле — перемещается только указатель (8 байт), а не вся структура целиком:

```rust
struct Huge { data: [u8; 1_000_000] }

fn takes_huge(h: Box<Huge>) { /* перемещается 8 байт, не мегабайт */ }
```

Аналог осознанного решения "положить в кучу через `new`/`unique_ptr`" в C++, когда объект слишком большой для стека или частого копирования по значению.

## `Box<[T]>` — boxed slice, легче `Vec<T>`

```rust
println!("{}", size_of::<Box<[i32]>>()); // 16
println!("{}", size_of::<Vec<i32>>());    // 24
```

`Box<[T]>` — это фиксированный по размеру срез в куче: указатель + длина (16 байт, толстый указатель, как и `Box<dyn Trait>`). `Vec<T>` — это указатель + длина + **capacity** (24 байта), потому что `Vec` может расти. Если известно, что коллекция больше не будет менять размер, `vec.into_boxed_slice()` даёт чуть более компактное представление — мелкая, но иногда значимая оптимизация памяти при хранении множества коллекций (например, кэш строк, где рост больше не нужен).

## `Box::leak` и `Box::into_raw`/`Box::from_raw` — мост в unsafe-мир, релевантно для FFI

Это уже прямо связано с твоей темой интеропа с C++:

```rust
// Box::leak -- намеренная утечка, получаем 'static ссылку
let boxed = Box::new(String::from("живёт вечно"));
let leaked: &'static mut String = Box::leak(boxed);
leaked.push_str("!");
println!("{leaked}"); // живёт вечно!

// Box::into_raw / Box::from_raw -- мост в unsafe/FFI мир
let b = Box::new(100);
let raw: *mut i32 = Box::into_raw(b); // теперь Rust не отвечает за память
unsafe {
    println!("через сырой указатель: {}", *raw); // 100
    let reclaimed = Box::from_raw(raw); // забираем обратно под управление Rust
    println!("reclaimed: {reclaimed}"); // 100
} // reclaimed корректно дропается здесь
```

`Box::into_raw` — "отпускает" память из-под контроля Rust, отдавая сырой указатель (`*mut T`) — именно так передают Rust-выделенную память через FFI-границу в C/C++-код, который потом должен либо сам управлять этой памятью, либо вернуть указатель обратно в Rust через `Box::from_raw`, чтобы тот снова начал следить за освобождением. Забыть вызвать `Box::from_raw` на своей стороне — это осознанная утечка (у `Box::leak` та же природа, только специально для случаев, когда объект должен жить до конца программы, например синглтон конфигурации). Здесь Rust не защищает тебя автоматически — ты явно вышел в `unsafe`, взяв на себя контракт "я лично гарантирую, что этот указатель употребляется корректно", ровно как при работе с сырыми указателями в C++.

## Сравнение с `unique_ptr` — таблица

| |C++ `unique_ptr<T>`|Rust `Box<T>`|
|---|---|---|
|Владение|Единоличное|Единоличное|
|Копирование|Запрещено (move-only)|Запрещено (move-only), `Clone` — явный глубокий клон|
|Автоматическое освобождение|Деструктор при выходе из scope|`Drop` при выходе из scope|
|Custom deleter|Есть (второй параметр шаблона)|Нет отдельного механизма — переопределяется через собственный `Drop` на обёртывающем типе|
|Поддержка полиморфизма|`unique_ptr<Base>`, хранящий `Derived*`|`Box<dyn Trait>` — trait object вместо наследования|
|Освобождение памяти вручную / передача во внешний код|`.release()`|`Box::into_raw`|
|Взятие сырого указателя обратно под управление|`unique_ptr<T>(raw_ptr)` конструктор|`Box::from_raw` (unsafe)|
|Намеренная утечка|`.release()` без последующего delete|`Box::leak`|
|nullable по умолчанию|Да (`nullptr` — валидное состояние)|Нет — `Box<T>` всегда указывает на валидные данные; отсутствие значения выражается через `Option<Box<T>>`|

Последняя строка — важное структурное отличие: в C++ `unique_ptr<T>` **может** быть пустым (`nullptr`) в любой момент, и это одна из типичных причин null-pointer dereference багов. `Box<T>` в Rust **не может** быть "пустым" — если нужно смоделировать "либо есть значение, либо нет", используется `Option<Box<T>>` — то самое niche-оптимизированное представление, которое разбирали в теме про enum (занимает те же 8 байт, что и просто `Box<T>`, `None` кодируется нулевым указателем).
