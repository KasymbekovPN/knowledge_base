## Передача по значению (by value)

```rust
fn take_value(v: Vec<i32>) {
    println!("{:?}", v);
} // v уничтожается здесь

let data = vec![1, 2, 3];
take_value(data);
// data здесь больше недоступна — moved
```

Это прямое продолжение move-семантики из первой части разговора. В C++ передача по значению **всегда** означает копию (если не написать `T&&` и не вызвать `std::move` явно на стороне вызывающего). В Rust передача по значению **по умолчанию — move**, если тип не реализует `Copy`:

```rust
fn take_copy(x: i32) { println!("{x}"); }

let n = 5;
take_copy(n);
println!("{n}"); // ОК! i32 — Copy, значит это была копия, не move
```

Так что "передача по значению" в Rust — это на самом деле два разных случая в зависимости от типа, а не один как в C++:

|Тип параметра|Что происходит|C++ аналог|
|---|---|---|
|Реализует `Copy` (`i32`, `f64`, `bool`, простые struct с `#[derive(Copy)]`)|Копия, оригинал остаётся доступен|передача по значению примитива|
|Не реализует `Copy` (`String`, `Vec`, `Box`, большинство struct)|Move, оригинал становится недействителен|передача по значению с последующим `std::move` на месте вызова, либо неявная копия, если `std::move` забыли|

## Передача по неизменяемой ссылке — `&T`

```rust
fn print_len(v: &Vec<i32>) {
    println!("{}", v.len());
}

let data = vec![1, 2, 3];
print_len(&data);
println!("{:?}", data); // data всё ещё доступна — только заимствовали
```

Прямой аналог `const T&` в C++:

```cpp
void print_len(const std::vector<int>& v) {
    std::cout << v.size();
}
```

Разница в гарантиях та же, что обсуждали для borrowing вообще: `const&` в C++ **можно обойти** через `const_cast` или через отдельный неконстантный алиас на тот же объект где-то ещё в программе — компилятор не проверяет отсутствие таких алиасов. `&T` в Rust — компилятор **гарантирует**, что пока жива эта неизменяемая ссылка, никто не сможет получить `&mut T` на тот же объект нигде в программе.

## Передача по изменяемой ссылке — `&mut T`

```rust
fn add_element(v: &mut Vec<i32>) {
    v.push(4);
}

let mut data = vec![1, 2, 3];
add_element(&mut data);
println!("{:?}", data); // [1, 2, 3, 4]
```

Аналог `T&` (неконстантная ссылка) в C++:

```cpp
void add_element(std::vector<int>& v) {
    v.push_back(4);
}
```

Ключевое отличие уже знакомо: `&mut T` в Rust — это **эксклюзивный** доступ. Пока функция держит `&mut data`, компилятор гарантирует, что вообще никто больше — ни другая `&mut`, ни `&` — не имеет доступа к `data` одновременно. В C++ ссылку `T&` можно свободно алиасить сколько угодно раз, и гонки данных при многопоточном доступе или инвалидация итераторов при модификации через один алиас, пока читаешь через другой — целиком на программисте.

## Модификатор `mut` — не такой, как `const` в C++, а его инверсия

Вот важный концептуальный сдвиг. В C++ по умолчанию всё изменяемо, и `const` — это то, что ты **добавляешь**, чтобы запретить изменение. В Rust по умолчанию всё **неизменяемо** (immutable), и `mut` — это то, что ты добавляешь, чтобы **разрешить** изменение:

```rust
let x = 5;
x = 6; // ОШИБКА: cannot assign twice to immutable variable

let mut y = 5;
y = 6; // ОК
```

`mut` — это модификатор **на самой переменной (binding)**, а не на типе, и это тоже отличается от C++, где `const` — часть типа:

```rust
fn modify(mut v: Vec<i32>) -> Vec<i32> {  // mut здесь — это можно менять v локально внутри функции
    v.push(99);  // разрешено, потому что параметр помечен mut
    v            // но это не влияет на то, что видит вызывающий — v пришла по значению (moved)
}
```

Важный нюанс: `mut` у параметра, принятого **по значению**, — это чисто локальное разрешение мутировать свою копию/перемещённый объект внутри тела функции. Это не то же самое, что `&mut T`. Если функция получает `v: Vec<i32>` (без `mut`), она вообще не сможет вызвать `v.push(...)`, даже несмотря на то, что она полностью владеет `v` — потому что связывание `v` неизменяемое, только владение есть.

```rust
fn broken(v: Vec<i32>) {
    v.push(1); // ОШИБКА: cannot borrow `v` as mutable, `v` is not declared as mutable
}

fn works(mut v: Vec<i32>) {
    v.push(1); // OK
}
```

## Сводная таблица — три способа передачи + модификатор

|Rust|Что происходит|C++ аналог|Можно изменять объект внутри функции?|Виден результат снаружи?|
|---|---|---|---|---|
|`fn f(x: T)`|move/copy|`void f(T x)`|Нет (без `mut`)|Нет|
|`fn f(mut x: T)`|move/copy + локальная мутабельность|`void f(T x)` + `x` не `const`|Да, но только своя копия|Нет|
|`fn f(x: &T)`|заимствование, read-only|`void f(const T& x)`|Нет|—|
|`fn f(x: &mut T)`|эксклюзивное заимствование|`void f(T& x)`|Да|Да|

## `mut` на полях структуры — то, чего нет вообще

В C++ можно пометить отдельное поле `mutable`, чтобы его можно было менять даже через `const`-объект (классика — кэш, ленивая инициализация, мьютексы в const-методах):

```cpp
class Widget {
    mutable std::mutex m; // можно лочить даже в const методах
    mutable int cache_ = -1;
};
```

В Rust **нет** модификатора `mut` на уровне отдельного поля. Мутабельность — это свойство **всего связывания целиком**: либо вся переменная `mut`, и тогда доступны все поля на запись, либо ничего не доступно на запись. Точечная "мутабельность одного поля независимо от остальных" реализуется через **interior mutability** — типы `Cell<T>` и `RefCell<T>`, которые оборачивают конкретное поле и разрешают изменение через `&self` (не `&mut self`), перенося проверку заимствования с этапа компиляции на рантайм:

```rust
use std::cell::RefCell;

struct Widget {
    cache: RefCell<i32>, // "как mutable в C++", но explicit и с рантайм-проверкой вместо compile-time
}

impl Widget {
    fn get_cached(&self) -> i32 { // &self, не &mut self!
        *self.cache.borrow_mut() += 1;
        *self.cache.borrow()
    }
}
```

Это прямой концептуальный аналог `mutable` в C++, только вместо "доверься программисту" — `RefCell` паникует в рантайме, если правило "1 writer XOR N readers" нарушено (например, два одновременных `borrow_mut()`), а не позволяет UB молча.

## `ref` / `ref mut` — модификаторы в pattern matching

Отдельный контекст, где встречается похожая механика, — деструктуризация:

```rust
let pair = (String::from("a"), String::from("b"));

match pair {
    (ref a, ref b) => println!("{a} {b}"), // берём ссылки, не забираем владение
}
// pair всё ещё доступна целиком
```

Это нужно, когда `match`/`let`-деструктуризация иначе попыталась бы **переместить** значения из `pair` наружу. На практике сейчас чаще используют match ergonomics — компилятор сам подставляет нужное заимствование, если матчишь по `&pair`:

```rust
match &pair {
    (a, b) => println!("{a} {b}"), // a, b автоматически стали &String
}
```

`ref`/`ref mut` явно всё ещё нужны в редких случаях, где ergonomics не справляются (сложные вложенные паттерны), но по умолчанию идиоматичный код использует автоматический вывод через `&`/`&mut` в самом `match`.
