## Ошибка 1: попытка мутировать, пока держишь read-ссылку

Самая частая. C++-привычка — взять ссылку на элемент коллекции и тут же модифицировать саму коллекцию.

```rust
let mut v = vec![1, 2, 3];
let first = &v[0];
v.push(4); // ОШИБКА: cannot borrow `v` as mutable because it is also borrowed as immutable
println!("{first}");
```

```
error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable
```

**Почему это не придирка компилятора:** `push` может вызвать реаллокацию буфера `Vec` — тогда `first` стал бы dangling pointer'ом. В C++ это ровно тот классический баг с инвалидацией итераторов/ссылок, который просто молча компилируется и стреляет в рантайме.

**Идиоматичный fix — сузить область жизни ссылки:**

```rust
let mut v = vec![1, 2, 3];
{
    let first = &v[0];
    println!("{first}");
} // first умирает здесь
v.push(4); // теперь OK
```

Или ещё лучше — не держать ссылку дольше, чем нужно, а скопировать значение сразу, если тип дешёвый (`i32` — `Copy`):

```rust
let mut v = vec![1, 2, 3];
let first = v[0]; // копия значения, не ссылка
v.push(4); // OK, first — независимая копия
println!("{first}");
```

Это не "костыль через .clone()" — для `Copy`-типов копирование значения вместо хранения ссылки часто и есть идиоматичное решение, а не обход правил.

## Ошибка 2: возврат ссылки на локальную переменную

Прямое продолжение того, что уже обсуждали в контексте lifetimes, но именно так это чаще всего впервые встречается на практике:

```rust
fn make_string() -> &String { // ОШИБКА уже в сигнатуре
    let s = String::from("hello");
    &s
} // s уничтожается здесь — возвращать на неё ссылку некуда
```

```
error[E0106]: missing lifetime specifier
```

**Разбор:** компилятор даже не доходит до тела функции — он видит `&String` в возвращаемом типе без lifetime-параметра и сразу спрашивает "ссылка на что?". Если явно написать lifetime, ошибка сдвинется в тело:

```rust
fn make_string<'a>() -> &'a String {
    let s = String::from("hello");
    &s // ОШИБКА: cannot return reference to local variable `s`
}
```

**Идиоматичный fix — вернуть владение, а не ссылку:**

```rust
fn make_string() -> String {
    let s = String::from("hello");
    s // move наружу, никакого clone не нужно
}
```

Это ключевой ментальный сдвиг: в C++ ты рефлекторно избегаешь возврата по значению из-за страха лишней копии (отсюда привычка возвращать ссылки/указатели). В Rust `return s` — это **move**, не копия, поэтому ничего не стоит возвращать `String`/`Vec`/что угодно по значению — компилятор сам оптимизирует это в NRVO-подобное поведение, где может.

## Ошибка 3: два `&mut` одновременно ("двойное заимствование")

```rust
let mut v = vec![1, 2, 3];
let a = &mut v;
let b = &mut v; // ОШИБКА: cannot borrow `v` as mutable more than once at a time
a.push(4);
b.push(5);
```

Здесь C++-интуиция вообще не видит проблемы — два неконстантных указателя на один объект это нормально, ответственность за отсутствие гонки на программисте.

**Идиоматичный fix — не пересекать время жизни заимствований:**

```rust
let mut v = vec![1, 2, 3];
{
    let a = &mut v;
    a.push(4);
} // a умер
{
    let b = &mut v;
    b.push(5);
}
```

**Или, если реально нужно два независимых мутабельных доступа к разным частям одной коллекции** — это отдельный частый кейс, для него есть готовые методы вместо ручного обхода правил:

```rust
let mut v = vec![1, 2, 3, 4];
let (left, right) = v.split_at_mut(2); // два независимых &mut [i32] на разные half
left[0] = 100;
right[0] = 200;
```

`split_at_mut` внутри использует `unsafe`, но предоставляет **безопасный** API наружу — компилятор доверяет этой конкретной операции, потому что она статически гарантирует непересекающиеся диапазоны. Это общий паттерн в Rust: сложная логика инкапсулируется в маленький `unsafe`-блок с безопасной оберткой, а не пропихивается через борьбу с borrow checker на каждом вызове.

## Ошибка 4: попытка вернуть ссылку на поле из метода, который забирает `&mut self`, и потом ещё раз дёрнуть `self`

```rust
struct Container {
    items: Vec<i32>,
}

impl Container {
    fn first_mut(&mut self) -> &mut i32 {
        &mut self.items[0]
    }

    fn broken(&mut self) {
        let first = self.first_mut();
        self.items.push(99); // ОШИБКА: cannot borrow `self.items` as mutable more than once
        println!("{first}");
    }
}
```

**Почему:** `first` — это `&mut i32`, заимствованный из `self.items`. Пока `first` жив, весь `self` (точнее, `self.items`) считается заимствованным изменяемо. `push` требует ещё одного `&mut self.items` — конфликт, ровно как в Ошибке 1, только через метод.

**Идиоматичный fix — сузить область жизни, как и раньше:**

```rust
fn fixed(&mut self) {
    {
        let first = self.first_mut();
        println!("{first}");
    } // first умер
    self.items.push(99); // OK
}
```

## Ошибка 5: итерация с одновременной модификацией коллекции

```rust
let mut v = vec![1, 2, 3, 4, 5];
for x in &v {
    if *x == 3 {
        v.push(100); // ОШИБКА: cannot borrow `v` as mutable
    }
}
```

В C++ это тот самый классический "iterator invalidation" — код скомпилируется, `push_back` может реаллоцировать буфер, и итератор `for` цикла станет dangling. UB, которое иногда даже не падает сразу, а тихо портит данные.

**Идиоматичный fix — собрать изменения отдельно, применить после цикла:**

```rust
let mut v = vec![1, 2, 3, 4, 5];
let mut to_add = Vec::new();
for x in &v {
    if *x == 3 {
        to_add.push(100);
    }
}
v.extend(to_add);
```

**Или использовать `retain`/`drain`/индексы вместо ссылок на элементы**, когда логика позволяет:

```rust
let mut v = vec![1, 2, 3, 4, 5];
v.retain(|&x| x != 3); // убрать все тройки — без ручной борьбы с итератором вообще
```

## Ошибка 6: замыкание живёт дольше, чем захваченная им ссылка

```rust
fn make_closure() -> impl Fn() -> i32 {
    let x = 10;
    || x + 1 // ОШИБКА, если бы захватывали по ссылке — closure may outlive borrowed value `x`
}
```

На самом деле для `i32` (Copy-тип) компилятор сам захватит по значению и это скомпилируется без warning'ов в актуальных редакциях — но с чем-то не-`Copy` проблема всплывает сразу:

```rust
fn make_closure() -> impl Fn() -> String {
    let s = String::from("hello");
    || format!("{s}!") // ОШИБКА: closure may outlive the current function, but it borrows `s`
}
```

**Идиоматичный fix — `move`, чтобы замыкание забрало владение, а не заимствовало:**

```rust
fn make_closure() -> impl Fn() -> String {
    let s = String::from("hello");
    move || format!("{s}!") // s перемещена внутрь замыкания, живёт столько же, сколько оно само
}
```

Это то самое `move`, которое разбирали в теме про замыкания — здесь наглядно видно, зачем оно нужно на практике, а не просто как синтаксис.

## Ошибка 7: struct, хранящая ссылку — lifetime-параметр расползается по всему коду

```rust
struct Parser {
    input: &str, // ОШИБКА: missing lifetime specifier
}
```

Компилятор требует явный lifetime:

```rust
struct Parser<'a> {
    input: &'a str,
}

impl<'a> Parser<'a> {
    fn new(input: &'a str) -> Self {
        Parser { input }
    }
}
```

Дальше начинающие часто пытаются использовать `Parser` так, что исходная строка не переживает парсер — и получают каскад ошибок про lifetimes, которые расползаются по всей цепочке вызовов, если структура с заимствованием передаётся глубже.

**Идиоматичный fix для большинства практических случаев — не хранить ссылку, хранить владеющий тип:**

```rust
struct Parser {
    input: String, // владеет данными сам — никаких lifetime-параметров вообще
}

impl Parser {
    fn new(input: String) -> Self {
        Parser { input }
    }
    // или fn new(input: &str) -> Self { Parser { input: input.to_string() } }
}
```

Это **самый частый совет** новичкам: struct с lifetime-параметром — это продвинутая техника для конкретных случаев производительности (парсеры без аллокаций, zero-copy-десериализация типа `serde` с `#[serde(borrow)]`), а не то, с чего стоит начинать. Если borrow checker разросся до нечитаемых сигнатур с кучей `'a` — почти всегда правильный ответ "просто владей данными", а не "распутать lifetimes любой ценой".

## Общий принцип, который стоит унести из всех примеров

Порядок разбора ошибки borrow checker должен быть таким:

1. **Можно ли сузить scope заимствования** (Ошибки 1, 3, 4) — часто достаточно `{}` блока или ранней ре-структуризации кода.
2. **Можно ли вернуть/хранить владение вместо ссылки** (Ошибки 2, 7) — обычно самый чистый fix, особенно для новичка: move дешёвый, не нужно бояться "лишней копии" как в C++.
3. **Нужен ли `move` для замыкания** (Ошибка 6) — если замыкание должно пережить текущий scope.
4. **Есть ли готовый безопасный API под эту задачу** (Ошибка 5, `split_at_mut` в Ошибке 3) — стандартная библиотека часто уже решила именно этот конфликт заимствований через `unsafe` внутри и безопасную обёртку снаружи.
5. **`.clone()`/`Rc`/`RefCell` — только если 1-4 реально не подходят**, и это осознанный компромисс (лишняя аллокация или рантайм-проверка), а не первая попытка "лишь бы скомпилировалось". Именно бездумное разбрасывание `.clone()` — то, что превращает Rust-код в "C++ с лишним синтаксисом", теряя часть смысла системы владения.
