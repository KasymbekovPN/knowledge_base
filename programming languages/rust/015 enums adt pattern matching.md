## ADT — что означает термин применительно к `enum`

ADT (algebraic data type) — это не что-то экзотическое, а просто способ классифицировать типы на два вида:

- **Произведение типов (product type)** — "И": объект содержит **все** перечисленные поля одновременно. Это `struct` — уже разбирали.
- **Сумма типов (sum type)** — "ИЛИ": объект — это **ровно один** из перечисленных вариантов, и никогда не может быть сразу несколькими. Это `enum` в Rust.

C++ отдельно поддерживает только "произведение" (`struct`/`class`), а нормальной "суммы" исторически не было вообще — `enum`/`enum class` в C++ это просто именованные целые числа, ни грамма данных на вариант, а `union` — небезопасное низкоуровневое перекрытие памяти без тега вообще (какое поле активно — на совести программиста). `std::variant` (C++17) — первая настоящая попытка дать C++ ADT, но она добавлена библиотекой поверх языка, а не встроена как часть синтаксиса.

## C-like enum — то, что напрямую совпадает с C++

```rust
#[derive(Debug)]
enum Direction {
    North,
    South,
    East,
    West,
}
```

Здесь `size_of::<Direction>() == 1` — компилятор выбирает минимальный размер, достаточный, чтобы закодировать 4 варианта (тут хватает 1 байта). Прямой аналог `enum class Direction { North, South, East, West };` в C++. Пока в `enum` нет данных на вариант — разница с C++ минимальна.

## `enum` как настоящий ADT — у каждого варианта СВОИ данные

Вот где расхождение становится принципиальным:

```rust
#[derive(Debug)]
enum Message {
    Quit,                       // unit-вариант — без данных
    Move { x: i32, y: i32 },    // struct-вариант — именованные поля
    Write(String),              // tuple-вариант — одно поле
    ChangeColor(i32, i32, i32), // tuple-вариант — три поля
}

fn process(msg: &Message) -> String {
    match msg {
        Message::Quit => "выход".to_string(),
        Message::Move { x, y } => format!("двигаюсь в ({x}, {y})"),
        Message::Write(text) => format!("пишу: {text}"),
        Message::ChangeColor(r, g, b) => format!("цвет: #{r:02x}{g:02x}{b:02x}"),
    }
}
```

Вывод для набора сообщений:

```
выход
двигаюсь в (10, 20)
пишу: привет
цвет: #ff0000
```

Один `enum` объединяет четыре структурно совершенно разных набора данных под одним типом. Это то, для чего в C++ раньше приходилось городить либо иерархию классов с виртуальным `process()` (полиморфизм через наследование — но тогда нельзя легко получить исчерпывающую проверку компилятором, и объекты живут в куче за указателями), либо вручную писать tagged union (enum-тег + union с данными + вечная опасность прочитать не то поле union, потому что тег и union никак формально не связаны компилятором).

`std::variant` в C++17 — ближе всего к этому по духу:

```cpp
struct Move { int x, y; };
struct Write { std::string text; };
struct ChangeColor { int r, g, b; };
using Message = std::variant<std::monostate, Move, Write, ChangeColor>;

std::string process(const Message& msg) {
    return std::visit([](auto&& m) -> std::string {
        using T = std::decay_t<decltype(m)>;
        if constexpr (std::is_same_v<T, std::monostate>) return "выход";
        else if constexpr (std::is_same_v<T, Move>) return "двигаюсь в (" + std::to_string(m.x) + ", " + std::to_string(m.y) + ")";
        // ...
    }, msg);
}
```

Работает похоже, но: типы вариантов объявляются отдельными структурами вовне, `std::visit` с `if constexpr`/`decltype` — не то что легко читается по сравнению с `match`, и, что важнее, **компилятор не заставляет** тебя обработать каждый вариант при добавлении нового типа в `variant` — если забыл ветку в `if constexpr`-цепочке, это либо тихо ничего не делает, либо падает в рантайме, а не в компиляции (в отличие от `match`, где недостающий вариант — жёсткая ошибка компиляции, уже разбирали в теме про `match`).

## Размер `enum` в памяти — тег + место под самый большой вариант

```rust
println!("size_of Message = {}", size_of::<Message>()); // 32
```

Механически: компилятор выделяет память под **тег** (какой вариант активен сейчас — обычно 1 машинное слово или меньше, зависит от числа вариантов) плюс место, достаточное, чтобы вместить **самый крупный** вариант (у `Message` это `Move { x: i32, y: i32 }` или `ChangeColor(i32,i32,i32)`, плюс выравнивание). Это ровно то же самое, что происходит с `union`+тег в C++ вручную — просто компилятор Rust делает это автоматически и безопасно, гарантируя, что прочитать поля можно только после проверки тега через `match`.

## Niche optimization — оптимизация, которой в ручном C++ tagged union нет

```rust
println!("{}", size_of::<Option<&i32>>()); // 8
println!("{}", size_of::<&i32>());          // 8
println!("{}", size_of::<Option<i32>>());   // 8 (i32 занимает 4, но выравнивание даёт 8)
println!("{}", size_of::<Option<Box<i32>>>()); // 8
```

`Option<&i32>` занимает **ровно столько же**, сколько сама `&i32` — ни байта под отдельный тег! Компилятор знает, что валидная ссылка **никогда** не бывает нулевым адресом, поэтому кодирует `None` как нулевой указатель, а `Some(ptr)` — как сам ненулевой указатель. Тега вообще нет — используется "непредставимое" значение исходного типа (niche) как маркер отсутствия. Это работает для `&T`, `Box<T>`, `NonNull<T>`, `NonZeroU32` и подобных типов автоматически, без каких-либо усилий с твоей стороны. В C++ ручной tagged union никогда не получит такую оптимизацию сам по себе — там либо явный nullable-указатель (что и так место экономит по той же причине, но без формальной гарантии типа "непустое значение"), либо `std::optional<T&>` (которого, кстати, до недавнего времени не существовало вообще — ссылки нельзя было напрямую класть в `std::optional`).

## Рекурсивные enum — требуют явной indirection

```rust
enum List {
    Cons(i32, List), // ОШИБКА
    Nil,
}
```

Ошибка:

```
error[E0072]: recursive type `List` has infinite size
help: insert some indirection (e.g., a `Box`, `Rc`, or `&`) to break the cycle
```

Логично: если `List` содержит `List` напрямую (не через указатель), размер типа был бы бесконечным — компилятор не может вычислить фиксированный размер на этапе компиляции. В C++ структура, содержащая сама себя по значению, тоже не компилируется по той же причине (`incomplete type` ошибка) — единственный способ и там, и там — уровень индирекции через указатель:

```rust
#[derive(Debug)]
enum List {
    Cons(i32, Box<List>), // Box — указатель на кучу, размер известен (просто размер указателя)
    Nil,
}

use List::{Cons, Nil};

impl List {
    fn sum(&self) -> i32 {
        match self {
            Cons(v, rest) => v + rest.sum(),
            Nil => 0,
        }
    }
}

let list = Cons(1, Box::new(Cons(2, Box::new(Cons(3, Box::new(Nil))))));
println!("{:?}", list);   // Cons(1, Cons(2, Cons(3, Nil)))
println!("sum = {}", list.sum()); // 6
```

Прямой аналог классического связного списка в C++ (`struct Node { int value; Node* next; };`), только `Box<List>` гарантирует единоличное владение и автоматическое освобождение — никакого ручного `delete`, никакой возможности забыть освободить память или удалить дважды.

## Как устроены `Option`/`Result` изнутри — теперь это можно объяснить буквально

```rust
enum MyOption<T> {
    MySome(T),
    MyNone,
}

enum MyResult<T, E> {
    MyOk(T),
    MyErr(E),
}
```

Это (с точностью до реальных имён `Some`/`None`/`Ok`/`Err`) буквально то, как определены `Option<T>` и `Result<T, E>` в стандартной библиотеке — не встроенная магия языка, а обычные generic-`enum`, которые ты уже умеешь писать сам. Именно поэтому `match` на `Option`/`Result` работает точно так же, как на любом своём `enum` — единая механика, никакого спецсинтаксиса.

## `#[repr(...)]` — явные дискриминанты для FFI

```rust
#[repr(u16)]
#[derive(Debug)]
enum HttpStatus {
    Ok = 200,
    NotFound = 404,
    ServerError = 500,
}

println!("{}", HttpStatus::NotFound as u16); // 404
```

Аналог `enum class HttpStatus : uint16_t { Ok = 200, NotFound = 404, ServerError = 500 };` в C++. Важно: `#[repr(...)]` нужен именно тогда, когда `enum` **не несёт данных** на вариантах и должен иметь предсказуемый ABI-совместимый layout (для FFI с C-кодом, что прямо релевантно твоей теме интеропа с C++). Для `enum` с данными на вариантах (как `Message` выше) `#[repr]` работает иначе (`#[repr(C)]` даёт layout, совместимый с C-style tagged union, но это отдельная, более редкая тема).

## `matches!` — быстрая проверка одного паттерна без `match`/`if let`

```rust
let x: MyOption<i32> = MyOption::MySome(5);
let is_some = matches!(x, MyOption::MySome(_));
println!("{is_some}"); // true
```

Макрос `matches!` разворачивается примерно в `match x { MyOption::MySome(_) => true, _ => false }` — удобно, когда нужен просто `bool`-ответ "совпадает ли с паттерном", без извлечения данных. Прямого однострочного аналога в C++ (даже с `std::variant::index()` или `std::holds_alternative<T>(v)`) — по сути то же самое, просто здесь работает с произвольными паттернами, а не только с "какой конкретный тип активен".

## Главный практический вывод — та самая гарантия рефакторинга

Возвращаясь к тому, что уже подчёркивали в теме про `match`: добавь сегодня `Message::Resize(u32, u32)` в `enum` — и каждый `match` по всей кодовой базе, где не стоит `_`, **откажется компилироваться**, пока не обработаешь новый вариант. В C++ с `enum class` + `switch` это в лучшем случае `-Wswitch` warning (который часто не включён как error), а с `std::variant` + ручным `if constexpr` — вообще ничего, тихий баг. Именно эта гарантия — причина, почему в Rust `enum` активно используют не только для простых "тегов", но и как основной механизм моделирования состояний (состояние сетевого соединения, узел AST, результат парсинга) — во всех местах, где в C++ разработчик рефлекторно тянется к иерархии классов с виртуальными функциями.
