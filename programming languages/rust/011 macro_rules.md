Макросы — тема, которая в Rust устроена принципиально иначе, чем в C/C++, хотя внешне (`#define` vs `macro_rules!`) может показаться похожей.

## Главное отличие от C-препроцессора: макросы Rust работают на уровне AST, а не текста

В C/C++ макрос — это **текстовая подстановка** на этапе препроцессинга, до того как компилятор вообще увидел синтаксис языка:

```cpp
#define SQUARE(x) x * x

int a = SQUARE(1 + 2); // раскрывается в 1 + 2 * 1 + 2 = 5, а не 9!
```

Классическая ловушка — препроцессор ничего не знает про приоритет операций, потому что просто копирует текст. Правильная версия требует скобок-костылей:

```cpp
#define SQUARE(x) ((x) * (x))
```

В Rust макросы работают **после** парсинга в токены (точнее — в поток токенов с сохранённой структурой, TokenStream), поэтому такой проблемы нет в принципе:

```rust
macro_rules! square {
    ($x:expr) => { $x * $x };
}

let a = square!(1 + 2); // корректно раскрывается с учётом границ выражения → 9
```

`$x:expr` говорит компилятору: "здесь целое выражение", и при подстановке оно автоматически оборачивается так, будто в скобках — приоритет операций не ломается никогда.

## Два принципиально разных вида макросов

Rust различает **декларативные** макросы (`macro_rules!`) и **процедурные** макросы (три подвида). Это не стилистическая разница, а разный механизм работы.

## Декларативные макросы — `macro_rules!`

Это pattern matching на уровне синтаксиса — очень похоже на `match`, только матчится не значение, а структура кода.

```rust
macro_rules! greet {
    () => {
        println!("Привет!");
    };
    ($name:expr) => {
        println!("Привет, {}!", $name);
    };
}

greet!();               // Привет!
greet!("Pablo");         // Привет, Pablo!
```

Несколько "веток" (arms) — компилятор пробует их по порядку, как в `match`, пока не найдёт совпадающий паттерн по количеству/типу аргументов.

### Фрагментные спецификаторы (`:expr`, `:ident`, `:ty` и т.д.)

Каждый `$name:fragment_type` указывает, **что именно** может стоять на этом месте:

```rust
macro_rules! make_function {
    ($fn_name:ident, $ret_type:ty, $value:expr) => {
        fn $fn_name() -> $ret_type {
            $value
        }
    };
}

make_function!(get_answer, i32, 42);

fn main() {
    println!("{}", get_answer()); // 42
}
```

Основные спецификаторы: `expr` (выражение), `ident` (идентификатор), `ty` (тип), `pat` (паттерн), `block` (блок `{}`), `stmt` (statement), `path` (путь `a::b::c`), `literal` (литерал), `tt` (token tree — вообще любой кусок токенов, самый гибкий и часто используемый для рекурсивных макросов).

### Повторения (`$(...)*`) — то, ради чего чаще всего пишут макросы

Вот пример, который наглядно показывает, зачем нужны макросы там, где обычная функция не справится:

```rust
macro_rules! max_of {
    ($first:expr) => { $first };
    ($first:expr, $($rest:expr),+) => {
        {
            let rest_max = max_of!($($rest),+);
            if $first > rest_max { $first } else { rest_max }
        }
    };
}

let m = max_of!(3, 7, 2, 9, 4);
println!("{m}"); // 9
```

`$($rest:expr),+` — "один или более `expr`, разделённых запятой", `+` (одно или больше) / `*` (ноль или больше) / `?` (ноль или один) — как квантификаторы в regex, только на уровне синтаксиса. Такой макрос принимает **произвольное число аргументов**, чего обычная функция в Rust сделать не может — только через `Vec`/срез, что меняет способ вызова.

### Как этим объясняются знакомые макросы, которые уже использовали в разговоре

`println!`, `vec!`, `format!` — это всё `macro_rules!`-макросы из стандартной библиотеки, не встроенный синтаксис языка:

```rust
// упрощённая идея того, как устроен vec!
macro_rules! my_vec {
    ($($x:expr),* $(,)?) => {
        {
            let mut v = Vec::new();
            $(v.push($x);)*
            v
        }
    };
}

let v = my_vec![1, 2, 3]; // разворачивается в Vec::new() + три push
```

Именно поэтому `vec![1, 2, 3]` умеет принимать произвольное число элементов — это раскрывается компилятором в цикл `push`, а не является отдельной языковой конструкцией с переменным числом параметров.

## Отличие `!` — как отличить вызов макроса от вызова функции

`!` в конце имени — обязательный синтаксический маркер: `println!(...)` — макрос, `println(...)` без `!` — была бы обычная функция (и не скомпилировалось бы, потому что такой функции не существует). Это чисто визуальная гарантия — при чтении кода сразу видно, что здесь происходит разворачивание на этапе компиляции, а не обычный вызов.

## Макро-гигиена (macro hygiene) — то, чего в C++ препроцессоре нет вообще

Это одна из самых важных практических гарантий. В C:

```cpp
#define SWAP(a, b) { int tmp = a; a = b; b = tmp; }

int tmp = 5;
int x = 1;
SWAP(tmp, x); // раскрывается в { int tmp = tmp; tmp = x; x = tmp; } — сломано! tmp затирает себя
```

Классический баг с захватом имени переменной — макрос случайно "видит" и конфликтует с переменной вызывающего кода. В Rust каждое раскрытие макроса **гигиенично**: переменные, введённые внутри макроса, не видны снаружи и не конфликтуют с одноимёнными снаружи, даже если совпадает написание:

```rust
macro_rules! swap_broken_in_spirit {
    ($a:expr, $b:expr) => {
        {
            let tmp = $a;  // этот `tmp` изолирован от любого внешнего `tmp`
            $a = $b;
            $b = tmp;
        }
    };
}

let tmp = 5;
let mut x = 1;
let mut y = 2;
swap_broken_in_spirit!(x, y); // работает корректно, несмотря на внешнюю переменную tmp
println!("{x} {y} {tmp}"); // 2 1 5 — tmp снаружи не тронут
```

Гигиена работает автоматически, без специальных усилий со стороны автора макроса — это встроенное свойство системы макросов, а не что-то, что нужно обеспечивать вручную (как в C, где единственная защита — соглашение об именовании через подчёркивания или явные временные имена).

## Процедурные макросы — три подвида, гораздо мощнее `macro_rules!`

Процедурные макросы — это уже не pattern matching, а полноценная **функция на этапе компиляции**, которая принимает `TokenStream` и возвращает `TokenStream`. Пишутся в отдельном crate с `proc-macro = true`.

### 1. `derive`-макросы — уже видели их в этом разговоре

```rust
#[derive(Debug, Clone, PartialEq, Default)]
struct Point {
    x: f64,
    y: f64,
}
```

Каждый из `Debug`, `Clone`, `PartialEq`, `Default` — процедурный derive-макрос, который смотрит на структуру `Point` (поля, их типы) и генерирует соответствующую реализацию трейта автоматически. Своя реализация derive-макроса выглядит примерно так (сильно упрощённо):

```rust
// в отдельном proc-macro crate
#[proc_macro_derive(MyTrait)]
pub fn my_trait_derive(input: TokenStream) -> TokenStream {
    let ast = syn::parse(input).unwrap(); // парсим структуру через crate syn
    // анализируем ast.ident (имя типа), ast.data (поля)
    // генерируем impl через crate quote
    quote! {
        impl MyTrait for #name {
            fn my_method(&self) { /* ... */ }
        }
    }.into()
}
```

`syn` (парсинг Rust-кода в AST) и `quote` (генерация кода обратно в токены) — стандартная пара crate'ов для написания процедурных макросов, почти всегда используются вместе.

### 2. Атрибутные макросы (`#[attribute]`)

```rust
#[tokio::main]
async fn main() {
    // тело функции трансформируется макросом перед компиляцией
}
```

`#[tokio::main]` — атрибутный процедурный макрос, который оборачивает тело `async fn main` в код запуска рантайма tokio. Атрибутный макрос получает на вход **весь элемент**, к которому применён (в данном случае — всю функцию целиком), и может полностью переписать её.

### 3. Функцио-подобные процедурные макросы

```rust
let query = sql!(SELECT * FROM users WHERE id = 1);
```

Синтаксически похожи на `macro_rules!` (вызов через `!`), но реализованы процедурно — могут делать произвольный анализ на этапе компиляции, например проверять SQL-синтаксис прямо во время сборки, а не по правилам pattern matching.

## Сравнение с шаблонами и `constexpr` в C++ — где границы

Это важный вопрос "а зачем макросы, если есть generics/traits" (уже разбирали generics в контексте `impl Fn`). Ключевое отличие: **макросы работают с синтаксисом**, generics — **с типами**.

```rust
// generics — работает с типами, не может породить новый синтаксис
fn identity<T>(x: T) -> T { x }

// макрос — может генерировать произвольный код, включая новые имена функций/структур
macro_rules! make_getter {
    ($field:ident, $ty:ty) => {
        fn $field(&self) -> $ty { self.$field }
    };
}
```

В C++ ближайший аналог мощности макросов — это **шаблоны на этапе компиляции** (для типобезопасной генерации) плюс **препроцессор** (для генерации именованных сущностей, `X_MACRO`-паттерны) — то есть в C++ это два разных, слабо связанных механизма. В Rust вся эта область (типобезопасная генерация — generics/traits, синтаксическая генерация — макросы) сведена к двум чётким инструментам, каждый в своей нише, без пересечения областей ответственности, как в C++, где иногда шаблонную метапрограммированную мешанину (`enable_if`, SFINAE) используют именно потому, что макросы недостаточно безопасны для этой задачи, а `constexpr` недостаточно гибок.

`constexpr`-функции в C++ (вычисление на этапе компиляции) ближе по духу не к макросам Rust, а к тому, что в Rust называется `const fn`:

```rust
const fn square(x: i32) -> i32 { x * x }
const RESULT: i32 = square(5); // вычислено на этапе компиляции
```

Это отдельная тема от макросов — `const fn` про **вычисление значений** во время компиляции, макросы — про **генерацию кода**.

## Когда использовать что — практическое правило

|Задача|Инструмент|
|---|---|
|Переменное число аргументов, DSL-подобный синтаксис|`macro_rules!`|
|Автоматическая реализация трейта по структуре данных|`derive`-макрос|
|Трансформация целой функции/модуля (например, инъекция рантайма)|атрибутный макрос|
|Полиморфизм по типу без генерации нового синтаксиса|generics + traits (не макрос)|
|Вычисление константы на этапе компиляции|`const fn` (не макрос)|
|Просто хочешь избежать дублирования похожего, но не идентичного кода|сначала подумай, не решается ли это generics/traits — макрос последний вариант|

Последняя строка — важный культурный момент в Rust-сообществе: макросы считаются более "тяжёлым" инструментом, чем в C/C++, где `#define` использовали для всего подряд (константы, инлайнинг, дженерик-подобный код). В Rust для констант есть `const`, для инлайнинга — `#[inline]`, для дженерик-кода — generics, и к макросам прибегают только когда ни один из этих механизмов не подходит именно из-за необходимости синтаксической генерации.
