Демангляция (demangling) — это обратное преобразование «искажённого» (mangled) имени, которое генерирует компилятор C++, обратно в человекочитаемую сигнатуру. Чтобы понять демангляцию, надо сначала понять, зачем имена вообще искажаются.

## Зачем компилятор искажает имена (mangling)

Линкер (компоновщик) работает с именами символов как с простыми строками и **ничего не знает о C++** — ни о перегрузке функций, ни о namespace, ни о шаблонах, ни о типах параметров. Для него символ — это просто уникальное имя.

Но в C++ имя функции _само по себе_ не уникально:

```cpp
void f(int);
void f(double);      // то же имя f, но другая функция (перегрузка)
void f(int, char);   // и ещё одна

namespace A { void f(int); }   // и ещё — в другом namespace
```

Если бы все они назывались просто `f`, линкер не смог бы их различить — конфликт имён. Поэтому компилятор **кодирует в имя символа всю информацию**, делающую его уникальным: пространство имён, имя функции, типы и количество параметров, const-квалификаторы, шаблонные аргументы. Это и есть mangling — «искажение» имени.

## Как это выглядит

Возьмём пример из нашего разбора отладки. Имя `counting_coro(int)` компилятор закодировал так:

```
_Z13counting_coroi
```

Расшифровка (схема Itanium ABI, которую используют GCC и Clang):

- `_Z` — префикс, помечающий искажённое имя C++
- `13` — длина следующего идентификатора (13 символов в «counting_coro»)
- `counting_coro` — само имя
- `i` — параметр типа `int` (`i` = int, `d` = double, `c` = char, ...)

Более сложный пример — функция в namespace:

```cpp
namespace A { void f(double, int); }
// -> _ZN1A1fEdi
//    _Z  N 1A 1f E d i
//        |  |  |  | | └─ int
//        |  |  |  | └─── double
//        |  |  |  └───── конец вложенности
//        |  |  └──────── f (1 символ)
//        |  └─────────── A (1 символ)
//        └────────────── N = вложенное имя (namespace/класс)
```

Видно, как в строку «упакованы» namespace `A`, имя `f` и типы параметров `double, int`. Шаблоны кодируются ещё длиннее и быстро становятся нечитаемыми.

## Демангляция — обратный путь

Демангляция превращает `_Z13counting_coroi` обратно в `counting_coro(int)`. Это нужно человеку — в выводе линкера, отладчика, профайлера, стек-трейсах символы хранятся в искажённом виде, и без демангляции читать их мучительно.

Проверю на нашем бинарнике — покажу искажённые имена и их расшифровку рядом.Идеальная иллюстрация. Сравни две формы одного и того же символа:

```
Искажённое (mangled):    _Z13counting_coroi
Демангленное (demangled): counting_coro(int)
```

И более сложный — `.actor`-клон корутины:

```
Искажённое:    _Z13counting_coroPZ13counting_coroiE24_Z13counting_coroi.Frame.actor
Демангленное:  counting_coro(...Frame*) [clone .actor]
```

Первая форма — то, что реально хранится в бинарнике (её видит линкер). Вторая — то, что нужно человеку. Флаг `-C` у `nm` (= `--demangle`) выполняет демангляцию автоматически.

## Инструменты демангляции

|Инструмент|Что делает|
|---|---|
|`nm -C` (или `--demangle`)|список символов сразу в читаемом виде|
|`c++filt`|фильтр: подаёшь искажённое имя — получаешь читаемое|
|`llvm-cxxfilt`|то же от LLVM|
|`llvm-nm --demangle`|LLVM-версия nm с демангляцией|

`c++filt` особенно удобен, когда выловил искажённое имя откуда-то (из лога, ошибки линкера) и хочешь его расшифровать:Видно, как `c++filt` расшифровывает разные случаи: обычную функцию, метод в namespace (`foo::bar(int)`), и даже инстанцированный шаблон (`void std::sort<int*>(int*, int*)`).

## Где демангляция нужна на практике

**Ошибки линкера.** Классика — «undefined reference to `_ZN3foo3barEi`». Прогнав через `c++filt`, понимаешь, что не хватает `foo::bar(int)`, а не загадочной абракадабры.

**Стек-трейсы и отладчики.** GDB/LLDB обычно деманглируют автоматически, но в сыром выводе (краш-дампы, `addr2line`, профайлеры вроде `perf`) имена бывают искажёнными — демангляция делает трейс читаемым. Именно поэтому в прошлом ответе про LLDB я писал `nm debug_coro | c++filt` — на случай, если штатной демангляции под рукой нет.

**Анализ бинарников.** Когда смотришь символы чужой библиотеки через `nm`/`objdump`, демангляция показывает реальные C++-сигнатуры.

## Связь с нашим разбором корутин

Демангляция была нужна именно для того, чтобы увидеть, во что компилятор превратил корутину. В искажённом виде `_Z13counting_coro...Frame.actor` нечитаемо, а после демангляции стало ясно: `counting_coro(...) [clone .actor]` — то самое тело корутины (один из трёх символов, на которые расщепляется корутина). Без демангляции разглядеть структуру `.actor`/`.destroy`/ramp было бы невозможно — поэтому при отладке корутин она особенно полезна.

## Важная оговорка про переносимость

Схема mangling **не стандартизирована** и зависит от компилятора/платформы. GCC и Clang используют общую схему **Itanium C++ ABI** (то, что мы видели: `_Z...`). А **MSVC** использует совершенно другую схему — имена там выглядят иначе (с `?`, `@` и т.д.), и расшифровывает их `undname.exe`, а не `c++filt`. Поэтому искажённые имена непереносимы между компиляторами — это одна из причин, по которой C++ не имеет стабильного ABI между разными тулчейнами.

## Аналогия

Mangling — как если бы в каталоге библиотеки книги хранились не по названию, а по уникальному штрихкоду, кодирующему автора, год, издание и язык (чтобы два разных издания «Гамлета» не перепутались). Штрихкод однозначен для системы, но человеку нечитаем. Демангляция — это сканер, который по штрихкоду показывает нормальное «Гамлет, Шекспир, изд. 2020». Линкеру нужен штрихкод (уникальность), человеку — название (читаемость).
