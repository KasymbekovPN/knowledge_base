[[RAII|<=]]

`std::recursive_mutex` — это тип мьютекса из заголовочного файла `<mutex>`, который **позволяет одному и тому же потоку захватывать его несколько раз без взаимоблокировки (deadlock)**.

> ✅ Это полезно, когда функция, уже удерживающая блокировку, может косвенно снова вызвать код, требующий ту же блокировку.

> ⚠️ Стандартный `std::mutex` **не позволяет** одному потоку захватывать его дважды.  
> Это приводит к **неопределённому поведению** (обычно deadlock).

## ⚠️ Важные моменты

| Особенность | Объяснение |
|-------------|------------|
| Может быть захвачен **одним потоком несколько раз** | Но не разными потоками одновременно |
| Каждый `lock()` должен быть сопровождён `unlock()` | Внутренний счётчик отслеживает количество захватов |
| Медленнее, чем `std::mutex` | Из-за дополнительной логики |
| Требует больше памяти | Хранит ID потока и счётчик |
| Не используйте без необходимости | Обычный `std::mutex` предпочтительнее |

## 🆚 `std::mutex` vs `std::recursive_mutex`

| Характеристика | `std::mutex` | `std::recursive_mutex` |
|----------------|--------------|-------------------------|
| Повторный захват тем же потоком | ❌ Приводит к deadlock / UB | ✅ Разрешён |
| Производительность | ⚡ Выше | Ниже |
| Память | Меньше | Больше |
| Использование по умолчанию | ✅ Рекомендуется | Только при необходимости |
| RAII-обёртки | `lock_guard`, `unique_lock` | Те же |

## 🛠 Как работает внутри?

`std::recursive_mutex` хранит:
- ID потока, который его захватил,
- Счётчик захватов.

Когда поток вызывает `lock()`:
- Если он уже владеет мьютексом — увеличивает счётчик,
- Если нет — ждёт освобождения.

При `unlock()`:
- Уменьшает счётчик,
- Фактически разблокирует только при счётчике 0.

## 📌 Когда использовать `std::recursive_mutex`?

| Ситуация | Почему |
|----------|--------|
| Рекурсивные функции с общим мьютексом | Безопасный доступ |
| Методы класса вызывают друг друга и используют один мьютекс | Частая практика |
| Нельзя изменить архитектуру для избежания повторного захвата | В legacy-коде |
| Работа с callback'ами, которые могут вернуться в тот же класс | Сложные сценарии |

## ❌ Когда НЕ использовать?

| Случай | Почему |
|-------|--------|
| Простые критические секции | Используйте `std::mutex` |
| Высокопроизводительный код | `recursive_mutex` медленнее |
| Можно реорганизовать код | Лучше переписать, чем полагаться на рекурсию |

## ✅ Лучшая практика

| Совет | Почему |
|------|--------|
| По возможности избегайте `recursive_mutex` | Признак сложной или запутанной архитектуры |
| Используйте, если альтернатива — дублирование кода или глубокие изменения | Прагматичное решение |
| Всегда используйте RAII (`lock_guard`, `unique_lock`) | Безопаснее ручного управления |
| Документируйте использование `recursive_mutex` | Чтобы другие понимали, зачем он нужен |
| Рассмотрите возможность рефакторинга | Может, стоит вынести логику? |

```cpp
#include <iostream>
#include <mutex>

using namespace std;

class Counter {

private:
    mutable recursive_mutex mtx;
    int count {0};

public:
    void inc() {
        lock_guard<recursive_mutex> lock(mtx);
        ++count;
    }

    void inc2() {
        lock_guard<recursive_mutex> lock(mtx);
        inc();
        inc();
    }

    void reset() {
        lock_guard<recursive_mutex> lock(mtx);
        count = 0;
    }

    int get() const {
        lock_guard<recursive_mutex> lock(mtx);
        return count;
    }
};

int main() {
    Counter counter;
    cout << counter.get() << endl;

    counter.inc();
    cout << counter.get() << endl;

    counter.reset();
    counter.inc2();
    cout << counter.get() << endl;

    return 0;
}
```
