## Что разворачивает co_await

Когда компилятор видит `co_await expr`, он работает с объектом-**awaiter**, у которого вызывает три метода в строгом порядке:

```cpp
// co_await expr  разворачивается примерно так:
auto&& awaiter = /* получить awaiter из expr */;
if (!awaiter.await_ready()) {        // 1. уже готово?
    // ... корутина приостанавливается ...
    awaiter.await_suspend(handle);   // 2. что делать при приостановке
    // ... управление уходит наружу; позже корутину возобновляют ...
}
return awaiter.await_resume();       // 3. результат co_await
```

## Три метода awaiter

**`await_ready() -> bool`** — вызывается первым. Отвечает на вопрос «значение уже готово, приостановка не нужна?». Если вернёт `true` — корутина **не** приостанавливается, сразу идёт к `await_resume()`. Это оптимизация: незачем платить за приостановку, если результат уже есть.

```cpp
bool await_ready() { return false; }  // всегда приостанавливаемся (suspend_always)
bool await_ready() { return true; }   // никогда (suspend_never)
```

**`await_suspend(handle) -> void | bool | coroutine_handle`** — вызывается, если `await_ready` вернул `false`, в момент приостановки. Получает handle **текущей** (приостанавливаемой) корутины. Здесь решают, что делать дальше: запланировать возобновление, запустить I/O, передать управление другой корутине. Тип возврата меняет поведение (разберу ниже).

**`await_resume() -> T`** — вызывается при возобновлении (или сразу, если `await_ready` дал `true`). Его возвращаемое значение становится **результатом всего выражения `co_await`**:

```cpp
int x = co_await something;   // x = awaiter.await_resume()
```

Здесь же обычно перебрасывают сохранённое исключение (как обсуждали в `Task`).

## Откуда берётся awaiter

Тонкость: объект, который ты передаёшь в `co_await`, не обязательно сам awaiter. Компилятор ищет awaiter в порядке:

1. Если у промиса есть `await_transform`, сначала `promise.await_transform(expr)`.
2. Если у результата есть `operator co_await` — вызывается он.
3. Иначе сам объект используется как awaiter.

Для простых случаев — пункт 3: объект сам реализует три метода. `std::suspend_always`/`suspend_never` — именно такие самодостаточные awaiter'ы. Вот они целиком (это весь их код):

```cpp
struct suspend_always {
    bool await_ready()    const noexcept { return false; }  // всегда приостановка
    void await_suspend(std::coroutine_handle<>) const noexcept {}
    void await_resume()   const noexcept {}
};
struct suspend_never {
    bool await_ready()    const noexcept { return true; }   // никогда
    void await_suspend(std::coroutine_handle<>) const noexcept {}
    void await_resume()   const noexcept {}
};
```

## Три варианта возврата await_suspend

Это самая важная развилка. Тип, который возвращает `await_suspend`, определяет, что произойдёт после приостановки:

|Возврат|Поведение|
|---|---|
|`void`|приостановиться и вернуть управление вызывающему `resume()`|
|`bool`|`true` — приостановиться (как void); `false` — **не** приостанавливаться, сразу `await_resume()`|
|`coroutine_handle`|**symmetric transfer**: немедленно возобновить возвращённую корутину, без роста стека|

Пример, демонстрирующий awaiter с `void`-возвратом и его взаимодействие с `await_ready`/`await_resume`. Вывод показывает точный порядок: `before` → `await_ready` → `await_suspend` → `await_resume` → `after, x = 99`. Видно, как значение из `await_resume()` (99) стало результатом `co_await`.

```cpp
struct MyAwaiter {
    bool await_ready() noexcept { return false; }      // не готово -> приостановка
    void await_suspend(std::coroutine_handle<> h) noexcept {
        h.resume();                                     // в реале: запланировать на потом
    }
    int await_resume() noexcept { return 99; }          // результат co_await
};
// ...
int x = co_await MyAwaiter{};   // x == 99
```

## Что произошло по шагам

1. `await_ready()` вернул `false` → корутина будет приостановлена.
2. `await_suspend(h)` получил handle текущей корутины. В реальном асинхронном коде здесь handle _сохранили бы_ и вернули управление наружу, а `resume()` вызвали бы позже — по завершении I/O (колбэк, таймер, готовность сокета). В демо я для наглядности возобновил сразу.
3. `await_resume()` вернул `99`, и это значение присвоилось `x`.

Именно так `co_await` превращает «ожидание» в значение: метод `await_resume` — точка, где асинхронный результат «материализуется» в обычную переменную.

## Symmetric transfer — почему важен возврат handle

Самый интересный вариант `await_suspend` — возврат `coroutine_handle`. Вспомни композицию `Task` (когда одна корутина `co_await`-ит другую): там `await_suspend` возвращал handle вложенной корутины.

**Проблема без него.** Если бы `await_suspend` имел тип `void` и внутри вызывал `other.resume()`, то возобновление вложенной корутины шло бы как **вложенный вызов** — кадр `resume()` ложится поверх текущего стека. В длинной цепочке корутин (A ждёт B, B ждёт C, ...) стек растёт с каждым звеном и в пределе **переполняется**.

```cpp
// ПЛОХО: рекурсивный рост стека
void await_suspend(std::coroutine_handle<> h) {
    other.resume();   // resume вложен в текущий стековый кадр
}
```

**Решение — symmetric transfer.** Если `await_suspend` _возвращает_ handle, компилятор не делает вложенный вызов, а выполняет **хвостовую передачу управления**: текущая корутина приостанавливается, и управление переходит к возвращённой корутине на том же уровне стека. Стек не растёт.

```cpp
// ХОРОШО: хвостовая передача, стек не растёт
std::coroutine_handle<> await_suspend(std::coroutine_handle<> h) {
    return other;     // управление переходит к other без вложения
}
```

Это и был механизм в нашем `Task`: `await_suspend` возвращал handle вложенной задачи (передавая ей управление), а её `final_suspend` возвращал handle ожидающего родителя (возвращая управление обратно) — обе передачи через symmetric transfer, поэтому сколь угодно длинная цепочка `co_await` работает с постоянным размером стека.

`std::noop_coroutine()` здесь — корректный «handle, которому передать управление, чтобы ничего не делать и выйти наружу» (когда возобновлять некого).

## Сводка по await_suspend

|Сигнатура возврата|Смысл|Типичное применение|
|---|---|---|
|`void`|приостановиться, отдать управление наружу|простое асинхронное ожидание (I/O-колбэк сохраняет handle)|
|`bool`|`true` — приостановиться; `false` — продолжить без приостановки|оптимизация: иногда результат успел появиться|
|`coroutine_handle`|symmetric transfer на эту корутину|композиция корутин, планировщики — без роста стека|

## Связка трёх методов в одной фразе

`await_ready` решает, _нужна ли_ приостановка; `await_suspend` решает, _что делать_ во время приостановки (и куда передать управление); `await_resume` решает, _какой результат_ вернуть при возобновлении. Готовые `suspend_always`/`suspend_never` — это просто крайние случаи `await_ready` (всегда/никогда) с пустыми остальными методами.
