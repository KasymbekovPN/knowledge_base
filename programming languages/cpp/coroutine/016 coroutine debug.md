[[programming languages/cpp/coroutine/_|<=]]

Корутины ломают многие интуиции отладки, потому что компилятор радикально переписывает функцию: одна корутина превращается в несколько частей, состояние уходит в кучу, а стек не отражает логический ход выполнения. Разберём, что именно видит отладчик и почему.

Начну с того, чтобы показать, во что компилятор превращает корутину — посмотрим на сгенерированные символы.Вот оно — первое, что сбивает с толку при отладке. Одна функция `counting_coro` в символах превратилась в **три разные функции**:

```
counting_coro(int)                              <- "ramp": то, что вызывает caller
counting_coro(...Frame*) [clone .actor]         <- тело корутины (вся логика!)
counting_coro(...Frame*) [clone .destroy]       <- уничтожение frame
```

## Почему одна корутина = три функции

Компилятор расщепляет корутину на части (это и есть та трансформация stackless-модели):

**`counting_coro(int)`** — «ramp» (пандус). Это то, что выполняется при _вызове_ корутины: аллоцирует frame, копирует параметры, создаёт промис, вызывает `get_return_object`, доводит до `initial_suspend`. Возвращает `Task` вызывающему. Логики тела тут почти нет.

**`[clone .actor]`** — «actor». Вот здесь живёт **всё тело корутины** — весь код между точками приостановки. Именно сюда `resume()` передаёт управление. Когда ты ставишь точку останова «на корутину», логически тебе нужен `.actor`, а не ramp.

**`[clone .destroy]`** — код уничтожения frame (деструкторы локальных + освобождение памяти), вызывается при `destroy()`.

Это объясняет загадочные `.actor`-фреймы, которые мелькали в выводе ASan ранее. Когда в трейсе видишь `counting_coro [clone .actor]` — это не баг символов, это и есть тело твоей корутины. GCC использует суффиксы `.actor`/`.destroy`, clang — имена вроде `counting_coro(int) (.resume)`.

## Почему стек-трейс «неправильный»

Это вторая большая ломка интуиции. Посмотрим, как выглядит стек при срабатывании внутри корутины.gdb здесь нет, поэтому стек-трейс объясню логически (а ты сможешь воспроизвести у себя). Суть в фундаментальном свойстве корутин из самого начала разбора: **корутина не живёт на стеке**.

Когда обычная функция `A` вызывает `B`, стек показывает `B → A` — естественную цепочку «кто кого вызвал». Но корутина возобновляется через `resume()`, и её логический «вызыватель» (тот, кто её когда-то запустил или ждёт) **не находится на стеке** в момент возобновления. На стеке только тот, кто вызвал `resume()` прямо сейчас.

Сравним обычный и корутинный стек при остановке в точке B нашего примера:

```
ОБЫЧНАЯ функция (как было бы):
  #0 counting_coro   <- мы здесь
  #1 main            <- кто вызвал — видно

КОРУТИНА (что реально):
  #0 counting_coro [clone .actor]   <- тело корутины
  #1 std::coroutine_handle::resume  <- механика возобновления
  #2 main                           <- тот, кто вызвал resume СЕЙЧАС
```

Во втором случае `main` оказался в трейсе только потому, что он вызвал `resume()` в этой итерации цикла. Если бы `resume()` пришёл из планировщика (как в нашем `scheduler`), в трейсе был бы `Scheduler::run`, а не логический «родитель» корутины. **Логическая цепочка «кто кого ждёт» (continuation chain) на стеке не отражена** — она хранится в данных (мы её хранили как `continuation` в промисе). Отладчик видит физический стек вызовов `resume`, а не логический поток корутин.

Это и есть главная сложность: в длинной цепочке `co_await` (A ждёт B ждёт C) стек покажет только текущий `.actor` + `resume` + кто дёрнул resume — а не `A → B → C`. Чтобы увидеть логическую цепочку, нужно вручную идти по `continuation`-указателям в промисах.

## Где искать переменные корутины

Третья ломка: локальные переменные корутины **не на стеке, а в куче** (в coroutine frame). Это влияет на отладку:

- Пока корутина **выполняется** (внутри `.actor`) — отладчик обычно показывает её локальные нормально, как обычные переменные.
- Когда корутина **приостановлена** — её frame жив в куче, но «текущего кадра» для неё на стеке нет. Чтобы посмотреть переменные приостановленной корутины, нужно добраться до frame через `coroutine_handle`.

В GDB есть помощь для этого. Покажу команды (для воспроизведения у себя):

```gdb
# поставить точку останова на ТЕЛО корутины (важно: на .actor)
break counting_coro

# когда остановились — посмотреть промис приостановленной корутины
# через встроенную поддержку (GDB 12+):
print h            # покажет coroutine_handle
# в новых GDB: команды для coroutine frame

# универсально — каст handle к типу frame (имя из символов):
# frame хранится по адресу из h.address()
```

В современных отладчиках поддержка растёт: GDB умеет показывать coroutine frame, в LLDB есть аналогичные средства. Но это всё ещё менее гладко, чем для обычных функций — частая жалоба на отладку корутин.

## Почему точки останова ведут себя странно

Четвёртый сюрприз. Поскольку тело разбито на участки между приостановками, и всё это — один `.actor`, выполняемый по кусочкам:

- **Брейкпоинт на строке** срабатывает каждый раз, когда `resume()` доводит выполнение до неё — то есть в _разных_ вызовах `resume`, с одного и того же `.actor`, но с разным состоянием frame.
- **Step over `co_await`** может «провалиться» в awaiter (`await_ready`/`await_suspend`/`await_resume`) и в механику resume — шаговая отладка через точку приостановки часто прыгает не туда, куда ждёшь, потому что управление физически уходит наружу (в того, кто вызвал resume) и возвращается позже.
- **Брейкпоинт «на функцию»** `break counting_coro` может встать на ramp, а не на `.actor` — и тогда сработает только раз при создании, а не при каждом resume. Иногда нужно явно целиться в `.actor`.

## Практические приёмы отладки корутин

Сведу в рекомендации:

**1. Логирование часто эффективнее пошаговой отладки.** Из-за прыжков управления через resume пошаговый проход капризен. Печать состояния на входе/выходе каждого `co_await` (как я делал `printf("step N")`) даёт более ясную картину потока, чем степпинг.

**2. Целься в `.actor`, когда нужно тело.** Понимай, что `break имя_корутины` может попасть в ramp. Для тела ставь брейкпоинт на конкретную строку внутри.

**3. Помни, что стек неполный.** Не ищи в стек-трейсе логического «родителя» корутины — его там нет. Логическую цепочку восстанавливай по `continuation` в промисах (если твой `Task` их хранит — закладывай это в дизайн ради отладки).

**4. Используй ASan/UBSan.** Как мы видели в разборе висячих ссылок — баги времени жизни frame невидимы без санитайзеров, а в корутинах они особенно часты. Это основной инструмент для корутинных багов.

**5. Свежий отладчик.** GDB 12+ и недавние LLDB заметно лучше понимают корутины (умеют показывать frame и промис). На старых версиях отладка корутин почти вслепую.

**6. Собирай с `-g -O0` для отладки.** На `-O2` трансформация корутины + инлайнинг + возможный HALO делают соответствие «код ↔ исполнение» ещё запутаннее. Хотя баги, проявляющиеся только на `-O2`, иногда приходится ловить и там.

## Связь с пройденным

Всё это — прямое следствие stackless-трансформации, с которой мы начинали. Тело корутины компилятор переписал в конечный автомат (`.actor`), состояние вынес в heap-frame, а переключения сделал через resume/return управления. Отладчик же заточен под классическую модель «функция на стеке». Отсюда все четыре ломки: функция расщеплена на три символа, стек не показывает логику, переменные в куче, брейкпоинты срабатывают по-новому. Понимание механики (что такое frame, ramp, actor, continuation) — и есть главный инструмент отладки: ты отлаживаешь не «странную функцию», а конечный автомат с состоянием в куче.

Приложу файл с примером — на нём удобно тренировать команды отладчика у себя (особенно посмотреть символы через `nm -C` и frame через gdb).Файл доступен выше.

Для тренировки у себя:

```bash
g++ -std=c++20 -g -O0 debug_coro.cpp -o debug_coro

# увидеть три символа корутины (ramp / .actor / .destroy):
nm -C debug_coro | grep counting_coro

# в gdb — посмотреть стек и frame на точке приостановки:
gdb ./debug_coro
(gdb) break counting_coro
(gdb) run
(gdb) bt          # увидишь .actor + resume + caller, но не логического родителя
(gdb) info locals
```


## Под LLDB

```bash
# Собирать лучше clang'ом — LLDB и Clang из одного проекта, символы корутин дружнее.
# (g++ тоже сгодится, но clang генерирует имена частей корутины в стиле, который LLDB понимает лучше.)
clang++ -std=c++20 -g -O0 debug_coro.cpp -o debug_coro
# либо: g++ -std=c++20 -g -O0 debug_coro.cpp -o debug_coro

# увидеть символы частей корутины (аналог nm; на macOS nm тоже есть):
nm debug_coro | c++filt | grep counting_coro
# или штатной утилитой LLVM с готовой демангляцией:
llvm-nm --demangle debug_coro | grep counting_coro

# отладка в LLDB:
lldb ./debug_coro
(lldb) breakpoint set --name counting_coro      # кратко: b counting_coro
(lldb) run                                       # кратко: r
(lldb) thread backtrace                          # кратко: bt — увидишь .resume + resume + caller
(lldb) frame variable                            # кратко: v / fr v — локальные (аналог info locals)
```

## Соответствие команд GDB → LLDB

|Задача|GDB|LLDB|Короткий алиас LLDB|
|---|---|---|---|
|Точка останова по имени|`break counting_coro`|`breakpoint set --name counting_coro`|`b counting_coro`|
|Точка останова по строке|`break file.cpp:30`|`breakpoint set --file debug_coro.cpp --line 30`|`b debug_coro.cpp:30`|
|Запуск|`run`|`process launch`|`r`|
|Стек-трейс|`bt`|`thread backtrace`|`bt`|
|Локальные переменные|`info locals`|`frame variable`|`v` или `fr v`|
|Напечатать выражение|`print h`|`frame variable h` / `expression h`|`p h`|
|Шаг с заходом|`step`|`thread step-in`|`s`|
|Шаг через|`next`|`thread step-over`|`n`|
|Продолжить|`continue`|`process continue`|`c`|

## Что увидишь и чем отличается от GDB

**Имена частей корутины.** Вспомни, GCC давал суффиксы `[clone .actor]` / `[clone .destroy]`. Clang называет их иначе — обычно `counting_coro(int) (.resume)` и `counting_coro(int) (.destroy)` (плюс ramp без суффикса). Поэтому при сборке clang'ом в `llvm-nm` ищи суффикс `.resume`, а не `.actor` — это та же сущность (тело корутины, куда передаёт управление `resume()`), просто другое имя клона. Логика из прошлого разбора не меняется: одна корутина → три символа (ramp / тело / destroy).

**Брейкпоинт на тело.** Как и в GDB, `b counting_coro` может встать на ramp, а не на `.resume`-клон. Если срабатывает только раз (при создании), а не при каждом `resume()`, целься в конкретную строку внутри тела: `b debug_coro.cpp:30`.

**Backtrace.** `bt` покажет ту же «непривычную» картину, что обсуждали: текущий клон тела + кадр механики `resume` + тот, кто вызвал `resume` сейчас (`main`) — но не логического родителя/continuation. Это свойство модели, а не отладчика, поэтому в LLDB оно ровно такое же.

**Просмотр приостановленной корутины.** Здесь LLDB исторически отставал от GDB по «из коробки» поддержке coroutine frame. Чтобы посмотреть переменные _приостановленной_ корутины (её frame в куче, текущего кадра на стеке нет), универсальный приём — добраться до frame через адрес из handle и привести к типу frame:

```lldb
# адрес frame = то, что вернул бы h.address()
(lldb) frame variable t.h          # посмотреть сам handle
# каст сырого адреса frame к сгенерированному типу кадра
# (имя типа подсмотри в символах: ...counting_coro...Frame)
(lldb) expression -- *(/* FrameType */ *)0xADDRESS
```

Это менее гладко, чем для обычных функций; на свежих LLDB поддержка лучше, на старых — почти вручную. Поэтому совет из прошлого ответа в силе: для отладки потока корутин логирование на границах `co_await` часто практичнее степпинга.

## Если это всё-таки macOS

Раз вспомнил LLDB — вероятно, ты на macOS (там это штатный отладчик). Два нюанса:

- Компилятор `clang++` там — это Apple Clang. Поддержка корутин есть, но проверь, что версия достаточно свежая (`clang++ --version`); на очень старых Xcode корутины могли требовать флагов.
- `nm` есть, `c++filt` есть; `llvm-nm`/`llvm-cxxfilt` появляются, если установлен LLVM через Homebrew (`brew install llvm`).

```cpp
#include <iostream>
#include <format>
#include <utility>
#include <coroutine>

struct Task {
    struct promise_type {
        int value{};

        Task get_return_object() {
            return Task{std::coroutine_handle<promise_type>::from_promise(*this)};
        }
        std::suspend_always initial_suspend() noexcept { return {}; }
        std::suspend_always final_suspend() noexcept { return {}; }
        void return_void() {}
        void unhandled_exception() {}
    };

    std::coroutine_handle<promise_type> h;

    explicit Task(std::coroutine_handle<promise_type> _handle): h{_handle} {}
    Task(Task&& _other) noexcept: h{std::exchange(_other.h, {})} {}
    ~Task() { if (h) h.destroy(); }
};

Task counting_core(int _start) {
    int x{_start}; // локальная переменная корутины
    std::cout <<std::format("step 0: x = {}\n", x);
    co_await std::suspend_always{}; // <-- точка приостановки A

    x += 10;
    std::cout <<std::format("step 1: x = {}\n", x);
    co_await std::suspend_always{}; // <-- точка приостановки B

    x += 100;
    std::cout <<std::format("step 2: x = {}\n", x);

    co_return;
}

int main() {
    Task t = counting_core(42);
    while (!t.h.done()) {
        t.h.resume();
    }

    return 0;
}
```

```
step 0: x = 42
step 1: x = 52
step 2: x = 152
```
