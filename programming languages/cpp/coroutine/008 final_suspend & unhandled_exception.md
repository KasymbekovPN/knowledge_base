`final_suspend` и `unhandled_exception` — это «выход» из корутины: один решает судьбу frame после завершения, второй ловит вылетевшее исключение. Они тесно связаны, поэтому разбираю вместе, с примером проброса исключения наружу.

## final_suspend

**Когда вызывается:** после того как тело корутины завершилось — либо нормально (через `co_return` / `return_void`/`return_value`), либо после `unhandled_exception()`. Результат — awaitable, который компилятор `co_await`-ит, как и у `initial_suspend`.

**Что решает:** приостановиться ли корутине **после завершения тела**, то есть оставить ли coroutine frame живым.

```cpp
// frame ОСТАЁТСЯ жив после завершения — кто-то снаружи должен сделать destroy()
std::suspend_always final_suspend() noexcept { return {}; }

// frame уничтожается АВТОМАТИЧЕСКИ сразу по завершении
std::suspend_never final_suspend() noexcept { return {}; }
```

Это решающий выбор, и он диктует, кто владеет временем жизни frame:

| |`suspend_always`|`suspend_never`|
|---|---|---|
|Судьба frame|остаётся жив|уничтожается сам|
|Кто вызывает `destroy()`|владелец снаружи (деструктор `Task`)|никто, уже уничтожен|
|Можно ли читать результат после завершения|да|нет (frame мёртв)|
|Опасность|утечка, если забыть `destroy()`|use-after-free, если хранить handle|

**Почему для `Task`/`Generator` нужен `suspend_always`:** нам нужно прочитать результат (`value`/`current`) уже _после_ того, как корутина завершилась. Если frame уничтожится сам (`suspend_never`), читать будет неоткуда — UB. Поэтому frame оставляют жить, а `~Task` потом вызывает `destroy()`. Это объясняет, почему во всех наших `Task`/`Generator` стояло `final_suspend → suspend_always` вместе с `if (h) h.destroy()` в деструкторе.

**Обязан быть `noexcept`.** Это требование стандарта — `final_suspend`, помеченный не-`noexcept`, делает программу ill-formed. Причина: на этом этапе обрабатывать исключение уже некому, корутина логически завершена.

**Symmetric transfer живёт здесь.** Именно `final_suspend` — место, где завершившаяся корутина может передать управление тому, кто её ждал (continuation). Это мы видели в композиции `Task`: `final_suspend` возвращал awaiter, возобновлявший родителя. Для простого случая достаточно `suspend_always`.

## unhandled_exception

**Когда вызывается:** если из тела корутины вылетело исключение, которое не было поймано внутри. Компилятор оборачивает тело корутины примерно так:

```cpp
// упрощённая модель того, что генерирует компилятор:
try {
    /* тело корутины */
} catch (...) {
    promise.unhandled_exception();   // <- сюда
}
// затем co_await promise.final_suspend();
```

**Что делать внутри:** есть три типовые стратегии.

```cpp
// 1. Жёстко падаем (просто, для примеров)
void unhandled_exception() { std::terminate(); }

// 2. Игнорируем (опасно — теряем ошибку)
void unhandled_exception() {}

// 3. Сохраняем для проброса наружу (правильно для Task)
void unhandled_exception() { exception = std::current_exception(); }
```

Третий вариант — единственно корректный, если хочешь, чтобы исключение из корутины «дошло» до вызывающего. `std::current_exception()` захватывает текущее летящее исключение в `std::exception_ptr`, который можно сохранить и позже перебросить через `std::rethrow_exception` — обычно в момент, когда вызывающий забирает результат.

Важный порядок: после `unhandled_exception()` управление **не выходит** из корутины напрямую — выполняется `final_suspend()`. Поэтому frame с сохранённым исключением остаётся жив (при `suspend_always`), и вызывающий сможет его извлечь.

## Полный пример: проброс исключения через Task

Соберу `Task<int>`, который сохраняет исключение в промисе и перебрасывает его, когда вызывающий читает результат. Проверю на двух сценариях — успех и исключение.Работает: успешный путь даёт `42`, а исключение из `boom()` ловится обычным `try/catch` в `main`. Ключевой код:

```cpp
struct promise_type {
    std::optional<T>   value;
    std::exception_ptr error;
    // ...
    std::suspend_always final_suspend() noexcept { return {}; }   // frame жив

    void return_value(T v) { value = std::move(v); }
    void unhandled_exception() {
        error = std::current_exception();   // захватываем летящее исключение
    }
};

T get() {
    auto& p = h.promise();
    if (p.error) std::rethrow_exception(p.error);   // перебрасываем здесь
    return std::move(*p.value);
}
```

## Что произошло по шагам в сценарии с исключением

1. `boom()` начинает выполняться (eager, `initial_suspend → suspend_never`).
2. Внутри тела вылетает `std::runtime_error`. Компилятор перехватывает его в неявном `catch(...)` и вызывает `unhandled_exception()`.
3. `unhandled_exception()` сохраняет исключение в `error` через `std::current_exception()` — оно не теряется, а «замораживается» в `exception_ptr`.
4. Далее выполняется `final_suspend() → suspend_always` — frame **остаётся жив** вместе с сохранённым `error`. Корутина завершена, но не уничтожена.
5. В `main` вызывается `get()`. Он видит непустой `error` и делает `std::rethrow_exception` — исключение «оживает» уже в контексте вызывающего и ловится обычным `try/catch`.
6. `~Task` уничтожает frame через `destroy()`.

## Почему final_suspend здесь критичен

Если бы стоял `final_suspend → suspend_never`, frame уничтожился бы сразу на шаге 4 — вместе с сохранённым `error`. К моменту вызова `get()` читать `error` и `value` было бы неоткуда: use-after-free. Именно связка `final_suspend → suspend_always` + хранение исключения в промисе + ручной `destroy()` в деструкторе делает проброс возможным. Это прямая иллюстрация того, почему два метода разбираются вместе: `unhandled_exception` _сохраняет_ ошибку, а `final_suspend` _сохраняет ей жизнь_ до момента чтения.

## Нюансы

**`std::optional<T>` вместо голого `T`** — потому что при исключении `return_value` не вызывается, значения нет. `optional` корректно отражает «результата может не быть», а заодно снимает требование default-конструируемости `T` (о чём говорили в пункте про `Task<void>`).

**Где перебрасывать.** В этом примере — в `get()`. В асинхронном `Task` исключение перебрасывают в `await_resume()`, чтобы оно вылетело в той корутине, которая делала `co_await` — тогда `co_await someTask` бросает так же естественно, как обычный вызов функции.

**`std::terminate()` как альтернатива.** Во всех предыдущих простых примерах в `unhandled_exception` стоял `std::terminate()` — это допустимо для учебного кода и для корутин, где исключения не ожидаются. Но для типа, претендующего на роль настоящего `Task`, нужен именно проброс через `exception_ptr`.

**`final_suspend` и symmetric transfer.** Здесь `final_suspend` тривиальный (`suspend_always`). В полноценном `Task` он, как разбирали в композиции задач, возвращал бы awaiter, который через symmetric transfer возобновляет ожидающую корутину — и тогда проброс исключения в `await_resume` родителя складывается с этим механизмом в единую цепочку.
