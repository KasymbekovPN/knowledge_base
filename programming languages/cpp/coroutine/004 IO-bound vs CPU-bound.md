**Различие в одном предложении:** I/O-bound задача большую часть времени _ждёт_ (диск, сеть, БД), почти не загружая процессор; CPU-bound задача _считает_, полностью загружая процессор.

## I/O-bound задачи

Время выполнения определяется скоростью ввода-вывода, а не процессора. Процессор по большей части простаивает в ожидании ответа.

Примеры: сетевые запросы, чтение/запись файлов, запросы к базе данных, ожидание ответа от внешнего API.

Масштаб ожидания стоит прочувствовать. Если один такт процессора принять за секунду:

|Операция|Реальное время|В «человеческом» масштабе|
|---|---|---|
|Обращение к L1-кешу|~1 нс|~1 секунда|
|Чтение из RAM|~100 нс|~2 минуты|
|SSD|~100 мкс|~1 день|
|Сетевой запрос (round-trip)|~1–100 мс|от недели до **нескольких лет**|

То есть в ожидании одного сетевого ответа процессор мог бы выполнить миллионы полезных операций. Вопрос лишь в том, как заполнить этот простой.

## CPU-bound задачи

Время определяется скоростью процессора. Он загружен на 100%, простоя нет.

Примеры: математические вычисления, обработка изображений, сжатие, шифрование, обучение моделей, парсинг больших объёмов данных.

Здесь нет «ожидания», которое можно было бы использовать для другой работы. Чтобы ускориться, нужно реальное _распараллеливание_ — раздать работу нескольким ядрам.

## Где корутины дают выигрыш — и почему

**Корутины выигрывают на I/O-bound задачах.** Их суть — дёшево уступить управление в точке ожидания, не блокируя поток. Пока одна корутина ждёт ответа от сети, тот же поток выполняет другие корутины. Простой процессора заполняется полезной работой.

Сравним два подхода к серверу, обслуживающему много одновременных соединений.

**Подход «поток на соединение» (блокирующий):**

```cpp
void handle(Connection c) {
    auto data = c.read();   // поток ЗАБЛОКИРОВАН, ждёт сеть,
                            // его стек (1–8 МБ) занят, процессор простаивает
    process(data);
    c.write(response);
}
// 10 000 соединений = 10 000 потоков = десятки ГБ памяти +
// тяжёлые context switch'и между ними
```

**Подход на корутинах (неблокирующий):**

```cpp
Task handle(Connection c) {
    auto data = co_await c.async_read();  // корутина уступает управление,
                                          // поток обслуживает другие корутины
    process(data);
    co_await c.async_write(response);
}
// 10 000 соединений = 10 000 корутин = десятки МБ +
// дешёвые переключения в пользовательском пространстве
```

Выигрыш именно потому, что у I/O-bound нагрузки **есть простой, который нечем заполнить при блокирующей модели**. Корутина превращает «поток сидит и ждёт» в «поток ждёт за тысячи соединений сразу».

**На CPU-bound задачах корутины выигрыша почти не дают.** Корутина не добавляет вычислительной мощности — на одном потоке она не создаёт параллелизма (это разбирали ранее). Если задача упирается в процессор, переключение между корутинами лишь добавит накладных расходов, не ускорив счёт. Здесь нужны **потоки на разных ядрах** — настоящий параллелизм.

## Сводка

| |I/O-bound|CPU-bound|
|---|---|---|
|Узкое место|Ожидание ввода-вывода|Скорость процессора|
|Процессор|Простаивает|Загружен на 100%|
|Что нужно|Заполнить простой → **корутины**|Больше ядер → **потоки**|
|Корутины помогают?|Да, сильно|Почти нет|
|Потоки помогают?|Помогают, но дорого по памяти|Да, это основной инструмент|

## Важная оговорка: «жадная» корутина

Поскольку модель кооперативная, **CPU-bound работу нельзя запускать прямо в корутине на общем потоке** — она не уступит управление и заблокирует все остальные корутины (об этой ловушке говорили в пункте про вытеснение).

Правильный приём — вынести тяжёлое вычисление на отдельный поток (например, в пул) и ожидать его результат:

```cpp
Task handle(Request req) {
    auto data = co_await async_read(req);        // I/O — корутина уступает
    auto result = co_await run_on_threadpool([&]{
        return heavy_computation(data);          // CPU — на отдельном ядре,
    });                                          // не блокирует event loop
    co_await async_write(result);                // I/O — снова уступает
}
```

## Итог

Корутины — инструмент для **конкурентного ожидания**, а не для ускорения вычислений. Они блестящи там, где много операций «запустил и жди» (серверы, сетевые клиенты, агрегаторы запросов), и нейтральны или вредны там, где нужно молотить числа. На практике системы комбинируют: корутины оркеструют I/O, пул потоков выполняет CPU-bound куски — и каждый инструмент работает там, где силён.
