**HALO** (Heap Allocation eLision Optimization) — оптимизация, при которой компилятор полностью устраняет аллокацию coroutine frame в куче, размещая его прямо в кадре вызывающей стороны (на стеке или внутри фрейма родительской корутины).

## Зачем фрейму вообще нужна аллокация

Когда создаётся корутина, её состояние (coroutine frame) нужно где-то разместить — оно должно пережить приостановку, то есть не может просто лежать в стеке вызывающего, который раскручивается при выходе из функции. По умолчанию компилятор вставляет вызов `operator new` для размещения фрейма в куче, а при уничтожении — `operator delete`.

```cpp
Task example() {
    co_await something;   // фрейм должен пережить приостановку →
}                         // по умолчанию аллоцируется в куче
```

Эта аллокация — главный источник накладных расходов корутин. HALO её убирает.

## Когда HALO применима

Ключевое условие: **время жизни корутины не выходит за пределы времени жизни вызывающего**. Если компилятор может доказать, что корутина будет создана, использована и уничтожена в рамках вызывающей функции — отдельная динамическая память не нужна, фрейм можно положить рядом, в кадр вызывающего.

Типичный случай — немедленное ожидание:

```cpp
Task<int> compute() {
    co_return 42;
}

Task<int> caller() {
    int x = co_await compute();   // compute() создаётся и полностью
                                  // завершается внутри caller —
                                  // её фрейм можно вложить в caller
    co_return x + 1;
}
```

Здесь корутина `compute` не «убегает» из `caller`: её handle никуда не сохраняется, не передаётся наружу, жизненный цикл вложен. Компилятор может разместить фрейм `compute` внутри фрейма `caller`, и аллокация исчезает.

А вот когда HALO **не** сработает — корутина переживает вызывающего:

```cpp
Task<int> make() {
    co_return 42;
}

std::vector<Task<int>> tasks;
void spawn() {
    tasks.push_back(make());   // handle сохраняется наружу,
                               // время жизни не вложено →
                               // аллокация в куче остаётся
}
```

## Почему это вообще возможно (и связь со stackless)

HALO опирается на то, что в stackless-модели **размер coroutine frame известен компилятору на этапе компиляции**. Зная точный размер, компилятор может зарезервировать под него место в кадре вызывающего — как под обычную локальную переменную. Со stackful-корутинами это было бы невозможно: их отдельный стек существует всегда.

Технически в стандарте это разрешено формулировкой о том, что компилятор _вправе_ не вызывать выделенный `operator new`, если может удовлетворить требования к времени жизни иначе. То есть HALO — это разрешённое стандартом устранение наблюдаемого вызова `new`.

## Практические нюансы

- **Это оптимизация, а не гарантия.** Стандарт _разрешает_ HALO, но не обязывает. Сработает ли она — зависит от компилятора, уровня оптимизации и от того, может ли он «увидеть» весь жизненный цикл (часто нужен инлайнинг). На `-O0` её обычно нет.
- **Требуется видимость для компилятора.** Если определение корутины в другой единице трансляции и не инлайнится, доказать вложенность времени жизни нельзя — аллокация останется. Поэтому корутины-кандидаты на HALO часто делают видимыми/инлайн.
- **Цепочка должна быть «прозрачной».** Промежуточные awaiter'ы и типы не должны прятать handle так, чтобы компилятор терял возможность доказать вложенность.
- Иногда упоминается как **CPEO** (Coroutine Pre-allocated Elision Optimization) или просто «coroutine frame elision» — суть та же.

## Итог

HALO превращает потенциально дорогую корутину (с аллокацией в куче на каждый вызов) в практически бесплатную, когда её жизненный цикл локален. Это одна из причин, по которой ленивые `Task`-цепочки и генераторы в C++ могут быть очень эффективными — но рассчитывать на неё как на гарантию нельзя, и в горячем коде имеет смысл проверять (через профилирование или счётчики аллокаций), действительно ли она сработала.
