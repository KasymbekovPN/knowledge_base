Sender/receiver — не просто ещё одна библиотека корутин, а попытка задать **общую модель асинхронности** для всего стандарта. Поскольку это активно меняющаяся область, проверю текущий статус — что именно и когда вошло в C++26.Статус подтверждён: P2300 (std::execution, он же senders/receivers) был официально принят в C++26 на пленарном заседании WG21 в Сент-Луисе в июне 2024 года.

## Зачем вообще sender/receiver, если есть корутины

Корутины — это _синтаксис_ для асинхронного кода: удобно писать последовательную логику с приостановками. Но они не отвечают на вопрос «_на чём_ и _как_ это выполняется» — нет стандартной модели исполнителей (executors), композиции, отмены, обработки ошибок. C++ намеренно стандартизировал корутины без типов .

Sender/receiver закрывает именно этот пробел: это **общая модель асинхронных вычислений**, не привязанная к корутинам. std::execution предоставляет базовую модель для выражения вычислений, добавляя поддержку конкурентности, параллелизма и асинхронности. Корутины и sender'ы при этом совместимы — корутину можно сделать sender'ом и наоборот.

## Три роли

Модель строится на трёх понятиях:

**Sender** — описание _отложенного_ вычисления, которое когда-нибудь произведёт результат. Сам по себе ничего не запускает — это «рецепт», ленивый по умолчанию (в отличие от eager-`std::future`). Композируется через алгоритмы.

**Receiver** — приёмник результата: набор из трёх каналов завершения, куда sender отправит исход:

- `set_value(values...)` — успех с результатом
- `set_error(err)` — ошибка
- `set_stopped()` — отмена

**Scheduler** — абстракция «где исполнять» (пул потоков, GPU, текущий поток). Из него получают sender, представляющий «начни здесь».

Три канала завершения — важное отличие от корутин: ошибка и **отмена** встроены в саму модель как равноправные исходы, а не прикручены сбоку.
## Как это выглядит

Композиция строится конвейером через `operator|` (как ranges):

```cpp
namespace ex = std::execution;

ex::scheduler auto sch = pool.get_scheduler();

ex::sender auto work =
      ex::schedule(sch)                       // начать на пуле
    | ex::then([]      { return 21; })         // преобразование результата
    | ex::then([](int x){ return x * 2; })     // ещё одно
    | ex::then([](int x){ std::cout << x; return x; });

auto [result] = std::this_thread::sync_wait(work).value();  // запустить и дождаться
```

Соответствие с тем, что мы строили руками:

|Наш код / корутины|std::execution|
|---|---|
|`Scheduler`|`scheduler` (например, от `static_thread_pool`)|
|`Task<T>`|`sender`|
|ручной `sync_wait` (мы писали такой)|`std::this_thread::sync_wait`|
|`co_await другой_task`|`then`, `let_value`, `when_all`, ...|
|`unhandled_exception` → проброс|канал `set_error`|
|(у нас не было) отмена|канал `set_stopped` + `stop_token`|

`sync_wait`, кстати, — ровно тот мост из асинхронного в синхронный код, который мы писали вручную в одном из примеров; здесь он стандартный.

## Структурированная конкурентность — главная идея

Ключевая ценность, ради которой это двигают в стандарт: senders/receivers позволяют применять структурированную конкурентность — решать конкурентные задачи без типичных проблем многопоточности вроде гонок данных, дедлоков и узких мест производительности.

Аналогия, которую приводят авторы, точная: переход от классического многопоточного программирования с потоками и блокировками к модели структурированной конкурентности подобен переходу от goto к структурному программированию с ясными абстракциями кода. То есть как структурное программирование заменило хаотичные `goto` вложенными блоками с понятным временем жизни, так sender-композиция заменяет «развешанные» колбэки и ручное управление задачами деревом вычислений с чёткими границами: дочерние задачи не переживают родителя, ошибки и отмена распространяются предсказуемо.

## Что реально вошло в C++26, а что нет

Тут важная сдержанность — стандартизировали фундамент, не всё:

P2300 даёт ядро: концепции sender/receiver/scheduler, базовые фабрики и алгоритмы (`then`, `when_all`, `let_value`, `schedule`, `sync_wait`, `run_loop`). P2300 закладывает основу для построения базовых sender'ов; отдельная статья P3109 описывает работу, которую планируют включить в стандарт сверх P2300.

Чего пока не хватает «из коробки» и за чем тянется P3109: несколько средств в P2300 требуют scheduler, но единственный предоставляемый — это run_loop; нужен готовый scheduler, использующий системный пул потоков платформы, иначе пользователям придётся идти в сторонние библиотеки или писать свой, чтобы задействовать несколько ядер. Также в планах — асинхронные сферы (async scopes), и, в перспективе, стандартная сеть поверх этой модели.

Это в точности повторяет историю самих корутин, на что прямо указывают: мы стандартизировали базовый каркас корутин без каких-либо типов корутин; в C++23 получили только std::generator. Та же стратегия — сначала фундамент, типы и алгоритмы дозреют в следующих стандартах.

## libunifex и stdexec — что это в этой картине

Поскольку C++26 ещё не у всех в компиляторах, реальные реализации живут в библиотеках:

**libunifex** (Meta) — _предшественник_ P2300, экспериментальная площадка, где модель обкатывалась. Исторически важна, но это не сам стандарт.

**stdexec** (NVIDIA) — _референсная реализация_ P2300. stdexec — экспериментальная референсная реализация модели Senders из P2300, принятой в стандарт C++26; её цель — дать референс для дополнений C++26, набрать опыт использования и предоставить NVIDIA-расширения для запуска кода на GPU. Именно через неё сейчас щупают `std::execution` (есть на Godbolt).

**beman::execution** — ещё одна реализация P2300R10, в разработке, пока не готова для продакшена.

GPU-аспект stdexec показателен: одна и та же sender-композиция может исполняться на пуле потоков или на GPU сменой scheduler'а — в этом сила абстракции «где исполнять».

## Куда движется стандарт — итог

Линия развития ясна и последовательна:

C++20 дал **механизм** корутин (приостановка/возобновление) без политики исполнения. C++23 добавил первый готовый тип — `std::generator`. C++26 добавляет **модель исполнения** — sender/receiver как единый язык для асинхронности, параллелизма и конкурентности, с встроенными ошибками, отменой и структурированной конкурентностью. Дальше (C++29 и далее) поверх этой модели достроят готовые scheduler'ы, async scopes и, вероятно, стандартную сеть.

Стратегически идея в том, чтобы у всей асинхронности в C++ был **один общий фундамент**: и корутины, и колбэки, и пулы потоков, и GPU, и (в будущем) сетевой ввод-вывод выражались через sender'ы и компоновались одними и теми же алгоритмами. Корутины при этом не отменяются — они становятся одним из удобных способов _писать_ sender'ы, а не отдельным островом.

Оговорка про сроки: P2300 проголосован в рабочий черновик C++26, но сам стандарт ещё не финализирован, и до полноценной поддержки в основных компиляторах (а тем более до готовых scheduler'ов из P3109) пройдёт время. Сегодня практический путь попробовать это — stdexec.

**Компилятор clang 22.1.0 — да, скомпилирует код на sender/receiver.** Никаких языковых расширений P2300 не требует: это чистый C++ (концепты, шаблоны, member-функции). Любой clang с поддержкой C++23/26 справится с фронтенд-частью.

**Но `#include <execution>` со стандартными `std::execution::sender`/`schedule`/`then`/`sync_wait` в штатной библиотеке clang (libc++) — на середину 2026 ещё, скорее всего, недоступно или неполно.** P2300 принят в C++26, но реализация в стандартных библиотеках отстаёт. По данным статуса libc++, даже сопутствующий `std::execution::task` (P3552) числится незакрытой задачей. По состоянию на май 2026 C++26 достиг feature freeze, но прогресс реализации сильно различается между основными тулчейнами, создавая сложную картину для практиков.

Это критично, потому что, повторюсь, **sender/receiver живёт в библиотеке, а не в компиляторе**. Версия clang сама по себе ничего не гарантирует — решает версия и полнота libc++/libstdc++, с которой ты собираешь.

## Что делать практически

```bash
git clone https://github.com/NVIDIA/stdexec.git
```

```cpp
// clang++ -std=c++26 -I stdexec/include my_async.cpp -o my_async
// & 'C:/Program Files/LLVM/bin/clang++.exe' -std=c++26 -I 'C:/projects/_3side/stdexec/include' 'C:\projects\knowledge_base\programming languages\cpp\coroutine\code\012 sender receiver scheduler\demo.cpp' -o 'C:\projects\knowledge_base\programming languages\cpp\coroutine\code\012 sender receiver scheduler/app.exe'

#include <iostream>
#include <format>
#include <stdexec/execution.hpp>
#include <exec/static_thread_pool.hpp>

namespace ex = stdexec;

int main() {
    exec::static_thread_pool pool{4};
    ex::scheduler auto sch = pool.get_scheduler();

    ex::sender auto work =
          ex::schedule(sch)
        | ex::then([]{ return 21; })
        | ex::then([](int x){ return x * 2; })
        | ex::then([](int x){
            std::cout << std::format("inner: {}\n", x);
            return x;
        });

    auto [r] = ex::sync_wait(work).value();
    std::cout << std::format("result: {}\n", r);
}
```

```
inner: 42
result: 42
```

`stdexec` именно для этого и существует: это экспериментальная референсная реализация модели Senders из P2300, принятой в стандарт C++26, призванная дать референс для дополнений C++26 и набрать опыт использования. Обрати внимание на namespace — пока это `stdexec::`, а не `std::execution::`; при переходе на штатную библиотеку поменяешь namespace и include.
