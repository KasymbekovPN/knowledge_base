[[programming languages/cpp/attributes/_|<=]]

`__attribute__((nonnull))` (`[[gnu::nonnull]]`) — помечает параметры-указатели функции как обязанные быть ненулевыми при каждом вызове. Даёт две вещи: компилятор может статически предупреждать о вызовах с очевидно `nullptr`-аргументом (`-Wnonnull`, часть `-Wall`), и может оптимизировать код внутри функции, исходя из того, что указатель точно не `nullptr` (например, убрать неявную проверку перед разыменованием).

```cpp
// без аргументов — nonnull применяется ко ВСЕМ указательным параметрам
__attribute__((nonnull))
void process(int* data, size_t size);

// с номерами параметров (считая с 1) — только конкретные указатели
__attribute__((nonnull(1, 3)))
void copy(const char* src, size_t unused_flag, char* dst);

int main() {
    process(nullptr, 10);   // warning: null argument where non-null required
}
```

Пример того, как атрибут меняет оптимизацию:

```cpp
__attribute__((nonnull))
int getFirst(int* arr) {
    if (arr == nullptr) {      // компилятор вправе решить, что эта ветка
        return -1;              // недостижима, и выкинуть её целиком —
    }                            // ведь по контракту arr никогда не nullptr
    return arr[0];
}
```

Если функцию всё-таки вызвать с `nullptr` (обходя предупреждение компилятора, например, передав указатель через переменную, значение которой не видно статически) — это UB: компилятор мог уже удалить проверку на `nullptr` внутри функции, полагаясь на атрибут, и тогда реальный `nullptr` приведёт к неопределённому поведению вместо ожидаемого раннего возврата.

Важные нюансы:

- Это **контракт, а не проверка** — как и `pure`/`const`/`assume`, обсуждавшиеся раньше: атрибут не вставляет runtime-assert, он либо включает статический анализ на этапе компиляции (когда `nullptr` виден статически), либо разрешает компилятору более агрессивные предположения, не гарантируя проверку в общем случае.
- Стандартного `[[nonnull]]` в самом C++ нет; в современном C++ для того же назначения предпочтительнее использовать `T&` (ссылку) вместо `T*`, когда указатель по контракту не может быть null — ссылки не могут (в теории) быть "нулевыми", и это выражается на уровне типа, а не как отдельная аннотация поверх указателя. `nonnull` остаётся полезен там, где по историческим/API причинам нужен именно указатель (C-совместимые интерфейсы, опциональные параметры через отдельные `nonnull`-указатели среди прочих nullable).
- Родственная, но более развитая система — **nullability-аннотации Clang** (`_Nonnull`, `_Nullable`, `_Null_unspecified`), в основном известные по Objective-C/Objective-C++ API, где они встраиваются прямо в тип указателя (`int * _Nonnull p`), а не привязываются отдельным атрибутом к параметру функции — более гранулярная и типобезопасная система, но менее распространена в чистом C++ коде.
- Статические анализаторы (Clang Static Analyzer, clang-tidy) используют `nonnull` как источник информации о контрактах API при поиске потенциальных разыменований `nullptr` — то есть атрибут полезен не только для кодогенерации компилятора, но и как метаданные для инструментов анализа.
