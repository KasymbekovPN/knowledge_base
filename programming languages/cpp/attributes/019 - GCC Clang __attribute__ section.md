[[programming languages/cpp/attributes/_|<=]]

`__attribute__((section("name")))` — размещает функцию или переменную в указанной секции объектного файла вместо секции по умолчанию (`.text` для кода, `.data`/`.bss`/`.rodata` для данных). Используется, когда нужен точный контроль над layout'ом бинарника — обычно в связке с кастомным линкер-скриптом, который знает, что делать с этой секцией.

```cpp
// embedded: таблица векторов прерываний должна лежать по фиксированному
// адресу в памяти (начало flash), а не там, куда компилятор обычно кладёт данные
__attribute__((section(".isr_vector")))
const void* vectorTable[] = {
    reinterpret_cast<void*>(&stackTop),
    reinterpret_cast<void*>(&resetHandler),
    reinterpret_cast<void*>(&nmiHandler),
    // ...
};

// произвольная функция, вынесенная в отдельную секцию, например
// чтобы линкер-скрипт разместил её в быстрой RAM, а не во flash
__attribute__((section(".fast_code")))
void criticalHotPath() { /* ... */ }
```

Типичный embedded-паттерн — "секция-массив" для регистрации чего-либо на этапе линковки (без рантайм-регистрации, в отличие от `constructor`-атрибута):

```cpp
struct TestCase {
    const char* name;
    void (*fn)();
};

#define REGISTER_TEST(fn) \
    __attribute__((section("test_cases"), used)) \
    static const TestCase test_##fn = {#fn, fn}

void test_addition() { /* ... */ }
REGISTER_TEST(test_addition);
```

Линкер-скрипт собирает все объекты из секции `test_cases` подряд в памяти, а в коде можно пройтись по ним через символы `__start_test_cases`/`__stop_test_cases` (GNU ld генерирует их автоматически для секций с "простым" именем):

```cpp
extern TestCase __start_test_cases[];
extern TestCase __stop_test_cases[];

for (TestCase* t = __start_test_cases; t != __stop_test_cases; ++t) {
    std::cout << "running " << t->name << "\n";
    t->fn();
}
```

Это статический (link-time) аналог того плагинного реестра, который мы собирали раньше через `dlopen` + `constructor` — только без динамической загрузки: все "плагины"/тесты уже известны на этапе линковки одного бинарника.

Практическое применение:

- **Embedded/прошивки** — таблицы векторов прерываний, размещение кода в конкретных областях памяти (flash vs RAM), данные по фиксированным адресам, ожидаемым бутлоадером.
- **регистрация без рантайм-кода** — юнит-тест-фреймворки (Google Test использует похожую технику), профилировщики, встроенные таблицы метаданных — без накладных расходов на `constructor`-вызовы при старте.
- **Линковка с memory-mapped регионами** — например, секция, которую линкер-скрипт кладёт ровно в область памяти, зарезервированную под конкретное аппаратное устройство.

Осторожности:

- Нужен линкер-скрипт (или знание того, куда стандартный линкер положит именованную секцию), иначе атрибут просто создаёт секцию, ничего не гарантируя об адресе — сам по себе `section` не задаёт адрес, только имя.
- `__start_NAME`/`__stop_NAME` символы GNU ld генерирует только для секций с именем, состоящим из допустимых символов C-идентификатора (без точки в начале в некоторых конфигурациях, хотя `.isr_vector` со стандартными ELF-именами тоже работает для других целей) — для кастомных секций-массивов принято называть без ведущей точки.
- Нужен `__attribute__((used))` вместе с `section`, если объект не используется явно из кода — иначе компилятор с оптимизациями может решить, что символ мёртвый, и выкинуть его до того, как линкер соберёт секцию.
- Полностью компилятор-специфично, MSVC-аналог — `#pragma section("name")` + `__declspec(allocate("name"))`, синтаксис заметно другой, писать кроссплатформенно так же, как `visibility`/`constructor` в этом чате, придётся через `#ifdef`.
