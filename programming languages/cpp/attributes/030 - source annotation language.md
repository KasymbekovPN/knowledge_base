SAL (Source Annotation Language) — система аннотаций MSVC для документирования и статической проверки контрактов функций: что параметр делает (вход/выход), может ли быть `null`, какого размера буфер, инициализирован ли он на входе. В отличие от GCC-атрибутов вроде `nonnull`, которые встраиваются в кодогенерацию компилятора, SAL — это в первую очередь метаданные для статического анализатора (`/analyze`, часть Visual Studio) и IntelliSense, а не для оптимизаций.

```cpp
#include <sal.h>

void copyBuffer(
    _In_reads_(srcSize) const char* src,   // указатель на srcSize элементов для чтения
    size_t srcSize,
    _Out_writes_(dstSize) char* dst,        // указатель на dstSize элементов для записи
    size_t dstSize
);

_Ret_maybenull_
char* tryAllocate(size_t size);              // возвращаемый указатель МОЖЕТ быть null

_Ret_notnull_
char* mustAllocate(size_t size);             // возвращаемый указатель гарантированно не null
```

Базовые направленческие аннотации:

```cpp
void process(
    _In_ int input,           // только читается функцией, не должен быть null (для указателей)
    _Out_ int* output,        // функция запишет значение, на входе содержимое неважно
    _Inout_ int* state        // и читается, и модифицируется функцией
);
```

Более развёрнутые варианты с явным указанием размера (важны для проверки переполнения буфера — исторически SAL создавался именно для борьбы с buffer overflow в Windows-коде):

```cpp
_Success_(return != 0)
bool readData(
    _Out_writes_bytes_to_(bufferSize, *bytesRead) void* buffer,
    size_t bufferSize,
    _Out_ size_t* bytesRead
);
```

Nullability-семейство (аналог GCC `nonnull`, но детальнее — раздельно для аргументов и возврата):

```cpp
void handle(_In_opt_ void* maybeNull);   // допускается null на входе
void handle2(_In_ void* notNull);         // null на входе — ошибка контракта

_Ret_maybenull_ void* find();             // возврат может быть null
_Ret_notnull_ void* create();             // возврат гарантированно не null
```

Как это устроено технически: SAL-макросы (`_In_`, `_Out_` и т.п.) определены в `<sal.h>` и в обычной сборке разворачиваются в пустоту (не влияют на кодогенерацию и ABI вообще) — они видны только `/analyze` (статическому анализатору Visual Studio, отдельный проход, не обычная компиляция) и инструментам вроде PREfast. Поэтому SAL можно свободно добавлять в заголовки без риска сломать что-либо на других компиляторах или в обычной сборке — просто игнорируется, если не запускать `/analyze`.

Сравнение с уже обсуждавшимся:

- **GCC `nonnull`** влияет на реальную кодогенерацию (компилятор может убрать проверку на `nullptr`, опираясь на контракт) — SAL `_In_`/`_Ret_notnull_` на кодогенерацию не влияет вообще, это чисто аналитическая аннотация.
- **Clang thread-safety `guarded_by`/`requires_capability`** — концептуально ближе к SAL по духу (тоже контракты для статического анализа), но SAL шире по охвату: не только про блокировки, а про направление данных, размеры буферов, nullability, успех/неуспех операции.
- **C++ Core Guidelines `gsl::not_null<T>`** — современная переносимая альтернатива части того, что делает SAL для nullability: вместо аннотации поверх `T*` используется отдельный тип-обёртка, проверяемый на уровне языка/шаблона, а не отдельным анализатором. Работает на любом компиляторе, а не только под `/analyze`.

Практический контекст: SAL активно используется в заголовках самого Windows SDK и в крупных C/C++ кодовых базах Microsoft (историческая причина появления — систематическая борьба с уязвимостями переполнения буфера в 2000-х), но в кроссплатформенном коде почти не встретишь — специфично для MSVC-тулчейна, требует `/analyze` для реальной пользы, и для равнозначной защиты в GCC/Clang-мире используют `nonnull`, `format`, а для размеров буферов — скорее `std::span`, sanitizers (ASan/UBSan) и статический анализ через clang-tidy/Coverity, чем прямой аналог SAL.
