`__declspec(dllexport)` / `__declspec(dllimport)` — механизм MSVC для явного экспорта/импорта символов из/в DLL. В отличие от GCC/Clang на ELF (где по умолчанию всё экспортируется, и `visibility("hidden")` нужен, чтобы скрыть), на Windows поведение обратное по духу реализации: чтобы символ попал в экспортируемую таблицу DLL, его нужно явно пометить `dllexport` при компиляции самой библиотеки, а тот, кто её использует, должен видеть тот же символ как `dllimport` — это два разных режима компиляции одного и того же заголовка.

```cpp
#if defined(BUILDING_MYLIB)
  #define MYLIB_API __declspec(dllexport)
#else
  #define MYLIB_API __declspec(dllimport)
#endif

class MYLIB_API Calculator {
public:
    Calculator();
    int add(int a, int b) const;
};

MYLIB_API int freeFunctionAdd(int a, int b);
```

При сборке самой DLL определяется `BUILDING_MYLIB` (например, через `target_compile_definitions(mylib PRIVATE BUILDING_MYLIB)` в CMake) — заголовок разворачивается в `dllexport`. Любой другой проект, который просто подключает этот заголовок и линкуется с `.lib` (import library), не определяет `BUILDING_MYLIB` — получает `dllimport`. Это ровно тот паттерн `MYLIB_EXPORTS`/`CORE_EXPORTS`, что уже использовался в демо-проектах выше — единственная реальная разница с Unix-версией макроса в том, что на Windows _нужны обе_ формы (`dllexport` при сборке, `dllimport` при использовании), тогда как `visibility("default")` в GCC — одна и та же форма в обоих случаях.

Важные нюансы, специфичные для Windows/MSVC:

- **`dllimport` — не просто "заглушка".** Он реально меняет кодогенерацию у потребителя библиотеки: обращение к экспортированной глобальной переменной или невиртуальной функции идёт через дополнительный уровень косвенности (импорт-thunk/таблицу), потому что адрес символа неизвестен на этапе компиляции потребителя, только на этапе загрузки DLL. Если забыть `dllimport` (или, что случается чаще, использовать заголовок без правильного значения макроса), в некоторых случаях компилируется без ошибки, но линковка или рантайм ведёт себя некорректно.
- **Классы целиком.** `dllexport`/`dllimport` на классе экспортирует все его нестатические методы и статические поля (аналог того, что "приватные методы всё равно попадают в экспорт" — тот же нюанс, что раньше обнаружился в demo с `visibility`).
- **Шаблоны нельзя экспортировать напрямую** — `dllexport` на шаблонном классе не работает так, как ожидается; типичное решение — явная инстанциация конкретных специализаций с `template class MYLIB_API std::vector<int>;` (осторожно, у стандартных контейнеров это чревато конфликтами с их собственными настройками экспорта).
- **Автоматическая генерация `.lib`.** При сборке DLL с `dllexport`-символами MSVC-линкер автоматически создаёт import library (`mylib.lib`) — именно с ней линкуется потребитель (сам `.dll` в момент линковки не нужен, только в рантайме).
- **`extern "C"`** часто добавляют вместе с `dllexport` для C-совместимых функций, чтобы убрать C++ name mangling и получить предсказуемое имя символа в экспортируемой таблице (важно, если DLL должна быть совместима с `LoadLibrary`+`GetProcAddress`, как в примере с плагинами выше, или с другими языками).

Ровно этот паттерн уже использовался в CORE_API/MYLIB_API макросах в предыдущих демо-проектах этого чата — там `dllexport`/`dllimport` были частью кроссплатформенного макроса именно для того, чтобы один и тот же заголовок работал и под GCC/Clang (`visibility`), и под MSVC (`declspec`).
