# Сборка модулей и инструментарий

## Почему сборка модулей принципиально сложнее

Корень всех трудностей — одно фундаментальное отличие от заголовков. Вспомните Этап 1: при `#include` каждая единица трансляции **независима**, их можно компилировать в любом порядке и параллельно. Заголовок — это просто текст, который вставляется; ему не нужна предварительная компиляция.

С модулями всё иначе. `import math;` требует, чтобы **BMI модуля `math` уже существовал** к моменту компиляции. А BMI порождается компиляцией интерфейса `math`. Значит:

**Появляется обязательный порядок компиляции.** Интерфейс модуля нужно скомпилировать **раньше** всех, кто его импортирует. Файлы больше не равноправны и не полностью независимы.

Это ломает привычную модель сборки. Раньше система сборки могла просто сказать «скомпилируй все `.cpp` параллельно, потом слинкуй». Теперь ей нужно сначала **узнать граф зависимостей между модулями** (кто кого импортирует), выстроить правильный порядок и только потом запускать компиляцию. А узнать этот граф можно, лишь заглянув внутрь файлов и прочитав строки `import`/`export module`. Эта задача называется **сканирование зависимостей модулей** (module dependency scanning), и именно она долго мешала системам сборки нормально поддержать модули.

## BMI — ключевой артефакт

**BMI (Built Module Interface)** — бинарный файл, в который компилируется интерфейс модуля. Это разобранное, готовое к подключению представление модуля. Важные свойства BMI, которые надо понимать:

**BMI не переносим.** Он привязан к конкретному компилятору, его версии и флагам компиляции. BMI, собранный Clang, не прочитает GCC. BMI, собранный с одним набором флагов, может не подойти при других флагах. Это не объектный файл и не библиотека — его нельзя распространять как артефакт. Каждый, кто собирает ваш код, генерирует BMI у себя.

**У каждого компилятора своё расширение и формат BMI:**

|Компилятор|Расширение BMI|
|---|---|
|MSVC|`.ifc`|
|GCC|`.gcm`|
|Clang|`.pcm`|

**BMI — это не объектный файл.** Тонкий момент: компиляция интерфейса модуля даёт **два** результата — BMI (для тех, кто импортирует) и объектный файл `.o` (с кодом, который пойдёт в линковку). Их не надо путать: BMI нужен на этапе компиляции потребителей, `.o` — на этапе линковки.

## Расширения исходных файлов

Стандарт C++ **не фиксирует** расширение для файла интерфейса модуля — это мы отмечали на Этапе 2. Сложились разные соглашения:

|Компилятор|Ожидаемое расширение интерфейса|Как иначе указать|
|---|---|---|
|MSVC|`.ixx`|флагом для произвольного имени|
|Clang|`.cppm`|флаг `-x c++-module`|
|GCC|обычный `.cpp`|определяет по содержимому|

Это само по себе создаёт трение: один и тот же проект под разные компиляторы может хотеть разных расширений. Многие проекты выбирают `.ixx` или `.cppm` как наиболее явные и настраивают систему сборки понимать их везде.

## Ручная компиляция — чтобы понять механику

Прежде чем уйти в CMake, полезно один раз увидеть «голые» команды. Возьмём модуль `math` (интерфейс + реализация) и `main.cpp`.

**Clang:**

```bash
# 1. интерфейс → BMI (.pcm) и объектный файл
clang++ -std=c++20 -x c++-module math.cppm --precompile -o math.pcm
clang++ -std=c++20 -c math.pcm -o math.o

# 2. потребитель — указываем, где взять BMI модуля
clang++ -std=c++20 -fprebuilt-module-path=. -c main.cpp -o main.o

# 3. линковка
clang++ math.o main.o -o program
```

**GCC:**

```bash
# GCC создаёт BMI автоматически при компиляции интерфейса
g++ -std=c++20 -fmodules-ts -c math.cpp -o math.o   # попутно появится gcm.cache/
g++ -std=c++20 -fmodules-ts -c main.cpp -o main.o
g++ math.o main.o -o program
```

**MSVC:**

```bash
# интерфейс .ixx → .ifc (BMI) + .obj
cl /std:c++20 /interface /c math.ixx
cl /std:c++20 /c main.cpp
link math.obj main.obj /OUT:program.exe
```

Замечания к этому: команды у трёх компиляторов **заметно разные** — флаги, порядок, способ указать путь к BMI. Это не косметика, а реальная причина, по которой кросс-компиляторная сборка модулей вручную мучительна. И обратите внимание: везде интерфейс собирается **до** потребителя, и потребителю надо **подсказать путь к BMI** (`-fprebuilt-module-path`, `gcm.cache`, автоматически в каталоге). Делать это руками на проекте из сотен файлов невозможно — отсюда необходимость системы сборки.

## CMake и модули

CMake — фактический стандарт сборки C++ (Этап 1), и именно через него большинство будет работать с модулями. Но поддержка модулей в CMake появилась **поздно и постепенно**, потому что CMake пришлось научиться тому самому сканированию зависимостей.

**Требования к окружению.** Для модулей в CMake нужно совпадение нескольких свежих компонентов: достаточно новая версия **CMake**, генератор, умеющий динамические зависимости (надёжнее всего **Ninja**; поддержка в Visual Studio-генераторе тоже есть), и свежий компилятор. Старые версии любого из звеньев работать не будут. Поскольку конкретные минимальные версии быстро сдвигаются, перед стартом стоит свериться с актуальной документацией CMake — но общий принцип: «берите максимально свежее всё».

**Как объявляются модули в CMake.** Файлы-интерфейсы модулей подключаются не как обычные исходники, а через специальную категорию источников — `FILE_SET` типа `CXX_MODULES`. Схематично:

```cmake
cmake_minimum_required(VERSION 3.28)
project(modules_demo CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(app main.cpp)

target_sources(app
  PUBLIC
    FILE_SET CXX_MODULES FILES
      math.cppm          # интерфейсные единицы модулей идут сюда
)
```

Идея: вы перечисляете интерфейсы модулей в `FILE_SET CXX_MODULES`, а CMake берёт на себя сканирование, определение порядка и передачу нужных флагов компилятору. Обычные `.cpp` (реализация, `main`) остаются обычными источниками.

**`import std;` в CMake.** Поддержка стандартного модуля `std` — отдельная история и появилась ещё позже. Она требует более новой версии CMake и до недавнего времени пряталась за экспериментальным флагом (нужно было явно «включить» возможность собирать модуль `std`). Это самый подвижный участок — здесь особенно важно смотреть текущую документацию вашей версии CMake.

## Проблема распространения библиотек

Важное практическое следствие, которое стоит осознать заранее. Раньше библиотеку с заголовками распространять было просто: отдал `.h` + скомпилированную `.lib`/`.a`, и всё. С модулями так **не получится**: BMI непереносим (привязан к компилятору/версии/флагам), поэтому отдать готовый BMI нельзя.

Это значит, что модульные библиотеки сейчас распространяют в виде **исходников интерфейсов модулей** (`.cppm`/`.ixx`), которые потребитель компилирует у себя. Экосистема распространения модульных библиотек (пакетные менеджеры, бинарные дистрибутивы) пока менее зрелая, чем для заголовков. Это одна из причин, почему сторонние библиотеки массово ещё не перешли на модули — у мира заголовков пока проще логистика.

## Практический совет по старту

Чтобы не утонуть, разумный порядок освоения сборки:

Начните с **одного компилятора и Ninja+CMake свежих версий** — не пытайтесь сразу сделать кросс-компиляторную сборку. Сначала заведите простейший проект из одного модуля через `FILE_SET CXX_MODULES`. Затем добавьте `import std;`, если ваш стек его поддерживает. И только потом усложняйте — несколько модулей, разделы, реализация в отдельных файлах. Если сборка «не видит» модуль или жалуется на BMI — почти всегда дело в версиях (что-то из CMake/компилятора/генератора недостаточно свежее) или в неправильном объявлении интерфейса как обычного источника вместо `FILE_SET CXX_MODULES`.

## Сводка

|Аспект|Суть|
|---|---|
|Порядок компиляции|интерфейс → раньше потребителей; нужен граф зависимостей|
|Сканирование зависимостей|система сборки читает `import`/`export module`, строит порядок|
|BMI|`.ifc` (MSVC) / `.gcm` (GCC) / `.pcm` (Clang); **непереносим**|
|BMI ≠ `.o`|компиляция интерфейса даёт и BMI, и объектный файл|
|Расширения|`.ixx` (MSVC) / `.cppm` (Clang) / `.cpp` (GCC)|
|CMake|`FILE_SET CXX_MODULES`, нужен Ninja и свежие версии|
|`import std;`|в CMake — отдельная, ещё более новая и подвижная поддержка|
|Распространение|только исходники интерфейсов; BMI распространять нельзя|

## Что вы освоили

Вы понимаете, почему сборка модулей сложнее заголовков (обязательный порядок компиляции и необходимость сканировать граф зависимостей), что такое BMI и почему он непереносим и не равен объектному файлу. Знаете расширения исходников и BMI у трёх компиляторов, видели «голые» команды компиляции и понимаете, почему они так различаются. Умеете подключить модуль в CMake через `FILE_SET CXX_MODULES` и знаете про требования к свежести инструментов. И осознаёте практическое следствие непереносимости BMI — модульные библиотеки распространяются исходниками.
