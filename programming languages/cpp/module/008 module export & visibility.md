# Экспорт и видимость в модулях

## Три уровня видимости в модуле

Ключевая модель, которую нужно держать в голове: внутри модуля каждое имя попадает в одну из трёх категорий видимости.

|Уровень|Кто видит|Как задаётся|
|---|---|---|
|Экспортированное|потребители модуля + весь модуль|`export`|
|Видимое в модуле|только единицы этого модуля|объявление без `export`|
|Локальное (внутренняя линковка)|только своя единица трансляции|`static`, анонимный namespace|

Первый уровень — публичный API. Второй — общая «кухня» модуля, доступная всем его файлам, но скрытая снаружи. Третий — приватные детали отдельного файла. Разберём каждый, особенно второй, который и есть новинка модулей.

## Модульная линковка (module linkage)

Вспомните Этап про линковку: были внешняя (вся программа), внутренняя (одна единица трансляции) и отсутствие линковки. Модули добавляют **четвёртый вид — модульную линковку**.

> Имя с модульной линковкой видно во всех единицах **своего модуля**, но не доступно за его пределами.

Именно её получает имя, объявленное в модуле **без** `export` и **без** `static`:

```cpp
export module bank;

export double getBalance();   // экспорт — внешняя видимость (публичный API)

double applyInterest(double); // НЕ export — модульная линковка
                              // видно во всех файлах модуля bank,
                              // но не у потребителей
```

Это принципиально новая возможность. В мире заголовков такого уровня не было: имя было либо `static` (заперто в одном `.cpp`), либо внешним (видно всей программе, со всеми рисками ODR и конфликтов). Модульная линковка даёт промежуточный, очень естественный уровень — «общее для компонента, но приватное для остального мира».

Сравнительная таблица замыкает картину из подготовительного этапа:

|Линковка|Видимость|Как получить|
|---|---|---|
|Внутренняя|одна единица трансляции|`static`, анонимный namespace|
|**Модульная**|**весь свой модуль**|**объявление в модуле без `export`**|
|Внешняя|вся программа|`export` в модуле; обычные глобальные имена вне модулей|

## Что значит «видимо в модуле» на практике

Вернёмся к примеру с реализацией из Этапа 3. Функция `applyInterest`, объявленная в интерфейсе без `export`, доступна в единице реализации того же модуля автоматически:

**`bank.ixx`:**

```cpp
export module bank;

export double getBalance();
double applyInterest(double amount);   // модульная линковка
```

**`bank_impl.cpp`:**

```cpp
module bank;

double applyInterest(double amount) {  // видим без всякого import
    return amount * 1.05;
}

double getBalance() {
    return applyInterest(1000.0);      // используем приватную функцию модуля
}
```

А вот потребитель её не увидит:

```cpp
import bank;

int main() {
    getBalance();          // OK — экспортировано
    applyInterest(100.0);  // ОШИБКА — не экспортировано, снаружи не существует
}
```

## Экспорт пространств имён

Систематизируем `export namespace`. Есть несколько способов управлять видимостью внутри namespace.

**Экспорт всего пространства имён:**

```cpp
export module geo;

export namespace geo {     // экспортируется КАЖДЫЙ член
    double area(double r);
    double perimeter(double r);
}
```

**Частичный экспорт** — namespace не помечен, экспортируются отдельные члены:

```cpp
export module geo;

namespace geo {
    export double area(double r);   // публичное
    double helper(double r);        // модульная линковка — приватный помощник
}
```

Тонкость: можно «дописывать» в одно и то же пространство имён из разных мест, экспортируя одни члены и скрывая другие. Пространство имён в модуле — это не монолит, а набор объявлений, у каждого своя видимость. Само имя `geo::` снаружи существует ровно настолько, насколько в нём есть хоть один экспортированный член.

## Реэкспорт: `export import`

Конструкцию `export import` мы видели дважды — для разделов (`export import :part;`) и для целых модулей. Соберём логику воедино.

`export import X;` означает: «импортировать X себе **и** передать его публичный интерфейс дальше — тем, кто импортирует меня».

**Модуль-агрегатор**, собирающий единый API из нескольких подмодулей:

```cpp
export module app;

export import app.math;     // потребитель app получит и app.math
export import app.io;       // ...и app.io
import app.internal;        // а это — только для внутреннего пользования app
```

Теперь потребителю достаточно одной строки:

```cpp
import app;                 // получает app.math и app.io разом

int main() {
    app::math::add(2, 3);   // доступно через реэкспорт
    // app::internal::...   // недоступно — импортирован без export
}
```

Это удобный приём для построения «фасада»: внутри библиотека разбита на много модулей, а наружу выставлен один аккуратный входной модуль.

Разница между двумя формами критична:

- `import X;` — X доступен **только внутри** текущего модуля
- `export import X;` — X доступен **и внутри, и у потребителей** текущего модуля

## Транзитивность видимости

Важный нюанс, который часто путает. Обычный `import` **не транзитивен**: если модуль `A` делает `import B;` (без export), то потребитель `A` модуль `B` **не** увидит автоматически.

```cpp
// A.ixx
export module A;
import B;                   // B доступен внутри A, но не реэкспортируется
export void useB();
```

```cpp
// main.cpp
import A;
// здесь сущности из B НЕ видны — нужно отдельно import B;
```

Это намеренное и полезное свойство: оно не даёт деталям реализации «протекать» через цепочку импортов, в отличие от заголовков, где `#include` тащил за собой всё транзитивно и неконтролируемо. Хотите передать зависимость дальше — делаете это явно через `export import`.

## Почему макросы не экспортируются — теперь строго

Возвращаемся к ключевому свойству, но теперь с полным пониманием механизма. `import` — это операция уровня **семантики языка**, она происходит уже **после** препроцессора. Макрос же — феномен **препроцессора**. Когда вы пишете `import bank;`, подключается разобранный BMI с _именами_ и _типами_, но никаких `#define` там нет — они «испарились» ещё на стадии препроцессинга интерфейса модуля.

Отсюда два следствия:

**Польза:** модуль физически не может «заразить» вас своими макросами. Проблема утечки `min`/`max` и подобных из заголовков (Этап про недостатки заголовков) в модулях невозможна в принципе.

**Ограничение:** если ваш старый API раздавал функциональность через макросы, передать их через `import` нельзя. Для этого приходится либо переписывать макросы на нормальные функции/константы (что обычно и к лучшему), либо использовать **header units**

## Видимость и ODR — связь замыкается

Соберём нить из подготовительного этапа. Помните, как тщательно приходилось управлять ODR в заголовках: `extern` для переменных, `inline` чтобы разрешить определение в нескольких единицах, `static` для приватности, осторожность с порядком включения. Модули заменяют этот ручной арсенал одной декларативной моделью:

Экспортировано или нет — решает `export`, а не `inline`/`static`-трюки. Приватность компонента даёт модульная линковка, а не `static`. Утечки определений не происходит, потому что нет текстового копирования — каждое имя определено один раз в своём BMI, риск нарушить «идентичность копий» исчезает. Транзитивная утечка контролируется через `export import`, а не пускается на самотёк, как `#include`.

## Сводная картина видимости

```
                    ┌─────────────────────────────────┐
                    │           Модуль bank            │
                    │                                  │
  потребитель  ◄────┤  export getBalance()   ← API     │
  (import bank)     │                                  │
       ✕  ◄─────────┤  applyInterest()  ← модульная    │
                    │                     линковка     │
                    │                                  │
                    │  static log()  ← только свой     │
                    │                  файл            │
                    └─────────────────────────────────┘
```

|Хочу…|Использую|
|---|---|
|Публичный API|`export`|
|Общий код внутри модуля|объявление без `export` (модульная линковка)|
|Приватное для одного файла|`static` / анонимный namespace|
|Передать чужой модуль потребителю|`export import X;`|
|Использовать чужой модуль только у себя|`import X;`|
|Экспортировать всё пространство имён|`export namespace N { }`|

## Что вы освоили

Вы понимаете четыре вида линковки (включая новую **модульную**), три уровня видимости в модуле и умеете точно ими управлять: `export` для API, объявление-без-export для внутренней «кухни», `static` для приватности файла. Знаете разницу между `import` и `export import` и почему обычный импорт **не** транзитивен. И главное — видите, как эта декларативная модель видимости заменяет весь хрупкий набор приёмов из мира заголовков (`extern`, `inline`, `static`, ручной контроль ODR) и делает невозможной утечку макросов.
