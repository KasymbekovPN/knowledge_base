# Стандартная библиотека как модуль: `import std;`

## Что это и откуда

Это возможность стандарта **C++23**: вся стандартная библиотека предоставляется как два готовых именованных модуля — **`std`** и **`std.compat`**. Вместо десятков `#include <...>` вы пишете одну строку:

```cpp
import std;

int main() {
    std::vector<int> v{3, 1, 2};
    std::sort(v.begin(), v.end());
    std::cout << v[0] << '\n';
    std::string s = "hello";
    return 0;
}
```

Один `import std;` даёт доступ ко **всему** содержимому стандартной библиотеки — контейнеры, алгоритмы, потоки, строки, `<chrono>`, `<thread>` и так далее. Не нужно помнить, какой тип в каком заголовке лежит.

## Два модуля: `std` и `std.compat`

Стандарт определяет именно два модуля, и разница между ними важна.

**`std`** экспортирует всё из пространства имён `std` — то есть «чистый» C++ интерфейс стандартной библиотеки. Имена C-функций в глобальном пространстве (вроде `::printf`, `::memcpy`) он **не** добавляет в глобальную область.

**`std.compat`** — это `std` плюс глобальные C-имена. Он дополнительно экспортирует функции из C-заголовков в глобальное пространство имён, как если бы вы сделали `#include <cstdio>` и получили и `std::printf`, и `::printf`.

```cpp
import std;

int main() {
    std::printf("ok\n");   // OK — в namespace std
    // printf("ok\n");     // ОШИБКА — глобального printf нет
}
```

```cpp
import std.compat;

int main() {
    printf("ok\n");        // OK — глобальные C-имена доступны
    std::printf("ok\n");   // тоже OK
}
```

Практическое правило: для нового C++ кода используйте **`std`**. Берите **`std.compat`** только при миграции старого кода, который полагается на глобальные C-функции без префикса `std::`, — чтобы не переписывать все вызовы.

## Чем это лучше header units

Вспомните Этап 6, где мы обсуждали `import <vector>;` как header unit. `import std;` — принципиально другой и лучший механизм. Сравним.

| |`import <vector>;` (header unit)|`import std;` (именованный модуль)|
|---|---|---|
|Что это|заголовок, обёрнутый как модуль|настоящий именованный модуль|
|Сколько строк|по одной на каждый заголовок|**одна** на всю библиотеку|
|Макросы|экспортирует (наследие заголовка)|не экспортирует (чистый модуль)|
|Поддержка инструментами|капризная, неравномерная|заметно лучше и стабильнее|
|Статус|C++20, на практике шероховат|C++23, рекомендуемый путь|

Ключевые практические плюсы `import std;`: одна строка вместо списка заголовков, и — поскольку это настоящий модуль — **никаких утечек макросов** из стандартных заголовков. Та самая проблема `min`/`max` из Windows-заголовков (Этап про недостатки заголовков) здесь не возникает в принципе.

Именно поэтому, как мы обсуждали в прошлых этапах, на практике многие проекты **пропускают** header units и сразу идут на `import std;` — он и удобнее, и надёжнее поддержан.

## Скорость компиляции — главный выигрыш

Это самая ощутимая выгода. Вернёмся к корню проблемы заголовков (подготовительный этап): `#include <vector>` тянет тысячи строк, и они **заново парсятся в каждой единице трансляции**. Включили `<vector>`, `<string>`, `<algorithm>`, `<map>` в сотне файлов — компилятор обработал их содержимое сто раз.

С `import std;` стандартная библиотека компилируется в BMI **один раз**, а дальше подключается готовой. На крупных проектах это даёт значительное сокращение времени сборки. Точные цифры зависят от проекта и компилятора, но порядок выигрыша — от десятков процентов; чем больше у вас единиц трансляции и чем тяжелее набор включаемых заголовков, тем заметнее эффект.

## Важное правило: нельзя смешивать `import std;` и `#include` как попало

Есть тонкость, на которой многие спотыкаются. Смешивание модульного и заголовочного подключения одной и той же части библиотеки в одной единице трансляции может приводить к проблемам — конфликтам и неоднозначностям. Безопасный принцип:

В пределах одной единицы трансляции выберите **один** способ для стандартной библиотеки. Либо `import std;`, либо `#include <...>`, но не мешайте их для одних и тех же сущностей.

Особенно осторожно — с порядком: если вам всё же нужен и `import std;`, и какой-то `#include`, который тянет стандартные заголовки, это территория тонких ошибок. Проще держать модульный код целиком на `import std;`.

И ещё нюанс: если вы пишете **свой** модуль и хотите внутри него использовать `import std;`, помните, что `import` идёт **после** объявления модуля (в отличие от `#include`, который шёл бы в глобальном фрагменте):

```cpp
export module mymodule;

import std;                        // import — после export module, не в глобальном фрагменте

export double mean(const std::vector<double>& v) {
    return std::reduce(v.begin(), v.end()) / v.size();
}
```

## Состояние поддержки

Честная картина на 2025–2026 год. `import std;` — самая зрелая часть модульной инфраструктуры, но «зрелая» не значит «бесшовная везде».

Все три основных компилятора (MSVC, GCC, Clang) в свежих версиях поддерживают `import std;`, и эта поддержка активно дорабатывалась. MSVC с Visual Studio продвинулся здесь раньше других. Для GCC и Clang часто требуются достаточно новые версии и явное указание стандарта C++23.

Тонкость в том, что `import std;` требует, чтобы **BMI стандартной библиотеки был собран** под ваш компилятор и флаги. Иногда это происходит автоматически, иногда систему сборки нужно настроить, чтобы она собрала модуль `std` перед вашим кодом. В CMake поддержка `import std;` появилась, но требует достаточно новой версии CMake и генератора, и иногда — включения экспериментального флага.

Поскольку всё это быстро меняется, перед использованием стоит свериться с актуальной документацией вашего компилятора и CMake — конкретные требования к версиям сдвигаются от релиза к релизу.

## Практический вывод

Если вы хотите попробовать модули с минимальными усилиями и реальной пользой — начинайте именно с `import std;`. Это:

Замена пачки `#include` стандартной библиотеки на одну строку. Реальное ускорение компиляции на сколько-нибудь крупном проекте. Защита от утечки макросов из стандартных заголовков. И при этом — не требует переписывать архитектуру: можно просто в новых файлах писать `import std;` вместо привычных includes, не трогая остальное.

Это самый дешёвый способ получить ощутимую отдачу от модулей уже сегодня, ещё до того, как вы начнёте проектировать собственные именованные модули.

## Что вы освоили

Вы знаете два стандартных модуля — `std` (чистый C++) и `std.compat` (плюс глобальные C-имена) — и когда какой брать. Понимаете, почему `import std;` лучше header units (одна строка, без макросов, надёжнее поддержан) и в чём его главная выгода (однократная компиляция стандартной библиотеки → ускорение сборки). Знаете правило не смешивать `import std;` с `#include` стандартной библиотеки в одной единице трансляции и помните, что внутри своего модуля `import std;` пишется после `export module`.
