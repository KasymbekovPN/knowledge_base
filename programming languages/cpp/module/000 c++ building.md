# Системы сборки C++: от исходника к исполняемому файлу

Чтобы понять модули (да и C++ вообще), нужно представлять путь, который проходит ваш код от текстового файла до работающей программы. Разберём его по шагам.

## Единица трансляции (translation unit)

Это **базовая единица компиляции** в C++. Грубо говоря, единица трансляции — это один `.cpp`-файл вместе со всем содержимым, которое в него подставил препроцессор (то есть со всеми раскрытыми `#include` и макросами).

Ключевая идея: компилятор обрабатывает каждую единицу трансляции **независимо от других**. Он ничего не знает о других `.cpp`-файлах вашего проекта. Именно поэтому существуют заголовочные файлы — они дают разным единицам трансляции общие объявления.

```
main.cpp  +  все его #include  =  единица трансляции 1
math.cpp  +  все его #include  =  единица трансляции 2
```

## Этапы сборки

Весь процесс делится на несколько фаз. Упрощённо их три: **препроцессинг → компиляция → линковка**.

### 1. Препроцессор (preprocessing)

Препроцессор — это «текстовый редактор», который работает **до** настоящего компилятора. Он обрабатывает все директивы, начинающиеся с `#`, и выполняет чисто текстовые операции:

- `#include <file>` — буквально вставляет содержимое файла на это место
- `#define MAX 100` — заменяет все вхождения `MAX` на `100`
- `#ifdef / #ifndef / #endif` — условно включает или вырезает куски кода
- удаляет комментарии

Результат работы препроцессора — это та самая единица трансляции: один большой текстовый файл без единой директивы `#`.

Именно здесь кроется **главная проблема заголовков**: если десять `.cpp`-файлов включают один тяжёлый заголовок, препроцессор честно вставит и заново обработает его содержимое десять раз. Отсюда — медленная компиляция и необходимость include guards, чтобы один заголовок не вставился дважды в одну единицу трансляции.

### 2. Компиляция (compilation)

Компилятор берёт готовую единицу трансляции и превращает её в **объектный файл** (`.o` или `.obj`) — машинный код для конкретной платформы. На этом этапе происходит:

- **лексический и синтаксический анализ** (разбор текста на токены и проверка грамматики)
- **семантический анализ** (проверка типов, разрешение имён)
- **оптимизация**
- генерация машинного кода

Важный момент: компилятор проверяет, что всё **объявлено**, но не требует, чтобы всё было **определено**. Если вы вызываете функцию `add()`, объявленную в заголовке, но определённую в другом `.cpp`, компилятор поверит вам «на слово» и оставит в объектном файле «пустое место» (символ) для линковщика.

```cpp
int add(int, int);   // объявление — компилятору этого достаточно
int x = add(2, 3);   // ок, определение найдёт линковщик
```

### 3. Линковка (linking)

Линковщик (linker) собирает все объектные файлы и библиотеки в **единый исполняемый файл**. Его главная задача — разрешить символы: связать каждый вызов функции с её реальным определением, разбросанным по разным объектным файлам.

```
main.o  +  math.o  +  стандартная библиотека  →  program.exe
```

Здесь возникают характерные ошибки:

- **undefined reference** («неопределённая ссылка») — функция объявлена и вызвана, но её определение нигде не найдено
- **multiple definition** («множественное определение») — одна и та же сущность определена в нескольких единицах трансляции, что нарушает **ODR** (One Definition Rule, правило одного определения)

## Полная картина

```
        препроцессор          компилятор           линковщик
.cpp  ───────────────►  ед.трансляции  ──────►  .o  ──────────┐
.h  (вставляется)                                              ├──►  .exe
.cpp  ───────────────►  ед.трансляции  ──────►  .o  ──────────┘
                                          + библиотеки
```

## Где здесь системы сборки

Когда файлов десятки и сотни, вызывать компилятор и линковщик вручную невозможно. **Системы сборки** (Make, CMake, Ninja, MSBuild) автоматизируют это: отслеживают зависимости между файлами, перекомпилируют только изменившиеся единицы трансляции и запускают линковку. **CMake** сегодня — фактический стандарт: он не компилирует сам, а генерирует конфигурацию для Make/Ninja/Visual Studio.

## Как это связано с модулями

Теперь понятно, что чинят модули. Они устраняют текстовую подстановку препроцессора: модуль компилируется в бинарный интерфейс (**BMI**) **один раз**, а при `import` подключается уже в готовом виде, а не вставляется текстом и не парсится заново. Это убирает повторную обработку заголовков, проблему утечки макросов и необходимость include guards. При этом этапы «компиляция → линковка» и понятие единицы трансляции сохраняются — модуль тоже остаётся единицей трансляции, просто другого вида.
