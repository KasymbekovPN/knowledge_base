# Традиционные заголовочные файлы в C++

## Зачем они вообще нужны

Вспомним ключевой факт из прошлой темы: компилятор обрабатывает каждую единицу трансляции (`.cpp`-файл) **независимо**. Файл `main.cpp` ничего не знает о том, что лежит в `math.cpp`.

Но при этом в C++ действует правило: чтобы что-то использовать, нужно сначала это **объявить**. Если `main.cpp` вызывает функцию `add()`, компилятор должен знать её сигнатуру — иначе он не пройдёт проверку типов.

Возникает дилемма: объявление нужно во многих файлах, но дублировать его руками — это кошмар сопровождения. Решение — вынести общие объявления в **заголовочный файл** и подключать его директивой `#include`.

## Как работает `#include`

`#include` — это директива **препроцессора**, и она делает ровно одну вещь: **буквально вставляет содержимое указанного файла** на своё место. Никакой магии, чистая текстовая подстановка.

**math.h** — заголовок с объявлением:

```cpp
int add(int a, int b);   // только объявление, без тела
```

**math.cpp** — определение:

```cpp
#include "math.h"
int add(int a, int b) {   // реализация
    return a + b;
}
```

**main.cpp** — использование:

```cpp
#include "math.h"        // сюда вставится строка объявления
int main() {
    return add(2, 3);    // компилятор знает сигнатуру add
}
```

После препроцессинга `main.cpp` фактически выглядит так, будто объявление `add` написано прямо в нём. Компилятор доволен, а реальное тело функции потом найдёт линковщик в `math.o`.

Кавычки против угловых скобок: `#include "file.h"` ищет файл сначала рядом с текущим (для ваших файлов), а `#include <file>` — в системных путях (для библиотек).

## Проблема двойного включения

Раз `#include` — это тупая подстановка, возникает опасная ситуация. Представьте:

```
a.h  включает  common.h
b.h  включает  common.h
main.cpp  включает  и a.h, и b.h
```

После работы препроцессора содержимое `common.h` окажется в `main.cpp` **дважды**. Если там объявлен класс или структура, получим ошибку **переопределения** — нарушение ODR (правила одного определения) в пределах одной единицы трансляции:

```cpp
// common.h
struct Point { int x, y; };   // если вставится дважды — ошибка компиляции
```

Нужен механизм, который скажет препроцессору: «этот файл уже вставлен, второй раз не надо». Таких механизма два.

## Include guards (стражи включения)

Это классический способ, работающий на условных директивах препроцессора:

```cpp
#ifndef MATH_H        // «если макрос MATH_H ещё не определён...»
#define MATH_H        // «...определи его...»

int add(int a, int b);   // ...и обработай содержимое

#endif                // конец защищённого блока
```

Логика проста. При первом включении макрос `MATH_H` не определён, поэтому препроцессор заходит внутрь, сразу определяет его и обрабатывает содержимое. При втором включении в той же единице трансляции макрос уже существует — и весь блок между `#ifndef` и `#endif` просто вырезается. Содержимое вставляется ровно один раз.

**Минусы include guards:**

- **Многословность** — три строки служебного кода в каждом заголовке.
- **Уникальность имён** — макрос `MATH_H` должен быть уникальным во всём проекте. Если в двух разных заголовках случайно совпадёт страж (например, оба назвали `UTILS_H`), один из файлов молча не включится — и вы получите загадочные ошибки.
- Имена легко ошибиться при копировании (опечатка в `#define` ломает защиту).

## `#pragma once`

Более современная альтернатива — одна строка в начале файла:

```cpp
#pragma once

int add(int a, int b);
```

Она говорит компилятору: «включай этот физический файл не более одного раза на единицу трансляции». Компилятор отслеживает файл по его пути/содержимому, а не по имени макроса.

**Плюсы:** короче, нет проблемы коллизии имён, чуть быстрее (компилятор может не открывать файл повторно).

**Минусы:** формально `#pragma once` **не входит в стандарт** C++ (хотя поддерживается всеми основными компиляторами). Редкие пограничные случаи: если один и тот же файл доступен по двум разным путям (символические ссылки, хитрая система сборки), компилятор может посчитать их разными файлами и включить дважды.

На практике сегодня `#pragma once` — самый распространённый выбор.

## Фундаментальные недостатки всего подхода

Стражи решают лишь одну частную проблему — двойное включение. Но сама модель «заголовок = текстовая вставка» порочна по своей сути:

**1. Медленная компиляция.** Если тяжёлый заголовок (скажем, `<vector>`) включён в 100 единиц трансляции, препроцессор вставит и компилятор заново распарсит его содержимое **100 раз**. Стандартные заголовки тянут за собой тысячи строк — отсюда долгая сборка крупных проектов.

**2. Утечка макросов.** Макросы не уважают области видимости. Если какой-то заголовок написал `#define max(a,b) ...`, этот макрос «протечёт» во все файлы ниже по цепочке включений и может сломать ваш код самым неожиданным образом. Классический конфликт — макрос `min`/`max` из Windows-заголовков ломает `std::min`.

**3. Зависимость от порядка включения.** Поскольку всё — это подстановка текста сверху вниз, порядок `#include` иногда **имеет значение**. Один заголовок может молча полагаться на то, что другой включён раньше. Это хрупко и непредсказуемо.

**4. Утечка деталей реализации.** В заголовок часто приходится выносить приватные детали (например, private-поля класса нужны компилятору для вычисления размера объекта). Они становятся видны всем, кто включает заголовок, хотя пользоваться ими нельзя.

**5. Дублирование объявлений и определений.** Объявление в `.h`, определение в `.cpp` — приходится поддерживать сигнатуру в двух местах. Рассинхрон ведёт к ошибкам.

## Как модули закрывают эти проблемы

Теперь ценность модулей очевидна — они бьют точно по этим болям:

|Проблема заголовков|Решение в модулях|
|---|---|
|Повторный парсинг при каждом `#include`|Модуль компилируется в бинарный интерфейс (BMI) **один раз**, при `import` подключается готовым|
|Утечка макросов|Макросы **не** экспортируются из модуля|
|Зависимость от порядка включения|Порядок `import` не важен|
|Утечка деталей реализации|Только помеченное `export` видно снаружи|
|Двойное включение, нужда в guards|Не существует как проблема — guards не нужны вовсе|

Грубо говоря, модули заменяют **текстовую** модель («скопируй этот файл сюда») на **семантическую** («дай мне уже разобранный интерфейс этого компонента»). Именно поэтому исчезают и стражи включения, и большинство перечисленных недостатков разом.
