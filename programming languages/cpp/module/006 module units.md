# Структура модуля: интерфейс и реализация

## Виды единиц модуля

Сначала систематизируем. Любой файл, принадлежащий модулю, — это **единица модуля** (module unit). Их четыре вида:

| Вид единицы          | Объявляется как         | Назначение                          |
| -------------------- | ----------------------- | ----------------------------------- |
| Интерфейсная единица | `export module M;`      | Публичный API модуля                |
| Единица реализации   | `module M;`             | Реализация, скрытая от потребителей |
| Интерфейсный раздел  | `export module M:part;` | Часть интерфейса                    |
| Раздел реализации    | `module M:part;`        | Часть реализации                    |

Разделы (partitions) — тема следующего этапа. Сейчас сосредоточимся на первых двух: **интерфейс** и **реализация**.

Ключевое правило: **первичная интерфейсная единица** (primary module interface unit) — та, что объявлена `export module M;` без двоеточия — должна быть **ровно одна** на модуль. Это «лицо» модуля. А вот единиц реализации может быть сколько угодно.

## Зачем разделять интерфейс и реализацию

На прошлых этапах мы определяли функции прямо в интерфейсе:

```cpp
export module math;
export int add(int a, int b) { return a + b; }   // и объявление, и тело здесь
```

Для маленьких функций это нормально. Но у такого подхода есть минусы для крупного кода: тело функции попадает в BMI, а значит, при изменении _реализации_ (не интерфейса) приходится перекомпилировать всех потребителей. Кроме того, смешивать публичный контракт с деталями реализации — плохо для читаемости.

Решение знакомо по заголовкам: в интерфейсе оставляем **объявления**, тела выносим в **единицу реализации**.

## Разделение на два файла

**Файл `math.ixx`** — интерфейс (только объявления):

```cpp
export module math;            // первичная интерфейсная единица

export int add(int a, int b);  // объявления — БЕЗ тел
export int sub(int a, int b);

int helper(int x);             // приватное объявление (не export)
```

**Файл `math_impl.cpp`** — реализация:

```cpp
module math;                   // единица реализации — БЕЗ export!

int add(int a, int b) {        // определение
    return a + b;
}

int sub(int a, int b) {
    return a - b + helper(0);
}

int helper(int x) {            // определение приватной функции
    return x * 2;
}
```

Обратите внимание на синтаксис: единица реализации начинается с `module math;` — **без** ключевого слова `export`. Именно отсутствие `export` отличает реализацию от интерфейса. Эта строка говорит: «данный файл принадлежит модулю `math`, но интерфейса не объявляет».

## Важнейшая особенность: реализация неявно «видит» интерфейс

Здесь — принципиальное отличие от заголовков, которое часто удивляет. В единице реализации `math_impl.cpp` **не нужно** ни `import math;`, ни `#include "math.ixx"`. Единица реализации **автоматически** видит всё из интерфейса своего модуля — и экспортированное (`add`, `sub`), и приватное (`helper`).

Сравните с заголовками: там `math.cpp` был обязан написать `#include "math.h"`, чтобы увидеть объявления. В модулях файлы одного модуля образуют единое целое — реализация знает интерфейс «из коробки».

```cpp
// math_impl.cpp
module math;        // этой строки достаточно
                    // helper и add видны без всякого import/include
```

Это снова устраняет дублирование и рассинхрон: объявление существует в одном месте (интерфейс), реализация просто его подхватывает.

## Что экспортируется, а что нет

Тонкость, которую важно усвоить: **экспортировать можно только в интерфейсной единице**. В единице реализации слово `export` запрещено вовсе.

```cpp
// math_impl.cpp
module math;
export int add(int, int) { ... }   // ОШИБКА: export в реализации недопустим
```

Логика проста: интерфейс решает, что видно снаружи; реализация лишь наполняет это телами. Видимость определяется один раз — в интерфейсе.

## Полная картина сборки

Теперь у нас три файла, и порядок компиляции становится ещё важнее:

```
math.ixx       ──компиляция──►  math BMI  +  math_interface.o
                                    │
math_impl.cpp  ──компиляция(читает BMI)──►  math_impl.o
                                    │
main.cpp       ──компиляция(читает BMI)──►  main.o
                                    │
       все .o ──линковка──►  program
```

Ключевой момент: и реализация, и потребитель (`main.cpp`) зависят от **BMI**, который порождает интерфейс. Поэтому интерфейс компилируется первым. Реализация и `main.cpp` могут компилироваться в любом порядке относительно друг друга — оба нуждаются только в готовом BMI интерфейса.

Условно на Clang:

```bash
clang++ -std=c++20 --precompile math.ixx -o math.pcm        # → BMI
clang++ -std=c++20 -c math.ixx -o math_iface.o
clang++ -std=c++20 -fmodule-file=math=math.pcm -c math_impl.cpp -o math_impl.o
clang++ -std=c++20 -fmodule-file=math=math.pcm -c main.cpp -o main.o
clang++ math_iface.o math_impl.o main.o -o program
```

## Глобальный фрагмент модуля

Теперь подробно о конструкции, которую мы упомянули мельком. Если внутри модуля нужно использовать **старый заголовок** через `#include`, его нельзя писать где попало. Препроцессорные включения должны идти в **глобальном фрагменте модуля** — зоне до объявления модуля, открываемой строкой `module;`:

```cpp
module;                        // ← начало глобального фрагмента

#include <cstdio>              // legacy-заголовки только здесь
#include <cmath>

export module math;            // ← конец глобального фрагмента, начало модуля

export double area(double r) {
    return M_PI * r * r;       // M_PI пришёл из <cmath>
}
```

Зачем такое ограничение? Содержимое глобального фрагмента **не становится частью модуля** и **не экспортируется** — оно обрабатывается по старым правилам препроцессора и видно только внутри этого файла. Так модуль изолирует «грязный» легаси-мир `#include` от своего чистого интерфейса. Имена и макросы из этих заголовков не утекут к потребителям модуля.

Правила глобального фрагмента:

- он **обязан** начинаться строкой `module;` (без имени)
- в нём допустимы **только** директивы препроцессора (`#include`, `#define`)
- он заканчивается строкой `export module M;`
- если глобальный фрагмент есть, `module;` должна быть самой первой конструкцией файла

## Приватный фрагмент модуля

Зеркальная конструкция — **приватный фрагмент модуля** (private module fragment). Он позволяет в _первичном интерфейсном файле_ спрятать реализацию, не заводя отдельную единицу реализации. Открывается строкой `module : private;`:

```cpp
export module math;            // интерфейс

export int add(int a, int b);  // объявление

module : private;              // ← всё ниже — приватная реализация

int add(int a, int b) {        // определение, скрытое от потребителей
    return a + b;
}
```

Смысл: всё после `module : private;` не попадает в BMI как видимый интерфейс — это приватная зона. Удобно для маленьких модулей, когда заводить отдельный `_impl.cpp` избыточно, но при этом хочется, чтобы изменение тел функций не дёргало перекомпиляцию потребителей.

Ограничение: приватный фрагмент допустим **только** в первичной интерфейсной единице и только один на модуль.

## Три способа разместить реализацию — сравнение

Итого, тело функции в модуле можно расположить тремя способами:

|Способ|Где|Когда применять|
|---|---|---|
|Прямо в интерфейсе|`export int f(){...}` в `.ixx`|Крошечные модули, inline-подобные функции|
|Приватный фрагмент|после `module : private;` в `.ixx`|Маленькие модули, реализация в одном файле|
|Отдельная единица реализации|`module M;` в другом `.cpp`|Крупные модули, много реализации, ускорение пересборки|

## Полный пример «по-взрослому»

Соберём всё вместе — модуль с легаси-заголовком, чистым интерфейсом и отдельной реализацией.

**`geometry.ixx`:**

```cpp
module;
#include <cmath>               // легаси-заголовок в глобальном фрагменте

export module geometry;        // первичный интерфейс

export double circleArea(double r);
export double circlePerimeter(double r);

double pi();                   // приватный помощник (не export)
```

**`geometry_impl.cpp`:**

```cpp
module geometry;               // реализация, без export

double pi() {
    return std::acos(-1.0);    // std:: доступен через интерфейс
}

double circleArea(double r) {
    return pi() * r * r;
}

double circlePerimeter(double r) {
    return 2 * pi() * r;
}
```

**`main.cpp`:**

```cpp
import geometry;
import <iostream>;

int main() {
    std::cout << geometry::circleArea(0); // (если бы был в namespace)
    std::cout << circleArea(2.0) << '\n'; // 12.566...
}
```

## Что вы освоили

Вы знаете четыре вида единиц модуля и умеете разделять модуль на интерфейс (`export module M;`) и реализацию (`module M;`). Понимаете, что реализация автоматически видит интерфейс без `import`, что `export` живёт только в интерфейсе, и что есть две специальные зоны: **глобальный фрагмент** (`module;`) для изоляции легаси-`#include` и **приватный фрагмент** (`module : private;`) для встроенной реализации. Главное — видите, как структура модуля убирает дублирование объявлений и изолирует старый мир препроцессора от чистого интерфейса.

```cpp
/*

clang++ -std=c++23 --precompile math3.cppm -o math3.pcm;

if ($?) { clang++ -std=c++23 --precompile math4.cppm -o math4.pcm; }

if ($?) { clang++ -std=c++23 "-fmodule-file=math3=math3.pcm" "-fmodule-file=math4=math4.pcm" demo.cpp math3_impl.cpp math3.pcm math4.pcm -o app.exe }

*/

import math3;
import math4;

#include <iostream>
#include <format>

int main() {
    int a{42};
    int b{111};
    std::cout << std::format("add({}, {}) = {}\n", a, b , add(a, b));
    std::cout << std::format("sub({}, {}) = {}\n", a, b , sub(a, b));
    std::cout << std::format("add4({}, {}) = {}\n", a, b , add4(a, b));

    return 0;
}
```

```
add(42, 111) = 153
sub(42, 111) = -69
add4(42, 111) = 153
```
