# Внутренняя и внешняя линковка в C++

Это понятие напрямую связано с тем, что мы разбирали: компилятор обрабатывает каждую единицу трансляции независимо, а потом линковщик сшивает их вместе. **Линковка (linkage)** — это свойство имени, которое определяет, **видно ли оно за пределами своей единицы трансляции** и могут ли разные части программы ссылаться на одну и ту же сущность.

Не путайте с **этапом линковки** (linking) из прошлой темы. Там — процесс сборки объектных файлов. Здесь — свойство имени, которое этим процессом управляет. Слово одно, смысл разный.

## Три вида линковки

У каждого имени (переменной, функции, типа) есть одна из трёх разновидностей линковки.

### Внешняя линковка (external linkage)

Имя видно **во всей программе**, из всех единиц трансляции. Если в `a.cpp` есть имя с внешней линковкой, то `b.cpp` может на него сослаться — и линковщик свяжет их с **одной и той же** сущностью.

По умолчанию внешнюю линковку имеют:

- глобальные функции
- глобальные переменные
- переменные, объявленные с `extern`

```cpp
// math.cpp
int counter = 0;           // внешняя линковка
void increment() {         // внешняя линковка
    counter++;
}
```

```cpp
// main.cpp
extern int counter;        // ссылаемся на counter из math.cpp
void increment();          // объявление функции из math.cpp

int main() {
    increment();           // линковщик найдёт тело в math.o
    return counter;        // та же самая переменная, что и в math.cpp
}
```

Здесь `counter` и `increment` — **одни и те же** сущности в обоих файлах. Это и есть внешняя линковка в действии.

### Внутренняя линковка (internal linkage)

Имя видно **только внутри своей единицы трансляции**. Другие `.cpp`-файлы его не видят, даже если объявят имя с точно таким же написанием — это будут **разные**, независимые сущности.

Внутреннюю линковку дают:

- ключевое слово `static` для глобальных имён
- **анонимные пространства имён** (современный предпочтительный способ)
- глобальные `const`-переменные (по умолчанию в C++ они имеют внутреннюю линковку)

```cpp
// file1.cpp
static int secret = 42;        // внутренняя линковка — виден только здесь
static void helper() { }       // тоже только в этом файле
```

```cpp
// file2.cpp
static int secret = 99;        // совершенно ДРУГАЯ переменная!
                               // конфликта с file1.cpp нет
```

Два `secret` мирно сосуществуют, потому что каждый «заперт» в своей единице трансляции. Линковщик их даже не видит.

Современный способ — анонимное пространство имён, оно даёт внутреннюю линковку всему содержимому:

```cpp
namespace {
    int secret = 42;       // внутренняя линковка
    void helper() { }      // внутренняя линковка
}
```

### Отсутствие линковки (no linkage)

Имя относится только к своей области видимости и нигде больше не доступно. Это локальные переменные внутри функций:

```cpp
void f() {
    int x = 5;    // нет линковки — существует только внутри f()
}
```

Этот случай обычно не вызывает вопросов, поэтому основное внимание — на первые два.

## Зачем это нужно: практический смысл

### 1. Избежать конфликтов имён (ODR)

Если бы всё имело внешнюю линковку, две вспомогательные функции с именем `helper()` в разных файлах столкнулись бы при линковке — ошибка **multiple definition**. Внутренняя линковка позволяет каждому файлу иметь свои приватные хелперы, не боясь коллизий.

### 2. Инкапсуляция на уровне файла

Внутренняя линковка — способ сказать «это деталь реализации данного `.cpp`, наружу не показывать». Аналог `private`, но для единицы трансляции, а не для класса.

### 3. Управление совместным доступом

Внешняя линковка нужна, когда несколько файлов должны работать с **одной** глобальной сущностью (общий счётчик, функция из библиотеки).

## Связь с заголовочными файлами и ODR

Здесь кроется тонкость, важная для предыдущей темы. Если вы определите **переменную с внешней линковкой прямо в заголовке**:

```cpp
// bad.h
int global = 5;     // определение с внешней линковкой
```

…и включите этот заголовок в два `.cpp`, то после препроцессинга `global` окажется определён в **двух** единицах трансляции с внешней линковкой — линковщик выдаст **multiple definition**. Именно поэтому в заголовках пишут `extern int global;` (только объявление), а определение кладут в один `.cpp`. А для констант это безопасно как раз потому, что у `const` по умолчанию **внутренняя** линковка — каждая единица трансляции получает свою копию, конфликта нет.

```cpp
// ok.h
const int MAX = 100;       // внутренняя линковка — можно в заголовке
extern int global;         // только объявление — определение в .cpp
inline int shared = 5;     // inline-переменная (C++17) — тоже можно в заголовке
```

## Связь с модулями

Это снова подсвечивает преимущество модулей. В мире заголовков управление видимостью держится на хрупких соглашениях: `static`, `extern`, `inline`, анонимные пространства имён, аккуратность с определениями в `.h`. Легко ошибиться.

Модули вводят **явную** модель: всё, что не помечено `export`, по умолчанию **не видно** снаружи модуля — это естественная инкапсуляция без `static`-трюков. А имена в модуле получают особый вид связывания (**module linkage**): они видны внутри всего модуля, но не утекают в остальную программу. Грубо говоря, модуль даёт то, что раньше приходилось вручную собирать из внутренней и внешней линковки, но делает это чисто и предсказуемо.

## Краткая сводка

|Вид линковки|Видимость|Как задать|
|---|---|---|
|Внешняя|Вся программа|по умолчанию для функций и глобальных переменных; `extern`|
|Внутренняя|Одна единица трансляции|`static`, анонимный `namespace`, `const` (по умолчанию)|
|Нет линковки|Локальная область|локальные переменные|
|Модульная (C++20)|Весь модуль|имя в модуле без `export`|
