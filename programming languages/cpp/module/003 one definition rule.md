# ODR — правило одного определения (One Definition Rule)

ODR — одно из фундаментальных правил C++, на котором держится вся модель раздельной компиляции. Оно постоянно всплывало в наших прошлых темах (заголовки, линковка), теперь разберём его системно.

## Объявление против определения

Сначала чёткое различие, без которого ODR не понять.

**Объявление (declaration)** сообщает компилятору, что нечто _существует_, — вводит имя и его тип, но не создаёт саму сущность:

```cpp
int add(int a, int b);     // объявление функции — тела нет
extern int counter;        // объявление переменной — память не выделяется
class Widget;              // объявление класса (forward declaration)
```

**Определение (definition)** — это объявление, которое вдобавок _создаёт_ сущность: выделяет память, задаёт тело функции, описывает содержимое класса:

```cpp
int add(int a, int b) { return a + b; }   // определение функции
int counter = 0;                          // определение переменной
class Widget { int x; };                  // определение класса
```

Правило-мнемоника: определение всегда является объявлением, но не наоборот.

## Формулировка ODR

Правило состоит из трёх частей.

### Часть 1. В пределах одной единицы трансляции

> Любая сущность (переменная, функция, класс, шаблон) может быть **определена не более одного раза** в одной единице трансляции.

**Объявлять** можно сколько угодно раз — это безвредно. **Определить** — только однажды.

```cpp
int add(int, int);     // объявление
int add(int, int);     // ещё одно объявление — ОК, дубликаты объявлений разрешены

int add(int a, int b) { return a + b; }   // определение
int add(int a, int b) { return a - b; }   // ОШИБКА: второе определение
```

Именно эту часть ODR нарушает двойное включение заголовка — и именно её защищают include guards и `#pragma once`. Если заголовок с определением класса вставится дважды, мы получим два определения `Widget` в одной единице трансляции — ошибку компиляции.

### Часть 2. Во всей программе

> Каждая сущность с внешней линковкой, которая реально **используется**, должна быть определена **ровно один раз** во всей программе (во всех единицах трансляции вместе).

Здесь два симметричных нарушения:

**Ноль определений** → ошибка линковки **undefined reference**:

```cpp
// main.cpp
void foo();        // объявлено
int main() { foo(); }   // используется, но нигде не определено → undefined reference
```

**Два и более определений** → ошибка линковки **multiple definition**:

```cpp
// a.cpp
int counter = 0;   // определение

// b.cpp
int counter = 5;   // ВТОРОЕ определение counter с внешней линковкой → multiple definition
```

Тут видна связь с линковкой из прошлой темы: эта часть ODR касается только сущностей с **внешней** линковкой. Имена с внутренней линковкой (`static`, анонимный namespace) живут каждое в своей единице трансляции, поэтому одноимённые определения в разных файлах конфликта не вызывают — для ODR это _разные_ сущности.

### Часть 3. Определения должны быть идентичными

Самая коварная часть.

> Если сущность (класс, inline-функция, шаблон) определяется в нескольких единицах трансляции, все определения должны быть **дословно идентичны** — одинаковая последовательность токенов и одинаковый смысл имён в них.

Это нужно, потому что некоторые сущности _обязаны_ присутствовать в каждой единице трансляции, которая их использует (об этом ниже). C++ разрешает это, но требует, чтобы все копии были абсолютно одинаковыми — как будто определение одно.

## Что МОЖНО определять в нескольких единицах трансляции

Вторая часть ODR запрещает дублировать определения с внешней линковкой. Но тогда как классы и inline-функции живут в заголовках, которые включаются всюду? Для них есть **исключение**: следующие сущности разрешено определять в каждой единице трансляции (при условии идентичности из части 3):

- определения **классов** и структур
- **inline**-функции и (с C++17) **inline**-переменные
- **шаблоны**
- перечисления (`enum`)

Поэтому класс безопасно определять в заголовке: даже попав в сто единиц трансляции, он не нарушает ODR — это легальное исключение. А вот обычную (не-inline) функцию или глобальную переменную определять в заголовке **нельзя** — она получит внешнюю линковку и нарушит часть 2.

```cpp
// widget.h — что можно класть в заголовок:
class Widget { int x; };            // класс — можно
inline int helper() { return 1; }   // inline-функция — можно
template<class T> T id(T v){return v;} // шаблон — можно
inline int shared = 0;              // inline-переменная (C++17) — можно

int add(int, int);                  // объявление функции — можно (это не определение)

// int bad() { return 0; }          // НЕЛЬЗЯ: не-inline определение → multiple definition
// int global = 5;                  // НЕЛЬЗЯ: определение переменной → multiple definition
```

Это объясняет, зачем существует ключевое слово `inline`. Изначально оно намекало компилятору «встрой вызов для скорости», но сегодня его главный смысл — именно **разрешить определение в нескольких единицах трансляции** без нарушения ODR.

## Самые опасные нарушения: тихие (ill-formed, no diagnostic required)

Части 1 и 2 ODR компилятор и линковщик ловят и выдают ошибку. А вот нарушение части 3 (неидентичные определения) стандарт помечает как **«ill-formed, no diagnostic required»** — компилятор **не обязан** его обнаруживать. Программа просто соберётся и будет вести себя непредсказуемо.

Классический пример — один и тот же класс по-разному определён в двух файлах:

```cpp
// a.cpp
struct Data { int x; };           // размер 4 байта

// b.cpp
struct Data { int x; double y; }; // размер 16 байт — ДРУГОЕ определение!
```

Оба файла скомпилируются. Но если они обмениваются объектами `Data`, один считает его 4-байтовым, другой 16-байтовым — это повреждение памяти, крах в рантайме, неуловимый баг. Чаще всего такое возникает, когда заголовок реально определяет класс по-разному из-за макросов или разных флагов компиляции в разных файлах.

## Как со всем этим связаны заголовки и модули

Соберём картину воедино. Заголовочные файлы — это инструмент **соблюдения** ODR: общее объявление выносится в `.h` и подключается всюду, чтобы во всех единицах трансляции совпадали сигнатуры. Но та же текстовая модель `#include` постоянно **создаёт угрозы** для ODR: двойное включение (часть 1), случайное определение переменной в заголовке (часть 2), расхождение определений из-за макросов и порядка включения (часть 3).

Модули убирают эти угрозы по самой своей конструкции. Сущность модуля имеет единый бинарный интерфейс (BMI) — нет текстового копирования, значит, нет и расхождения копий (часть 3 не может нарушиться случайно). Нет повторной вставки — не нужны guards (часть 1). Видимость управляется `export`, а не ручными `inline`/`static`-трюками. Грубо говоря, модули превращают соблюдение ODR из дисциплины программиста, держащейся на соглашениях, в гарантию, встроенную в язык.

## Краткая сводка

|Уровень ODR|Что требует|Нарушение →|
|---|---|---|
|Единица трансляции|≤ 1 определения|ошибка компиляции|
|Вся программа (внешняя линковка)|ровно 1 определение используемого|undefined / multiple reference (линковка)|
|Идентичность копий|все определения дословно равны|тихий UB, диагностика не требуется|
|Исключения|классы, inline, шаблоны можно определять везде|при условии идентичности|
