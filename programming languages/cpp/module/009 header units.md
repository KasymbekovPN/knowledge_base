# Header units и миграция со старого кода

## Проблема перехода

Допустим, вы хотите начать использовать модули, но весь ваш код (и стандартная библиотека, и сторонние библиотеки) — это заголовки с `#include`. Переписать всё разом на полноценные модули невозможно. Нужен **постепенный** путь. C++20 предлагает для этого две промежуточные конструкции: **header units** и подключение легаси-заголовков через **глобальный фрагмент модуля**.

## Header units (заголовочные единицы)

**Header unit** — это обычный заголовочный файл, который компилятор обрабатывает **как модуль**. Вместо текстовой вставки через `#include` его можно подключить через `import`:

```cpp
import <vector>;        // header unit вместо #include <vector>
import <string>;
import "myheader.h";    // свой заголовок как header unit

int main() {
    std::vector<int> v{1, 2, 3};
    return v.size();
}
```

Синтаксически это похоже на импорт модуля, но в угловых скобках или кавычках стоит **имя файла**, а не имя модуля. Это и есть признак header unit: `import <header>` против `import module_name`.

### Что происходит под капотом

Компилятор берёт заголовок, обрабатывает его и создаёт из него бинарный артефакт (по сути, тот же BMI). При `import <vector>;` подключается этот готовый артефакт, а не текст файла. Результат: заголовок парсится **один раз**, а не заново в каждой единице трансляции. Уже одно это ускоряет сборку, даже если вы не написали ни одного собственного модуля.

### Чем header unit отличается от настоящего модуля

Это ключевое различие этапа. Header unit — **не** полноценный именованный модуль, а «модулеподобная обёртка» вокруг старого заголовка. Отсюда принципиальные отличия:

| |Header unit (`import <h>`)|Именованный модуль (`import M`)|
|---|---|---|
|Что импортируется|существующий заголовочный файл|специально написанный модуль|
|Имя|имя файла (`<vector>`)|имя модуля (`graphics`)|
|Видимость имён|**всё**, что в заголовке, видно (как при `#include`)|только помеченное `export`|
|Макросы|**экспортируются!**|не экспортируются|
|Инкапсуляция|нет (наследует «всё наружу» от заголовка)|да (по умолчанию закрыто)|
|Назначение|мост к легаси, миграция|новый код|

Самое важное отличие — **header units экспортируют макросы**. В отличие от настоящих модулей, макросы, определённые в заголовке, при `import <header>;` становятся доступны. Это сделано намеренно: многие заголовки раздают функциональность через макросы, и без этого header units не были бы пригодны как замена `#include`.

```cpp
// config.h
#define MAX_SIZE 100
inline int helper() { return 42; }
```

```cpp
import "config.h";    // header unit

int main() {
    int x = MAX_SIZE;  // РАБОТАЕТ — макрос из header unit доступен
    return helper();   // и обычные имена тоже видны (без всякого export)
}
```

Сравните: будь `config` настоящим модулем, `MAX_SIZE` был бы недоступен, а `helper` пришлось бы пометить `export`. Header unit ведёт себя «как `#include`, но быстрее и аккуратнее».

### Ограничения header units

Не любой заголовок можно превратить в header unit. Он должен быть **importable** (импортируемым). Стандартные библиотечные заголовки гарантированно импортируемы. Свой заголовок обычно тоже годится, но есть требования: он не должен зависеть от макросов, определённых _снаружи_ до его включения (header unit обрабатывается изолированно, он не видит макросы из точки импорта). Заголовки, которые рассчитаны на «настройку макросами перед включением» (классический приём вроде `#define SOME_OPTION` перед `#include`), как header units работать не будут — их оставляют на обычный `#include`.

## Подключение легаси-заголовков внутри модуля

Второй механизм мы уже видели — **глобальный фрагмент модуля**. Когда вы пишете модуль, но вам нужен старый заголовок, который нельзя или не хочется превращать в header unit, его подключают через `#include` в глобальном фрагменте:

```cpp
module;                 // глобальный фрагмент
#include <cstdio>       // легаси-заголовок обычным образом
#include "legacy.h"

export module mymodule;

export void doWork() {
    printf("...");      // используем legacy внутри модуля
}
```

Принципиальный момент: содержимое глобального фрагмента **не экспортируется** и **не утекает** к потребителям модуля. `printf` доступен внутри `mymodule`, но тот, кто сделает `import mymodule;`, его через ваш модуль не получит. Так модуль изолирует «грязный» легаси-мир внутри себя.

### Header unit против `#include` в глобальном фрагменте

Два способа использовать заголовок внутри модуля — когда какой:

`import <header>;` внутри модуля — заголовок обрабатывается как единый разделяемый BMI, быстрее, и его имена видны в вашем модуле. Предпочтительно для импортируемых заголовков.

`#include` в глобальном фрагменте — когда заголовок не импортируем (зависит от внешних макросов, хитро устроен) или когда вам нужны его макросы внутри модуля. Запасной, более «текстовый» путь.

## Стратегия постепенной миграции

Собрав инструменты, выстроим реалистичный план перевода существующего проекта. Миграция идёт «снизу вверх» и по шагам, не ломая сборку.

**Шаг 1. Замените `#include` стандартной библиотеки на header units.** Самый дешёвый выигрыш: меняете `#include <vector>` на `import <vector>;` (или, если доступен C++23, сразу на `import std;`). Код почти не меняется, сборка ускоряется. Это не требует никакой реструктуризации.

**Шаг 2. Оберните стабильные собственные заголовки в header units.** Заголовки, которые редко меняются и хорошо себя ведут (не зависят от внешних макросов), переведите на `import "myheader.h";`. Тоже минимум правок.

**Шаг 3. Начните писать новый код как настоящие модули.** Новые компоненты создавайте сразу модулями. Внутри них старые зависимости подключайте через header units или глобальный фрагмент — новый модуль спокойно сосуществует со старым кодом.

**Шаг 4. Постепенно конвертируйте старые компоненты в модули.** Берёте по одному стабильному, хорошо инкапсулированному компоненту и переписываете его пару `.h`/`.cpp` в интерфейс/реализацию модуля. Начинать лучше с «листьев» дерева зависимостей — у кого меньше всего собственных зависимостей.

**Шаг 5. Двигайтесь вверх по графу зависимостей.** Когда нижние компоненты стали модулями, переходите к тем, что от них зависят. Так фронт миграции постепенно поднимается от базовых утилит к верхним слоям приложения.

Ключевой принцип всей стратегии: **модули и заголовки полностью совместимы и сосуществуют**. Не нужно «большого взрыва» — проект может годами быть гибридным, частично на модулях, частично на заголовках, и это нормально работает.

## Важная оговорка про инструментарий

Честное предупреждение перед практикой: header units на 2025–2026 год поддерживаются компиляторами и системами сборки **неравномерно и местами капризно**. Полноценные именованные модули и `import std;` сейчас получают больше внимания и часто работают надёжнее, чем header units. В частности, в CMake поддержка header units отставала от поддержки обычных модулей. Поэтому на практике многие проекты пропускают шаги 1–2 с header units и сразу идут на `import std;` (C++23) плюс новые именованные модули, оставляя совсем старые заголовки на обычном `#include` в глобальном фрагменте.

## Сводка

|Конструкция|Запись|Роль|
|---|---|---|
|Header unit (библиотечный)|`import <vector>;`|быстрая замена `#include` для импортируемых заголовков|
|Header unit (свой)|`import "myheader.h";`|то же для собственных стабильных заголовков|
|Легаси в глобальном фрагменте|`module;` + `#include`|подключить неимпортируемый заголовок внутри модуля, изолированно|
|Именованный модуль|`import graphics;`|новый код, полноценная инкапсуляция|

Главные отличия header unit от модуля: header unit раскрывает **всё** содержимое заголовка и **экспортирует макросы**, тогда как модуль показывает только `export` и макросы не пропускает.

## Что вы освоили

Вы понимаете, что такое header unit и чем он отличается от настоящего модуля (раскрывает всё, пропускает макросы, служит мостом к легаси). Знаете два способа подключить старый заголовок внутри модуля — `import <header>;` и `#include` в глобальном фрагменте — и когда какой выбрать. И главное — у вас есть пошаговая стратегия миграции «снизу вверх», опирающаяся на сосуществование модулей и заголовков, с реалистичной поправкой на текущее состояние инструментов.

### config.h
```cpp
#define MAX_SIZE 100
inline int get_number() { return 42; }
```

### demo.cpp
```cpp
/*

clang++ -std=c++23 -x c++-system-header --precompile iostream -o iostream.pcm;

if ($?) { clang++ -std=c++23 -x c++-system-header --precompile format -o format.pcm }

if ($?) { clang++ -std=c++23 -x c++-system-header --precompile vector -o vector.pcm }

if ($?) { clang++ -std=c++23 -x c++-header --precompile config.h -o config.pcm }

if ($?) { clang++ -std=c++23 "-fmodule-file=iostream=iostream.pcm" "-fmodule-file=format=format.pcm" "-fmodule-file=vector=vector.pcm" "-fmodule-file=config.h=config.pcm" demo.cpp iostream.pcm format.pcm vector.pcm config.pcm -o app.exe }

*/

import <iostream>;
import <format>;
import <vector>;
import "config.h";

int main() {
    std::vector<int> vec{1, 2, 3};
    std::cout << std::format("vec size {}\n", vec.size());
    std::cout << std::format("MAX_SIZE {}\n", MAX_SIZE);
    std::cout << std::format("numver {}\n", get_number());

    return 0;
}
```
