

CPU и многопоточность - это ядро моего архитекторского опыта. Я проектировал и развивал высоконагруженную многопоточную систему на C++: пул потоков, синхронизация через мьютексы, распределение обработки данных от множества источников между воркерами. 

SIMD - на уровне явного использования интринсиков (SSE/AVX) практического опыта не было; полагался на автовекторизацию компилятора и алгоритмическую оптимизацию а не на ручную векторизацию.

MCU / embedded - здесь у меня более глубокий опыт: STM32/ARM Cortex-M на регистровом уровне - таймеры, DMA, ADC/DAC, прерывания, работа в условиях жёстких ограничений по памяти и реальному времени (терминалы защит электрооборудования, устройство плавного пуска с управлением электродвигателем, блок измерения температур). 

GPU/DSP/NPU - прямого опыта нет.

Для профилирования и диагностики использую связку **iperf + perf + GDB + санитайзеры** - каждый инструмент под свою задачу: iperf для проверки пропускной способности сети как таковой, perf для поиска hotspot'ов на уровне CPU, GDB для точечной отладки логики, санитайзеры (AddressSanitizer) - для проблем с памятью.
Недавний кейс: один из модулей системы начал «терять» сообщения - часть данных просто не доходила до обработки. Первая гипотеза, естественно, была сетевая: пакеты теряются на передаче, проблема в канале или в сетевом стеке. Проверил через iperf - пропускная способность и стабильность канала были в норме.
Дальше запустил perf - искал hotspot, где система могла не успевать обрабатывать входящий поток и поэтому «ронять» сообщения из-за перегрузки. perf показал конкретный горячий участок кода, который и стал точкой входа для дальнейшего разбора.
С этим hotspot'ом пошёл в GDB - точечно прошёл логику вокруг него и обнаружил, что проблема не в производительности отдельного алгоритма, а архитектурная: недостаток был в самой очереди обработки сообщений - при определённых условиях очередь теряла сообщения не из-за нехватки CPU, а из-за некорректной логики самой структуры.

Практический опыт работы с периферийными интерфейсами у меня в основном из embedded-практики - терминалы защит электрооборудования, устройство плавного пуска, блок измерения температур.

- CAN - использовался как основная шина для коммуникации терминалов защит между собой и с системой сбора данных
- I2C/SPI - применялись для взаимодействия с периферией на плате - датчики температуры.
- UART -  стандартная отладочная/сервисная связь с устройствами через Modbus RTU поверх RS-485.
- Ethernet, CSI - практического опыта на уровне bare-metal нет; Ethernet на прикладном уровне (сокеты, TCP/IP) есть из high-load серверной практики.

На предыдущем месте работы мы использовали DSL - объектно-ориентированный язык, реализованный поверх C++, который среди прочего предоставлял механизм критических секций на базе RWLock. В ходе ревью кода мне несколько раз встречался непоследовательный порядок захвата разных экземпляров RWLock в разных потоках выполнения - это могло привести к deadlock-у при высокой нагрузке.

Вопрос:

Насколько уверенно Вы владеете Python для прототипирования гипотез? Какие библиотеки чаще всего используете и как быстро проверяете идеи перед переносом в C++?

Ответ:

Python владею на базовом уровне - использую для скриптов и утилит (автоматизация, обработка данных). Дополнительно проходил курс повышения квалификации от OTUS по Natural Language Processing (NLP), в рамках которого использовал NumPy и PyTorch в учебных целях.

Для быстрой проверки идей перед переносом в C++ обычно иду другим путём: пишу минимальный прототип сразу на C++ (небольшая изолированная функция/модуль без интеграции в основную систему) - это часто быстрее, чем переключаться на Python и потом переписывать. Python использую в основном для разовой обработки данных или визуализации результата.

В тех случаях, когда PoC писался на Python с последующим переносом на C++, скорость реализации зависела в основном от двух факторов: сложности самого алгоритма и от того, насколько «одноразовым» был Python-прототип.
