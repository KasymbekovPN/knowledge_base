# `std::mutex` vs `std::recursive_mutex` vs `std::shared_mutex`

## `std::mutex`

**Что это:** базовый эксклюзивный мьютекс — только один поток может владеть блокировкой в любой момент времени.

**Когда использовать:** это выбор по умолчанию в 95% случаев — защита критической секции, куда попадает только один поток за раз (изменение общего состояния, доступ к не-thread-safe структуре данных).

**Ключевое ограничение:** **нельзя захватывать повторно из того же потока** — попытка повторного `lock()` из потока, который уже владеет мьютексом, приводит к **deadlock** (поток блокирует сам себя) — это undefined behavior по стандарту.

```cpp
std::mutex mtx;
void foo() {
    std::lock_guard<std::mutex> lock(mtx);
    // критическая секция
}
```

---

## `std::recursive_mutex`

**Что это:** тот же эксклюзивный мьютекс, но **допускает повторный захват из того же потока** — внутри ведётся счётчик, сколько раз текущий владелец захватил блокировку; освободить полностью нужно столько же раз (`unlock()`), сколько было `lock()`.

**Когда использовать:** когда функция, уже держащая мьютекс, может **рекурсивно или косвенно вызвать саму себя** (или другую функцию, тоже требующую тот же лок) — например, рекурсивный алгоритм над защищённой структурой, или метод класса, вызывающий другой публичный метод того же класса, который тоже блокирует тот же мьютекс.

```cpp
std::recursive_mutex mtx;
void foo() {
    std::lock_guard<std::recursive_mutex> lock(mtx);
    bar();  // bar() тоже захватывает mtx — без recursive_mutex был бы deadlock
}
void bar() {
    std::lock_guard<std::recursive_mutex> lock(mtx);
    // ...
}
```

**⚠️ Важное предостережение для собеседования:** `recursive_mutex` часто считается **code smell** — его необходимость обычно сигнализирует о проблеме в архитектуре (нечёткое разделение ответственности между методами класса относительно захвата блокировок). Хороший ответ на собеседовании: _«использую как временное решение, но при возможности рефакторю так, чтобы не требовался рекурсивный захват — например, выделяю приватный "не блокирующий" вариант метода, который вызывается изнутри, когда лок уже держится»_.

---

## `std::shared_mutex` (C++17)

**Что это:** мьютекс с **двумя режимами блокировки** — эксклюзивным (writer) и разделяемым (reader): произвольное число потоков может **одновременно** держать shared-блокировку (`lock_shared()`), но эксклюзивная блокировка (`lock()`) требует, чтобы **не было ни одного** другого держателя (ни shared, ни exclusive).

**Когда использовать:** классический паттерн **"readers-writer lock"** — данные читаются **значительно чаще**, чем изменяются, и параллельное чтение безопасно (не искажает результат). Пример: конфигурация, кэш, справочник, который обновляется редко, но читается постоянно из множества потоков.

```cpp
std::shared_mutex mtx;
int data;

int read() {
    std::shared_lock<std::shared_mutex> lock(mtx);  // разделяемая блокировка
    return data;  // одновременно с другими читателями
}

void write(int v) {
    std::unique_lock<std::shared_mutex> lock(mtx);  // эксклюзивная блокировка
    data = v;  // монопольный доступ
}
```

**⚠️ Важное предостережение:** `shared_mutex` **не всегда быстрее** обычного `mutex` — у него более сложная внутренняя реализация (нужно отслеживать количество читателей), поэтому при **малом времени удержания блокировки** или **частой записи** обычный `mutex` может оказаться эффективнее из-за меньших накладных расходов на саму примитивную операцию lock/unlock. Выигрыш `shared_mutex` проявляется именно при **длительном чтении и редкой записи** — например, чтение занимает заметное время (сложная структура данных), и читателей много одновременно.

# Memory Order в `std::atomic` — краткая справка

**Проблема, которую решают memory order.** Современные процессоры и компиляторы агрессивно **переупорядочивают инструкции** для оптимизации (out-of-order execution, кэш-иерархия с задержками распространения между ядрами) — если бы это не контролировалось, изменение переменной в одном потоке могло бы стать видимым другому потоку в "неправильном" порядке относительно других изменений. Memory order — это способ явно указать компилятору и процессору, **какие гарантии видимости и упорядочивания** нужны для конкретной атомарной операции, вместо того чтобы всегда платить за самые строгие (и самые медленные) гарантии.

**`seq_cst` (sequentially consistent) — режим по умолчанию.** Если вы не указываете memory order явно (`counter.fetch_add(1)` без второго аргумента), используется именно `seq_cst` — самая строгая и самая интуитивно понятная модель: **все** потоки видят **все** атомарные операции **в одном и том же глобальном порядке**, как будто существует единая "хронология событий" для всей программы. Это самый безопасный выбор — рассуждать о корректности проще всего, потому что не нужно думать о тонкостях переупорядочивания. Плата — это **самая дорогая** гарантия: на большинстве архитектур требует полных барьеров памяти (memory fence), блокирующих оптимизации процессора в обе стороны.

**`relaxed` — минимальные гарантии.** Даёт только атомарность самой операции (нет "разрывов" при одновременном чтении/записи), но **никак не упорядочивает** её относительно других операций в памяти — компилятор и процессор вольны переставлять соседний код как угодно. Используется, когда нужен **только сам факт атомарности** без синхронизации других данных — классический пример: независимый счётчик статистики/метрик (`stats_counter.fetch_add(1, std::memory_order_relaxed)`), где важно не потерять инкременты при гонке, но совершенно не важно, в каком порядке относительно другого кода это произойдёт.

**`acquire`/`release` — парная синхронизация "точка передачи данных".** Это основной инструмент для классического паттерна "один поток подготовил данные → сигнализирует готовность → другой поток видит и данные, и сигнал корректно упорядоченными":

- **`release`** на операции записи гарантирует, что **все обращения к памяти до неё** (в коде потока-писателя) не переместятся компилятором/процессором **после** неё
- **`acquire`** на операции чтения гарантирует, что **все обращения к памяти после неё** (в коде потока-читателя) не переместятся **до** неё
- Если поток B делает `acquire`-чтение атомарной переменной и видит значение, записанное потоком A через `release`-запись — B гарантированно видит **все** обычные (неатомарные) изменения памяти, которые A сделал **до** своей `release`-записи

Классический пример — флаг готовности данных:

```cpp
std::atomic<bool> ready{false};
int data;

// Поток A (писатель)
data = 42;
ready.store(true, std::memory_order_release);   // всё выше гарантированно "видно" после

// Поток B (читатель)
while (!ready.load(std::memory_order_acquire)) { }  // если true — data точно уже 42
std::cout << data;
```

**Когда ослаблять с `seq_cst` до `acquire`/`release` или `relaxed`.** Практический подход: **начинайте с `seq_cst`** (это по умолчанию, и правильно, что по умолчанию — безопасность важнее производительности до тех пор, пока профилирование не покажет обратное). Ослаблять стоит только когда: (1) профилирование **реально показало**, что синхронизация атомиков — узкое место (hot path с очень частыми атомарными операциями под высокой конкуренцией потоков), и (2) вы можете **формально обосновать**, какая именно гарантия вам нужна — если это просто независимый счётчик без связи с другими данными, `relaxed` безопасен; если это классический паттерн "публикация данных + флаг готовности", `acquire`/`release` достаточно и обычно даёт заметный выигрыш на многоядерных системах по сравнению с `seq_cst`, потому что не требует полного барьера памяти на каждой операции. Преждевременная оптимизация в эту сторону — частый источник крайне тяжело воспроизводимых багов (race conditions, которые проявляются только на определённых архитектурах или под специфической нагрузкой), поэтому это тот случай, где принцип "сначала корректность, потом производительность" стоит соблюдать особенно строго.

# `memory_order_acq_rel`

**Суть.** `acq_rel` — это комбинация **`acquire` + `release` одновременно**, применяемая к **одной и той же операции**. Используется исключительно для **read-modify-write (RMW)** операций — то есть таких, которые одновременно и читают текущее значение, и записывают новое за одну атомарную операцию: `fetch_add`, `fetch_sub`, `exchange`, `compare_exchange_strong/weak` и подобные. Для чистого чтения (`load`) или чистой записи (`store`) `acq_rel` не имеет смысла и не применяется — там существуют только "половинки" (`acquire` для load, `release` для store).

**Что гарантирует.** RMW-операция с `acq_rel` действует одновременно в двух направлениях:

- Как **`acquire`** для своей "read"-части — обращения к памяти **после** этой операции (в коде текущего потока) не могут переместиться **до** неё
- Как **`release`** для своей "write"-части — обращения к памяти **до** этой операции не могут переместиться **после** неё

Иными словами, вокруг этой единственной атомарной операции ставится **двусторонний барьер**: ничего не "просачивается" ни снаружи внутрь, ни изнутри наружу через эту точку — но, в отличие от `seq_cst`, это ограничение действует только относительно **этой конкретной переменной и цепочки её acquire/release-связей**, а не даёт единого глобального порядка для всех атомарных операций во всей программе.

**Типичный пример использования — счётчик с постобработкой на основе результата RMW:**

```cpp
std::atomic<int> ref_count{1};

// Поток, уменьшающий счётчик ссылок (аналог shared_ptr)
if (ref_count.fetch_sub(1, std::memory_order_acq_rel) == 1) {
    // Это был последний владелец — можно безопасно освобождать ресурс.
    // acquire-часть гарантирует, что мы видим все изменения ресурса,
    // сделанные другими потоками до их decrement.
    // release-часть гарантирует, что наши собственные изменения перед
    // этим decrement видны следующему, кто увидит новое значение счётчика.
    delete_resource();
}
```

Это, по сути, упрощённая версия того, как под капотом реализовано управление счётчиком в `shared_ptr` — прямая связь с тем, что мы разбирали ранее про control block и atomic reference counting.

**Когда `acq_rel` недостаточно и нужен именно `seq_cst`.** `acq_rel` синхронизирует **только цепочку операций над одной конкретной атомарной переменной** (release одного потока "видится" с acquire другого именно через эту переменную) — он **не даёт единого тотального порядка** между операциями над **разными** атомарными переменными, если несколько потоков одновременно работают с несколькими независимыми атомиками и от программы требуется, чтобы все потоки согласились на **один и тот же относительный порядок** этих разных операций (классический пример — паттерн Dekker's algorithm / independent reads-independent writes, где `acq_rel` может дать результат, который выглядит нарушающим "здравый смысл" последовательности, а `seq_cst` — нет). Если в коде используется несколько разных атомарных переменных, и логика полагается на "все потоки видят операции над ними в одном общем порядке" — нужен именно `seq_cst`, `acq_rel` для этого не спроектирован.

**Практический вывод для собеседования:** `acq_rel` — разумный, чуть более дешёвый компромисс между `seq_cst` (самый безопасный, но самый дорогой) и раздельными `acquire`/`release` (которые применимы только к load/store по отдельности, не к RMW) — используется именно тогда, когда конкретная RMW-операция должна одновременно "видеть предыдущее" и "публиковать своё", но нет необходимости в глобальном тотальном порядке между несколькими независимыми атомарными переменными сразу.

# `std::future` / `std::promise` / `std::async`: справка

## Общая картина

Пара `promise` + `future` образует **одноразовый канал передачи результата** между потоками. `std::promise` (сторона производителя) кладёт в общее состояние (shared state) значение или исключение. `std::future` (сторона потребителя) забирает его, блокируясь, пока результат не готов. Оба типа **move-only**.

## `std::promise` + `std::future`

```cpp
#include <future>
#include <thread>
#include <iostream>

void worker(std::promise<int> p) {
    try {
        int result = compute();            // может бросить исключение
        p.set_value(result);
    } catch (...) {
        p.set_exception(std::current_exception());
    }
}

int main() {
    std::promise<int> p;
    std::future<int> f = p.get_future();   // получить можно ТОЛЬКО ОДИН раз
    std::thread t(worker, std::move(p));

    std::cout << f.get() << '\n';          // блокируется до set_value/set_exception
    t.join();
}
```

**Что нужно помнить:**

- `get()` можно вызвать **один раз**. После него `valid() == false`, повторный вызов не определён стандартом.
- Если в потоке было `set_exception`, то `get()` **пробросит это исключение** в вызывающий поток. Это главное преимущество перед голым `std::thread`, где необработанное исключение вызывает `std::terminate`.
- `wait()` ждёт без извлечения результата. `wait_for(duration)` и `wait_until(time_point)` возвращают `std::future_status` (`ready` / `timeout` / `deferred`).
- Стандартные `future_error`: `get_future()` дважды бросает `future_already_retrieved`. `set_value()` дважды бросает `promise_already_satisfied`. Если promise уничтожен без значения, `get()` бросит `broken_promise`.
- `set_value` _happens-before_ возврату из `get()`. Дополнительных барьеров для передаваемых данных не нужно.

## `std::async`

Запускает функцию и сразу возвращает `future` с её результатом:

```cpp
auto f1 = std::async(std::launch::async, [] { return heavy(1); });
auto f2 = std::async(std::launch::async, [] { return heavy(2); });
int total = f1.get() + f2.get();           // обе задачи шли параллельно
```

**Политики запуска:**

- `std::launch::async` запускает **в новом потоке** (гарантированно конкурентно).
- `std::launch::deferred` — **ленивый запуск**: функция выполнится в потоке, вызвавшем `get()`/`wait()`, потоков нет вообще.
- Без указания политики (по умолчанию `async | deferred`) реализация **сама выбирает**. Поэтому на собеседовании политику лучше указывать явно.

**Классические подводные камни (любимые вопросы интервьюеров):**

1. **Деструктор future от `async` блокирует до завершения задачи.**

```cpp
std::async(std::launch::async, task1);   // временный future уничтожается сразу и блокирует здесь
std::async(std::launch::async, task2);   // task2 стартует только после task1, всё выполнилось последовательно
```

Возвращаемое значение `async` нужно **сохранять в переменную**.

2. **Ловушка `deferred` при опросе:**

```cpp
while (f.wait_for(10ms) != std::future_status::ready) { }   // бесконечный цикл, если задача deferred
```

`wait_for` на deferred-задаче возвращает `deferred` и не запускает её. Отсюда правило: явно указывайте `launch::async` или проверяйте `future_status::deferred`.

3. **`async` не пул потоков.** Каждый вызов может создать новый поток, отмены задач нет. Для высокой нагрузки это не подходит.

## `std::shared_future` и `std::packaged_task`

```cpp
// shared_future: копируемый, get() можно вызывать многократно, из разных потоков
std::shared_future<int> sf = p.get_future().share();

// packaged_task: оборачивает вызываемый объект и даёт future на его результат
std::packaged_task<int(int, int)> task([](int a, int b) { return a + b; });
auto f = task.get_future();
std::thread t(std::move(task), 2, 3);
t.join();
int r = f.get();                            // 5
```

`packaged_task` полезен, когда нужно **отделить создание задачи от её запуска** (например, положить в очередь пула потоков, а результат получить через future).

## Когда что выбирать

|Инструмент|Когда использовать|
|---|---|
|**`std::async`**|Быстро запустить одну независимую задачу и получить результат/исключение|
|**`std::promise`**|Результат готовится в **произвольном месте кода** (не в одной функции): колбэк, другой поток, несколько этапов|
|**`std::packaged_task`**|Задачу нужно **передать куда-то** (очередь, пул) и запустить позже|
|**`std::thread`**|Нужен полный контроль над потоком, результат не нужен, либо долгоживущий рабочий поток|
|**`condition_variable`**|**Многократные** события/сигналы (future одноразовый)|

## Короткие формулировки для интервью

- **«Чем future отличается от condition_variable?»** Future передаёт **одно значение один раз**, вместе с исключением, и сам управляет синхронизацией. `condition_variable` — примитив для **повторяющихся** уведомлений и требует мьютекса и предиката.
- **«Почему нельзя игнорировать результат `std::async`?»** Деструктор future блокируется до завершения задачи, поэтому «запусти и забудь» превращается в последовательное выполнение.
- **«Что если в задаче исключение?»** Оно сохраняется в shared state и перебрасывается при `get()`.

Если хотите, могу дать короткую задачу для блокнота в том же формате, что и предыдущие: например, «параллельная сумма диапазона через несколько `std::async` с корректной обработкой исключений».

# Сложность операций контейнеров STL

| Операция                                     | `vector`         | `deque` | `list`            | `map`                  | `unordered_map`             |
| -------------------------------------------- | ---------------- | ------- | ----------------- | ---------------------- | --------------------------- |
| Доступ по индексу `[]` / `at`                | O(1)             | O(1)    | O(n), индекса нет | O(log n) по ключу      | O(1) в среднем по ключу     |
| `push_back`                                  | O(1) амортиз.    | O(1)    | O(1)              | —                      | —                           |
| `push_front`                                 | O(n), метода нет | O(1)    | O(1)              | —                      | —                           |
| Вставка / удаление в середине (по итератору) | O(n)             | O(n)    | **O(1)**          | —                      | —                           |
| Поиск значения (`find`)                      | O(n)             | O(n)    | O(n)              | O(log n)               | O(1) в среднем, O(n) худший |
| Вставка / удаление по ключу                  | —                | —       | —                 | O(log n)               | O(1) в среднем, O(n) худший |
| Обход                                        | O(n)             | O(n)    | O(n)              | O(n), в порядке ключей | O(n), порядок не определён  |
| `size()`                                     | O(1)             | O(1)    | O(1) (с C++11)    | O(1)                   | O(1)                        |

## Внутреннее устройство (откуда берутся цифры)

- **`vector`**: непрерывный массив. При нехватке ёмкости выделяется блок примерно вдвое больше и все элементы перемещаются, отсюда «амортизированное» O(1). `reserve(n)` заранее убирает реаллокации.
- **`deque`**: массив блоков фиксированного размера плюс таблица указателей на них. Вставка на обоих концах дешёвая, индексирование чуть медленнее, чем у `vector`, из-за двойной адресации.
- **`list`**: двусвязный список. Вставка и удаление по известному итератору не двигают других элементов, но поиск и доступ линейные, а кэш-локальность плохая.
- **`map`**: красно-чёрное дерево, поэтому O(log n) на всё и **упорядоченность** ключей (`lower_bound`, диапазонные запросы).
- **`unordered_map`**: хэш-таблица с цепочками. Среднее O(1) держится, пока хэши распределены равномерно и коэффициент загрузки не превышен. `rehash` стоит O(n) и запускается автоматически при росте.

## Инвалидация итераторов

| Контейнер       | Что инвалидируется                                                                                                                                  |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `vector`        | `push_back`/`insert`: **все** итераторы и ссылки при реаллокации, иначе только с точки вставки; `erase`: с точки удаления и дальше                  |
| `deque`         | `push_back`/`push_front`: **все итераторы**, но **ссылки и указатели на элементы остаются валидными**; вставка/удаление в середине инвалидирует всё |
| `list`          | Только итераторы на **удалённый** элемент                                                                                                           |
| `map`           | Только итераторы на **удалённый** элемент                                                                                                           |
| `unordered_map` | При `rehash` итераторы инвалидируются, а **ссылки и указатели на элементы остаются валидными**                                                      |

## Практические выводы

1. **`vector` по умолчанию.** Непрерывная память даёт отличную кэш-локальность, и на реальных размерах он обгоняет `list` даже там, где по асимптотике `list` выигрывает.
2. **`list` оправдан редко:** нужны стабильные итераторы и ссылки при частых вставках и удалениях в середине, либо `splice` за O(1).
3. **`map` против `unordered_map`:** нужен порядок или диапазонные запросы, либо важна гарантированная O(log n) в худшем случае, значит `map`. Нужен максимально быстрый поиск по ключу без порядка, значит `unordered_map`.
4. **`erase` в цикле по `vector`** это O(n²). Для массового удаления используйте идиому erase-remove: `v.erase(std::remove_if(v.begin(), v.end(), pred), v.end())` за O(n) (или `std::erase_if` в C++20).
5. **`operator[]` у `map` и `unordered_map` вставляет элемент**, если ключа нет. Для чтения без вставки используйте `find` или `at`.

## Короткая формулировка для интервью

> `vector`: доступ O(1), `push_back` амортизированно O(1), вставка в середину O(n). `deque`: то же плюс O(1) на обоих концах. `list`: O(1) вставка по итератору, доступ и поиск O(n). `map`: всё за O(log n), упорядочен. `unordered_map`: в среднем O(1), в худшем O(n). По умолчанию выбираю `vector` из-за кэш-локальности.

# Инвалидация итераторов: правила по контейнерам

Под **инвалидацией** понимается, что итератор, указатель или ссылка на элемент после операции больше нельзя использовать (UB). Про ссылки и указатели правила часто отличаются от правил для итераторов, и на этом строятся вопросы на интервью.

## `vector`

| Операция                                                                  | Что инвалидируется                                               |
| ------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `push_back` / `emplace_back`, **без реаллокации** (`size() < capacity()`) | Только `end()`. Остальные итераторы, указатели и ссылки валидны  |
| `push_back` / `emplace_back`, **с реаллокацией** (`size() == capacity()`) | **Всё**: итераторы, указатели, ссылки, `end()`                   |
| `insert` / `emplace` в середину, без реаллокации                          | Всё **с точки вставки и правее**, включая `end()`. Левее валидно |
| `insert` / `emplace`, с реаллокацией                                      | Всё                                                              |
| `erase`                                                                   | Всё **с точки удаления и правее**, включая `end()`               |
| `pop_back`                                                                | Только удалённый элемент и `end()`                               |
| `reserve(n)`, если ёмкость выросла                                        | Всё                                                              |
| `shrink_to_fit`, `clear`, `resize` (с ростом)                             | Всё (`clear` оставляет ёмкость, но итераторы недействительны)    |

Ответ на ваш вопрос: `push_back` инвалидирует всё, когда происходит реаллокация, то есть когда до вставки `size() == capacity()`. Иначе инвалидируется только `end()`. Заранее исключить первый случай можно через `reserve(n)`, но только если вы уверены, что `n` хватит.

## `deque`

| Операция                                           | Итераторы                     | Указатели и ссылки на элементы |
| -------------------------------------------------- | ----------------------------- | ------------------------------ |
| `push_back` / `push_front` / `emplace_*` на концах | **Все инвалидируются**        | **Остаются валидными**         |
| `insert` / `erase` в середине                      | Все                           | Все                            |
| `pop_front`                                        | Только удалённого элемента    | Только удалённого              |
| `pop_back`                                         | Удалённого элемента и `end()` | Только удалённого              |

Особенность `deque`: итераторы на нём хрупкие, потому что внутри таблица блоков, а элементы физически не двигаются, поэтому ссылки живут. Это противоположность `vector`, где ссылки и итераторы инвалидируются одновременно.

## `list` и `forward_list`

|Операция|Что инвалидируется|
|---|---|
|Любые вставки (`insert`, `push_*`, `emplace_*`)|**Ничего**|
|`erase`, `pop_*`, `remove`|Только итераторы и ссылки на удалённые элементы|
|`splice`|Итераторы на перемещённые элементы остаются валидными, но теперь относятся к контейнеру-получателю|
|`sort`, `merge`, `reverse`, `unique`|Ничего (перестраиваются связи, элементы не двигаются)|

Это главный аргумент в пользу `list`: стабильность итераторов и ссылок при любых модификациях.

## `map` / `set` / `multimap` / `multiset`

|Операция|Что инвалидируется|
|---|---|
|`insert`, `emplace`, `operator[]`|**Ничего**|
|`erase`|Только итераторы и ссылки на удалённые элементы|
|`extract` (C++17)|Только на извлечённый узел (у самого узла-хэндла ссылки остаются валидными)|

Дерево балансируется перестановкой указателей между узлами, а сами узлы остаются на своих местах в памяти.

## `unordered_map` / `unordered_set`

| Операция                                                                | Итераторы              | Указатели и ссылки на элементы |
| ----------------------------------------------------------------------- | ---------------------- | ------------------------------ |
| Вставка **без rehash**                                                  | Валидны                | Валидны                        |
| Вставка **с rehash** (размер превысил `bucket_count * max_load_factor`) | **Все инвалидируются** | **Остаются валидными**         |
| `rehash`, `reserve`                                                     | Все                    | Валидны                        |
| `erase`                                                                 | Только на удалённые    | Только на удалённые            |

Это симметрично `deque`: ссылки переживают, итераторы нет. Узлы хэш-таблицы аллоцируются отдельно и не двигаются, а вот порядок обхода по бакетам меняется, поэтому итераторы теряют смысл.

## Сводная таблица «переживают ли ссылки на элементы»

| Контейнер            | Реаллокация или перестройка | Ссылки на элементы     |
| -------------------- | --------------------------- | ---------------------- |
| `vector`             | При росте ёмкости           | **Нет**                |
| `deque`              | При `push_*` на концах      | **Да** (итераторы нет) |
| `list`, `map`, `set` | Не бывает                   | **Да**                 |
| `unordered_*`        | При rehash                  | **Да** (итераторы нет) |

## Классические ловушки

**1. Ссылка на элемент вектора, пережившая `push_back`:**

```cpp
std::vector<int> v{1, 2, 3};
int& r = v[0];
v.push_back(4);        // возможна реаллокация
std::cout << r;        // ❌ UB, если случилась реаллокация
```

**2. `erase` в цикле:**

```cpp
for (auto it = v.begin(); it != v.end(); ++it) {
    if (pred(*it)) v.erase(it);          // ❌ it инвалидирован, дальше ++it это UB
}

for (auto it = v.begin(); it != v.end(); ) {
    if (pred(*it)) it = v.erase(it);     // ✅ erase возвращает следующий валидный итератор
    else ++it;
}
```

Для `map`/`set` и `list` `it = c.erase(it)` работает так же. Для массового удаления из `vector` лучше erase-remove идиома (или `std::erase_if` в C++20): O(n) вместо O(n²).

**3. Кэшированный `end()`:**

```cpp
auto e = v.end();
for (auto it = v.begin(); it != e; ++it) {
    v.push_back(*it);      // ❌ e перестаёт быть верным после вставки
}
```

**4. Вставка элемента самого контейнера:** `v.push_back(v[0]);` формально безопасна, стандарт требует, чтобы реализация это выдерживала (аргумент может ссылаться на элемент вектора, реаллокация не должна его «съесть»). На интервью такой пример иногда дают как проверку.

## Короткая формулировка для интервью

> У `vector` `push_back` инвалидирует всё при реаллокации (когда `size == capacity`), иначе только `end()`; вставка и удаление в середине инвалидируют всё правее точки. У `deque` вставка на концах инвалидирует итераторы, но не ссылки. У `list`, `map`, `set` вставка ничего не инвалидирует, а `erase` только удаляемый элемент. У `unordered_*` rehash инвалидирует итераторы, но ссылки на элементы остаются валидными.

# Erase-remove идиома

## Проблема, которую она решает

`std::remove` и `std::remove_if` **не удаляют элементы из контейнера**: алгоритмы работают только с парой итераторов и не знают про сам контейнер, поэтому размер изменить не могут. Они **сдвигают** нужные элементы в начало диапазона и возвращают итератор на новый «логический конец». Хвост после этой границы остаётся в валидном, но неопределённом состоянии. Физически удалить его должен сам контейнер через `erase`.

```cpp
#include <algorithm>
#include <vector>

std::vector<int> v{1, 2, 3, 2, 4, 2, 5};

// удалить все элементы со значением 2
v.erase(std::remove(v.begin(), v.end(), 2), v.end());
// v = {1, 3, 4, 5}

// удалить по условию
v.erase(std::remove_if(v.begin(), v.end(), [](int x) { return x % 2 == 0; }), v.end());
```

## Как это работает по шагам

```
до:          [1, 2, 3, 2, 4, 2, 5]
remove(2):   [1, 3, 4, 5, ?, ?, ?]    ← ? — moved-from значения, использовать нельзя
                         ^
                         it (возвращённый итератор, новый логический конец)
erase(it, end):
после:       [1, 3, 4, 5]
```

`remove` идёт двумя указателями: «читающий» пробегает весь диапазон, «пишущий» копирует (перемещает) в свою позицию только те элементы, которые нужно оставить. Сложность **O(n)** и порядок оставшихся элементов **сохраняется** (алгоритм стабилен). Затем `erase(first, last)` для `vector` просто уменьшает размер, без лишних сдвигов.

## C++20: `std::erase` и `std::erase_if`

Начиная с C++20 идиому можно не писать руками:

```cpp
std::erase(v, 2);                                      // удалить все == 2
std::erase_if(v, [](int x) { return x % 2 == 0; });    // удалить по условию
```

Обе функции возвращают число удалённых элементов. Они определены для стандартных контейнеров, в том числе для `map`, `set` и `list`.

## Ловушки, которые стоит проговорить на собеседовании

**1. Забытый `erase`. Самая частая ошибка.**

```cpp
std::remove(v.begin(), v.end(), 2);   // ❌ размер не изменился, в хвосте мусор
```

Компилятор не предупредит (в новых версиях `remove` помечен `[[nodiscard]]`, и предупреждение появится). Размер `v` останется прежним.

**2. Неверный второй аргумент `erase`.**

```cpp
v.erase(std::remove(v.begin(), v.end(), 2));            // ❌ удалит ТОЛЬКО один элемент, оставшийся хвост останется
v.erase(std::remove(v.begin(), v.end(), 2), v.end());   // ✅ диапазон [новый_конец, end)
```

Перегрузка `erase(iterator)` с одним аргументом удалит один элемент по итератору и оставит остальное.

**3. `remove` на `map`, `set` и `unordered_*` использовать нельзя.**  
У ассоциативных контейнеров ключи константные, `remove` пытается **перезаписывать** элементы, и код не скомпилируется. Для них: цикл с `it = c.erase(it)` или `std::erase_if` (C++20).

```cpp
for (auto it = m.begin(); it != m.end(); ) {
    if (pred(*it)) it = m.erase(it);   // ✅
    else ++it;
}
```

**4. Для `std::list` есть свои методы.** `list::remove(value)` и `list::remove_if(pred)` действительно **удаляют** элементы (это члены-функции, знающие про контейнер) и делают это за O(n) без перемещений, просто перецепляя узлы. Идиома erase-remove для списка не нужна.

**5. Указатели-владельцы.** Если в векторе лежат сырые указатели, `remove` **не освобождает** память, а элементы в хвосте после `remove` становятся неопределёнными, так что удалять по ним поздно. Освобождать надо до `remove`, или пользоваться `unique_ptr` (тогда всё работает корректно, потому что перемещение переносит владение).

**6. Сложность против наивного цикла.** Цикл с `v.erase(it)` для `vector` это **O(n²)**: каждое удаление сдвигает хвост. Erase-remove это **O(n)**.

## Что могут попросить написать от руки

Иногда просят реализовать сам `remove_if`. Это короткая задача на два указателя:

```cpp
template <typename It, typename Pred>
It my_remove_if(It first, It last, Pred pred) {
    It out = first;
    for (It in = first; in != last; ++in) {
        if (!pred(*in)) {
            if (out != in) *out = std::move(*in);
            ++out;
        }
    }
    return out;    // новый логический конец
}
```

Комментарий, который стоит произнести вслух: `out` всегда позади или на одной позиции с `in`, поэтому перезапись безопасна, а порядок оставшихся элементов сохраняется.

## Короткая формулировка для интервью

> `remove`/`remove_if` только переставляют элементы, которые нужно оставить, в начало диапазона и возвращают новый логический конец за O(n), но контейнер не уменьшают. Настоящее удаление делает `erase(new_end, end())`. С C++20 это заменено `std::erase`/`std::erase_if`. Для ассоциативных контейнеров нужен цикл с `it = c.erase(it)`, а у `list` есть собственные `remove`/`remove_if`.

## Что именно просят

Для встроенных типов (`int`, `std::string`) у `std::unordered_map` уже есть готовые `std::hash` и `std::equal_to`. Для своего типа их нужно **предоставить самому**:

|Контейнер|Что нужно от ключа|
|---|---|
|`std::map` / `std::set`|**Компаратор** (строгий слабый порядок): `operator<` или свой функтор|
|`std::unordered_map` / `std::unordered_set`|**Хэш-функция** + **проверка равенства** (`operator==` или свой функтор)|

Слова «компаратор» и «хэшер» в моём плане относились к этим двум разным контейнерам.

## Пример: `unordered_map` с ключом-структурой

```cpp
#include <cstddef>
#include <functional>
#include <unordered_map>
#include <string>

struct Point {
    int x;
    int y;

    bool operator==(const Point& other) const {   // равенство обязательно
        return x == other.x && y == other.y;
    }
};

struct PointHash {
    std::size_t operator()(const Point& p) const noexcept {
        std::size_t h1 = std::hash<int>{}(p.x);
        std::size_t h2 = std::hash<int>{}(p.y);
        return h1 ^ (h2 << 1);                    // простая комбинация, см. замечания ниже
    }
};

int main() {
    std::unordered_map<Point, std::string, PointHash> m;   // третий параметр — хэшер
    m[{1, 2}] = "a";
    m[{3, 4}] = "b";
}
```

`std::unordered_map` принимает шаблонные параметры `<Key, Value, Hash, KeyEqual, Alloc>`. Если `Hash` не указан, берётся `std::hash<Key>`. Если `KeyEqual` не указан, берётся `std::equal_to<Key>`, который вызывает `operator==`.

## Альтернатива: специализация `std::hash`

Тогда третий параметр можно не писать:

```cpp
namespace std {
template <>
struct hash<Point> {
    std::size_t operator()(const Point& p) const noexcept {
        return std::hash<int>{}(p.x) ^ (std::hash<int>{}(p.y) << 1);
    }
};
}

std::unordered_map<Point, std::string> m;   // хэшер подхватится автоматически
```

Специализировать `std::hash` для своих типов разрешено стандартом (это исключение из запрета добавлять что-либо в `std`).

## Аналогичный пример для `std::map`

```cpp
struct PointLess {
    bool operator()(const Point& a, const Point& b) const {
        return std::tie(a.x, a.y) < std::tie(b.x, b.y);   // лексикографический порядок
    }
};

std::map<Point, std::string, PointLess> m;

// или просто определить operator< в самой структуре, тогда третий параметр не нужен
```

## Что проверяют интервьюеры

1. **Согласованность хэша и равенства.** Обязательное правило: если `a == b`, то `hash(a) == hash(b)`. Обратное не требуется (коллизии допустимы). Нарушение приводит к тому, что элемент «пропадает» из контейнера.
2. **Качество комбинирования хэшей.** Вариант `h1 ^ h2` плох: он симметричен (`Point{1,2}` и `Point{2,1}` дадут одинаковый хэш) и обнуляется для равных полей. Обычно используют `hash_combine` в стиле Boost:

```cpp
inline void hash_combine(std::size_t& seed, std::size_t v) {
    seed ^= v + 0x9e3779b97f4a7c15ULL + (seed << 6) + (seed >> 2);
}

struct PointHash {
    std::size_t operator()(const Point& p) const noexcept {
        std::size_t seed = 0;
        hash_combine(seed, std::hash<int>{}(p.x));
        hash_combine(seed, std::hash<int>{}(p.y));
        return seed;
    }
};
```

3. **Константность `operator()`**: хэшер и компаратор вызываются на `const` объекте, значит `operator()` должен быть `const`.
4. **Строгий слабый порядок для компаратора**: для `std::map` нельзя использовать `<=`. Он нарушает иррефлексивность, и последствием бывает UB и зависание.
5. **Не менять ключ после вставки**: изменение полей, участвующих в хэше или сравнении, ломает контейнер.

## Когда действительно просят «реализовать свою хэш-таблицу»

Это отдельная задача (обычно формулируется как «реализуйте `HashMap` с методами `put`/`get`/`erase`»). Её признак в условии: явно сказано «без использования `std::unordered_map`». В нашем случае формулировка «пример `unordered_map` с кастомным hash» означает именно использование стандартного контейнера с вашим хэшером.

## Короткая формулировка для интервью

> Для `unordered_map` с пользовательским ключом нужно предоставить хэш-функцию и сравнение на равенство: либо функтор третьим параметром шаблона, либо специализацию `std::hash` плюс `operator==`. Главное требование: равные ключи должны давать равные хэши. Для `map` вместо этого нужен компаратор со строгим слабым порядком.

# Const-correctness

**Идея:** всё, что не должно меняться, помечается `const`, чтобы компилятор ловил нарушения. Это часть контракта интерфейса: по сигнатуре видно, что метод не меняет объект, а функция не меняет аргумент.

## Правила для методов

**Метод должен быть `const`, если он не меняет наблюдаемое состояние объекта.**

```cpp
class Account {
    int balance_;
public:
    int balance() const { return balance_; }      // ✅ геттер
    void deposit(int x) { balance_ += x; }        // изменяет — не const
};
```

Зачем это нужно: на `const`-объекте (или через `const&`) можно вызывать **только** `const`-методы.

```cpp
void print(const Account& a) {
    a.balance();     // ✅
    a.deposit(1);    // ❌ ошибка компиляции
}
```

Если геттер забыли пометить `const`, его нельзя вызвать через `const&`, и ошибка расползается по всему коду. Пометить `const` нужно всё, что только читает: геттеры, `size()`, `empty()`, `print`, `find` и т.д.

## Правила для параметров

|Случай|Как передавать|
|---|---|
|Читаем, тип **дорогой в копировании** (`std::string`, `vector`, структуры)|`const T&`|
|Читаем, тип **дешёвый** (`int`, `double`, указатель, `string_view`)|по значению `T`|
|Нужно изменить аргумент у вызывающего|`T&`|
|Забираем владение / перемещаем|`T` по значению + `std::move` внутри, или `T&&`|

```cpp
void log(const std::string& msg);   // ✅ не копируем и не меняем
void log(std::string_view msg);     // ✅ ещё лучше для чтения строки
void inc(int& x);                   // меняет аргумент
int  sq(int x);                     // не const int&: копировать int дешевле
```

Ставить `const` у параметра **по значению** в объявлении бессмысленно (`void f(const int x)`: вызывающему всё равно), но в определении можно, чтобы защитить локальную копию от случайного изменения.

## Указатели: где стоит `const`

Читайте справа налево:

```cpp
const int* p;         // указатель на const int: значение менять нельзя, p перепривязывать можно
int* const p;         // const-указатель на int: значение менять можно, p перепривязывать нельзя
const int* const p;   // нельзя ни то, ни другое
```

## Возвращаемые значения

```cpp
const std::string& name() const { return name_; }   // ✅ возврат ссылки на член без копирования и без права менять
std::string name() const { return name_; }           // ✅ копия, безопасно при временных объектах
const int f();                                        // ❌ const у возврата по значению бессмысленен и мешает move
```

## Перегрузка по const

Когда нужен и мутирующий, и читающий доступ, пишут два варианта:

```cpp
T& operator[](size_t i)             { return data_[i]; }
const T& operator[](size_t i) const { return data_[i]; }
```

Так устроены стандартные контейнеры: на `const vector` вернётся `const&`.

## `mutable` и `const` в многопоточности

- **`mutable`** разрешает менять поле внутри `const`-метода. Оправдано для кэша, счётчика обращений и, главное, для **мьютекса**: метод `size() const` обязан захватывать `mtx_`, а `lock()` меняет мьютекс.

```cpp
class Queue {
    mutable std::mutex mtx_;      // нужен, чтобы блокировать внутри const-методов
    std::deque<int> data_;
public:
    size_t size() const {
        std::lock_guard<std::mutex> lk{mtx_};
        return data_.size();
    }
};
```

- **Правило стандартной библиотеки:** `const`-методы должны быть **потокобезопасны** для одновременного вызова из нескольких потоков (при отсутствии записи). Поэтому `mutable`-поле обязано быть защищено (мьютекс, `atomic`), иначе «const» будет обманывать.

## Смысл const бывает двух видов

- **Побитовая (bitwise) const:** метод не меняет ни одного бита объекта. Это то, что проверяет компилятор.
- **Логическая (logical) const:** метод не меняет **наблюдаемое** состояние, но может менять внутренние детали (кэш, мьютекс) через `mutable`. Это то, что имеет в виду хороший интерфейс.

## Частые ловушки

1. **`const`-метод возвращает неконстантный указатель или ссылку на данные, на которые указывает член.** Если член это `T*`, то в `const`-методе `const` действует на сам указатель, но не на `*ptr`. Тогда `const` обманывает: метод формально константен, а изменить данные через него можно.
2. **`const T&` на временный объект живёт до конца полного выражения.** Возвращать ссылку на локальную переменную нельзя вообще, это UB.
3. **Забытый `const` на операторах сравнения и `operator[]`** ломает работу с контейнерами и алгоритмами STL.
4. **`const_cast`** для снятия `const` допустим только если объект **изначально не был создан как const**. Иначе запись это UB. Хорошая практика: на интервью упомянуть, что его использование часто сигнал плохого дизайна.
5. **`const` не заражает вложенные объекты «по глубине»:** `const std::vector<Widget*>` запрещает менять сам вектор, но не сами `Widget`.

## Для интервью: как проговаривать при проектировании API

> Помечаю `const` все методы, которые не меняют наблюдаемое состояние, чтобы их можно было вызывать через `const&`. Тяжёлые параметры на чтение принимаю через `const T&`, дешёвые по значению. Если нужны и чтение, и изменение, делаю две перегрузки по `const`. Мьютекс и кэш помечаю `mutable`, и `const`-методы остаются потокобезопасными.

# Владение объектом в сигнатуре

**Идея:** по типу параметра или возвращаемого значения должно быть однозначно видно, **кто отвечает за уничтожение объекта** и как долго он должен жить. Вместо комментариев «вызывающий должен освободить» используется система типов.

## Что означает каждый тип

|В сигнатуре|Смысл|
|---|---|
|`T&` / `const T&`|**Не владеет.** Объект точно существует (не `null`), живёт дольше вызова|
|`T*` / `const T*`|**Не владеет** (наблюдатель). Может быть `nullptr` («опционально»)|
|`std::unique_ptr<T>`|**Единоличное владение**, передаётся владение целиком|
|`std::shared_ptr<T>`|**Разделяемое владение**, время жизни определяется последним владельцем|
|`std::weak_ptr<T>`|**Не владеет**, но может проверить, жив ли объект|
|`T` (по значению)|Копия или перемещение, владеет собственной копией|

## Как это выглядит в параметрах функций

```cpp
void inspect(const Widget& w);               // только смотрю, не null, не храню
void inspectOpt(const Widget* w);            // смотрю, но объекта может не быть
void modify(Widget& w);                      // меняю объект вызывающего
void take(std::unique_ptr<Widget> w);        // забираю владение целиком
void share(std::shared_ptr<Widget> w);       // становлюсь совладельцем
void observe(std::weak_ptr<Widget> w);       // не продлеваю жизнь
void store(Widget w);                        // храню собственную копию (или перемещённую)
```

Вызывающий код читается сам:

```cpp
take(std::move(ptr));    // явно видно, что владение уходит
inspect(*ptr);           // владение остаётся у ptr
```

## Возвращаемые значения

```cpp
std::unique_ptr<Widget> create();     // фабрика: передаёт владение вызывающему
Widget& get();                        // возвращает ссылку на существующий объект, не владение
Widget* find();                       // может вернуть nullptr, владение остаётся у контейнера
std::shared_ptr<Widget> lookup();     // возвращает совладение, например из кэша
```

## Практические правила выбора

1. **По умолчанию: по ссылке, если функция не хранит объект.** Функция, которая только использует объект на время вызова, не должна знать о том, как он управляется (`unique_ptr`, `shared_ptr` или стек). Передавать `const shared_ptr<T>&` только ради чтения это запах.
2. **`unique_ptr` в аргументе означает «sink»**: функция забирает владение, вызывающий обязан `std::move`. Если владение не нужно, принимаем ссылку или указатель.
3. **`shared_ptr` используется тогда, когда владение действительно разделено** и время жизни определить заранее нельзя. Это самый дорогой вариант (атомарный счётчик, control block), и многие «shared» на деле не нужны.
4. **Сырой указатель допустим только как невладеющий наблюдатель.** Владеющие голые указатели (`new` без обёртки) запрещены современным стилем.
5. **Фабрики возвращают `unique_ptr`**: из него всегда можно сделать `shared_ptr`, а обратно нельзя.
6. **`weak_ptr` разрывает циклы** (родитель ↔ потомок) и позволяет кэшу не продлевать жизнь объектов.

## Пример дизайна: узел дерева

```cpp
class Node {
    std::vector<std::unique_ptr<Node>> children_;   // родитель владеет детьми
    Node* parent_{nullptr};                         // ребёнок не владеет родителем (наблюдатель)
public:
    Node* addChild(std::unique_ptr<Node> c) {       // забираем владение
        c->parent_ = this;
        children_.push_back(std::move(c));
        return children_.back().get();              // возвращаем невладеющий указатель
    }
};
```

По типам видно всю схему: дети принадлежат родителю через `unique_ptr`, обратная связь идёт сырым указателем, потому что родитель гарантированно переживает ребёнка. Никаких циклов и утечек.

## Ловушки

- **`shared_ptr` там, где хватило бы `unique_ptr`:** лишние атомарные операции и неясное время жизни.
- **`unique_ptr` в параметре, когда владение функции не нужно:** заставляет вызывающего отдавать владение зря.
- **Возврат ссылки или указателя на локальную переменную или на элемент контейнера, который может реаллоцироваться** (мы разбирали в инвалидации итераторов).
- **Два `shared_ptr`, созданных из одного сырого указателя:** два независимых control block, двойное удаление. Для этого есть `enable_shared_from_this`.
- **Циклы из `shared_ptr`:** утечка, лечится `weak_ptr`.
- **Передача `this` куда-то как владеющего:** нужно `shared_from_this()`, иначе владение неопределено.

## Короткая формулировка для интервью

> Владение должно читаться по сигнатуре: ссылка означает «использую, не владею, объект есть», сырой указатель — «наблюдаю, возможно `null`», `unique_ptr` — «забираю или отдаю единоличное владение», `shared_ptr` — «разделяю владение». Вход по ссылке или `const&`, если функция не хранит объект; `unique_ptr` для sink и для фабрик; `shared_ptr` только при реально разделяемом времени жизни; `weak_ptr` для обратных связей.

# Гарантии безопасности исключений (exception safety)

**Идея:** если внутри метода вылетело исключение, нужно чётко знать, **в каком состоянии остались объект и ресурсы**. Есть четыре уровня, от слабого к сильному.

## Четыре уровня

| Гарантия                 | Что обещает после исключения                                                                                                |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| **Отсутствие гарантий**  | Утечки, битое состояние, UB. Так писать нельзя                                                                              |
| **Basic**                | Нет утечек, все инварианты сохранены, объект валиден, но **состояние может быть изменено** (неизвестно, какое)              |
| **Strong**               | **Транзакционность**: либо операция выполнена полностью, либо состояние **точно такое же, как до вызова** (commit/rollback) |
| **No-throw** (`nothrow`) | Исключений **не бросает никогда** (помечается `noexcept`)                                                                   |

## Примеры на `vector`

- `push_back` даёт **strong**, если перемещающий конструктор `T` не бросает (`noexcept`), иначе при реаллокации стандартная библиотека использует копирование, чтобы сохранить strong. Это причина, по которой `noexcept` на move-конструкторе важен для производительности.
- `insert` в середину даёт **basic** в общем случае (сдвиг элементов нельзя откатить).
- `pop_back`, `size`, `swap`, деструкторы дают **no-throw**.

## Как получить strong: идиома copy-and-swap

Сначала делаем всю рискованную работу над **копией**, и только в конце «коммитим» через неброском операции:

```cpp
class Buffer {
    std::vector<int> data_;
public:
    void assign(const std::vector<int>& src) {
        std::vector<int> tmp = src;      // может бросить (bad_alloc), состояние this не тронуто
        data_.swap(tmp);                 // noexcept: коммит
    }
};
```

Если исключение случилось при копировании, `data_` остаётся прежним. Это strong. Оператор присваивания через copy-and-swap работает так же:

```cpp
Buffer& operator=(Buffer other) noexcept {   // копия делается при передаче параметра
    swap(other);
    return *this;
}
```

## Как получить basic: RAII

Основа всего: любой ресурс (память, мьютекс, файл) лежит в объекте с деструктором. Тогда при раскрутке стека всё освободится, и утечек нет:

```cpp
void f() {
    auto p = std::make_unique<Widget>();     // ✅ освободится при исключении
    std::lock_guard<std::mutex> lk{mtx};     // ✅ разблокируется при исключении
    mayThrow();
}
```

## Классические нарушения

**1. Сырые ресурсы без RAII:**

```cpp
void f() {
    Widget* w = new Widget;
    mayThrow();          // ❌ утечка w
    delete w;
}
```

**2. Изменение состояния до операции, которая может бросить:**

```cpp
void Account::transfer(Account& to, int x) {
    balance_ -= x;              // изменили
    to.deposit(x);              // бросило исключение: деньги потеряны
}
```

Исправление: сначала выполнить всё, что может бросить, потом менять состояние неброскими операциями (`swap`, присваивание примитивов). Либо использовать откат.

**3. Порядок в `pop`:** в очереди мы делали сначала `T value = std::move(front())`, потом `pop_front()`. Если бы порядок был обратным, исключение при перемещении привело бы к потерянному элементу. Именно поэтому в `std::stack::pop` возвращаемое значение отделено от удаления (`top()` + `pop()`).

**4. Исключение в деструкторе:** деструкторы по умолчанию `noexcept`. Исключение, вылетевшее во время раскрутки стека, вызывает `std::terminate`.

## `noexcept`: что нужно знать

- `noexcept` это **часть контракта**: если функция всё же бросит, вызывается `std::terminate`, и раскрутки стека нет.
- Обязательно `noexcept`: деструкторы (по умолчанию), `swap`, move-конструктор и move-присваивание (иначе `vector` при росте копирует вместо перемещения), функции освобождения памяти.
- Не ставьте `noexcept` на то, что реально может бросить (аллокации, ввод-вывод).
- Оператор `noexcept(expr)` позволяет проверить это в шаблонах: `std::move_if_noexcept` перемещает только если move не бросает.

## Как называть гарантию в ответе

Примеры формулировок для своих методов:

- `Queue::enqueue`: _«Strong при условии, что перемещение `T` не бросает: `push_back` либо вставит элемент, либо не изменит очередь; мьютекс освободится через RAII»._
- `Queue::dequeue`: _«Basic-to-strong: сначала перемещаем `front()` в локальную переменную, и только потом `pop_front()`; если перемещение бросит, элемент остаётся в очереди, а если бросит после перемещения, элемент потерян, поэтому строгая гарантия зависит от `noexcept`-перемещения `T`»._
- `CustomLock`/`lock_guard`: _«No-throw в деструкторе (`unlock` не бросает)»._
- `getInstance()` через `call_once`: _«Strong для инициализации: при исключении флаг остаётся невыполненным, следующий вызов повторит попытку»._

## Практическое правило

Стремитесь к **basic** как минимальному стандарту (RAII везде), а **strong** делайте там, где это дёшево (copy-and-swap, подготовить результат заранее и закоммитить неброскими операциями), и **no-throw** для `swap`, деструкторов и move. Строгая гарантия часто стоит дороже (лишние копии), и в критичных по скорости местах её сознательно заменяют basic.

## Короткая формулировка для интервью

> Различаю четыре уровня: без гарантий (недопустимо), basic (нет утечек, инварианты сохранены, состояние может измениться), strong (транзакционно: либо успех, либо состояние как до вызова) и no-throw (`noexcept`). Basic достигаю через RAII, strong через copy-and-swap: готовлю результат на копии и коммичу неброскими операциями. Move-конструктор и swap всегда помечаю `noexcept`.

# Правило наименьшего удивления (Principle of Least Astonishment)

**Идея:** интерфейс должен вести себя так, как пользователь **ожидает по названию, сигнатуре и общим соглашениям языка**. Если поведение приходится «угадывать» или запоминать как исключение, значит дизайн плохой.

## Где чаще всего нарушают

**1. Имя не соответствует действию.**

```cpp
size_t Container::size() const;     // ✅ ожидание: O(1), не меняет объект
size_t Container::size();           // ❌ вдруг пересчитывает, блокирует, ходит в сеть
bool   Cache::empty();              // ❌ если внутри вычищает протухшие записи, «empty» удивит
```

Правило: запросы (`get`, `size`, `empty`, `find`, `is_*`) не должны менять наблюдаемое состояние. Команды называются глаголами (`clear`, `insert`, `reset`).

**2. Скрытая мутация аргумента.**

```cpp
void print(std::vector<int> v);        // ✅ копия, безопасно
void print(std::vector<int>& v);       // ❌ по неконстантной ссылке: читатель решит, что функция может менять
void print(const std::vector<int>& v); // ✅ намерение видно
```

Если функция меняет аргумент, это видно по `T&`, и стоит отразить в имени (`normalize(v)`, а не `getNormalized(v)`).

**3. Побочные эффекты в геттерах и операторах.**  
`operator[]` у `std::map` **вставляет** элемент при обращении по отсутствующему ключу. Это классический пример нарушения: чтение неожиданно меняет контейнер, в том числе `size()`. Из-за него у `map` есть `at` и `find`, а для `const map` `operator[]` вообще недоступен.

**4. Неявные преобразования.**

```cpp
class Timeout { public: Timeout(int ms); };
void wait(Timeout t);
wait(5);        // ❌ 5 что: миллисекунд, секунд? Неявное конструирование скрывает единицы
```

Исправление: `explicit` на конструкторах с одним аргументом и строгие типы (`std::chrono::milliseconds`). В стандартной библиотеке именно поэтому `explicit` стоит на конструкторах, принимающих размер (`vector(size_t)`).

**5. Неожиданные владение и время жизни.**

```cpp
Widget* create();          // ❌ кто освобождает? неочевидно
std::unique_ptr<Widget> create();  // ✅ владение видно (тема, которую мы разбирали)
```

То же с возвратом ссылок и `string_view` на временные объекты: вызывающий не ожидает, что данные исчезнут.

**6. Скрытая блокировка, ввод-вывод, аллокации.**  
Метод с невинным именем не должен внезапно выполнять сетевой запрос, писать в файл или блокироваться на мьютексе, если это не отражено в имени или документации (`fetch`, `save`, `waitFor`). Особенно опасно в hot-path и в деструкторах.

**7. Асимметрия пар операций.**  
Если есть `open`, то должен быть `close`. Если `lock` блокирует, `try_lock` не блокирует. Если `begin()`/`end()` дают полуинтервал, нельзя на одной перегрузке менять семантику на «включительно».

**8. Несогласованность с соглашениями языка и библиотеки.**  
Если стандартные контейнеры возвращают `bool` от `empty()`, а ваш возвращает счётчик, это удивляет. То же с `operator==`, требующим отдельной семантики, отличной от сравнения значений, и с `operator<<`, который изменяет состояние объекта.

## Проверочные вопросы при проектировании

1. **Можно ли догадаться о поведении по имени и типам?**
2. **Есть ли побочные эффекты, о которых вызывающий не просил?** (кэширование, логирование, ленивая инициализация, мутация)
3. **Понятно ли, кто владеет объектом, кто его освобождает?**
4. **Что произойдёт при неправильном использовании:** тихая порча данных или ошибка компиляции? Предпочитайте ошибку компиляции (`explicit`, `[[nodiscard]]`, `const`, строгие типы).
5. **Согласуется ли API с соседними методами и со стандартной библиотекой?**

## Инструменты C++ для «предсказуемости»

- **`const`**: запрет побочных эффектов, видимый в сигнатуре;
- **`explicit`**: запрет неявных конверсий;
- **`[[nodiscard]]`**: результат нельзя молча игнорировать (`remove`, коды ошибок, `try_lock`);
- **`noexcept`**: явный контракт об исключениях;
- **`= delete`**: явный запрет нежелательных операций (копирование, перегрузки, неверные типы аргументов);
- **`override`/`final`**: чтобы наследование не переопределяло поведение случайно.

## Как это применять на секции

При проектировании класса на интервью полезно проговаривать выбор вслух:

- _«`size()` у меня `const` и O(1), потому что пользователь ожидает именно этого»_
- _«Конструктор принимает `std::chrono::milliseconds`, а не `int`, чтобы не путать единицы»_
- _«Конструктор `explicit`, чтобы не было неявного преобразования из числа в мой тип»_
- _«`enqueue` принимает `T` по значению и перемещает: владение видно по сигнатуре»_

## Короткая формулировка для интервью

> API должно вести себя так, как ожидает пользователь по имени и сигнатуре. Запросы не меняют состояние (`const`), команды называются глаголами, владение видно по типам, неявные конверсии закрыты `explicit`, игнорирование результата ловится `[[nodiscard]]`. Классический контрпример: `std::map::operator[]`, который при чтении вставляет элемент.
