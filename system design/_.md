# System Design: Поисковый рантайм с шардированием и graceful degradation

## Формулировка задачи, которую вероятно дадут

_"Спроектируйте поисковый рантайм, обрабатывающий запросы к индексу объёмом в петабайты, с шардированием данных между узлами, который продолжает отвечать (пусть и с деградацией качества) при потере одного или нескольких шардов."_

Это открытый system-design вопрос без единственного правильного ответа — оценивается не "угадывание" ожидаемой архитектуры, а умение проговорить компромиссы и последовательно раскрыть требования вглубь. Ниже — разбор по темам, которые explicit упомянуты как ожидаемые.

---

## 1. Шардирование — как разбить индекс

### Постановка проблемы

Индекс объёмом в петабайты физически не помещается на один узел — ни по памяти, ни по диску, ни по пропускной способности на чтение при миллионах RPS. Нужно разбить его на **шарды**, каждый из которых обслуживается отдельным набором узлов.

### Два основных способа шардирования для поискового индекса

**Document-based sharding (горизонтальное партиционирование по документам).** Каждый шард хранит **полный** инвертированный индекс, но только для **подмножества** документов (например, документы 0–10M на шарде 1, 10M–20M на шарде 2, и так далее). Запрос отправляется **на все** шарды параллельно (scatter-gather), каждый ищет в своей части документов, координатор сливает top-K результатов с каждого шарда (это прямая связь с **Merge k Sorted Lists**, который разбирали раньше — coordinator получает k отсортированных по релевантности списков и сливает их через heap).

**Term-based sharding (партиционирование по термам).** Каждый шард хранит полный posting-лист **только для части словаря** (например, термы A–M на шарде 1, N–Z на шарде 2). Запрос идёт только на те шарды, где есть нужные термы — потенциально меньше сетевого трафика на простой запрос, но пересечение posting-листов для многословного запроса (AND нескольких термов) может потребовать пересылки больших списков между шардами для вычисления пересечения — это узкое место, которое плохо масштабируется на запросы с популярными термами (posting-лист для частого слова огромен).

**На практике** доминирует document-based sharding (так устроены Elasticsearch, Solr, внутренние системы крупных поисковиков) — он даёт куда более предсказуемую балансировку нагрузки и не создаёт "горячих" шардов из-за перекоса частоты термов.

### Consistent hashing — как распределить документы/шарды по узлам

Наивный `hash(doc_id) % N` (где N — число узлов) ломается при изменении N: при добавлении/удалении узла **почти все** документы должны переехать на новый узел (весь модуль пересчитывается). Это неприемлемо для системы с петабайтами данных — перебалансировка при каждом изменении топологии кластера обойдётся в огромный объём передаваемых данных.

**Consistent hashing** решает это: узлы и ключи (документы/шарды) хэшируются в одно и то же кольцевое пространство (обычно `[0, 2^32)`), документ принадлежит ближайшему по кольцу узлу **по часовой стрелке**. При добавлении/удалении узла перемещается только та часть ключей, что лежала в диапазоне кольца, "принадлежавшем" этому узлу — **не** весь датасет, а в среднем `~1/N` от общего объёма.

Практическое уточнение, которое стоит проговорить: чистый consistent hashing даёт неравномерное распределение при малом числе узлов (кольцо может лечь так, что один узел получит непропорционально много ключей) — решается через **virtual nodes** (каждый физический узел представлен множеством точек на кольце, например 100–200 виртуальных узлов на одну физическую машину), что усредняет распределение нагрузки.

## 2. Репликация — зачем и как

### Зачем

Один шард на одном узле — single point of failure: при падении узла целый кусок индекса становится недоступен, и (в зависимости от стратегии) либо весь запрос падает, либо возвращается частичный результат без этого шарда. Репликация — хранение **копий** каждого шарда на нескольких узлах — даёт отказоустойчивость и, как побочный эффект, увеличивает пропускную способность на чтение (запросы к шарду можно балансировать между его репликами).

### Master-replica vs. multi-master для поискового индекса

Поисковый индекс в подавляющем большинстве систем — **read-heavy** и **almost-immutable** в рамках одного сегмента (документы добавляются батчами, обновления редки относительно чтений). Это делает **primary-replica** схему (один узел — источник истины для записи, реплики только читают и асинхронно подтягивают обновления) значительно проще и достаточной, чем multi-master с разрешением конфликтов записи — потому что конкурентных записей в один и тот же документ почти нет, и сложность multi-master (vector clocks, conflict resolution) здесь не окупается.

### Immutable segments + atomic swap — паттерн, который стоит явно назвать

Здесь прямая связь с тем, что уже обсуждалось в контексте Trie/Autocomplete: реальные поисковые индексы (Lucene-подобные системы) устроены как **набор неизменяемых сегментов**. Обновление индекса не мутирует существующий сегмент — создаётся **новый** сегмент с изменениями, и он атомарно "подключается" к общему view индекса (через смену указателя/манифеста, который перечисляет активные сегменты). Это даёт read-конкурентность без блокировок на чтение (та же lock-free-тема, explicit упомянутая как слабое место) — читатели видят согласованный snapshot сегментов, пока фоновый процесс готовит следующий.

## 3. Кворумы — согласованность чтения/записи при репликации

### Постановка

Если у шарда есть, скажем, 3 реплики, и одна из них временно отстала (не успела применить последнее обновление) — сколько реплик нужно опросить, чтобы быть уверенным в свежести/корректности ответа?

### Формула кворума

При N репликах, W — минимальное число реплик, подтверждающих **запись**, R — минимальное число реплик, опрашиваемых при **чтении**. Если `W + R > N` — гарантируется, что **хотя бы одна** реплика из тех, что участвовали в записи, попадёт в множество опрошенных при чтении (пересечение множеств размера W и R в пуле размера N не может быть пустым, если их сумма превышает N) — это даёт **строгую консистентность чтения после записи** (read-your-writes).

**Применительно к поисковому индексу** строгий кворум на каждый **поисковый запрос** — избыточная и дорогая гарантия: для read-heavy системы с редкими обновлениями и допустимой eventual consistency (документ, добавленный секунду назад, не обязан появиться в результатах поиска мгновенно на 100% реплик) обычно достаточно **R=1** (читаем с любой доступной реплики, ближайшей по latency) при **W = большинство** (majority write) для записи — компромисс в пользу latency чтения за счёт небольшой вероятности прочитать чуть устаревшие данные с отдельной "отстающей" реплики. Это стоит явно проговорить как осознанный trade-off, а не как "давайте сделаем строгую консистентность everywhere", что для поиска почти всегда избыточно.

## 4. Graceful degradation при потере шарда — центральный вопрос формулировки

### Два принципиально разных сценария потери

**Потеря реплики шарда (но не всех реплик).** Решается прозрачно — координатор перенаправляет запросы к оставшимся здоровым репликам того же шарда. С точки зрения клиента ничего не произошло, кроме, возможно, небольшого роста latency (оставшиеся реплики принимают на себя больше нагрузки).

**Потеря всех реплик шарда одновременно** (или временная недоступность всего физического сегмента кластера, например, целого дата-центра) — вот здесь и встаёт вопрос **graceful degradation**, который explicit упомянут в вопросе.

### Стратегии деградации при полной потере шарда

**Partial results с явной пометкой.** Координатор отправляет запрос на все живые шарды, ждёт ответов с **таймаутом**, и если один шард не ответил вовремя (недоступен или слишком медленный) — возвращает результат **без** этого шарда, но с явным флагом в ответе (`"partial": true`, или метаданные вроде "результаты неполны, покрытие: 87% индекса"). Это принципиально лучше, чем два наивных альтернативных подхода: (а) ждать бесконечно, пока шард не восстановится (недопустимая latency), или (б) вернуть полную ошибку всему запросу из-за одного недоступного шарда (недопустимая доступность — один упавший шард из тысячи роняет 100% запросов).

**Timeout budget / deadline propagation.** У запроса есть общий бюджет времени (например, "весь запрос должен уложиться в 200мс"). Координатор передаёт этот дедлайн вниз каждому шарду; если конкретный шард не успевает — его результат просто не учитывается, но остальные шарды, уложившиеся в бюджет, дают полноценный частичный ответ. Это не позволяет одному медленному/упавшему шарду "утащить за собой" latency всего запроса (защита от tail latency amplification — классическая проблема scatter-gather архитектур: чем больше шардов участвует в одном запросе, тем выше вероятность, что **хотя бы один** из них окажется медленным в конкретный момент, и p99 latency всего запроса определяется худшим из участников, а не средним).

**Приоритизация "важных" шардов.** Если шардирование сделано так, что определённые шарды содержат более "ценные" документы (например, свежие или высокотрафиковые), деградация может быть **неравномерной** — при нехватке ресурсов/времени в первую очередь опрашивать шарды с высокоприоритетным контентом, жертвуя менее значимыми.

**Кэширование последнего известного состояния.** Для полностью недоступного шарда — можно вернуть результаты из **кэша** (последний успешный ответ этого шарда на похожий запрос), явно помечая их как потенциально устаревшие — это уместно только для не самых свежих/динамичных данных, и не подходит, если контент шарда часто меняется.

## 5. Trade-off между полнотой ответа и latency — центральная тема, которую нужно уметь формализовать

Это ключевая мысль, которую интервьюер почти наверняка ждёт явно проговорённой, а не просто подразумеваемой: **у поисковой системы нет единственно верного ответа "правильно" ли деградировать** — есть explicit выбор точки на кривой trade-off между:

- **Completeness** (полнота): доля индекса, реально участвовавшая в формировании ответа.
- **Latency**: время, за которое пользователь получил ответ.
- **Availability**: вероятность, что запрос вообще получит хоть какой-то ответ, а не ошибку.

Конкретные решения, которые определяют точку на этой кривой:

- **Короче timeout** → ниже latency, ниже completeness (больше шардов не успеет ответить).
- **Строгий кворум на чтение** → выше consistency/completeness, выше latency (нужно ждать больше реплик).
- **Разрешить partial results** → выше availability (система не падает целиком из-за одного шарда), но требует **явной коммуникации** этого компромисса пользователю/вызывающей системе (иначе partial result молча выдаётся как будто полный — что хуже explicit ошибки в системах, где полнота критична, например, финансовый поиск vs. общий web-search, где неполнота почти незаметна пользователю).

**Хороший ответ на интервью** — не выбрать "единственно верную" стратегию, а явно продемонстрировать понимание, что выбор зависит от **продуктовых требований**: для, например, юридического/финансового поиска (где пропущенный документ может быть критичен) completeness может быть важнее latency — там уместнее строгий кворум и retry с бэкоффом вместо мгновенного partial result; для обычного web-search'а с миллионами RPS — наоборот, скорость ответа обычно важнее гарантированной полноты, и partial results с деградацией — стандартная практика (это то, что реально происходит в крупных поисковых системах при частичных сбоях).

## Как лучше всего представить ответ на интервью — структура рассказа

1. **Уточняющие вопросы** в начале (ожидаемо и приветствуется): какой SLA по latency? Насколько критична полнота ответа (финансовый/юридический поиск vs. общий)? Как часто обновляется индекс (real-time vs. батчевое переиндексирование раз в сутки)?
2. **Верхнеуровневая архитектура**: шардирование (document-based) + репликация (primary-replica с async replication) + coordinator/query router, который делает scatter-gather.
3. **Углубление в конкретный запрошенный сценарий** — потеря шарда: сценарии частичной/полной потери, timeout budget, partial results с явной пометкой.
4. **Явное озвучивание trade-off'ов** — не как одна фраза в конце, а как рамка, в которой принимается каждое архитектурное решение по ходу рассказа.
5. **Готовность к follow-up** — почти наверняка спросят "а как обновляется индекс без даунтайма" (immutable segments + atomic swap), "а как балансировать нагрузку между репликами" (round-robin / least-loaded / latency-aware routing), "а как обнаружить, что шард упал" (health checks, heartbeat, circuit breaker паттерн на стороне coordinator).
