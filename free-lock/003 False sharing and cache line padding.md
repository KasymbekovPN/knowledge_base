
# False sharing и cache line padding — полный разбор

Это прямое продолжение того, что уже разбирали на примере `head`/`tail`, но здесь соберём как отдельную тему целиком — потому что в чек-листе Блока 1 это был отдельный пункт, и на собеседованиях его часто спрашивают в отрыве от конкретной структуры.

## Механизм на уровне кэш-когерентности

Кэш-линия (обычно 64 байта на x86-64 и большинстве ARM) — минимальная единица, которой оперирует протокол когерентности кэшей (MESI/MOESI). Состояния линии:

- **Modified** — линия изменена, есть только у одного ядра, остальные копии невалидны
- **Exclusive** — линия чистая, есть только у одного ядра
- **Shared** — линия есть у нескольких ядер, все read-only
- **Invalid** — копия у этого ядра невалидна

Когда ядро A пишет в переменную внутри линии, находящейся в состоянии Shared у других ядер, протокол обязан разослать invalidate всем остальным держателям этой линии — **целиком**, независимо от того, какой конкретно байт внутри линии изменился.

## Пример на массиве atomics (а не только двух переменных)

Более показательный пример, чем head/tail — массив per-thread счётчиков:

```cpp
constexpr int NUM_THREADS = 4;
std::atomic<long> counters[NUM_THREADS]; // BAD: все в 1-2 кэш-линиях

void worker(int id) {
    for (int i = 0; i < 100'000'000; ++i) {
        counters[id].fetch_add(1, std::memory_order_relaxed);
    }
}
```

`std::atomic<long>` — 8 байт, кэш-линия — 64 байта → **8 счётчиков помещаются в одну линию**. При 4 потоках все они дерутся за 1 (максимум 2 при неудачном выравнивании структуры) кэш-линии, хотя логически каждый поток работает со своей, независимой переменной. На реальном железе такой бенчмарк деградирует в разы (типично 3-10x) по сравнению с паддингом — это не теоретическая, а легко воспроизводимая вещь.

## Решение: явный padding

```cpp
struct alignas(64) PaddedCounter {
    std::atomic<long> value{0};
    // компилятор сам добавит padding до 64 байт из-за alignas,
    // но явный член иногда добавляют для читаемости:
    char padding[64 - sizeof(std::atomic<long>)];
};

PaddedCounter counters[NUM_THREADS]; // GOOD: каждый в своей линии
```

`alignas(64)` гарантирует, что каждый объект `PaddedCounter` начинается на границе, кратной 64 байтам, и (если size тоже кратен 64 — а с explicit padding это так) следующий объект массива начнётся в следующей кэш-линии.

## Портируемая константа вместо magic number 64

C++17 добавил в `<new>`:

```cpp
#include <new>

struct alignas(std::hardware_destructive_interference_size) PaddedCounter {
    std::atomic<long> value{0};
};
```

- **`hardware_destructive_interference_size`** — минимальная рекомендуемая дистанция между двумя объектами, чтобы избежать false sharing (используем для _разведения_ несвязанных данных).
- **`hardware_constructive_interference_size`** — максимальный рекомендуемый размер, чтобы данные гарантированно попали в одну линию (используем, когда наоборот хотим, чтобы связанные данные лежали вместе — "constructive" sharing, когда несколько полей всегда читаются вместе одним потоком).

На большинстве x86-64 обе константы равны 64, но на некоторых платформах (например, у некоторых Apple Silicon декларируется 128 из-за особенностей prefetcher'а) они могут отличаться — поэтому стандартная константа предпочтительнее хардкода.

**Важная деталь:** значение этих констант — `constexpr`, известное на этапе компиляции для конкретного таргета, но реальный размер кэш-линии определяется во время выполнения на конкретном CPU — если бинарник собран под generic x86-64 и запущен на процессоре с нестандартным размером линии, гарантия становится приблизительной. Для абсолютной переносимости в крайних случаях приходится определять размер линии через `/sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size` в рантайме, но на практике 64 байта — settled default для подавляющего большинства production-таргетов.

## Обратная сторона: over-padding

Padding не бесплатен — это прямой рост потребления памяти и **давления на кэш** (cache footprint). Если бездумно паддить каждое поле каждой структуры:

```cpp
struct BadIdea {
    alignas(64) std::atomic<int> a; // 64 байта ради 4-байтного int
    alignas(64) std::atomic<int> b; // ещё 64 байта
    alignas(64) std::atomic<int> c; // ещё 64
};
// 192 байта вместо потенциальных 12 — если a, b, c читаются ВМЕСТЕ
// одним потоком, это ХУЖЕ, а не лучше: больше кэш-промахов на чтение,
// больше TLB-давления
```

**Правило:** паддить нужно только те поля, которые (а) пишутся разными потоками, и (б) конкурируют по частоте записи достаточно, чтобы contention был заметен. Поля, которые всегда читаются одним потоком вместе (даже если это разные потоки в разное время) — паддить не нужно, там наоборот выгодна одна кэш-линия (constructive sharing).

## Как обнаружить false sharing эмпирически (а не гадать)

1. **`perf c2c`** (Linux, `perf c2c record` / `perf c2c report`) — прямо показывает cache-to-cache transfers между ядрами по конкретным адресам, с указанием, какая именно переменная/структура является источником contention. Это самый прямой инструмент, не нужно гадать по коду.
2. **Intel VTune** — "Memory Access" анализ, показывает false sharing hotspots визуально.
3. **Эмпирический A/B бенчмарк**: замерить throughput до/после добавления padding — если разница в разы, это подтверждает false sharing (аккуратно: разница может быть и из-за других эффектов, поэтому `perf c2c` надёжнее как первичный диагноз).

## Связь с темой чата/broadcast из архитектурного блока

Это прямо аукается в дизайне чат-сервера: если у каждого подписчика своя SPSC-очередь (как обсуждали в Блоке 3), и эти очереди лежат в общем массиве подряд — `Queue queues[MAX_SUBSCRIBERS]` — то head/tail индексы соседних очередей будут false-share друг с другом при высокой частоте сообщений, даже если очереди логически независимы. Паддинг каждой `Queue` до размера кэш-линии (или кратного ей) — обязательный пункт в реализации, а не опциональная оптимизация.

## Резюме для собеседования

Ключевая формулировка: _false sharing — это ложная (не по данным, а по физическому расположению) конкуренция за кэш-линию между потоками, которые пишут в логически независимые переменные, лежащие рядом в памяти; решается выравниванием/паддингом до размера кэш-линии (`alignas(std::hardware_destructive_interference_size)`), но избыточный padding вредит cache footprint, поэтому паддить нужно точечно, там где реально показал профайлер (`perf c2c`), а не по умолчанию везде._

## Блок 3 — Архитектура lock-free чат-сервера (1 неделя)

**Ключевые решения для чата конкретно:**

- [ ] **Модель потоков**: thread-per-connection vs event loop (epoll/io_uring) + пул воркеров — lock-free структуры чаще всего нужны именно во второй модели, как shared-state между воркерами
- [ ] **Message queue на клиента**: SPSC от воркера к connection-writer (один producer — логика чата, один consumer — сетевой поток на отправку)
- [ ] **Broadcast**: тут MPSC/MPMC не всегда лучший выбор — часто эффективнее copy-on-write список подписчиков (RCU-style) + каждому подписчику своя SPSC-очередь, чем один общий lock-free broadcast-канал
- [ ] **Backpressure**: что делать, если consumer медленнее producer — bounded queue + drop policy vs unbounded + memory blowup
- [ ] **Reclamation проблема**: если пользователь отключается, когда безопасно освободить его структуры при lock-free доступе (hazard pointers / epoch-based / RCU)

**Практика:** собрать минимальный прототип — N потоков-писателей кладут сообщения в шину, M потоков-читателей (эмулируют коннекты) их разбирают, с метриками latency/throughput под нагрузкой.

**Источники:** статьи про архитектуру Discord/Slack backend (общие принципы, не lock-free специфика, но полезно для контекста), RCU paper (Paul McKenney), доклады про io_uring + lock-free от CppCon/Meeting C++.
