
# IOCP: теория

IOCP (I/O Completion Ports) — механизм Windows, концептуально ближе всего к тому, что мы уже разобрали для io_uring: **completion-based**, а не readiness-based модель. Но у IOCP есть своя, уникальная особенность, которой нет ни у epoll, ни у io_uring — **встроенное управление пулом потоков-обработчиков**. Это стоит разобрать отдельно, потому что именно это исторически было headline-фичей IOCP с момента появления в Windows NT.

## Базовые понятия

**Overlapped I/O** — фундамент, на котором стоит IOCP. Это асинхронный режим вызова `ReadFile`/`WriteFile`/`WSARecv`/`WSASend` и т.п.: вы передаёте структуру `OVERLAPPED`, вызов **не блокируется**, а сразу возвращает управление (обычно с кодом `ERROR_IO_PENDING` — "операция поставлена в очередь"). Реальный результат придёт позже, асинхронно.

**Completion Port** — объект ядра, по сути очередь для "готовых результатов" overlapped-операций. Создаётся один раз:

```cpp
HANDLE iocp = CreateIoCompletionPort(INVALID_HANDLE_VALUE, nullptr, 0, 0);
```

**Ассоциация хендла с портом** — тот же вызов `CreateIoCompletionPort`, но с уже существующим портом и конкретным сокетом/файлом:

```cpp
CreateIoCompletionPort((HANDLE)client_fd, iocp, completion_key, 0);
```

С этого момента **все** асинхронные операции над этим хендлом будут класть свои результаты в очередь именно этого порта. `completion_key` — произвольное значение (обычно указатель на контекст соединения), которое вы получите обратно вместе с каждым результатом — способ узнать "это завершение какого именно объекта".

## Жизненный цикл операции

1. Инициируете операцию: `WSARecv(fd, ..., &overlapped, nullptr)`.
2. Если данные уже готовы — может завершиться синхронно сразу же (в зависимости от флагов, поставленных на хендл).
3. Иначе — `WSA_IO_PENDING`, ядро продолжает работу асинхронно.
4. Когда операция реально завершается (данные пришли, буфер заполнен) — ядро кладёт **completion packet** в очередь порта.
5. Поток, блокированный в `GetQueuedCompletionStatus()`, просыпается и получает: код ошибки, число переданных байт, `completion_key` и указатель на ту же структуру `OVERLAPPED`, что вы передавали на шаге 1.

Тот же intrusive-трюк, что использовали в демке: `OVERLAPPED` — первое поле вашей структуры-контекста, поэтому `reinterpret_cast<IoContext*>(overlapped)` восстанавливает весь контекст обратно — концептуально то же, что `io_uring_sqe_set_data()`/`io_uring_cqe_get_data()`.

## Главное отличие от io_uring — встроенный пул потоков

![[iocp_thread_pool_model.svg|700]]

Concurrency value — встроенный троттлинг потоков

При создании порта можно указать **`NumberOfConcurrentThreads`** — четвёртый параметр `CreateIoCompletionPort`:

```cpp
HANDLE iocp = CreateIoCompletionPort(INVALID_HANDLE_VALUE, nullptr, 0, /* concurrency = */ 4);
```

Это не "максимум потоков, которые могут вызвать `GetQueuedCompletionStatus`" (их может быть сколько угодно, обычно рекомендуют 2×число ядер) — это **максимум одновременно АКТИВНЫХ (runnable) потоков**, которых ядро позволит держать невыпущенными из порта разом. Если поток A блокируется внутри своей обработки (например, зовёт синхронный I/O или другой блокирующий примитив), ядро замечает, что "активных" стало меньше нужного числа, и немедленно выпускает следующий поток из очереди `GetQueuedCompletionStatus` — даже если у вас запущено 16 воркер-потоков, ядро само следит, чтобы одновременно **работало** не больше `concurrency`, что обычно выставляют равным числу физических ядер, чтобы избежать oversubscription и лишних context switch'ей.

Это встроенный, регулируемый ядром аналог того, что в epoll/io_uring вам приходится строить самостоятельно (worker pool + task queue из Блока 3 этого разговора). IOCP по сути объединяет в себе и completion-notification, и load-balancing пула потоков в одном примитиве ОС.

## LIFO wake order — намеренный, не баг

Когда несколько потоков блокированы в `GetQueuedCompletionStatus()` и появляется новый completion packet, Windows будит **последний уснувший** поток (LIFO), а не самый долго ждущий (FIFO, как было бы "честно" в терминах fairness). Логика: этот поток **недавно** выполнялся, его стек и часть его рабочих данных, скорее всего, ещё "тёплые" в кэше процессора — разбудить именно его дешевле (меньше cache misses), чем поток, простаивавший давно. Прямая параллель с тем, что разбирали про cache locality и false sharing — только здесь это решение сознательно встроено в планировщик ОС ради throughput, а не fairness.

## `PostQueuedCompletionStatus` — искусственные completion'ы

Можно вручную положить в очередь порта "поддельный" completion, не связанный ни с каким реальным I/O:

```cpp
PostQueuedCompletionStatus(iocp, 0, SHUTDOWN_KEY, nullptr);
```

Это стандартный способ **корректно остановить** воркер-потоки — без "таймаута на GetQueuedCompletionStatus + проверка флага" (тот приём с 100мс, который мы использовали в демках и для epoll, и для io_uring): просто шлёте по одному "выключающему" completion на каждый воркер, и `GetQueuedCompletionStatus` немедленно возвращает управление с этим сигналом. Это чище, чем polling-таймаут — в реальном коде на IOCP graceful shutdown обычно делают именно так, а не через искусственный таймаут, который я использовал в демке для простоты.

## Сравнение io_uring vs IOCP

|                              | io_uring                                               | IOCP                                                                           |
| ---------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------ |
| Механизм передачи данных     | Общая память (mmap), SQ/CQ кольца                      | Через сам syscall (`WSARecv` и т.п.) + очередь порта                           |
| Нужен ли syscall на submit   | Нет (в режиме SQPOLL)                                  | Да — сам вызов `WSARecv`/`ReadFile` и есть submit                              |
| Управление пулом потоков     | Нет — сами строите worker pool (как в наших демках)    | Встроено — concurrency value + LIFO wake                                       |
| Батчинг разнородных операций | Да — много разных SQE за один `io_uring_enter`         | Нет прямого батчинга на уровне API                                             |
| Граница появления            | Linux 5.1 (2019)                                       | Windows NT 3.51 (1996) — на 23 года раньше                                     |
| Философия                    | "Дай мне общую память, я сам решу, когда сказать ядру" | "Каждая операция — свой явный асинхронный вызов, ядро сама балансирует потоки" |

## Практический вывод

IOCP старше и проще концептуально в одном смысле (нет разделяемых колец, каждая операция — обычный явный вызов с `OVERLAPPED`), но даёт то, чего io_uring не даёт вообще — **готовый, проверенный десятилетиями механизм балансировки нагрузки между потоками**. Если бы мы переносили архитектуру Блока 3 (реактор + worker pool + lock-free шина) на Windows буквально, честный вывод был бы: сам worker pool с MPMC-очередью, который мы строили вручную, во многом **дублирует** то, что IOCP даёт "из коробки" через concurrency value — на Windows идиоматичнее было бы дать каждому воркер-потоку напрямую звать `GetQueuedCompletionStatus` на одном и том же порту, без отдельной lock-free шины между "реактором" и "воркерами", потому что сам IOCP уже и есть эта шина, только с балансировкой потоков внутри ядра.
