
# Разница между atomicity и ordering

Это два независимых свойства, которые легко смешать, потому что `std::atomic` даёт оба сразу — но они решают разные проблемы.

## Atomicity (атомарность)

**Что гарантирует:** операция выполняется целиком, без возможности другому потоку увидеть "промежуточное" состояние. Нет data race на самой операции.

Без атомарности:

```cpp
int counter = 0; // обычный int, НЕ atomic

void increment() {
    counter++; // это НЕ одна операция!
}
```

`counter++` на уровне машинного кода — это как минимум три шага: load, add, store. Если два потока выполняют это одновременно:

```
Поток A: load counter (0)
Поток B: load counter (0)
Поток A: add 1 → 1
Поток B: add 1 → 1
Поток A: store 1
Поток B: store 1
```

Итог: `counter == 1`, хотя инкрементов было два. Это data race — undefined behavior, компилятор вообще не обязан вести себя предсказуемо.

С атомарностью:

```cpp
std::atomic<int> counter{0};

void increment() {
    counter.fetch_add(1, std::memory_order_relaxed); // атомарно
}
```

Даже с `relaxed` — самым слабым memory_order — гонки не будет. `fetch_add` целиком выполняется как одна неделимая операция на уровне процессора (обычно `LOCK XADD` на x86). Оба инкремента гарантированно учтутся, финальное значение будет 2.

**Ключевой момент: atomicity — это защита от гонки на _самой переменной_, и её даёт уже `relaxed`.**

## Ordering (упорядочивание)

**Что гарантирует:** в каком порядке операции — атомарные и обычные — видны _другим_ потокам относительно друг друга. Это не про корректность одной переменной, а про взаимное расположение нескольких операций.

Вернёмся к примеру из предыдущего разбора:

```cpp
std::atomic<int> x{0}, y{0};

// Поток A
x.store(1, std::memory_order_relaxed);
y.store(1, std::memory_order_relaxed);

// Поток B
if (y.load(std::memory_order_relaxed) == 1) {
    assert(x.load(std::memory_order_relaxed) == 1); // МОЖЕТ УПАСТЬ
}
```

Здесь никакой гонки на переменных нет — `x` и `y` оба atomic, каждое отдельное чтение/запись корректно и не UB. Но `relaxed` не гарантирует, что поток B увидит запись в `x` раньше записи в `y`, даже если в потоке A они шли именно в этом порядке. Компилятор и CPU вправе переставить эти две независимые записи местами с точки зрения стороннего наблюдателя — это называется reordering, и relaxed его не запрещает.

**assert может упасть — не потому что данные повреждены, а потому что порядок не гарантирован.**

## Наглядное разделение на одном примере

```cpp
std::string payload;
std::atomic<bool> ready{false};

// Поток-производитель
payload = "hello";                              // (A) обычная запись
ready.store(true, std::memory_order_relaxed);   // (B) atomic-запись

// Поток-потребитель
while (!ready.load(std::memory_order_relaxed)) {} // (C)
std::cout << payload;                             // (D)
```

- **Atomicity** тут ни при чём для (A)/(D) — `payload` вообще не atomic. Проблема, которую нужно решить — чтобы (D) увидело результат (A).
- Флаг `ready` сам по себе атомарен (нет UB на его чтении/записи) даже с `relaxed`.
- Но **ordering недостаточен**: `relaxed` не гарантирует, что (A) видно до того, как (C) увидит `true`. Компилятор может переставить (A) и (B) местами, или CPU может отразить (B) в кэше другого ядра раньше (A). В итоге (D) может напечатать пустую строку — притом что гонки на `ready` как таковой нет.

Именно поэтому нужен `release`/`acquire`:

```cpp
ready.store(true, std::memory_order_release);   // (B'): публикует (A)
while (!ready.load(std::memory_order_acquire)) {} // (C'): получает (A)
```

Теперь ordering тоже гарантирован: (A) happens-before (D).

## Итоговая таблица

|Свойство|Что защищает|Даёт ли `relaxed`|
|---|---|---|
|Atomicity|Целостность самой atomic-переменной (нет UB, нет "порванных" значений)|Да, всегда — это свойство любого atomic-типа независимо от memory_order|
|Ordering|Видимый порядок операций (atomic и обычных) между потоками|Нет — нужен минимум acquire/release|

Практическое следствие: если вам нужен просто корректный счётчик без зависимостей от других данных — `relaxed` полностью достаточен, вы получаете atomicity "бесплатно". Но как только логика опирается на то, что "если поток B увидел X, значит он должен видеть и Y" — это уже вопрос ordering, и `relaxed` тут не поможет, нужен acquire/release или seq_cst.
