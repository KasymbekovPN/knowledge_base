
Модель памяти `std::memory_order_seq_cst` (Sequential Consistency — последовательная согласованность) — это режим работы атомиков по умолчанию.

Она накладывает все ограничения модели `acq_rel` (двусторонние барьеры Acquire-Release), но добавляет к ним важнейшее глобальное свойство: Total Order (Единый глобальный порядок). Все операции `seq_cst` во всех потоках выстраиваются процессором в одну общую, строго последовательную временную линию. Ни одно ядро процессора не может увидеть изменения в другом порядке, отличном от остальных ядер.

## Применяемый пример: Декорации алгоритма Деккера (Взаимное исключение)

Классический пример, где `acq_rel` не справляется и приводит к багам, а `seq_cst` жизненно необходим — это ситуация, когда два потока параллельно выставляют свои собственные флаги присутствия и проверяют флаг соседа.

```cpp
#include <atomic>
#include <thread>
#include <iostream>
#include <cassert>

std::atomic<bool> flag1{false};
std::atomic<bool> flag2{false};
std::atomic<int> critical_counter{0};

void thread1() {
    // 1. Выставляем свой флаг (Запись)
    flag1.store(true, std::memory_order_seq_cst);
    
    // 2. Проверяем флаг соседа (Чтение)
    if (!flag2.load(std::memory_order_seq_cst)) {
        // Мы зашли в критическую секцию
        critical_counter.fetch_add(1, std::memory_order_relaxed);
    }
}

void thread2() {
    // 1. Выставляем свой флаг (Запись)
    flag2.store(true, std::memory_order_seq_cst);
    
    // 2. Проверяем флаг соседа (Чтение)
    if (!flag1.load(std::memory_order_seq_cst)) {
        // Мы зашли в критическую секцию
        critical_counter.fetch_add(1, std::memory_order_relaxed);
    }
}

int main() {
    std::thread t1(thread1);
    std::thread t2(thread2);
    t1.join(); t2.join();
    
    // При seq_cst counter гарантированно будет либо 1, либо 2 (но никогда не 0!)
    std::cout << "Counter: " << critical_counter.load() << "\n";
    return 0;
}
```

## Временная диаграмма для `memory_order_seq_cst`

Если бы в коде выше использовался `acq_rel`, оба потока могли бы одновременно выставить свои флаги, но из-за буферов записи ядер процессора _не успеть увидеть_ флаги друг друга. В итоге оба потока вошли бы в критическую секцию одновременно (`critical_counter` стал бы равен `2`, нарушив взаимное исключение).

`seq_cst` жестко пресекает это поведение на уровне шины процессора.

```text
 Начальное состояние: flag1 = false, flag2 = false (в общей памяти)
 Глобальная ось времени (Total Order), разделяемая всеми ядрами процессора:
 ========================================================================================
 ВРЕМЯ (t)     ПОТОК 1                                    ПОТОК 2
   │
   │ t1        [Запись] flag1 = true (seq_cst)
   │           ⚠️ Процессор КОРРЕКТНО блокирует шину
   │           и жестко сбрасывает буфер записи в кэш.
   │               │
   │               └───► [ flag1 = true становится глобально видно ВСЕМ ядрам ]
   │
   │ t2                                                   [Запись] flag2 = true (seq_cst)
   │                                                      (Видит, что flag1 уже true,
   │                                                      но послушно пишет свой флаг)
   │
   │ t3                                                   [Чтение] flag1 (seq_cst)
   │                                                      ──► Возвращает true!
   │                                                      (Поток 2 видит flag1=true,
   │                                                      условие 'if' провалено,
   │                                                      Поток 2 НЕ заходит в секцию)
   │
   │ t4        [Чтение] flag2 (seq_cst)
   │           ──► Возвращает true!
   │           (Поток 1 видит, что Поток 2 успел взвести флаг)
   ▼
 Итог: Полная согласованность. Ни один поток не зашел в секцию, баг исключен.
```

## Ключевые особенности `seq_cst` на диаграмме:

1. Тотальное упорядочивание:  
    Процессор физически выстраивает транзакции. Событие `t1` (запись `flag1`) гарантированно произошло _до_ события `t2` (запись `flag2`). В модели `acq_rel` такого глобального арбитра нет — там Поток 1 мог думать, что его запись была первой, а Поток 2 в этот же миг думал бы, что первой была его запись.
2. Аппаратная цена (Почему это медленно):  
    Чтобы обеспечить такое поведение на x86-64, компилятор обязан сопровождать любую операцию _записи_ (`store`) инструкцией `mfence` (Memory Fence) или использовать тяжелую атомарную замену `xchg` (как мы видели в вашем Godbolt-выхлопе для `main`). Это заставляет ядро процессора полностью останавливать свой конвейер и ждать, пока данные физически дойдут до общей памяти, парализуя спекулятивное выполнение.

## Сравнение в ассемблере x86-64 для операции `.store()`

Посмотрите, как драматически меняется ассемблер обычной записи в зависимости от модели:

- При `memory_order_release`:
    
    ```assembly
    mov     DWORD PTR flag[rip], edi   ; Простое копирование в память, дешево
    ```
    
- При `memory_order_seq_cst`:
    
    ```assembly
    mov     eax, edi
    xchg    eax, DWORD PTR flag[rip]   ; ⚠️ Встроенный LOCK! Тяжелый сброс буферов CPU
    ```
