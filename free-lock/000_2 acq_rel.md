
Модель памяти `std::memory_order_acq_rel` (Acquire-Release) предназначена исключительно для атомарных операций типа RMW (Read-Modify-Write) — таких как `fetch_add`, `exchange`, или `compare_exchange`.

Она объединяет в себе два барьера:

1. Фаза Чтения (Acquire): Входящий барьер. Все последующие чтения и записи кода не могут подняться выше этой операции. Мы «захватываем» изменения из других потоков.
2. Фаза Записи (Release): Исходящий барьер. Все предыдущие чтения и записи кода не могут опуститься ниже этой операции. Мы «освобождаем» и публикуем свои изменения для других потоков.

## Применяемый пример: Передача эстафеты в циклическом кольце (Ring Buffer / Токен)

Представим три потока, которые по очереди обрабатывают пакет данных. Каждый поток должен атомарно увеличить счетчик этапа (`step`), прочитать данные, оставленные предыдущим потоком, изменить их и передать следующему.

```cpp
#include <atomic>
#include <thread>
#include <iostream>
#include <string>

std::string shared_data = "";
std::atomic<int> stage{0}; // Общий атомарный счетчик этапов

void thread_worker(int my_ticket, const std::string& append_msg) {
    // Крутимся (relaxed), пока не наступит наша очередь
    while (stage.load(std::memory_order_relaxed) != my_ticket) {
        #if defined(__x86_64__) || defined(_M_X64)
        __builtin_ia32_pause();
        #endif
    }

    // --- НАЧАЛО КРИТИЧЕСКОЙ СЕКЦИИ ---
    // Благодаря тому, что предыдущий поток сделал RELEASE, мы гарантированно видим его данные
    shared_data += " -> [" + append_msg + "]";

    // КЛЮЧЕВОЙ МОМЕНТ: атомарно увеличиваем этап на 1.
    // Нам нужен ACQ_REL, потому что fetch_add — это RMW:
    // 1. ACQUIRE-фаза закрывает замок сверху (чтобы чтение shared_data не улетело вверх)
    // 2. RELEASE-фаза проталкивает наши изменения shared_data вниз (для следующего потока)
    stage.fetch_add(1, std::memory_order_acq_rel);
    // --- КОНЕЦ КРИТИЧЕСКОЙ СЕКЦИИ ---
}

int main() {
    std::thread t1(thread_worker, 0, "Поток 1 обработал");
    std::thread t2(thread_worker, 1, "Поток 2 обработал");

    t1.join();
    t2.join();

    std::cout << "Результат:" << shared_data << "\n";
    return 0;
}
```

## Временная диаграмма для `memory_order_acq_rel`

Диаграмма наглядно показывает, как операция `fetch_add` с `acq_rel` зажимает изменения в жесткие тиски-барьеры, обеспечивая безопасную передачу обычных (не атомарных) данных между потоками.

```text
 Переменные: shared_data = "" (обычная память), stage = 0 (атомарная)
 =====================================================================================
 ВРЕМЯ (t)     ПОТОК 1 (Писатель / Читатель)          ПОТОК 2 (Следующий Читатель)
   │
   │ t1        [Запись] shared_data = "Поток 1"
   │                │
   │                ▼ (Все операции СВЕРХУ не могут опуститься ниже фазы Release)
   │ t2        [RMW] stage.fetch_add(1, ACQ_REL)
   │            ├── Фаза Чтения (Acquire) 
   │            └── Фаза Записи (Release) ───┐ 
   │                                         │
   │           ═════════════════════════╪════════ Synchronizes-With ════════════
   │                                         │
   │ t3                                      └─► while (stage.load(ACQUIRE) != 1) 
   │                                              (Выходит из цикла, считывая stage=1)
   │                                                 │
   │                                                 ▼ (Все операции СНИЗУ не могут подняться)
   │ t4                                          [Чтение] shared_data 
   │                                              (Гарантированно видит "Поток 1")
   │                                                 │
   │ t5                                          [Запись] shared_data += " Поток 2"
   │                                                 │
   │                                                 ▼ (Опять зажимаем барьером)
   │ t6                                          [RMW] stage.fetch_add(1, ACQ_REL)
   ▼
```

## Ключевые особенности `acq_rel` на диаграмме:

1. Двухсторонний замок (События t2 и t6):  
    Инструкция `fetch_add` в момент `t2` одновременно работает и как финал для Потока 1 (срабатывает встроенный `release`), и как потенциальная точка старта для тех, кто читал `stage` до него. Она не дает строке `shared_data = "Поток 1"` «провалиться» вниз конвейера.
2. Связующее звено (Synchronizes-With):  
    Как только Поток 2 в момент `t3` считывает значение `1`, сгенерированное фазой записи `acq_rel`, между Потоком 1 и Потоком 2 выстраивается невидимый мост синхронизации памяти. Поток 2 физически не сможет увидеть старое состояние кэша.
3. Почему не `seq_cst`?  
    `acq_rel` работает быстрее, чем по умолчанию (`seq_cst`). На архитектурах со слабой моделью памяти (ARM64) `acq_rel` синхронизирует потоки _только по цепочке зависимости этой конкретной переменной `stage`_. Она не заставляет процессор выстраивать абсолютно все остальные атомарные переменные в программе в один глобальный тотальный порядок, что экономит такты процессора
