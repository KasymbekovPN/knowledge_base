
Здесь принципиально другая идея: вместо того чтобы **заранее** угадывать распределение нагрузки, каждый воркер работает со своей **собственной** очередью задач, а простаивающие воркеры **сами** забирают работу у перегруженных — без центрального роутера вообще.

### Разбор механизма — почему это Chase-Lev deque, а не то, что мы уже строили

Это классическая техника из Cilk, Intel TBB, планировщика горутин в Go. У каждого воркера — **своя** двусторонняя очередь (deque):

- **Владелец** работает со своим концом (`bottom`) в режиме **LIFO** — кладёт новую задачу и сам же первым её забирает. LIFO выбран не случайно: недавно добавленная задача с высокой вероятностью всё ещё "тёплая" в кэше процессора (та же логика, что разбирали для LIFO wake order в IOCP).
- **Вор** (простаивающий воркер) ворует с **противоположного** конца (`top`) в режиме **FIFO** — забирает самые **старые** задачи владельца, которые тот, скорее всего, ещё не скоро бы взял сам.

**Почему нужна именно эта, отдельная структура, а не MPSC/MPMC, которые мы уже строили:**

|                          | MPSC / MPMC (Vyukov)                                | Chase-Lev work-stealing deque                                                                                  |
| ------------------------ | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Кто пишет                | Много producer'ов                                   | **Один** владелец                                                                                              |
| Кто читает               | Много consumer'ов, все с равным приоритетом доступа | Владелец (свой конец) + воры (чужой конец) — **разные концы, разная семантика**                                |
| Порядок                  | FIFO для всех                                       | LIFO для владельца, FIFO для воров — **одновременно, на одной структуре**                                      |
| Основной паттерн доступа | Симметричный push/pop                               | **Асимметричный**: владелец работает почти всегда без contention (свой конец), воры — редкие "набеги" на чужой |

Это принципиально другая структура данных — Chase-Lev deque (названа по авторам статьи 2005 года), не переиспользование MPMC-очереди под новую задачу. Реализация опирается на **тот же набор примитивов**, что мы использовали весь этот разговор — `std::atomic`, `compare_exchange`, тщательный выбор memory_order — но с другим contract: только владелец делает non-atomic (или дёшево-atomic) push/pop на своём конце, воры делают дорогой CAS только когда реально пытаются украсть — то есть contention возникает только в **редком** случае кражи, а не на каждой обычной операции.

### Практический компромисс между двумя подходами

| |Hash + load-aware routing|Work-stealing|
|---|---|---|
|Сложность реализации|Средняя (нужны метрики + политика ребаланса)|Высокая (нужна отдельная lock-free deque-структура на воркер)|
|Гарантия порядка на клиента|Сохраняется всегда (SPSC), если ребаланс синхронизирован аккуратно|**Ломается** без доп. мер — если задачи одного клиента украдены разными ворами, порядок обработки не гарантирован|
|Реакция на всплеск нагрузки|Не мгновенная — ребаланс требует детекции + миграции|Мгновенная — воры сами реагируют, как только освобождаются|
|Где чаще применяется|Message queue брокеры, sharded storage (наш чат-сценарий)|Task schedulers общего назначения (Cilk, TBB, Go runtime, thread pool executors)|

**Ключевой практический вывод для архитектуры чата конкретно**: work-stealing прекрасно подходит для **stateless** задач общего назначения (сериализация, шифрование, любая работа без привязки к конкретному client-state), но плохо сочетается с требованием "сообщения одного клиента должны обрабатываться строго по порядку", потому что кража по определению переносит задачу на **другой** поток — если у клиента украли задачу №5, а задачу №6 обрабатывает исходный владелец параллельно, порядок доставки может нарушиться. Поэтому для broadcast/per-client логики из нашего Блока 3 более естественным выбором остаётся hash-based sharding с load-aware ребалансом, а work-stealing лучше подошёл бы для отдельного pool'а, обрабатывающего **stateless** побочные задачи (например, генерацию превью файлов, отправленных в чат) — там порядок между разными файлами не важен.
