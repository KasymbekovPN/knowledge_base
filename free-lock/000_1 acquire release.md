
Классический сценарий для использования связки `acquire` / `release` — это передача готовых данных (полезной нагрузки) из одного потока в другой через атомарный флаг готовности.

Представьте, что Поток 1 подготавливает тяжелые данные (например, заполняет массив или объект), а Поток 2 ждет, пока эти данные будут готовы, чтобы начать их обрабатывать. Нам нужно гарантировать, что Поток 2 не начнет читать данные до того, как они полностью запишутся, и что процессор не переставит инструкции местами.

## Пример кода на C++

```cpp
#include <atomic>
#include <thread>
#include <iostream>
#include <string>
#include <chrono>

// Неатомарные, обычные данные ("полезная нагрузка")
std::string shared_data = "";

// Атомарный флаг готовности
std::atomic<bool> is_ready{false};

void producer_thread() {
    // 1. Подготавливаем обычные данные
    shared_data = "Важные данные из Потока 1";
    
    // 2. Публикуем флаг готовности с семантикой RELEASE.
    // Это ГАРАНТИРУЕТ, что запись в 'shared_data' физически произойдет ДО 
    // того, как 'is_ready' станет true. Процессор не имеет права переставить 
    // эти строки местами.
    is_ready.store(true, std::memory_order_release);
}

void consumer_thread() {
    // 1. Крутимся в цикле (spin-wait) и ждем флаг с семантикой ACQUIRE.
    while (!is_ready.load(std::memory_order_acquire)) {
        // Просто ждем готовности
        // или std::this-thread::yield();
    }
    
    // 2. Читаем данные.
    // Благодаря ACQUIRE мы на 100% уверены, что этот поток увидит 
    // актуальное значение 'shared_data', записанное в первом потоке.
    std::cout << "Поток 2 прочитал: " << shared_data << "\n";
}

int main() {
    std::thread t2(consumer_thread);
    std::this_thread::sleep_for(std::chrono::milliseconds(100)); // Имитация задержки перед отправкой
    std::thread t1(producer_thread);

    t1.join();
    t2.join();
    return 0;
}
```

## Как это работает на уровне памяти (Временная диаграмма)

Связка `release` и `acquire` создает между потоками так называемое отношение «Synchronizes-With» (Синхронизировано с).

```text
 ПОТОК 1 (Producer)                               ПОТОК 2 (Consumer)
─────────────────────────────────────────────────────────────────────────────────
 [Запись] shared_data = "..." 
        │
        ▼ (Все операции СВЕРХУ не могут уйти вниз)
 [Запись] is_ready.store(true, RELEASE) 
        │
        │ ═══════════ Синхронизация по шине памяти ═══════════╗
        │                                                     ▼
                                            while(!is_ready.load(ACQUIRE)) { ... }
                                                              │
                                            ┌─────────────────┘
                                            ▼ (Все операции СНИЗУ не могут уйти вверх)
                                            [Чтение] Проверяем shared_data
```

## Что произошло бы при использовании `memory_order_relaxed`?

Если бы мы заменили обе модели на `relaxed`, программа получила бы Undefined Behavior (Data Race), и вот почему:

1. Ошибки компилятора/процессора в Потоке 1: Конвейер процессора мог бы решить: _«Ой, запись в `is_ready` и `shared_data` никак не связаны по регистрам, давайте я сначала отправлю в память флаг `is_ready = true`, а строку запишу чуть позже»_.
2. Результат: Поток 2 видит флаг `true`, выходит из цикла, пытается прочитать `shared_data`, а там еще лежит пустая строка или мусор, потому что Поток 1 физически не успел дописать данные.

## Резюме:

- `release` (на запись) — это барьер, который «проталкивает» все предыдущие изменения в памяти вперед и не дает им застрять в локальных буферах ядра.
- `acquire` (на чтение) — это замок, который заставляет ядро процессора обновить свой кэш и гарантирует, что последующие чтения увидят всё, что было «протолкнуто» барьером `release`.

В современном C++ вместо `std::this_thread::yield()` для эффективного ожидания в lock-free структурах используют связку методов **`std::atomic::wait()`** и **`std::atomic::notify_one() / notify_all()`**.

Перенос блокировки на методы `std::atomic::wait()` и `std::atomic::notify_one()`, появившиеся в C++20, превращает наш `Spinlock` в полноценный, ультраэффективный Futex-based Mutex (замок на базе системных фьютексов).

## В чем главная фишка `std::atomic::wait()`?

Вместо того чтобы бесконечно сжигать циклы процессора вхолостую (как чистый `Spinlock`) или постоянно дергать планировщик ОС (как `yield()`), метод `.wait()` работает интеллектуально:

1. Он проверяет значение атомарной переменной.
2. Если оно не изменилось, он блокирует поток на уровне ядра ОС (через системный вызов `futex` в Linux/WSL или `WaitOnAddress` в Windows). Поток засыпает и потребляет 0% ресурсов CPU.
3. Когда другой поток вызывает `.notify_one()`, операционная система мгновенно будит спящий поток.

Поскольку `std::atomic_flag` в C++20 также получил методы `.wait()` и `.notify_*`, мы можем переписать наш класс, сохранив минимальный размер структуры (всего 1 байт).

## Реализация эффективного замка на C++20

```cpp
#include <atomic>
#include <thread>
#include <vector>
#include <iostream>
#include <chrono>

class FutexLock {
private:
    // true означает "занято", false — "свободно"
    std::atomic<bool> is_locked{false}; 

public:
    void lock() noexcept {
        for (;;) {
            // Пытаемся атомарно захватить лок (записать true, если было false)
            // Используем memory_order_acquire для входа в критическую секцию
            if (!is_locked.exchange(true, std::memory_order_acquire)) {
                return; // Успешно захватили!
            }

            // Если лок занят (был true), мы не крутимся в цикле, 
            // а засыпаем до тех пор, пока значение is_locked остается true.
            // Ждем в relaxed-режиме, так как это просто блокирующее ожидание.
            is_locked.wait(true, std::memory_order_relaxed);
        }
    }

    void unlock() noexcept {
        // Освобождаем лок с семантикой release
        is_locked.store(false, std::memory_order_release);

        // Будим ровно один поток, который сейчас заснул внутри метода .wait()
        is_locked.notify_one();
    }
};

// ============================================================
// Тестовый бенчмарк высокой конкуренции (Contention)
// ============================================================
constexpr int NUM_THREADS = 8;
constexpr int ITERATIONS = 1'000'000;
long long global_counter = 0;
FutexLock mutex_cxx20;

void worker() {
    for (int i = 0; i < ITERATIONS; ++i) {
        mutex_cxx20.lock();
        global_counter++; // Критическая секция
        mutex_cxx20.unlock();
    }
}

int main() {
    std::vector<std::thread> threads;
    auto start = std::chrono::steady_clock::now(); // Используем надежный steady_clock!

    for (int i = 0; i < NUM_THREADS; ++i) {
        threads.emplace_back(worker);
    }

    for (auto& t : threads) {
        t.join();
    }

    auto end = std::chrono::steady_clock::now();
    std::chrono::duration<double, std::milli> elapsed = end - start;

    std::cout << "Результат счетчика: " << global_counter << std::endl;
    std::cout << "Время выполнения: " << elapsed.count() << " ms" << std::endl;
    return 0;
}
```

## Как это изменит картину под `perf`?

Если вы скомпилируете этот код (с флагом `-std=c++20`) и запустите сбор профиля внутри вашего контейнера/WSL через `perf record`, результаты кардинально изменятся по сравнению с первой версией:

1. Исчезнет 99% оверхеда внутри функции `worker`: Потоки больше не тратят процессорное время на бесконечные циклы ожидания.
2. Появление системных вызовов ядра (Kernel space): Основной оверхед сместится в сторону функций операционной системы. В отчете `perf report` вы увидите символы, связанные с системными вызовами:
    
    - `[k] futex_wait` или `[k] do_futex` (внутренние механизмы фьютексов ядра Linux/WSL).
    - Процессор тратит время только на засыпание и пробуждение потоков, а не на холостой ход.
    

## Что выбрать на практике?

- Чистый `Spinlock` с `pause`: Идеален, если критическая секция экстремально короткая (буквально 1-5 инструкций процессора), а конкуренция между потоками низкая. В этом случае поток успевает захватить замок до того, как `pause` сделает много итераций, избегая дорогих системных вызовов.
- `std::atomic::wait()` (C++20): Идеальный индустриальный стандарт для общего случая. Если замок освобождается быстро — он работает со скоростью спинлока прямо в user-space. Если замок заблокирован надолго — он плавно переводит поток в спящий режим, не перегревая процессор.

## 1. Как изменится производительность, если использовать `std::mutex`?

Если заменить наш `FutexLock` на стандартный `std::mutex`, производительность в данном конкретном бенчмарке останется примерно такой же или незначительно вырастет.

Почему так происходит?

- Общая механика под капотом: В современных реализациях C++ (включая GCC/Clang на Linux и MSVC на Windows через WSL) `std::mutex` устроен как гибридный замок. При вызове `lock()` он не усыпляет поток мгновенно. Сначала он делает короткую серию попыток захватить замок вхолостую (атомарный spin-wait в user-space). Если замок освобождается быстро, поток заходит в него без системных вызовов. И только если замок стабильно занят, `std::mutex` делает системный вызов `futex` и отправляет поток спать.
- Преимущество `std::mutex`: Стандартный мьютекс пишется авторами компиляторов и операционных систем под конкретное железо. Внутри него зашиты адаптивные алгоритмы (например, экспоненциальный back-off: поток крутится в цикле чуть дольше или меньше в зависимости от количества ядер процессора). Наш кастомный `FutexLock` засыпает на первой же неудачной итерации, что при жесткой конкуренции (8 потоков на 1 миллион итераций) генерирует чуть больше тяжелых системных вызовов пробуждения, чем оптимизированный `std::mutex`.

## 2. Приведенный выше код — блокирующий или lock-free?

Код `FutexLock` на базе `std::atomic::wait()` является 100% блокирующим (Blocking). Он НЕ является lock-free.

Давайте разберем, почему наличие `std::atomic` внутри класса часто вводит в заблуждение, и в чем их принципиальная разница:

- Почему он блокирующий?  
    В определении `lock-free` алгоритмов заложено главное правило: _хотя бы один поток в системе гарантированно совершает полезный прогресс за конечное число шагов_.  
    В нашем коде, если Поток 1 захватил лок и внутри критической секции операционная система решила его приостановить (сделать preemption), все остальные 7 потоков полностью остановятся. Они вызовут метод `.wait()` и уснут на неопределенный срок, пока Поток 1 не проснется и не вызовет `unlock()`. Система в этот момент не совершает никакого прогресса. Это классическое поведение блокирующей синхронизации.
- Зачем там `std::atomic`?  
    Атомарные операции здесь используются не для создания безблокировочного алгоритма, а как инструмент низкоуровневой сборки самого блокирующего замка. С помощью атомарного `.exchange()` мы безопасно проверяем состояние флага, а с помощью `.wait()` и `.notify_one()` командуем операционной системе усыпить или разбудить поток.

## В чем разница нагляднее:

1. Lock-Free алгоритм (например, стек Трайбера из начала нашего диалога): Потоки вообще не имеют методов `lock()` и `unlock()`. Они в бесконечном цикле `compare_exchange` пытаются пропихнуть свою операцию. Если один поток завис, другие продолжают успешно добавлять элементы в стек.
2. Блокирующий алгоритм (`std::mutex`, `Spinlock`, `FutexLock`): Есть явная критическая секция. Пока один поток внутри, остальные курят бамбук (либо сжигая CPU в спинлоке, либо засыпая в фьютексе).
