
# ABA problem и способы борьбы

## Суть проблемы

CAS (`compare_exchange`) проверяет только _значение_, а не _историю_ этого значения. Если переменная была `A`, потом стала `B`, потом снова стала `A` — CAS увидит "ничего не изменилось" и успешно выполнится, хотя между двумя моментами произошли важные события.

## Классический сценарий на Treiber stack

Возьмём стек из прошлого разбора: `Head → A → B → C`.

```
Поток 1 (pop): читает head = A, видит A->next = B,
               готовится сделать CAS(head: A → B)
               ...но ПРЕРЫВАЕТСЯ ОС прямо перед CAS...

Поток 2: успевает выполнить:
    pop() → снимает A (head = B)
    pop() → снимает B (head = C)
    delete A                          // память A освобождена!
    push(D) → аллокатор переиспользует адрес A для D
              (head = D, D->next = C)

Поток 1: возобновляется, выполняет CAS(head: A → B)
    head СЕЙЧАС равен D, но по адресу это тот же указатель "A"!
    Если аллокатор вернул точно тот же адрес — CAS видит
    "head == A" (потому что D физически лежит по адресу A) → УСПЕХ

Результат: head = B, но B уже был удалён потоком 2!
Use-after-free / повреждение стека.
```

Проблема именно в том, что указатель "A" _технически_ тот же битовый паттерн, но семантически — это уже другой объект.

## Способ 1: Tagged pointers (counted pointers)

**Идея:** приклеить к указателю монотонно растущий счётчик (tag/generation), и сравнивать CAS не по указателю, а по паре (pointer, tag). Даже если адрес переиспользован, tag будет другим.

```cpp
struct TaggedPtr {
    Node* ptr;
    uint64_t tag;
};

// Обычно упаковывается в один атомарный 128-бит блок
// (нужен double-width CAS: cmpxchg16b на x86-64)
std::atomic<TaggedPtr> head; // требует alignas и лежит в границах,
                              // где поддерживается 128-бит CAS

void push(Node* new_node) {
    TaggedPtr old_head = head.load(std::memory_order_relaxed);
    TaggedPtr new_head;
    do {
        new_node->next = old_head.ptr;
        new_head = {new_node, old_head.tag + 1}; // инкремент tag!
    } while (!head.compare_exchange_weak(
                 old_head, new_head,
                 std::memory_order_acq_rel,
                 std::memory_order_relaxed));
}
```

Теперь в сценарии выше: когда поток 1 возобновится, `head.tag` уже увеличился (после операций потока 2), поэтому CAS(old_head с устаревшим tag) провалится — ABA обнаружена.

**Ограничения:**

- Нужен double-width CAS (128 бит на 64-битной архитектуре) — не везде эффективно поддерживается, и не все архитектуры это позволяют (x86-64 — да через `cmpxchg16b`, ARM — через `casp` начиная с ARMv8.1).
- Tag может переполниться и "обернуться" (wraparound) — теоретическая, но не нулевая вероятность коллизии при очень долгой работе.
- Не решает проблему **когда** можно безопасно освободить память — только защищает сам CAS. Проблема use-after-free при доступе к `old_head.ptr->next` до CAS остаётся, если память уже переиспользована для объекта другого типа/размера.

## Способ 2: Hazard Pointers

**Идея:** прежде чем поток разыменовывает указатель на shared-узел, он "объявляет" этот указатель в глобальном списке hazard pointers. Поток, который хочет освободить память, обязан сначала проверить, не числится ли адрес в чьём-то hazard-списке — если числится, освобождение откладывается.

```cpp
// Упрощённая схема (реальная реализация сложнее, но идея такая)
thread_local std::atomic<Node*> hazard_ptr{nullptr};
std::vector<std::atomic<Node*>*> all_hazard_ptrs; // список всех потоков

bool pop(T& result) {
    Node* old_head;
    do {
        old_head = head.load(std::memory_order_acquire);
        hazard_ptr.store(old_head, std::memory_order_release); // (*) объявляем
        // Перепроверяем: head мог измениться, пока мы объявляли hazard
        if (head.load(std::memory_order_acquire) != old_head) {
            continue; // старое значение уже не актуально, повторяем
        }
    } while (!head.compare_exchange_weak(
                 old_head, old_head->next,
                 std::memory_order_acq_rel, std::memory_order_acquire));

    result = std::move(old_head->data);
    hazard_ptr.store(nullptr, std::memory_order_release);

    retire_node(old_head); // не delete сразу! откладываем
    return true;
}

void retire_node(Node* node) {
    retired_list.push_back(node);
    // Периодически: сканируем retired_list, и для каждого узла
    // проверяем all_hazard_ptrs — если ни один поток не держит
    // этот указатель как hazard, можно delete
    scan_and_reclaim();
}
```

**Плюсы:**

- Не требует double-width CAS, работает с обычным указателем.
- Даёт точную, детерминированную безопасность — узел не освобождается, пока хоть один поток на него ссылается.

**Минусы:**

- Оверхед на каждую операцию: атомарная запись hazard pointer + перепроверка + периодическое сканирование списка retired-узлов (обычно O(количество потоков) на каждый reclaim-проход).
- Усложняет код — нужна отдельная инфраструктура (глобальный реестр hazard pointers per-thread).
- Не тривиально расширяется на структуры с несколькими указателями за операцию (например, очереди с head+tail).

## Способ 3: Epoch-based reclamation (EBR)

**Идея:** вместо отслеживания конкретных указателей — отслеживать "эпохи". Каждый поток при входе в критическую секцию (доступ к shared-структуре) объявляет текущую глобальную эпоху. Память, помеченная на удаление в эпохе N, может быть реально освобождена только когда _все_ активные потоки продвинулись за эпоху N (то есть точно не держат указателей из старой эпохи).

```cpp
std::atomic<uint64_t> global_epoch{0};
thread_local std::atomic<uint64_t> local_epoch{0};
thread_local bool in_critical_section = false;

struct EpochGuard {
    EpochGuard() {
        local_epoch.store(global_epoch.load(std::memory_order_acquire),
                           std::memory_order_release);
        in_critical_section = true;
    }
    ~EpochGuard() {
        in_critical_section = false;
    }
};

bool pop(T& result) {
    EpochGuard guard; // объявляем: "я сейчас в текущей эпохе"

    Node* old_head = head.load(std::memory_order_acquire);
    while (old_head && !head.compare_exchange_weak(
               old_head, old_head->next,
               std::memory_order_acq_rel, std::memory_order_acquire)) {}

    if (!old_head) return false;
    result = std::move(old_head->data);

    retire(old_head, global_epoch.load(std::memory_order_relaxed));
    return true;
}

// Периодически (например, раз в N операций):
void try_advance_epoch_and_reclaim() {
    uint64_t min_active_epoch = /* минимум по всем local_epoch активных потоков */;
    // Всё, что retire'нуто в эпохе < min_active_epoch, безопасно удалить
    reclaim_older_than(min_active_epoch);
    global_epoch.fetch_add(1, std::memory_order_acq_rel);
}
```

**Плюсы:**

- Обычно быстрее hazard pointers "в среднем" — нет необходимости отслеживать каждый конкретный указатель, только счётчик эпохи (одна атомарная запись на вход в критическую секцию).
- Проще реализовать корректно для сложных структур с несколькими указателями (RCU в Linux kernel построен на похожей идее).

**Минусы:**

- **Не гарантирует bounded memory** в худшем случае: если один поток "завис" в критической секции (например, засыпал/был вытеснен планировщиком) надолго, эпоха не может продвинуться, и retired-узлы копятся неограниченно — в отличие от hazard pointers, где память освобождается сразу, как только конкретный поток перестал держать указатель.
- Задержка освобождения памяти обычно выше, чем у hazard pointers (реclaim идёт "пачками" по эпохам, а не по факту освобождения конкретного указателя).

## Сравнительная таблица

|Метод|Оверхед на операцию|Bounded memory|Сложность реализации|Где используется|
|---|---|---|---|---|
|Tagged pointers|Минимальный (нужен 128-бит CAS)|Да (для самого CAS), но не решает reclaim в общем случае|Низкая, но зависит от HW-поддержки double-CAS|Простые lock-free стеки/списки на x86-64|
|Hazard Pointers|Средний (atomic store + scan)|Да, строго|Средняя-высокая|folly::AtomicHazardPointers, libcds|
|Epoch-based (EBR)|Низкий (обычно)|Нет (в худшем случае unbounded)|Средняя|RCU в Linux kernel, crossbeam-epoch (Rust!)|

Раз ты также смотришь в сторону Rust — там `crossbeam-epoch` реализует EBR "из коробки" и это один из самых прямых мостиков между C++ lock-free опытом и идиоматичным Rust: концепции идентичны, просто типобезопасность API немного другая (`Guard`, `Atomic<T>`, `Shared<'g, T>`).

**Практический вывод для собеседований:** если спрашивают "как решить ABA" — базовый ответ tagged pointers достаточен для junior/middle уровня, но для senior обычно ожидают понимания trade-off между hazard pointers (точный, но дороже) и epoch-based (дешевле, но unbounded memory в худшем случае), плюс упоминание, что в C++20 `std::atomic<std::shared_ptr<T>>` частично решает эту проблему через reference counting — ценой atomic refcount на каждый доступ (медленнее, чем raw pointer + hazard pointers, но сильно проще в коде).

# `std::atomic<std::shared_ptr<T>>` (C++20) как решение проблемы ABA/reclamation

## Что это и зачем появилось

До C++20 атомарные операции над `std::shared_ptr` делались через свободные функции — `std::atomic_load(&sp)`, `std::atomic_store(&sp, new_sp)`, `std::atomic_compare_exchange_weak(&sp, ...)` — которые были легко использовать неправильно (ничто не мешало кому-то забыть их и работать с `shared_ptr` напрямую, получив гонку). C++20 сделал это специализацией `std::atomic<std::shared_ptr<T>>`, аналогично `std::atomic<int>` — единый типобезопасный интерфейс.

**Ключевая идея:** `shared_ptr` уже решает проблему "когда безопасно освободить объект" через reference counting. Если сделать _саму операцию инкремента/декремента счётчика и подмену указателя_ атомарной, то ABA problem и use-after-free исчезают почти автоматически — потому что пока хоть один поток держит `shared_ptr` (то есть инкрементировал refcount), объект просто не будет удалён, вне зависимости от того, что происходит с "головой" структуры.

## Применение к Treiber stack

Возвращаемся к стеку из предыдущих разборов — теперь без tagged pointers и без ручных hazard pointers:

```cpp
#include <memory>
#include <atomic>

template<typename T>
class TreiberStack {
    struct Node {
        T data;
        std::shared_ptr<Node> next;
        Node(T val) : data(std::move(val)) {}
    };

    std::atomic<std::shared_ptr<Node>> head;

public:
    void push(T value) {
        auto new_node = std::make_shared<Node>(std::move(value));
        new_node->next = head.load(std::memory_order_relaxed);

        // compare_exchange для atomic<shared_ptr> сравнивает
        // сами указатели (control block identity), не содержимое
        while (!head.compare_exchange_weak(
                   new_node->next, new_node,
                   std::memory_order_acq_rel,
                   std::memory_order_relaxed)) {
            // new_node->next обновлён автоматически до актуального head
        }
    }

    bool pop(T& result) {
        std::shared_ptr<Node> old_head = head.load(std::memory_order_acquire);

        while (old_head &&
               !head.compare_exchange_weak(
                   old_head, old_head->next,
                   std::memory_order_acq_rel,
                   std::memory_order_acquire)) {
            // old_head автоматически обновлён до нового head при неудаче
        }

        if (!old_head) return false;

        result = std::move(old_head->data);
        return true;
        // old_head выходит из scope — refcount уменьшается,
        // если это была последняя ссылка, Node уничтожается ЗДЕСЬ,
        // безопасно, никакого use-after-free
    }
};
```

**Что изменилось по сравнению с raw-pointer версией:**

- Никакого `delete old_head` вручную и никакого ABA на уровне указателя — даже если бы адрес переиспользовался, `shared_ptr` в `compare_exchange` сравнивается вместе со своим control block/identity через атомарный механизм, а не голым битовым паттерном адреса.
- Пока другой поток держит копию `old_head` (например, застрял в цикле CAS выше), refcount не даст объект удалить — это ровно та же гарантия, что даёт hazard pointer, но получена "бесплатно" через существующий механизм shared_ptr.

## Как это реализовано под капотом (важно для понимания цены)

`std::atomic<std::shared_ptr<T>>` — это НЕ волшебство поверх одного machine word. Проблема в том, что `shared_ptr` — это на самом деле **два указателя** (control block + object pointer), а атомарный CAS в железе умеет работать максимум с двумя словами (double-width CAS, `cmpxchg16b` на x86-64). Стандарт не гарантирует lock-free реализацию этой специализации — нужно проверять в рантайме:

```cpp
std::atomic<std::shared_ptr<int>> ap;
std::cout << ap.is_lock_free(); // может быть false!
```

Если `is_lock_free() == false`, реализация под капотом использует **внутренний мьютекс/спинлок** (часто — таблица спинлоков, захешированная по адресу control block'а, как в libstdc++/libc++). То есть вы получаете API атомика, но по факту это может быть просто lock-based операция, спрятанная за интерфейсом — то есть это **не всегда честный lock-free примитив**.

На практике: libstdc++ (GCC) и libc++ (Clang) на большинстве x86-64 платформ реализуют это через spinlock table, а не через настоящий hardware double-CAS, потому что control block содержит два независимых атомарных счётчика (strong+weak refs) плюс сам указатель — уместить всё это в одну lock-free CAS-операцию сложнее, чем кажется.

## Стоимость по сравнению с hazard pointers / EBR

|Критерий|`atomic<shared_ptr<T>>`|Hazard Pointers|Epoch-based (EBR)|
|---|---|---|---|
|Простота кода|Максимальная — почти как обычный код|Средняя-низкая, много инфраструктуры|Средняя|
|Реально lock-free?|Часто **нет** (spinlock внутри)|Да|Да|
|Стоимость на операцию|Atomic refcount inc/dec на КАЖДЫЙ доступ (не только на push/pop)|Atomic store hazard + периодический scan|Atomic epoch read при входе в критическую секцию|
|Память|Управляется автоматически|Нужен ручной retired-list + reclaim|Нужен ручной retired-list + epoch tracking|
|Where used|Быстрые прототипы, некритичный по латентности код|Высокопроизводительные библиотеки (folly, libcds)|Rust (crossbeam-epoch), Linux RCU|

**Главный практический минус:** каждое разыменование/копирование `shared_ptr` — это atomic increment/decrement refcount, причём **на control block**, который у всех узлов разный (это отдельная кэш-линия на каждый узел, ещё и с contention, если много потоков одновременно держат ссылки на один и тот же узел). В hot-path lock-free структуре (например, MPMC-очередь с миллионами операций в секунду) это может оказаться на порядок медленнее, чем hazard pointers с точечным overhead.

## Когда что выбирать на практике

- **`atomic<shared_ptr<T>>`**: прототипирование, некритичный по производительности код, места, где корректность важнее наносекунд, или когда `shared_ptr` и так уже используется в кодовой базе (нет смысла городить hazard pointers ради экономии, которая не измерялась).
- **Hazard pointers**: производственный high-throughput lock-free код, где профилирование показало, что refcounting — bottleneck. Даёт bounded memory и точный контроль.
- **EBR**: похожий сценарий, но когда можно допустить чуть менее строгий bound на память ради более простой и часто более быстрой реализации на массовых операциях (это то, что использует Rust-экосистема через `crossbeam-epoch` — прямая параллель с вашим интересом к Rust).

**Для собеседования** ключевая фраза, которую стоит произнести: _"`atomic<shared_ptr>` решает ABA через reference counting вместо identity-сравнения указателя, но платит за это atomic refcount overhead на каждый доступ и не гарантирует lock-free (нужно проверять `is_lock_free()`), поэтому в hot-path структурах предпочтительнее hazard pointers или epoch-based reclamation"_ — это показывает, что вы понимаете не просто "какое решение есть", а trade-off между ними.

## Блок 3 — Архитектура lock-free чат-сервера (1 неделя)

**Ключевые решения для чата конкретно:**

- [ ] **Модель потоков**: thread-per-connection vs event loop (epoll/io_uring) + пул воркеров — lock-free структуры чаще всего нужны именно во второй модели, как shared-state между воркерами
- [ ] **Message queue на клиента**: SPSC от воркера к connection-writer (один producer — логика чата, один consumer — сетевой поток на отправку)
- [ ] **Broadcast**: тут MPSC/MPMC не всегда лучший выбор — часто эффективнее copy-on-write список подписчиков (RCU-style) + каждому подписчику своя SPSC-очередь, чем один общий lock-free broadcast-канал
- [ ] **Backpressure**: что делать, если consumer медленнее producer — bounded queue + drop policy vs unbounded + memory blowup
- [ ] **Reclamation проблема**: если пользователь отключается, когда безопасно освободить его структуры при lock-free доступе (hazard pointers / epoch-based / RCU)

**Практика:** собрать минимальный прототип — N потоков-писателей кладут сообщения в шину, M потоков-читателей (эмулируют коннекты) их разбирают, с метриками latency/throughput под нагрузкой.

**Источники:** статьи про архитектуру Discord/Slack backend (общие принципы, не lock-free специфика, но полезно для контекста), RCU paper (Paul McKenney), доклады про io_uring + lock-free от CppCon/Meeting C++.
