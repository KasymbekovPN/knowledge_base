### Подход 1: Hash по client ID с учётом load balancing

#### Проблема простого хеширования — "горячий шард"

Простое `hash(client_id) % N` (то, что мы использовали в `spsc_writer_demo.cpp` через `fd % num_workers`) гарантирует **детерминированность** (один клиент всегда попадает к одному воркеру — что нужно для SPSC-корректности), но не гарантирует **равномерность нагрузки**. Если несколько активных клиентов случайно захешировались на один воркер — этот воркер станет bottleneck'ом, пока остальные простаивают:

### Разбор — почему хеша самого по себе недостаточно

Хеш `client_id % N` детерминирован (важно для SPSC-корректности, как разбирали в `spsc_writer_demo.cpp`), но **статичен** — он не знает и не может знать, кто из клиентов окажется активным болтуном, а кто будет молчать сутками. Реальное распределение активности в чате почти никогда не равномерно (Zipf-подобное — небольшое число очень активных пользователей/групповых чатов создают основную нагрузку).

**Варианты "с учётом load balancing", о которых шла речь:**

1. **Периодический ребаланс** — метрики нагрузки на каждый воркер (очередь глубины, задержка обработки) собираются и сравниваются; "тяжёлых" клиентов явно **переносят** на менее загруженный воркер. Цена: миграция клиента требует аккуратной синхронизации — старый воркер должен доработать все in-flight сообщения этого клиента, прежде чем новый начнёт принимать (иначе нарушится порядок доставки — тот самый SPSC-контракт).
2. **Consistent hashing с virtual nodes** — вместо `hash % N` каждому воркеру назначается несколько точек на "кольце" хешей; при перегрузке одного воркера можно добавить ему меньше virtual nodes (меньше клиентов в среднем достанется), не трогая остальных — типичный приём из систем вроде Cassandra/DynamoDB, но здесь применяется не к данным, а к маршрутизации клиентов.
3. **Взвешенный хеш** (weighted rendezvous hashing) — воркеры с большей текущей нагрузкой получают меньший "вес" в хеш-функции, снижая вероятность назначения им новых клиентов, без необходимости мигрировать уже подключённых.

Все три варианта **сохраняют** ключевое свойство — детерминированность на клиента (SPSC остаётся корректным), но платят сложностью учёта метрик и (для первого варианта) миграции состояния.
