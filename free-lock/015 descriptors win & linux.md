
# Дескрипторы: Linux (fd) vs Windows (HANDLE)

## Linux — file descriptor (fd)

**Что это:** маленькое неотрицательное целое число (`int`), индекс в **таблице открытых файлов конкретного процесса**. Каждая запись в этой таблице ссылается на **open file description** — структуру в ядре, которая хранит текущую позицию чтения/записи, флаги доступа и указатель на реальный inode/сокет/пайп.

```
Процесс                      Ядро
┌─────────────────┐         ┌──────────────────────┐
│ fd table         │            │ open file descriptions│
│  0 → stdin       │────────▶│ [терминал, offset=0]  │
│  1 → stdout      │────────▶│ [терминал, offset=0]  │
│  2 → stderr      │────────▶│ [терминал, offset=0]  │
│  3 → listen_fd   │────────▶│ [сокет, LISTEN]       │
│  4 → client_fd   │────────▶│ [сокет, ESTABLISHED]  │
└─────────────────┘         └──────────────────────┘
```

**Философия "всё — файл"**: сокеты, обычные файлы, пайпы, устройства, даже директории (для некоторых операций) — все представлены одним и тем же типом `int` и одними и теми же системными вызовами: `read()`, `write()`, `close()`. Именно поэтому в нашем portable-коде на Linux не пришлось разделять `socket_read`/`read` — можно было бы использовать `read()` напрямую (хотя `recv()`/`send()` мы выбрали ради совместимости с Windows, где это не так — см. ниже).

**Числа переиспользуются агрессивно.** Ядро всегда выдаёт **наименьший свободный** номер — именно поэтому в отладке `io_uring_server` мы видели `fd=37` как совершенно легитимное значение: к тому моменту теста было открыто и закрыто достаточно сокетов, что счётчик дошёл до этого числа. Это прямая параллель ABA problem: если вы держите "старый" fd после `close()`, а потом кто-то другой открывает новый файл — велика вероятность получить **тот же номер fd**, что и было закрыто. Отсюда правило: никогда не используйте fd после `close()`, даже если "ещё не переиспользовали" — гарантий на это нет.

**`0`, `1`, `2` зарезервированы** по конвенции: stdin, stdout, stderr — но это именно конвенция, не аппаратное ограничение.

## Windows — HANDLE

**Что это:** непрозрачный (`opaque`) идентификатор, технически `void*` (тип `HANDLE`), значение которого **не является индексом** в предсказуемом смысле — оно генерируется диспетчером объектов ядра (Object Manager) и не гарантированно маленькое или последовательное.

```c
typedef void* HANDLE;
```

**HANDLE унифицирован для большинства объектов ядра** — файлы, потоки, процессы, мьютексы, события, семафоры — все представлены `HANDLE`, и закрываются одной и той же функцией:

```c
CloseHandle(h);
```

## Ключевое различие — `SOCKET` НЕ является `HANDLE` исторически

Здесь кроется практическая ловушка, с которой мы уже столкнулись в portable-коде. Winsock (сокеты Windows) исторически вырос из портирования **Berkeley Sockets API** (BSD/Unix происхождение), а не из родного Windows I/O — поэтому у него отдельный тип:

```c
typedef UINT_PTR SOCKET;
```

И отдельная функция закрытия:

```c
closesocket(s);   // НЕ CloseHandle(s)!
```

**Почему это важно на практике:** `CloseHandle()` на `SOCKET` в общем случае **не будет работать корректно** (хотя технически `SOCKET` под капотом современных Windows тоже является объектом ядра и в _некоторых_ случаях `CloseHandle` формально сработает — но это не документированное, не гарантированное поведение, полагаться на него нельзя). Именно поэтому в нашем `thread_per_connection_portable.cpp` мы явно развели:

```cpp
#ifdef _WIN32
    inline void close_socket(socket_t s) { closesocket(s); }
#else
    inline void close_socket(socket_t s) { close(s); }
#endif
```

## Сравнительная таблица

|                            | Linux fd                                              | Windows HANDLE                                                                  | Windows SOCKET                                                                                                     |
| -------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Тип                        | `int`                                                 | `void*` (opaque)                                                                | `UINT_PTR`                                                                                                         |
| Значение "нет дескриптора" | `-1`                                                  | `INVALID_HANDLE_VALUE` (не `nullptr`!)                                          | `INVALID_SOCKET` (тоже не 0/-1, а `~0`)                                                                            |
| Закрытие                   | `close()`                                             | `CloseHandle()`                                                                 | `closesocket()`                                                                                                    |
| Универсальность            | Один тип для файлов/сокетов/пайпов/устройств          | Один тип для большинства объектов ядра (файлы, потоки, события...)              | Отдельный тип, не взаимозаменяем с HANDLE напрямую                                                                 |
| Числовые значения          | Маленькие, последовательные, активно переиспользуются | Непредсказуемые, генерируются диспетчером объектов                              | Аналогично HANDLE — непрозрачное значение                                                                          |
| read/write                 | `read()`/`write()` работают universally               | `ReadFile()`/`WriteFile()` — для файлов/пайпов/некоторых сокетов (с overlapped) | `recv()`/`send()` — стандартный способ, `ReadFile`/`WriteFile` работают только для overlapped-сокетов с оговорками |

## Почему в нашем коде `INVALID_SOCK` определён по-разному

```cpp
#ifdef _WIN32
    constexpr socket_t INVALID_SOCK = INVALID_SOCKET;  // определено как (SOCKET)(~0)
#else
    constexpr socket_t INVALID_SOCK = -1;               // обычное -1 для int
#endif
```

Это прямое следствие разницы типов: на Linux `int` естественно принимает `-1` как "невалидное" значение (сравнение `fd < 0` — стандартная проверка ошибки во всех POSIX API). На Windows `SOCKET` — беззнаковый (`UINT_PTR`), поэтому `-1` там на самом деле означает "все биты установлены" (`0xFFFFFFFFFFFFFFFF` на 64-бит), что и есть `INVALID_SOCKET` — но обозначается отдельной именованной константой, а не литералом `-1`, потому что прямое сравнение `if (sock < 0)` на беззнаковом типе **никогда не сработает** (беззнаковое число не может быть отрицательным) — ещё одна причина, по которой в нашем коде везде `== INVALID_SOCK`, а не `< 0`.

## Наследование дескрипторов между процессами

- **Linux**: `fork()` копирует **всю** таблицу fd в дочерний процесс (те же номера, те же open file descriptions). `exec*()` по умолчанию сохраняет их, если явно не выставлен флаг `FD_CLOEXEC` (`close-on-exec`).
- **Windows**: `HANDLE` наследуется в дочерний процесс, только если явно создан как **inheritable** (флаг `bInheritHandle` в `SECURITY_ATTRIBUTES` при создании, или `SetHandleInformation` позже) — и только если `CreateProcess()` вызван с `bInheritHandles = TRUE`. По умолчанию — **не** наследуется, в отличие от Linux, где по умолчанию наследуется (обратная default-политика между платформами).

## Практический вывод для кросс-платформенного кода

Именно из-за этой связки различий (`int` vs `void*`/`UINT_PTR`, `close()` vs `closesocket()`/`CloseHandle()`, `-1` vs именованные константы) единственный практичный подход — то, что мы и сделали: **типизировать через `using socket_t = ...`** и спрятать все различия за именованными функциями-обёртками (`close_socket()`, `INVALID_SOCK`), а не пытаться писать один буквальный код, работающий на битовом уровне одинаково на обеих платформах — сами дескрипторы устроены слишком по-разному для этого.
