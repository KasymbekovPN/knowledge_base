
# IPC: теория и виды

## Что такое IPC

**IPC (Inter-Process Communication)** — набор механизмов, позволяющих независимым процессам (каждый со своим изолированным виртуальным адресным пространством) обмениваться данными и синхронизировать своё выполнение. Изоляция адресных пространств — фундаментальное свойство современных ОС (защита памяти, security), но она же делает прямой обмен данными между процессами невозможным без явного посредничества ядра или специально организованной общей области памяти.

## Классификация по способу передачи данных

**Механизмы с копированием через ядро** — данные физически проходят через буфер в пространстве ядра при каждой операции:

- **Pipe / FIFO** — однонаправленный байтовый поток. Pipe работает только между родственными процессами (имеющими общего предка через `fork()`), FIFO (named pipe) — между любыми, потому что у него есть путь в файловой системе, по которому его находят.
- **Unix domain socket** — байтовый поток или датаграммы, обмен происходит локально на одной машине без сетевого стека. В отличие от pipe, полнодуплексный, и, что важно, единственный из перечисленных здесь механизмов, способный передавать **файловые дескрипторы** между процессами.
- **Message queue** — дискретные, типизированные сообщения с приоритетами, а не непрерывный поток байт. Получатель забирает сообщения целиком, а не произвольными кусками, как из pipe.
- **Signals** — асинхронное уведомление о событии, без содержательных данных (кроме небольшого числа через `sigqueue`). Ближе к прерыванию, чем к каналу передачи данных.

**Механизм без копирования** — данные не проходят через ядро на каждую операцию:

- **Shared memory** — несколько процессов отображают на свои виртуальные адресные пространства **один и тот же** физический участок памяти. Чтение/запись — обычные операции с памятью, без syscall. Это даёт максимальную пропускную способность и минимальную задержку среди всех IPC-механизмов, но ценой полного отсутствия встроенной синхронизации — ядро не знает и не следит за тем, что происходит внутри разделяемого региона, вся координация (кто, когда и что может читать/писать) — целиком ответственность самих процессов.

**Отдельная категория — примитивы синхронизации без передачи данных:**

- **Semaphores** (счётчики в ядре) и другие подобные объекты синхронизации нужны именно там, где выбран IPC без копирования (shared memory) — потому что сам механизм передачи данных не предоставляет никакой упорядоченности или взаимоисключения самостоятельно.

## Ключевой компромисс между двумя семействами

Механизмы с копированием через ядро **платят производительностью за встроенную безопасность**: каждая операция — системный вызов, данные буферизуются и упорядочиваются самим ядром, что автоматически даёт атомарность на уровне сообщения/операции и естественную точку синхронизации (получатель блокируется, пока не появятся данные).

Shared memory — противоположный полюс: **максимальная производительность за счёт полного отсутствия гарантий** со стороны ОС. Никакой автоматической атомарности, никакого встроенного упорядочивания, никакой защиты от одновременной записи двух процессов в одно и то же место — всё это нужно выстраивать самостоятельно, что естественным образом подводит к тем же вопросам, что разбирались для потоков внутри одного процесса (атомарность операций, memory ordering, синхронизация доступа), только применительно к границе между процессами, а не между потоками.

## Почему выбор механизма — не только про скорость

Помимо производительности, механизмы различаются по:

- **Требованию родства процессов** — некоторые работают только между процессом-родителем и его потомками (появившимися через `fork()`), другие — между любыми независимыми процессами, если у них есть общий способ "договориться", по какому имени/пути найти друг друга.
- **Направленности** — однонаправленные (данные текут только в одну сторону) против дуплексных.
- **Структурированности данных** — непрерывный неструктурированный поток байт против дискретных сообщений с чёткими границами.
- **Встроенной синхронизации** — есть ли естественная точка "заблокироваться и подождать данные" в самом механизме, или это нужно организовывать отдельно.

Выбор конкретного механизма для конкретной задачи — это балансирование между тем, насколько критична производительность, насколько сложна логика синхронизации, которую готовы взять на себя, и насколько структурированы и часты передаваемые данные.
