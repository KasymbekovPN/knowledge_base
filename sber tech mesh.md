Вопрос:
Расскажите, как Вы применяете RAII и семантику перемещения (move semantics) для управления ресурсами в горячих путях, какие типы умных указателей предпочитаете использовать и в каких случаях, а также как обеспечиваете correctness времени жизни объектов и строгую const-correctness в API? Приведите пару примеров из практики.

Ответ:

В архитектуре движка исполнения сценариев (пул потоков, обрабатывающий сотни параллельных сценариев) я использовал `unique_ptr` для владения контекстом выполнения каждого сценария — контекст создаётся один раз при старте сценария и передаётся через `std::move` между этапами обработки, без копирования тяжёлых внутренних структур на каждом шаге.

В модуле автоматической генерации и горячей замены (hot-swap) кода провайдеров опроса - там, где несколько потоков могли одновременно обращаться к активной версии провайдера, пока новая версия компилировалась и подгружалась - использовал `shared_ptr` осознанно, именно потому что там разделяемое владение с неопределённым моментом освобождения старой версии было необходимо (нельзя было гарантировать, что конкретный поток закончил использовать старый провайдер к моменту переключения), а RAII гарантировал, что старая версия корректно уничтожится сразу после того, как последний поток закончит с ней работу.

Const-correctness: придерживаюсь принципа - если метод не должен модифицировать состояние объекта - он обязан быть `const`, и это распространяется на все параметры, передаваемые по ссылке, если они не должны быть изменены вызываемым кодом. Это не просто стилистика - const-correctness в публичном API документирует контракт для других разработчиков команды и ловит ошибки на этапе компиляции, а не в рантайме под нагрузкой.


RAII в hot-path: время жизни ресурса привязано к времени жизни объекта — деструктор гарантированно освобождает его при любом пути выхода, включая исключения, что критично для консистентности под нагрузкой.

**Умные указатели:** `unique_ptr` — выбор по умолчанию для единоличного владения в hot-path (нулевой overhead vs сырой указатель). `shared_ptr` — только при реальном разделяемом владении с неопределённым временем жизни, осознанно избегаю в самых горячих участках из-за atomic reference counting под нагрузкой. Сырые указатели/ссылки — для невладеющего наблюдения, когда время жизни объекта гарантированно шире.

**Move-семантика:** использую для передачи объектов между этапами конвейера обработки без копирования — например, буферов между стадиями обработки в разных потоках.

**Const-correctness:** если метод/параметр не должен модифицировать состояние — обязателен `const`; это часть контракта API, а не стилистика, и ловит ошибки на этапе компиляции.

**Примеры:** в движке исполнения сценариев использовал `unique_ptr` для контекста выполнения, передаваемого через `std::move` между этапами (парсинг → выполнение → уведомление) без копирования. В модуле hot-swap кода провайдеров опроса использовал `shared_ptr` осознанно — там несколько потоков могли одновременно работать со старой версией провайдера, пока подгружалась новая, и разделяемое владение с неопределённым моментом освобождения было необходимо.
