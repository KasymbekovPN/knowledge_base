
## Суть задачи

Дано k отсортированных связных списков (linked lists). Нужно слить их в один отсортированный список.

Наивно: сложить все элементы в один массив, отсортировать — `O(N log N)`, где N — суммарное число элементов во всех списках. Но раз каждый список уже отсортирован, это расточительно — мы выбрасываем уже готовую структуру.

## Идея — k-way merge через heap

Заводим min-heap размера k, в который кладём **по одному** "текущему" элементу от каждого списка (голову каждого списка). На каждом шаге:

1. Достаём минимум из heap — это следующий элемент результата.
2. Смотрим, из какого списка он был — берём **следующий** элемент этого же списка и кладём его в heap вместо извлечённого.
3. Повторяем, пока heap не опустеет.

Ключевое отличие от top-K из прошлого разбора: там heap ограничивал размер результата (K элементов на выходе), здесь heap ограничивает **число активных "источников"** (k списков), а на выходе — все N элементов, просто в правильном порядке.

Сложность: `O(N log k)` — каждый из N элементов проходит через heap размера k один раз.

```cpp
#include <format>
#include <iostream>
#include <queue>
#include <string>
#include <vector>

namespace {

    struct Node {
        int val;
        Node* next;
        explicit Node(const int x) : val(x), next(nullptr) {}
    };

    Node* create_nodes(std::vector<int>& nums) {
        if (nums.empty()) return nullptr;

        const auto value = nums.front();
        nums.erase(nums.begin(), nums.begin() + 1);

        const auto node = new Node(value);
        node->next = create_nodes(nums);

        return node;
    }

    void display_lists(const Node* head) {
        if (head == nullptr) {
            std::cout << "NULL\n";
            return;
        }

        std::cout << std::format("{} ", head->val);
        display_lists(head->next);
    }

    Node* merge_k_lists(const std::vector<Node*>& lists) {
        auto cmp = [](const Node* a, const Node* b) -> bool { return a->val > b->val; };
        std::priority_queue<Node*, std::vector<Node*>, decltype(cmp)> heap(cmp);

        for (const auto n: lists) {
            if (n) heap.push(n);
        }

        Node dummy{0};
        Node* tail = &dummy;

        while (!heap.empty()) {
            Node* curr = heap.top();
            heap.pop();

            tail->next = curr;
            tail = tail->next;

            if (curr->next) heap.push(curr->next);
        }

        return dummy.next;
    }

}

int main() {
    std::vector<int> nums0 = {1, 2, 3};
    std::vector<int> nums1 = {3, 4, 5};
    std::vector<int> nums2 = {5, 6, 7};

    const auto n0{create_nodes(nums0)};
    const auto n1{create_nodes(nums1)};
    const auto n2{create_nodes(nums2)};

    std::cout << "N0\n";
    display_lists(n0);
    std::cout << "N1\n";
    display_lists(n1);
    std::cout << "N2\n";
    display_lists(n2);

    const std::vector<Node*> nodes{n0, n1, n2};
    const auto result{merge_k_lists(nodes)};
    display_lists(result);
}

```

Важный нюанс, который любят спросить на собеседовании: почему в heap кладём **указатели на узлы**, а не голые значения? Потому что нам нужно после извлечения минимума знать, откуда он пришёл, чтобы подставить следующий элемент именно из того же источника. Если бы хранили только значения — потеряли бы эту связь.

## Параллель с поисковым рантаймом

Это прямая модель слияния **posting-листов** инвертированного индекса или результатов с разных шардов:

**Сценарий 1 — слияние posting-листов одного термина/запроса.**  
В инвертированном индексе posting-лист для каждого термина отсортирован (обычно по doc_id, для быстрого пересечения через intersection/skip-lists). Если запрос — это OR нескольких термов, нужно слить их posting-листы в единый поток, отсортированный по doc_id, — это ровно k-way merge, k = число термов.

**Сценарий 2 — слияние результатов с шардов (более вероятный контекст для вашей вакансии).**  
Каждый шард уже вернул свой **локальный top-K**, отсортированный по релевантности (используя heap из прошлого разбора). Coordinator получает k отсортированных списков (по одному на шард) и должен слить их в глобальный top-K — здесь применяется ровно эта структура, с одним отличием: не нужно проходить весь список целиком, достаточно вытащить top-K глобально, то есть merge останавливается после K извлечений, а не продолжается до конца всех списков.

Это стоит явно проговорить на собеседовании, если зададут именно system-design-вариацию: "чистый" LC23 идёт до конца всех списков, а в реальном поисковом coordinator'е вы обычно **комбинируете** merge с top-K cutoff — то есть после того, как извлекли K элементов, дальше сливать не нужно, можно остановиться (early termination), что даёт `O(K log k)` вместо `O(N log k)`, где N — суммарный размер всех локальных результатов.

## Вероятные усложнения на интервью

- **"А что если один из шардов ответил с задержкой/отказал?"** — это explicit тема "graceful degradation" из вакансии: нужно предусмотреть таймаут на shard-запрос и продолжить merge с оставшимися k-1 источниками, явно пометив ответ как частичный (partial result).
- **"А как это распараллелить?"** — можно заметить, что сам merge — принципиально последовательная операция (heap — общее разделяемое состояние), но подготовка данных (получение списков от шардов) полностью параллельна; тут может всплыть вопрос про lock-free структуру для сбора ответов от шардов, если делать это без блокировок.
- **"Что если списки очень большие и не помещаются в память?"** — потоковая версия (то же самое, но с итераторами/generators вместо реальных списков в памяти) — актуально для случая, когда posting-лист хранится на диске.
