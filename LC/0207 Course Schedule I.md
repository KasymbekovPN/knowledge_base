
## Суть задачи

Дано `numCourses` курсов (пронумерованы 0..n-1) и список пар `[a, b]`, означающих "чтобы взять курс `a`, нужно сначала взять курс `b`" (b — пререквизит a). Нужно определить, **возможно ли** пройти все курсы — то есть нет ли **цикла** в графе зависимостей (если A требует B, а B прямо или косвенно требует A — пройти оба невозможно ни в каком порядке).

Это классическая задача **обнаружения цикла в ориентированном графе**, эквивалентная вопросу "существует ли топологическая сортировка для этого графа".


```cpp
#include <iostream>
#include <format>
#include <vector>
#include <queue>

namespace bfs {
    static bool can_finish(const int num_courses, const std::vector<std::vector<int>>& prerequisites) {
        std::vector<std::vector<int>> graph(num_courses);
        std::vector<int> in_degree(num_courses, 0);

        for (auto& p: prerequisites) {
            const int course = p[0];
            const int prereq = p[1];
            graph[prereq].push_back(course);
            in_degree[course]++;
        }

        std::queue<int> q;
        for (int i{}; i < num_courses; ++i) {
            if (in_degree[i] == 0) q.push(i);
        }

        int processed{};
        while (!q.empty()) {
            const int cur{q.front()};
            q.pop();
            processed++;

            for (int next: graph[cur]) {
                if (--in_degree[next] == 0) q.push(next);
            }
        }

        return processed == num_courses;
    }

    static void run_test(const int num_courses,
                         const std::vector<std::vector<int>>& prerequisites,
                         const bool expected) {
        const bool result{can_finish(num_courses, prerequisites) == expected};
        std::cout << std::format("num_courses -> {}, expected: {}, result: {}\n",
            num_courses,
            expected == true ? "true" : "false",
            result ? "OK" : "FAIL");
    }

    static void tests() {
        // Пример 1: numCourses=2, prerequisites=[[1,0]]
        // Чтобы взять курс 1, нужен курс 0. Цикла нет -> можно пройти все.
        run_test(2, {{1, 0}}, true);

        // Пример 2: numCourses=2, prerequisites=[[1,0],[0,1]]
        // Курс 1 требует 0, курс 0 требует 1 -> цикл -> невозможно.
        run_test(2, {{1, 0}, {0, 1}}, false);

        // Пример 3: numCourses=4, prerequisites=[[1,0],[2,1],[3,2]]
        // Линейная цепочка 0->1->2->3, цикла нет.
        run_test(4, {{1, 0}, {2, 1}, {3, 2}}, true);

        // Пример 4: numCourses=3, prerequisites=[[0,1],[1,2],[2,0]]
        // Цикл 0->1->2->0.
        run_test(3, {{0, 1}, {1, 2}, {2, 0}}, false);

        // Пример 5: numCourses=3, prerequisites={} — нет зависимостей вообще
        run_test(3, {}, true);
    }

}

namespace dfs {
    static constexpr int STATE_UNVISITED{0};
    static constexpr int STATE_VISITING{1};
    static constexpr int STATE_VISITED{2};

    static bool dfs(const int node, const std::vector<std::vector<int>>& graph, std::vector<int>& state) {
        if (state[node] == STATE_VISITING) return false; // visiting -> нашли цикл
        if (state[node] == STATE_VISITED) return true; // visited -> уже проверено, цикла нет

        state[node] = STATE_VISITING; // помечаем "сейчас обрабатываем"
        for (const auto& next: graph[node]) {
            if (!dfs(next, graph, state)) return false;
        }

        state[node] = STATE_VISITED; // полностью обработан

        return true;
    }

    static bool can_finish(const int num_courses, const std::vector<std::vector<int>>& prerequisites) {
        std::vector<std::vector<int>> graph(num_courses);
        for (auto& p: prerequisites) {
            graph[p[0]].push_back(p[1]); // graph[a] = список пререквизитов курса a
        }

        std::vector<int> state(num_courses, 0);

        for (int i{}; i < num_courses; ++i) {
            if (!dfs(i, graph, state)) return false;
        }

        return true;
    }

    static void run_test(const int num_courses,
                         const std::vector<std::vector<int>>& prerequisites,
                         const bool expected) {
        const bool result{can_finish(num_courses, prerequisites) == expected};
        std::cout << std::format("num_courses -> {}, expected: {}, result: {}\n",
            num_courses,
            expected == true ? "true" : "false",
            result ? "OK" : "FAIL");
    }

    static void tests() {
        // Пример 1: numCourses=2, prerequisites=[[1,0]]
        // Курс 1 требует курс 0. Цикла нет.
        run_test(2, {{1, 0}}, true);

        // Пример 2: numCourses=2, prerequisites=[[1,0],[0,1]]
        // Взаимный цикл 1<->0.
        run_test(2, {{1, 0}, {0, 1}}, false);

        // Пример 3: numCourses=4, prerequisites=[[1,0],[2,1],[3,2]]
        // Линейная цепочка зависимостей, цикла нет.
        run_test(4, {{1, 0}, {2, 1}, {3, 2}}, true);

        // Пример 4: numCourses=3, prerequisites=[[0,1],[1,2],[2,0]]
        // Цикл 0->1->2->0.
        run_test(3, {{0, 1}, {1, 2}, {2, 0}}, false);

        // Пример 5: без зависимостей вообще
        run_test(3, {}, true);

        // Пример 6: общий пререквизит у нескольких курсов (не цикл, но заходит в один узел дважды)
        // Курсы 1 и 2 оба требуют курс 0. DFS должен корректно пройти через "visited" узел 0
        // без ложного срабатывания на цикл.
        run_test(3, {{1, 0}, {2, 0}}, true);
    }

}


int main() {
    // bfs::tests();
    dfs::tests();

    return 0;
}

```

## Идея — два стандартных подхода

### Подход 1: BFS через Kahn's algorithm (топологическая сортировка через in-degree)

Идея: курс можно "взять" только тогда, когда все его пререквизиты уже взяты. Считаем **in-degree** каждого узла (сколько пререквизитов у курса), кладём в очередь все курсы с `in-degree == 0` (без зависимостей — с них можно начинать), затем итеративно "берём" курс, уменьшаем in-degree всех, кто от него зависел, и если чей-то in-degree дошёл до 0 — добавляем в очередь. Если в итоге обработали **все** n курсов — цикла нет; если часть курсов осталась необработанной — они образуют цикл (их in-degree никогда не дойдёт до 0, потому что зависят друг от друга по кругу).

### Подход 2: DFS с трёхцветной разметкой (более естественно обобщается на LC210)

Идея: обходим граф DFS, помечая каждый узел одним из трёх состояний: `unvisited` (белый), `visiting` (серый — сейчас в текущем стеке рекурсии), `visited` (чёрный — полностью обработан, цикла через него нет). Если во время DFS мы встречаем узел, который уже **`visiting`** (серый) — значит, мы вернулись в узел, который сами же сейчас обрабатываем в этой же ветке рекурсии — это и есть цикл (back edge в терминологии обхода графов).

**Почему нужны именно три состояния, а не просто `visited: bool`.** Если бы был только один флаг "посещён/не посещён", вы бы не отличили "этот узел уже полностью проверен, цикла нет" от "этот узел сейчас в процессе обработки в текущей ветке рекурсии" — а различие критично: попасть повторно в узел, который **уже завершён** (чёрный) — нормально (это просто общий пререквизит для нескольких курсов, не цикл), а попасть в узел, который **ещё обрабатывается** (серый) — это и есть цикл.

Сложность обоих подходов: `O(V + E)`, где V — число курсов, E — число пар зависимостей — каждый узел и каждое ребро обрабатывается константное число раз.

## Какой подход выбрать на собеседовании

BFS (Kahn's) обычно **предпочтительнее** для LC207/210 по двум причинам:

1. **Не рекурсивный** — не рискует переполнением стека на графах с длинной цепочкой зависимостей (тысячи курсов подряд друг за другом дали бы рекурсию глубиной в тысячи вызовов). Это тот же класс проблемы, что упоминался раньше про `unique_ptr`-цепочки — глубокая рекурсия на реальных данных может реально стрельнуть.
2. **Естественно даёт сам порядок** топологической сортировки (порядок, в котором курсы вынимались из очереди) — что нужно для LC210 (Course Schedule II, где просят вернуть сам порядок, а не только "возможно/невозможно"). DFS-версия тоже может это дать (через порядок завершения узлов, в обратном порядке), но менее очевидно и легче ошибиться в деталях.

## Параллель с вакансией

Это прямая модель **планировщика стадий выполнения запроса**, о котором явно сказано в описании вакансии. Поисковый запрос часто раскладывается на граф операций (например: "получить posting-листы" → "пересечь/объединить" → "посчитать score" → "отсортировать top-K" → "применить фильтры") — некоторые стадии не могут начаться, пока не завершились их зависимости. Это ровно DAG, и:

- **Обнаружение цикла (LC207)** — прямая параллель с **валидацией плана запроса**: если из-за ошибки в построении query plan образовалась циклическая зависимость между стадиями — это баг, который нужно поймать **до** попытки исполнения, иначе рантайм зависнет в дедлоке или бесконечном ожидании.
- **Сам топологический порядок (LC210)** — это буквально **порядок исполнения стадий**: какие стадии можно запускать параллельно (все с одинаковым "уровнем" в топологической сортировке — то есть все, чьи зависимости уже удовлетворены одновременно), а какие обязаны ждать.

## Вероятные усложнения на интервью

- **"А что если граф огромный (миллионы узлов/рёбер) и не помещается в память одного хоста?"** — уводит к распределённому построению DAG и, возможно, распределённой топологической сортировке (стадии обрабатываются на разных узлах, синхронизация через message passing).
- **"Как распараллелить исполнение самого DAG, а не просто найти порядок?"** — естественное развитие: BFS-подход (Kahn's) **сам по себе** уже даёт параллелизм "бесплатно" — все узлы с текущим `in-degree == 0` можно исполнять **одновременно** (это ровно то, что происходит в реальных task schedulers — например, в build-системах вроде Bazel/Ninja, где независимые таргеты собираются параллельно). Стоит явно это назвать — DAG-scheduler для вашей вакансии, скорее всего, устроен именно так.
- **"Что если зависимость не жёсткая (must), а soft (желательная, но не блокирующая)?"** — более продвинутый вариант планировщика, где приходится взвешивать trade-off latency/completeness (снова explicit тема вакансии) — это уже не чистый DAG-scheduling, а что-то ближе к priority-based scheduling с deadline.
