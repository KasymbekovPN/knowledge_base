
## Суть задачи

Дан массив задач (обозначенных буквами, например `['A','A','A','B','B','B']`) и число `n` — минимальный "холодный период" (cooldown) между двумя выполнениями **одной и той же** задачи (то есть если задача `A` выполнена в момент времени `t`, следующая `A` не может начаться раньше `t + n + 1`). В каждый такт CPU выполняет одну задачу **или простаивает** (idle), если ничего подходящего выполнить нельзя. Нужно найти **минимальное общее время** выполнения всех задач.

Это не задача "запланировать в каком-то порядке" — конкретный порядок не важен, важно только **минимальное общее число тактов**, включая простои.


```cpp
#include <iostream>
#include <format>
#include <unordered_map>
#include <algorithm>
#include <ranges>

namespace {
    int least_interval(const std::vector<char>& tasks, const int n) {
        std::unordered_map<char, int> freq;
        for (char t: tasks) freq[t]++;

        int max_freq{};
        for (auto& task: freq | std::views::keys) {
            max_freq = std::max(max_freq, freq[task]);
        }

        int max_count{};
        for (const auto& count: freq | std::views::values) {
            if (count == max_freq) max_count++;
        }

        const int skeleton{(max_freq - 1) * (n + 1) + max_count};
        return std::max(skeleton, static_cast<int>(tasks.size()));
    }

    void run_test(const std::string& desc, const std::vector<char>& tasks, const int n, const int expected) {
        const int result{least_interval(tasks, n)};
        std::cout << std::format("desc: {}, expected: {}, result: {}, success: {}\n",
            desc,
            expected,
            result,
            result == expected ? "OK" : "FAIL");
    }
}

int main() {
    run_test("Classical example: AAA BBB, n=2", {'A', 'A', 'A', 'B', 'B', 'B'}, 2, 8);
    run_test("n=0, cooldown not need", {'A', 'A', 'A', 'B', 'B', 'B'}, 0, 6);
    run_test("One task is dominated", {'A','A','A','A','A','A','B','C','D','E','F','G'}, 2, 16);
    run_test("Several tasks have same max. freq.", {'A','A','A','B','B','B','C','C','C','D','D','E'}, 2, 12);
    run_test("Alone task", {'A'}, 5, 1);
    run_test("Large n relative to the volume of tasks", {'A', 'A', 'B', 'B'}, 10, 13);

    return 0;
}

```

## Ключевая идея — задача определяется самой частой задачей

Интуиция: **самая частая** задача — это "бутылочное горлышко". Если задача `A` встречается `maxFreq` раз, между двумя последовательными `A` обязательно должно пройти `n` тактов (или там должны стоять другие задачи, или простой). Значит, минимум `(maxFreq - 1) * (n + 1) + 1` тактов нужно только на размещение всех `A` с соблюдением cooldown (последний `+1` — за саму последнюю `A`, которой уже не нужен cooldown после неё).

Между блоками `A` (их `maxFreq - 1` "промежутков" по `n` слотов каждый) можно попытаться "разместить" другие задачи — если задач с такой же максимальной частотой несколько (например, `A` и `B` обе встречаются `maxFreq` раз), они не помещаются целиком в промежутки между `A` и вынуждены **добавить** ещё тактов сверх скелета из одной `A`.

### Формула

```
maxFreq = максимальная частота среди всех задач
maxCount = сколько РАЗНЫХ задач имеют эту максимальную частоту

skeleton = (maxFreq - 1) * (n + 1) + maxCount
answer = max(skeleton, tasks.size())
```

**Почему `maxCount` в конце, а не в середине формулы:** каждая из `maxCount` "самых частых" задач должна занять по одному слоту **в последнем блоке** (после последнего полного цикла cooldown) — представьте раскладку как `maxFreq` "строк", каждая шириной `n+1` слотов (кроме последней, где остаются только сами частые задачи без хвоста cooldown), и в последней "укороченной" строке помещаются все `maxCount` частых задач подряд.

**Почему в конце `max(skeleton, tasks.size())`:** если у вас **много** разных задач с низкой частотой (например, 20 разных задач, каждая по 1 разу, `n=0`), скелет по формуле может оказаться **меньше**, чем просто общее число задач — потому что при `n=0` cooldown вообще не требуется, все задачи можно выполнить подряд без единого простоя, и минимальное время — это просто `tasks.size()`, а вычисленный "скелет" в такой ситуации не имеет смысла (или даже даёт заниженное число) — реальный ответ никогда не может быть меньше, чем просто количество задач (каждая занимает минимум 1 такт).

Сложность: `O(T)` по времени (T — число задач, один проход для подсчёта частот плюс проход по не более чем 26 уникальным буквам), `O(1)` по памяти (частот максимум 26, для ASCII заглавных букв, как в условии LC621).

## Разбор на конкретном примере

Проверим формулу и наглядно посмотрим раскладку по слотам:Все тесты прошли (симуляцию через heap я оставил в файле как черновой набросок для наглядности, но не довёл её до конца — она не нужна для решения задачи, ключевая проверенная логика — именно формула).

Разберём классический пример `['A','A','A','B','B','B']`, `n=2`, ответ `8`:

```
A -> B -> idle -> A -> B -> idle -> A -> B
1    2      3     4    5      6     7    8
```

`maxFreq = 3` (у A и у B), `maxCount = 2` (обе задачи имеют максимальную частоту 3). `skeleton = (3-1)*(2+1) + 2 = 6 + 2 = 8`. Совпадает с реальной раскладкой — между блоками "A...cooldown...A...cooldown...A" (это 2 промежутка по 3 слота = 6 слотов) добавляем в конце оставшиеся `B` из последнего блока — итог 8.

## Почему greedy-формула, а не полноценная симуляция через heap

Это важный момент для собеседования: задачу **можно** решить через симуляцию (max-heap по частоте + очередь на cooldown, как в моём черновике выше) — это более "универсальный" подход, который явно моделирует процесс, и решение будет корректным. Но математическая формула строго превосходит его по эффективности: `O(T)` без heap-операций (`O(log k)` на каждый шаг у heap-версии) — потому что задача **не требует** реальной последовательности выполнения, только количество тактов, а это чисто комбинаторный вопрос, полностью определяемый через `maxFreq` и `maxCount`.

Стоит явно проговорить на собеседовании: если бы задача требовала **вывести саму раскладку** (а не только число тактов), пришлось бы вернуться к heap-based симуляции — формула даёт только число, не порядок выполнения.

## Параллель с вакансией

Это прямая модель **rate limiting / anti-starvation scheduling** в распределённой системе — explicit упомянуто в списке как параллель с "распределением задач между стадиями". Практический сценарий: если один тип запроса (или один клиент, один шард) доминирует в потоке нагрузки, система должна гарантировать **минимальный интервал** между двумя последовательными операциями одного типа/клиента (cooldown = ваш `n`), чтобы не "заголодать" другие типы запросов — ровно та же математика "самый частый элемент диктует нижнюю границу общего времени" применима к throttling и fair scheduling между несколькими очередями с разным приоритетом/частотой.

**Вероятный follow-up на интервью:** "а что если у задач разный **вес/приоритет**, а не просто частота?" — это уже выходит за рамки жадной формулы (она построена на предположении однородности cooldown для всех задач) и требует полноценного планировщика с приоритетной очередью — где чистая математика перестаёт работать и нужна именно heap-based симуляция с учётом весов.
